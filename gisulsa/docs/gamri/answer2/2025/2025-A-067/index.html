067번 · HDFS 읽기·쓰기 성능

제26회(2025년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1) HDFS 구성 요소​

구성 요소역할
NameNode메타데이터 전담 마스터. 디렉터리 구조, 파일-블록 매핑, 블록이 어느 DataNode에 있는지를 메모리에 관리. 실제 데이터는 저장하지 않는다
DataNode실제 블록 데이터를 디스크에 저장하는 슬레이브. 주기적으로 NameNode에 하트비트와 블록 리포트를 보냄
Secondary NameNodefsimage 와 edits 로그를 주기적으로 병합(체크포인팅). NameNode의 백업/대체가 아니다
ClientNameNode에서 블록 위치를 받아 DataNode와 직접 데이터를 주고받는다

핵심은 제어 경로(메타데이터)와 데이터 경로(실제 블록)의 분리다. 데이터가 NameNode를 거치지 않으므로 NameNode가 병목이 되지 않는다.

2) 블록과 복제​

항목기본값 / 설명
블록 크기128MB(하둡 2.x 이후). 디스크 탐색 시간 대비 전송 시간 비율을 높이기 위해 크게 잡음
복제 계수(replication factor)3 (dfs.replication)
랙 인식(rack awareness) 배치1번째: 클라이언트와 같은 노드(또는 임의 노드), 2번째: 다른 랙의 노드, 3번째: 2번째와 같은 랙의 다른 노드

이 배치 정책은 내결함성(랙 하나가 통째로 죽어도 데이터 보존)과 쓰기 대역폭 절약(랙 간 전송을 1회로 제한)을 동시에 노린다.

3) 읽기(read) 경로​

1. Client → NameNode : "파일 F를 읽고 싶다"
2. NameNode → Client : 블록 목록 + 각 블록의 복제본 DataNode 주소 목록
                       (클라이언트와의 네트워크 거리 순으로 정렬해서 반환)
3. Client → 가장 가까운 DataNode 1곳 : 블록 전송 요청
4. DataNode → Client : 블록 스트리밍 (체크섬 검증)
5. 해당 노드 장애 시 → 다음으로 가까운 복제본으로 재시도

네트워크 거리(network distance) 우선순위

순위위치비용
1같은 노드(로컬 디스크)가장 저렴
2같은 랙의 다른 노드랙 내 스위치만 경유
3다른 랙의 노드랙 간 스위치 경유
4다른 데이터센터가장 비쌈

복제본이 3개 있으므로 읽기는 그중 가장 가까운 하나만 읽으면 끝난다. 복제는 읽기 입장에서 부담이 아니라 선택지(지역성 향상) 다.

4) 쓰기(write) 경로 — 복제 파이프라인​

1. Client → NameNode : 파일 생성 요청
2. NameNode → Client : 블록 ID + 복제본을 저장할 DataNode 3곳의 목록(파이프라인 순서)
3. Client → DN1 → DN2 → DN3 : 패킷을 순차 전달 (복제 파이프라인)
4. DN3 → DN2 → DN1 → Client : ACK를 역방향으로 전달
5. 모든 복제본의 ACK가 돌아와야 해당 패킷이 완료 처리됨
6. 마지막에 Client → NameNode : 파일 완료(complete) 통보

쓰기는 3개 복제본 전부에 기록되고 ACK가 돌아올 때까지 기다려야 한다. 게다가 최소 하나는 다른 랙에 있으므로 랙 간 네트워크 홉까지 포함된다.

5) 읽기/쓰기 비용 비교​

구분접촉하는 DataNode 수네트워크 경로상대 비용
읽기1개(가장 가까운 복제본)가능하면 로컬/같은 랙저렴, 빠름
쓰기3개 전부(파이프라인)랙 간 홉 포함, ACK 왕복비쌈, 느림

6) HDFS의 설계 가정​

가정설명
WORM(Write Once, Read Many)한 번 쓰고 여러 번 읽는 배치 분석 워크로드에 최적화
높은 처리량 > 낮은 지연대용량 순차 스캔에 유리, 저지연 임의 접근에는 부적합
추가(append)만 지원임의 위치 수정(random write)은 지원하지 않음
대용량 파일 지향작은 파일이 많으면 NameNode 메모리 압박(small file problem)

정답​

상세 풀이​

[1단계] 읽기 비용 산정​

클라이언트가 블록 하나를 읽을 때, NameNode는 복제본 3곳의 주소를 네트워크 거리 순으로 정렬해 돌려준다. 클라이언트는 그중 맨 앞(가장 가까운) 한 곳에서만 데이터를 받는다.

읽기 비용 = (블록 크기) × 1회 전송, 가급적 로컬 디스크 또는 같은 랙

같은 노드에 복제본이 있으면 네트워크를 거의 타지 않는 데이터 지역성(data locality) 이 실현된다. MapReduce/Spark가 "데이터가 있는 노드로 계산을 보내는" 이유가 바로 이것이다.

[2단계] 쓰기 비용 산정​

클라이언트가 블록 하나를 쓸 때는 복제 파이프라인을 따라 3곳 모두에 기록되고, 마지막 노드에서 출발한 ACK가 역방향으로 전부 돌아와야 완료된다.

Client ──패킷──→ DN1 ──패킷──→ DN2 ──패킷──→ DN3
Client ←──ACK── DN1 ←──ACK── DN2 ←──ACK── DN3
                         ↑ 하나라도 늦으면 전체가 대기
비용 요소읽기쓰기
디스크 I/O1회3회(복제본마다)
네트워크 전송최대 1홉파이프라인 3구간 + 랙 간 홉
대기 조건첫 노드 응답만모든 복제본 ACK

따라서 쓰기가 읽기보다 구조적으로 느리다.

[3단계] 보기 대조​

보기읽기에 대한 서술쓰기에 대한 서술사실 여부
①가까운 DataNode에서 가져와 빠름모든 복제본 저장을 기다려 느림둘 다 사실
②모든 DataNode에서 수집해야 느림특정 DataNode에만 기록해 빠름읽기·쓰기 설명이 완전히 뒤바뀜
③NameNode에서 읽고 씀NameNode에서 읽고 씀NameNode는 메타데이터만 다룸
④쓰기 완료 후에만 읽기 가능해 읽기가 느림—인과관계가 성립하지 않음

정답은 ①.

보기별 판정​

보기판정근거
①✅ 정답읽기는 네트워크 거리 순으로 가장 가까운 복제본 1곳만 읽고, 쓰기는 복제 파이프라인에서 모든 복제본의 ACK를 기다린다
②❌ 오답읽기는 복제본 1곳만 읽으면 되고, 쓰기는 복제본 전부에 기록한다. 서술이 정반대다
③❌ 오답NameNode는 메타데이터만 관리하며 실제 데이터는 클라이언트와 DataNode가 직접 주고받는다
④❌ 오답쓰기 완료 후 읽기가 가능한 것(WORM)은 사실이나, 그것이 읽기를 느리게 만드는 원인은 아니다

오답 이유​

  • ②가 틀린 이유: 읽기와 쓰기의 설명이 서로 뒤바뀌어 있다. 복제의 성격을 반대로 이해한 결과다.
    • "읽기는 모든 DataNode에서 수집해야 하므로 느리다" → 틀렸다. HDFS의 복제본 3개는 동일한 내용의 사본이지, 데이터를 쪼개 나눠 가진 조각이 아니다(RAID-0이나 이레이저 코딩의 스트라이핑과 혼동한 서술이다). 따라서 한 곳만 읽으면 충분하며, 오히려 복제본이 많을수록 가까운 곳을 고를 확률이 높아져 읽기에 유리하다.
    • "쓰기는 특정 DataNode에만 기록하면 되므로 빠르다" → 틀렸다. 한 곳에만 기록하면 그 노드가 죽는 순간 데이터가 사라지므로 HDFS의 내결함성 설계에 위배된다. 실제로는 복제 파이프라인으로 3곳 모두에 기록하고 ACK를 모두 받아야 한다.
  • ③이 틀린 이유: "HDFS는 데이터를 항상 NameNode에서 읽고 쓴다"는 서술은 HDFS 아키텍처의 가장 기본적인 원칙을 정면으로 위반한다. NameNode는 메타데이터(네임스페이스, 블록 위치 매핑)만 메모리에 관리하는 마스터이며, 실제 블록 데이터는 DataNode에 저장된다. 클라이언트는 NameNode에서 "블록이 어디 있는지"만 물어본 뒤 DataNode와 직접 데이터를 주고받는다. 만약 모든 데이터가 NameNode를 경유한다면 단일 노드가 클러스터 전체의 대역폭 병목이 되어 수천 노드 규모의 확장이 불가능하다. 또 "성능 차이가 없다"는 결론도 틀렸다. 복제 때문에 읽기와 쓰기의 비용은 구조적으로 다르다.
  • ④가 틀린 이유: 두 부분으로 나누어 볼 수 있다. 앞부분 "쓰기가 완료된 후에만 읽기가 가능하다"는 HDFS의 WORM(Write Once, Read Many) 모델과 관련된 사실에 가깝다. HDFS는 파일이 닫히기 전까지 마지막 블록의 가시성을 보장하지 않는다(hflush/hsync 를 쓰지 않는 한). 그러나 뒷부분 "그래서 쓰기에 비해 읽기가 느리다"는 결론이 논리적으로 성립하지 않는다. 읽기를 시작할 수 있는 시점에 관한 제약일 뿐, 일단 시작된 읽기의 속도와는 무관하기 때문이다. 오히려 실제 성능은 정반대로, 복제본 전부를 기다려야 하는 쓰기가 더 느리다. 올바른 서술은 "HDFS는 WORM 모델이라 파일이 닫힌 뒤에야 온전히 읽을 수 있으며, 복제 파이프라인 때문에 쓰기가 읽기보다 느리다"이다.
  • ①이 옳은 이유: 읽기 경로에서 NameNode가 복제본 주소를 네트워크 거리 순으로 정렬해 주고 클라이언트가 가장 가까운 한 곳만 읽는다는 점, 쓰기 경로에서 복제 파이프라인이 모든 복제본의 ACK를 기다린다는 점을 모두 정확히 서술했다.

핵심 정리​

  • NameNode = 메타데이터만, DataNode = 실제 블록. 클라이언트는 NameNode에서 블록 위치만 받고 DataNode와 직접 데이터를 주고받는다. 제어 경로와 데이터 경로의 분리가 HDFS 확장성의 핵심이다.
  • 읽기: 복제본 3개 중 네트워크 거리가 가장 가까운 1곳만 읽는다 → 복제가 오히려 지역성을 높여 읽기를 빠르게 만든다.
  • 쓰기: 복제 파이프라인으로 3곳 전부에 기록하고 ACK가 모두 돌아와야 완료된다 → 디스크 I/O 3회 + 랙 간 홉 + 왕복 대기로 읽기보다 느리다.
  • HDFS 복제본은 똑같은 내용의 사본이지 데이터를 쪼갠 조각이 아니다. 스트라이핑과 혼동하면 ②처럼 읽기·쓰기 비용을 정반대로 판단하게 된다.
  • HDFS는 WORM(한 번 쓰고 여러 번 읽는) 모델로, 대용량 순차 읽기 처리량에 최적화되어 있고 임의 위치 수정은 지원하지 않는다.

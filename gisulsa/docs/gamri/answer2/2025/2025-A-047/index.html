047번 · RESTful 서비스의 올바른 사용 예

제26회(2025년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

REST(REpresentational State Transfer)의 기본 개념​

REST는 Roy Fielding이 제안한 아키텍처 스타일로, 웹의 기존 인프라(HTTP, URI)를 그대로 활용해 자원을 다루는 방식이다. 핵심 원칙은 세 가지다.

구성 요소표현 방법예
자원(Resource)URI 로 식별/rest/api/v1/user/1
행위(Verb)HTTP 메소드 로 표현GET, POST, PUT, PATCH, DELETE
표현(Representation)JSON, XML 등 메시지 본문{"username": "홍길동"}

HTTP 메소드와 CRUD 매핑 (정확히 암기할 것)​

CRUDHTTP 메소드의미멱등성안전성
CreatePOST자원 생성(컬렉션에 추가)✗✗
ReadGET자원 조회✓✓
UpdatePUT / PATCH전체 교체 / 부분 수정✓ (PUT)✗
DeleteDELETE자원 삭제✓✗

주의: READ, UPDATE, CREATE 는 CRUD 연산의 이름일 뿐 HTTP 메소드 이름이 아니다. HTTP/1.1 표준이 정의한 메소드는 GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, TRACE, CONNECT 이다. 이 문제는 바로 이 차이를 묻는다.

RESTful URI 설계 규칙​

규칙나쁜 예좋은 예
URI에는 명사(자원) 만, 동사는 HTTP 메소드로GET /getUser/1GET /users/1
컬렉션은 복수형 권장/user/users
개별 자원은 식별자로 지정/users?id=1/users/1
계층 구조는 / 로 표현/users_orders/users/1/orders
소문자 사용, 밑줄 대신 하이픈/User_Info/user-info
URI 끝에 / 를 붙이지 않음/users/1//users/1
파일 확장자를 URI에 포함하지 않음/users/1.jsonAccept 헤더로 협상

PUT vs PATCH​

  • PUT: 자원 전체를 교체한다. 요청 본문에 없는 필드는 초기화/삭제될 수 있다. 멱등이다.
  • PATCH: 자원의 일부 필드만 수정한다. 본문에 담긴 필드만 갱신된다.

회원 정보 중 비밀번호만 바꾸는 경우라면 엄밀하게는 PATCH 가 더 적절하지만, 시험에서는 통상 수정 = PUT 또는 PATCH 로 본다. 어느 쪽이든 UPDATE 라는 메소드는 존재하지 않는다.

문제​

정답​

③

상세 풀이​

각 항목을 "① 사용한 메소드가 HTTP 표준 메소드인가 → ② 그 메소드가 의도한 행위와 맞는가 → ③ URI가 자원을 올바로 식별하는가" 순으로 점검한다.

가 — 회원 정보 조회​

READ http://localhost:8080/rest/api/v1/user/1
  • 문제점: READ 는 HTTP 메소드가 아니다. CRUD의 Read 연산 이름을 그대로 쓴 것이다.
  • URI(/user/1)로 특정 회원을 식별한 점은 올바르나, 메소드가 표준이 아니므로 RESTful하지 않다.
  • 올바른 형태: GET http://localhost:8080/rest/api/v1/user/1
  • → 부적절

나 — 회원 가입(생성)​

POST http://localhost:8080/rest/api/v1/user
{"username": "박혜자", "password": "5798", "email": "hyeja@google.com", ... }
  • POST 는 HTTP 표준 메소드이며, 새 자원을 컬렉션에 추가(Create) 하는 데 사용한다. 회원 가입은 신규 자원 생성이므로 정확하다.
  • URI가 /user 로 컬렉션을 가리킨다. 아직 식별자가 없는 신규 자원을 만드는 것이므로 /user/1 같은 개별 식별자를 쓰지 않는 것이 옳다.
  • 생성할 자원의 표현을 요청 본문(JSON) 에 담은 것도 REST 원칙에 부합한다.
  • → 적절

다 — 회원 정보 수정​

UPDATE http://localhost:8080/rest/api/v1/user/1
{"password": "9057"}
  • 문제점: UPDATE 는 HTTP 메소드가 아니다. 가와 동일한 유형의 오류다.
  • 올바른 형태: PUT http://localhost:8080/rest/api/v1/user/1 (전체 교체) 또는 PATCH .../user/1 (부분 수정). 비밀번호 하나만 바꾸므로 PATCH 가 더 정확하다.
  • → 부적절

라 — 회원 탈퇴(삭제)​

DELETE http://localhost:8080/rest/api/v1/user/1
  • DELETE 는 HTTP 표준 메소드이며 자원 삭제(Delete) 를 의미한다. 회원 탈퇴는 회원 자원의 삭제이므로 정확하다.
  • URI /user/1 이 삭제 대상 자원을 식별자로 정확히 지정하고 있다.
  • 본문 없이 URI와 메소드만으로 행위가 완전히 표현된다는 점도 REST답다.
  • → 적절

결론​

올바른 사용 예는 나, 라 이므로 정답은 ③ 이다.

항목사용 메소드HTTP 표준 메소드인가판정올바른 형태
가READ✗부적절GET /user/1
나POST✓적절그대로
다UPDATE✗부적절PUT 또는 PATCH /user/1
라DELETE✓적절그대로

보기별 판정​

보기판정근거
① 가, 라❌ 오답라는 옳지만 가의 READ 는 HTTP 메소드가 아니다.
② 가, 다❌ 오답가(READ)와 다(UPDATE) 둘 다 HTTP 메소드가 아니다. 가장 나쁜 조합.
③ 나, 라✅ 정답POST(생성)와 DELETE(삭제) 모두 HTTP 표준 메소드이며 행위와 정확히 대응한다.
④ 나, 다, 라❌ 오답나·라는 옳지만 다의 UPDATE 가 HTTP 메소드가 아니므로 포함될 수 없다.

오답 이유​

  • ① 가, 라 — 라(DELETE)는 올바른 사용 예가 맞다. 그러나 가는 조회 목적으로 READ 를 사용했는데, READ 는 CRUD 개념어일 뿐 HTTP 프로토콜이 정의한 메소드가 아니다. 서버는 이 요청을 이해할 수 없으며, 실제로는 501 Not Implemented 또는 405 Method Not Allowed 응답을 받게 된다. 조회는 반드시 GET 을 써야 하며, GET은 안전(safe)하고 멱등(idempotent)한 메소드로 캐싱도 가능하다.
  • ② 가, 다 — 네 보기 중 유일하게 올바른 항목이 하나도 없는 조합이다. READ 와 UPDATE 모두 HTTP 메소드로 존재하지 않는다. CRUD 용어(Create/Read/Update/Delete)와 HTTP 메소드(POST/GET/PUT·PATCH/DELETE)를 혼동한 전형적 오류를 두 번 반복한 셈이다.
  • ④ 나, 다, 라 — 나(POST 생성)와 라(DELETE 삭제)는 옳으므로 "많이 맞았으니 정답일 것"이라는 착시를 노린 보기다. 그러나 다가 UPDATE 라는 존재하지 않는 메소드를 사용하므로 이 조합은 성립할 수 없다. 만약 다가 PUT 또는 PATCH 였다면 ④가 정답이 되었을 것이므로, 메소드 이름 한 단어의 차이가 답을 가른다는 점을 주의해야 한다.

핵심 정리​

  • CRUD 용어 ≠ HTTP 메소드: Create→POST, Read→GET, Update→PUT/PATCH, Delete→DELETE. READ, UPDATE, CREATE 라는 HTTP 메소드는 없다.
  • REST는 자원은 URI로, 행위는 HTTP 메소드로 표현한다. URI에 getUser, deleteUser 같은 동사를 넣지 않는다.
  • 생성(POST)은 컬렉션 URI(/user) 에, 조회·수정·삭제는 개별 자원 URI(/user/1) 에 요청한다.
  • GET은 안전·멱등, PUT·DELETE는 멱등, POST는 비멱등이다.

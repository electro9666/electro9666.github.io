082번 · IPv6 헤더 필드

제26회(2025년) 정보시스템감리사 A형 — 시스템 구조

사전 지식​

IPv4 헤더 구조 (가변 길이, 최소 20바이트)​

필드크기역할
Version4비트버전(=4)
IHL(Header Length)4비트헤더 길이(가변이므로 필요)
Type of Service / DSCP8비트서비스 품질 표시
Total Length16비트헤더 + 데이터 전체 길이
Identification / Flags / Fragment Offset32비트송신 측 및 중간 라우터의 단편화 제어
Time to Live(TTL)8비트라우터 통과 시마다 1씩 감소, 0이면 폐기(무한 순환 방지)
Protocol8비트상위 프로토콜 번호(TCP=6, UDP=17 등)
Header Checksum16비트헤더 오류 검사(매 홉마다 재계산)
Source / Destination Address각 32비트송·수신 IP 주소
Options + Padding가변선택 옵션

IPv6 헤더 구조 (고정 40바이트)​

IPv6는 라우터 처리 부담을 줄이기 위해 헤더를 40바이트 고정 길이로 단순화하고, 부가 기능은 확장 헤더(Extension Header)로 분리했다.

필드크기역할IPv4 대응
Version4비트버전(=6)Version
Traffic Class8비트트래픽 우선순위·QoS 분류Type of Service
Flow Label20비트동일 플로우(스트림) 식별자 — 실시간 트래픽의 일관된 처리IPv4에 없음(신설)
Payload Length16비트기본 헤더를 제외한 페이로드 길이Total Length
Next Header8비트다음 확장 헤더 또는 상위 프로토콜Protocol
Hop Limit8비트홉마다 1 감소, 0이면 폐기TTL의 개명·대체
Source / Destination Address각 128비트송·수신 IPv6 주소Source/Destination Address

IPv4 → IPv6에서 사라진 필드​

사라진 IPv4 필드사라진 이유
IHL헤더가 40바이트 고정이라 불필요
Identification / Flags / Fragment Offset단편화를 송신 호스트만 수행(Fragment 확장 헤더로 이동)
Header ChecksumL2(이더넷 FCS)·L4(TCP/UDP 체크섬)와 중복이라 제거 → 라우터 처리 속도 향상
Options확장 헤더 체인으로 대체
TTL이름과 의미를 정확히 하여 Hop Limit 으로 대체

TTL은 원래 '시간(초)'을 의미하도록 설계됐지만 실제 구현은 홉 수를 세는 방식이었다. IPv6는 이 불일치를 바로잡아 필드명을 Hop Limit(홉 제한)으로 바꾸었다. 즉 기능은 계승되었으나 IPv6 헤더에 'Time to Live'라는 이름의 필드는 존재하지 않는다.

문제​

정답​

③

상세 풀이​

문항은 "IPv6 헤더에 포함되는 필드로 가장 적절하지 않은 것"을 묻는다. 즉 IPv6 헤더에 없는 필드를 고르면 된다.

1단계 — IPv6 기본 헤더 40바이트의 8개 필드를 나열한다.

Version(4b) | Traffic Class(8b) | Flow Label(20b)     ← 4바이트
Payload Length(16b) | Next Header(8b) | Hop Limit(8b) ← 4바이트
Source Address(128b)                                  ← 16바이트
Destination Address(128b)                             ← 16바이트
합계 40바이트

2단계 — 보기를 이 목록과 대조한다.

보기IPv6 기본 헤더 포함 여부소속
① Hop Limit포함 ✅IPv6 고유(TTL 대체)
② Flow Label포함 ✅IPv6 신설
③ Time to Live미포함 ❌IPv4 전용
④ Traffic Class포함 ✅IPv4의 ToS를 계승

3단계 — 함정 확인.

③ TTL과 ① Hop Limit은 "홉 수를 세어 무한 루프를 막는다"는 기능이 동일하다. 그래서 "기능이 있으니 필드도 있겠지"라고 넘겨짚으면 틀린다. 문항이 묻는 것은 기능이 아니라 필드 이름의 존재 여부이며, IPv6 표준(RFC 8200) 헤더 포맷에 'Time to Live'라는 필드명은 없다.

따라서 정답은 ③이다.

보기별 판정​

보기판정근거
① Hop Limit오답 보기(옳은 설명)IPv6 기본 헤더의 8비트 필드. 라우터 통과 시 1씩 감소, 0이면 패킷 폐기
② Flow Label오답 보기(옳은 설명)IPv6에서 신설된 20비트 필드. 동일 플로우 패킷을 같은 경로·같은 QoS로 처리하도록 표시
③ Time to Live✅ 정답 보기(IPv6 헤더에 없음)IPv4 헤더 필드. IPv6에서는 Hop Limit이 그 역할을 대체하며 TTL이라는 필드는 존재하지 않음
④ Traffic Class오답 보기(옳은 설명)IPv6 기본 헤더의 8비트 필드. IPv4의 Type of Service에 대응하며 DSCP/ECN으로 세분 사용

오답 이유​

'가장 적절하지 않은 것'을 고르는 유형이므로 ①·②·④는 모두 IPv6 헤더에 실제로 존재하는 옳은 보기이며, 그래서 정답이 아니다.

  • ① Hop Limit — IPv6 기본 헤더 40바이트 중 39번째 바이트에 위치하는 8비트 필드다. 각 라우터가 전달 시 1을 감소시키고 0이 되면 패킷을 폐기한 뒤 ICMPv6 Time Exceeded를 회신한다. traceroute6가 동작하는 원리이기도 하다. IPv6 헤더에 명백히 포함되므로 정답이 될 수 없다.
  • ② Flow Label — IPv4에는 없던 IPv6 전용 20비트 필드로, 송신 호스트가 같은 값의 레이블을 붙인 패킷들을 라우터가 하나의 흐름으로 인식해 동일하게 처리하게 한다. VoIP·스트리밍처럼 지연 편차에 민감한 실시간 트래픽의 QoS 보장에 쓰인다. IPv6 고유 필드이므로 정답이 될 수 없다.
  • ④ Traffic Class — IPv4의 Type of Service(ToS) 필드를 계승한 8비트 필드로, 상위 6비트는 DSCP(차등 서비스 코드포인트), 하위 2비트는 ECN(명시적 혼잡 통보)으로 사용한다. 역시 IPv6 기본 헤더의 구성 요소이므로 정답이 아니다.
  • 만약 보기가 Header Checksum, IHL, Identification, Fragment Offset, Options 중 하나였다면 그것도 정답이 될 수 있었다. 모두 IPv6에서 제거되었거나 확장 헤더로 옮겨간 IPv4 전용 필드이기 때문이다.

핵심 정리​

  • IPv6 기본 헤더는 40바이트 고정 8개 필드: Version, Traffic Class, Flow Label, Payload Length, Next Header, Hop Limit, Source/Destination Address.
  • TTL(IPv4) ↔ Hop Limit(IPv6): 기능은 같지만 이름이 다르다. IPv6 헤더에 TTL이라는 필드는 없다.
  • IPv6에서 삭제된 IPv4 필드: IHL, Header Checksum, 단편화 관련 3개 필드(Identification/Flags/Fragment Offset), Options.
  • Flow Label은 IPv6에만 있는 신설 필드로 실시간 트래픽의 QoS 처리를 위한 흐름 식별자다.

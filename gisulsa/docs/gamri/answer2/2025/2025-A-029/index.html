029번 · 시퀀스 다이어그램에서 아키텍처 패턴 식별 — Master-Slave

제26회(2025년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. 보기에 등장한 네 가지 패턴​

패턴구조제어 흐름의 특징대표 사례
Pipe and Filter필터(처리 단계)들이 파이프로 직렬 연결데이터가 필터1 → 필터2 → 필터3 으로 단계적으로 변환되며 흘러감. 각 필터의 처리 내용이 서로 다름컴파일러(어휘→구문→의미→코드생성), Unix 파이프라인
Master-Slave하나의 마스터와 동일한 기능을 가진 여러 슬레이브마스터가 작업을 분할(split) 해 슬레이브들에게 병렬 분배하고, 결과를 취합(merge) 해 최종 결과 산출병렬 계산, MapReduce, 내고장성 중복 계산, 부하 분산
Front Controller모든 요청을 받는 단일 진입점 컨트롤러요청을 받아 적절한 핸들러로 라우팅하고 공통 관심사(인증·로깅)를 처리. 분할·병렬·취합이 없음Spring DispatcherServlet, Struts ActionServlet
MVCModel · View · Controller 3역할 분리사용자 입력은 Controller, 상태·로직은 Model, 표현은 View. 관심사의 역할 분리가 본질웹 MVC 프레임워크, GUI 애플리케이션

2. Master-Slave 패턴의 식별 신호​

다음 세 가지가 연속으로 나타나면 Master-Slave다.

1) 분할(split)   : 마스터가 입력을 부분 작업으로 나눈다
2) 분배(dispatch): 동일한 연산을 수행하는 여러 슬레이브에게 동시에 위임한다
3) 취합(merge)   : 슬레이브들의 부분 결과를 모아 하나의 결과로 결합한다

또한 슬레이브들은 서로 같은 종류(동일 타입·동일 인터페이스) 이며, 서로 통신하지 않고 오직 마스터하고만 대화한다. Pipe and Filter와 구분되는 결정적 지점이 바로 이것이다. Pipe and Filter는 처리 단계가 서로 다르고 직렬로 이어지는 반면, Master-Slave는 처리 단계가 서로 같고 병렬로 갈라진다.

3. UML 시퀀스 다이어그램의 결합 프래그먼트(Combined Fragment)​

시퀀스 다이어그램에서 사각 프레임 좌상단에 붙는 라벨을 연산자(interaction operator) 라 한다.

연산자의미
alt조건에 따라 택일 실행(if-else)
opt조건이 참일 때만 실행(if)
loop반복 실행
par내부의 피연산자들이 병렬(parallel) 실행 — 점선으로 구분된 각 영역이 동시에 수행됨
critical원자적(비인터럽트) 구간
ref다른 상호작용을 참조

par 프래그먼트는 "동시 실행"의 직접적 표기이므로, 이것이 보이면 병렬 분배형 패턴(Master-Slave)을 우선 의심한다.

문제​

정답​

②

상세 풀이​

1단계 — 다이어그램의 메시지 흐름을 순서대로 읽는다​

라이프라인은 :UI, :Main, :Controller, :Controller (동일 타입 컨트롤러 2개)이다.

메시지내용해석
1.0:UI → :Main — service(data: LargeData[]): int대용량 배열 데이터를 처리해 달라는 요청
1.1:Main → :Main (자기 호출) — [data1, data2] = split(data)마스터가 입력을 두 조각으로 분할
par결합 프래그먼트 시작내부의 두 영역이 병렬 실행
1.2:Main → :Controller(1) — subResult1 = do(data1)첫 번째 슬레이브에 부분 작업 위임
1.3:Main → :Controller(2) — subResult2 = do(data2)두 번째 슬레이브에 부분 작업 위임 (1.2와 동시)
1.4:Main → :Main (자기 호출) — result = merge(subResult1, subResult2)부분 결과를 하나로 취합
1.5:Main ⇢ :UI — :result (반환, 점선)최종 결과 반환

2단계 — 패턴의 식별 신호와 대조한다​

Master-Slave의 신호다이어그램에서의 근거
① 분할(split)메시지 1.1의 split(data) — 이름부터 split
② 동일 기능 슬레이브에 병렬 분배1.2·1.3이 par 프래그먼트 안에 있고, 두 수신자가 모두 :Controller(같은 타입), 호출 메시지도 모두 do(...) 로 동일
③ 취합(merge)메시지 1.4의 merge(subResult1, subResult2) — 이름부터 merge
④ 슬레이브 간 통신 없음두 :Controller 라이프라인 사이에는 메시지가 하나도 없음. 오직 :Main 하고만 통신
⑤ 마스터가 최종 책임:Main이 요청을 받고 결과를 :UI에 반환

split → par(do, do) → merge 라는 세 박자가 완벽히 갖춰졌다. 이는 Master-Slave(마스터-슬레이브) 패턴의 교과서적 시퀀스다. :Main이 마스터, 두 :Controller가 슬레이브다.

3단계 — 왜 다른 패턴이 아닌지 확인한다​

  • Pipe and Filter라면: :Main → :Controller(1) → :Controller(2) → ... 처럼 메시지가 직렬로 이어져야 하고, 각 단계가 앞 단계의 출력을 입력으로 받아 서로 다른 변환을 수행해야 한다. 그러나 여기서는 두 호출이 par 안에서 병렬이고, 각각 원본 데이터의 조각(data1, data2)을 받아 같은 연산 do() 를 수행한다. 직렬 변환 사슬이 전혀 없다.
  • Front Controller라면: 단일 진입점이 요청 유형에 따라 서로 다른 핸들러 하나를 골라 위임해야 한다. 분할도 병렬 분배도 취합도 나타나지 않는다.
  • MVC라면: Model, View, Controller 세 역할이 라이프라인으로 구분되고, Controller가 Model을 갱신하면 View가 갱신 결과를 표현하는 흐름이 보여야 한다. 여기에는 Model이나 View에 해당하는 라이프라인이 없고, :Controller 두 개는 역할이 다른 것이 아니라 똑같은 역할의 복제본이다.

4단계 — 결론​

정답은 ② Master-Slave이다.

보기별 판정​

보기판정근거
① Pipe and Filter❌ 오답필터가 직렬로 연결되어 단계별로 서로 다른 변환을 수행해야 하나, 여기서는 par로 병렬이며 두 호출 모두 동일한 do()
② Master-Slave✅ 정답split() 분할 → par 안에서 동일 타입 :Controller 2개에 do() 병렬 분배 → merge() 취합
③ Front Controller❌ 오답단일 진입점의 요청 라우팅 패턴. 분할·병렬·취합 흐름이 없음
④ MVC❌ 오답Model·View·Controller 역할 분리 구조. 다이어그램에 Model·View 라이프라인이 없고 Controller는 동일 역할의 복제본 2개

오답 이유​

① Pipe and Filter — 데이터가 필터들을 순차적으로 통과하며 각 단계에서 조금씩 변환되는 구조다. 컴파일러처럼 어휘분석 → 구문분석 → 의미분석 → 코드생성으로 이어지며, 앞 필터의 출력이 다음 필터의 입력이 되고 각 필터는 서로 다른 일을 한다. 그러나 본 다이어그램은 (ㄱ) 두 호출이 par 결합 프래그먼트 안에 있어 순차가 아니라 병렬이고, (ㄴ) :Controller 두 개가 받는 것은 앞 단계의 출력이 아니라 원본을 쪼갠 조각 data1, data2 이며, (ㄷ) 두 컨트롤러가 수행하는 연산이 do() 로 동일하다. 세 가지 모두 Pipe and Filter와 배치된다. "여러 처리 객체가 나온다"는 인상만으로 고르면 빠지는 함정이다.

③ Front Controller — 웹 애플리케이션에서 모든 HTTP 요청을 하나의 서블릿(예: DispatcherServlet)이 받아 인증·로깅 같은 공통 처리를 한 뒤, 요청 URL에 맞는 개별 핸들러 하나에게 넘기는 패턴이다. 핵심은 진입점 단일화와 라우팅이지 병렬 처리가 아니다. 본 다이어그램에서 :Main이 단일 진입점처럼 보이는 것은 사실이나, :Main은 요청을 라우팅하는 것이 아니라 데이터를 분할해 동시에 여러 일꾼에게 뿌리고 결과를 합치고 있다. split·par·merge 어느 것도 Front Controller의 요소가 아니므로 오답이다.

④ MVC(Model View Controller) — 사용자 인터페이스를 Model(데이터·업무 로직), View(표현), Controller(입력 처리와 흐름 제어) 로 나누는 패턴이다. MVC라면 라이프라인에 :Model과 :View가 등장하고, 컨트롤러가 모델을 갱신한 뒤 뷰가 갱신된 모델을 읽어 표현하는 흐름이 나타나야 한다. 본 다이어그램의 라이프라인은 :UI, :Main, :Controller ×2 뿐이며, 두 :Controller는 역할이 분리된 서로 다른 구성요소가 아니라 동일한 연산을 수행하는 복제본이다. :Controller라는 이름만 보고 MVC를 떠올리게 만든 것이 이 보기의 함정이며, 패턴 식별은 이름이 아니라 메시지 흐름의 형태로 해야 한다.

핵심 정리​

  • split → par(동일 연산 병렬 위임) → merge 세 박자가 보이면 Master-Slave다. 본 문항은 :Main이 마스터, 두 :Controller가 슬레이브다.
  • Pipe and Filter = 직렬 + 서로 다른 변환, Master-Slave = 병렬 + 동일 연산 + 결과 취합. 이 대비가 ①과 ②를 가른다.
  • UML 시퀀스의 par 결합 프래그먼트는 병렬 실행을 뜻한다. alt(택일), opt(조건), loop(반복)와 함께 반드시 구분해 둘 것.
  • 라이프라인의 이름(:Controller)이 아니라 메시지의 형태로 패턴을 판별한다. 동일 타입 라이프라인이 여러 개 나란히 있으면 역할 분리(MVC)가 아니라 복제·분산(Master-Slave)을 의심한다.

035번 · 오픈소스 라이선스 의무사항

제26회(2025년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

오픈소스 라이선스의 두 축 — 고지 의무와 카피레프트​

오픈소스 라이선스의 의무사항은 크게 두 가지로 나뉜다.

  1. 고지(notice) 의무 — 저작권 표시, 라이선스 사본, 보증 부인(무보증) 문구를 유지·제공할 것. 거의 모든 오픈소스 라이선스가 요구한다.
  2. 카피레프트(copyleft) 의무 — 소스코드를 공개하고, 파생 저작물에 동일 라이선스를 적용할 것. 공개 범위(전파 범위) 에 따라 라이선스가 갈린다.
구분전파 범위대표 라이선스
강한 카피레프트링크한 응용 프로그램 전체까지 동일 라이선스 강제GPL, AGPL
약한 카피레프트(부분)라이브러리(해당 저작물) 자체의 수정분만 공개, 링크한 프로그램은 독점 가능LGPL, MPL, EPL
비카피레프트(허용형)소스 공개 의무 없음, 고지 의무만BSD, MIT, Apache 2.0

LGPL의 고유 의무 — "라이브러리 교체 자유"​

LGPL(GNU Lesser General Public License)은 GPL을 라이브러리에 한정해 완화한 라이선스로, 다음 두 항목이 LGPL에서만 나타나는 결정적 지문이다.

  • 응용 프로그램 배포 시 "본 라이브러리를 사용한다"는 사실을 명시할 것 (LGPL 2.1 제6조, "give prominent notice that the Library is used")
  • 사용자가 라이브러리를 수정·교체한 뒤에도 응용 프로그램을 계속 사용할 수 있도록 보장할 것 — 동적 링크를 쓰거나, 정적 링크라면 오브젝트 파일을 제공해 재링크(relink) 가 가능하게 할 것

이 "사용자가 라이브러리를 갈아 끼울 자유"는 LGPL이 응용 프로그램 본체의 소스 공개를 면제해 주는 대가로 요구하는 조건이다. GPL·MPL·BSD 어디에도 이런 조항이 없다.

각 라이선스의 성격 요약​

  • GPL — 프로그램의 일부라도 GPL 코드를 링크하면 전체를 GPL로 배포해야 하고 전체 소스를 공개해야 한다("전염성"). 응용 프로그램의 독점 배포가 불가능하다.
  • MPL(Mozilla Public License) — 파일(file) 단위 카피레프트. MPL 코드가 들어 있는 파일만 MPL로 공개하고, 새로 추가한 별도 파일은 독점으로 둘 수 있다. 라이브러리 교체 보장 조항은 없다.
  • BSD — 저작권 고지, 라이선스 조건문, 무보증 문구를 유지하기만 하면 소스 비공개 상용 배포가 자유롭다. 수정 사실 명기 의무도 소스 공개 의무도 없다.
  • Apache 2.0 — BSD형이되 수정 사실 명기와 특허 라이선스(NOTICE 파일) 조항이 추가된다.

상세 풀이​

제시된 일곱 개 의무를 성격별로 분류해 나가면 후보가 순차적으로 좁혀진다.

1단계 — 공통 고지 의무(가·나·다)로는 구분되지 않음

  • 가: 복제본에 저작권 안내 + 무보증 명시
  • 나: 라이선스 안내와 보증책임 고지사항을 원본 그대로 유지
  • 다: 양도받는 모든 이에게 라이선스 사본 제공

이 세 가지는 BSD·MPL·LGPL·GPL 모두가 요구하는 기본 고지 의무이므로 변별력이 없다.

2단계 — "수정 사실과 날짜 명기"(라)로 BSD 탈락

라의 "수정한 경우 수정사실과 날짜를 파일에 명기"는 GPL/LGPL 제2조(a)와 MPL에 있는 조항이다. BSD에는 수정 사실 명기 의무가 없다. → ④ BSD 탈락.

동시에 라의 앞부분 "라이브러리 형태로의 수정을 허용하며" 라는 표현이 이 라이선스가 라이브러리를 규율 대상으로 삼는 라이선스임을 시사한다.

3단계 — "소스코드 제공 또는 제공 약정서"(마)로 범위 확인

마는 "원본저작물 및 파생저작물에 대한 소스코드를 제공하거나 요청 시 제공하겠다는 약정서(written offer) 를 제공"이다. 이 3년간 유효한 서면 약정서 방식은 GPL/LGPL 제3조(b)에 규정된 전형적 조항이다. MPL은 서면 약정서 방식이 아니라 소스 코드를 온라인 등으로 접근 가능하게 두는 방식을 쓴다. → ① MPL 탈락.

4단계 — 결정타: 바·사 조항으로 GPL 탈락, LGPL 확정

  • 바. "응용 프로그램을 배포할 경우, 본 라이브러리를 사용하고 있다는 사실을 명시할 것" → 응용 프로그램이 라이브러리와 별개의 저작물로 존재함을 전제한다. GPL이라면 응용 프로그램 전체가 같은 저작물로 취급되어 이런 "사용 사실 명시" 조항이 필요 없다.
  • 사. "사용자가 라이브러리를 수정해도 응용 프로그램을 사용할 수 있도록 허용할 것" → 사용자가 라이브러리를 개선·교체한 뒤 재링크해서 쓸 자유를 보장하라는 것으로, LGPL 2.1 제6조의 핵심 의무다. 이 조항은 오직 LGPL에만 존재한다.

바·사가 함께 등장하면 답은 LGPL 하나로 확정된다. 따라서 정답은 ③이다.

보기별 판정​

보기판정근거
① MPL❌ 오답파일 단위 공개가 핵심이며, 라이브러리 사용 사실 명시(바)·라이브러리 교체 보장(사) 조항이 없다.
② GPL❌ 오답링크한 응용 프로그램 전체에 GPL을 강제하므로, 응용 프로그램을 독립 저작물로 전제하는 바·사 조항이 성립하지 않는다.
③ LGPL✅ 정답고지 의무(가~다) + 수정 사실 명기(라) + 소스 제공/약정서(마)에 더해, 라이브러리 사용 사실 명시(바) 와 사용자의 라이브러리 교체·재링크 보장(사) 이라는 LGPL 고유 의무를 모두 포함한다.
④ BSD❌ 오답고지 의무만 있고 수정 사실 명기·소스 공개·라이브러리 관련 의무가 전혀 없다.

오답 이유​

  • ① MPL(Mozilla Public License) — MPL은 파일 단위 약한 카피레프트로, MPL 코드가 포함된 파일을 수정하면 그 파일만 MPL로 공개하면 되고 새로 추가한 파일은 독점으로 유지할 수 있다. 가~라(고지, 수정 사실 명기)까지는 유사하지만, MPL의 소스 공개 방식은 "요청 시 제공 약정서(written offer)"가 아니라 배포와 함께 또는 온라인으로 접근 가능하게 둘 것이다. 무엇보다 바(라이브러리 사용 사실 명시)와 사(사용자의 라이브러리 수정 후에도 응용 프로그램 사용 보장)에 해당하는 조항이 MPL에는 존재하지 않는다.
  • ② GPL(General Public License) — GPL은 강한 카피레프트로, GPL 라이브러리를 링크한 응용 프로그램은 전체가 GPL 파생 저작물이 되어 응용 프로그램 소스까지 모두 공개해야 한다. 그러므로 "응용 프로그램은 독점으로 두되 라이브러리를 쓴다는 사실만 명시하라(바)", "사용자가 라이브러리를 바꿔 끼울 수 있게 하라(사)"는 식의 완화 조건 자체가 필요 없다. 이 두 조항이 나온 시점에서 응용 프로그램의 독점 배포를 허용하는 라이선스임이 확정되므로 GPL은 배제된다.
  • ④ BSD(Berkeley Software Distribution) — BSD는 고지 의무만 있는 허용형(permissive) 라이선스다. 저작권 표시·조건문·무보증 문구만 유지하면 수정·비공개·상용 배포가 모두 자유롭다. 라(수정 사실·날짜 명기), 마(소스코드 제공 또는 제공 약정서), 바, 사 어느 것도 BSD의 의무가 아니다. 제시된 의무 목록의 절반 이상이 BSD에 존재하지 않으므로 가장 먼저 탈락한다.

핵심 정리​

  • 라이선스 구분의 1차 기준은 카피레프트의 전파 범위다: GPL = 링크한 프로그램 전체, LGPL = 라이브러리까지만, MPL = 수정한 파일까지만, BSD/MIT/Apache = 공개 의무 없음.
  • 지문에 "라이브러리 사용 사실 명시" 와 "사용자가 라이브러리를 수정/교체해도 응용 프로그램을 쓸 수 있게 보장(재링크 허용)" 이 보이면 무조건 LGPL이다.
  • "수정 사실과 날짜 명기"가 있으면 BSD/MIT는 탈락하고, "소스코드 제공 또는 3년 유효 서면 약정서" 방식이 보이면 GPL 계열(GPL/LGPL)로 좁혀진다.

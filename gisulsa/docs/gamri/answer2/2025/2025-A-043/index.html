043번 · 요구사항 검증(Validation) 점검 항목

제26회(2025년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

요구사항 확인(Validation)과 검증(Verification)​

구분질문관점
Verification(검증)"제품을 제대로 만들고 있는가?"산출물이 앞 단계 명세를 정확히 구현했는가
Validation(확인)"제대로 된 제품을 만들고 있는가?"산출물이 사용자의 실제 요구를 충족하는가

요구사항 공학 단계의 요구사항 검증(requirements validation) 은 SRS가 확정되기 전에 오류를 잡아내는 활동이다. 요구사항 단계의 결함을 설계·구현 이후에 발견하면 수정 비용이 수십 배로 증가하므로(오류 비용 증폭 법칙), 이 단계의 점검이 매우 중요하다.

Sommerville의 요구사항 검증 점검 항목 (핵심 암기 대상)​

점검 항목영문점검 내용대표 질문
유효성 점검Validity checks요구사항이 사용자의 실제 요구를 반영하는지"이것이 정말 사용자가 원하는 기능인가?"
일관성 점검Consistency checks요구사항 간 상충·모순되는 제약조건이 없는지"A 요구와 B 요구가 서로 충돌하지 않는가?"
완전성 점검Completeness checks사용자가 의도한 모든 기능과 제약이 포함되었는지"빠진 요구사항은 없는가?"
실현성 점검Realism checks현재 기술·지식·예산·일정으로 구현 가능한지"주어진 자원으로 만들 수 있는가?"
검증 가능성Verifiability요구사항을 테스트로 확인할 수 있게 기술했는지"합격/불합격을 판정할 수 있는가?"

각 항목을 구분하는 키워드​

  • 유효성 → "사용자의 실제 요구", "진짜 필요한가"
  • 일관성 → "상충", "모순", "충돌"
  • 완전성 → "모두 포함", "누락"
  • 실현성 → "기술·예산·일정으로 구현 가능"
  • 검증 가능성 → "테스트 가능", "측정 가능"

요구사항 검증 기법​

기법설명
요구사항 검토(review/inspection)이해관계자가 SRS를 함께 읽으며 결함을 찾음
프로토타이핑실행 모델을 보여 주어 사용자가 요구를 확인
테스트 케이스 생성각 요구사항에 대한 테스트를 작성해 보며 검증 가능성 확인
모델 검증시스템 모델(UML 등)의 일관성 자동 점검
CRUD 분석 / 요구사항 추적표누락·중복 여부 점검

문제​

정답​

①

상세 풀이​

제시된 가~라를 표준 점검 항목에 하나씩 대응시킨다.

가 — "요구사항이 사용자의 실제 요구를 반영하는지 점검한다"​

"사용자의 실제 요구를 반영"은 Validity checks(유효성 점검) 의 정의 그 자체다. 이해관계자가 각자 다른 요구를 제시했을 때, 명세된 요구가 진짜 필요한 것인지 판단하는 활동이다.

→ 가 = 유효성 점검

나 — "요구사항이 서로 상충하지 않고 서로 모순인 제약조건이 없는지 점검한다"​

"상충", "모순"은 Consistency checks(일관성 점검) 의 키워드다. 같은 대상에 대해 서로 다른 제약이 부여되어 있지 않은지를 본다.

→ 나 = 일관성 점검

다 — "사용자가 의도한 모든 기능과 제약조건이 요구사항에 포함되었는지 점검한다"​

"모든 기능과 제약이 포함"은 누락 여부, 즉 Completeness checks(완전성 점검) 이다.

→ 다 = 완전성 점검

라 — "현재의 기술과 지식을 사용해서 주어진 예산으로 실제로 구현이 가능한지 점검한다"​

"현재 기술·지식·예산으로 구현 가능"은 Realism checks(실현성 점검) 이다.

→ 라 = 실현성 점검

대응표 정리​

항목정답 매핑
가유효성 점검(validity)
나일관성 점검(consistency)
다완전성 점검(completeness)
라실현성 점검(realism)

이 매핑과 완전히 일치하는 보기는 ①(가 - 유효성 점검, 나 - 일관성 점검) 뿐이다.

보기별 판정​

보기판정근거
① 가 - 유효성 점검, 나 - 일관성 점검✅ 정답두 연결 모두 표준 정의와 일치한다.
② 가 - 실현성 점검, 나 - 완전성 점검❌ 오답가는 유효성, 나는 일관성이어야 한다. 두 항목 모두 오매핑.
③ 다 - 완전성 점검, 라 - 유효성 점검❌ 오답다-완전성은 맞지만, 라는 유효성이 아니라 실현성이다. 한 쪽이 틀리므로 전체가 오답.
④ 다 - 일관성 점검, 라 - 실현성 점검❌ 오답라-실현성은 맞지만, 다는 일관성이 아니라 완전성이다. 한 쪽이 틀리므로 전체가 오답.

오답 이유​

  • ② — "가 - 실현성 점검"이 틀렸다. 가는 사용자의 실제 요구 반영 여부를 보므로 유효성이다. 실현성은 "기술·예산으로 만들 수 있는가"를 묻는 라에 해당한다. 또한 "나 - 완전성 점검"도 틀렸다. 나의 키워드는 '상충·모순'이므로 일관성이며, 완전성은 '누락 여부'를 보는 다에 해당한다. 두 개 모두 틀린 보기다.
  • ③ — "다 - 완전성 점검"은 올바른 연결이지만, "라 - 유효성 점검"이 틀렸다. 라의 서술("현재의 기술과 지식", "주어진 예산으로 구현 가능")에는 사용자 요구 반영이라는 개념이 전혀 없다. 라는 실현성 점검(realism) 이다. 이처럼 절반만 맞는 보기가 전형적인 함정이다.
  • ④ — "라 - 실현성 점검"은 올바른 연결이지만, "다 - 일관성 점검"이 틀렸다. 다의 서술("의도한 모든 기능과 제약조건이 포함되었는지")은 누락 검사이므로 완전성 점검(completeness) 이다. 일관성은 요구사항 간 충돌 여부를 보는 나에 해당한다.

핵심 정리​

  • 유효성(가)=사용자 실제 요구, 일관성(나)=상충·모순, 완전성(다)=누락 없음, 실현성(라)=기술·예산 구현 가능 — 가나다라 순서가 그대로 유효성·일관성·완전성·실현성 순이다.
  • 매칭형 문제는 보기 두 쌍 중 하나만 틀려도 오답이므로, 정답 후보를 고를 때 두 쌍을 모두 검증해야 한다.
  • 검증 가능성(verifiability)도 Sommerville의 점검 항목에 포함되므로 함께 외워 둔다.
  • Validation은 "제대로 된 제품", Verification은 "제품을 제대로"로 구분한다.

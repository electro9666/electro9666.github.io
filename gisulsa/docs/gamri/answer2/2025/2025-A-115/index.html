115번 · 시큐어 코딩 — 입력 데이터 검증 취약점 분류

제26회(2025년) 정보시스템감리사 A형 — 보안

사전 지식​

소프트웨어 개발보안(시큐어 코딩) 취약점 7대 분류​

행정안전부·KISA 「소프트웨어 개발보안 가이드」는 소스 코드 보안약점을 7개 유형으로 분류한다. 이 분류표가 문제의 뼈대다.

분류정의대표 보안약점
1. 입력 데이터 검증 및 표현입력값에 대한 검증 누락·부적절, 잘못된 형식 지정으로 발생SQL 삽입, 코드 삽입, 경로 조작 및 자원 삽입, XSS, 운영체제 명령어 삽입, 위험한 형식 파일 업로드, 신뢰되지 않는 URL 주소로 자동접속 연결, 메모리 버퍼 오버플로우, 포맷 스트링 삽입, 정수형 오버플로우, LDAP/XQuery/XPath 삽입
2. 보안 기능인증·접근제어·기밀성·암호화·권한 관리를 부적절하게 구현부적절한 인가, 취약한 암호 알고리즘 사용, 하드코드된 비밀번호, 중요정보 평문 저장·전송
3. 시간 및 상태동시 또는 거의 동시 수행을 지원하는 병렬 환경에서 시간·상태를 부적절하게 관리경쟁 조건(Race Condition): TOCTOU, 종료되지 않는 반복문 또는 재귀 함수
4. 에러 처리에러를 처리하지 않거나 불충분하게 처리해 중요정보가 노출오류 메시지를 통한 정보 노출, 오류 상황 대응 부재, 부적절한 예외 처리
5. 코드 오류타입 변환·자원 해제 등 개발자의 코딩 실수널 포인터 역참조, 부적절한 자원 해제, 해제된 자원 사용, 초기화되지 않은 변수 사용
6. 캡슐화중요 데이터·기능을 불충분하게 캡슐화해 비인가자에게 노출잘못된 세션에 의한 데이터 정보 노출, 제거되지 않고 남은 디버그 코드, Public 메서드로부터 반환된 Private 배열
7. API 오용의도된 사용에 반하는 방법으로 API를 사용DNS lookup에 의존한 보안 결정, 취약한 API 사용

보기에 등장한 약점들의 소속​

보안약점분류설명
포맷 스트링 삽입입력 데이터 검증 및 표현외부 입력값을 printf 계열 함수의 형식 문자열 인자로 직접 전달할 때 발생. %n, %x 등으로 메모리 열람·변조가 가능하다. 올바른 코드는 printf("%s", input).
신뢰되지 않는 URL 주소로 자동접속 연결입력 데이터 검증 및 표현외부 입력값을 리다이렉트 대상 URL로 그대로 사용해 피싱 사이트로 유도(Open Redirect)되는 약점. 화이트리스트 검증 필요.
메모리 버퍼 오버플로우입력 데이터 검증 및 표현입력 데이터의 길이를 검증하지 않고 고정 크기 버퍼에 복사해 인접 메모리를 침범. strcpy 대신 strncpy, 경계 검사 필요.
경쟁 조건(Race Condition)시간 및 상태검사 시점(Time of Check)과 사용 시점(Time of Use) 사이에 상태가 바뀌어 발생하는 TOCTOU 문제. 입력값 내용과 무관하다.

경쟁 조건(TOCTOU)이 입력값 검증 문제가 아닌 이유​

if (access("/tmp/file", W_OK) == 0) {   /* 검사 시점 */
    /* ← 이 틈에 공격자가 /tmp/file 을 심볼릭 링크로 교체 */
    fd = open("/tmp/file", O_WRONLY);   /* 사용 시점 */
    write(fd, data, len);
}

여기서 문제가 되는 것은 입력 데이터의 값이나 형식이 아니라 두 연산 사이의 시간 간극과 원자성 결여다. 아무리 입력값을 철저히 검증해도 이 간극 자체는 사라지지 않는다. 대응 수단도 입력 검증이 아니라 동기화(락·세마포어·뮤텍스), 원자적 연산, 임계 구역 설정이다.

문제​

정답​

③

상세 풀이​

  1. 문항은 "입력 데이터에 대한 검증을 소홀히 하여 발생할 수 있는 보안 취약점과 가장 거리가 먼 것"을 묻는다. 즉 시큐어 코딩 7대 분류 중 '입력 데이터 검증 및 표현'에 속하지 않는 보기를 찾으면 된다.
  2. ① 포맷 스트링 삽입 → 외부 입력값을 형식 문자열로 그대로 넘긴 데서 비롯되므로 입력값 검증 미흡이 원인. 해당 분류에 속한다.
  3. ② 신뢰되지 않은 URL 주소로 자동 접속 연결 → 외부 입력값을 리다이렉트 대상 URL로 검증 없이 사용한 결과. 해당 분류에 속한다.
  4. ④ 메모리 버퍼 오버플로우 → 입력 데이터의 길이 검증 누락이 직접 원인. 해당 분류에 속한다.
  5. ③ 경쟁 조건 → 병렬 실행 환경에서 공유 자원에 대한 동시 접근과 연산의 비원자성이 원인이다. 「소프트웨어 개발보안 가이드」에서도 '시간 및 상태' 분류에 속한다. 입력값을 아무리 검증해도 예방되지 않는다.

따라서 입력값 검증과 가장 거리가 먼 보기는 ③이다.

보기별 판정​

보기판정근거
① 포맷 스트링 삽입❌ 오답'입력 데이터 검증 및 표현' 분류. 외부 입력을 형식 문자열로 직접 사용한 것이 원인이다.
② 신뢰되지 않은 URL주소로 자동 접속 연결❌ 오답'입력 데이터 검증 및 표현' 분류. 리다이렉트 대상 URL을 검증하지 않아 발생한다.
③ 경쟁 조건✅ 정답'시간 및 상태' 분류. 공유 자원 동시 접근·비원자성 문제로 입력값 검증과 무관하다.
④ 메모리 버퍼 오버플로우❌ 오답'입력 데이터 검증 및 표현' 분류. 입력 길이를 검증하지 않은 것이 직접 원인이다.

오답 이유​

"가장 거리가 먼 것"을 고르는 문항이므로, 아래는 왜 나머지 세 보기가 입력값 검증 미흡에서 비롯되는지에 대한 설명이다.

  • ① 포맷 스트링 삽입이 입력값 검증 문제인 이유: printf(input)처럼 외부 입력값을 형식 문자열 자리에 그대로 넣으면, 입력에 포함된 %x·%s·%n 같은 변환 지정자가 실행되어 스택 메모리 열람이나 임의 주소 쓰기가 가능해진다. 입력값을 "데이터"가 아니라 "형식 지정 명령"으로 해석하게 만든 것이므로, 분류상 명백히 입력 데이터 검증 및 표현에 해당한다. 대응은 printf("%s", input)처럼 형식 문자열을 상수로 고정하고 입력을 인자로만 넘기는 것이다.
  • ② 신뢰되지 않은 URL 주소로 자동 접속 연결이 입력값 검증 문제인 이유: response.sendRedirect(request.getParameter("url")) 같은 코드는 외부에서 지정한 임의 URL로 사용자를 이동시킨다. 공격자는 신뢰받는 도메인의 링크를 미끼로 삼아 피싱 사이트로 유도할 수 있다. 원인은 리다이렉트 대상 값에 대한 화이트리스트 검증 누락이므로 입력값 검증 영역이다.
  • ④ 메모리 버퍼 오버플로우가 입력값 검증 문제인 이유: char buf[64]; strcpy(buf, input);에서 input이 64바이트를 넘으면 인접 메모리(복귀 주소 포함)를 덮어쓴다. 원인은 입력 데이터의 길이를 검증하지 않은 것이다. 대응은 경계 검사와 strncpy·snprintf 같은 길이 제한 함수 사용, 안전한 언어·컴파일러 보호 기능(스택 카나리, ASLR, DEP) 적용이다.
  • ③ 경쟁 조건이 거리가 먼 이유(핵심): 경쟁 조건은 둘 이상의 실행 흐름이 공유 자원에 동시 접근할 때, 실행 순서(타이밍)에 따라 결과가 달라지는 문제다. 특히 TOCTOU는 검사와 사용 사이의 시간 간극이 취약점의 본질이다. 입력값이 아무리 깨끗하고 완벽히 검증되었더라도, 검사 이후 사용 전까지 외부에서 대상 자원(파일·변수·레코드)을 바꿔치기하면 공격이 성립한다. 따라서 대응책도 입력 검증이 아니라 락·뮤텍스·세마포어를 통한 동기화, 원자적 연산 사용, 임계 구역 최소화, 파일 디스크립터 기반 접근(open 후 fstat) 이다. 시큐어 코딩 가이드의 분류도 '시간 및 상태'로 별도 항목이므로 네 보기 중 유일하게 다른 범주에 속한다.

핵심 정리​

  • 「소프트웨어 개발보안 가이드」의 7대 분류(입력 데이터 검증 및 표현 / 보안 기능 / 시간 및 상태 / 에러 처리 / 코드 오류 / 캡슐화 / API 오용)를 기억하면 이 유형의 문제는 분류 대조만으로 풀린다.
  • 포맷 스트링, 버퍼 오버플로우, 오픈 리다이렉트, SQL·명령어 삽입, XSS는 모두 입력 데이터 검증 및 표현 소속이다.
  • 경쟁 조건(TOCTOU) 은 시간 및 상태 소속으로, 원인은 입력값이 아니라 동시 접근과 비원자성이며 대응도 동기화다.
  • "입력값을 더 잘 검증하면 막을 수 있는가?"를 자문하면 분류를 빠르게 판별할 수 있다. 경쟁 조건만 "아니오"다.

070번 · 로그 기반 회복(REDO/UNDO)

제26회(2025년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1) 로그 레코드의 구조​

회복을 위해 DBMS는 모든 변경을 로그(log) 에 순서대로 기록한다. 이 문항의 표기는 다음과 같다.

로그 레코드의미
(start, T)트랜잭션 T가 시작됨
(T, D, v1, v2)T가 데이터 D를 v1(변경 전) 에서 v2(변경 후) 로 바꿈
(commit, T)T가 성공적으로 완료됨
(abort, T)T가 철회됨
(checkpoint)검사점. 이 시점에 버퍼의 변경 내용을 디스크에 반영

(T, D, v1, v2) 처럼 변경 전 값(v1)과 변경 후 값(v2)을 함께 기록하므로 UNDO와 REDO를 모두 수행할 수 있다.

2) 즉시 갱신(immediate update)​

기법커밋 전 디스크 반영필요한 회복 연산
즉시 갱신(immediate update)허용됨 (커밋 전에도 디스크에 쓸 수 있음)UNDO + REDO 둘 다
지연 갱신(deferred update)금지 (커밋 후에만 반영)REDO만 (UNDO 불필요)

즉시 갱신에서는 커밋하지 않은 트랜잭션의 변경이 이미 디스크에 반영되어 있을 수 있으므로 반드시 UNDO가 필요하다. 이 문항은 즉시 갱신이므로 UNDO와 REDO를 모두 고려해야 한다.

3) WAL(Write-Ahead Logging) 규약​

데이터를 디스크에 쓰기 전에, 그 변경을 기록한 로그를 먼저 디스크에 써야 한다.

이 규약 덕분에 장애 후 로그만 읽으면 어떤 변경이 어디까지 진행되었는지 복원할 수 있다.

4) 검사점(checkpoint)의 역할​

검사점 시점에 DBMS는 다음을 수행한다.

  1. 로그 버퍼의 모든 레코드를 디스크에 강제 기록
  2. 수정된 데이터 버퍼(dirty page)를 디스크에 강제 기록
  3. (checkpoint) 레코드를 로그에 기록 (실제 구현에서는 검사점 시점에 활성 상태인 트랜잭션 목록을 함께 기록)

효과: 검사점 이전에 커밋을 완료한 트랜잭션의 변경은 이미 디스크에 안전하게 반영되어 있으므로 REDO 대상에서 제외할 수 있다. 회복 시 로그 전체를 처음부터 읽지 않아도 되어 회복 시간이 크게 단축된다.

5) REDO 대상과 UNDO 대상 판별​

장애 발생 시점을 기준으로 트랜잭션을 분류한다.

트랜잭션 상태처리이유
검사점 이전에 커밋 완료처리 불필요변경이 이미 디스크에 반영됨
검사점 이후에 커밋 완료REDO(변경 후 값 v2 재적용)커밋했으므로 지속성(durability) 보장 필요. 버퍼에만 있다 사라졌을 수 있음
커밋하지 못하고 장애 발생(활성 상태)UNDO(변경 전 값 v1로 복원)원자성(atomicity) 보장. 부분 반영을 되돌려야 함

6) 회복 절차와 방향​

단계스캔 방향대상적용 값
분석(analysis)검사점 → 로그 끝전체REDO 리스트와 UNDO 리스트 작성
REDO앞 → 뒤(정방향)REDO 리스트변경 후 값 v2
UNDO뒤 → 앞(역방향)UNDO 리스트변경 전 값 v1

UNDO를 역방향으로 하는 이유는 같은 데이터가 여러 번 갱신되었을 때 가장 오래된 원래 값까지 되돌리기 위해서다. REDO를 정방향으로 하는 이유는 최종 갱신 결과를 남기기 위해서다.

상세 풀이​

[1단계] 로그를 시간순으로 정리​

순번로그 레코드내용
1(start, T1)T1 시작
2(T1, A, 10, 15)T1: A를 10 → 15
3(start, T2)T2 시작
4(T2, B, 5, 7)T2: B를 5 → 7
5(commit, T1)T1 커밋 완료
6(checkpoint)검사점 — 여기까지의 변경이 디스크에 반영됨
7(start, T3)T3 시작
8(T3, C, 8, 9)T3: C를 8 → 9
9(T2, A, 15, 20)T2: A를 15 → 20
10(T3, D, 12, 14)T3: D를 12 → 14
11(commit, T3)T3 커밋 완료
—*system crash*장애 발생

[2단계] 트랜잭션 분류 (분석 단계)​

트랜잭션시작커밋검사점과의 관계처리
T1순번 1순번 5검사점 이전에 커밋처리 불필요(이미 디스크 반영)
T2순번 3없음검사점 시점에 활성, 장애 시까지 미커밋UNDO
T3순번 7순번 11검사점 이후에 커밋REDO
REDO 리스트 = { T3 }
UNDO 리스트 = { T2 }
T1 = 처리 없음 (검사점으로 이미 안전)

[3단계] REDO 수행 (정방향, 변경 후 값 v2 적용)​

T3의 갱신 로그를 순번이 작은 것부터 재적용한다.

순번로그연산결과
8(T3, C, 8, 9)C ← 9 (v2)C = 9
10(T3, D, 12, 14)D ← 14 (v2)D = 14

[4단계] UNDO 수행 (역방향, 변경 전 값 v1 복원)​

T2의 갱신 로그를 순번이 큰 것부터 거꾸로 되돌린다.

순번로그연산결과
9(T2, A, 15, 20)A ← 15 (v1)A = 15
4(T2, B, 5, 7)B ← 5 (v1)B = 5

순번 9를 먼저 되돌려 A가 20에서 15로 복원된다. 이 15는 커밋된 T1이 남긴 정당한 값이므로 여기서 멈추는 것이 옳다.

[5단계] 각 데이터의 값 변화 추적​

데이터 A

초기 10
 → (순번 2)  T1이 15로 변경        ← T1은 커밋됨. 검사점으로 디스크 반영 완료
 → (순번 9)  T2가 20으로 변경      ← T2는 미커밋
 → [UNDO]    15로 복원
최종 A = 15

데이터 B

초기 5
 → (순번 4)  T2가 7로 변경          ← T2는 미커밋 (변경은 검사점에서 디스크에 반영됨)
 → [UNDO]    5로 복원
최종 B = 5

검사점이 T2의 변경(B = 7)을 디스크에 밀어 넣었더라도, T2가 커밋하지 못했으므로 반드시 되돌려야 한다. 즉시 갱신 기법에서 UNDO가 필요한 이유가 바로 이것이다.

데이터 C

초기 8
 → (순번 8)  T3가 9로 변경          ← T3는 커밋됨 (검사점 이후)
 → [REDO]    9로 재적용
최종 C = 9        ← 보기 ③은 8이라고 했으므로 틀림

데이터 D

초기 12
 → (순번 10) T3가 14로 변경         ← T3는 커밋됨
 → [REDO]    14로 재적용
최종 D = 14

[6단계] 최종 상태와 보기 대조​

데이터복구 후 올바른 값근거보기일치 여부
A15T1 커밋값 유지 + T2 UNDO① A : 15일치
B5T2 UNDO② B : 5일치
C9T3 REDO③ C : 8불일치
D14T3 REDO④ D : 14일치

"틀린 것"을 묻고 있으므로 정답은 ③.

보기별 판정​

보기판정근거
① A : 15오답 보기(값이 맞음)T1(커밋)이 만든 15가 유지되고, T2(미커밋)의 20은 UNDO로 15로 복원
② B : 5오답 보기(값이 맞음)T2가 미커밋이므로 UNDO하여 변경 전 값 5로 복원
③ C : 8정답 보기(값이 틀림)T3가 커밋되었으므로 REDO로 9가 되어야 한다
④ D : 14오답 보기(값이 맞음)T3가 커밋되었으므로 REDO로 변경 후 값 14 적용

오답 이유​

  • ③ 이 틀린 이유: C를 갱신한 것은 T3((T3, C, 8, 9))이고, T3는 장애 직전에 (commit, T3) 로 커밋을 완료했다. 커밋된 트랜잭션의 결과는 지속성(durability) 원칙에 따라 반드시 보존되어야 하므로, 회복 관리자는 T3를 REDO 리스트에 넣고 변경 후 값인 9를 재적용한다. 따라서 복구 후 C는 9이지 8이 아니다. 8이라고 답하려면 T3가 UNDO 대상이어야 하는데, T3는 커밋했으므로 결코 UNDO 대상이 될 수 없다. 이 보기는 "장애가 났으니 진행 중이던 작업은 모두 취소된다"는 막연한 직관을 노린 함정이다. 실제 기준은 장애 시점이 아니라 커밋 여부다.
  • ①이 옳은 이유: A는 두 번 갱신되었다. T1이 10 → 15로 바꾸었고(커밋됨), 이후 T2가 15 → 20으로 바꾸었다(미커밋). T2가 UNDO 대상이므로 (T2, A, 15, 20) 의 변경 전 값인 15로 되돌린다. 이때 15는 커밋된 T1이 남긴 값이므로 더 이상 되돌리지 않고 여기서 멈춘다. 주의할 점은 T1까지 UNDO하여 10으로 만들면 안 된다는 것이다. 커밋된 트랜잭션의 결과를 취소하는 것은 지속성 위반이다. 같은 데이터에 여러 트랜잭션의 갱신이 겹칠 때 어디까지 되돌릴지 정확히 판단해야 하는 부분이다.
  • ②가 옳은 이유: B를 갱신한 T2는 (commit, T2) 로그가 끝내 나타나지 않았다. 장애 시점에 활성 상태였으므로 UNDO 대상이고, (T2, B, 5, 7) 의 변경 전 값 5로 복원된다. 한 가지 짚어둘 점은 B의 갱신이 검사점 이전에 일어나 값 7이 이미 디스크에 기록되었을 가능성이 높다는 것이다. 그럼에도 불구하고 미커밋 트랜잭션이므로 되돌려야 하며, 이것이 즉시 갱신 기법에서 UNDO가 필수인 이유다. 지연 갱신이었다면 애초에 7이 디스크에 반영되지 않았을 것이다.
  • ④가 옳은 이유: D를 갱신한 (T3, D, 12, 14) 역시 커밋된 T3의 작업이므로 REDO 대상이다. 변경 후 값 14를 재적용한다. C와 완전히 같은 논리이며, C(보기 ③)와 D(보기 ④)의 처리가 달라야 할 이유는 전혀 없다. 두 보기가 같은 트랜잭션의 갱신을 다루면서 한쪽만 변경 전 값을 제시했다는 점만 알아차려도, ③이 틀렸음을 빠르게 짚어낼 수 있다.

핵심 정리​

  • 판단 기준은 오직 커밋 여부다. (commit, T) 로그가 있으면 REDO(변경 후 값 v2), 없으면 UNDO(변경 전 값 v1). 장애 시점에 얼마나 가까웠는지는 무관하다.
  • 검사점 이전에 커밋한 트랜잭션(T1)은 REDO 대상에서 제외된다. 검사점에서 이미 디스크에 반영되었기 때문이며, 이것이 검사점이 회복 시간을 줄여 주는 원리다.
  • 즉시 갱신 + 검사점 조합에서도 미커밋 트랜잭션은 반드시 UNDO해야 한다. 검사점이 T2의 변경(B = 7)을 디스크에 밀어 넣었더라도 커밋하지 않았으므로 5로 되돌린다.
  • REDO는 정방향, UNDO는 역방향으로 스캔한다. 한 데이터가 여러 번 갱신된 경우(A: 10 → 15 → 20) UNDO는 미커밋 트랜잭션의 변경까지만 되돌리고, 커밋된 트랜잭션이 남긴 값(15)에서 멈춘다.
  • 이 문항의 최종 값: A = 15, B = 5, C = 9, D = 14.

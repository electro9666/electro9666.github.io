030번 · 클래스 다이어그램을 Java 소스코드로 옮기기

제26회(2025년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. UML 클래스 다이어그램의 서체·장식 규칙​

UML은 글자의 모양(서체·밑줄) 자체에 의미를 부여한다. 이것이 이 문항의 핵심이다.

표기의미Java 대응
이탤릭체 클래스명추상 클래스(abstract class)abstract class
이탤릭체 연산명추상 연산(abstract operation)abstract 메서드
밑줄 그은 속성/연산분류자 범위(classifier scope) = 클래스 변수·클래스 메서드static
밑줄 없는 속성/연산인스턴스 범위(instance scope)인스턴스 필드·메서드
«interface» 스테레오타입인터페이스interface

2. 가시성(visibility) 기호​

기호가시성Java
-privateprivate
+publicpublic
#protectedprotected
~package(제한자 없음)

3. 관계선의 화살표 머리와 선 종류​

표기관계Java 대응
실선 + 속이 빈 삼각형일반화(Generalization) = 상속extends
점선 + 속이 빈 삼각형실체화(Realization) = 인터페이스 구현implements
실선 + 열린 화살표연관(Association)참조 필드
점선 + 열린 화살표의존(Dependency)지역변수·매개변수 사용
속이 빈 마름모 / 채워진 마름모집합(Aggregation) / 합성(Composition)참조 필드

삼각형의 방향: 삼각형은 부모(상위) 쪽에 붙는다. 자식 ──▷ 부모 로 읽는다.

4. 속성 제약(property modifier) {...}​

속성 뒤 중괄호 안의 표기는 UML의 속성 제약이다.

제약의미Java 대응
{readOnly}생성 후 값을 변경할 수 없음final
{ordered} / {unordered}다중값의 순서 유지 여부List / Set
{unique} / {nonunique}중복 허용 여부Set / List
{union}, {subsets}, {redefines}파생·부분집합·재정의 관계—

5. 속성 표기의 전체 문법​

[가시성] 이름 : 타입 [다중성] [= 초기값] [{속성 제약}]

예: - attr1 : int {readOnly} ⇒ private final int attr1;

6. Java 키워드 정리​

키워드의미
extends클래스(추상 클래스 포함)를 상속
implements인터페이스를 구현
final (필드)한 번 초기화되면 재대입 불가 — 읽기 전용
static (필드)인스턴스가 아닌 클래스에 소속되어 모든 인스턴스가 공유

문제​

정답​

④

정답 도출에 관한 참고: 이 문항은 보기가 표 안의 코드 블록으로 조판되어 있어 공식 문제지(정답 포함본)에도 정답 표기가 남아 있지 않다. 아래 정답은 원본 문제 이미지를 직접 판독한 뒤 UML 표기 규칙을 적용해 도출한 것이며, 판독 근거와 도출 과정을 상세 풀이에 모두 밝힌다.

상세 풀이​

1단계 — 이미지에서 다이어그램을 정확히 판독한다​

원본 이미지(images/q030.png)의 상단 클래스 다이어그램에서 다음 네 가지를 확인했다.

#판독 내용이미지상의 근거
1Class1의 이름이 이탤릭체로 기울어져 있다왼쪽 상자의 Class1이 굵은 기울임꼴. 오른쪽 Class2는 곧은 글씨체로 대비됨
2두 클래스는 실선 + 속이 빈(흰) 삼각형으로 연결되고, 삼각형은 Class1 쪽에 붙어 있다선이 끊김 없는 실선이며, 화살표 머리가 채워지지 않은 삼각형
3첫 번째 속성이 - attr1 : int **{readOnly}** 이다속성명 뒤에 중괄호 제약 {readOnly} 표기. 밑줄 없음
4두 번째 속성 - attr2 : int 는 밑줄이 그어져 있다attr2: int 전체에 언더라인. 제약 표기는 없음

두 속성 모두 앞에 가시성 기호 - 가 붙어 있으므로 private이다.

2단계 — 판독 결과를 Java 문법으로 변환한다​

판독UML 규칙Java 변환
Class1 이탤릭이탤릭 클래스명 = 추상 클래스Class1은 인터페이스가 아니라 abstract class
실선 + 빈 삼각형, 삼각형이 Class1 쪽일반화(상속), Class2가 자식class Class2 **extends** Class1
- attr1 : int {readOnly}- = private, {readOnly} = 변경 불가private **final** int attr1;
- attr2 : int (밑줄)- = private, 밑줄 = 분류자 범위private **static** int attr2;

3단계 — 조합한 정답 코드​

class Class2 extends Class1 {
  private final int attr1;
  private static int attr2;
}

4단계 — 보기와 대조​

보기상속 키워드attr1attr2일치 여부
①extends ✅private int ❌ (final 누락)private int ❌ (static 누락)2개 불일치
②implements ❌private int ❌ (final 누락)private static int ✅2개 불일치
③implements ❌private final int ✅private int ❌ (static 누락)2개 불일치
④extends ✅private final int ✅private static int ✅3개 모두 일치

세 가지 판정 요소(상속 키워드 / {readOnly} → final / 밑줄 → static)를 모두 만족하는 보기는 ④ 하나뿐이다.

5단계 — 도출의 확실성 점검​

이 문항은 정답 표기가 소실되었으나, 다음 이유로 ④ 이외의 답이 성립할 여지가 없다.

  1. 상속 키워드: 선이 실선이고 삼각형이 비어 있으며 Class1이 이탤릭(추상 클래스) 이다. 점선이었다면 실체화(implements)이겠지만 이미지상 명백한 실선이다. 또한 Class1에 «interface» 스테레오타입이 없고 이탤릭으로만 표기되었으므로 인터페이스가 아닌 추상 클래스이며, Java에서 추상 클래스는 extends로만 상속한다. ⇒ ②·③ 탈락 확정.
  2. {readOnly}: UML 명세에서 readOnly는 값의 재대입을 금지하는 제약이고, Java에서 이에 직접 대응하는 것은 final 필드다. ⇒ ①·② 탈락 확정.
  3. 밑줄: UML에서 밑줄은 오직 분류자 범위(static)를 뜻하며 다른 해석이 없다. ⇒ ①·③ 탈락 확정.

세 근거가 각각 서로 다른 두 보기를 배제하여 교집합으로 ④만 남는다. 네 개의 보기가 extends/implements × final 유무 × static 유무 를 조합해 만들어졌다는 구성 자체가, 출제 의도가 UML 표기 3요소(이탤릭·빈 삼각형 실선·밑줄·{readOnly})를 Java 키워드로 정확히 매핑할 수 있는가임을 보여 준다.

보기별 판정​

보기판정근거
① extends / int attr1 / int attr2❌ 오답상속 키워드는 맞으나 {readOnly} → final 과 밑줄 → static 을 둘 다 반영하지 못함
② implements / int attr1 / static int attr2❌ 오답실선+빈 삼각형은 extends인데 implements로 잘못 옮겼고, {readOnly} → final 누락
③ implements / final int attr1 / int attr2❌ 오답final은 맞으나 implements가 틀렸고 밑줄 → static 누락
④ extends / final int attr1 / static int attr2✅ 정답이탤릭(추상 클래스) + 실선·빈 삼각형 = extends, {readOnly} = final, 밑줄 = static 3요소 모두 정확

오답 이유​

① class Class2 extends Class1 { private int attr1; private int attr2; } — 관계선 해석(extends)만 맞고 속성의 장식 표기를 전부 무시한 보기다. 다이어그램은 attr1에 {readOnly} 제약을, attr2에 밑줄을 명시했는데, 이 코드는 두 속성을 모두 평범한 인스턴스 필드로 선언했다. 이렇게 되면 attr1이 생성 후에도 자유롭게 변경 가능해지고({readOnly} 위반), attr2가 인스턴스마다 별도로 존재하게 되어(분류자 범위 위반) 다이어그램이 규정한 제약을 전혀 표현하지 못한다. "클래스명 밑줄·중괄호는 장식일 뿐"이라고 넘기면 고르게 되는 보기다.

② class Class2 implements Class1 { private int attr1; private static int attr2; } — 밑줄 → static 하나만 맞고 나머지 둘이 틀렸다.

  • implements가 틀린 이유: Java에서 implements는 인터페이스를 구현할 때만 쓴다. UML에서 인터페이스 구현(실체화)은 점선 + 빈 삼각형으로 그리고, 인터페이스에는 보통 «interface» 스테레오타입을 붙인다. 이미지의 연결선은 실선이며 Class1은 스테레오타입 없이 이탤릭체로만 표기되어 있으므로 추상 클래스다. 추상 클래스는 extends로 상속한다.
  • private int attr1이 틀린 이유: {readOnly}를 반영하지 않아 final이 빠졌다.

③ class Class2 implements Class1 { private final int attr1; private int attr2; } — {readOnly} → final 하나만 맞고 나머지 둘이 틀렸다. implements 오류는 ②와 같은 이유다. 추가로 attr2의 밑줄을 놓쳐 static을 빠뜨렸다. UML에서 밑줄은 오직 "분류자 범위(classifier scope)", 즉 인스턴스가 아니라 클래스 자체에 소속된 멤버를 의미하며 Java의 static에 1:1로 대응한다. 밑줄을 단순 강조 표시로 오해하면 이 보기를 고르게 된다.

④ — 정답 보기 — 다이어그램의 네 가지 표기(이탤릭 클래스명, 실선+빈 삼각형, {readOnly}, 밑줄)를 모두 올바른 Java 키워드(abstract한 부모를 extends, final, static)로 옮겼다. 참고로 private final int attr1; 은 선언 시점에 초기화하지 않았으므로 생성자에서 반드시 초기화해야 컴파일된다(blank final). 시험 보기에서는 생성자를 생략했을 뿐 문법 판단에는 영향이 없다.

핵심 정리​

  • UML 표기 → Java 매핑 4종: 이탤릭 클래스명 = abstract class, 실선 + 빈 삼각형 = extends, 점선 + 빈 삼각형 = implements, 밑줄 = static, {readOnly} = final.
  • 삼각형은 항상 부모 쪽에 붙는다. 자식 ──▷ 부모.
  • 가시성 기호 -=private, +=public, #=protected, ~=package.
  • 본 문항은 extends/implements × final × static 세 축으로 보기를 구성했으므로, 세 축을 각각 독립적으로 판정하면 ④만 남는다.
  • 이 문항처럼 정답 표기가 없는 경우에도, 표기 규칙이 일의적(一義的) 이면 답은 유일하게 확정된다. 실선/점선과 밑줄 유무를 원본 이미지에서 직접 확인하는 것이 관건이다.

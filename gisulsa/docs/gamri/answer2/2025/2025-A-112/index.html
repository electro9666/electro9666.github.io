112번 · 데이터베이스 암호화 방식(API·Plug-In·Hybrid)

제26회(2025년) 정보시스템감리사 A형 — 보안

사전 지식​

DB 암호화 방식의 분류 기준​

DB 암호화 솔루션은 암·복호화 모듈이 어디에 설치되고 누가 호출하는가에 따라 구분한다. 이 기준만 확실히 잡으면 모든 변형 문제를 풀 수 있다.

구분모듈 설치 위치호출 주체응용 프로그램 수정DB 서버 부하
API 방식애플리케이션(WAS) 서버 — 라이브러리 형태응용 프로그램이 직접 호출필요(전체 또는 일부)낮음 (WAS가 연산 부담)
Plug-In 방식DB 서버 — 패키지/에이전트 형태DBMS가 트리거·뷰·함수로 자동 처리최소화높음 (DB 서버가 연산 부담)
Hybrid 방식양쪽구간별로 선택부분적분산
(참고) TDEDBMS 커널 내장DBMS 엔진없음중간, 컬럼 단위 제어 약함
(참고) 파일 암호화OS 파일 계층OS/커널 드라이버없음중간, 컬럼 단위 제어 불가

방식별 특징 상세​

API 방식

  • 암·복호화 라이브러리를 애플리케이션 서버에 두고, 소스 코드에서 encrypt()·decrypt()를 직접 호출한다.
  • 연산이 WAS에서 일어나므로 DB 서버 성능에 주는 영향이 작다. WAS는 수평 확장이 쉬워 확장성도 유리하다.
  • 대신 암호화 대상 컬럼을 다루는 모든 SQL과 로직을 수정해야 하므로 구축 공수와 기간이 크다. 레거시 시스템에서는 이 비용이 도입 장벽이 된다.

Plug-In 방식

  • 암·복호화 모듈을 DB 서버에 설치하고, 원본 테이블을 감싸는 뷰(View)와 트리거, 사용자 정의 함수로 암·복호화를 자동 수행한다.
  • 응용 프로그램은 기존 SQL을 거의 그대로 쓸 수 있어 애플리케이션 수정이 최소화된다. 도입이 빠르다.
  • 다만 암·복호화 연산이 DB 서버 CPU를 소모하므로 DB 서버 부하가 커지고, 대량 조회·배치 처리 시 성능 저하가 나타나기 쉽다. 인덱스 활용도 제약을 받는다.

Hybrid(혼합) 방식

  • 두 방식의 장점을 결합한다. DB 서버 부하가 걱정되는 대용량 트랜잭션·배치 구간은 API 방식으로 WAS에서 처리하고, 수정 부담이 큰 일반 업무 구간은 Plug-In 방식으로 무수정 적용하는 식으로 구간을 나눈다.

암기 포인트​

  • API = Application 쪽 = 라이브러리 = 소스 수정 필요 = DB 부하 적음
  • Plug-In = DB 쪽 = 에이전트/트리거 = 소스 수정 최소 = DB 부하 큼

상세 풀이​

"가장 적절하지 않은 것"을 고르는 문항이므로, 틀린 설명을 담은 보기가 정답 보기가 된다.

  1. ① "Plug-In 방식은 DB 서버에 암복호화 모듈이 설치되는 방식으로, 구축 시 응용 프로그램의 수정을 최소화할 수 있다." → Plug-In의 정의 그대로다. DB 서버에 모듈을 두고 뷰·트리거로 자동 처리하므로 애플리케이션 수정이 최소화된다. 옳다.
  2. ② "API 방식은 DB 서버에 영향을 주지 않아 성능 저하는 적은 편이지만, 응용 프로그램 전체 또는 일부의 수정이 필요하다." → API 방식의 장단점을 정확히 서술했다. 옳다.
  3. ③ "Plug-In 방식은 암복호화 모듈이 라이브러리 형태로 각 애플리케이션 서버에 설치되고, 응용 프로그램에서 해당 모듈을 호출하는 방식이다." → 설명 내용이 API 방식의 정의다. 주어만 Plug-In으로 바꿔 놓은 전형적인 정의 뒤바꾸기 함정이다. 틀렸다.
  4. ④ "하이브리드 방식에서는 대용량 트랜잭션 처리에 Plug-In 방식을 사용하고, 성능 저하가 발생할 수 있는 부분은 API 방식을 사용한다." → 하이브리드의 구간 분리 전략을 서술한 것으로, 성능 민감 구간을 API로 빼는 취지에 부합한다. 옳다.

③이 ②와 정면으로 모순된다는 점만 알아채도 답을 고를 수 있다. ②가 이미 "API = 애플리케이션이 호출, 소스 수정 필요"라고 못 박고 있으므로, 같은 설명을 Plug-In에 붙인 ③은 동시에 참일 수 없다.

따라서 정답(적절하지 않은 보기)은 ③이다.

보기별 판정​

보기판정근거
①오답 보기(옳은 설명)Plug-In은 DB 서버에 모듈을 설치하고 뷰·트리거로 자동 처리하므로 응용 프로그램 수정이 최소화된다.
②오답 보기(옳은 설명)API 방식은 WAS에서 암·복호화하므로 DB 서버 부하가 적지만 소스 코드 수정이 수반된다.
③✅ 정답 보기(틀린 설명)"라이브러리 형태로 애플리케이션 서버에 설치되고 응용 프로그램이 호출"하는 것은 API 방식의 설명이다.
④오답 보기(옳은 설명)하이브리드는 구간별로 두 방식을 선택 적용해 수정 부담과 DB 부하를 함께 완화한다.

오답 이유​

"적절하지 않은 것"을 찾는 문항이므로, 아래는 왜 나머지 세 보기가 올바른 설명인지에 대한 근거다.

  • ①이 옳은 이유: Plug-In 방식의 정의는 "DB 서버에 암·복호화 에이전트를 설치"하는 것이다. 원본 테이블은 이름을 바꾸어 감추고 동일한 이름의 뷰를 만들어 SELECT 시 자동 복호화, INSERT/UPDATE 시 트리거로 자동 암호화되게 구성한다. 그 결과 애플리케이션은 기존 SQL을 그대로 유지할 수 있어 수정 최소화가 성립한다.
  • ②가 옳은 이유: API 방식은 암·복호화 연산이 WAS에서 일어나므로 DB 서버 CPU를 쓰지 않는다. 따라서 DB 서버 성능 저하가 적다. 반면 암호화 컬럼을 참조하는 조회·입력 로직마다 라이브러리 호출을 넣어야 하므로 응용 프로그램 전체 또는 일부 수정이 불가피하다. 장단점 서술이 모두 정확하다.
  • ④가 옳은 이유: 하이브리드의 존재 이유가 바로 "한 방식만 쓰면 생기는 약점을 다른 방식으로 메우기"다. DB 서버에 부담을 주는 구간(대용량 조회·배치 등 성능 저하가 우려되는 부분)은 API 방식으로 WAS에 연산을 넘기고, 그 밖의 일반 구간은 Plug-In으로 무수정 적용한다. 보기 ④는 이 구간 분리 전략을 서술한 것이므로 적절한 설명으로 처리된다.
  • ③이 틀린 이유(핵심): Plug-In 방식의 모듈은 DB 서버에 설치되고 DBMS가 뷰·트리거를 통해 스스로 호출한다. 응용 프로그램이 라이브러리를 직접 호출하는 구조가 아니다. 보기 ③이 서술한 "라이브러리 형태 + 애플리케이션 서버 설치 + 응용 프로그램이 호출"은 API 방식의 정의를 그대로 옮겨 온 것이므로 명백히 부적절하다.

핵심 정리​

  • API = 애플리케이션 서버에 라이브러리, 소스 수정 필요, DB 부하 적음 / Plug-In = DB 서버에 에이전트, 소스 수정 최소, DB 부하 큼. 이 대조표만 외우면 정의 뒤바꾸기 함정을 바로 잡아낸다.
  • Plug-In은 뷰·트리거·사용자 정의 함수로 암·복호화를 투명하게 처리해 애플리케이션 무수정을 달성한다.
  • 하이브리드는 성능 민감 구간은 API, 수정 부담 큰 구간은 Plug-In으로 나누어 두 방식의 약점을 상쇄한다.
  • 보기 안에서 같은 설명이 서로 다른 용어에 붙어 모순을 이루면, 그중 하나가 정답 보기일 가능성이 매우 높다.

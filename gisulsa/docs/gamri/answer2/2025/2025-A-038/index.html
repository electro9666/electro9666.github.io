038번 · 파이프-필터 아키텍처 뷰

제26회(2025년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

아키텍처 뷰(View)와 뷰타입​

소프트웨어 아키텍처는 하나의 그림으로 다 표현할 수 없으므로, 관심사에 따라 여러 뷰(view) 로 나누어 기술한다. 대표적으로 SEI의 Views and Beyond 접근에서는 세 가지 뷰타입(viewtype) 을 둔다.

뷰타입관심사대표 스타일(뷰)
모듈 뷰타입정적 구현 단위의 구성분할, 사용, 계층(Layered), 일반화
컴포넌트-커넥터(C&C) 뷰타입실행 시점의 구성 요소와 상호작용파이프-필터, 클라이언트-서버, 피어투피어, 발행-구독, 공유데이터
할당 뷰타입소프트웨어와 환경의 매핑배치(Deployment), 구현, 작업 할당

이 문항의 네 보기는 모두 C&C 뷰타입에 속하는 상호작용 스타일이다. 따라서 "구성 요소들이 실행 중에 어떤 방식으로 데이터를 주고받는가" 가 판별 기준이 된다.

C&C 스타일 4종 비교​

스타일컴포넌트커넥터상호작용 형태전형적 사례
파이프-필터(Pipe and Filter)필터(데이터 변환 처리기)파이프(단방향 데이터 스트림)데이터가 흐름을 따라 순차적으로 변환되며 최종 목적지에 도달컴파일러(어휘→구문→의미→코드 생성), UNIX 셸 파이프, ETL, 스트림 처리
클라이언트-서버(Client-Server)클라이언트, 서버요청/응답 프로토콜클라이언트가 요청하면 서버가 응답(동기, 다대일)웹 브라우저-웹 서버, DB 접속
피어투피어(Peer to Peer)대등한 피어상호 호출 커넥터모든 노드가 클라이언트이자 서버로 대등하게 상호 호출파일 공유 네트워크, 블록체인 노드
발행-구독(Publish-Subscribe)발행자, 구독자이벤트 버스/토픽발행자가 이벤트를 던지면 구독한 대상들이 비동기로 통보받음(발신자와 수신자가 서로를 모름)메시지 브로커(Kafka, MQTT), GUI 이벤트

파이프-필터의 세부 특징​

구성 요소

  • 필터(Filter) — 입력 스트림을 읽어 변환(transform)한 뒤 출력 스트림으로 내보내는 독립 처리 단위. 다른 필터의 존재를 알지 못한다.
  • 파이프(Pipe) — 앞 필터의 출력을 뒤 필터의 입력으로 전달하는 단방향 통로. 버퍼 역할도 한다.

장점

  • 필터 간 결합도가 낮아 재사용·교체·재배열이 쉽다.
  • 필터를 독립 프로세스로 돌려 병렬 처리(파이프라이닝) 가 가능하다.
  • 전체 입출력 동작을 개별 필터 동작의 합성으로 단순 이해할 수 있다.

단점

  • 상태를 공유하기 어렵고, 필터마다 데이터 파싱·직렬화 오버헤드가 발생한다.
  • 대화형(interactive) 처리나 오류 처리에 약하다.

상세 풀이​

제시문의 두 문장을 키워드로 분해한다.

제시문키워드시사점
"데이터 처리가 일련의 흐름을 가지고 있고, 데이터는 이 흐름 상에서 중간에 처리된다."일련의 흐름, 중간 처리데이터가 연속된 단계들을 순차 통과하며, 각 단계가 처리를 담당한다 → 처리 단계 = 필터, 단계 사이의 통로 = 파이프
"흐름에 따른 데이터의 변환이 이루어지고 데이터는 변환이 완료되어 최종 목적지에 다다르게 된다."변환(transform), 최종 목적지변환의 연쇄(transformation chain) 와 단방향 종착점의 존재 → 요청/응답(양방향)이나 이벤트 통보 구조가 아님

판정 절차는 다음과 같다.

  1. 양방향 요청-응답인가? 아니다. 제시문에는 "요청"도 "응답"도 없고 데이터가 한 방향으로 흘러 최종 목적지에 도달한다. → ② 클라이언트-서버 배제.
  2. 대등한 노드끼리 서로 호출하는가? 아니다. 데이터는 앞 단계에서 뒤 단계로만 흐르며 되돌아오지 않는다. → ① 피어투피어 배제.
  3. 이벤트를 발행하고 구독자가 비동기로 받는가? 아니다. "구독", "이벤트", "통지" 같은 표현이 없고, 대신 단계별 변환이 강조된다. → ④ 발행-구독 배제.
  4. 데이터가 순차적 흐름을 따라 단계마다 변환되어 최종 목적지에 도달하는가? 그렇다. 이는 필터가 데이터를 변환하고 파이프가 다음 필터로 전달하는 구조의 정의다. → ③ 파이프와 필터 뷰.

가장 친숙한 예가 컴파일러다. 소스 코드가 어휘 분석 → 구문 분석 → 의미 분석 → 최적화 → 코드 생성 단계를 차례로 통과하면서 매 단계 다른 형태로 변환되고, 마지막에 목적 코드라는 최종 결과물에 도달한다. UNIX 셸의 cat file | grep err | sort | uniq 도 동일한 구조다.

따라서 정답은 ③ 파이프와 필터 뷰(Pipe and Filter View) 다.

보기별 판정​

보기판정근거
① 피어 투 피어 뷰❌ 오답대등한 노드 간 양방향 상호 호출 구조로, 단방향 변환 흐름과 최종 목적지 개념이 없다.
② 클라이언트-서버 뷰❌ 오답요청-응답의 왕복 구조이며, 데이터가 단계마다 변환되며 전진하지 않는다.
③ 파이프와 필터 뷰✅ 정답필터가 데이터를 변환하고 파이프가 다음 필터로 전달해 순차 변환 후 최종 목적지에 도달하는 구조와 정확히 일치한다.
④ 발행-구독 뷰❌ 오답이벤트 기반 비동기 통지 구조로, 발행자는 수신자를 모르며 데이터의 단계적 변환이 핵심이 아니다.

오답 이유​

  • ① 피어 투 피어 뷰(Peer to Peer View) — 모든 노드가 클라이언트이면서 동시에 서버로 동작하여 서로를 대등하게 호출하는 구조다. 중앙 서버 없이 노드들이 직접 연결되며, 각 피어는 서비스를 요청할 수도 제공할 수도 있다. 제시문이 말하는 "흐름 상에서 중간에 처리되고 최종 목적지에 다다른다" 는 단방향 진행 개념이 피어투피어에는 없다. 피어투피어에서는 데이터가 어느 방향으로도 오갈 수 있고 정해진 종착점이 없다.
  • ② 클라이언트-서버 뷰(Client-Server View) — 컴포넌트가 클라이언트와 서버라는 두 역할로 나뉘고, 클라이언트가 요청을 보내면 서버가 그 요청을 처리해 응답을 되돌려 주는 왕복(round-trip) 구조다. 데이터가 여러 단계를 거치며 형태가 바뀌어 가는 변환 연쇄가 아니라, 동일한 요청에 대한 결과를 회신하는 관계다. 제시문에는 요청·응답 개념이 전혀 등장하지 않는다.
  • ④ 발행-구독 뷰(Publish-Subscribe View) — 발행자가 이벤트(토픽) 를 발행하면 그 토픽을 구독한 컴포넌트들이 비동기로 통보받는 구조로, 발행자와 구독자가 서로의 존재를 알 필요가 없다(느슨한 결합). 하나의 이벤트가 여러 구독자에게 동시에 전달되는 다대다 구조가 특징이며, 제시문의 "흐름을 따라 단계적으로 변환되어 하나의 최종 목적지에 도달" 하는 선형 파이프라인과 구조가 다르다. 데이터가 각 구독자에게 도달한 뒤 변환되어 다음 단계로 이어진다는 보장도 없다.

핵심 정리​

  • "데이터가 흐름(flow)을 따라 단계마다 변환(transform)되어 최종 목적지에 도달" = 파이프-필터 뷰. 필터 = 처리·변환 단위, 파이프 = 단방향 전달 통로.
  • 네 보기는 모두 컴포넌트-커넥터(C&C) 뷰타입의 스타일이며, 판별 기준은 상호작용 방식이다: 파이프-필터=단방향 변환 스트림, 클라이언트-서버=요청/응답, 피어투피어=대등한 상호 호출, 발행-구독=이벤트 비동기 통지.
  • 파이프-필터의 대표 사례는 컴파일러의 단계별 처리, UNIX 셸 파이프, ETL·스트림 처리 파이프라인이다. 필터 간 결합도가 낮아 재사용·재배열·병렬 처리에 유리하지만, 상태 공유와 대화형 처리에는 부적합하다.

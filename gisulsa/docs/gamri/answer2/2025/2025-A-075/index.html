075번 · 대표 데이터 저장·교환 포맷의 특징

제26회(2025년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. 데이터 구조의 두 축 — 평면(flat) vs 계층(hierarchical)​

데이터 포맷을 가르는 가장 중요한 기준은 중첩(nesting) 구조를 표현할 수 있는가다.

구분특징대표 포맷
평면(flat/tabular)행·열의 2차원 표. 한 셀에는 원자값 하나CSV, TSV, 고정 길이 레코드
계층(hierarchical/tree)값 안에 다시 객체·배열을 품을 수 있음JSON, XML, YAML
키-값(key-value)키 하나에 값 하나를 대응시키는 사전 구조Redis, DynamoDB 등 KVS

2. 포맷별 상세 비교​

항목CSVJSONXMLKey-Value Store
구조행·열 평면객체/배열 중첩 트리태그 기반 중첩 트리키 → 값 단일 매핑
중첩 표현불가능가능가능값 자체를 문자열/BLOB로 두므로 구조적 표현은 없음
스키마없음(헤더 행 정도)선택(JSON Schema)강함(DTD, XML Schema)없음(스키마리스)
메타데이터없음키 이름만태그·속성·네임스페이스로 풍부없음
용량/파싱가장 가볍고 빠름가벼움태그 반복으로 무거움조회 O(1)에 가까움
주 용도정형 데이터 대량 적재, 스프레드시트 교환웹 API·네트워크 통신문서 저장·교환, 설정, 전자문서 표준캐시, 세션, NoSQL 저장소

3. CSV(Comma-Separated Values)의 한계​

  • RFC 4180이 사실상의 표준이나 구분자(쉼표/탭/세미콜론), 인용 부호, 개행 처리 방식이 구현마다 다르다.
  • 모든 행이 동일한 열 구조를 가진다는 전제 위에 서 있다. 한 셀 안에 또 다른 표나 목록을 넣을 수 없다.
  • 중첩 데이터를 억지로 담으려면 열 이름을 addr.city, items.0.name 처럼 평탄화(flattening) 하거나, 셀 안에 JSON 문자열을 넣는 우회책을 써야 한다. 이는 포맷이 중첩을 지원하는 것이 아니라 포맷 밖에서 인코딩하는 것이다.
  • 자료형 개념이 없어 모든 값이 문자열로 취급되며, 날짜·숫자 해석은 읽는 쪽에 달려 있다.

4. JSON과 XML의 관계​

JSON은 "속성-이름 : 값" 쌍의 집합인 객체와 배열로 구성되며, XML과 마찬가지로 트리 구조를 이룬다. 둘 다 텍스트 기반 교환 포맷이라는 점에서 역할이 겹치지만,

비교JSONXML
표기 부피작음({ }, [ ])큼(여닫는 태그 반복)
속성(attribute) 개념없음(키-값만)있음(요소 + 속성)
주석·네임스페이스없음있음
검증 스키마JSON Schema(선택적)DTD / XML Schema(성숙)
문서 지향성약함(데이터 지향)강함(혼합 콘텐츠 표현 가능)

5. Key-Value Store​

키를 해시하여 값을 즉시 찾는 구조로, 조회 성능이 매우 빠르다. 값의 내부 구조를 DB가 해석하지 않으므로(불투명, opaque) 범위 검색이나 값 조건 검색에는 취약하다. Redis, Memcached, Amazon DynamoDB 등이 대표적이며 NoSQL의 가장 단순한 유형으로 분류된다.

상세 풀이​

"가장 적합하지 않은 것"을 고르는 유형이므로, 정답 보기는 설명에 오류가 있는 보기다.

1단계 — ①, ②, ③ 검증

  • ① Key-Value Store: "키와 값 형태로 저장, 고속 검색, NoSQL에서 많이 사용" → 해시 기반 조회로 O(1)에 가까운 성능을 내고, Redis·DynamoDB 등 NoSQL의 대표 유형이다. 적합.
  • ② JSON: "속성-이름 쌍, 트리 구조, XML과 유사한 역할, 문자열 기반, 네트워크 통신에 자주 사용" → JSON은 {"key": value} 의 속성-이름 쌍 집합이고 객체·배열 중첩으로 트리를 이루며, REST API의 사실상 표준 페이로드다. 적합.
  • ③ XML: "태그로 계층 구조 표현, 문서 형식 데이터 저장·교환에 주로 사용" → 여닫는 태그로 요소를 중첩해 계층을 구성하며 전자문서·설정 파일 교환의 오랜 표준이다. 적합.

2단계 — ④ 검증

④는 두 부분으로 나뉜다.

④의 서술판정
"쉼표 또는 탭으로 데이터를 구분하여 저장"맞음(탭 구분은 TSV로 부르지만 CSV 계열로 묶어 설명하는 것이 통례)
"행과 열 구조를 갖는다"맞음
"정형 데이터 저장에 적합하다"맞음
"중첩 구조를 표현할 수 있다"틀림

CSV는 한 행이 곧 한 레코드이고 각 셀은 원자값 하나만 담는 평면 구조다. 셀 안에 하위 레코드 집합을 담는 문법이 존재하지 않으므로 중첩(계층) 구조를 표현할 수 없다. 중첩이 필요하면 JSON이나 XML을 써야 한다.

3단계 — 결론

CSV에 대해 "중첩 구조를 표현할 수 있다"고 서술한 ④ 가 가장 적합하지 않다.

보기별 판정​

보기판정근거
① Key-Value Store❌ 오답 보기(설명은 적절)키-값 매핑, 해시 기반 고속 조회, NoSQL의 대표 유형이라는 설명이 모두 맞다
② JSON❌ 오답 보기(설명은 적절)속성-이름 쌍 · 트리 구조 · 텍스트 기반 · 네트워크 통신 활용 모두 정확하다
③ XML❌ 오답 보기(설명은 적절)태그를 이용한 계층 구조 표현과 문서 교환 용도가 XML의 본래 성격이다
④ CSV✅ 정답 보기(설명이 부적합)구분자·행열 구조·정형 데이터 적합성은 맞으나 "중첩 구조를 표현할 수 있다"가 틀렸다

오답 이유​

  • ① — Key-Value Store를 "고속 검색이 가능한 구조"라 한 것은 키에 대한 단건 조회(point lookup) 를 말하는 것으로 정확하다. (다만 값 조건 검색이나 범위 질의는 느리다는 점이 함께 기억되어야 한다.) NoSQL 4대 유형(키-값 / 문서 / 컬럼 패밀리 / 그래프) 중 첫 번째에 해당하므로 "NoSQL에서 많이 사용된다"도 옳다.
  • ② — JSON을 "XML과 유사한 역할"이라 한 표현이 어색해 보일 수 있으나, 둘 다 텍스트 기반 계층형 데이터 교환 포맷이라는 점에서 역할이 겹치는 것이 맞다. 문법과 부피는 다르지만 담당하는 기능 영역은 동일하다. "문자열 기반의 데이터 표현 방식"도 JSON이 바이너리가 아닌 텍스트 포맷이라는 사실과 부합한다.
  • ③ — XML은 SGML에서 파생된 문서 마크업 언어로 출발했고, 지금도 전자문서·설정·산업 표준 스키마에서 널리 쓰인다. "태그를 사용하여 계층적 구조의 데이터를 표현"은 XML의 정의 그 자체다.
  • ④(정답 보기) — 앞 세 문장은 CSV의 특징으로 정확하지만 마지막 "중첩 구조를 표현할 수 있다"가 CSV의 본질적 한계를 정반대로 서술했다. CSV는 모든 행이 동일한 열 집합을 갖는 2차원 표만 담을 수 있으며, 값 안에 다시 구조를 넣는 문법이 없다. 실무에서 중첩 JSON을 CSV로 내보낼 때 user.address.city 처럼 열 이름을 평탄화하거나 셀에 JSON 문자열을 밀어 넣는 것은 포맷이 중첩을 지원해서가 아니라 손실을 감수한 우회다. 올바른 서술은 "CSV는 평면적인 행·열 구조만 표현할 수 있어 중첩 구조는 표현할 수 없으며, 중첩이 필요하면 JSON·XML을 사용한다"이다.

핵심 정리​

  • CSV = 평면(flat) 전용. 행·열 2차원 표만 담으며 중첩·계층 구조는 표현할 수 없다. 이 문항의 유일한 판정 포인트다.
  • JSON·XML = 계층(tree) 표현 가능. 중첩 데이터 교환이 필요하면 이 둘을 쓴다. JSON은 가볍고 API 통신에, XML은 스키마·속성·네임스페이스가 필요한 문서 교환에 강하다.
  • Key-Value Store는 키 단건 조회가 매우 빠른 대신 값의 내부를 DB가 해석하지 않아 조건·범위 검색에 약하다.
  • 포맷 비교 문항은 "평면이냐 계층이냐", "스키마가 있느냐", "주 용도가 무엇이냐" 세 가지로 갈래를 잡으면 대부분 풀린다.

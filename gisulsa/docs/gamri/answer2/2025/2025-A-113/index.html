113번 · 웹 취약점 식별 — XSS

제26회(2025년) 정보시스템감리사 A형 — 보안

사전 지식​

Cross Site Scripting(XSS)​

공격자가 웹 애플리케이션에 스크립트를 삽입하고, 그 페이지를 열람한 다른 최종 사용자의 브라우저에서 해당 스크립트가 실행되게 하는 취약점이다. 신뢰 관계가 깨지는 지점은 "사용자 → 웹사이트"이며, 피해자는 사이트를 방문한 다른 사용자다.

유형저장 위치동작
Stored(저장형)서버 DB·게시판삽입된 스크립트가 저장되어, 해당 글을 읽는 모든 사용자에게 실행된다
Reflected(반사형)저장되지 않음URL 파라미터 등에 담긴 스크립트가 응답에 그대로 반사되어 실행된다. 피싱 링크와 결합
DOM based클라이언트서버를 거치지 않고 클라이언트 스크립트가 DOM을 조작하는 과정에서 실행된다

주요 피해는 세션 쿠키 탈취, 세션 하이재킹, 화면 변조, 키로깅, 악성 사이트 리다이렉션이다.

대응: 출력 시 HTML 엔티티 인코딩(&, <, >, ", '), 입력값 화이트리스트 검증, 쿠키에 HttpOnly 속성 부여, CSP(Content Security Policy) 적용.

혼동하기 쉬운 취약점 비교​

취약점정의공격 대상/피해자핵심 구분점
XSS웹앱을 통해 다른 사용자 브라우저에서 임의 스크립트 실행사이트를 방문한 다른 사용자스크립트가 피해자 브라우저에서 실행됨
CSRF인증된 사용자의 권한을 도용해 원치 않는 요청을 수행시킴인증된 사용자의 계정·서버 상태요청 위조이며 스크립트 실행 자체가 목적이 아님
Directory Indexing디렉터리 기본 문서 부재 시 파일 목록이 노출되는 서버 설정 취약점서버의 파일 구조 정보정보 노출, 스크립트 실행과 무관
XPath InjectionXML 문서를 조회하는 XPath 질의에 입력값이 삽입되어 질의 구조가 변조됨XML 데이터 저장소SQL 삽입의 XML 판, 서버 측 질의 변조

XSS와 CSRF의 신뢰 방향이 시험에 자주 나온다.

  • XSS: 사용자가 사이트를 신뢰한다는 점을 악용한다.
  • CSRF: 사이트가 사용자(의 인증 세션)를 신뢰한다는 점을 악용한다.

문제​

정답​

④

상세 풀이​

  1. 제시문의 핵심 어구는 세 가지다. ① "웹 애플리케이션을 사용해서"(공격 경로가 웹앱), ② "다른 최종 사용자의 클라이언트에서"(피해자는 제3의 사용자, 실행 위치는 브라우저), ③ "임의의 스크립트가 실행"(실행되는 것은 스크립트).
  2. 이 세 조건을 모두 만족하는 것은 XSS의 정의다. OWASP와 KISA 「소프트웨어 개발보안 가이드」의 XSS 정의 문장과 거의 일치한다.
  3. ③ CSRF도 "다른 사용자"가 관련되지만, CSRF의 결과물은 위조된 HTTP 요청의 전송이지 피해자 브라우저에서의 임의 스크립트 실행이 아니다. 제시문은 "스크립트가 실행되는 취약점"이라고 명시했으므로 XSS가 더 정확하다.
  4. ①·②는 실행 위치가 서버 측이거나 스크립트 실행과 무관한 정보 노출이므로 제시문과 맞지 않는다.

따라서 정답은 ④이다.

보기별 판정​

보기판정근거
① Directory Indexing❌ 오답웹 서버 설정 미흡으로 디렉터리 내 파일 목록이 노출되는 정보 노출 취약점. 스크립트 실행과 무관.
② XPath Injection❌ 오답XML 데이터를 조회하는 XPath 질의가 변조되는 서버 측 주입 취약점. 실행 위치가 클라이언트가 아니다.
③ CSRF❌ 오답인증된 사용자의 권한으로 원치 않는 요청을 수행시키는 공격. 임의 스크립트 실행이 정의가 아니다.
④ XSS✅ 정답웹 애플리케이션을 통해 다른 최종 사용자의 브라우저에서 임의 스크립트가 실행되는 취약점의 정의 그 자체.

오답 이유​

  • ① Directory Indexing: 웹 서버에서 디렉터리 리스팅 옵션(Apache의 Options Indexes 등)이 켜져 있고 index.html 같은 기본 문서가 없을 때, 브라우저가 해당 디렉터리의 파일 목록을 그대로 보여 주는 설정상의 취약점이다. 백업 파일·소스 파일·설정 파일이 노출되어 후속 공격의 단서가 되는 것이 피해이며, 어떤 스크립트도 실행되지 않는다. 대응은 디렉터리 리스팅 비활성화와 기본 문서 배치다.
  • ② XPath Injection: 사용자 입력을 문자열 연결로 XPath 질의에 끼워 넣을 때, 입력값이 XPath 문법으로 해석되어 질의 조건이 변조되는 취약점이다(SQL 삽입의 XML 버전). 인증 우회나 XML 문서 전체 열람이 피해이며, 변조와 실행이 일어나는 곳은 서버다. 제시문의 "다른 최종 사용자의 클라이언트에서 실행"과 어긋난다.
  • ③ CSRF: 피해자가 이미 로그인한 상태임을 이용해, 공격자가 준비한 페이지가 피해자 브라우저로 하여금 대상 사이트에 위조된 요청(비밀번호 변경, 송금, 게시글 작성 등)을 보내게 하는 공격이다. 핵심은 요청의 위조와 권한 도용이지 "임의 스크립트 실행"이 아니다. 실제로 CSRF는 공격 페이지에 폼과 자동 제출만 있어도 성립하며 대상 사이트 안에서 스크립트가 실행될 필요가 없다. 대응도 XSS와 달리 CSRF 토큰, Referer 검증, SameSite 쿠키, 재인증이다. 다만 XSS가 있으면 CSRF 토큰도 탈취할 수 있어 XSS가 더 강력한 취약점으로 평가된다는 점은 함께 기억할 만하다.

핵심 정리​

  • XSS의 정의 문장은 **"웹 애플리케이션을 통해 다른 최종 사용자의 브라우저에서 임의의 스크립트가 실행된다"**이다. 이 문장 자체가 출제 포인트다.
  • XSS는 사용자가 사이트를 신뢰하는 점을, CSRF는 사이트가 사용자 세션을 신뢰하는 점을 악용한다. 신뢰의 방향으로 구분하라.
  • XSS 대응은 출력 시 HTML 엔티티 인코딩이 핵심이며, HttpOnly 쿠키와 CSP가 보조 수단이다. CSRF 대응은 CSRF 토큰이 핵심으로 서로 다르다.
  • Directory Indexing은 정보 노출, XPath Injection은 서버 측 질의 변조로 실행 주체와 위치가 XSS와 전혀 다르다.

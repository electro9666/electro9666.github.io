065번 · 저장 프로시저와 트리거의 특성 구분

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. 데이터베이스 안에서 실행되는 프로그램들​

애플리케이션 코드가 아니라 DBMS 서버 내부에 저장되어 실행되는 프로그램 객체들이 있다. 이들을 묶어 저장 모듈(stored module) 또는 SQL/PSM(Persistent Stored Module)이라 부른다.

객체호출 방식인자반환값소속
저장 프로시저(stored procedure)CALL / EXECUTE — 명시적 호출IN / OUT / INOUTOUT 인자, 결과 집합스키마에 독립적으로 존재
저장 함수(stored function)식(expression) 안에서 호출IN만반드시 1개 값 반환스키마에 독립적으로 존재
트리거(trigger)자동(암시적) 발화없음없음특정 테이블·뷰에 종속

2. 저장 프로시저(stored procedure)​

CREATE PROCEDURE 급여인상 (IN 사번 INT, IN 비율 DECIMAL, OUT 새급여 DECIMAL)
BEGIN
  UPDATE 직원 SET 급여 = 급여 * (1 + 비율) WHERE 직원번호 = 사번;
  SELECT 급여 INTO 새급여 FROM 직원 WHERE 직원번호 = 사번;
END;

CALL 급여인상(101, 0.05, @결과);     -- 사용자가 직접 호출
특성설명
매개변수IN(입력), OUT(출력), INOUT(양방향)을 선언할 수 있다
호출 주체사용자/애플리케이션이 CALL 로 명시적으로 호출
저장 위치DB 카탈로그(데이터 사전)에 소스와 실행 계획이 저장
컴파일최초 실행 시(또는 생성 시) 컴파일되어 파싱·최적화 결과가 캐시됨 → 재호출 시 빠름
장점네트워크 왕복 감소, 실행 계획 재사용, 비즈니스 로직 중앙화, 권한을 프로시저 단위로 부여 가능

3. 트리거(trigger)​

CREATE TRIGGER 급여이력기록
AFTER UPDATE OF 급여 ON 직원          -- ← 특정 테이블에 '할당'된다
FOR EACH ROW
BEGIN
  INSERT INTO 급여이력 VALUES (OLD.직원번호, OLD.급여, NEW.급여, CURRENT_DATE);
END;

트리거는 ECA(Event–Condition–Action) 규칙으로 설명된다.

요소내용예
Event무엇이 일어났을 때INSERT / UPDATE / DELETE
Condition어떤 조건이면WHEN (NEW.급여 > OLD.급여 * 1.5)
Action무엇을 할 것인가이력 테이블에 기록, 예외 발생 등
특성설명
소속ON 테이블명 으로 특정 테이블 또는 뷰에 할당된다. 그 객체를 DROP 하면 트리거도 함께 사라진다
호출 주체DBMS가 자동으로 발화. 사용자가 CALL 트리거명 으로 부를 수 없다
매개변수없다. 대신 OLD / NEW 전이 변수로 변경 전후 값에 접근
반환값없다. 값을 돌려주는 개념 자체가 없다
발화 시점BEFORE / AFTER / INSTEAD OF(주로 뷰 갱신용)
단위FOR EACH ROW(행 단위) / FOR EACH STATEMENT(문장 단위)
용도무결성 제약 강화, 감사 로그, 파생 컬럼 자동 갱신, 뷰 갱신 지원

4. 두 객체의 정면 비교​

비교 항목저장 프로시저트리거
호출명시적(CALL, EXECUTE)암시적(DML 이벤트 시 자동)
입력 인자받을 수 있음(IN/OUT/INOUT)받을 수 없음
결과 반환가능(OUT 인자, 결과 집합)불가능
특정 테이블 종속아니오 — 독립 객체예 — ON 테이블/뷰
DB에 저장·컴파일예예(단, 정의상 강조점은 프로시저 쪽)
트랜잭션 제어(COMMIT 등)대체로 가능대체로 금지(호출 트랜잭션에 포함)
비활성화해당 없음ALTER TRIGGER ... DISABLE 가능

5. 혼동하기 쉬운 인접 개념​

개념구별 포인트
저장 프로시저 vs 저장 함수함수는 반드시 값을 1개 반환하며 SQL 식 안에서 호출 가능. 프로시저는 CALL 전용
트리거 vs 제약조건(CHECK, FK)제약조건은 선언적이고 최적화기가 활용. 트리거는 절차적이며 복잡한 규칙 표현 가능하나 비용·연쇄 발화 위험
트리거 vs 저장 프로시저트리거 본문에서 프로시저를 호출할 수는 있으나, 트리거 자체는 호출당하는 쪽이 아니라 발화되는 쪽
"DB에 저장된다"프로시저·함수·트리거 모두 해당. 이 문장만으로는 구별되지 않음

문제​

정답​

③

상세 풀이​

이 문항은 <보기> ㄱ~ㄹ 중 저장 프로시저의 특성만을 고르는 문제다. 네 항목을 하나씩 귀속시킨다.

ㄱ. "입력 인자를 받을 수 있고 결과를 돌려줄 수 있다."​

→ 저장 프로시저

CREATE PROCEDURE p(IN a INT, OUT b INT) 처럼 매개변수를 선언하고 CALL p(10, @r) 로 호출해 결과를 받는다. 반면 트리거는 매개변수 선언 자체가 문법에 없고, 값을 반환할 수도 없다. 트리거가 변경 전후 값을 보는 수단은 매개변수가 아니라 OLD / NEW 전이 변수다. 따라서 ㄱ은 두 객체를 가르는 결정적 판별 기준이다.

ㄴ. "테이블이나 뷰에 할당된다."​

→ 트리거

CREATE TRIGGER ... ON 직원 처럼 트리거는 반드시 대상 객체를 지정해 정의된다. 그 테이블이나 뷰에 종속된 자식 객체이므로, 대상을 DROP TABLE 하면 트리거도 함께 제거된다. 저장 프로시저는 어느 테이블에도 매이지 않는 독립 스키마 객체이며, 본문에서 여러 테이블을 자유롭게 다룰 수 있다. "할당된다(assigned to)"는 표현 자체가 트리거 정의문의 ON 절을 가리킨다.

ㄷ. "INSERT, DELETE, UPDATE 명령 실행 시 DBMS에 의하여 수행된다."​

→ 트리거

트리거의 정의 그 자체다. 사용자가 부르는 것이 아니라 DML 이벤트가 발생하면 DBMS가 알아서 발화시킨다. 이 "자동 실행(implicit invocation)" 성질이 트리거를 감사 로그·무결성 강화에 쓰는 이유이며, 동시에 개발자가 실행 흐름을 눈으로 좇기 어렵게 만드는 단점이기도 하다. 저장 프로시저는 반대로 명시적 CALL 없이는 절대 실행되지 않는다.

ㄹ. "데이터베이스에 저장되어 필요시 컴파일되며 데이터베이스에 부속된다."​

→ 저장 프로시저

"stored procedure"라는 이름이 곧 이 특성이다. 프로시저 소스는 DB 카탈로그에 저장되고, 최초 실행 시 파싱·최적화를 거쳐 컴파일된 실행 계획이 캐시되며 이후 호출에서 재사용된다. 이것이 애플리케이션이 매번 SQL 텍스트를 보내는 방식보다 빠른 이유다.

다만 주의할 점이 있다. "DB에 저장된다"는 성질은 트리거에도 해당한다. 그렇다면 ㄹ은 왜 저장 프로시저 쪽으로 분류되는가?

  1. 문항의 구조 — 네 항목 중 ㄴ·ㄷ은 트리거에만 성립하는 배타적 특성이다. 따라서 "저장 프로시저의 특성만 모은 것"에는 ㄴ·ㄷ이 들어갈 수 없고, 남는 후보 조합은 {ㄱ}, {ㄹ}, {ㄱ, ㄹ} 뿐이다. 보기 중 이를 만족하는 것은 ③ ㄱ, ㄹ 하나다.
  2. 용어의 지시성 — "데이터베이스에 저장되어 필요시 컴파일된다"는 문장은 stored procedure의 표준 교과서적 정의문이다. 트리거의 정의문은 "이벤트 발생 시 자동 실행되는 ECA 규칙"이지 "저장·컴파일"이 아니다.

조합 검증​

보기구성각 항목 귀속판정
① ㄱ, ㄴ인자/반환 + 테이블 할당프로시저 + 트리거❌ ㄴ이 트리거 특성
② ㄴ, ㄷ테이블 할당 + 자동 실행트리거 + 트리거❌ 완전히 트리거 쪽 묶음
③ ㄱ, ㄹ인자/반환 + 저장·컴파일프로시저 + 프로시저✅
④ ㄷ, ㄹ자동 실행 + 저장·컴파일트리거 + 프로시저❌ ㄷ이 트리거 특성

보기별 판정​

보기판정근거
① ㄱ, ㄴ오답 보기ㄱ은 맞지만 ㄴ("테이블이나 뷰에 할당")은 트리거의 ON 절 특성
② ㄴ, ㄷ오답 보기ㄴ·ㄷ 둘 다 트리거 특성. 저장 프로시저와는 정반대 묶음
③ ㄱ, ㄹ✅ 정답 보기ㄱ(IN/OUT 인자와 결과 반환)·ㄹ(DB에 저장·컴파일)은 모두 저장 프로시저의 정의적 특성이며, 트리거 고유 특성(ㄴ·ㄷ)을 배제한 유일한 조합
④ ㄷ, ㄹ오답 보기ㄹ은 맞지만 ㄷ("DML 시 DBMS가 자동 수행")은 트리거의 암시적 발화 특성

오답 이유​

  • ①이 틀린 이유: ㄱ은 저장 프로시저의 특성이 맞다. 그러나 ㄴ "테이블이나 뷰에 할당된다"는 CREATE TRIGGER ... ON 테이블명 구문이 말하는 트리거의 종속성이다. 저장 프로시저는 CREATE PROCEDURE 에 ON 테이블 같은 절이 없고, 어떤 테이블도 참조하지 않는 순수 계산 프로시저도 만들 수 있다.

  • ②가 틀린 이유: 두 항목 모두 트리거 특성이다. ㄴ은 트리거의 소속(대상 객체 종속), ㄷ은 트리거의 발화 방식(DML 이벤트 시 자동 실행)으로, 사실상 "트리거의 특성만 모은 것"에 해당하는 보기다. 질문이 "트리거에 해당하는 특성"이었다면 ②가 정답이 되었을 것이다.

  • ③이 맞는 이유: ㄱ은 매개변수와 반환값의 존재로 트리거를 즉시 배제하고, ㄹ은 "stored"라는 이름이 지시하는 저장·컴파일 특성이다. 두 항목 어디에도 테이블 종속성이나 자동 발화가 들어 있지 않아, 트리거 고유 특성을 하나도 포함하지 않는 유일한 조합이다.

  • ④가 틀린 이유: ㄹ은 저장 프로시저 특성이 맞다. 그러나 ㄷ "INSERT, DELETE, UPDATE 명령 실행 시 DBMS에 의하여 수행된다"는 사용자가 부르지 않아도 알아서 실행된다는 뜻으로, 저장 프로시저의 명시적 CALL 호출 방식과 정반대다. 저장 프로시저를 DML 시점에 자동 실행하고 싶다면 그것을 호출하는 트리거를 따로 만들어야 한다.

핵심 정리​

  • 호출 방식이 최우선 판별 기준이다. 저장 프로시저 = 명시적 CALL, 트리거 = DML 이벤트에 의한 자동(암시적) 발화.
  • 트리거는 인자를 받지도, 값을 반환하지도 않는다. 변경 전후 값은 OLD / NEW 전이 변수로 참조한다. 따라서 "입력 인자"·"반환값"이라는 단어가 보이면 무조건 저장 프로시저다.
  • 트리거는 ON 테이블/뷰 로 특정 객체에 종속되며 그 객체가 삭제되면 함께 사라진다. 저장 프로시저는 독립 스키마 객체다.
  • 트리거는 ECA(Event–Condition–Action) 규칙으로 이해하고, BEFORE/AFTER/INSTEAD OF, FOR EACH ROW/FOR EACH STATEMENT 구분을 함께 기억한다.
  • 이 문제의 결정타: ㄴ("테이블·뷰에 할당")과 ㄷ("DML 시 DBMS가 자동 수행")은 명백한 트리거 특성이므로, 이 둘을 하나도 포함하지 않는 조합은 ③(ㄱ, ㄹ)뿐이다.

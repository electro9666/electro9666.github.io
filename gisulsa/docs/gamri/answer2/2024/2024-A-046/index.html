046번 · SOLID 원칙 중 의존관계 역전 원칙(DIP)

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. SOLID 5원칙 한눈에 보기​

Robert C. Martin이 정리한 객체지향 설계의 다섯 원칙이다. 목표는 공통적으로 변경에 강한 구조를 만드는 것이다.

약어원칙한 줄 정의핵심 키워드
SRPSingle Responsibility Principle클래스는 변경의 이유가 하나여야 한다책임, 응집도
OCPOpen/Closed Principle확장에는 열려 있고 변경에는 닫혀 있어야 한다확장, 수정 없이
LSPLiskov Substitution Principle하위 타입은 상위 타입을 대체할 수 있어야 한다치환 가능성, 계약
ISPInterface Segregation Principle클라이언트는 사용하지 않는 메소드에 의존하지 않아야 한다인터페이스 분리, 크기
DIPDependency Inversion Principle고수준·저수준 모듈 모두 추상에 의존해야 한다추상화, 의존 방향

2. DIP의 정식 정의​

DIP는 두 문장으로 이루어진다.

(1) 고수준 모듈(high-level module)은 저수준 모듈(low-level module)에 의존해서는 안 된다. 둘 다 추상(abstraction)에 의존해야 한다. (2) 추상은 구체적인 것(details)에 의존해서는 안 된다. 구체적인 것이 추상에 의존해야 한다.

여기서 "역전(inversion)" 은 화살표 방향이 뒤집힌다는 뜻이다.

구분의존 방향
전통적 계층 구조고수준(업무 정책) → 저수준(DB·파일·네트워크 구현)
DIP 적용 후고수준 → 인터페이스 ← 저수준

전통 구조에서는 DB를 바꾸면 업무 로직까지 고쳐야 한다. DIP를 적용하면 저수준 구현이 인터페이스를 구현하는(implements) 쪽이 되므로, 구현체를 갈아끼워도 고수준 코드는 그대로다.

3. 왜 "추상에 의존"이 이득인가​

관점설명
변경 빈도인터페이스·추상 클래스는 계약이라 자주 바뀌지 않는다. 구체 클래스는 알고리즘·라이브러리·성능 사정으로 자주 바뀐다. 덜 변하는 것에 기대야 파급이 작다
결합도구체 타입을 참조하면 그 타입의 변경이 곧바로 전파된다. 추상 타입 참조는 컴파일 의존성을 끊는다
테스트 용이성인터페이스로 의존하면 테스트에서 Mock/Stub 주입이 가능하다
구현 수단의존성 주입(DI), 팩토리, 서비스 로케이터, Spring의 @Autowired 등이 DIP를 실현하는 기법이다

주의: DIP(원칙)와 DI(의존성 주입, 기법)는 다르다. DI는 DIP를 실현하는 여러 수단 중 하나다.

4. 원칙별 판별 키워드​

문제 지문에서 어떤 단어가 보이면 어떤 원칙인지 정리한 표다.

지문에 등장하는 표현지목되는 원칙
"추상 클래스/인터페이스에 의존한다", "구체 클래스를 직접 참조하지 않는다"DIP
"확장에는 열려 있고 변경에는 닫혀 있다", "기존 코드를 수정하지 않고 기능 추가"OCP
"하위 클래스가 상위 클래스를 대체해도 정상 동작", "사전조건 강화 금지"LSP
"사용하지 않는 메소드를 강제로 구현하게 하지 마라", "인터페이스를 잘게 나눈다"ISP
"클래스가 한 가지 책임만", "변경 이유가 하나"SRP

5. 혼동하기 쉬운 인접 개념​

혼동 쌍구분 기준
DIP vs OCPDIP는 의존의 방향, OCP는 변경 없이 확장 가능한가라는 결과. DIP·LSP는 OCP를 달성하는 수단이므로 함께 등장하지만, 지문이 "무엇에 의존하는가"를 말하면 DIP다
DIP vs ISP둘 다 인터페이스를 다루지만, DIP는 추상 타입을 참조하라(의존 대상의 성격), ISP는 인터페이스를 작게 쪼개라(의존 대상의 크기)
DIP vs DI원칙(principle) vs 구현 기법(technique)
LSP vs 단순 상속LSP는 문법적 상속이 아니라 행위의 계약(behavioral subtyping) 을 요구한다
SRP vs ISPSRP는 클래스의 책임, ISP는 인터페이스의 크기

6. 코드로 보는 DIP​

위반 사례 — 고수준 서비스가 저수준 구현 클래스를 직접 참조한다.

class MySqlOrderRepository { void save(Order o) { /* ... */ } }

class OrderService {                 // 고수준 모듈
    private MySqlOrderRepository repo = new MySqlOrderRepository();  // 구체 클래스에 의존
    void place(Order o) { repo.save(o); }
}

저장소를 다른 DBMS나 메모리 구현으로 바꾸면 OrderService를 고쳐야 하고, 단위 테스트에서 실제 DB 없이는 실행할 수 없다.

DIP 적용 — 양쪽이 모두 인터페이스에 의존하게 만든다.

interface OrderRepository { void save(Order o); }                    // 추상

class MySqlOrderRepository implements OrderRepository { /* ... */ }  // 구체 → 추상에 의존

class OrderService {                 // 고수준 모듈
    private final OrderRepository repo;                              // 추상에 의존
    OrderService(OrderRepository repo) { this.repo = repo; }         // 의존성 주입
    void place(Order o) { repo.save(o); }
}

OrderService → OrderRepository ← MySqlOrderRepository 로 화살표가 가운데 인터페이스를 향해 모인다. 저수준 모듈이 추상을 향해 의존하게 된 이 방향 뒤집힘이 곧 역전(inversion) 이다.

정답​

②

상세 풀이​

"가장 적절한 것"을 고르는 정의 매칭 유형이다. 지문을 두 부분으로 쪼개어 읽는다.

  • 앞부분 — "추상 클래스와 인터페이스는 구체적인 클래스보다 덜 변하기 때문에" → DIP의 근거(rationale). 변경 빈도가 낮은 쪽에 기대라는 논지다.
  • 뒷부분 — "외부에서 해당 클래스를 참조하기 위해서는 가능한 추상 클래스에 의존한다" → DIP의 처방. "의존한다"라는 술어와 "추상"이라는 목적어가 함께 나오는 순간 DIP로 확정된다.

이는 DIP 정의 문장 (2) "추상은 구체에 의존해서는 안 되고, 구체가 추상에 의존해야 한다"를 풀어 쓴 서술이다.

보기를 순서대로 판정한다.

  1. ①ISP — 인터페이스를 얼마나 잘게 나눌 것인가에 관한 원칙이다. 지문에는 인터페이스의 크기·분리에 관한 언급이 전혀 없다. → 아니다.
  2. ②DIP — "구체 클래스가 아니라 추상에 의존하라"는 정의 그 자체다. → 정답.
  3. ③OCP — 확장/변경이라는 대비가 지문에 없다. 지문은 "덜 변한다"는 변경 빈도를 의존 대상 선택의 근거로 들 뿐, "수정 없이 확장"을 말하지 않는다. → 아니다.
  4. ④LSP — 상위/하위 타입의 치환 가능성을 다루는데, 지문에는 상속 계층이나 대체 가능성에 대한 언급이 없다. → 아니다.

보기판정근거
① ISP (Interface Segregation Principle)오답 보기클라이언트가 쓰지 않는 메소드에 의존하지 않도록 인터페이스를 분리하라는 원칙. 지문은 인터페이스 분리를 말하지 않는다
② DIP (Dependency Inversion Principle)✅ 정답 보기"구체가 아닌 추상에 의존하라"는 DIP 정의를 그대로 서술
③ OCP (Open/Closed Principle)오답 보기확장에 열림, 변경에 닫힘에 관한 원칙. 지문의 주제는 확장/변경이 아니라 의존 대상 선택
④ LSP (Liskov Substitution Principle)오답 보기하위 타입의 상위 타입 대체 가능성에 관한 원칙. 지문에 치환 관련 서술이 없다

오답 이유​

  • ①이 틀린 이유: ISP는 "뚱뚱한(fat) 인터페이스를 역할별로 쪼개라"는 원칙으로, 위반 사례는 하나의 인터페이스에 수십 개 메소드를 몰아넣어 구현 클래스가 쓰지도 않는 메소드를 빈 구현으로 채우는 경우다. 지문이 ISP가 되려면 "클라이언트가 사용하는 기능만 담은 인터페이스로 분리한다"처럼 인터페이스의 크기·응집도를 말해야 한다.
  • ②가 맞는 이유: DIP는 의존의 대상을 추상으로 바꾸고, 그 결과 컴파일 시점 의존 방향이 역전되게 하는 원칙이다. 지문의 "구체적인 클래스보다 덜 변한다"는 표현은 DIP를 정당화하는 표준 논거이며, "가능한 추상 클래스에 의존한다"는 표현은 처방 그 자체다.
  • ③이 틀린 이유: OCP는 결과적 성질이고 DIP는 그것을 달성하는 수단이므로 둘은 자주 함께 언급된다. 그러나 지문에는 "기능을 추가할 때 기존 코드를 수정하지 않는다"는 OCP의 핵심 대비가 없다. OCP를 가리키려면 "새 기능은 상속·구현으로 추가하되 기존 클래스는 수정하지 않는다" 같은 서술이어야 한다.
  • ④가 틀린 이유: LSP는 "직사각형-정사각형 문제"처럼 하위 타입이 상위 타입의 계약을 깨뜨리지 않아야 한다는 원칙이다. 지문에 상위/하위 타입 간 대체나 사전·사후조건 이야기가 전혀 없으므로 대응하지 않는다. LSP를 가리키려면 "상위 타입을 사용하는 코드가 하위 타입을 받아도 동일하게 동작해야 한다"는 서술이 필요하다.

핵심 정리​

  • DIP = "추상에 의존하라". 고수준·저수준 모듈이 모두 인터페이스에 의존하고, 구체 클래스가 인터페이스를 구현함으로써 의존 방향이 역전된다.
  • DIP의 근거는 추상은 덜 변하고 구체는 자주 변한다는 사실이며, 실현 기법은 의존성 주입(DI)·팩토리 등이다. 원칙(DIP)과 기법(DI)을 구분해야 한다.
  • 지문 키워드로 원칙을 구분한다: 의존 대상 → DIP / 인터페이스 크기 → ISP / 확장·수정 → OCP / 치환 → LSP / 책임 → SRP.
  • "구체 클래스가 아니라 가능한 추상 클래스·인터페이스에 의존한다"는 문장은 DIP의 정의 문장을 그대로 옮긴 것이며, 이것이 오답을 가려내는 결정타다.

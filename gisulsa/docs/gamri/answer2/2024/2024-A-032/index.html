032번 · 리팩토링 — 매개변수 할당 제거(Remove Assignments to Parameters)

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. 리팩토링이란​

리팩토링(Refactoring) 은 소프트웨어의 겉으로 드러나는 동작(external behavior)은 바꾸지 않으면서 내부 구조를 개선하는 작업이다. Martin Fowler의 Refactoring: Improving the Design of Existing Code 가 사실상의 표준 카탈로그이며, 각 기법은 "어떤 냄새(code smell)가 나면 / 어떤 절차로 / 무엇으로 바꾼다"는 형식으로 정의된다.

리팩토링 문항을 푸는 요령은 단 하나다. "적용 전"과 "적용 후"의 차이 한 가지를 정확히 짚어내고, 그 차이를 일으키는 기법의 이름을 고른다. 비슷해 보이는 기법이 여러 개라도 "무엇이 없어졌는가 / 무엇이 새로 생겼는가"를 대조하면 하나로 좁혀진다.

2. 매개변수(parameter) 취급에 관한 두 가지 전달 방식​

전달 방식의미매개변수에 대입하면
값에 의한 전달(pass by value)인자 값을 복사해 넘김. Java의 원시 타입, C의 일반 변수복사본만 바뀌고 호출자에게는 영향 없음
참조에 의한 전달(pass by reference)변수 자체(또는 주소)를 넘김. C++ 참조, C의 포인터대입이 호출자의 변수까지 바꿈

Java처럼 객체 참조를 값으로 전달하는 언어에서는 더 헷갈린다. param.setX(1) (객체 상태 변경)과 param = new Foo() (참조 자체 재대입)는 결과가 전혀 다르기 때문이다.

바로 이 혼동 때문에 Fowler는 "매개변수에는 대입하지 말라" 는 규칙을 리팩토링으로 만들었다. 매개변수를 읽기 전용으로 유지하면, 코드를 읽는 사람이 "이 매개변수는 메소드 끝까지 넘겨받은 그 값" 이라고 안심하고 가정할 수 있다.

3. Remove Assignments to Parameters의 표준 절차​

동기: 매개변수에 값을 대입하고 있다. 조치: 매개변수 대신 임시 변수(temp) 를 사용한다.

// before
int discount(int inputVal, int quantity) {
    if (inputVal > 50) inputVal -= 2;
    ...
    return inputVal;
}

// after
int discount(int inputVal, int quantity) {
    int result = inputVal;          // ① 임시 변수를 만들어 매개변수 값을 복사
    if (inputVal > 50) result -= 2; // ② 이후의 모든 대입은 임시 변수에만
    ...
    return result;
}

절차는 세 단계다.

  1. 매개변수와 같은 타입의 임시 변수를 선언하고 매개변수 값으로 초기화한다.
  2. 대입 이후에 매개변수를 읽던 곳을 모두 임시 변수로 바꾼다.
  3. 매개변수에 대한 대입문을 임시 변수에 대한 대입문으로 바꾼다.

효과는 두 가지다. (가) 매개변수가 읽기 전용이 되어 의미가 명확해지고, (나) 임시 변수가 분리되어 있으므로 이어서 Extract Method(메소드 추출) 같은 후속 리팩토링을 적용하기 쉬워진다. Java에서는 마무리로 매개변수에 final을 붙여 재대입을 컴파일 단계에서 막기도 한다.

4. 혼동하기 쉬운 인접 기법​

기법적용 대상(냄새)적용 전 → 적용 후핵심 구분점
Split Temporary Variable(임시변수 분리)이미 존재하는 임시 변수 하나가 서로 다른 두 가지 용도로 두 번 이상 대입됨 (temp = 2*(h+w); ... temp = h*w;)용도마다 별개의 임시 변수로 쪼갬출발점이 매개변수가 아니라 임시 변수이고, 용도가 둘 이상이어야 함
Remove Assignments to Parameters(매개변수 할당 제거)매개변수에 대입이 일어남임시 변수를 새로 도입해 매개변수를 읽기 전용화출발점이 매개변수, 결과는 임시 변수 1개 추가
Introduce Explaining Variable(설명 변수 도입)복잡한 수식을 읽기 어려움수식 일부를 이름 있는 임시 변수로 추출대입 문제가 아니라 가독성 문제
Remove Middle Man(중간자 제거)클래스가 위임만 하는 메소드(delegate) 로 가득 참클라이언트가 실제 객체를 직접 호출메소드 내부 변수가 아니라 클래스 간 위임 구조 문제
Replace Conditional with Polymorphism(조건문의 다형성 대체)타입 코드에 따른 switch/if 분기가 반복서브클래스별 오버라이드 메소드로 분산조건 분기 구조를 바꿈

문제​

정답​

②

상세 풀이​

"가장 적절한 것"을 고르는 긍정형 기법 식별 문항이다. 적용 전/후 코드의 차이 한 줄을 찾는 것이 전부다.

  1. 적용 전

    int increment(int inValue, int Qty, int amount) {
      if (inValue > 50) inValue++;     // 매개변수 자체를 증가시킴
      ....

    (원본 지면에는 inValues++ 로 인쇄되어 있으나 선언된 매개변수명은 inValue 이므로 오탈자이며, 문항의 의도는 매개변수 inValue 에 대한 증가 연산이다.)

  2. 적용 후

    int increment(int inValue, int Qty, int amount) {
      int grade = inValue;             // ← 새로 생긴 줄: 임시 변수 도입
      if (inValue > 50) grade++;       // 증가 대상이 매개변수 → 임시 변수로 이동
      ....

  3. 차이 정리

    항목적용 전적용 후
    매개변수 inValue조건 판정 + 대입(증가) 대상조건 판정에만 사용, 읽기 전용
    임시 변수없음grade 새로 생김(inValue 로 초기화)
    증가 연산의 대상매개변수임시 변수

    "매개변수에 대한 대입을 없애고, 그 자리를 새로 만든 임시 변수가 대신한다" — Fowler의 Remove Assignments to Parameters 절차와 1:1로 일치한다. 따라서 ②.

보기별 판정​

보기판정근거
① 임시변수 분리(Split temporary variable)오답 보기쪼갤 기존 임시 변수가 적용 전 코드에 없다. 이 기법은 임시 변수를 1개 → 2개로 나누는 것인데, 여기서는 0개 → 1개로 늘었다
② 매개변수 할당 제거(Remove assignments to parameters)✅ 정답 보기매개변수 inValue 에 대한 증가 연산을 없애고 임시 변수 grade 를 도입해 매개변수를 읽기 전용으로 만들었다
③ 중간자 제거(Remove middle man)오답 보기위임 메소드나 클래스 간 관계가 코드에 전혀 등장하지 않는다
④ 조건 다형성 대체(Replace conditional with polymorphism)오답 보기if 문이 그대로 남아 있고 서브클래스도 만들어지지 않았다

오답 이유​

  • ①이 틀린 이유: 이름이 비슷해 가장 많이 걸리는 함정이다. Split Temporary Variable은 "임시 변수 하나가 서로 다른 두 책임을 겸하고 있을 때" 쓴다. 예를 들어 double temp = 2*(h+w); print(temp); temp = h*w; print(temp); 처럼 temp가 둘레와 넓이 두 용도로 쓰이면 perimeter, area 로 나눈다. 본 문항의 적용 전 코드에는 임시 변수 자체가 하나도 없고, 적용 후에 비로소 grade 가 새로 생겼다. 변수 개수의 변화 방향(0→1 vs 1→2)과 출발점(매개변수 vs 임시 변수)이 모두 다르다.
  • ②가 맞는 이유: 리팩토링 전후의 유일한 구조적 변화가 "매개변수에 대한 대입 → 임시 변수에 대한 대입"이다. 이 변환이 곧 기법의 정의다. 매개변수에 대입하면 값 전달/참조 전달의 의미가 흐려지고, 메소드 중간부터 매개변수의 값이 호출 시점 값과 달라져 코드를 읽는 사람이 인자를 신뢰할 수 없게 되는데, 이 기법이 그 문제를 없앤다.
  • ③이 틀린 이유: Remove Middle Man은 클래스 설계 수준의 기법이다. 예컨대 Person.getManager() 가 내부적으로 department.getManager() 만 호출하는 위임 메소드가 여러 개 쌓였을 때, 클라이언트가 person.getDepartment().getManager() 로 실제 객체를 직접 다루게 바꾼다. 본 문항은 메소드 하나의 지역 변수 수준 변화이므로 대상 자체가 다르다.
  • ④가 틀린 이유: 이 기법을 적용했다면 적용 후 코드에 if (inValue > 50) 이 사라지고 대신 상위 타입과 서브클래스, 오버라이드된 메소드가 나타나야 한다. 그러나 적용 후에도 if 문은 그대로 있다. 오히려 40번 문항의 "(라) 너무 많은 Switch, if 문장"에 대응하는 기법이라는 점을 함께 묶어 기억하면 좋다.

핵심 정리​

  • Remove Assignments to Parameters: 매개변수에 대입이 있으면 같은 타입의 임시 변수를 새로 만들어 그쪽에만 대입하고, 매개변수는 읽기 전용으로 남긴다. Java에서는 마무리로 final 을 붙인다.
  • Split Temporary Variable: 이미 있는 임시 변수 하나가 두 용도로 쓰일 때 용도별로 쪼갠다. 출발점이 임시 변수라는 점이 결정적 차이다.
  • 리팩토링 코드 비교 문항은 "무엇이 새로 생겼고 무엇이 사라졌는가" 만 보면 된다.
  • 적용 전에 임시 변수가 없었고(쪼갤 대상 부재), 대입 대상이 매개변수였다 — 이 두 사실이 ①을 버리고 ②를 택하게 하는 결정타다.

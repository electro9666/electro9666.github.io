104번 · 위험한 형식의 파일 업로드 대응 방안

제25회(2024년) 정보시스템감리사 A형 — 보안

사전 지식​

1. 악성 파일 업로드 공격이 성립하는 조건​

웹셸(webshell) 공격은 다음 세 조건이 모두 충족될 때 성립한다.

조건내용무너뜨리는 대책
ⓐ 업로드 가능서버가 .jsp, .php, .asp 등 실행 가능한 확장자를 받아들임확장자·MIME 화이트리스트 검사
ⓑ 호출 가능저장된 파일에 공격자가 URL로 직접 접근할 수 있음웹 문서 루트 밖에 저장, 파일명·경로 난수화
ⓒ 실행 가능웹 서버/애플리케이션 엔진이 그 파일을 스크립트로 해석·실행함실행 권한 제거, 업로드 디렉터리 핸들러 매핑 해제

세 고리 중 하나만 끊어도 공격은 실패한다. 그래서 실무에서는 세 가지를 모두 적용하는 다층 방어를 권고한다. 반대로 말하면, 어떤 조치가 이 고리를 오히려 연결해 주는지를 보면 부적절한 대책을 바로 골라낼 수 있다.

2. OWASP File Upload Cheat Sheet의 핵심 권고​

OWASP Cheat Sheet Series의 File Upload Cheat Sheet 는 다음을 명시한다.

  • 저장 위치: "Store the files outside the webroot, where only administrative access is allowed." — 업로드 파일은 웹 루트(document root) 밖, 관리 권한으로만 접근 가능한 경로에 보관한다.
  • 파일명: "creating a random string as a filename, such as generating a UUID/GUID, is essential." — UUID/GUID 같은 난수 문자열로 파일명을 재생성한다.
  • 확장자: "List allowed extensions. Only allow safe and critical extensions for business functionality." — 업무에 필요한 안전한 확장자만 허용 목록(화이트리스트) 으로 지정한다.
  • 그 밖에 파일 크기 제한, 매직 바이트(파일 시그니처) 검증, 안티바이러스 스캔, 이미지 재인코딩(re-write), 업로드 사용자 인증·권한 확인 등을 권고한다.

국내에서도 KISA의 웹 취약점 점검·소프트웨어 개발보안 가이드가 동일하게 "업로드 파일은 웹 루트 외부 경로에 저장하고, 다운로드는 별도 스크립트를 통해서만 제공" 하도록 권고한다.

3. '웹 문서 루트 안 vs 밖'이 만드는 차이​

[웹 루트 안에 저장]
  /var/www/html/upload/shell.jsp
  → http://target/upload/shell.jsp  로 직접 호출 가능
  → 웹 컨테이너가 JSP로 해석·실행 → 원격 명령 실행(RCE)

[웹 루트 밖에 저장]
  /data/uploads/9f2c1b7e-4a8d-4f0c-93aa-2b1e7d5c6f11
  → URL 매핑 자체가 없어 직접 호출 불가
  → 다운로드는 download.jsp?id=1234 같은 스크립트가
     권한 검사 후 파일을 읽어 스트림으로 내려 줌

두 번째 방식은 ⓑ(호출 가능)와 ⓒ(실행 가능)를 동시에 끊는다. 게다가 다운로드 스크립트를 경유하므로 접근 권한 검사와 감사 로그를 덧붙일 수 있다. 다만 다운로드 스크립트는 경로 조작(Path Traversal, ../../etc/passwd) 에 취약해지기 쉬우므로, 식별자는 파일 경로가 아니라 DB의 키 값으로 받아야 한다.

4. 확장자 검증 — 화이트리스트가 필요한 이유​

블랙리스트(금지 확장자 목록)는 우회 기법이 끝없이 나온다.

우회 기법예시
대소문자 변형shell.PhP, shell.JsP
이중 확장자shell.jpg.php, shell.php.jpg(특정 설정에서 실행)
널 바이트 삽입shell.php%00.jpg
대체 확장자.php3, .php5, .phtml, .phar, .jspx, .asa, .cer
후행 문자shell.php., shell.php (Windows가 절삭)
설정 파일 업로드.htaccess, web.config 를 올려 임의 확장자를 실행 대상으로 등록

그래서 "허용할 것만 명시" 하는 화이트리스트가 원칙이며, 확장자 검사에 더해 파일 시그니처(매직 바이트) 와 MIME 타입을 함께 확인해야 한다. 단, 클라이언트가 보내는 Content-Type 헤더는 위조 가능하므로 서버 측에서 실제 바이트를 검사해야 한다.

5. 혼동하기 쉬운 인접 개념​

대책끊는 고리단독으로 충분한가
화이트리스트 확장자 검증ⓐ 업로드아니오 — 매직 바이트 위조, 이미지 내 코드 삽입 가능
실행 속성(x) 제거ⓒ 실행(일부)아니오 — CGI가 아닌 모듈/컨테이너 해석 방식(mod_php, 서블릿 컨테이너)은 실행 비트와 무관하게 동작할 수 있음
파일명·경로 난수화ⓑ 호출아니오 — 경로가 노출되면 무력화. 보조 수단
웹 루트 밖 저장ⓑ + ⓒ 동시가장 근본적. 다운로드 스크립트의 경로 조작 방지와 함께 적용
업로드 디렉터리 스크립트 핸들러 해제ⓒ 실행설정 누락·오버라이드 위험 존재

상세 풀이​

"가장 적절하지 않은 것"을 고르는 유형이므로, 오히려 위험을 키우거나 권고에 반하는 조치를 찾는다.

  1. ① 저장된 파일에서 실행 속성(x 권한)을 제거 — 서버 측에서 파일이 직접 실행되는 경로를 줄이는 조치다. OWASP도 파일 실행이 필요한 경우 사전 스캔을 요구할 만큼 실행 가능성 자체를 위험으로 본다. → 적절.
  2. ② 화이트리스트 방식으로 허용된 형식만 업로드 — OWASP의 "List allowed extensions. Only allow safe and critical extensions" 와 정확히 일치한다. 블랙리스트는 우회가 쉬워 부적절하다. → 적절.
  3. ③ 저장 경로를 웹 서버의 문서 디렉터리 내부에 고정 — OWASP의 "Store the files outside the webroot" 와 정반대다. 문서 루트 안에 두면 공격자가 업로드한 웹셸을 URL로 바로 호출할 수 있어 ⓑ·ⓒ 고리가 한꺼번에 열린다. → 부적절 = 정답.
  4. ④ 파일명·경로를 유추 불가능한 임의 문자열로 변경 — OWASP의 "creating a random string as a filename, such as generating a UUID/GUID, is essential" 과 일치한다. 공격자가 업로드 결과물의 위치를 추정하지 못하게 한다. → 적절.

보기별 판정​

보기판정근거
① 실행 속성 제거오답 보기(적절한 설명)저장 파일의 서버 측 직접 실행 경로 차단. 업로드 디렉터리의 스크립트 핸들러 해제와 함께 적용하는 표준 조치
② 화이트리스트 형식 제한오답 보기(적절한 설명)OWASP File Upload Cheat Sheet — "List allowed extensions" (블랙리스트는 대소문자·이중확장자·널바이트로 우회 가능)
③ 문서 디렉터리 내부에 저장 경로 고정✅ 정답 보기(적절하지 않은 설명)OWASP — "Store the files outside the webroot". 내부 저장은 웹셸 직접 호출을 허용해 위험을 키움
④ 파일명·경로 난수화오답 보기(적절한 설명)OWASP — UUID/GUID 등 임의 문자열 파일명 생성 권고

오답 이유​

  • ①이 적절한 이유: 업로드 파일은 데이터일 뿐 프로그램이 아니다. 실행 권한을 남겨 둘 이유가 없으며, CGI 방식이나 OS 명령 경유 실행 경로를 차단한다. 다만 이것만으로는 부족하다 — mod_php나 서블릿 컨테이너처럼 엔진이 파일을 읽어 해석하는 방식은 실행 비트가 없어도 동작할 수 있으므로, 업로드 디렉터리에서 스크립트 핸들러 매핑을 해제하는 설정을 함께 적용해야 한다.
  • ②가 적절한 이유: 금지 목록은 언제나 불완전하다. .php5, .phtml, .jspx, .phar, .htaccess 같은 변종이 계속 생기고, 대소문자·이중 확장자·널 바이트로 쉽게 우회된다. 허용 목록은 업무상 필요한 소수(예: jpg, png, pdf, hwp)만 남기므로 이런 변종을 구조적으로 배제한다.
  • ③이 부적절한 이유: 문서 루트 안에 저장하면 http://target/upload/shell.jsp 형태로 URL 매핑이 자동으로 생긴다. 확장자 검사를 우회해 웹셸이 한 번 올라가면 그대로 원격 명령 실행으로 이어진다. 게다가 "경로가 문서 디렉터리 내부에 고정"이면 공격자가 저장 위치를 쉽게 특정할 수 있어 ④의 난수화 효과까지 약화시킨다. 올바른 서술은 "업로드 파일은 웹 문서 루트 외부의 비공개 경로에 저장하고, 필요한 경우 권한 검사를 수행하는 별도 다운로드 스크립트를 통해서만 제공한다" 이다.
  • ④가 적절한 이유: 공격자는 업로드 후 그 파일을 찾아서 호출해야 공격이 완성된다. 원본 파일명을 그대로 쓰면 위치가 그대로 노출되지만, UUID 등으로 재명명하고 저장 경로를 분산하면 추정이 사실상 불가능해진다. 원본 파일명은 DB에 별도 보관해 다운로드 시 표시용으로만 쓴다.

핵심 정리​

  • 악성 파일 업로드는 ⓐ 업로드 가능 + ⓑ URL 호출 가능 + ⓒ 실행 가능의 세 고리가 모두 이어질 때 성립한다. 하나만 끊어도 막힌다.
  • OWASP File Upload Cheat Sheet 3대 권고 — 웹 루트 밖 저장 / UUID 등 난수 파일명 / 허용 확장자 화이트리스트.
  • 확장자 검사는 화이트리스트 + 매직 바이트(파일 시그니처) 병행. 클라이언트가 보낸 Content-Type은 믿지 않는다.
  • 업로드 파일을 웹 문서 루트 '내부'에 저장하라는 서술은 OWASP 권고와 정반대이며, 웹셸 직접 호출을 허용하는 가장 위험한 설정이다.

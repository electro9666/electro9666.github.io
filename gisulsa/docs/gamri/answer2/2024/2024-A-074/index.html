074번 · WAL에서 AFIM·BFIM이 대비하는 회복 연산

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. 트랜잭션과 ACID — 회복이 필요한 이유​

속성의미보장 수단
원자성(Atomicity)전부 반영 또는 전무 반영UNDO(로그 기반 취소)
일관성(Consistency)제약조건 유지무결성 제약, 트랜잭션 논리
고립성(Isolation)동시 실행이 직렬 실행과 동일잠금(2PL), MVCC
지속성(Durability)커밋된 결과는 장애에도 유지REDO(로그 기반 재적용)

원자성 ↔ UNDO, 지속성 ↔ REDO 라는 대응이 이 문제의 뼈대다.

2. 로그 레코드에 담기는 두 이미지​

DBMS가 데이터 항목 XXX를 갱신할 때 기록하는 갱신 로그는 대략 다음 형태다.

<T_i, X, BFIM, AFIM>
  T_i   : 트랜잭션 식별자
  X     : 갱신 대상 데이터 항목
  BFIM  : Before Image — 갱신 "이전" 값 (old value)
  AFIM  : After  Image — 갱신 "이후" 값 (new value)
이미지뜻담는 값쓰이는 연산왜
BFIM(Before Image)갱신 전 모습old valueUNDO되돌리려면 예전 값이 필요
AFIM(After Image)갱신 후 모습new valueREDO다시 적용하려면 새 값이 필요

기억법: After → Apply again → REDO / Before → Back out → UNDO

3. WAL(Write-Ahead Logging)의 두 규칙​

WAL은 "데이터보다 로그를 먼저 쓴다"는 원칙이며, 구체적으로 두 규칙으로 나뉜다.

규칙내용보장하는 것
① UNDO 규칙변경된 데이터 페이지를 디스크에 쓰기 전에, 그 페이지의 BFIM 로그를 먼저 디스크에 강제 출력(force) 한다미커밋 갱신이 디스크에 나가도 되돌릴 수 있음(원자성)
② REDO 규칙트랜잭션이 커밋하기 전에, 그 트랜잭션의 AFIM 로그를 모두 디스크에 강제 출력한다커밋 후 장애에도 재적용할 수 있음(지속성)

규칙 ①이 없으면 "되돌릴 방법 없이 더러운 데이터가 디스크에 남는" 사태가, 규칙 ②가 없으면 "커밋했다고 응답했는데 결과가 사라지는" 사태가 벌어진다.

4. 버퍼 관리 정책과 UNDO/REDO의 필요성​

WAL이 두 이미지를 모두 남기는 이유는 실무 DBMS가 채택하는 버퍼 정책 때문이다.

정책의미필요해지는 연산
STEAL미커밋 트랜잭션의 더티 페이지도 버퍼에서 쫓아내 디스크에 쓸 수 있음UNDO 필요(← BFIM)
NO-STEAL커밋 전에는 절대 안 씀UNDO 불필요(버퍼 압박 큼)
NO-FORCE커밋 시점에 데이터 페이지를 강제로 디스크에 쓰지 않음REDO 필요(← AFIM)
FORCE커밋 시 즉시 디스크에 기록REDO 불필요(커밋 지연 큼)

상용 DBMS는 성능을 위해 STEAL / NO-FORCE를 택하므로, UNDO와 REDO가 모두 필요하고 따라서 BFIM과 AFIM을 모두 기록한다.

5. 장애 회복 절차 (ARIES 3단계)​

단계하는 일사용하는 이미지
분석(Analysis)마지막 체크포인트부터 로그를 읽어 더티 페이지 테이블·트랜잭션 테이블 복원—
재수행(Redo)로그의 모든 갱신을 다시 적용해 장애 직전 상태를 복원(repeating history)AFIM
취소(Undo)커밋하지 못한 패자(loser) 트랜잭션의 갱신을 역순으로 되돌림BFIM
  • REDO 대상: 체크포인트 이후 커밋 완료했으나 디스크 반영이 불확실한 트랜잭션
  • UNDO 대상: 장애 시점에 커밋하지 못한 진행 중 트랜잭션

6. 혼동하기 쉬운 인접 개념​

용어의미이 문제와의 관계
VOLATILE / PERSISTENT저장장치의 휘발성 여부(주기억장치 vs 디스크)저장 매체 분류 용어일 뿐, 로그 이미지의 용도가 아님
즉시 갱신(immediate update)커밋 전에도 디스크 반영 허용UNDO + REDO 모두 필요
지연 갱신(deferred update)커밋 전까지 디스크 미반영REDO만 필요(NO-UNDO)
그림자 페이징(shadow paging)페이지 사본 교체 방식로그 없이 회복(NO-UNDO/NO-REDO)
체크포인트회복 시작점을 앞당기는 동기화 지점REDO 범위 축소

상세 풀이​

1단계 — 문제 구조 파악​

지문이 요구하는 것은 두 빈칸의 대응이다.

빈칸지문묻는 것
(가)"항목의 AFIM(After Image) 을 기록 … 트랜잭션의 (가)에 대비"AFIM이 필요한 회복 연산
(나)"항목의 BFIM(Before Image) 을 기록 … 트랜잭션의 (나)에 대비"BFIM이 필요한 회복 연산

2단계 — (가) AFIM → REDO​

AFIM은 갱신 이후의 새 값이다.

시나리오: 트랜잭션 TTT가 XXX를 100 → 150으로 바꾸고 커밋했다. NO-FORCE 정책이라 데이터 페이지는 아직 디스크에 안 나갔는데 시스템이 다운됐다.

재기동 후 디스크의 XXX는 여전히 100이다. 커밋했다고 사용자에게 응답했으므로 150이어야 한다. 이때 로그의 AFIM = 150을 읽어 다시 써 넣는 것이 REDO다.

(가)=REDO(지속성 Durability 보장)\text{(가)} = \textbf{REDO} \quad (\text{지속성 Durability 보장})(가)=REDO(지속성 Durability 보장)

3단계 — (나) BFIM → UNDO​

BFIM은 갱신 이전의 옛 값이다.

시나리오: 트랜잭션 TTT가 XXX를 100 → 150으로 바꿨고, STEAL 정책 때문에 이 더티 페이지가 커밋 전에 디스크로 나갔다. 그 상태에서 TTT가 철회(abort) 되거나 시스템이 다운됐다.

디스크의 XXX는 150이지만 TTT는 커밋되지 않았으므로 100으로 되돌려야 한다. 이때 로그의 BFIM = 100을 읽어 복구하는 것이 UNDO다.

(나)=UNDO(원자성 Atomicity 보장)\text{(나)} = \textbf{UNDO} \quad (\text{원자성 Atomicity 보장})(나)=UNDO(원자성 Atomicity 보장)

4단계 — WAL 두 규칙과의 정합성 확인​

WAL 규칙먼저 써야 하는 로그대비하는 연산대응 빈칸
데이터 페이지 디스크 기록 전BFIMUNDO(나)
트랜잭션 커밋 전AFIMREDO(가)

두 규칙이 각각 BFIM↔UNDO, AFIM↔REDO로 짝지어지므로 3단계까지의 판정과 정확히 일치한다.

5단계 — 결론​

(가) REDO, (나) UNDO → 정답 ③

한 장 요약​

이미지값연산대상 트랜잭션보장 ACID관련 버퍼 정책
AFIM(After)newREDO커밋 완료 후 장애지속성NO-FORCE
BFIM(Before)oldUNDO커밋 못 한 진행 중원자성STEAL

보기별 판정​

보기판정근거
① (가) VOLATILE (나) PERSISTENT오답 보기휘발성/비휘발성은 저장장치 분류 용어로, 로그 이미지가 "대비하는 연산"이 될 수 없다
② (가) PERSISTENT (나) VOLATILE오답 보기①과 마찬가지로 범주 자체가 틀렸고, 순서를 바꿔도 의미가 생기지 않는다
③ (가) REDO (나) UNDO✅ 정답 보기AFIM(새 값) → 재적용 REDO, BFIM(옛 값) → 취소 UNDO. WAL 두 규칙과도 정합
④ (가) UNDO (나) REDO오답 보기AFIM과 BFIM의 역할을 정반대로 뒤바꿨다. 옛 값 없이 되돌릴 수 없고, 새 값 없이 재적용할 수 없다

오답 이유​

  • ①이 틀린 이유: VOLATILE(휘발성)·PERSISTENT(영속성)는 저장 매체가 전원 차단 시 내용을 잃는가를 나타내는 용어다. 회복 기법 문맥에서 "휘발성 저장장치(주기억장치)에 있던 로그를 비휘발성 저장장치(디스크)로 강제 출력한다"처럼 쓰이긴 하지만, 그것은 로그를 어디에 두는가의 문제이지 AFIM/BFIM이 무엇에 대비하는가에 대한 답이 아니다. 빈칸 앞의 "트랜잭션의 ○○에 대비"라는 서술에는 연산 이름이 들어가야 한다.
  • ②가 틀린 이유: ①과 같은 범주 오류이며 순서만 뒤집혔다. "트랜잭션의 PERSISTENT에 대비한다"는 문장 자체가 성립하지 않는다.
  • ③이 맞는 이유: 위 2~4단계에서 본 대로 AFIM은 커밋된 트랜잭션의 결과를 다시 적용(REDO) 하는 데, BFIM은 미커밋 트랜잭션의 변경을 되돌리는(UNDO) 데 사용된다. 상용 DBMS의 STEAL/NO-FORCE 정책이 두 연산을 모두 요구하므로 로그에 두 이미지를 함께 남기는 것이다.
  • ④가 틀린 이유: 가장 많이 걸리는 함정으로, After↔Before를 뒤바꾼 보기다. UNDO는 "취소"이므로 갱신 이전 값(BFIM) 이 있어야 하고, REDO는 "재실행"이므로 갱신 이후 값(AFIM) 이 있어야 한다. 만약 ④처럼 AFIM으로 UNDO를 시도하면 새 값을 다시 써 넣는 꼴이라 오히려 취소가 되지 않고, BFIM으로 REDO를 시도하면 옛 값으로 되돌려 커밋 결과가 사라진다. "After = 앞으로 다시(REDO), Before = 뒤로 되돌리기(UNDO)" 로 외워 두면 헷갈리지 않는다.

핵심 정리​

  • AFIM(After Image) = 갱신 후 값 → REDO(지속성), BFIM(Before Image) = 갱신 전 값 → UNDO(원자성). 두 글자 A/B와 연산이 일대일 대응한다.
  • WAL 두 규칙: ⓐ 데이터 페이지를 디스크에 쓰기 전에 BFIM 로그를 먼저 출력(UNDO 보장), ⓑ 커밋 전에 AFIM 로그를 모두 출력(REDO 보장).
  • 상용 DBMS는 STEAL + NO-FORCE를 택하므로 UNDO와 REDO가 모두 필요하고, 그래서 두 이미지를 함께 로깅한다. 지연 갱신(NO-STEAL/FORCE)이라면 REDO만으로도 충분하다.
  • 회복 시 REDO는 커밋된 트랜잭션, UNDO는 커밋되지 못한 트랜잭션이 대상이다. ARIES는 Analysis → Redo(전부 재수행) → Undo(패자만 취소) 3단계로 처리한다.
  • 이 문제의 결정타: VOLATILE/PERSISTENT는 저장장치 용어라 애초에 답이 될 수 없고, 남은 두 보기는 순서만 다르다. After Image는 REDO, Before Image는 UNDO 라는 대응을 정확히 잡으면 ③이 즉답이다.

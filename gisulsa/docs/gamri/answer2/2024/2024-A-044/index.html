044번 · 상황에 맞는 요구사항 추출(도출) 기법 선택

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. 요구공학의 단계와 "추출"의 위치​

단계영문하는 일
추출(도출)Elicitation이해관계자로부터 요구를 끌어낸다. 본 문항의 대상
분석Analysis충돌·중복·모호성을 정리하고 우선순위를 매긴다
명세SpecificationSRS 등 문서로 기술한다
확인·검증Validation & Verification요구가 맞는지, 제대로 적혔는지 확인한다
관리Management변경·추적성(traceability)을 관리한다

요구사항 추출이 어려운 근본 이유는 이해관계자가 자신이 원하는 것을 언어로 정확히 표현하지 못한다는 데 있다. 이를 흔히 암묵지(tacit knowledge) 문제라 부르며, 기법 선택은 "이해관계자가 무엇을 얼마나 알고 있는가"에 따라 달라진다.

2. 주요 요구사항 추출 기법 비교​

기법방식산출물강점한계
인터뷰(Interview)1:1 또는 소규모 질의응답. 구조적/비구조적/반구조적면담 기록, 요구 목록깊이 있는 정보, 배경·이유 파악응답자가 아는 것만 나온다. 암묵지·미지의 요구에는 무력
설문(Questionnaire)표준화된 문항 배포통계 데이터다수 대상, 비용 저렴심층 탐색 불가, 응답률 문제
관찰(Observation)사용자의 현행 업무 수행을 지켜봄. 민족지학적(ethnographic) 기법업무 흐름, 실제 작업 절차말로 표현되지 않는 암묵지·현행 실무 포착이미 존재하는 업무만 관찰 가능. 신규 기능에는 적용 불가. 호손 효과
브레인스토밍(Brainstorming)집단이 자유롭게 아이디어를 발산아이디어 목록창의적·새로운 아이디어 다량 확보발산 기법이라 검증·수렴은 별도 필요. 실체가 없어 평가 어려움
프로토타이핑(Prototyping)최종 시스템 일부를 빠르게 구현해 보여주고 피드백 수집동작하는 시제품 + 피드백고객이 보고 만지며 요구를 구체화. 아이디어의 시험·검증비용·기간 소요, 시제품을 완제품으로 오인할 위험
워크숍(JAD/RAD)이해관계자를 한자리에 모아 집중 세션합의된 요구 목록이견을 즉시 조율일정 조율 어려움
문서 분석 / 리버스 엔지니어링기존 문서·레거시 코드 분석현행 기능 목록현행 시스템 파악미래 요구는 나오지 않음
유스케이스·시나리오사용자-시스템 상호작용을 이야기로 서술유스케이스 명세기능 요구를 구조화비기능 요구 표현이 약함

3. 프로토타이핑을 지시하는 전형적 단서​

시험에서 프로토타이핑을 답으로 유도할 때 반복되는 표현들이다.

단서 표현의미
"고객이 요구사항을 명확히 알지 못한다"말로 물어서는(인터뷰) 나오지 않는다
"일부 기능을 빠르게 구현한다"실제 산출물 제작이 있다 = 프로토타이핑의 결정적 표지
"조기 피드백을 받는다"개발 완료 전에 사용자의 반응을 본다
"아이디어를 시험·검증한다"발산이 아니라 수렴·확인 단계
"사용자 인터페이스를 미리 확인"화면 프로토타입

4. 프로토타이핑의 종류​

구분설명
진화적(evolutionary) 프로토타입시제품을 계속 다듬어 최종 제품으로 발전시킨다
폐기형(throwaway) 프로토타입요구 확인 목적만 달성하고 버린다. 요구사항 추출 목적에 주로 사용
수평적(horizontal)화면·UI 등 넓고 얕게 구현
수직적(vertical)특정 기능 하나를 끝까지 깊게 구현
Low-fidelity / High-fidelity종이 스케치·와이어프레임 / 실제 동작 화면

5. 혼동하기 쉬운 인접 개념​

혼동구분 기준
브레인스토밍 vs 프로토타이핑발산(아이디어 생성) vs 수렴(아이디어 검증). 지문 "다"의 "시험하고 검증"이 후자
관찰 vs 프로토타이핑현행 업무를 본다 vs 미래 시스템을 만들어 본다
인터뷰 vs 프로토타이핑고객이 아는 것을 캐낸다 vs 고객이 모르는 것을 보여줘 깨닫게 한다
프로토타이핑 vs 파일럿(Pilot)전자는 요구 확인용 시제품, 후자는 완성된 시스템을 일부 조직에 먼저 적용
프로토타이핑 vs MVP전자는 폐기 가능한 학습 수단, 후자는 실제 출시되는 최소 기능 제품

문제​

정답​

④

상세 풀이​

"가장 적절한 것"을 고르는 긍정형 문항이다. 제시된 세 조건을 하나씩 기법 요건으로 번역한다.

  1. 조건 (가) "고객이 자신의 요구사항을 구체적으로 파악하고 있지 못함" → 묻는 방식(인터뷰·설문)은 배제된다. 고객이 모르는 것을 물어봐야 답이 나오지 않기 때문이다. 고객이 보고 반응할 대상을 만들어 주는 기법이 필요하다.
  2. 조건 (나) "최종 시스템의 예상 기능 중 일부를 빠르게 구현하여 조기 피드백" → 기법 중 실제로 무언가를 만드는 것은 프로토타이핑뿐이다. 관찰·인터뷰·브레인스토밍에는 구현 행위가 없다. 이 한 문장이 사실상 답을 확정한다.
  3. 조건 (다) "발굴된 아이디어를 시험하고 검증하여 새로운 아이디어를 얻음" → 아이디어를 만들어내는(발산) 단계가 아니라 이미 나온 아이디어를 실물로 확인하는(수렴·검증) 단계다. 브레인스토밍은 전자, 프로토타이핑은 후자다. 또한 시제품을 써 본 사용자가 "이것 말고 이런 것이 필요하다"고 말하면서 새 요구가 파생되는 것은 프로토타이핑의 대표적 효과다.

세 조건이 모두 프로토타이핑(Prototyping) 을 가리키므로 ④가 정답이다.

조건별 충족 여부 교차표​

네 기법을 세 조건에 대해 모두 대조하면 프로토타이핑만 세 칸이 모두 채워진다.

기법(가) 고객이 요구를 모름(나) 일부 기능을 빠르게 구현(다) 아이디어 시험·검증
① 관찰부분 충족 (암묵지는 포착하나 신규 기능은 불가)✗ 구현 행위 없음✗ 검증 수단 없음
② 인터뷰✗ 아는 것만 나옴✗ 구현 행위 없음부분 충족 (질의로 확인은 가능)
③ 브레인스토밍부분 충족 (아이디어는 나옴)✗ 구현 행위 없음✗ 발산 기법이라 검증이 목적이 아님
④ 프로토타이핑✅✅✅

이처럼 여러 조건이 나열된 문항은 가장 배타적인 조건부터 적용하는 것이 빠르다. 여기서는 "빠르게 구현"이라는 (나)가 네 기법 중 셋을 한 번에 탈락시키는 조건이다.

보기별 판정​

보기판정근거
① 관찰(Observation)오답 보기현행 업무를 지켜보는 기법. 구현 행위가 없고, 아직 존재하지 않는 신규 기능은 관찰 대상 자체가 없다 → (나)·(다) 불충족
② 인터뷰(Interview)오답 보기응답자가 아는 범위만 수집된다 → (가) 불충족. 구현물이 없어 (나)도 불충족
③ 브레인스토밍(Brainstorming)오답 보기아이디어 발산 기법. (다)가 요구하는 시험·검증(수렴)과 목적이 반대이고, (나)의 구현도 없다
④ 프로토타이핑(Prototyping)✅ 정답 보기요구가 불명확할 때(가) 일부 기능을 시제품으로 구현해(나) 사용자의 반응으로 아이디어를 검증·확장(다)하는 기법

오답 이유​

  • ①이 틀린 이유: 관찰은 사용자가 말로 설명하지 못하는 현행 업무 절차와 암묵지를 포착하는 데 강점이 있어 (가)의 일부는 충족할 수 있다. 그러나 "최종 시스템의 예상 기능 중 일부를 빠르게 구현"(나)은 관찰의 활동 범위 밖이며, 아직 만들어지지 않은 기능은 관찰할 대상이 없다. (다)의 "시험·검증"도 관찰로는 불가능하다.
  • ②가 틀린 이유: 인터뷰는 이해관계자가 자신의 요구를 어느 정도 알고 있을 때 가장 효과적이다. 지문 (가)는 정확히 그 전제가 깨진 상황이므로 인터뷰의 효용이 제한된다. 또 인터뷰는 대화로 끝나기 때문에 (나)의 조기 구현·피드백 순환을 만들어내지 못한다.
  • ③이 틀린 이유: 브레인스토밍은 비판을 유보하고 아이디어를 많이 쏟아내는 발산 기법이다. 지문 (다)는 "발굴된 아이디어를 시험하고 검증"이라고 적어 이미 발산이 끝난 뒤의 단계임을 밝히고 있다. 브레인스토밍 산출물은 아이디어 목록일 뿐 동작하는 결과물이 아니므로 (나)도 충족하지 못한다.
  • ④가 맞는 이유: 프로토타이핑은 (가) 요구 불명확 상황을 전제로 고안된 기법이고, (나) 일부 기능의 신속 구현이 그 정의적 활동이며, (다) 시제품을 통한 시험·검증과 그로부터의 요구 파생이 기대 효과다. 세 조건이 하나도 어긋나지 않는다.

핵심 정리​

  • 요구사항 추출 기법 선택은 "이해관계자가 자신의 요구를 아는가"로 갈린다. 안다 → 인터뷰·워크숍, 말로 못 한다(암묵지) → 관찰, 아예 모른다 → 프로토타이핑.
  • 발산 vs 수렴: 브레인스토밍은 아이디어를 만들고, 프로토타이핑은 만든 아이디어를 실물로 검증한다.
  • 관찰은 현행 업무만 볼 수 있어 신규 기능 도출에는 적합하지 않다.
  • "일부 기능을 빠르게 구현하여 조기 피드백"은 실제 산출물을 만드는 유일한 기법인 프로토타이핑을 직접 지시하는 결정적 단서다.

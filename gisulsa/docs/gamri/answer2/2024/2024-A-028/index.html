028번 · 상황에 맞는 UML 다이어그램 선택 — 활동 다이어그램

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. UML 2.x 다이어그램 분류​

UML 2.x의 14개 다이어그램은 구조(structural) 와 행위(behavioral) 로 나뉜다.

대분류다이어그램표현 대상
구조클래스, 객체, 패키지, 컴포넌트, 배치, 복합구조, 프로파일시스템의 정적 구성
행위유스케이스, 활동, 상태머신시스템의 동적 행위
행위 – 상호작용순차, 통신, 상호작용개요, 타이밍객체 간 메시지 교환

2. 네 개 후보 다이어그램의 성격​

다이어그램분류무엇을 표현하나주 구성요소
활동(Activity)행위작업의 흐름(workflow)과 제어 흐름. 업무 절차, 알고리즘, 유스케이스 내부 시나리오액션, 제어 흐름, 판단(decision)/병합(merge), fork/join, 파티션(swimlane), 시작·종료 노드
상태(State machine)행위하나의 객체가 생애 동안 거치는 상태와 전이상태, 전이, 이벤트/가드/액션, 진입·퇴출 액션
클래스(Class)구조클래스·속성·오퍼레이션과 정적 관계클래스, 연관, 일반화, 집합/합성, 의존
유스케이스(Use case)행위액터와 시스템 기능의 관계(외부 관점)액터, 유스케이스, 시스템 경계, include/extend/일반화

3. 활동 다이어그램의 두 가지 결정적 기능​

문제의 (가)·(나)를 각각 해결하는 장치가 활동 다이어그램 안에 모두 들어 있다.

(가) 액터 관점 모델링 → 파티션(partition, 스윔레인)

활동 다이어그램은 다이어그램을 세로 또는 가로 레인으로 나누고, 각 액션을 그 일을 수행하는 액터/역할/조직 단위의 레인에 배치한다. 이렇게 하면 "전체 시스템 수준에서 누가 무엇을 언제 하는가"가 한 장에 드러난다. 그래서 활동 다이어그램은 업무 프로세스 모델링(BPM)의 사실상 표준 표기로 쓰인다.

(나) 제어 흐름 · 동기화 · 병렬 수행 → 제어 흐름과 fork/join

노드기호의미
판단(Decision)마름모, 나가는 간선이 여럿가드 조건에 따라 한 경로만 선택
병합(Merge)마름모, 들어오는 간선이 여럿여러 경로 중 먼저 도착한 것이 그대로 진행
분기(Fork)굵은 막대, 나가는 간선이 여럿병렬(동시) 수행 시작 — 모든 경로가 동시에 진행
결합(Join)굵은 막대, 들어오는 간선이 여럿동기화 — 들어오는 모든 흐름이 도착해야 진행

즉 fork = 병렬 수행 가능성, join = 동기화 필요성을 그대로 표기한다. 또한 액션들이 제어 흐름 화살표로 순서 지어지므로 알고리즘 설계를 순서도처럼 표현할 수 있다. (UML 2.x부터 활동 다이어그램은 페트리넷 기반의 토큰 흐름 의미론을 갖는다.)

4. 왜 다른 다이어그램으로는 안 되는가​

조건ActivityStateClassUse Case
(가) 전체 시스템 수준, 각 액터 관점✅ 파티션(스윔레인)✗ 단일 객체 한정✗ 액터 개념 없음✅ 액터가 1급 요소
(나) 제어 흐름·알고리즘 설계✅ 제어 흐름 + 액션△ 전이로 간접 표현✗ 정적 구조만✗ 표현 수단 없음
(나) 동기화 필요성✅ join✗✗✗
(나) 병렬 수행 가능성✅ fork△ 직교 상태(orthogonal region)로 제한적✗✗
(가) + (나) 동시 충족✅ 유일✗✗✗

5. 혼동하기 쉬운 인접 개념​

구분활동 다이어그램상태 다이어그램
노드의 의미액션(하는 일)상태(있는 상태)
전이의 계기앞 액션의 완료(완료 전이)외부 이벤트 발생
관점여러 객체·액터에 걸친 절차한 객체의 생애주기
병렬 표현fork/join으로 명시적직교 상태(orthogonal region)로 제한적
구분활동 다이어그램유스케이스 다이어그램
추상 수준유스케이스 내부의 절차유스케이스 목록과 액터 관계(외부 관점)
흐름 표현가능(제어 흐름)불가능(관계선만 존재)
흔한 조합유스케이스 명세의 이벤트 흐름을 활동 다이어그램으로 상세화—

문제​

정답​

상세 풀이​

(가)와 (나) 두 조건을 동시에 만족하는 다이어그램을 고르는 복합 조건형 문항이다. 조건별로 걸러 본다.

(가) 전체 시스템 수준에서 시스템과 상호작용하는 각 액터의 관점에서 모델링

  • 활동 다이어그램: 파티션(스윔레인) 으로 액션을 액터별 레인에 배치 → ✅
  • 유스케이스 다이어그램: 액터가 1급 요소 → ✅
  • 상태 다이어그램: 단일 객체의 상태 전이만 다룸 → ✗
  • 클래스 다이어그램: 액터 개념 자체가 없음 → ✗

→ 남는 후보: ① 활동, ④ 유스케이스

(나) 객체 사이의 제어 흐름 및 알고리즘 설계, 동기화 필요성 또는 병렬 수행 가능성 파악

  • 활동 다이어그램: 제어 흐름 화살표로 알고리즘을, fork로 병렬 수행을, join으로 동기화를 표현 → ✅
  • 유스케이스 다이어그램: 액터-유스케이스 관계선(연관·include·extend)만 있을 뿐 순서·분기·병렬·동기화를 표현할 문법이 없다 → ✗

→ ① 활동 다이어그램만 두 조건을 모두 만족한다.

이 문항의 함정은 (가)만 읽고 반사적으로 ④ 유스케이스 다이어그램을 고르게 만드는 구조다. (가)의 "각 액터의 관점"은 유스케이스에도 활동 다이어그램(파티션)에도 해당하므로 (가)만으로는 답이 갈리지 않으며, 결정적 조건은 (나) 다.

보기별 판정​

보기판정근거
① Activity Diagram✅ 정답 보기파티션(스윔레인) 으로 (가) 액터 관점을, 제어 흐름 + fork/join 으로 (나) 알고리즘·병렬 수행·동기화를 모두 표현
② State Diagram오답 보기단일 객체 하나의 상태 전이를 다룸. "여러 객체 사이"·"각 액터 관점"에 부적합하고 병렬은 직교 상태로만 제한적 표현
③ Class Diagram오답 보기구조 다이어그램. 클래스·속성·관계 등 정적 구조만 표현하며 제어 흐름·시간 순서·병렬성을 전혀 담지 못함
④ Use Case Diagram오답 보기(가)의 액터 관점은 충족하나, 유스케이스 간 실행 순서·분기·동기화·병렬성을 표현할 문법이 없어 (나)를 만족하지 못함

오답 이유​

  • ①이 맞는 이유: 활동 다이어그램은 UML 행위 다이어그램 중 유일하게 절차(흐름)와 수행 주체(파티션)를 한 장에 결합할 수 있다. (가)는 파티션으로, (나)는 제어 흐름·fork·join으로 해결되며, fork는 "여기서부터 동시에 진행 가능", join은 "모두 도착해야 다음으로 진행(동기화)"을 명시적으로 나타낸다.
  • ②가 틀린 이유: 상태 다이어그램의 주어는 객체 하나다. 그 객체가 어떤 이벤트를 받아 어떤 상태로 옮겨가는지를 그린다. 문제의 (나)는 "시스템 객체 사이의 제어 흐름"이라고 명시했으므로 주어가 복수이고, (가)의 "각 액터 관점" 역시 상태 다이어그램의 표현 대상이 아니다. 상태 다이어그램을 쓰려면 "주문 객체의 생애주기를 모델링하고자 함" 같은 서술이어야 한다.
  • ③이 틀린 이유: 클래스 다이어그램은 구조 다이어그램으로, 시간 개념이 없다. 클래스 간 연관·일반화·의존을 보여줄 뿐 "무엇이 먼저 실행되는가", "무엇을 병렬로 할 수 있는가"를 표현할 수단이 없다. (가)·(나) 어느 조건도 만족하지 못하는 유일한 보기다.
  • ④가 틀린 이유: 유스케이스 다이어그램은 시스템이 무엇을 해주는가(what) 를 외부 관점에서 목록화한다. 액터와 유스케이스를 선으로 잇고 include/extend로 관계를 표시할 뿐, 유스케이스들 사이의 실행 순서를 규정하지 않는다(include/extend는 실행 순서가 아니라 포함·확장 관계다). 따라서 알고리즘 설계, 동기화 지점, 병렬 수행 가능성을 파악하려는 (나)에는 쓸 수 없다. 실무에서는 유스케이스로 범위를 잡은 뒤 각 유스케이스의 이벤트 흐름을 활동 다이어그램으로 상세화하는 방식으로 두 다이어그램을 함께 쓴다.

핵심 정리​

  • 활동 다이어그램의 두 무기: 파티션(스윔레인) = 누가 하는가, fork/join = 병렬 수행 / 동기화.
  • 판단(decision)/병합(merge) = 마름모, 택일, 분기(fork)/결합(join) = 굵은 막대, 동시·동기화 — 기호와 의미를 짝으로 외운다.
  • 상태 다이어그램은 객체 하나의 생애주기, 유스케이스 다이어그램은 액터-기능 관계(순서 표현 불가), 클래스 다이어그램은 정적 구조.
  • "동기화"와 "병렬 수행"이라는 단어가 나오면 곧바로 활동 다이어그램의 fork/join이다. (가)의 '액터 관점'만 보고 유스케이스를 고르지 않도록, 두 조건을 모두 만족하는지 반드시 확인할 것.

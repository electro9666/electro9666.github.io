116번 · HMAC이 제공하는 것과 제공하지 못하는 것

제25회(2024년) 정보시스템감리사 A형 — 보안

사전 지식​

1. 메시지 인증 코드(MAC)란 무엇인가​

MAC(Message Authentication Code) 은 송수신자가 공유한 비밀키와 메시지를 입력으로 받아 생성하는 짧은 고정 길이 태그다. 수신자는 받은 메시지로 같은 계산을 해 태그가 일치하는지 본다.

단계동작
송신송신자가 T=MAC(K,M)T = \mathrm{MAC}(K, M)T=MAC(K,M) 을 계산해 (M,T)(M, T)(M,T) 를 전송
수신수신자가 받은 M′M'M′ 으로 T′=MAC(K,M′)T' = \mathrm{MAC}(K, M')T′=MAC(K,M′) 를 계산
판정T=T′T = T'T=T′ 이면 변조 없음 + 키를 아는 자가 만든 것으로 판단

MAC이 제공하는 성질과 제공하지 못하는 성질은 명확히 갈린다.

보안 성질MAC(HMAC) 제공 여부이유
무결성(Integrity)✅ 제공메시지가 한 비트만 바뀌어도 태그가 달라짐
(송신자) 인증(Authentication)✅ 제공비밀키를 아는 자만 올바른 태그를 만들 수 있음
기밀성(Confidentiality)❌ 미제공MAC은 메시지를 숨기지 않음(암호화와 별도)
부인방지(Non-repudiation)❌ 미제공수신자도 같은 키를 갖고 있어 동일한 태그를 만들 수 있음

마지막 행이 이 문제의 정답 근거다.

2. 해시 함수만으로는 왜 부족한가 — 키가 필요한 이유​

방식계산문제점
단순 해시H(M)H(M)H(M)공격자가 MMM 을 M∗M^{*}M∗ 로 바꾸고 H(M∗)H(M^{*})H(M∗) 도 새로 계산해 붙이면 탐지 불가. 키가 없어 누구나 만들 수 있음
단순 키 결합H(K∥M)H(K \parallel M)H(K∥M)길이 확장 공격(length extension attack) 에 취약(MD5/SHA-1/SHA-2의 Merkle–Damgård 구조 특성)
H(M∥K)H(M \parallel K)H(M∥K)해시 충돌이 발견되면 위조 가능
HMAC이중 해시 + ipad/opad위 문제들을 구조적으로 회피. RFC 2104 로 표준화

3. HMAC의 정의 — RFC 2104​

RFC 2104(HMAC: Keyed-Hashing for Message Authentication) 가 정의하는 계산식은 다음과 같다.

HMAC(K,M)=H((K′⊕opad)∥H((K′⊕ipad)∥M))\mathrm{HMAC}(K, M) = H\big((K' \oplus opad) \parallel H((K' \oplus ipad) \parallel M)\big)HMAC(K,M)=H((K′⊕opad)∥H((K′⊕ipad)∥M))

기호의미RFC 2104 규정
HHH기반 해시 함수MD5, SHA-1, SHA-256 등
BBB해시의 블록 바이트 길이"B=64 for all the above mentioned examples"
LLL해시 출력 바이트 길이"L=16 for MD5, L=20 for SHA-1"
K′K'K′키를 BBB 바이트로 맞춘 값BBB 보다 길면 해시 후 0 패딩, 짧으면 0 패딩
ipadipadipad내부 패딩"the byte 0x36 repeated B times"
opadopadopad외부 패딩"the byte 0x5C repeated B times"
키 길이 권고최소 LLL 바이트"minimal recommended length for K is L bytes"이며 LLL 미만은 "strongly discouraged"

출처 확인: RFC Editor의 RFC 2104 원문(rfc-editor.org)에서 정의식, ipad/opad 값, B·L의 의미, 키 길이 권고를 확인하였다.

직접 계산으로 검증했을 때 위 식대로 손으로 조립한 값과 표준 라이브러리의 HMAC-SHA256 출력이 정확히 일치한다.

항목값
키 secretkey, 메시지 hello world, 해시 SHA-256, B=64B = 64B=64—
수식대로 직접 계산ae6cd2605d622316564d1f76bfc0c04f89d9fafb14f45b3e18c2a3e28bdef29d
표준 라이브러리 hmac.new(...).hexdigest()ae6cd2605d622316564d1f76bfc0c04f89d9fafb14f45b3e18c2a3e28bdef29d
일치 여부일치

ipad와 opad로 키를 두 번 서로 다르게 변형해 두 번 해시하는 구조 덕분에, 기반 해시에 일부 약점이 있어도 HMAC 전체의 안전성은 비교적 견고하게 유지된다.

4. MAC vs 전자서명 — 부인방지의 갈림길​

구분MAC / HMAC전자서명(Digital Signature)
키 체계대칭키(양측이 동일 키 공유)비대칭키(서명은 개인키, 검증은 공개키)
태그 생성 가능자송신자와 수신자 둘 다개인키 보유자(서명자) 한 사람만
무결성✅✅
송신자 인증✅(키 공유자 범위 내)✅
부인방지❌ 불가✅ 가능
제3자(재판관) 증명❌ 불가✅ 가능
속도빠름(해시 연산)느림(공개키 연산)
대표HMAC-SHA256, CMACRSA-PSS, ECDSA, KCDSA

부인방지가 왜 MAC으로 불가능한가를 논리적으로 따져 보자.

  1. 키 KKK 는 송신자 A와 수신자 B가 똑같이 갖고 있다.
  2. 따라서 어떤 태그 T=HMAC(K,M)T = \mathrm{HMAC}(K, M)T=HMAC(K,M) 을 보여 줘도, A가 만들었는지 B가 스스로 만들었는지 구별할 방법이 없다.
  3. B가 "A가 이 메시지를 보냈다"고 제3자에게 주장해도, A는 "B가 직접 만든 것"이라고 반박할 수 있고 제3자는 판별 불가하다.
  4. 반면 전자서명은 개인키를 가진 사람이 서명자 본인뿐이므로, 서명이 공개키로 검증되면 서명자가 만들었다는 것이 증명된다.

5. 혼동하기 쉬운 인접 개념​

개념키제공 성질헷갈리는 지점
해시(SHA-256)키 없음무결성(우발적 오류 탐지)누구나 재계산 가능하므로 의도적 변조는 못 막음
MAC / HMAC대칭키무결성 + 송신자 인증부인방지 ❌, 기밀성 ❌
전자서명비대칭키무결성 + 인증 + 부인방지기밀성은 별도
HMAC vs CMAC둘 다 대칭키동일HMAC은 해시 기반, CMAC은 블록암호(AES) 기반
HMAC vs 암호화——HMAC은 메시지를 숨기지 않는다. 기밀성이 필요하면 AES-GCM 같은 인증 암호(AEAD) 를 쓴다

상세 풀이​

"가장 적절하지 않은 것"을 고르는 부정형 문항이다. 이 문항의 특이점은 ②와 ③이 정면으로 모순된다는 것이다.

  • ②: "제3자를 위한 증명은 제공할 수 없다"
  • ③: "송신자가 부인하는 경우 수신자는 송신자가 보낸 사실을 증명할 수 있다"

둘 중 하나는 반드시 틀렸다. 그리고 옳은 쪽은 ②다. MAC은 부인방지를 제공하지 못하기 때문이다.

  1. ① "수신자는 메시지의 변경 여부뿐만 아니라 올바른 송신자가 생성한 메시지임을 확인할 수 있다." → MAC의 기본 성질인 무결성 + 송신자 인증을 서술한 것이다. 비밀키를 모르면 올바른 태그를 만들 수 없으므로, 태그가 검증되면 "키를 아는 상대가 보냈고 도중에 변조되지 않았다"는 것이 확인된다. → 적절.
  2. ② "송신자와 수신자 사이에 메시지 인증을 제공하지만, 제3자를 위한 증명은 제공할 수 없다." → 대칭키 공유 구조의 필연적 결과다. 키를 둘 다 갖고 있으므로 제3자는 누가 태그를 만들었는지 판별할 수 없다. MAC의 한계를 정확히 서술했다. → 적절.
  3. ③ "송신자가 메시지를 보낸 사실을 부인하는 경우 수신자는 송신자가 메시지를 보낸 사실을 증명할 수 있다." → 이것은 부인방지(non-repudiation) 를 주장하는 문장이다. 그러나 수신자도 동일한 비밀키를 갖고 있어 같은 태그를 스스로 위조할 수 있으므로, 그 태그가 송신자가 만든 것이라는 점을 제3자에게 입증할 수 없다. HMAC은 부인방지를 제공하지 않는다. → 부적절 = 정답.
  4. ④ "메시지 인증코드를 생성하기 위해 송신자와 수신자는 사전에 공통의 비밀키를 공유해야 한다." → MAC의 전제 조건이다. HMAC은 대칭키 기반이므로 사전 키 공유(수동 배포 또는 DH·TLS 핸드셰이크 등의 키 합의)가 필요하다. → 적절.

정리하면 ①·④는 HMAC의 성질과 전제, ②는 HMAC의 한계를 옳게 서술했고, ③만 그 한계를 부정한다.

오답 이유​

  • ①이 적절한 이유: 태그 계산에 비밀키가 입력으로 들어가므로, 키를 모르는 공격자는 메시지를 바꾼 뒤 그에 맞는 태그를 새로 만들 수 없다. 따라서 태그가 검증되면 ⓐ 메시지가 변조되지 않았고 ⓑ 키를 공유한 정당한 상대가 만들었다는 두 가지가 동시에 확인된다. 키 없는 단순 해시가 ⓑ를 제공하지 못한다는 점과 대비된다.
  • ②가 적절한 이유: "당사자 간 인증은 되지만 제3자 증명은 안 된다"는 문장은 MAC의 한계를 정확히 표현한 것이다. A와 B만 아는 키로 만든 태그는 A·B 사이에서는 서로를 확인하는 근거가 되지만, 재판관 C 입장에서는 A가 만들었는지 B가 만들었는지 알 수 없다. ②는 ③의 정확한 반대 명제이므로 둘이 동시에 참일 수 없다는 점을 알아채면 답을 빠르게 좁힐 수 있다.
  • ③이 부적절한 이유: 부인방지는 "서명자 한 사람만이 만들 수 있는 값" 이 있어야 성립한다. HMAC은 HMAC(K,M)\mathrm{HMAC}(K, M)HMAC(K,M) 을 계산하는 데 필요한 KKK 를 송신자와 수신자가 똑같이 갖고 있으므로, 수신자가 임의의 메시지에 대해 유효한 태그를 스스로 만들어 "송신자가 보냈다"고 주장할 수 있다. 송신자는 언제든 "수신자가 위조했다"고 반박할 수 있고 제3자는 판별할 수 없다. 올바른 서술로 고치면 "송신자가 부인하는 경우 수신자는 이를 증명할 수 없으며, 부인방지가 필요하면 송신자의 개인키로 생성하는 전자서명을 사용해야 한다"가 된다.
  • ④가 적절한 이유: HMAC은 이름 그대로 Keyed-Hashing, 즉 키를 사용하는 해시다. 양측이 동일한 KKK 를 갖고 있어야 같은 태그를 계산할 수 있으므로 사전 키 공유가 필수 전제다. 실무에서는 TLS 핸드셰이크나 Diffie–Hellman 키 합의로 세션키를 만든 뒤 그로부터 MAC 키를 파생(HKDF 등)하는 방식으로 이 요구를 충족한다.

핵심 정리​

  • HMAC(RFC 2104) 정의: HMAC(K,M)=H((K′⊕opad)∥H((K′⊕ipad)∥M))\mathrm{HMAC}(K, M) = H\big((K' \oplus opad) \parallel H((K' \oplus ipad) \parallel M)\big)HMAC(K,M)=H((K′⊕opad)∥H((K′⊕ipad)∥M)), ipad = 0x36 반복, opad = 0x5C 반복, 키 길이는 해시 출력 길이 LLL 이상 권고.
  • HMAC이 제공하는 것: 무결성 + 송신자 인증. 제공하지 못하는 것: 기밀성, 부인방지.
  • 부인방지는 전자서명(송신자 개인키로 생성)으로만 달성된다. MAC은 양측이 같은 키를 가지므로 원리상 불가능하다.
  • ②("제3자 증명 불가")와 ③("부인 시 증명 가능")은 서로 모순되는 명제 — 이런 쌍이 보기 안에 있으면 둘 중 하나가 답이며, MAC의 성질상 참인 쪽은 ②다. 이것이 이 문제의 결정타다.

055번 · 외래키 선언 위치와 ON DELETE CASCADE 구문

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. 무결성 제약조건의 종류​

제약조건내용SQL 선언
개체 무결성(entity integrity)기본키는 NULL일 수 없고 유일해야 함PRIMARY KEY
참조 무결성(referential integrity)외래키 값은 참조하는 릴레이션의 기본키 값 중 하나이거나 NULL이어야 함FOREIGN KEY ... REFERENCES ...
도메인 무결성속성 값이 정의된 도메인에 속해야 함데이터 타입, CHECK
고유 무결성특정 속성 값이 중복되지 않아야 함UNIQUE
NULL 무결성특정 속성에 NULL을 허용하지 않음NOT NULL

2. 부모(참조되는) 릴레이션과 자식(참조하는) 릴레이션​

참조 관계에는 항상 방향이 있다.

역할다른 이름가진 것
부모(parent)참조되는(referenced) 릴레이션기본키
자식(child)참조하는(referencing) 릴레이션외래키

핵심 규칙 — 외래키 제약과 참조 동작(referential action)은 반드시 FOREIGN KEY 를 가진 쪽, 즉 자식 릴레이션에 선언한다.

CREATE TABLE 부모 (
  키 ... PRIMARY KEY          -- 부모에는 아무 선언도 하지 않는다
);

CREATE TABLE 자식 (
  ...,
  FOREIGN KEY (키) REFERENCES 부모(키)  -- 자식에 선언
    ON DELETE CASCADE
);

3. 참조 동작(referential action) 5종​

부모 투플이 삭제(DELETE) 되거나 부모의 기본키가 갱신(UPDATE) 될 때, 그것을 참조하고 있던 자식 투플을 어떻게 처리할지 지정하는 옵션이다. SQL 표준 구문은 ON DELETE <동작> / ON UPDATE <동작> 이다.

동작부모 투플 삭제 시 자식 투플의 처리
NO ACTION (기본값)참조하는 자식이 있으면 삭제를 거부(제약 위반 오류). 문 종료 시점에 검사
RESTRICT참조하는 자식이 있으면 즉시 삭제를 거부. 검사 시점만 NO ACTION과 다름
CASCADE자식 투플도 함께 삭제(연쇄 삭제)
SET NULL자식의 외래키 값을 NULL로 변경
SET DEFAULT자식의 외래키 값을 정의된 기본값으로 변경

문제에서 요구하는 "계좌 투플이 삭제되면 예금자 투플도 같이 삭제"는 정확히 ON DELETE CASCADE 다.

IN DELETE CASCADE 라는 구문은 SQL 표준에도, 어떤 상용 DBMS에도 존재하지 않는다. 예약어는 ON 이다.

4. 이 문항의 스키마 분석​

릴레이션속성기본키외래키
고객(고객번호, 이름, 주소)고객번호—
계좌(계좌번호, 지점명, 잔고)계좌번호—
예금자(고객번호, 계좌번호, 계좌생성날짜)(고객번호, 계좌번호) 복합키고객번호 → 고객, 계좌번호 → 계좌

예금자는 고객과 계좌 사이의 N:M 관계를 표현하는 관계 릴레이션이다. 따라서

  • 부모 = 계좌(계좌번호가 기본키)
  • 자식 = 예금자(계좌번호를 외래키로 가짐)

이 방향이 확정되면 선언 위치와 구문이 자동으로 결정된다.

CREATE TABLE 예금자 (
  고객번호  CHAR(10),
  계좌번호  CHAR(10),
  계좌생성날짜 DATE,
  PRIMARY KEY (고객번호, 계좌번호),
  FOREIGN KEY (고객번호) REFERENCES 고객(고객번호),
  FOREIGN KEY (계좌번호) REFERENCES 계좌(계좌번호) ON DELETE CASCADE
);

5. 혼동하기 쉬운 인접 개념​

혼동 지점정리
선언을 부모에 하는가 자식에 하는가항상 자식(외래키 보유 쪽). 부모 테이블 정의에는 참조 동작을 쓸 자리가 없다
ON DELETE vs ON UPDATE삭제 시 동작과 갱신 시 동작은 별도로 지정한다. 한 제약에 둘 다 붙일 수 있다
CASCADE vs SET NULLCASCADE는 자식 행 자체를 삭제, SET NULL은 행은 남기고 외래키만 NULL
참조 동작의 기본값아무것도 쓰지 않으면 NO ACTION — 즉 부모 삭제가 거부된다
연쇄 삭제의 전파자식이 또 다른 테이블의 부모라면 CASCADE가 연쇄적으로 전파되므로 대량 삭제에 주의

문제​

정답​

①

상세 풀이​

네 보기는 두 개의 축으로 갈린다. 각 축을 독립적으로 판정하면 정답이 하나로 좁혀진다.

보기축 1: 선언 위치와 참조 방향축 2: 키워드
①예금자에 선언, REFERENCES 계좌ON DELETE CASCADE
②예금자에 선언, REFERENCES 계좌IN DELETE CASCADE
③계좌에 선언, REFERENCES 예금자ON DELETE CASCADE
④계좌에 선언, REFERENCES 예금자IN DELETE CASCADE

축 1 — 어느 릴레이션에 선언해야 하는가​

요구사항은 "계좌의 투플이 삭제되면 예금자의 투플도 같이 삭제"다. 여기서

  • 삭제의 원인이 되는 쪽 = 계좌 → 부모
  • 삭제의 결과를 받는 쪽 = 예금자 → 자식

참조 무결성 제약과 참조 동작은 외래키를 가진 자식 릴레이션에 선언한다. 따라서 선언 위치는 예금자이고, 참조 대상은 REFERENCES 계좌(계좌번호) 여야 한다.

③·④처럼 계좌 릴레이션에 FOREIGN KEY(계좌번호) REFERENCES 예금자(계좌번호) 를 쓰면 방향이 완전히 뒤집힌다. 문제는 세 가지다.

  1. 동작이 반대가 된다. 이렇게 선언하면 "예금자가 삭제될 때 계좌가 삭제"되어 요구사항과 정반대다.
  2. 의미상 모순이다. 계좌번호는 계좌 릴레이션의 기본키인데, 이를 동시에 다른 릴레이션을 참조하는 외래키로 두는 것은 "계좌는 예금자에 등록되어야만 존재할 수 있다"는 이상한 제약이 된다.
  3. 참조 대상이 키가 아니다. 외래키는 참조 대상 릴레이션의 기본키 또는 UNIQUE 속성을 가리켜야 한다. 예금자의 기본키는 (고객번호, 계좌번호) 복합키이므로 계좌번호 단독은 유일하지 않아(한 계좌에 공동 예금자가 여러 명일 수 있다) 참조 대상이 될 수 없다. 즉 이 문장은 DBMS에서 실행 자체가 실패한다.

→ ③·④ 탈락. 남는 것은 ①·②.

축 2 — ON 인가 IN 인가​

SQL 표준의 참조 동작 절은 다음 형식으로만 정의되어 있다.

<referential triggered action> ::=
      ON UPDATE <referential action> [ ON DELETE <referential action> ]
    | ON DELETE <referential action> [ ON UPDATE <referential action> ]

<referential action> ::= CASCADE | SET NULL | SET DEFAULT | RESTRICT | NO ACTION

키워드는 ON 이며 IN DELETE ... 라는 문법은 존재하지 않는다. IN 은 SQL에서 WHERE x IN (...) 처럼 집합 소속 검사 연산자로 쓰이는 전혀 다른 예약어다.

→ ②·④ 탈락.

결론​

두 축을 모두 통과하는 것은 ① 하나뿐이다.

CREATE TABLE 예금자 (
  고객번호  ...,
  계좌번호  ...,
  계좌생성날짜 ...,
  PRIMARY KEY (고객번호, 계좌번호),
  FOREIGN KEY (계좌번호) REFERENCES 계좌(계좌번호) ON DELETE CASCADE   -- ①
);

동작 확인​

계좌에서 계좌번호 A100 인 행을 삭제하면 다음이 일어난다.

시점계좌예금자
삭제 전(A100, 강남, 500000)(C01, A100, 2024-03-01), (C02, A100, 2024-03-01)
DELETE FROM 계좌 WHERE 계좌번호='A100' 실행 후해당 행 삭제두 행 모두 자동 삭제

만약 ON DELETE 절을 생략했다면 기본값 NO ACTION 이 적용되어, 예금자에 참조 행이 남아 있으므로 계좌의 삭제 자체가 거부되었을 것이다.

보기별 판정​

보기판정근거
① 예금자에 REFERENCES 계좌(계좌번호) ON DELETE CASCADE✅ 정답 보기선언 위치(자식=예금자)와 참조 방향(→계좌), 표준 키워드 ON DELETE CASCADE 를 모두 만족
② 예금자에 ... IN DELETE CASCADE오답 보기위치·방향은 맞으나 IN DELETE는 SQL에 존재하지 않는 구문이다. 올바른 예약어는 ON
③ 계좌에 REFERENCES 예금자(계좌번호) ON DELETE CASCADE오답 보기참조 방향이 정반대. 이대로면 예금자 삭제 시 계좌가 삭제된다. 게다가 예금자의 계좌번호는 단독으로 유일하지 않아 참조 대상이 될 수 없다
④ 계좌에 ... IN DELETE CASCADE오답 보기방향도 반대이고 구문도 틀린 이중 오류 보기

오답 이유​

  • ②가 틀린 이유: 참조 방향과 선언 위치는 ①과 동일하게 올바르다. 유일한 차이는 ON 을 IN 으로 바꾼 것인데, 이것만으로 문법 오류가 되어 CREATE TABLE 문이 실행되지 않는다. SQL 표준에서 참조 동작 절은 ON DELETE <action> / ON UPDATE <action> 으로만 정의되며, IN 은 WHERE 부서 IN ('영업','총무') 같은 집합 소속 연산자로 쓰이는 별개의 예약어다. 두 보기가 키워드 한 글자만 다르게 배치된 것은 응시자가 방향 판단에만 집중하다가 구문을 흘려 보게 만드는 함정이다.
  • ③이 틀린 이유: 세 가지가 동시에 잘못되었다. 첫째, 선언 위치가 부모 쪽(계좌) 이다. 외래키와 참조 동작은 반드시 자식 릴레이션에 선언해야 한다. 둘째, 동작이 요구와 반대가 된다. 이 선언은 "예금자 투플이 삭제되면 계좌 투플을 삭제하라"는 뜻이므로, 문제가 요구한 "계좌 삭제 → 예금자 삭제"와 정반대다. 셋째, 계좌번호는 계좌의 기본키인데 이를 동시에 예금자를 참조하는 외래키로 만들면, 예금자에 등록되지 않은 계좌는 존재할 수 없다는 비현실적 제약이 생기고, 예금자의 계좌번호가 단독으로는 유일하지 않아 참조 대상 자격조차 갖추지 못한다.
  • ④가 틀린 이유: ③의 방향 오류와 ②의 구문 오류를 동시에 가진 보기다. 계좌에 선언한 점, REFERENCES 예금자 로 방향을 뒤집은 점, IN DELETE 라는 비표준 구문을 쓴 점 모두 틀렸다. 네 보기 중 가장 명백한 오답이며, 보기 배치상 2×2 조합표를 채우기 위해 만들어진 항목이다.

핵심 정리​

  • 외래키 제약과 참조 동작은 언제나 FOREIGN KEY 를 가진 자식(참조하는) 릴레이션에 선언한다. 부모 테이블 정의에는 쓸 자리가 없다.
  • "부모가 삭제될 때 자식도 삭제"는 ON DELETE CASCADE. 반대로 자식만 남기고 외래키를 비우려면 ON DELETE SET NULL, 삭제를 막으려면 기본값 NO ACTION(또는 RESTRICT).
  • 참조 동작 5종 — NO ACTION / RESTRICT / CASCADE / SET NULL / SET DEFAULT. 아무것도 지정하지 않으면 NO ACTION 이 적용된다.
  • 이 문항은 ① 선언 위치·참조 방향과 ② ON 키워드 두 축의 2×2 조합이다. 각 축을 따로 판정하면 실수 없이 ①로 수렴한다.
  • IN DELETE CASCADE 라는 구문은 SQL에 존재하지 않는다. 올바른 예약어는 ON 이며, 이 한 글자가 ①과 ②를 가르는 결정타다.

100번 · TCP 연결 설정의 순서번호·확인응답번호 계산

제25회(2024년) 정보시스템감리사 A형 — 시스템 구조

사전 지식​

1. TCP 헤더의 순서번호와 확인응답번호​

TCP(RFC 793, 현행 RFC 9293)는 바이트 스트림에 번호를 붙여 신뢰성을 확보한다.

필드크기의미
Sequence Number(Seq. No.)32비트이 세그먼트가 담은 데이터의 첫 바이트 번호
Acknowledgement Number(ACK No.)32비트다음에 받기를 기대하는 바이트 번호 (= 지금까지 잘 받은 마지막 바이트 + 1)
Flags각 1비트URG, ACK, PSH, RST, SYN, FIN
Window16비트수신 가능한 버퍼 크기(흐름 제어)

여기서 ACK No. 는 "누적 확인응답(cumulative ACK)" 이며, "이 번호 직전까지는 모두 잘 받았고 이제 이 번호를 달라"는 뜻이다. 그래서 계산의 기본 공식은 다음과 같다.

ACK No. = (수신한 세그먼트의 Seq. No.) + (그 세그먼트가 소비한 시퀀스 공간)

2. 반드시 알아야 할 규칙 — SYN과 FIN은 1바이트를 소비한다​

세그먼트 종류소비하는 시퀀스 공간
데이터 nnn 바이트nnn
SYN 플래그1 (데이터가 없어도)
FIN 플래그1 (데이터가 없어도)
순수 ACK(데이터·SYN·FIN 없음)0 ← 시퀀스 번호를 소비하지 않음

SYN·FIN이 1바이트를 소비하도록 설계한 이유는, 연결의 시작과 끝이라는 제어 이벤트 자체에도 확인응답과 재전송이 필요하기 때문이다(이를 "팬텀 바이트"라 부르기도 한다).

이 규칙에서 곧바로 다음이 따라 나온다.

  • 상대의 SYN(Seq = xxx)에 대한 확인응답은 ACK No. = x+1x + 1x+1
  • SYN을 보낸 쪽이 다음에 보낼 세그먼트의 Seq. No. = x+1x + 1x+1
  • 순수 ACK는 시퀀스 공간을 소비하지 않으므로, 그 다음 세그먼트의 Seq. No.는 그대로 유지된다

3. TCP 3-way handshake의 전체 흐름​

서버 ISN을 yyy, 클라이언트 ISN(Initial Sequence Number)을 xxx 라 하면:

클라이언트                                             서버
    │                                                  │  (LISTEN: 신호 청취 중)
    │ ──── ①  SYN,  Seq = x  ─────────────────────────► │
    │                                                  │  (SYN 수신 완료)
    │ ◄─── ②  SYN+ACK,  Seq = y,  ACK = x + 1  ──────── │
    │  (연결 생성 확인)                                  │
    │ ──── ③  ACK,  Seq = x + 1,  ACK = y + 1  ───────► │
    │                                                  │  (연결 생성 확인)
  ESTABLISHED                                     ESTABLISHED
단계보내는 쪽플래그Seq. No.ACK No.설명
①클라이언트SYNxxx(무의미)자신의 ISN을 알림
②서버SYN + ACKyyyx+1x+1x+1자신의 ISN을 알리며 ①을 확인
③클라이언트ACKx+1x+1x+1y+1y+1y+1②를 확인. SYN이 1을 소비했으므로 Seq는 x+1x+1x+1

ISN을 0이 아닌 임의의 값으로 시작하는 이유는 이전 연결의 지연된 세그먼트가 새 연결에 섞이는 것을 막고 시퀀스 번호 추측 공격을 어렵게 하기 위함이다.

4. 참고 — 연결 종료(4-way handshake)​

단계보내는 쪽플래그설명
①AFIN더 보낼 데이터 없음(A→B 방향 종료)
②BACKFIN 확인(ACK No. = FIN의 Seq + 1)
③BFINB도 보낼 데이터 없음
④AACK확인 후 TIME-WAIT(2×MSL) 상태 유지

FIN 역시 1바이트를 소비하므로 ACK No.에 +1을 적용한다. 종료가 4단계인 것은 한쪽이 먼저 끊어도 반대 방향은 계속 데이터를 보낼 수 있는 half-close를 허용하기 때문이다.

5. 혼동하기 쉬운 인접 개념​

오해사실
"SYN은 데이터가 없으니 시퀀스 번호를 안 쓴다"SYN·FIN은 각각 1바이트를 소비한다
"순수 ACK도 시퀀스 번호를 1 증가시킨다"순수 ACK는 0바이트 소비. 다음 Seq가 그대로 유지된다
"③단계의 Seq는 서버의 Seq(y)를 따른다"아니다. 자기 자신이 보낸 SYN의 Seq + 1(= x+1x+1x+1)
"ACK No.는 마지막으로 받은 바이트 번호"다음에 기대하는 바이트 번호(= 마지막 + 1)

상세 풀이​

1단계 — 그림에서 주어진 값 정리​

문제 그림(클라이언트–서버 시퀀스 다이어그램)에서 읽어낸 값은 다음과 같다.

단계방향세그먼트Seq. No.ACK No.
① SYN 송신클라이언트 → 서버SYN7(표시 없음)
② SYN 수신 완료서버 → 클라이언트SYN + ACK38ⓐ
③ 연결 생성 확인클라이언트 → 서버ACKⓑⓒ

즉 클라이언트 ISN x=7x = 7x=7, 서버 ISN y=38y = 38y=38 이다.

2단계 — 적용할 규칙​

규칙 1)  ACK No.   = 수신한 세그먼트의 Seq. No. + 1   (SYN이 시퀀스 공간 1을 소비)
규칙 2)  다음 Seq. No. = 직전에 보낸 SYN의 Seq. No. + 1

3단계 — ⓐ·ⓑ·ⓒ 계산 전개​

빈칸무엇인가계산 근거식값
ⓐ서버가 보내는 ACK No.클라이언트 SYN(Seq=7)을 확인 → SYN이 1바이트 소비7+17 + 17+18
ⓑ클라이언트가 보내는 Seq. No.자신이 보낸 SYN(Seq=7)이 1바이트를 소비했으므로 다음 번호7+17 + 17+18
ⓒ클라이언트가 보내는 ACK No.서버 SYN+ACK(Seq=38)을 확인 → SYN이 1바이트 소비38+138 + 138+139

ⓐ와 ⓑ가 모두 8인 것은 우연이 아니다. 서버가 "다음에 8번 바이트를 기대한다(ⓐ=8)"고 알렸으므로, 클라이언트가 실제로 보내는 세그먼트의 Seq. No.(ⓑ)도 정확히 8이어야 한다. ACK No.와 상대방의 다음 Seq. No.는 항상 일치한다는 점이 검산 포인트다.

4단계 — 합 계산​

ⓐ + ⓑ + ⓒ  =  8 + 8 + 39  =  55

따라서 정답은 ④ 55.

5단계 — 완성된 핸드셰이크 표​

단계방향플래그Seq. No.ACK No.
①클라이언트 → 서버SYN7—
②서버 → 클라이언트SYN + ACK388 (ⓐ)
③클라이언트 → 서버ACK8 (ⓑ)39 (ⓒ)

이후 클라이언트가 데이터를 보내기 시작하면 첫 데이터 세그먼트의 Seq. No.도 8이다(③의 순수 ACK는 시퀀스 공간을 소비하지 않기 때문).

보기별 판정​

보기판정근거
① 52오답 보기ⓒ에 +1을 적용하지 않고 38을 그대로 쓰면서 다른 값도 틀린 경우(예: 7+7+38)
② 53오답 보기ⓐ 또는 ⓑ 중 하나에 +1을 빠뜨린 값(7+8+38 = 53)
③ 54오답 보기세 칸 중 한 곳에서만 +1을 누락한 값(8+8+38 = 54)
④ 55✅ 정답 보기ⓐ=8, ⓑ=8, ⓒ=39 → 8+8+39 = 55

오답 이유​

  • ①(52)이 틀린 이유: SYN이 시퀀스 공간을 소비한다는 규칙을 아예 적용하지 않고 7+7+38=527 + 7 + 38 = 527+7+38=52 로 계산한 결과다. ⓐ와 ⓒ는 "확인응답 번호"이므로 받은 Seq를 그대로 되돌려 보내는 것이 아니라 반드시 +1 해야 한다.
  • ②(53)가 틀린 이유: ⓒ에 +1을 적용하지 않은 경우다(8+7+388 + 7 + 388+7+38 또는 7+8+38=537 + 8 + 38 = 537+8+38=53). 서버의 SYN+ACK 역시 SYN 플래그가 세워져 있으므로 1바이트를 소비하며, 클라이언트는 ACK No.를 38+1=3938+1=3938+1=39 로 보내야 한다.
  • ③(54)가 틀린 이유: ⓐ·ⓑ는 올바르게 8로 구했으나 ⓒ를 서버의 Seq 38 그대로 둔 경우다(8+8+38=548 + 8 + 38 = 548+8+38=54). 또는 ⓑ를 서버의 Seq(38)로 착각하고 다른 값에서 오차가 상쇄된 경우에도 나올 수 있다. ⓑ는 클라이언트 자신의 시퀀스 번호이므로 서버 값(38)이 들어갈 자리가 아니다.
  • ④가 정답인 이유: 세 빈칸 모두에 "SYN은 1바이트를 소비한다"는 규칙을 일관되게 적용하면 ⓐ=8, ⓑ=8, ⓒ=39가 되고 합은 55다. 검산으로 "서버가 알린 ACK No. ⓐ(8) = 클라이언트가 실제로 보낸 Seq. No. ⓑ(8)"가 일치하는 것도 확인된다.

핵심 정리​

  • ACK No. = 다음에 받기를 기대하는 바이트 번호이며, SYN과 FIN은 데이터가 없어도 각각 시퀀스 공간 1을 소비한다. 순수 ACK는 0을 소비한다.
  • 3-way handshake 공식: 클라이언트 ISN xxx, 서버 ISN yyy 일 때 → ① SYN, Seq=x → ② SYN+ACK, Seq=y, ACK=x+1 → ③ ACK, Seq=x+1, ACK=y+1.
  • 본 문항 대입: x=7x=7x=7, y=38y=38y=38 → ⓐ = 8, ⓑ = 8, ⓒ = 39, 합 55.
  • 검산 요령: 한쪽이 보낸 ACK No.는 상대가 다음에 보낼 Seq. No.와 반드시 같다. ⓐ와 ⓑ가 모두 8로 일치하는 것이 그 증거다.
  • 결정타: 계산 자체는 덧셈뿐이지만, "SYN이 시퀀스 번호 1개를 소비한다"는 규칙을 세 칸 모두에 빠짐없이 적용해야 55가 나온다.

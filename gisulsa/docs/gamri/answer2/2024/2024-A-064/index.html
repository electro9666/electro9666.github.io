064번 · EER 모델의 범주(category, union type)

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. EER(Enhanced ER) 모델이 추가한 것​

기본 ER 모델(개체·속성·관계)만으로는 표현하기 어려운 의미 구조를 담기 위해 확장된 개념이 EER이다.

개념한 줄 정의
세분화(specialization)하나의 상위 개체를 여러 하위 개체로 나눔(하향식)
일반화(generalization)여러 하위 개체의 공통점을 뽑아 상위 개체를 만듦(상향식)
범주(category) / 합집합 타입(union type)서로 다른 여러 상위 개체 타입의 합집합을 하나의 하위 개체로 정의
집단화(aggregation)관계 자체를 하나의 상위 개체로 추상화
속성/관계 상속하위 개체가 상위 개체의 속성과 관계를 물려받음

2. 세분화와 일반화 — 같은 구조, 반대 방향​

              ┌───────────┐
              │  EMPLOYEE │   ← 상위 타입 1개
              └─────┬─────┘
                    │
                   (d)          ← 원 안에 d(분리) 또는 o(중첩)
           ┌────────┼────────┐
           ⊂        ⊂        ⊂
      ┌────┴──┐ ┌───┴───┐ ┌──┴────┐
      │SECRETARY│ │ENGINEER│ │TECHNICIAN│   ← 하위 타입 여러 개
      └────────┘ └────────┘ └─────────┘
구분세분화일반화
방향상위 → 하위(top-down)하위 → 상위(bottom-up)
시작점EMPLOYEE 하나를 역할별로 나눔CAR, TRUCK을 보고 VEHICLE을 만듦
결과 구조상위 1개 : 하위 N개상위 1개 : 하위 N개

두 개념 모두 상위 타입이 하나뿐이라는 점이 핵심이다. 결과로 만들어지는 다이어그램 구조는 동일하고, 설계자가 어느 쪽에서 출발했는가만 다르다.

3. 범주(category) — 상위 타입이 여럿인 유일한 구조​

   ┌────────┐  ┌──────┐  ┌─────────┐
   │ PERSON │  │ BANK │  │ COMPANY │   ← 상위 타입 여러 개
   └────┬───┘  └───┬──┘  └────┬────┘
        └──────────┼──────────┘
                  (∪)                  ← 원 안에 합집합 기호 U
                   │
                   ⊂
             ┌─────┴─────┐
             │   OWNER   │             ← 하위 타입 1개
             └───────────┘

범주는 OWNER⊆PERSON∪BANK∪COMPANY\text{OWNER} \subseteq \text{PERSON} \cup \text{BANK} \cup \text{COMPANY}OWNER⊆PERSON∪BANK∪COMPANY 를 표현한다.

성질내용
표기원 안의 ∪(합집합) 기호, 여러 상위 타입에서 선이 모임
멤버각 OWNER 인스턴스는 상위 타입 중 정확히 하나의 인스턴스
상속선택적 상속(selective inheritance) — 자기가 속한 그 상위 타입의 속성만 상속
키상위 타입들의 키가 서로 다르므로 보통 대리 키(surrogate key) 를 도입
전체/부분상위 타입 전부가 범주에 속하면 전체 범주, 일부만이면 부분 범주

4. 범주 vs 공유 하위 타입(shared subclass) — 가장 중요한 대비​

둘 다 "여러 상위 타입에 선이 연결된" 모습이라 혼동하기 쉽지만, 의미가 정반대다.

항목범주 (union type)공유 하위 타입 (multiple inheritance)
논리 연산합집합 ∪ (OR)교집합 ∩ (AND)
표기상위들이 원(∪) 하나로 모인 뒤 하위로 ⊂각 상위에서 하위로 ⊂ 선이 개별로 연결
멤버 자격상위 중 어느 하나의 멤버이면 됨상위 모두의 멤버여야 함
상속선택적 — 자기가 속한 상위의 속성만전부 — 모든 상위의 속성을 다 상속
예OWNER = PERSON ∪ BANK ∪ COMPANYENGINEERING_MANAGER = ENGINEER ∩ MANAGER ∩ SALARIED_EMPLOYEE

문제의 다이어그램에는 세 상위 타입의 선이 원 안의 ∪ 기호 하나로 모인 뒤 OWNER로 내려간다. 따라서 공유 하위 타입이 아니라 범주다.

5. 집단화(aggregation)​

   ┌──────────┐          ┌──────────┐
   │ EMPLOYEE │──〈근무〉──│ PROJECT  │
   └──────────┘          └──────────┘
          └──── 이 관계 전체를 하나의 개체로 ────┐
                                        ┌──────┴──────┐
                                        │  ASSIGNMENT │──〈평가〉──│ MANAGER │
                                        └─────────────┘

집단화는 "관계에 다시 관계를 걸어야 할 때" 쓴다. 관계를 개체처럼 취급해 상위 수준 개체로 묶는 추상화이며, 상속 개념(⊂)과는 무관하다.

6. 혼동하기 쉬운 인접 개념​

개념상위 타입 수상속 방식표기 기호
세분화1개전부 상속원 안 d/o, ⊂
일반화1개전부 상속원 안 d/o, ⊂
범주여러 개선택적 상속원 안 ∪, ⊂
공유 하위 타입여러 개전부 상속각 상위에서 ⊂ 개별 연결
집단화해당 없음상속 아님관계를 감싸는 사각형
제약표기의미
분리(disjoint)원 안 d인스턴스가 하위 타입 중 최대 1개에만 속함
중첩(overlapping)원 안 o인스턴스가 여러 하위 타입에 동시에 속할 수 있음
전체(total)이중선상위의 모든 인스턴스가 어느 하위에 반드시 속함
부분(partial)단일선어느 하위에도 속하지 않는 상위 인스턴스가 있을 수 있음

문제​

정답​

③

상세 풀이​

1단계 — 다이어그램 판독​

이미지의 구조는 다음과 같다.

요소내용
최상단PERSON, BANK, COMPANY 세 개의 개체 타입이 나란히 배치
중간세 개체에서 나온 선이 원 안의 U(합집합) 기호 하나로 모임
그 아래원에서 부분집합 기호(⊂) 를 거쳐 OWNER 로 연결
하단OWNER —M— 〈OWNS〉 —N— VEHICLE 의 M:N 관계

2단계 — 결정적 단서 세 가지​

  1. 상위 타입이 3개다. 세분화·일반화는 상위 타입이 하나뿐인 구조이므로 이 시점에서 ①·②는 배제된다.
  2. 원 안의 기호가 ∪(합집합)다. 세분화·일반화에서는 원 안에 d(disjoint) 또는 o(overlapping)가 들어간다. ∪ 는 범주 전용 표기다.
  3. 선이 원 하나로 모였다가 하위로 내려간다. 각 상위에서 하위로 선이 개별 연결되었다면 공유 하위 타입(다중 상속)이지만, 여기서는 ∪ 원을 거친다.

3단계 — 의미 해석​

OWNER  ⊆  PERSON∪BANK∪COMPANY\text{OWNER} \;\subseteq\; \text{PERSON} \cup \text{BANK} \cup \text{COMPANY}OWNER⊆PERSON∪BANK∪COMPANY

자동차 소유주는 사람이거나, 은행이거나, 회사다. 어느 소유주 하나를 집어 보면 그 인스턴스는 세 타입 중 정확히 하나의 인스턴스다. 사람이면서 동시에 은행인 소유주는 없다. 이것이 범주의 정의 그대로다.

문제 문장의 "PERSON, BANK, COMPANY 개체가 자동차 소유주가 될 수 있음"은 논리적으로 OR(합집합) 이다. 만약 "세 가지 모두여야 한다"였다면 공유 하위 타입(교집합)이었을 것이다.

4단계 — 상속 방식으로 재확인​

범주의 선택적 상속이 이 모델링에서 왜 필요한지 보면 판단이 굳어진다.

상위 타입고유 속성 예
PERSON주민등록번호, 생년월일, 주소
BANK은행코드, 지점명
COMPANY사업자등록번호, 대표자명

세 타입은 키도 속성도 완전히 다르다. 만약 일반화(상위 1개 : 하위 N개)였다면 OWNER가 상위가 되어 세 타입이 공통 속성을 물려받아야 하는데, 공통 속성이 사실상 없다. 반대로 범주에서는 OWNER 인스턴스마다 자신이 속한 상위 타입의 속성만 상속하므로 이 이질성이 자연스럽게 수용된다. 관계 OWNS 는 OWNER 수준에서 한 번만 정의하면 세 종류 소유주 모두에 적용된다 — 이것이 범주를 쓰는 실질적 이득이다.

5단계 — 결론​

여러 상위 타입의 합집합으로 하나의 하위 타입을 정의한 것 → 범주(category) → ③

보기별 판정​

보기판정근거
① 세분화(specialization)오답 보기상위 타입 1개를 여러 하위로 나누는 하향식 개념. 본 다이어그램은 상위가 3개이고 하위가 1개로 방향이 정반대
② 일반화(generalization)오답 보기여러 하위의 공통 속성을 뽑아 상위 1개를 만드는 상향식 개념. PERSON/BANK/COMPANY는 공통 속성이 거의 없고 구조상 상위가 여럿이라 불일치
③ 범주(category)✅ 정답 보기원 안의 ∪ 기호, 상위 3개 → 하위 1개 구조, OWNER⊆PERSON∪BANK∪COMPANY\text{OWNER} \subseteq \text{PERSON} \cup \text{BANK} \cup \text{COMPANY}OWNER⊆PERSON∪BANK∪COMPANY 라는 합집합 타입의 정의에 정확히 부합
④ 집단화(aggregation)오답 보기관계 자체를 개체로 추상화하는 개념. 다이어그램에서 추상화된 것은 관계 OWNS 가 아니라 세 개체 타입의 합집합이므로 무관

오답 이유​

  • ①이 틀린 이유: 세분화는 "EMPLOYEE를 SECRETARY / ENGINEER / TECHNICIAN으로 나눈다"처럼 하나의 상위 타입에서 출발해 하위로 갈라지는 구조다. 다이어그램의 화살 방향은 PERSON·BANK·COMPANY 셋에서 OWNER 하나로 모이고 있어 정반대다. 만약 OWNER가 상위이고 그 아래에 세 하위가 달렸다면 세분화라 부를 수 있었겠지만, 그렇다면 은행과 사람이 "소유주의 일종"이 되어 의미가 달라진다.

  • ②가 틀린 이유: 일반화는 여러 하위 타입의 공통 속성을 추출해 하나의 상위 타입을 만드는 과정이며, 결과 구조는 세분화와 같은 상위 1개 : 하위 N개다. 얼핏 "세 개체를 묶어 OWNER를 만들었다"는 점에서 일반화처럼 보이지만 결정적 차이가 있다. 일반화에서는 상위가 만들어지고 하위가 상위의 모든 속성을 상속하는 반면, 범주에서는 하위가 만들어지고 각 인스턴스가 자기 상위의 속성만 선택적으로 상속한다. 또한 일반화라면 원 안에 d/o 가 들어가지 ∪ 가 들어가지 않는다.

  • ③이 맞는 이유: 원 안의 ∪ 기호는 EER 표기법에서 범주 전용이다. 구조(상위 다수 → 하위 1개), 기호(∪), 의미(합집합 타입, 선택적 상속)가 모두 일치한다. Elmasri/Navathe 교재의 대표 예제인 OWNER–VEHICLE 사례가 그대로 출제된 문항이다.

  • ④가 틀린 이유: 집단화는 "EMPLOYEE와 PROJECT의 근무 관계"처럼 관계를 하나의 개체로 승격시켜 그 위에 다시 관계를 걸 때 쓰는 추상화다. 본 다이어그램의 OWNS 관계는 평범한 M:N 관계일 뿐 개체로 승격되지 않았고, 추상화의 대상은 관계가 아니라 세 개체 타입의 집합이다. 상속 기호(⊂)가 등장한다는 점에서도 집단화와 구별된다.

핵심 정리​

  • 범주(category) = 합집합 타입(union type) — 하위⊆상위1∪상위2∪⋯\text{하위} \subseteq \text{상위}_1 \cup \text{상위}_2 \cup \cdots하위⊆상위1​∪상위2​∪⋯ 를 표현하며, 원 안의 ∪ 기호로 표기한다.
  • 판별 요령: 상위 타입이 몇 개인가를 먼저 세라. 상위가 1개면 세분화/일반화, 여러 개면 범주 또는 공유 하위 타입이다.
  • 상위가 여럿일 때의 2차 판별: 선이 ∪ 원으로 모이면 범주(OR, 선택적 상속), 개별 ⊂ 선으로 각각 연결되면 공유 하위 타입(AND, 전부 상속) 이다.
  • 범주의 실익은 키와 속성이 전혀 다른 이질적 개체들을 하나의 관계에 참여시킬 수 있다는 것이다. 그래서 보통 대리 키를 둔다.
  • 이 문제의 결정타: PERSON·BANK·COMPANY 세 상위 타입의 선이 ∪ 원 하나로 모여 OWNER로 내려가는 구조 — 이것은 EER에서 오직 범주(category)만의 표기다.

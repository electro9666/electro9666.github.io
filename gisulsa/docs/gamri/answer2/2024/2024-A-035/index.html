035번 · 타입 코드(type code) 리팩토링 후의 클래스 다이어그램

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. 타입 코드(Type Code)란 무엇이고 왜 냄새인가​

객체의 종류를 정수나 문자열 상수로 표현한 필드를 타입 코드라고 한다.

class Video {
    private int kindCode;    // 0 = VHS, 1 = CD
    private int priceCode;   // 0 = Normal, 1 = Discount
}

타입 코드 자체는 컴파일러가 막지 않지만, 시간이 지나면 타입 코드 값을 검사하는 switch/if 분기가 코드 곳곳에 퍼진다. 종류가 하나 늘 때마다 모든 분기문을 찾아 고쳐야 하므로 Shotgun Surgery 로 이어지고, 잘못된 정수 값을 넣어도 컴파일러가 잡지 못한다. 그래서 Fowler는 타입 코드를 제거하는 리팩토링을 여러 개 마련해 두었다.

2. 타입 코드 제거 3형제 — 선택 기준은 "변경 가능성"​

기법적용 조건결과 구조관계
Replace Type Code with Class타입 코드가 행위에 영향을 주지 않고 단순 값일 때타입 코드를 타입 안전한 값 클래스로 대체연관
Replace Type Code with Subclasses타입 코드가 행위에 영향을 주고, 객체 생성 후 변하지 않을 때(불변)타입 코드 값마다 서브클래스를 만들고 원 클래스를 추상 클래스로상속(일반화)
Replace Type Code with State/Strategy타입 코드가 행위에 영향을 주지만, 실행 중 값이 바뀔 수 있을 때(가변)타입 코드를 상태/전략 객체로 뽑고 원 클래스가 이를 보유연관(위임)

핵심은 두 번째 열이다.

  • 불변(immutable)이면 서브클래싱: 객체의 클래스는 생성 후 바꿀 수 없으므로, "종류"가 절대 변하지 않는 경우에만 서브클래스로 표현할 수 있다.
  • 가변(mutable)이면 위임: 실행 중 종류가 바뀌어야 한다면 서브클래스로는 표현이 불가능하다(Java/C++에서 객체의 클래스를 런타임에 바꿀 수 없다). 대신 별도의 상태 객체를 필드로 두고 그 참조를 교체하면 종류 변경이 가능해진다. 이것이 State/Strategy 패턴이다.

3. UML 클래스 다이어그램 표기법 — 이 문제에서 반드시 구분할 4가지​

관계선 모양화살촉의미
일반화(Generalization)실선속이 빈 삼각형상속. "B는 A의 일종이다"
실체화(Realization)점선속이 빈 삼각형인터페이스 구현. "B는 인터페이스 A를 구현한다"
연관(Association)실선열린 화살표(꺾인 선) 또는 무표기구조적 참조. "A는 B를 가리킨다"
의존(Dependency)점선열린 화살표일시적 사용 관계

실선 vs 점선이 일반화와 실체화를 가르는 유일한 시각적 차이이며, 화살촉(빈 삼각형)은 동일하다. 따라서 다이어그램 보기 문제에서는 선이 실선인지 점선인지를 반드시 확인해야 한다.

또한 추상 클래스와 인터페이스의 표기 차이도 알아야 한다.

요소표기하위 요소와의 연결선
추상 클래스클래스명을 이탤릭체 로 표기(또는 «abstract»)일반화 = 실선 + 빈 삼각형
인터페이스«interface» 스테레오타입실체화 = 점선 + 빈 삼각형

4. 속성 표기와 제약(constraint)​

UML 속성 표기법은 가시성 이름 : 타입 [다중도] = 기본값 {제약} 형식이다.

기호/키워드의미
-private 가시성
+public 가시성
# protected 가시성
{readOnly}읽기 전용. 객체 생성 시 값이 정해지고 이후 변경 불가(불변)
{ordered}, {unique}컬렉션 속성의 순서·유일성 제약

{readOnly} 는 이 문항의 결정적 단서다. 위 2절의 선택 기준("불변이면 서브클래스, 가변이면 State/Strategy")을 적용할 근거를 UML 표기가 직접 제공하고 있기 때문이다.

5. 혼동하기 쉬운 인접 개념​

착각실제
타입 코드는 무조건 서브클래스로 바꾸면 된다값이 변할 수 있으면 서브클래싱 불가. State/Strategy로 위임해야 한다
추상 클래스와 서브클래스는 점선으로 잇는다실선 + 빈 삼각형(일반화). 점선은 인터페이스 구현(실체화) 전용
클래스명이 이탤릭이면 인터페이스다이탤릭은 추상 클래스. 인터페이스는 «interface» 로 표기

정답​

상세 풀이​

1단계 — 원본 클래스에서 단서 읽기​

지문 위의 원본 클래스 다이어그램은 다음과 같다.

┌─────────────────────────────┐
│           Video             │
├─────────────────────────────┤
│ -  kindCode: int {readOnly} │
│ -  priceCode: int           │
└─────────────────────────────┘

두 속성의 차이는 제약 표기 하나뿐이다.

속성의미하는 값제약변경 가능성
kindCodeVHS, CD{readOnly}불변 — 생성 후 바뀌지 않음
priceCodeNormal, Discount없음가변 — 실행 중 바뀔 수 있음

비디오테이프의 매체 종류(VHS/CD) 는 물리적으로 정해지면 바뀌지 않지만, 가격 정책(정가/할인) 은 프로모션에 따라 언제든 바뀔 수 있다는 도메인 상식과도 일치한다.

2단계 — 각 속성에 적용할 기법 결정​

속성변경 가능성적용 기법결과 구조다이어그램상 모양
kindCode {readOnly}불변Replace Type Code with SubclassesVideo 를 추상 클래스로 하고 VHS, CD 서브클래스 생성Video 아래로 일반화(실선 + 빈 삼각형)
priceCode가변Replace Type Code with State/Strategy추상 클래스 Price 와 서브클래스 Normal, Discount 를 만들고 Video 가 Price 를 보유Video → Price 연관, Price 아래로 일반화(실선)

따라서 정답 다이어그램이 갖춰야 할 조건은 세 가지다.

  1. Video 의 서브클래스가 VHS, CD 여야 한다. (불변 속성이 상속 계층)
  2. Video 가 연관(위임)하는 추상 클래스는 Price 여야 한다. (가변 속성이 위임 계층)
  3. Price 와 Normal/Discount 는 실선(일반화)으로 연결되어야 한다. Price 는 인터페이스가 아니라 이탤릭체로 표기된 추상 클래스이기 때문이다.

3단계 — 네 보기 대조​

원본 이미지의 네 다이어그램을 직접 확인한 결과는 다음과 같다.

보기Video 의 서브클래스Video 가 연관하는 클래스그 클래스의 서브클래스하위 계층의 선 모양
①VHS, CDPriceNormal, Discount양쪽 모두 실선(일반화)
②Normal, DiscountKindVHS, CD양쪽 모두 실선(일반화)
③VHS, CDPriceNormal, DiscountVideo 쪽은 실선, Price 쪽은 점선(실체화)
④Normal, DiscountKindVHS, CDVideo 쪽은 실선, Kind 쪽은 점선(실체화)
  • ① 은 조건 1·2·3을 모두 만족한다. → 정답
  • ②·④ 는 조건 1·2를 정반대로 적용했다. 불변인 kindCode를 위임 계층(Kind)으로, 가변인 priceCode를 상속 계층으로 만들었다.
  • ③ 은 계층 배치(조건 1·2)는 ①과 같지만 조건 3을 위반했다. Price 가 추상 클래스(이탤릭 클래스 표기)인데 Normal/Discount 를 점선으로 연결해 실체화 관계로 그렸다.

4단계 — 결론​

세 조건을 모두 만족하는 것은 ① 뿐이다.

보기별 판정​

보기판정근거
① Video ← VHS/CD 상속 + Video → Price 연관 + Price ← Normal/Discount 상속(실선)✅ 정답 보기불변 kindCode 는 서브클래스로, 가변 priceCode 는 State/Strategy 위임으로. 두 상속 관계 모두 실선(일반화)으로 올바르게 표기
② Video ← Normal/Discount 상속 + Video → Kind 연관 + Kind ← VHS/CD 상속오답 보기기법 적용 대상이 정반대. 가변인 priceCode를 서브클래스로, 불변인 kindCode를 위임으로 처리
③ ①과 같은 배치이나 Price ← Normal/Discount 가 점선오답 보기Price 는 추상 클래스이므로 일반화(실선) 를 써야 한다. 점선은 인터페이스 실체화 표기
④ ②와 같은 배치이며 Kind ← VHS/CD 가 점선오답 보기기법 적용 대상이 반대인 데다 표기법까지 틀렸다(이중 오류)

오답 이유​

  • ①이 맞는 이유: {readOnly} 는 UML에서 "생성 이후 값을 바꿀 수 없다"는 제약이다. 값이 절대 바뀌지 않으므로 객체의 클래스 자체로 종류를 표현해도 무방하다 → VHS, CD 서브클래스. 반대로 priceCode 에는 제약이 없어 실행 중 Normal ↔ Discount 로 바뀔 수 있는데, 자바·C++에서는 객체가 이미 생성된 뒤 그 클래스를 바꿀 수 없으므로 서브클래싱으로는 표현할 수 없다 → Price 객체를 필드로 들고 참조를 교체하는 State/Strategy. 표기도 둘 다 추상 클래스에 대한 상속이므로 실선 + 빈 삼각형이 맞다.
  • ②가 틀린 이유: 두 기법의 적용 대상이 완전히 뒤바뀌었다. 이 구조에서는 가격 정책이 바뀔 때마다 Video 객체를 Normal 에서 Discount 로 다시 만들어야 하는데, 이는 객체의 식별자와 나머지 상태를 모두 옮겨야 한다는 뜻이라 현실적으로 불가능하다. 반대로 절대 바뀌지 않는 매체 종류를 굳이 교체 가능한 Kind 객체로 위임하는 것은 불필요한 간접 계층을 만든다.
  • ③이 틀린 이유: 계층 배치는 옳게 판단했으므로 절반은 맞혔지만, UML 표기법에서 걸린다. 보기 ③의 Price 는 다른 보기들과 동일하게 이탤릭체 클래스 박스로 그려진 추상 클래스다. 추상 클래스와 그 하위 클래스는 일반화 관계 = 실선 + 속이 빈 삼각형으로 이어야 하고, 점선 + 빈 삼각형은 인터페이스 실체화(realization) 전용이다. 올바르게 고치려면 점선을 실선으로 바꾸거나, Price 를 «interface» 로 선언해야 한다.
  • ④가 틀린 이유: ②의 배치 오류와 ③의 표기 오류를 모두 갖고 있다. 기법 적용 대상도 반대이고, Kind 와 VHS/CD 사이도 점선이다. 네 보기 중 가장 명확히 배제된다.

핵심 정리​

  • 타입 코드 제거 기법의 선택 기준은 변경 가능성 하나다. 불변 → Replace Type Code with Subclasses(상속), 가변 → Replace Type Code with State/Strategy(위임). 행위와 무관한 단순 값이면 Replace Type Code with Class.
  • 가변 타입 코드를 서브클래스로 바꿀 수 없는 이유는 객체 생성 후에는 클래스를 바꿀 수 없기 때문이다. State/Strategy는 참조 교체로 이를 우회한다.
  • UML: 일반화 = 실선 + 빈 삼각형(상속), 실체화 = 점선 + 빈 삼각형(인터페이스 구현). 이탤릭 클래스명은 추상 클래스다.
  • kindCode: int {readOnly} 의 {readOnly} 한 단어가 "VHS/CD는 상속, Normal/Discount는 위임"을 결정한다 — 이것이 ②·④를 버리게 하는 결정타이고, Price 하위의 선이 실선인지 점선인지가 ③을 버리게 하는 결정타다.

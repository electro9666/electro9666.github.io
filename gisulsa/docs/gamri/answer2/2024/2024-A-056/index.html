056번 · N:M 관계의 관계 모델 사상(mapping)

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. E-R 다이어그램의 표기법​

기호의미
사각형개체 타입(entity type) — 예: STUDENT, COURSE
마름모관계 타입(relationship type) — 예: ENROL
타원속성(attribute)
밑줄 친 타원기본키 속성
이중 타원다중값 속성
점선 타원유도 속성
선 위의 1 / N / M카디널리티 비율(관계에 참여하는 개수)
이중선전체 참여(total participation)

2. 카디널리티 비율 3종​

비율의미예
1:1한쪽 개체 하나가 상대 개체 하나와만 관계사원 ↔ 사원증
1:N한쪽 개체 하나가 상대 개체 여럿과 관계부서 ↔ 사원
N:M양쪽 모두 상대 여럿과 관계학생 ↔ 과목(수강)

3. E-R 모델 → 관계 모델 사상 규칙 (이 문항의 핵심)​

사상 대상규칙결과
개체 타입개체마다 릴레이션 1개 생성, 개체의 키 속성이 기본키STUDENT(SNO, Name)
1:1 관계어느 한쪽에 상대의 기본키를 외래키로 추가(전체 참여 쪽에 두는 것이 유리)릴레이션 추가 없음
1:N 관계N쪽(자식) 릴레이션에 1쪽의 기본키를 외래키로 추가. 관계 속성도 N쪽에 추가릴레이션 추가 없음
N:M 관계반드시 별도의 관계 릴레이션 생성. 양쪽 개체의 기본키를 모두 외래키로 가져와 그 조합을 복합 기본키로 삼고, 관계 속성을 일반 속성으로 포함릴레이션 1개 추가
다중값 속성별도 릴레이션 생성(개체 키 + 다중값 속성이 복합 기본키)릴레이션 1개 추가
약한 개체소유 개체의 기본키 + 부분키를 복합 기본키로릴레이션 1개 추가

4. 왜 N:M 관계는 반드시 별도 릴레이션이어야 하는가​

한 학생이 여러 과목을 듣고, 한 과목을 여러 학생이 듣는다고 하자. 만약 STUDENT에 CNO를 넣으면 다음과 같은 문제가 생긴다.

STUDENT(SNO, Name, CNO, Grade)
S01, 김철수, DB101, A
S01, 김철수, OS201, B     ← SNO가 더 이상 유일하지 않다!
  • 기본키 붕괴: SNO 하나가 여러 행에 나타나 SNO는 더 이상 기본키가 될 수 없다.
  • 1NF 위반 또는 중복: 한 칸에 DB101, OS201 처럼 여러 값을 넣으면 제1정규형 위반이고, 행을 늘리면 Name이 중복 저장된다.
  • 의미 왜곡: SNO를 기본키로 유지하려면 학생당 과목이 하나여야 하므로 N:M이 1:N으로 축소된다.

따라서 N:M은 양쪽 개체의 기본키 조합을 키로 하는 제3의 릴레이션으로 표현해야 한다. 이 릴레이션을 교차 릴레이션(associative / junction / bridge table) 이라고 부른다.

5. 관계 속성(relationship attribute)의 배치 규칙​

관계 타입에 붙은 속성(여기서는 Grade)은 "어느 학생의 어느 과목"이라는 쌍이 정해져야 값이 결정되는 속성이다.

카디널리티관계 속성을 어디에 두는가
1:1외래키를 넣은 쪽 릴레이션
1:NN쪽 릴레이션
N:M새로 만든 관계 릴레이션

Grade를 STUDENT에 두면 "학생당 성적 하나", COURSE에 두면 "과목당 성적 하나"가 되어 둘 다 틀리다. Grade는 (SNO, CNO) 쌍에 함수적으로 종속되므로 그 쌍을 키로 갖는 릴레이션에 있어야 한다.

6. 혼동하기 쉬운 인접 개념​

혼동 지점정리
관계 릴레이션에 별도 인공키를 둘 수 있는가실무에서는 ENROL_ID 같은 대리키를 쓰기도 하지만, 이론상 사상 결과는 (SNO, CNO) 복합 기본키다
관계 릴레이션에 외래키만 있으면 되나외래키 조합이 동시에 기본키여야 한다. 기본키가 없으면 릴레이션이 성립하지 않는다
1:N인데 관계 릴레이션을 만들면 틀린가정보 손실은 없지만 불필요한 조인이 생기므로 표준 사상 규칙은 N쪽에 외래키를 넣는 것이다
다대다를 1:N 두 개로 본다는 말관계 릴레이션을 만들면 STUDENT 1:N ENROL M:1 COURSE 구조가 된다. 같은 이야기다

문제​

정답​

④

상세 풀이​

0단계 — 다이어그램 읽기​

원본 이미지를 확인하면 다이어그램의 구성은 다음과 같다.

요소내용
개체 STUDENT (사각형)속성 SNO(밑줄 = 기본키), Name
개체 COURSE (사각형)속성 CNO(밑줄 = 기본키), CName
관계 ENROL (마름모)속성 Grade
카디널리티STUDENT 쪽 N, COURSE 쪽 M → N:M 다대다

즉 "Grade라는 관계 속성을 가진 N:M 관계" 라는, N:M 사상 규칙을 묻는 가장 전형적인 형태다.

1단계 — 개체 타입 사상​

각 개체는 릴레이션 하나가 된다.

STUDENT(SNO, Name)     -- 기본키 SNO
COURSE(CNO, CName)     -- 기본키 CNO

이 두 릴레이션에는 관계와 관련된 속성이 전혀 들어가지 않는다. 보기 ②·③·④가 이 형태를 유지하고 있고, ①만 STUDENT에 CNO·Grade를 끼워 넣었다.

2단계 — 카디널리티 확인 → N:M​

다이어그램의 STUDENT 쪽에 N, COURSE 쪽에 M 이 표기되어 있으므로 다대다다. 사상 규칙에 따라 별도의 관계 릴레이션이 반드시 필요하다.

이 시점에서 관계 릴레이션이 없는 ①·②는 즉시 탈락한다.

3단계 — 관계 릴레이션 구성​

N:M 사상 규칙을 그대로 적용한다.

구성 요소내용역할
SNOSTUDENT의 기본키를 가져옴외래키 + 복합 기본키의 일부
CNOCOURSE의 기본키를 가져옴외래키 + 복합 기본키의 일부
Grade관계 타입 ENROL의 속성일반 속성
ENROL(SNO, CNO, Grade)
  기본키 : (SNO, CNO)
  외래키 : SNO → STUDENT(SNO), CNO → COURSE(CNO)

문제의 단서 "이탤릭체는 외래 키를 의미한다"에 맞춰 보기 ④를 보면 ENROL(*SNO, CNO*, Grade) 처럼 SNO와 CNO가 이탤릭으로 표기되어 있어 두 속성이 외래키임을 정확히 나타낸다.

4단계 — 최종 스키마​

CREATE TABLE STUDENT (
  SNO   CHAR(5) PRIMARY KEY,
  Name  VARCHAR(50)
);
CREATE TABLE COURSE (
  CNO   CHAR(5) PRIMARY KEY,
  CName VARCHAR(50)
);
CREATE TABLE ENROL (
  SNO   CHAR(5),
  CNO   CHAR(5),
  Grade CHAR(2),
  PRIMARY KEY (SNO, CNO),
  FOREIGN KEY (SNO) REFERENCES STUDENT(SNO),
  FOREIGN KEY (CNO) REFERENCES COURSE(CNO)
);

→ 보기 ④ 와 일치한다.

5단계 — 데이터로 확인​

"학생 S01이 DB101에서 A, OS201에서 B를 받았다"는 사실을 각 보기 구조에 담아 보면 차이가 분명해진다.

구조저장 가능?문제점
① STUDENT(SNO, Name, CNO, Grade)❌S01 행이 두 개 필요 → SNO가 기본키일 수 없음. 학생당 과목 1개로 축소됨
② COURSE(CNO, CName, SNO, Grade)❌DB101을 여러 학생이 들으면 CNO 행이 여러 개 → CNO가 기본키일 수 없음
③ ENROL(Grade)❌(A), (B) 만 저장 → 누구의 어느 과목 성적인지 알 수 없음. 기본키 부재
④ ENROL(SNO, CNO, Grade)✅(S01, DB101, A), (S01, OS201, B) — 정확히 표현됨

보기별 판정​

보기판정근거
① STUDENT(SNO, Name, CNO, Grade), COURSE(CNO, CName)오답 보기1:N 사상 방식을 N:M에 잘못 적용. 한 학생이 한 과목만 수강 가능해져 관계가 왜곡되고, SNO가 기본키 자격을 잃는다
② STUDENT(SNO, Name), COURSE(CNO, CName, SNO, Grade)오답 보기①과 같은 오류를 방향만 바꾼 것. 한 과목을 한 학생만 수강 가능해진다
③ STUDENT(SNO, Name), COURSE(CNO, CName), ENROL(Grade)오답 보기관계 릴레이션은 만들었으나 양쪽 외래키(SNO, CNO)를 누락. 기본키가 없어 어느 학생의 어느 과목 성적인지 식별 불가
④ STUDENT(SNO, Name), COURSE(CNO, CName), ENROL(SNO, CNO, Grade)✅ 정답 보기N:M 사상 규칙 그대로 — 별도 관계 릴레이션 + 양쪽 기본키를 외래키 겸 복합 기본키로 + 관계 속성 Grade 포함

오답 이유​

  • ①이 틀린 이유: STUDENT에 CNO를 외래키로 넣는 것은 1:N 관계의 사상 방식이다. 이 구조는 "학생 하나가 과목 하나를 가리킨다"는 뜻이므로, 한 학생이 여러 과목을 수강하는 N:M 관계를 표현할 수 없다. 억지로 여러 행을 만들면 SNO가 중복되어 기본키 제약이 깨지고, Name이 반복 저장되어 갱신 이상이 생긴다. 또한 Grade를 STUDENT에 두면 "학생당 성적 하나"라는 잘못된 의미가 된다. 다이어그램에 N과 M이 함께 표기된 것을 놓치고 1:N으로 읽으면 이 보기를 고르게 된다.
  • ②가 틀린 이유: ①과 완전히 동일한 오류를 방향만 반대로 적용한 것이다. COURSE에 SNO를 넣으면 "과목 하나가 학생 하나를 가리킨다"는 1:N 구조가 되어, 한 과목을 여러 학생이 수강하는 상황을 담을 수 없다. DB101을 30명이 듣는다면 CNO = DB101 인 행이 30개 필요해지고 CNO가 기본키 자격을 잃는다. N:M 관계에서는 어느 쪽에 외래키를 넣더라도 반드시 실패하며, 이것이 별도 릴레이션이 필요한 근본 이유다.
  • ③이 틀린 이유: 별도의 관계 릴레이션을 만든 것까지는 방향이 맞았으나, 관계 릴레이션의 본질인 양쪽 기본키(SNO, CNO)를 빠뜨렸다. ENROL(Grade) 에는 성적 값만 들어 있어 그것이 누구의, 어느 과목 성적인지 식별할 수단이 전혀 없다. 기본키가 없으므로 릴레이션의 정의(투플의 유일성)조차 만족하지 못하고, 실제로는 A, B, C 같은 값이 중복된 무의미한 집합이 된다. 관계 릴레이션의 구성 요소는 "양쪽 기본키(복합 기본키 겸 외래키) + 관계 속성" 세 가지 모두임을 기억해야 한다. N:M 사상 규칙을 절반만 알고 있을 때 걸리는 함정이다.

핵심 정리​

  • N:M 관계는 반드시 별도의 관계 릴레이션으로 사상한다. 그 릴레이션은 양쪽 개체의 기본키를 외래키로 가져와 그 조합을 복합 기본키로 삼고, 관계 속성을 일반 속성으로 포함한다.
  • 카디널리티별 사상 규칙: 1:1 → 어느 한쪽에 외래키 / 1:N → N쪽에 외래키 / N:M → 별도 릴레이션. 릴레이션 개수가 늘어나는 것은 N:M뿐이다.
  • 관계 속성(Grade)은 (SNO, CNO) 쌍에 종속되므로, 그 쌍을 키로 갖는 관계 릴레이션에 있어야 한다. 개체 릴레이션에 두면 의미가 왜곡된다.
  • 관계 릴레이션의 구성은 "양쪽 기본키 + 관계 속성" 세 요소다. 외래키를 빠뜨린 ③ 같은 보기를 걸러내는 것이 이 문항의 두 번째 관문이다.
  • 다이어그램에서 N과 M을 먼저 확인하라. N:M임을 확인하는 순간 ①·②는 즉시 탈락하고, 관계 릴레이션의 키 구성을 보는 순간 ③도 탈락해 ④만 남는다.

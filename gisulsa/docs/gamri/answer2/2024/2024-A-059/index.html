059번 · 인덱스 ROWID를 이용한 테이블 블록 액세스 메커니즘

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. ROWID — 행의 물리적 주소​

ROWID는 테이블의 한 행이 디스크상 어디에 저장되어 있는지를 나타내는 주소값이다. Oracle의 확장 ROWID는 18자리 문자열로 다음 네 요소로 구성된다.

구성 요소자릿수의미
오브젝트 번호(Object ID)6어떤 세그먼트(테이블/파티션)에 속하는가
상대 파일 번호(File #)3어느 데이터 파일인가
블록 번호(Block #)6그 파일의 몇 번째 블록인가
행 번호(Row #)3블록 안에서 몇 번째 행인가

이 중 파일 번호 + 블록 번호를 합친 것을 DBA(Data Block Address) 라고 부르며, 버퍼 캐시를 찾을 때의 검색 키 역할을 한다.

인덱스 리프 블록에는 (인덱스 키 값, ROWID) 쌍이 저장되어 있다. 따라서 인덱스를 스캔해 조건에 맞는 키를 찾으면, 거기에 딸린 ROWID로 테이블의 해당 블록을 직접 찾아갈 수 있다. 이를 테이블 랜덤 액세스(Table Access by Index ROWID) 라고 한다.

2. 버퍼 캐시(Buffer Cache)의 구조​

디스크 I/O는 메모리 접근보다 수만 배 느리므로, DBMS는 자주 쓰는 블록을 메모리에 캐싱한다. 그 메모리 영역이 버퍼 캐시이며, 두 가지 관리 구조를 함께 쓴다.

구조목적동작
해시 체인(Hash Chain)"이 블록이 캐시에 있는가"를 빠르게 찾기DBA에 해시 함수를 적용해 해시 버킷을 정하고, 그 버킷에 매달린 연결 리스트(체인) 를 스캔해 버퍼 헤더를 찾는다
LRU 리스트"어느 버퍼를 비워 재사용할 것인가"를 결정최근 사용 순으로 버퍼를 늘어놓고, 가장 오래 쓰이지 않은 쪽(LRU 끝)부터 재사용 후보로 삼는다

두 구조의 용도가 다르다는 점이 중요하다. 해시 체인은 찾기(lookup) 용, LRU 리스트는 비우기(replacement) 용이다. 순서를 뒤섞어 외우면 이 문항을 틀린다.

3. 버퍼 상태와 Dirty 버퍼​

버퍼 상태의미바로 재사용 가능?
Free (사용 가능)비어 있거나 디스크와 내용이 같음✅ 즉시 가능
Dirty (더티)메모리에서 변경되었으나 아직 디스크에 반영되지 않음❌ 먼저 디스크에 기록(flush)해야 함
Pinned (사용 중)현재 다른 프로세스가 읽거나 쓰는 중❌ 불가

Dirty 버퍼를 그냥 덮어쓰면 변경 내용이 소실되므로, 반드시 DBWR(Database Writer) 프로세스가 디스크에 기록한 뒤에야 재사용할 수 있다.

4. 캐시 히트와 캐시 미스​

경우흐름비용
캐시 히트(hit)DBA 해싱 → 해시 체인 스캔 → 버퍼 발견 → 읽고 종료메모리 접근만 (논리적 읽기)
캐시 미스(miss)DBA 해싱 → 해시 체인 스캔 → 못 찾음 → 빈 버퍼 확보 → 디스크 I/O → 캐시 적재 → 읽기디스크 I/O 발생 (물리적 읽기)

핵심 원칙은 "먼저 메모리를 뒤지고, 없을 때만 디스크로 간다" 이다. 디스크 읽기(보기 ㄴ)는 언제나 맨 마지막에 온다.

5. 전체 메커니즘의 표준 순서​

1. 인덱스 리프 블록에서 ROWID 획득
   → ROWID에서 DBA(파일번호 + 블록번호) 추출
   → DBA에 해시 함수 적용 → 해시 버킷 번호 확인            ← ㄹ

2. 해당 해시 버킷에 연결된 해시 체인을 스캔
   → 원하는 블록의 버퍼 헤더가 있는지 확인                   ← ㄷ
   [발견 → 캐시 히트, 여기서 종료]

   ↓ (캐시 미스인 경우에만 계속)

3. 블록을 적재할 공간이 필요
   → LRU 리스트를 스캔하며 사용 가능한 빈 버퍼 탐색          ← ㄱ

4. 스캔 중 Dirty 버퍼만 만나 빈 버퍼가 없으면
   → DBWR가 Dirty 버퍼를 디스크에 기록해 빈 버퍼 확보       ← ㅁ

5. 확보한 빈 버퍼에 디스크에서 블록을 읽어 적재              ← ㄴ

6. 혼동하기 쉬운 인접 개념​

혼동 지점정리
해시 체인과 LRU 리스트의 순서해시 체인 스캔(찾기)이 먼저, LRU 스캔(비우기)은 못 찾았을 때만. 목적이 다르다
ㄱ(빈 버퍼 탐색)과 ㅁ(Dirty 기록)의 선후ㄱ이 먼저. LRU를 스캔해 보고 빈 버퍼가 없을 때 비로소 ㅁ이 발생한다. ㅁ은 ㄱ의 결과로 생기는 예외 처리다
디스크 읽기(ㄴ)의 위치항상 마지막. 캐시 탐색과 공간 확보가 모두 끝난 뒤에야 물리적 I/O가 일어난다
논리적 읽기 vs 물리적 읽기버퍼 캐시에서 읽으면 논리적 읽기, 디스크까지 가면 물리적 읽기. 튜닝의 목표는 물리적 읽기를 줄이는 것
인덱스 스캔의 비용인덱스로 찾은 ROWID마다 테이블 블록을 1회씩 랜덤 액세스하므로, 대상 행이 많으면 풀 스캔보다 느려질 수 있다

문제​

정답​

②

상세 풀이​

다섯 단계를 인과 관계에 따라 배열하는 순서 배열형 문항이다. 각 보기의 첫 단계와 중간 단계를 기준으로 하나씩 소거하면 빠르다.

1단계 — 출발점은 무엇인가​

문제가 "인덱스 ROWID를 이용해 테이블 블록을 읽는 메커니즘"이라고 명시했으므로, 모든 과정은 인덱스에서 ROWID를 읽는 것에서 시작한다.

ㄹ. 인덱스에서 하나의 ROWID를 읽고 디스크상의 블록위치정보를 해시 함수에 적용해 해시값을 확인한다.

ROWID에서 DBA(파일번호 + 블록번호)를 꺼내 해시 함수에 넣어야 어느 해시 버킷을 봐야 할지 알 수 있다. 해시값이 없으면 다음 단계인 해시 체인 스캔을 시작할 수조차 없다.

  • ③(ㄷ으로 시작) 탈락 — 해시값을 모르는데 어떤 버킷의 체인을 스캔한단 말인가.
  • ①(ㅁ으로 시작) 탈락 — 아직 아무것도 찾아보지 않았는데 Dirty 버퍼부터 기록할 이유가 없다.

남은 후보: ② ㄹ-ㄷ-ㄱ-ㅁ-ㄴ 과 ④ ㄹ-ㄷ-ㅁ-ㄱ-ㄴ

2단계 — ㄷ: 캐시에 이미 있는지 확인​

ㄷ. 해시 버켓에 연결된 해시 체인을 스캔하면서 블록 헤더를 찾는다.

해시 버킷에 매달린 체인을 따라가며 원하는 DBA의 버퍼 헤더가 있는지 본다.

  • 찾으면(캐시 히트) → 그 버퍼를 읽고 여기서 끝난다. 이후 단계는 일어나지 않는다.
  • 못 찾으면(캐시 미스) → 블록을 디스크에서 읽어와야 하므로 다음 단계로 간다.

②·④ 모두 ㄹ-ㄷ 으로 시작하므로 여기까지는 동일하다.

3단계 — ㄱ과 ㅁ, 어느 것이 먼저인가 (②와 ④를 가르는 결정적 지점)​

두 보기의 유일한 차이는 ㄱ(LRU 스캔으로 빈 버퍼 찾기) 과 ㅁ(Dirty 버퍼를 기록해 빈 버퍼 확보) 의 순서다.

보기순서해석
②ㄱ → ㅁ먼저 LRU를 훑어 빈 버퍼를 찾아보고, 없으면 Dirty를 기록해 만든다
④ㅁ → ㄱ무조건 Dirty부터 기록한 뒤 빈 버퍼를 찾는다

인과 관계를 따져 보면 답은 분명하다.

ㅁ은 ㄱ의 결과로 발생하는 예외 처리다.

  • 서버 프로세스는 블록을 적재할 자리가 필요하면 먼저 LRU 리스트를 스캔한다(ㄱ). 이는 "쓸 수 있는 버퍼가 이미 있는지" 확인하는 탐색 행위다.
  • 스캔 도중 Free 버퍼를 만나면 즉시 그것을 쓴다. 이 경우 ㅁ은 아예 일어나지 않는다.
  • 스캔을 계속해도 Dirty 버퍼만 나오면, 그제야 DBWR를 깨워 Dirty 버퍼를 디스크에 기록하게 하고(ㅁ) 빈 버퍼를 확보한다.

즉 탐색(ㄱ)이 먼저이고, 기록(ㅁ)은 탐색이 실패했을 때만 발생하는 후속 조치다. ④처럼 "빈 버퍼가 있는지 확인도 하기 전에 Dirty 버퍼를 디스크에 기록한다"면, 이미 쓸 수 있는 빈 버퍼가 있는 상황에서도 불필요한 디스크 쓰기를 하게 되어 설계상으로도 성립하지 않는다.

→ ④ 탈락, ② 확정

4단계 — ㄴ: 마지막은 디스크 읽기​

ㄴ. 디스크에서 블록을 읽어 버퍼 캐시에 적재한다.

빈 버퍼를 확보한 뒤에야 비로소 디스크 I/O가 일어난다. 적재할 공간 없이 디스크에서 읽어올 수는 없으므로 ㄴ은 반드시 ㄱ·ㅁ 뒤에 온다. ①이 ㄴ을 세 번째에 둔 것도 이 원칙에 어긋난다.

결론​

ㄹ→ㄷ→ㄱ→ㅁ→ㄴ\text{ㄹ} \rightarrow \text{ㄷ} \rightarrow \text{ㄱ} \rightarrow \text{ㅁ} \rightarrow \text{ㄴ}ㄹ→ㄷ→ㄱ→ㅁ→ㄴ

→ 정답 ②

각 단계의 요약​

순서기호단계사용하는 구조목적
1ㄹROWID 읽고 DBA를 해싱인덱스 리프 블록, 해시 함수어느 버킷을 볼지 결정
2ㄷ해시 체인 스캔해시 체인캐시에 있는지 탐색
3ㄱLRU 리스트 스캔LRU 리스트빈 버퍼 탐색
4ㅁDirty 버퍼 디스크 기록DBWR빈 버퍼 확보(예외 처리)
5ㄴ디스크 → 버퍼 캐시 적재디스크 I/O블록 획득

보기별 판정​

보기판정근거
① ㅁ-ㄱ-ㄴ-ㄹ-ㄷ오답 보기ㅁ으로 시작하는 것이 근본적 오류. 아무것도 찾아보지 않은 상태에서 Dirty 버퍼를 기록할 이유가 없고, ROWID를 읽는 ㄹ이 넷째로 밀려 인과가 완전히 뒤집혔다
② ㄹ-ㄷ-ㄱ-ㅁ-ㄴ✅ 정답 보기ROWID 해싱 → 해시 체인 탐색 → LRU 빈 버퍼 탐색 → Dirty 기록으로 확보 → 디스크 적재. 탐색이 기록보다 앞서고, 디스크 I/O가 마지막이라는 두 원칙을 모두 만족
③ ㄷ-ㄹ-ㄱ-ㄴ-ㅁ오답 보기ㄷ으로 시작 — 해시값(ㄹ)을 모르는 상태에서 해시 체인을 스캔할 수 없다. 또한 ㅁ이 디스크 적재(ㄴ) 뒤에 와서 "빈 버퍼 없이 적재"라는 모순이 생긴다
④ ㄹ-ㄷ-ㅁ-ㄱ-ㄴ오답 보기앞 두 단계는 맞으나 ㅁ과 ㄱ의 순서가 뒤바뀜. 빈 버퍼를 찾아보기도 전에 Dirty 버퍼를 기록한다는 것은 불필요한 디스크 쓰기이며 실제 동작과 다르다

오답 이유​

  • ①이 틀린 이유: 순서가 ㅁ-ㄱ-ㄴ-ㄹ-ㄷ 으로, 전체 흐름이 거꾸로 서 있다. 첫 단계 ㅁ(Dirty 버퍼 기록)은 "적재할 빈 버퍼가 없다"는 상황이 확인된 뒤에나 의미가 있는데, 여기서는 그 상황 판단(ㄷ, ㄱ)보다 앞에 놓였다. 더 결정적으로, 모든 과정의 출발점인 ㄹ(인덱스에서 ROWID 읽기)이 네 번째에 있다. ROWID를 읽기도 전에 어떤 블록을 캐시에서 찾고 디스크에서 읽어온다는 것인지 설명할 수 없다. 또한 디스크 적재(ㄴ)가 세 번째에 와서 "캐시 탐색보다 물리적 읽기가 먼저"라는 불가능한 순서가 된다.
  • ③이 틀린 이유: ㄷ(해시 체인 스캔)으로 시작한 점이 첫 오류다. 해시 체인을 스캔하려면 어느 해시 버킷인지를 알아야 하고, 그 버킷 번호는 ㄹ에서 DBA에 해시 함수를 적용해야 나온다. 즉 ㄹ 없이는 ㄷ이 성립할 수 없다. 두 번째 오류는 마지막의 ㄴ → ㅁ 순서다. 디스크에서 블록을 읽어 캐시에 적재(ㄴ)하려면 그 블록을 담을 빈 버퍼가 이미 확보되어 있어야 하는데, 빈 버퍼를 만드는 작업(ㅁ)이 그 뒤에 온다. 적재할 공간 없이 적재한다는 모순이다.
  • ④가 틀린 이유: 앞의 ㄹ-ㄷ 두 단계는 정확하며, 오직 세 번째와 네 번째의 ㅁ·ㄱ 순서만 ②와 다르다. 이 한 곳이 이 문항의 핵심 변별점이다. 실제 동작은 "LRU 리스트를 스캔하면서 사용 가능한 버퍼를 찾다가(ㄱ), 빈 버퍼가 나오지 않고 Dirty 버퍼만 만나면 그때 DBWR에게 기록을 요청한다(ㅁ)"이다. 즉 ㅁ은 ㄱ의 조건부 후속 조치이지 선행 조건이 아니다. ④의 순서대로라면 캐시에 빈 버퍼가 충분히 남아 있는 상황에서도 매번 Dirty 버퍼를 디스크에 쓰게 되어, 불필요한 물리적 쓰기가 발생하고 성능이 크게 떨어진다. "빈 버퍼 탐색이 먼저, Dirty 기록은 그 결과"라는 인과를 정확히 알아야 ②와 ④를 구분할 수 있다.

핵심 정리​

  • ROWID = 오브젝트 번호 + 파일 번호 + 블록 번호 + 행 번호. 이 중 파일 번호 + 블록 번호 = DBA가 버퍼 캐시 탐색의 해시 키가 된다.
  • 버퍼 캐시의 두 구조는 용도가 다르다. 해시 체인 = 찾기(lookup), LRU 리스트 = 비우기(replacement). 따라서 해시 체인 스캔이 LRU 스캔보다 항상 먼저다.
  • ㅁ(Dirty 버퍼 기록)은 ㄱ(LRU 스캔)의 결과로 발생하는 예외 처리다. 빈 버퍼가 바로 발견되면 ㅁ은 일어나지 않는다. 이 인과 관계가 ②와 ④를 가르는 결정타다.
  • 물리적 디스크 읽기(ㄴ)는 언제나 마지막이다. 캐시 탐색과 공간 확보가 모두 끝난 뒤에만 일어난다.
  • 전체 순서는 ㄹ(ROWID 해싱) → ㄷ(해시 체인 탐색) → ㄱ(LRU 빈 버퍼 탐색) → ㅁ(Dirty 기록) → ㄴ(디스크 적재) 이다. "탐색 먼저, 기록은 나중, 디스크는 맨 마지막"으로 기억하면 흔들리지 않는다.

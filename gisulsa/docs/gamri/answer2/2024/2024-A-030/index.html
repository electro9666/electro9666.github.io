030번 · 객체지향 개념 — 다형성과 동적 바인딩

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. 객체지향의 4대 특성​

특성정의무엇을 해결하나
캡슐화(Encapsulation)데이터와 그 데이터를 다루는 연산을 하나의 객체로 묶고, 내부를 외부로부터 감춤내부 구현 변경이 외부로 파급되지 않게 함
정보은닉(Information Hiding)내부 표현·구현 세부를 외부에 노출하지 않고 공개 인터페이스로만 접근하게 함결합도 감소, 변경 국지화
상속(Inheritance)상위 클래스의 속성·연산을 하위 클래스가 물려받음코드 재사용, 계층적 분류
다형성(Polymorphism)같은 메시지(호출)가 수신 객체의 타입에 따라 다르게 동작함조건 분기 제거, 확장에 열린 설계

2. 다형성의 종류​

종류원어결정 시점예
오버로딩(중복 정의)ad-hoc / overloading컴파일 시점(정적 바인딩)print(int), print(String) — 매개변수 시그니처로 구분
오버라이딩(재정의)subtype / inclusion polymorphism실행 시점(동적 바인딩)상위 타입 참조로 호출하면 실제 객체의 재정의 메소드 실행
매개변수 다형성parametric polymorphism컴파일 시점제네릭 List<T>, 템플릿
강제 다형성coercion컴파일/실행자동 형변환(int → double)

정보처리·감리 시험에서 "다형성"이라 하면 대개 오버라이딩 + 동적 바인딩을 가리킨다.

3. 정적 바인딩 vs 동적 바인딩​

ClosedFigure closedFigure;          // 선언 타입(정적 타입) = ClosedFigure
closedFigure = new Rectangle();     // 실제 타입(동적 타입) = Rectangle
closedFigure.getArea();             // 어느 getArea()가 실행되는가?
구분무엇을 기준으로 결정시점
정적(이른) 바인딩선언 타입(변수에 적힌 타입)컴파일
동적(늦은) 바인딩실제 참조 중인 객체의 타입실행

Java·C#의 인스턴스 메소드, C++의 virtual 메소드는 동적 바인딩된다. 내부적으로는 각 클래스마다 가상 함수 테이블(vtable) 을 두고, 객체가 자기 클래스의 테이블을 가리켜 실행 시점에 실제 구현 주소를 찾아간다. 반면 필드(멤버 변수), static 메소드, private/final 메소드는 정적 바인딩되므로 다형성이 적용되지 않는다.

4. 업캐스팅 — 다형성의 전제 조건​

ClosedFigure ← Rectangle
ClosedFigure ← Circle

Rectangle과 Circle이 ClosedFigure의 하위 타입(상속 또는 인터페이스 구현)이므로, 상위 타입 변수에 하위 타입 객체를 대입하는 업캐스팅(upcasting) 이 명시적 형변환 없이 허용된다. 이것이 리스코프 치환 원칙(LSP)이 말하는 "하위 타입은 상위 타입을 대체할 수 있어야 한다"의 실행 형태다.

즉 상속은 다형성이 성립하기 위한 전제이지, 코드에서 드러나는 현상 자체는 아니다. 이 구분이 본 문항의 핵심이다.

5. 다형성이 주는 설계 효과​

다형성이 없다면 도형 면적 계산은 이렇게 된다.

if (obj instanceof Rectangle)   area = ((Rectangle)obj).rectArea();
else if (obj instanceof Circle) area = ((Circle)obj).circleArea();
else if (obj instanceof Triangle) ...   // 도형이 늘 때마다 여기를 수정

다형성을 쓰면 호출부는 한 줄로 끝난다.

area = closedFigure.getArea();   // 도형이 늘어도 호출부는 그대로

새 도형을 추가할 때 기존 코드를 고치지 않고 새 클래스만 추가하면 되므로, 개방-폐쇄 원칙(OCP: 확장에는 열려 있고 수정에는 닫혀 있다) 이 달성된다.

6. 혼동하기 쉬운 인접 개념​

개념코드에서 드러나는 증거본 문항 코드에서
상속class Rectangle extends ClosedFigure 같은 계층 선언선언부가 제시되지 않음. 전제로만 존재
정보은닉private 필드 + getter/setter, 접근 제어자나타나지 않음
의존성한 클래스가 다른 클래스를 사용(매개변수·지역변수·반환형)존재하긴 하나 (가)·(나)의 핵심 현상이 아님
다형성동일한 호출문이 대입된 객체에 따라 다른 결과(가)·(나)가 정확히 이 구조
오버로딩 vs 오버라이딩오버로딩은 시그니처가 다른 동명 메소드, 오버라이딩은 시그니처가 같은 상위 메소드 재정의오버라이딩

상세 풀이​

코드의 구조를 따라가 본다.

ClosedFigure closedFigure;        // 상위 타입 참조변수 선언
Rectangle r = new Rectangle();    // 하위 타입 객체 생성
Circle    c = new Circle();       // 하위 타입 객체 생성

closedFigure = r;                 // 업캐스팅 — 실제 타입은 Rectangle
closedFigure.getArea();  ……… (가) // Rectangle의 getArea() 실행
closedFigure = c;                 // 업캐스팅 — 실제 타입은 Circle
closedFigure.getArea();  ……… (나) // Circle의 getArea() 실행
  • 문법적으로 완전히 동일한 호출문 closedFigure.getArea() 가 두 번 나온다.
  • 그런데 (가)에서는 직사각형 면적 계산(가로 × 세로), (나)에서는 원 면적 계산(πr2\pi r^2πr2)이 실행된다.
  • 차이를 만든 유일한 원인은 그 시점에 참조변수가 가리키고 있는 실제 객체의 타입이다.

"같은 메시지, 다른 동작"이 바로 다형성(polymorphism) 의 정의이며, 구체적으로는 메소드 오버라이딩 + 실행 시점 동적 바인딩에 의해 구현된다. 따라서 ③이 정답이다.

컴파일러는 closedFigure의 선언 타입인 ClosedFigure에 getArea()가 존재하는지만 검사해 통과시키고, 실제 어느 구현을 실행할지는 런타임에 객체의 클래스 정보(vtable)를 보고 결정한다. 이 "컴파일 시점 타입 검사 / 실행 시점 구현 선택"의 분리가 다형성의 기술적 메커니즘이다.

보기별 판정​

보기판정근거
① 상속(inheritance)오답 보기Rectangle·Circle이 ClosedFigure의 하위 타입이라는 관계는 다형성이 성립하기 위한 전제일 뿐, (가)·(나)에서 드러난 현상 자체는 아님. 게다가 코드에 상속 선언부가 제시되어 있지 않음
② 정보은닉(information hiding)오답 보기내부 구현·데이터를 감추고 공개 인터페이스로만 접근하게 하는 원리. 접근 제어자나 getter/setter 구조가 코드에 나타나지 않음
③ 다형성(polymorphism)✅ 정답 보기동일한 호출문 closedFigure.getArea() 가 실제 참조 객체(Rectangle/Circle)에 따라 서로 다른 메소드로 실행됨 = 오버라이딩 + 동적 바인딩
④ 의존성(dependency)오답 보기한 클래스가 다른 클래스를 사용하는 구조적 관계. (가)·(나)가 보여주는 "호출 결과가 달라지는" 핵심 현상을 설명하지 못함

오답 이유​

  • ①이 틀린 이유: 상속은 다형성의 필요조건이다. Rectangle·Circle이 ClosedFigure를 상속(또는 구현)하지 않았다면 closedFigure = r; 대입 자체가 컴파일 오류가 난다. 그러나 문제는 "(가)와 (나)에 나타난 개념"을 묻는다. 코드에 표시된 (가)·(나) 지점에서 관찰되는 것은 계층 관계가 아니라 같은 호출이 다르게 동작하는 현상이다. 상속만으로는 (가)와 (나)가 왜 다른 결과를 내는지 설명되지 않는다.
  • ②가 틀린 이유: 정보은닉은 private 필드와 공개 메소드처럼 접근 범위를 제한하는 설계로 나타난다. 제시된 코드에는 접근 제어자도 없고, 내부 상태를 감추는 구조도 드러나지 않는다. (getArea()라는 메소드 이름 때문에 캡슐화를 떠올리기 쉽지만, 그것은 면적을 반환하는 연산일 뿐 필드 접근자가 아니다.)
  • ③이 맞는 이유: 다형성의 정의 그대로다. 참조변수의 선언 타입은 ClosedFigure로 고정되어 있으나 실제 타입은 대입에 따라 Rectangle → Circle로 바뀌고, 호출되는 getArea() 구현도 함께 바뀐다. 호출부 코드는 한 글자도 달라지지 않았는데 동작이 달라졌다는 점이 결정적이다.
  • ④가 틀린 이유: 의존성(dependency)은 "A가 B를 사용한다"는 구조적 관계로, UML에서 점선 화살표로 표기한다. 이 코드에도 의존 관계가 존재하기는 하지만, 그것은 어느 객체지향 코드에나 있는 일반적 속성이다. (가)·(나)에서 특별히 드러난 개념을 묻는 문항이므로, 호출 결과의 분화를 설명하는 다형성이 답이다.

핵심 정리​

  • 다형성 = 같은 메시지, 다른 동작. 상위 타입 참조로 호출하되 실제 객체의 재정의 메소드가 실행되는 것이 전형적 형태다.
  • 메커니즘: 업캐스팅 → 컴파일러는 선언 타입으로 검사 → 실행 시점에 실제 타입의 구현을 동적 바인딩(vtable) 으로 선택.
  • 오버로딩 = 컴파일 시점(정적 바인딩) / 오버라이딩 = 실행 시점(동적 바인딩) — 시점 대비로 외운다.
  • 다형성의 설계 효과는 instanceof 분기 제거와 개방-폐쇄 원칙(OCP) 달성이다.
  • 상속은 다형성의 '전제'이고 다형성은 '나타난 현상'이다. 동일한 호출문이 대입된 객체에 따라 다른 결과를 낸다면, 묻는 것은 언제나 상속이 아니라 다형성이다.

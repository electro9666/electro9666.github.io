051번 · NoSQL의 4대 데이터 모델과 문서 기반 모델

제25회(2024년) 정보시스템감리사 A형 — 데이터베이스

사전 지식​

1. NoSQL이 등장한 배경​

관계형 DBMS(RDBMS)는 고정 스키마 + ACID 트랜잭션 + 정규화를 전제로 설계되었다. 그러나 웹·모바일·IoT 환경에서 다음 요구가 커지면서 한계가 드러났다.

요구RDBMS의 한계NoSQL의 대응
수평 확장(scale-out)조인·트랜잭션 때문에 샤딩이 어려움샤딩·복제를 기본 아키텍처로 내장
비정형·반정형 데이터컬럼을 미리 정의해야 함스키마리스(schema-less) 저장
초당 수만 건의 쓰기강한 일관성 유지 비용결과적 일관성(eventual consistency) 허용
스키마 변경 빈번ALTER TABLE 비용·잠금레코드마다 구조가 달라도 무방

NoSQL은 "No SQL"이 아니라 "Not Only SQL"로 읽으며, CAP 정리에서 가용성(A)과 분할 내성(P) 을 우선하고 일관성(C)을 완화한 계열이 많다.

2. NoSQL의 4대 데이터 모델 (이 문항의 핵심)​

모델저장 단위값의 구조질의 방식대표 제품
키-값(Key-Value)key → value 한 쌍DB 입장에서 값은 불투명한 바이트 덩어리키로만 조회Redis, Riak, Amazon DynamoDB, Memcached
문서(Document)문서(document) 1건JSON / BSON / XML — 중첩 객체·배열 허용, 자기 기술적(self-describing)키 조회 + 문서 내부 필드 질의·인덱싱MongoDB, CouchDB, Couchbase, Amazon DocumentDB
컬럼 패밀리(Column-Family / Wide-Column)행 키 + 컬럼 패밀리행마다 컬럼 집합이 달라도 됨행 키 범위 스캔Cassandra, HBase, Google Bigtable
그래프(Graph)정점(node) + 간선(edge)관계 자체를 1급 객체로 저장그래프 탐색(Cypher, Gremlin)Neo4j, JanusGraph, Amazon Neptune

시험에서는 "제품명 → 모델" 매핑을 그대로 묻는 경우가 많다. MongoDB → 문서, Redis → 키-값, Cassandra/HBase → 컬럼 패밀리, Neo4j → 그래프 네 쌍은 반드시 외워 둔다.

3. 문서 기반 모델(document based data model)의 특징​

{
  "_id": "S01",
  "name": "홍길동",
  "address": { "city": "서울", "zip": "04524" },
  "courses": [
    { "code": "DB101", "grade": "A" },
    { "code": "OS201", "grade": "B" }
  ]
}
  • JSON 기반 — MongoDB는 이를 이진 직렬화한 BSON(Binary JSON) 으로 저장해 타입(날짜, 정수, 바이너리)과 탐색 성능을 보강한다. CouchDB는 순수 JSON을 쓴다.
  • 중첩(nested) 구조와 배열을 그대로 담아, 관계형이라면 여러 테이블로 쪼개 조인해야 할 데이터를 한 문서에 응집시킨다(비정규화 지향).
  • 자기 기술적(self-describing) — 각 문서가 필드 이름을 함께 갖고 있어 문서마다 구조가 달라도 된다.
  • 키-값 모델과 달리 값의 내부를 DB가 이해하므로, db.students.find({ "address.city": "서울" }) 처럼 내부 필드에 대한 질의와 보조 인덱스가 가능하다. 이것이 키-값과 문서 모델을 가르는 결정적 차이다.

4. 혼동하기 쉬운 인접 개념​

용어실제 의미이 문항과의 관계
객체 지향 데이터 모델(OODM)클래스·상속·다형성·메소드까지 DB에 저장하는 OODBMS(ObjectStore, db4o, Versant)의 모델. 1990년대에 등장했으며 NoSQL 계열이 아니다.보기 ②. "객체를 저장한다"는 지문 표현에 낚이기 쉽다
객체-관계 데이터 모델(ORDM)RDBMS에 사용자 정의 타입·상속을 더한 것(PostgreSQL, Oracle Object Type)역시 NoSQL 분류가 아님
구조 기반 데이터 모델NoSQL·데이터 모델링 이론 어디에도 존재하지 않는 용어보기 ③, 출제자가 만든 허구
자바 기반 데이터 모델존재하지 않는 용어. MongoDB는 C++로 구현되었고 언어 중립적 드라이버를 제공한다보기 ④, 허구

상세 풀이​

지문의 두 단서를 각각 어떤 모델이 만족하는지 확인하는 지목형 문항이다.

1단계 — 단서 ①: "JSON을 기반으로 복잡한 구조의 객체를 저장"​

NoSQL 4대 모델 중 JSON을 저장 포맷으로 명시하는 것은 문서 기반 모델뿐이다.

  • 키-값: 값이 불투명한 바이트열이므로 JSON일 수도 있으나, DB가 그 구조를 해석하지 않는다. "복잡한 구조의 객체를 데이터로 저장한다"는 표현과 맞지 않는다.
  • 컬럼 패밀리: 행-컬럼의 2차원 구조이며 JSON 중첩 문서가 아니다.
  • 그래프: 정점·간선 구조이며 JSON 문서 단위가 아니다.

2단계 — 단서 ②: "대표적인 제품이 MongoDB"​

MongoDB는 문서 기반 NoSQL의 사실상 표준 제품이다. 데이터를 BSON 문서로 저장하고, 컬렉션(collection) 단위로 문서를 묶는다.

관계형 용어MongoDB 대응
테이블(table)컬렉션(collection)
행(row/tuple)문서(document)
열(column)필드(field)
기본키_id
조인집계 파이프라인의 lookup 스테이지(제한적) / 문서 내 임베딩

3단계 — 결론​

두 단서가 모두 문서 기반 데이터 모델을 가리킨다 → 정답 ①.

나머지 세 보기 중 ②는 실재하지만 NoSQL이 아닌 OODBMS의 모델이고, ③·④는 데이터 모델 분류 체계에 존재하지 않는 용어다.

보기별 판정​

보기판정근거
① 문서 기반 데이터 모델✅ 정답 보기JSON/BSON 문서 단위 저장 + 중첩 구조 허용 + 대표 제품 MongoDB — 지문의 두 단서를 모두 만족
② 객체 지향 데이터 모델오답 보기OODBMS(ObjectStore, db4o)의 모델. 클래스·상속·메소드를 저장하며 NoSQL 4대 분류에 속하지 않는다. MongoDB는 OODBMS가 아니다
③ 구조 기반 데이터 모델오답 보기존재하지 않는 용어. NoSQL 분류(키-값/문서/컬럼 패밀리/그래프) 어디에도 없다
④ 자바 기반 데이터 모델오답 보기존재하지 않는 용어. JSON의 "JavaScript"를 Java로 오인하게 만든 함정이며, JavaScript와 Java는 무관하다

오답 이유​

  • ②가 틀린 이유: 객체 지향 데이터 모델은 1990년대 OODBMS(ObjectStore, db4o, Versant)가 채택한 모델로, 클래스 정의·상속 관계·메소드(행위)까지 데이터베이스가 관리한다는 점이 핵심이다. 반면 MongoDB의 문서는 데이터(상태)만 담을 뿐 메소드나 상속 계층을 저장하지 않는다. 또한 OODM은 애초에 NoSQL 운동보다 10년 이상 앞서 나온 개념이라 "빅데이터 시스템의 NoSQL 데이터 모델 중 하나"라는 지문 전제와도 어긋난다. "복잡한 구조의 객체"라는 문구만 보고 고르면 안 된다.
  • ③이 틀린 이유: "구조 기반 데이터 모델"이라는 명칭은 NoSQL 분류 체계는 물론 일반 데이터 모델링 이론에도 존재하지 않는다. 출제자가 그럴듯한 한자어를 조합해 만든 보기다. 계층형·망형·관계형·객체형이 전통적 4대 데이터 모델이고, NoSQL 쪽은 키-값·문서·컬럼 패밀리·그래프 4종이다. 이 8개 어디에도 "구조 기반"은 없다.
  • ④가 틀린 이유: JSON의 "JS"는 JavaScript이지 Java가 아니며, 두 언어는 이름만 비슷할 뿐 계통이 전혀 다르다. 이 보기는 그 혼동을 노린 함정이다. 또한 MongoDB 서버는 C++로 작성되었고, Java·Python·Node.js·Go 등 다양한 언어 드라이버를 제공하므로 "자바 기반"이라 부를 근거도 없다. "자바 기반 데이터 모델"이라는 분류 자체가 존재하지 않는다.

핵심 정리​

  • NoSQL 4대 데이터 모델은 키-값 / 문서 / 컬럼 패밀리 / 그래프다. 대표 제품 매핑(Redis / MongoDB / Cassandra·HBase / Neo4j)까지 함께 외운다.
  • 문서 모델 = JSON·BSON·XML 문서 단위 저장 + 중첩 객체·배열 + 자기 기술적 스키마. 키-값과의 차이는 DB가 값의 내부를 해석해 필드 단위 질의·인덱싱이 가능한가이다.
  • 객체 지향 데이터 모델은 OODBMS의 모델이며 NoSQL 분류에 포함되지 않는다. "객체를 저장한다"는 표현에 현혹되지 말 것.
  • "MongoDB" 한 단어만 보고도 문서 기반 모델을 즉시 지목할 수 있어야 한다. 나머지 두 보기(구조 기반·자바 기반)는 실재하지 않는 용어이므로, 실제로는 ①과 ② 사이의 2지선다 문제다.

037번 · 변성 테스팅(Metamorphic Testing)

제25회(2024년) 정보시스템감리사 A형 — 소프트웨어 공학

사전 지식​

1. 테스트 오라클 문제(Test Oracle Problem)​

테스트를 하려면 "이 입력에 대한 올바른 출력은 무엇인가" 를 판정할 수 있어야 한다. 이 판정 기준을 테스트 오라클(test oracle) 이라고 한다.

그런데 현실에는 오라클을 얻기 어려운 소프트웨어가 많다.

유형예시오라클을 얻기 어려운 이유
과학·수치 계산미분방정식 해석기, 유한요소 해석정답을 사람이 손으로 계산할 수 없음
검색·추천검색 엔진 랭킹, 추천 시스템"정확한 정답 목록"이 정의되지 않음
기계학습분류기, 번역기, 자율주행 인식개별 입력의 정답 라벨을 모두 알 수 없음
컴파일러·최적화코드 최적화 결과기대 출력 코드가 유일하지 않음
대규모 그래프·경로 탐색지도 경로 거리 계산모든 지점 쌍의 정답 거리를 미리 알 수 없음

이런 상황을 테스트 오라클 문제라 하며, 이를 우회하기 위해 고안된 기법이 변성 테스팅이다.

2. 변성 테스팅(Metamorphic Testing)의 원리​

핵심 발상은 다음과 같다.

개별 출력의 정답을 몰라도, 여러 실행 결과들 사이에 반드시 성립해야 하는 "관계"는 알 수 있다.

이 관계를 변성 관계(Metamorphic Relation, MR) 라고 한다. 절차는 세 단계다.

  1. 원본 테스트케이스(source test case) 를 하나 실행해 출력을 얻는다. 이 출력이 맞는지는 판정하지 않는다.
  2. 변성 관계에 따라 입력을 변형해 후속 테스트케이스(follow-up test case) 를 만들고 실행한다.
  3. 두 출력이 변성 관계를 위반하면 결함이 있다고 판정한다.

변성 관계를 위반하면 둘 중 적어도 하나는 틀렸다는 사실이 확정되므로, 개별 정답을 몰라도 결함의 존재를 증명할 수 있다. 다만 관계를 만족한다고 해서 둘 다 옳다는 보장은 없다(둘 다 같은 방식으로 틀렸을 수 있다).

3. 대표적인 변성 관계 유형​

유형변성 관계예시
대칭성(symmetry)f(a, b) = f(b, a)무방향 그래프의 거리 getDistance(A,B) = getDistance(B,A)
순열 불변(permutation)입력 순서를 바꿔도 결과 동일sort 결과, 합계·평균
가법성/배수성입력을 k배 하면 출력도 k배선형 시스템, 면적 계산
포함 관계(monotonicity)입력 집합이 커지면 결과가 줄지 않음검색 색인에 문서를 추가하면 검색 결과 수가 줄지 않음
주기성sin(x) = sin(x + 2π)삼각함수 라이브러리
의미 보존 변환동의어 치환 후에도 분류 결과 동일텍스트 분류기, 기계번역
삼각 부등식d(A,C) ≤ d(A,B) + d(B,C)경로 거리 계산

특히 첫 번째 행 대칭성이 본 문항의 상황과 정확히 일치한다.

4. 비교 대상 기법들​

기법분류케이스 도출 근거오라클이 필요한가
Equivalence partitioning(동등 분할)명세 기반(블랙박스)입력 도메인을 동일 처리가 기대되는 구간으로 나누고 각 구간 대표값 1개씩 선택필요(각 케이스의 기대 결과를 알아야 함)
Boundary value analysis(경계값 분석)명세 기반동등 분할의 경계 부근 값필요
Decision table testing(결정 테이블)명세 기반조건들의 조합과 각 조합에 대응하는 액션을 표로 정리필요
State transition testing(상태 전이)명세 기반상태·이벤트·전이 모델필요
Metamorphic testing(변성 테스팅)명세 기반선행 케이스 + 변성 관계 → 후속 케이스불필요(관계만 검사)
Requirement-based testing(요구사항 기반)명세 기반명세된 요구사항 항목 하나하나에서 직접 도출, 요구사항 추적성 확보가 목적필요

변성 테스팅만이 "정답을 몰라도 된다"는 칸에 해당한다는 것이 결정적 구분점이다.

5. 혼동하기 쉬운 인접 개념​

착각실제
두 케이스를 만들었으니 동등 분할이다동등 분할은 입력 도메인 분할에서 대표값을 뽑는 것이지, 앞 케이스로부터 뒤 케이스를 유도하지 않는다
조건이 두 가지이므로 결정 테이블이다결정 테이블은 조건 조합 × 액션 표가 전제된다. 본문에는 조건 조합표가 없다
요구사항(대칭성)에서 나왔으니 요구사항 기반이다요구사항 기반은 요구사항 항목 자체를 케이스로 옮기는 것. 본문은 첫 케이스의 결과 D를 재사용해 둘째 케이스의 기대값으로 삼았다는 점이 결정적
회귀 테스트와 같다회귀 테스트는 같은 입력을 버전 간 비교. 변성 테스팅은 같은 버전에서 다른 입력을 비교

문제​

정답​

③

상세 풀이​

"가장 적절한 것"을 고르는 긍정형 기법 식별 문항이다. 지문의 절차를 분해해 각 기법의 정의와 대조한다.

1단계 — 지문 절차 분해​

순서지문 내용기법 용어로 번역
①getDistance(A, B) 를 실행해 거리 D 를 얻고 첫 번째 테스트케이스로 결정원본 테스트케이스(source test case) 생성. 이때 D가 올바른 값인지는 검증하지 않았다
②"이를 바탕으로" 시작/목적을 맞바꾼 getDistance(B, A) 를 만듦변성 관계(대칭성) 에 따른 입력 변형
③그 기대 결과를 동일한 거리 D 로 정함후속 테스트케이스(follow-up test case) 의 기대값을 원본의 출력에서 가져옴

2단계 — 결정적 단서 두 가지​

  1. "이를 바탕으로" — 두 번째 케이스가 첫 번째 케이스로부터 유도되었다. 동등 분할·결정 테이블·요구사항 기반은 모두 케이스를 명세로부터 독립적으로 도출하므로 케이스 사이에 이런 유도 관계가 없다.
  2. 기대값이 절대값이 아니라 "동일한 D" — 문제는 D가 몇인지 끝까지 밝히지 않는다. 즉 정답을 모르는 상태에서도 테스트가 성립한다. 이것이 테스트 오라클 문제를 우회하는 변성 테스팅의 정체다.

"양방향(무방향) 그래프에서 A→B 거리와 B→A 거리는 같아야 한다"는 것은 대칭성이라는 변성 관계이며, 위 3절 표의 첫 행과 정확히 일치한다.

3단계 — 결론​

두 단서를 모두 만족하는 것은 Metamorphic testing, 즉 ③이다.

① Equivalence partitioning오답 보기입력 도메인을 동등 클래스로 분할한 흔적이 없고, 케이스 간 유도 관계도 없다
② Decision table testing오답 보기조건 조합과 액션을 정리한 표가 전제되어야 하는데 본문에 조건 조합이 없다
③ Metamorphic testing✅ 정답 보기대칭성이라는 변성 관계로 원본 케이스에서 후속 케이스를 유도하고, 기대값을 원본 출력 D로 지정
④ Requirement-based testing오답 보기요구사항 문서 항목에서 직접 케이스를 뽑은 것이 아니라, 첫 케이스의 실행 결과를 재사용했다

오답 이유​

  • ①이 틀린 이유: 동등 분할이었다면 "시작 위치가 유효한 노드일 때 / 존재하지 않는 노드일 때 / null일 때"처럼 입력 도메인을 성질별로 나누고 각 구간의 대표값을 뽑았어야 한다. 본문에는 그런 분할이 전혀 없고, 오히려 두 케이스가 같은 동등 클래스(유효한 두 노드) 안에 있다. 게다가 동등 분할은 각 케이스의 기대 결과를 명세로부터 따로 알아야 하는데, 본문은 D의 값을 모른 채 진행한다.
  • ②가 틀린 이유: 결정 테이블 테스팅이었다면 "조건 1: 시작 노드 존재, 조건 2: 목적 노드 존재, 조건 3: 경로 존재" 같은 조건들과 그 조합(T/F 열)별 액션이 표로 제시되고, 각 열이 하나의 케이스가 되어야 한다. 본문에는 조건이 하나도 열거되지 않았고 조합표도 없다. 케이스가 2개인 것은 조건 조합이 2가지여서가 아니라 원본·후속 관계이기 때문이다.
  • ③이 맞는 이유: 변성 테스팅의 세 요소가 모두 명시적으로 등장한다. (가) 원본 케이스 getDistance(A,B) → D, (나) 변성 관계 = 무방향 그래프의 대칭성 f(A,B) = f(B,A), (다) 후속 케이스 getDistance(B,A) 의 기대 결과 = 동일한 D. 만약 실행 결과가 D와 다르면 두 실행 중 최소 하나에 결함이 있다는 것이 확정되므로, D의 참값을 몰라도 결함을 검출할 수 있다.
  • ④가 틀린 이유: 요구사항 기반 테스팅은 요구사항 명세의 각 항목(예: "REQ-12: 두 지점 간 최단 거리를 반환한다")에 대해 그 항목을 검증하는 케이스를 만들고 요구사항–테스트케이스 추적표를 유지하는 접근이다. 케이스들 사이에는 유도 관계가 없고, 각 케이스의 기대 결과는 요구사항에서 직접 나온다. 본문에서는 둘째 케이스의 기대값을 요구사항이 아니라 첫째 케이스의 실행 출력에서 가져왔으므로 성격이 다르다. 물론 "양방향 그래프이므로 대칭이어야 한다"는 성질 자체는 요구사항에서 비롯되지만, 그 성질을 "관계"로 삼아 후속 케이스를 유도하는 순간 기법의 이름은 변성 테스팅이 된다.

핵심 정리​

  • 테스트 오라클 문제: 개별 입력의 정답 출력을 알기 어려운 소프트웨어(과학 계산, 검색, 기계학습, 컴파일러 등)가 존재한다. 변성 테스팅은 이를 우회하는 기법이다.
  • 변성 테스팅 절차: 원본 케이스 실행 → 변성 관계로 입력 변형 → 후속 케이스 실행 → 두 출력이 관계를 위반하면 결함.
  • 대표 변성 관계: 대칭성, 순열 불변, 배수성, 포함 관계(단조성), 주기성, 의미 보존 변환, 삼각 부등식.
  • "이를 바탕으로 두 번째 케이스를 만들었다" + "기대값이 구체적 수치가 아니라 첫 케이스와 동일한 값" — 이 두 표현이 보이면 변성 테스팅이다. 다른 기법은 케이스를 명세에서 각각 독립적으로 도출하며 기대 결과도 따로 알아야 한다는 점이 결정타다.

소프트웨어 규모 산정

문제​

5.소프트웨어 개발에 필요한 규모 산정 방식 종류와 특징을 비교 설명하고, 공공 소프트웨어 사업 규모 산정 방식의 현실적 개선 방안에 대하여 설명하시오.

Ⅰ. 개요​

1. 배경​

소프트웨어 규모 산정은 개발 비용·기간·인력을 결정하는 출발점이다. 그러나 산정이 부정확하면 과소 산정 시 저가 수주와 품질 저하로, 과다 산정 시 예산 낭비와 감사 지적으로 이어진다.

   [규모 산정 실패의 악순환]

   **부정확한 규모 산정**
        │
        ├─ **과소 산정** → 저가 수주 → **인력 부족·야근** →
        │                  품질 저하 → 재작업 → **추가 비용**
        │
        └─ **과다 산정** → 예산 낭비 → 감사 지적 → **보수적 산정 관행**
        ▼
   [근본 문제] **"몇 명이 몇 개월"(투입 인월, M/M)** 중심의 관행
        │  · 생산성이 높을수록 **대가가 줄어드는 역설**
        │  · 산출물이 아닌 **투입에 대가를 지급**
        ▼
   [해법 방향] **투입(Input) 중심 → 산출물·기능(Output) 중심**
        ▼
   근거 : **소프트웨어 진흥법**(적정 대가 지급), **SW사업 대가산정 가이드**(KOSA),
          **ISO/IEC 14143**(기능규모 측정), **ISO/IEC 20926**(IFPUG FPA)

2. 규모 산정의 위치​

   **규모(Size) 산정** ── 얼마나 큰 소프트웨어인가 (FP·LOC)
        ▼
   **공수(Effort) 산정** ── 얼마나 많은 노력이 필요한가 (M/M)
        ▼
   **기간·인력 산정** ── 얼마나 오래, 몇 명이 필요한가
        ▼
   **비용(Cost) 산정** ── 얼마의 대가를 지급할 것인가

   ⇒ **규모가 모든 산정의 기초** — 규모가 틀리면 이후 전부 틀림

Ⅱ. 소프트웨어 규모 산정 방식의 종류와 특징​

1. 분류 체계​

 ┌──────────── **규모 산정 방식의 분류** ────────────┐
 │                                                   │
 │  **[1] 하향식**(Top-down) — 전체에서 세부로         │
 │      · **전문가 판단**(Expert Judgment)            │
 │      · **델파이법**(Delphi), **광의의 델파이**      │
 │      · **유추법**(Analogy) — 유사 사례 비교        │
 │                                                   │
 │  **[2] 상향식**(Bottom-up) — 세부에서 전체로        │
 │      · **WBS 기반 산정**                           │
 │      · **LOC 기반**(원시 코드 라인)                │
 │      · **개발 단계별 공수 산정**                    │
 │                                                   │
 │  **[3] 수학적 모델**(Algorithmic)                  │
 │      · **COCOMO / COCOMO II**                      │
 │      · **Putnam(SLIM)** 모델                       │
 │      · **Function Point(기능점수)** ★ **공공 표준**  │
 │      · **Use Case Point**, **COSMIC FP**           │
 │                                                   │
 │  **[4] 애자일 기반**                                │
 │      · **스토리 포인트**(Story Point)              │
 │      · **플래닝 포커**(Planning Poker)             │
 │      · **T-Shirt 사이징**                          │
 └───────────────────────────────────────────────────┘

2. 주요 산정 방식 상세​

■ ① 전문가 판단 / 델파이법​

항목내용
개념해당 분야 전문가의 경험과 지식에 근거하여 규모·공수를 추정
델파이법은 다수 전문가의 익명 의견을 반복 수렴하여 합의 도출
절차(델파이)전문가 선정 → 익명 개별 추정 → 결과 취합·공유 → 재추정 반복 → 수렴
광의의 델파이(Wideband Delphi)익명 추정 + 집단 토론을 결합하여 수렴 속도·정확도 향상
장점· 신속·저비용, 요구사항이 불명확한 초기 단계에 유용
· 신기술·특수 상황 등 정량 모델이 없는 경우 적용 가능
단점· 주관성 — 전문가에 따라 편차 큼
· 객관적 근거 제시 곤란 → 발주기관 설득·감사 대응 어려움
· 편향(낙관 편향·앵커링) 개입

■ ② 유추법 (Analogy / 비교 견적)​

항목내용
개념유사한 과거 프로젝트의 실적 데이터와 비교하여 규모를 추정
절차유사 프로젝트 식별 → 차이점 분석 → 보정계수 적용 → 규모 산출
장점실적 데이터 기반으로 신뢰성 확보, 이해하기 쉬움
단점· 유사 프로젝트 실적 DB가 필수 ← 국내 조직 대부분 부재
· 차이점 보정의 주관성
· 신규 기술·신규 업무에는 적용 곤란

■ ③ LOC (Line of Code, 원시 코드 라인 수)​

항목내용
개념개발할 소스코드 라인 수를 추정하여 규모로 사용
산정낙관치·중간치·비관치를 활용한 기대치(PERT) 산정
기대 LOC = (낙관치 + 4×중간치 + 비관치) / 6
장점직관적, 실제 산출물과 직접 연결, 측정 용이(완료 후)
단점· 개발 언어·개발자 역량에 따라 편차 극심(같은 기능 = 다른 LOC)
· 개발 초기 추정이 매우 어려움
· 재사용·자동 생성 코드 처리 곤란
· 코드를 길게 쓸수록 대가가 커지는 역인센티브
· 사용자 관점 가치와 무관

■ ④ COCOMO (Constructive Cost Model)​

항목내용
개념Barry Boehm이 제시한 LOC 기반 수학적 공수 산정 모델
기본 산식노력(E) = a × (KLOC)^b × EAF
개발기간(D) = c × E^d
프로젝트 유형· 조직형(Organic) — 소규모·단순(< 50 KLOC), 익숙한 업무
· 반분리형(Semi-detached) — 중간 규모(< 300 KLOC)
· 내장형(Embedded) — 대규모·복잡, 하드웨어 제약
모델 단계· 기본형(Basic) — LOC만 사용
· 중간형(Intermediate) — 15개 비용동인(Cost Driver) 반영
· 발전형(Detailed/Advanced) — 개발 단계별 세분화
COCOMO II현대적 개발(객체지향·재사용·COTS) 반영, FP 입력 지원
단계별 모델(응용 구성·초기 설계·후 아키텍처)
장점정량적·체계적, 비용동인으로 프로젝트 특성 반영 가능
단점LOC 추정에 의존(초기 산정 곤란), 계수 보정 필요, 국내 실정 반영 미흡

■ ⑤ Putnam 모델 (SLIM)​

항목내용
개념소프트웨어 생애주기 동안의 노력 분포가 Rayleigh 곡선을 따른다는 가정
특징개발 기간과 노력의 관계를 모델링 — 기간을 단축하면 노력이 급증(4승에 비례)
시사점"인력을 두 배 투입해도 기간은 절반이 되지 않는다"(Brooks의 법칙)
→ 무리한 기간 단축의 비효율을 정량적으로 설명
도구SLIM(Software Life Cycle Management)

■ ⑥ 기능점수 (Function Point, FP) ★ 공공 표준​

항목내용
개념사용자 관점에서 제공되는 기능의 양을 정량화한 규모 단위
Allan Albrecht(IBM) 제안, IFPUG가 표준화
표준ISO/IEC 20926(IFPUG FPA), ISO/IEC 14143(기능규모 측정 개념)
핵심 특징개발 언어·기술·개발자와 무관 → 객관적·일관된 규모 측정
   [**기능점수의 5대 구성요소**]

   ┌──────── **데이터 기능**(Data Function) ────────┐
   │ **ILF**(내부논리파일) — 시스템 **내부에서 관리** │
   │ **EIF**(외부연계파일) — **외부에서 참조**만 함  │
   ├──────── **트랜잭션 기능**(Transaction) ────────┤
   │ **EI**(외부입력) — 데이터 **입력·등록·수정·삭제**│
   │ **EO**(외부출력) — **가공·계산**된 결과 출력    │
   │ **EQ**(외부조회) — **가공 없는 단순 조회**      │
   └────────────────────────────────────────────────┘

   [**산정 방식 2가지**]
   **① 정통법**(상세법) — 각 기능의 **복잡도(단순·보통·복잡)** 를 판정
        · 정확하나 **상세 설계 완료 후 적용 가능**
   **② 간이법**(평균복잡도법) ★ **공공 사업 표준**
        · 복잡도를 **평균값으로 일괄 적용**
        · **기획·발주 단계에서 적용 가능** → 예산 산정에 활용

   [**대가 산정 흐름**]
   **기능점수(FP)** × **FP당 단가** × **보정계수** = **SW 개발비**
        ※ 보정계수 : 애플리케이션 유형·언어·품질·특성 요구수준 등
구분내용
장점· 기술·언어 독립적 → 객관적 비교 가능
· 사용자 관점의 기능 기준 → 발주자가 이해 가능
· 기획·설계 단계 조기 산정 가능(간이법)
· 국제 표준, 공공 사업 공식 산정 방식
· 투입이 아닌 산출물 기준 → 생산성 향상 유인
단점· 측정에 전문성 필요(FP 전문가), 측정 비용·시간
· 비기능 요구사항 반영 미흡 — 성능·보안·아키텍처 난이도
· 유지보수·재개발에 적용 곤란
· 알고리즘 중심 SW(임베디드·과학계산)에 부적합
· 측정자에 따른 편차 가능

■ ⑦ 유스케이스 포인트 (UCP) / COSMIC FP​

방식내용
유스케이스 포인트유스케이스 수와 복잡도, 액터 복잡도를 기반으로 규모 산정
→ 객체지향·UML 기반 개발에 적합
COSMIC FP(ISO/IEC 19761)데이터 이동(Entry·Exit·Read·Write) 횟수로 측정
→ 실시간·임베디드 시스템에 적합(IFPUG의 약점 보완)

■ ⑧ 스토리 포인트 (Agile)​

항목내용
개념상대적 크기(복잡도·불확실성·작업량)를 팀이 합의하여 부여하는 무차원 단위
방법플래닝 포커 — 피보나치 수열(1,2,3,5,8,13) 카드로 팀이 동시 제시·토론·합의
속도(Velocity)스프린트당 완료한 스토리 포인트 합계 → 향후 일정 예측
장점신속, 팀 합의 기반, 상대 비교가 절대 추정보다 정확, 반복하며 정교화
단점· 팀마다 기준이 달라 조직 간 비교 불가
· 계약·예산 산정 근거로 부적합(공공 발주에 사용 곤란)
· 초기 팀 속도 미확보 시 예측 불가

3. 산정 방식 종합 비교​

비교 기준전문가 판단·델파이유추법LOC / COCOMO기능점수(FP)스토리 포인트
산정 기준전문가 경험유사 실적코드 라인 수사용자 기능상대적 크기
적용 시점기획 초기초기설계 이후기획~설계(간이법)스프린트 계획
객관성낮음중간중간높음낮음(팀 내부만)
기술 독립성—낮음낮음(언어 종속)높음중간
측정 비용매우 낮음낮음중간높음(전문가 필요)낮음
정확도낮음실적 DB에 의존중간높음팀 성숙도에 의존
비기능 반영가능(주관적)부분비용동인으로 반영미흡 ← 약점부분
계약 근거부적합보조보조적합(공공 표준)부적합
국제 표준없음없음없음ISO/IEC 20926없음
적합 상황요구 불명확 초기실적 DB 보유코드 규모 예측 가능공공 SW사업애자일 개발
   [**적용 시점별 권장 방식**]

   **기획·타당성 검토** → 전문가 판단·유추법·**FP 간이법**
        ▼
   **예산 요구·발주(RFP)** → **FP 간이법** ★ (공공 표준)
        ▼
   **설계 완료 후** → **FP 정통법** (정산·변경 대가)
        ▼
   **개발 진행 중(애자일)** → 스토리 포인트 (팀 내부 계획)
        ▼
   **완료 후 실적 관리** → LOC·실제 공수 → **실적 DB 축적**

Ⅲ. 공공 SW사업 규모 산정의 현황과 문제점​

1. 현행 제도​

   [**SW사업 대가산정 체계**(KOSA 가이드)]

   **[개발비]**
        · **기능점수(FP) 방식** ← **원칙**
          FP × 단가 × 보정계수
        · **투입공수(M/M) 방식** ← 예외(FP 적용 곤란 시)

   **[유지관리·운영비]**
        · 요율제 / FP / **투입공수**
        · **고정비·변동비** 방식

   **[기타]** ISP·ISMP 수립비, 상용SW 유지관리비

2. 문제점​

구분문제점내용
① 산정 시점요구사항 미확정 상태의 산정· 예산 확보를 위해 기획 단계에서 산정하나 요구사항이 불명확
· 상세화되면서 범위가 증가하나 예산은 고정
· 결과적으로 과업 범위 초과 → 무상 추가 개발
② FP 방식의 한계비기능 요구사항 미반영· FP는 기능의 양만 측정 — 성능·보안·가용성·아키텍처 난이도 미반영
· 동일 FP라도 대국민 서비스와 내부 시스템의 난이도가 전혀 다름
· 클라우드 전환·MSA·AI 등 신기술 특성 반영 곤란
재개발·고도화 적용 곤란기존 시스템 재개발 시 분석·이관 공수가 반영되지 않음
측정 전문성 부족발주기관에 FP 측정·검증 역량 부재 → 수행사 산정치 수용
③ 단가·보정계수현실 반영 미흡· FP 단가가 실제 인건비 상승을 따라가지 못함
· 보정계수의 객관적 근거 취약
④ 투입 중심 관행M/M 관행의 지속· FP로 산정해도 결국 "몇 명 몇 개월"로 환산·관리
· 생산성을 높이면 대가가 줄어드는 역설
· 자동화·재사용·AI 활용의 인센티브 부재
⑤ 과업 변경 관리변경 시 대가 조정 미흡· 과업 추가에도 예산 증액이 어려움(예산 편성 경직성)
· 과업심의위원회 제도가 있으나 실질적 대가 조정으로 이어지지 않음
⑥ 실적 데이터국가 차원 실적 DB 부재· 유추법·검증의 기초가 되는 프로젝트 실적 데이터 미축적
· 산정의 타당성을 검증할 기준값(Benchmark) 부재
⑦ 발주 역량발주기관 전문성 부족· 요구사항 상세화·규모 검증 역량 미흡
· 감사 리스크로 인한 보수적 산정
⑧ 저가 수주경쟁에 의한 가격 하락적정 산정에도 불구하고 낙찰 과정에서 대가 하락

Ⅳ. 현실적 개선 방안​

 ┌────────── **개선 방안 체계** ──────────┐
 │  **① 산정 기법의 정교화**               │
 │  **② 비기능 요구사항 반영**             │
 │  **③ 요구사항 상세화 강화**             │
 │  **④ 실적 데이터 기반 체계 구축**       │
 │  **⑤ 변경 대응 유연성 확보**            │
 │  **⑥ 발주 역량·거버넌스 강화**          │
 │  **⑦ 계약 방식의 근본 전환**            │
 └────────────────────────────────────────┘

1. 단기 개선 방안 (제도 보완)​

개선 방안세부 내용
① 비기능 요구사항 반영 체계 마련· 성능·보안·가용성·접근성 등 비기능 요구를 별도 보정계수 또는 가산 항목으로 반영
· 아키텍처 복잡도(MSA·분산·실시간) 반영 지표 신설
· AI·클라우드 네이티브 등 신기술 유형별 계수 개발
· 국제적으로 논의되는 SNAP(Software Non-functional Assessment Process) 도입 검토
② 단가·보정계수 현실화· FP 단가의 정기 현행화(인건비·물가 반영)
· 보정계수의 실증 데이터 기반 재산정
· 사업 유형별(신규·재개발·고도화) 차등 단가
③ 요구사항 상세화 강화· ISP/ISMP 단계에서 요구사항 상세화하여 산정 정확도 제고
· SW사업 요구사항 상세화 지침 준수 의무화
· 상세화가 어려운 사업은 분리 발주(설계-구현 분리) 검토
④ 2단계 산정 체계 도입· 1단계(예산 확보) : FP 간이법으로 개략 산정 + 예비비
· 2단계(설계 완료 후) : FP 정통법으로 정산·조정
· 요구사항 확정 시점에 대가를 조정하는 정산형 계약
⑤ 재개발·고도화 산정 기준 마련· 기존 시스템 분석·이관 공수를 반영한 별도 산정식
· 레거시 복잡도를 고려한 보정

2. 중기 개선 방안 (기반 구축)​

개선 방안세부 내용
⑥ 국가 SW사업 실적 DB 구축(핵심)· 완료 사업의 FP·실제 공수·기간·비용·결함률을 표준 양식으로 수집·축적
· 유형별 생산성 기준값(Benchmark) 산출·공표
· 산정 결과의 타당성 검증 기준으로 활용
· ISBSG 등 국제 벤치마크 데이터와 비교
⑦ FP 측정·검증 체계 확립· 제3자 FP 검증 제도 도입(대규모 사업 의무화)
· FP 전문가 양성·자격 제도 확대
· 자동 FP 측정 도구 개발·보급
· 발주기관 대상 산정 컨설팅 지원
⑧ 과업 변경 대응 유연화· 과업심의위원회의 실질화 — 심의 결과가 대가 조정으로 연결되도록 강제
· 변경 대가 예비비 편성 제도화
· 변경 요청의 FP 기반 정량 산정
· 고정비/변동비 방식 확대 적용
⑨ 발주 역량 강화· 발주기관 담당자 교육·자격 제도
· 전문기관 사전 검토·컨설팅 지원(NIA·KOSA)
· 감사 면책 기준 마련 — 가이드 준수 시 책임 완화 → 보수적 산정 관행 완화

3. 장기 개선 방안 (패러다임 전환)​

개선 방안세부 내용
⑩ 투입 → 성과 중심 계약 전환(근본)· M/M 중심 관리에서 탈피 — 산출물·서비스 수준 기준
· 성과 기반 계약(Performance-based Contract)
· 운영·유지관리는 SLA 기반 서비스 계약
· "몇 명이 몇 달"이 아니라 "무엇을 얼마나 잘"
⑪ 애자일·반복 개발 대응 제도· 요구사항 변화가 큰 사업에 애자일 계약 모델 도입
· 반복 주기별 산정·정산(Iterative Contracting)
· 총 예산 한도 내 우선순위 기반 범위 조정 허용
· 공공 애자일 사업 가이드·표준 계약서 마련
⑫ 생산성 향상 인센티브· 재사용·자동화·AI 활용으로 공수를 줄인 경우 불이익이 없도록 설계
· 산출물 기준 대가 지급 → 생산성 향상분이 수행사 이익으로 귀속
· 품질·성과 우수 시 인센티브
⑬ AI 코딩 시대 대응· 생성형 AI 활용으로 개발 생산성이 급변하는 환경 반영
· 단순 코딩 공수 감소 vs 설계·검증 공수 증가를 반영한 새로운 산정 모델 연구
· AI 활용 사업의 품질 검증 비용 반영
⑭ 신기술 유형 산정 체계클라우드 전환·데이터 구축·AI 모델 개발 등 기존 FP로 측정 불가능한 사업의 별도 산정 기준 마련
   [**개선 방안의 우선순위와 논리**]

   **1순위 : 요구사항 상세화 + 2단계 산정**
        │  → 산정 오차의 근본 원인은 **요구사항 불확정**
        │  → 설계 후 정산 구조로 **불확실성 흡수**
        ▼
   **2순위 : 실적 DB 구축**
        │  → 모든 산정 검증의 **기준값** — 없으면 개선 자체가 불가능
        ▼
   **3순위 : 비기능 요구 반영 + 단가 현실화**
        │  → FP의 구조적 약점 보완
        ▼
   **4순위 : 과업변경 대가 조정 실질화 + 발주 역량**
        │  → 제도는 있으나 작동하지 않는 부분의 실효화
        ▼
   **5순위 : 성과 기반 계약으로의 전환**
        │  → 가장 근본적이나 **장기 과제**

Ⅴ. 결론​

소프트웨어 규모 산정 방식은 ① 전문가 판단·델파이(주관적·신속), ② 유추법(실적 기반), ③ LOC·COCOMO(코드 기반 수학적 모델), ④ 기능점수(사용자 기능 기반·국제 표준), ⑤ 스토리 포인트(애자일 상대 추정) 로 구분된다. 이 중 기능점수(FP)는 개발 언어와 기술에 독립적이고, 사용자 관점의 기능을 기준으로 하며, 국제 표준(ISO/IEC 20926)에 근거한다는 점에서 공공 SW사업의 공식 산정 방식으로 채택되어 있다.

그러나 현행 공공 SW사업의 규모 산정은 세 가지 구조적 한계를 안고 있다. 첫째, 요구사항이 확정되지 않은 기획 단계에서 예산을 확정해야 하므로 산정 오차가 필연적이다. 둘째, FP는 기능의 양만 측정하므로 성능·보안·가용성 같은 비기능 요구사항과 아키텍처 복잡도를 반영하지 못한다. 동일한 FP라도 대국민 서비스와 내부 시스템의 실제 난이도는 크게 다르다. 셋째, FP로 산정하더라도 결국 투입 인월(M/M)로 환산하여 관리하므로, 생산성을 높이면 오히려 대가가 줄어드는 역설이 지속된다.

따라서 개선 방안은 단계적으로 접근해야 한다. 단기적으로는 ① 요구사항 상세화를 강화하고 ② 설계 완료 후 정산하는 2단계 산정 체계를 도입하여 불확실성을 흡수하고, ③ 비기능 요구사항을 보정계수나 가산 항목으로 반영하며 ④ FP 단가를 현실화해야 한다. 중기적으로는 ⑤ 국가 차원의 SW사업 실적 DB를 구축하는 것이 무엇보다 중요하다. 실적 데이터 없이는 어떤 산정도 검증할 수 없고, 개선의 근거도 마련할 수 없기 때문이다. 아울러 ⑥ 과업심의위원회의 심의 결과가 실제 대가 조정으로 이어지도록 제도를 실질화하고, 감사 면책 기준을 마련하여 발주기관의 보수적 산정 관행을 완화해야 한다.

장기적으로는 투입 중심에서 성과 중심으로 계약 패러다임 자체를 전환하는 것이 근본 해법이다. 산출물과 서비스 수준을 기준으로 대가를 지급하면, 재사용·자동화·AI 활용을 통한 생산성 향상이 수행사의 이익으로 귀속되어 혁신 유인이 생긴다. 특히 생성형 AI가 개발 생산성을 근본적으로 바꾸고 있는 현 시점에서, 코딩 공수 중심의 산정 모델은 급속히 타당성을 잃어가고 있다. 단순 구현 공수는 줄어드는 반면 설계·검증·품질 관리 공수는 오히려 증가하는 새로운 현실을 반영한 산정 체계 연구가 시급하다.

결국 규모 산정 문제의 본질은 기법의 정교함이 아니라 "불확실한 요구사항을 확정된 예산에 억지로 맞추는 구조" 에 있다. 이를 해결하려면 요구사항 상세화에 대한 선행 투자, 변경에 유연하게 대응하는 계약 구조, 그리고 이를 뒷받침하는 실적 데이터 기반이라는 세 요소가 함께 갖추어져야 한다.

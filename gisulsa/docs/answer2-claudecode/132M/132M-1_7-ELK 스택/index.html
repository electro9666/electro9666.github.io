ELK 스택

문제​

7.ELK(Elasticsearch/Logstash/Kibana) 스택

Ⅰ. 개요​

ELK 스택은 Elasticsearch(검색·저장) + Logstash(수집·가공) + Kibana(시각화) 로 구성된 오픈소스 로그 통합 분석 플랫폼이다. 경량 수집기인 Beats가 추가되어 현재는 Elastic Stack으로 불린다.

   [등장 배경]
   MSA·클라우드 확산 → **로그가 수십~수백 서버에 분산**
        │  · 장애 시 **서버마다 접속하여 grep** → 원인 추적 지연
        │  · 비정형 로그 형식 제각각, **상관 분석 불가**
        │  · 대용량 로그의 **실시간 검색 요구**
        ▼
   [**ELK 스택**] **로그 중앙 집중 → 정형화 → 실시간 검색·시각화**
   ⇒ 관측성(Observability)·보안관제(SIEM)의 사실상 표준 오픈소스

Ⅱ. 구성요소 및 아키텍처​

 ┌─ **[수집원]** 애플리케이션·서버·네트워크 장비·DB·클라우드 ─┐
 └───────────────────────┬─────────────────────────────────────┘
                         ▼
 ┌─ **Beats**(경량 수집 에이전트) ─────────────────────────────┐
 │  Filebeat(로그) · Metricbeat(지표) · Packetbeat(패킷) ·      │
 │  Winlogbeat(윈도우 이벤트) · Auditbeat(감사)                 │
 │  ※ Go 기반 **경량** — 수집 대상 서버에 부담 최소             │
 └───────────────────────┬─────────────────────────────────────┘
                         ▼   (대용량 시 **Kafka/Redis 버퍼** 삽입)
 ┌─ **Logstash**(수집·변환·적재 파이프라인) ───────────────────┐
 │  **Input**(수집) → **Filter**(파싱·가공) → **Output**(전송)   │
 │  · grok 정규식 파싱, mutate·date·geoip·json 필터             │
 │  · **비정형 로그 → 정형 필드**로 구조화                       │
 │  ※ JVM 기반 — 무거움, 대신 **강력한 변환 기능**               │
 └───────────────────────┬─────────────────────────────────────┘
                         ▼
 ┌─ **Elasticsearch**(분산 검색·분석 엔진) ────────────────────┐
 │  · **Apache Lucene** 기반 **역색인(Inverted Index)**          │
 │  · 분산 구조 : **인덱스 → 샤드(Shard) → 복제본(Replica)**     │
 │  · **near real-time 검색**(약 1초), 집계(Aggregation)         │
 │  · RESTful API, JSON 문서 저장(스키마 유연)                   │
 └───────────────────────┬─────────────────────────────────────┘
                         ▼
 ┌─ **Kibana**(시각화·탐색 UI) ────────────────────────────────┐
 │  Discover(로그 검색) · Dashboard · Visualize ·               │
 │  **Alerting**(임계치 경보) · APM · **SIEM(Security)** · 관리   │
 └──────────────────────────────────────────────────────────────┘
구성요소역할특징
Elasticsearch저장·색인·검색·집계역색인 구조로 전문 검색 고속, 분산·수평 확장, 고가용성(복제)
Logstash수집·변환·적재200여 종 플러그인, grok 파싱으로 비정형 → 정형, 자원 소모 큼
Kibana시각화·탐색·관리대시보드, 알림, 사용자 권한 관리
Beats경량 수집 에이전트서버 부하 최소, Logstash 또는 ES로 직접 전송
Elasticsearch 핵심 개념내용
인덱스(Index)RDB의 데이터베이스에 해당, 문서의 논리적 집합
문서(Document)저장 단위(JSON), RDB의 행(Row)
샤드(Shard)인덱스를 나눈 물리적 분할 단위 → 수평 확장의 기본
복제본(Replica)샤드의 사본 → 고가용성 + 읽기 성능 향상
역색인단어 → 문서 목록 매핑 → 전문 검색 초고속
매핑(Mapping)필드 타입 정의(RDB 스키마 유사)

Ⅲ. 활용 및 비교​

활용 분야내용
통합 로그 관리분산 시스템 로그 중앙화, 장애 원인 신속 추적
애플리케이션 모니터링APM 연계 — 응답시간·오류율·트랜잭션 추적
보안 관제(SIEM)보안 이벤트 상관분석, 침해 탐지·포렌식, 컴플라이언스 로그 보관
비즈니스 분석이용자 행태·검색어·트래픽 분석
전문 검색 엔진사이트 내 검색, 상품 검색(Elasticsearch 단독 활용)
인프라 모니터링서버·컨테이너 자원 지표 수집·시각화
구분내용
장점· 오픈소스 — 라이선스 비용 절감
· 실시간에 가까운 대용량 검색(역색인)
· 수평 확장 용이(노드 추가)
· 풍부한 플러그인·생태계, 스키마 유연
· 로그·지표·보안을 하나의 플랫폼에서 통합
단점· 자원 소모 큼 — 메모리(JVM 힙)·디스크 요구량 높음
· 운영 난이도 — 샤드 설계·클러스터 튜닝 전문성 필요
· 트랜잭션·조인 미지원 — RDBMS 대체 불가
· 라이선스 변경 이슈(SSPL) → OpenSearch 포크 발생
· 보안 기능 일부는 유료 구독 필요(구버전)
대안 비교특징
OpenSearchElasticsearch 7.10 기반 AWS 주도 오픈소스 포크(Apache 2.0)
Grafana Loki레이블 기반 경량 로그 수집 — 전문 색인 없이 저비용, Grafana 연동
Splunk상용 SIEM 강자 — 기능 우수, 비용 매우 높음
EFKLogstash 대신 Fluentd/Fluent Bit — 쿠버네티스 환경에서 선호

Ⅳ. 구축·운영 시 고려사항​

고려사항내용
① 용량 산정일 로그 발생량 × 보존기간 × 복제본 수 × 색인 오버헤드(약 1.1~1.5배) → 디스크·노드 수 산정
② 샤드 설계샤드 과다 시 오버헤드(권장 샤드당 10~50GB) → 초기 설계가 성능 좌우, 사후 변경 어려움
③ 인덱스 수명주기(ILM)Hot–Warm–Cold–Delete 계층화 → 오래된 로그는 저비용 저장소로, 보존기간 후 자동 삭제
④ 노드 역할 분리Master / Data / Ingest / Coordinating 노드 역할 분리로 안정성 확보, Master는 3대 이상(홀수)
⑤ 수집 버퍼링트래픽 급증 시 유실 방지 → Kafka·Redis 큐 삽입
⑥ 로그 표준화애플리케이션이 구조화 로그(JSON) 를 남기면 grok 파싱 불필요 → 성능·정확도 향상
⑦ 보안· 기본 설정은 인증 없이 개방 → 외부 노출 시 대량 유출 사고 다발
· 인증·TLS·역할 기반 접근제어(RBAC) 필수, 인터넷 직접 노출 금지
· 개인정보 마스킹(로그에 주민번호·카드번호 포함 주의)
⑧ 가용성복제본 1 이상, 다중 AZ 분산, 스냅샷 백업
⑨ 성능 튜닝JVM 힙은 물리 메모리의 50%·32GB 이하, 리프레시 간격 조정, 벌크 색인
⑩ 라이선스 검토Elastic License(SSPL) vs OpenSearch(Apache 2.0) — 공공·상용 배포 시 확인

Ⅴ. 결론​

ELK 스택은 분산 환경에서 흩어진 로그를 중앙에 모아 정형화하고, 역색인 기반으로 실시간 검색·시각화하는 통합 관측성 플랫폼으로, 오픈소스임에도 상용 제품에 준하는 기능을 제공하여 사실상의 표준으로 자리 잡았다.

도입 시 반드시 유의할 점은 두 가지이다. 첫째, 운영 난이도와 자원 소모가 결코 낮지 않다. 특히 샤드 설계는 사후 변경이 어려워 초기 설계가 장기 성능을 좌우하며, 인덱스 수명주기(ILM) 관리 없이 운영하면 디스크 비용이 기하급수적으로 증가한다. 둘째, 보안 설정이 필수이다. 기본 상태로 인터넷에 노출된 Elasticsearch가 대량 정보 유출 사고의 원인이 된 사례가 다수 있으므로, 인증·TLS·접근제어를 반드시 적용하고 로그에 개인정보가 남지 않도록 마스킹해야 한다.

효율 측면에서 가장 효과적인 개선은 애플리케이션 단계에서 구조화 로그(JSON)를 생성하는 것이다. 이렇게 하면 Logstash의 grok 파싱 부담이 사라져 자원 소모와 파싱 오류가 함께 감소한다. 최근에는 쿠버네티스 환경에서 Fluent Bit 기반 EFK나 경량 Loki를 선택하는 사례도 늘고 있으므로, 로그 규모와 검색 요구 수준에 따라 적정 아키텍처를 선택하는 판단이 필요하다.

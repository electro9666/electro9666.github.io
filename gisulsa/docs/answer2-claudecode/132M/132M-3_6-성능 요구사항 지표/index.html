성능 요구사항 지표

문제​

6.정보시스템의 성능 요구사항 작성 시 고려해야 하는 주요 성능지표 및 내용에 대하여 설명하시오.

Ⅰ. 개요​

1. 배경​

정보시스템 실패의 상당수는 기능 결함이 아니라 성능 미달에서 비롯된다. 그럼에도 실무에서는 성능 요구사항이 "빠르게 처리되어야 한다" 와 같이 정성적·모호하게 기술되어 검증이 불가능한 경우가 많다.

   [성능 요구사항 부실의 결과]

   "**응답이 빨라야 한다**", "**동시 사용자를 많이 수용해야 한다**"
        │
        │  · **측정 불가** → 검수 기준 없음 → **인수 분쟁**
        │  · 하드웨어 규모산정 근거 부재 → **과다·과소 산정**
        │  · 성능 시험 설계 불가 → 운영 후 장애 발생
        │  · 아키텍처 설계 시 성능 목표 미반영
        ▼
   [원칙] **"측정할 수 없으면 요구사항이 아니다"**
        ▼
   성능 요구사항은 **① 지표 + ② 목표값 + ③ 측정 조건**의
   세 요소가 모두 갖춰져야 완결됨
        ▼
   근거 : **ISO/IEC 25010**(성능 효율성), **ISO/IEC 25023**(측정 지표),
          **SW사업 요구사항 상세화 지침**(**PER** — 성능 요구사항)

2. 성능 요구사항의 위치​

   [**SW사업 요구사항 분류 체계**]
   **SFR**(기능) · **PER**(**성능**) · **SER**(보안) · **INR**(인터페이스)
   **DAR**(데이터) · **TER**(테스트) · **QUR**(품질) · **COR**(제약)
   **PMR**(프로젝트관리) · **PSR**(프로젝트지원)
        ▲
        └─ 본 문제의 대상

   [**ISO/IEC 25010 — 성능 효율성(Performance Efficiency)**]
   ┌────────────────┬──────────────────────────────────┐
   │ **시간 반응성**  │ **응답시간·처리량·턴어라운드 타임** │
   │ (Time Behaviour)│                                  │
   │ **자원 활용성**  │ **CPU·메모리·디스크·네트워크 사용률**│
   │ (Resource Util.)│                                  │
   │ **용량**        │ **최대 수용 한계**(사용자·데이터·연결)│
   │ (Capacity)      │                                  │
   └────────────────┴──────────────────────────────────┘

Ⅱ. 주요 성능지표​

1. 성능지표의 분류 체계​

 ┌────────── **성능지표의 4대 범주** ──────────┐
 │                                             │
 │  **① 응답성 지표**(사용자 체감)              │
 │      응답시간 · 지연시간 · 턴어라운드타임    │
 │                                             │
 │  **② 처리량 지표**(시스템 능력)              │
 │      TPS · OPS · 대역폭 · 배치 처리량        │
 │                                             │
 │  **③ 용량·수용성 지표**(규모)                │
 │      동시 사용자 · 동시 세션 · 데이터 용량   │
 │                                             │
 │  **④ 자원 사용률 지표**(효율성)              │
 │      CPU · 메모리 · 디스크 I/O · 네트워크    │
 │                                             │
 │  **(+) 안정성·확장성 지표**                  │
 │      가용성 · 오류율 · 확장성 · 복구시간     │
 └─────────────────────────────────────────────┘

2. ① 응답성 지표 (Responsiveness)​

지표정의목표값 예시
응답시간(Response Time)사용자 요청 시점부터 결과가 화면에 표시될 때까지 소요 시간
= 네트워크 지연 + 서버 처리 + 렌더링		온라인 조회 3초 이내
단순 조회 2초, 통계 10초
지연시간(Latency)요청이 시스템에 도달하여 첫 응답이 시작되기까지의 시간100ms 이내
턴어라운드 타임(Turnaround Time)배치·일괄 작업의 시작부터 완료까지 소요 시간일 마감 배치 2시간 이내
첫 바이트 시간(TTFB)서버가 첫 응답 바이트를 보내기까지200ms 이내
페이지 로딩 시간웹 페이지 전체 렌더링 완료 시간3초 이내
웹 성능 지표(Core Web Vitals)LCP(최대 콘텐츠 표시) 2.5초, INP(상호작용 응답) 200ms, CLS(레이아웃 이동) 0.1 이하사용자 체감 품질
   [**응답시간 목표 설정의 근거 — 사용자 인지 기준**]

   **0.1초 이하** : 즉각적 반응으로 인지 → 흐름 유지
   **1초 이내**   : 사고 흐름 유지, 지연 인지하나 수용
   **3초 이내**   : 일반적 웹 서비스 **수용 한계**
   **10초 초과**  : **주의 이탈** → 사용자 이탈·재요청 발생

   ⇒ 무조건 빠를수록 좋은 것이 아니라
      **업무 특성별로 합리적 목표**를 설정해야 함
      (실시간 조회 vs 대용량 통계는 기준이 달라야 함)

3. ② 처리량 지표 (Throughput)​

지표정의목표값 예시
TPS(Transactions Per Second)초당 처리 트랜잭션 수 — 가장 대표적 처리량 지표피크 시 500 TPS
QPS / RPS초당 질의 수 / 초당 요청 수1,000 RPS
tpmCTPC-C 벤치마크 기준 분당 트랜잭션 — HW 규모산정의 기준 단위규모산정 지침 활용
OPS(Operations Per Second)초당 연산 처리 수—
IOPS초당 디스크 입출력 횟수스토리지 10,000 IOPS
대역폭·전송률단위 시간당 전송 데이터량500 Mbps
배치 처리량단위 시간당 처리 건수시간당 100만 건
   [**응답시간과 처리량의 관계**]

   처리량 ▲
          │        ╭──────╮ ← **최대 처리량**(포화점)
          │      ╱          ╲
          │    ╱              ╲  ← 과부하 시 **처리량 감소**
          │  ╱                  ╲   (스래싱·큐 대기 폭증)
          └────────────────────────▶ 부하(동시 사용자 수)

   응답시간 ▲                    ╱
            │                  ╱ ← **급격히 악화**
            │           ─────╯
            │  ────────
            └────────────────────────▶ 부하

   ⇒ **처리량과 응답시간은 상충** — 부하가 증가하면 처리량은 늘지만
      일정 시점(**Knee Point**)을 넘으면 **응답시간이 급격히 악화**
   ⇒ 성능 요구사항은 **"어느 부하 수준에서의 응답시간"** 을 명시해야 함

4. ③ 용량·수용성 지표 (Capacity)​

지표정의유의사항
동시 사용자 수(Concurrent User)동시에 시스템을 사용 중인 사용자 수정의를 명확히 해야 함(아래 참조)
동시 접속자 수세션이 유지되고 있는 사용자 수—
최대 세션 수시스템이 유지 가능한 최대 세션WAS·DB 커넥션 한계
총 등록 사용자 수전체 가입자 수동시 사용자와 구분
데이터 용량저장 가능한 최대 데이터량, 연 증가율5년 후 100TB
최대 파일 크기·건수업로드 제한, 테이블 최대 행 수—
연결 수용량최대 DB 커넥션·네트워크 연결 수—
   [**"동시 사용자"의 3가지 정의 — 반드시 명확히 할 것**]

   ┌────────────────────┬──────────────────────────────────┐
   │ **총 사용자**       │ 시스템에 등록된 전체 사용자      │
   │ (Total User)        │ 예: 10,000명                     │
   ├────────────────────┼──────────────────────────────────┤
   │ **동시 접속자**     │ 로그인하여 **세션을 유지** 중     │
   │ (Concurrent User)   │ 통상 총 사용자의 **10~20%**       │
   │                     │ 예: 1,000~2,000명                │
   ├────────────────────┼──────────────────────────────────┤
   │ **동시 요청자**     │ **실제로 동시에 요청을 발생**     │
   │ (Active/Simultaneous)│ 동시 접속자의 **5~10%**          │
   │                     │ 예: 50~200명 ← **부하 산정 기준** │
   └────────────────────┴──────────────────────────────────┘

   ⇒ 정의를 혼동하면 **규모산정이 수십 배 왜곡**됨
   ⇒ 요구사항에는 **"어떤 정의의 동시 사용자인지"** 반드시 명시

5. ④ 자원 사용률 지표 (Resource Utilization)​

지표정의권장 목표
CPU 사용률피크 시 평균 CPU 점유율70% 이하(여유 확보)
메모리 사용률물리 메모리 점유율, 힙 사용률80% 이하, GC 빈도 관리
디스크 사용률저장 공간 점유율, 디스크 I/O 대기80% 이하
네트워크 사용률회선 대역폭 점유율50% 이하
DB 커넥션 사용률커넥션 풀 점유율80% 이하
스레드 사용률WAS 스레드 풀 점유율80% 이하

여유율 확보의 이유 : 자원 사용률이 임계치(통상 70~80%)를 초과하면 응답시간이 비선형적으로 급증한다. 따라서 목표는 "100% 활용"이 아니라 "임계치 이하 유지" 이다.

6. ⑤ 안정성·확장성 지표​

지표정의목표값 예시
가용성(Availability)서비스 정상 가동 비율99.9%(연 8.76시간 중단)
오류율(Error Rate)전체 요청 중 오류 응답 비율0.1% 이하
MTBF / MTTR평균 무장애 시간 / 평균 복구 시간MTTR 30분 이내
RTO / RPO복구 목표 시간 / 복구 목표 시점RTO 2시간, RPO 5분
확장성(Scalability)부하 증가 시 자원 추가로 성능 확보 가능 여부노드 2배 → 처리량 1.8배
부하 내구성장시간 부하 시 성능 유지24시간 부하 시 저하 5% 이내

Ⅲ. 성능 요구사항 작성 방법​

1. 성능 요구사항의 3요소​

   [**완결된 성능 요구사항의 구성**]

   **① 지표**(무엇을)  +  **② 목표값**(얼마나)  +  **③ 측정 조건**(어떤 상황에서)

   ┌──────────────────────────────────────────────────────────┐
   │ ✕ **나쁜 예**                                              │
   │   "조회 화면은 빠르게 응답해야 한다"                       │
   │   → 지표·목표값·조건 모두 없음 → **검증 불가**              │
   ├──────────────────────────────────────────────────────────┤
   │ △ **미흡한 예**                                            │
   │   "조회 응답시간은 3초 이내여야 한다"                      │
   │   → 측정 조건 없음(**몇 명이 접속했을 때? 데이터 몇 건?**)  │
   ├──────────────────────────────────────────────────────────┤
   │ ○ **좋은 예**                                              │
   │   "**동시 요청 사용자 200명 부하 상태**에서                 │
   │    **최근 1개월 거래내역 조회**(약 1,000건) 요청의          │
   │    **95 백분위(P95) 응답시간이 3초 이내**여야 한다.         │
   │    (측정 위치: 웹서버 기준, 오류율 0.1% 이하)"              │
   └──────────────────────────────────────────────────────────┘

2. 성능 요구사항 정의서 작성 항목​

항목내용예시
요구사항 ID고유 식별자(추적성)PER-001
요구사항 명간결한 제목거래내역 조회 응답시간
성능 지표측정 대상 지표응답시간(P95)
목표값정량적 기준3초 이내
측정 조건부하 수준·데이터 규모·환경동시 요청 200명, 데이터 1,000건
측정 위치어디서 측정하는가웹서버 기준(클라이언트 렌더링 제외)
측정 방법시험 도구·시나리오JMeter 부하시험, 30분 지속
판정 기준합격 조건P95 ≤ 3초 AND 오류율 ≤ 0.1%
적용 대상대상 업무·화면마이페이지 > 거래내역
우선순위중요도Must

3. 통계적 기준의 중요성 — 평균 vs 백분위​

   [**평균값의 함정**]

   응답시간 측정 결과 100건:
   90건 = 1초,  10건 = 20초
        ▼
   **평균 = 2.9초** → "3초 이내 목표 달성!" ✓
        │
        │  그러나 **10%의 사용자는 20초를 기다림**
        ▼
   ⇒ **평균은 극단값을 감춘다**

   [**백분위(Percentile) 사용 권장**]
   **P50**(중앙값) : 일반적 사용자 체감
   **P90 / P95**   : **실무 표준 기준** — 대다수 사용자 보장
   **P99**         : 최악 사례 관리(금융·핵심 거래)

   ⇒ 성능 요구사항은 **"평균 3초"가 아니라 "P95 3초"** 로 기술

4. 지표 간 상호 관계 (Trade-off)​

   ┌──────────────────────────────────────────────────────┐
   │ **응답시간** ◀──── 상충 ────▶ **처리량**              │
   │  (배치 크기를 키우면 처리량↑ 응답시간↑)               │
   │                                                      │
   │ **성능** ◀──── 상충 ────▶ **비용**                    │
   │  (자원 증설로 성능 확보 → TCO 증가)                   │
   │                                                      │
   │ **성능** ◀──── 상충 ────▶ **보안·정합성**             │
   │  (암호화·트랜잭션 잠금 → 성능 저하)                   │
   │                                                      │
   │ **자원 사용률** ◀──── 상충 ────▶ **응답시간 안정성**   │
   │  (사용률을 높이면 효율↑ 그러나 응답시간 급증 위험)     │
   └──────────────────────────────────────────────────────┘
   ⇒ **모든 지표를 최대화할 수 없음**
   ⇒ 업무 특성에 따라 **우선순위를 정하고 균형점을 명시**해야 함

Ⅳ. 성능 요구사항의 검증 및 활용​

1. 성능 시험 유형​

시험 유형목적확인 지표
부하 시험(Load Test)목표 부하에서 성능 목표 충족 여부 확인응답시간·TPS·자원 사용률
스트레스 시험(Stress Test)한계점(임계 부하) 및 초과 시 거동 확인최대 처리량, 장애 지점
스파이크 시험(Spike Test)급격한 부하 증가 시 대응 확인오토스케일링 동작
내구성 시험(Endurance/Soak)장시간 운영 시 성능 저하·메모리 누수 확인힙 사용량 추이, 응답시간
용량 시험(Capacity Test)최대 수용 가능 규모 산정최대 동시 사용자
확장성 시험(Scalability Test)자원 추가 시 선형 확장 여부노드 수 대비 처리량

2. 활용 — 요구사항이 미치는 영향​

   [**성능 요구사항의 파급 효과**]

   **성능 요구사항 정의**(PER)
        │
        ├──▶ **아키텍처 설계** — 캐시·비동기·분산 구조 결정
        │
        ├──▶ **HW 규모산정**(TTAK.KO-10.0292) — tpmC·IOPS 산정 근거
        │
        ├──▶ **DB 설계** — 인덱스·파티셔닝·반정규화 판단 기준
        │
        ├──▶ **성능 시험 설계** — 시나리오·목표값·판정 기준
        │
        ├──▶ **검수·인수 기준** — 계약상 이행 여부 판단
        │
        └──▶ **운영 SLA** — 서비스 수준 협약의 기초

3. 작성 시 고려사항​

고려사항내용
① 측정 가능성 확보"측정할 수 없으면 요구사항이 아니다" — 지표·목표값·조건 3요소 필수
② 백분위 기준 사용평균이 아닌 P95·P99 기준으로 기술 → 극단값 은폐 방지
③ 동시 사용자 정의 명확화총 사용자 / 동시 접속자 / 동시 요청자를 혼동하면 규모산정이 수십 배 왜곡
④ 측정 위치·범위 명시클라이언트 렌더링 포함 여부, 네트워크 구간 포함 여부
⑤ 업무별 차등 목표단순 조회·복합 통계·배치를 동일 기준으로 묶지 말 것
⑥ 피크 시점 기준평상시가 아닌 최대 부하 시점(월말·이벤트) 기준
⑦ 미래 증가율 반영3~5년 후 데이터량·사용자 증가를 반영한 목표
⑧ 데이터 규모 명시성능은 데이터량에 크게 좌우 → 시험 데이터 규모를 요구사항에 포함
⑨ 시험 환경 정의운영 환경과 다른 축소 환경에서는 결과 왜곡 → 환경 조건 명시
⑩ 상충 관계 인지성능·비용·보안의 Trade-off를 인지하고 우선순위 합의
⑪ 클라우드 환경 반영오토스케일링 전제 시 목표 정의 방식이 달라짐(고정 자원 vs 탄력적)
⑫ 검수 기준 연계성능 요구사항이 인수 기준·SLA와 일관되도록

Ⅴ. 결론​

정보시스템의 성능 요구사항은 응답성(응답시간·턴어라운드타임), 처리량(TPS·tpmC·IOPS), 용량(동시 사용자·데이터 용량), 자원 사용률(CPU·메모리·네트워크) 이라는 네 가지 범주의 지표로 구성되며, 여기에 가용성·오류율·확장성 등 안정성 지표가 보완된다.

성능 요구사항 작성의 핵심 원칙은 "측정할 수 없으면 요구사항이 아니다" 이다. 완결된 성능 요구사항은 ① 지표, ② 정량적 목표값, ③ 측정 조건(부하 수준·데이터 규모·측정 위치) 이라는 세 요소를 모두 갖추어야 하며, 이 중 하나라도 빠지면 검증 불가능한 문장에 그쳐 인수 단계의 분쟁으로 이어진다.

실무에서 특히 유의해야 할 두 가지 함정이 있다. 첫째, 평균값의 함정이다. 평균 응답시간이 목표를 충족해도 일부 사용자는 극단적으로 긴 지연을 경험할 수 있으므로, P95·P99 백분위 기준으로 기술해야 한다. 둘째, 동시 사용자 정의의 혼동이다. 총 사용자·동시 접속자·동시 요청자는 통상 10배 이상 차이가 나므로, 정의를 명확히 하지 않으면 하드웨어 규모산정이 수십 배 왜곡된다.

또한 성능 지표들은 서로 상충 관계에 있음을 인식해야 한다. 처리량을 높이면 응답시간이 늘고, 자원 사용률을 높이면 효율은 좋아지지만 응답시간이 불안정해지며, 보안과 정합성 강화는 성능을 저하시킨다. 따라서 성능 요구사항 정의는 모든 지표를 최대화하는 작업이 아니라, 업무 특성에 맞게 우선순위를 정하고 합리적 균형점을 명시하는 의사결정 과정이다.

끝으로 성능 요구사항은 단순한 문서가 아니라 아키텍처 설계·하드웨어 규모산정·성능 시험 설계·검수 기준·운영 SLA로 파급되는 모든 후속 활동의 출발점이다. 따라서 요구사항 정의 단계에서 발주기관과 수행사가 측정 방법과 판정 기준까지 함께 합의해 두는 것이 프로젝트 성공의 실질적 전제 조건이 된다.

FIPS 140-2

문제​

1.FIPS(Federal Information Processing Standard) 140-2 에 대하여 다음을 설명하시오.
가.FIPS 140-2 레벨 분류
나.암호화 시스템 설계 시 고려사항
다.암호화 시스템의 보안 요소
라.보안 위협 대응 전략

Ⅰ. 개요​

1. 배경​

암호 알고리즘이 아무리 안전해도 이를 구현한 모듈(하드웨어·소프트웨어)에 결함이 있으면 전체 보안이 무너진다. 실제 침해 사고의 다수는 알고리즘 자체가 아니라 키 관리 부실·난수 생성 취약·구현 오류에서 발생한다.

   [문제의식 — "알고리즘의 안전성 ≠ 구현의 안전성"]

   AES-256 사용  ○ (알고리즘은 안전)
        │
        │  그러나 실제 구현에서
        │  · **난수 생성기가 취약**해 키가 예측 가능
        │  · **키를 평문으로 메모리·파일에 저장**
        │  · 모듈 물리 탈취 시 **키 추출 가능**
        │  · **부채널 공격**(전력·시간 분석)에 노출
        ▼
   ⇒ **암호 모듈 자체를 검증하는 표준**이 필요
        ▼
   [**FIPS 140-2**] 미국 **NIST** 제정(2001), 미 연방정부 조달 필수 요건
   · **암호 모듈의 설계·구현·운영 전반**에 대한 보안 요구사항
   · **CMVP**(Cryptographic Module Validation Program)를 통해 검증
   · 후속 표준 **FIPS 140-3**(2019, ISO/IEC 19790 기반)로 전환 중
   · 국내 대응 : **KCMVP**(암호모듈 검증제도, 국정원/KISA)

2. 개요​

항목내용
정식 명칭Security Requirements for Cryptographic Modules
제정 기관미국 NIST(국립표준기술연구소)
검증 프로그램CMVP(미국 NIST + 캐나다 CCCS 공동 운영)
대상암호 모듈(HSM·스마트카드·TPM·암호 라이브러리·VPN 장비 등)
적용 대상미 연방정부 및 계약자, 금융·의료 등 규제 산업, 글로벌 조달 요건
보안 수준Level 1 ~ Level 4 (4단계)
후속 표준FIPS 140-3(2019 승인, 2021 시행) — ISO/IEC 19790·24759 기반
※ FIPS 140-2 신규 검증은 종료, 기존 인증은 일정 기간 유효
국내 유사 제도KCMVP — 국내 검증대상 암호 알고리즘(ARIA·SEED·LEA·HIGHT 등) 기반

Ⅱ. 가. FIPS 140-2 레벨 분류​

1. 4개 보안 수준의 개요​

 ┌────────── **FIPS 140-2 보안 수준(Security Level)** ──────────┐
 │                                                              │
 │  **Level 1** — **기본 요구사항**                              │
 │      승인된 알고리즘 사용, 물리적 보호 요구 없음              │
 │      예) **소프트웨어 암호 라이브러리**(OpenSSL FIPS 모듈)     │
 │                                                              │
 │  **Level 2** — **물리적 변조 증거**(Tamper Evidence)          │
 │      변조 시 흔적이 남는 봉인, **역할 기반 인증**              │
 │      예) 봉인 실링된 장비, **스마트카드**                      │
 │                                                              │
 │  **Level 3** — **물리적 변조 저항 + 키 자동 소거**             │
 │      침입 감지 시 **평문 키 자동 삭제(Zeroization)**           │
 │      **신원 기반 인증**, 평문 키 입출력의 물리적 분리          │
 │      예) **HSM**(하드웨어 보안 모듈) ← **금융권 표준**         │
 │                                                              │
 │  **Level 4** — **최고 수준의 물리적 보안**                     │
 │      **전방위 침입 탐지**, 환경 공격(전압·온도) 대응           │
 │      예) 군사·국가 기밀 등급 장비                              │
 └──────────────────────────────────────────────────────────────┘

3. 11개 보안 요구 영역​

FIPS 140-2는 11개 영역에 대해 각각 레벨을 평가하며, 최종 등급은 가장 낮은 영역의 레벨로 결정된다.

   [**11개 보안 요구 영역**]
   ① **암호 모듈 사양**(Specification)
   ② **모듈 포트 및 인터페이스**(Ports and Interfaces)
   ③ **역할·서비스·인증**(Roles, Services, Authentication)
   ④ **유한 상태 모델**(Finite State Model)
   ⑤ **물리적 보안**(Physical Security)
   ⑥ **운영 환경**(Operational Environment)
   ⑦ **암호키 관리**(Cryptographic Key Management) ★ **핵심**
   ⑧ **EMI/EMC**(전자기 간섭·적합성)
   ⑨ **자체 시험**(Self-Tests) ★
   ⑩ **설계 보증**(Design Assurance)
   ⑪ **기타 공격 완화**(Mitigation of Other Attacks)

   ⇒ **최종 등급 = MIN(11개 영역의 각 레벨)**
      "가장 약한 고리가 전체 등급을 결정" ← **목걸이 원칙**
주요 영역내용
⑦ 암호키 관리키의 생성·분배·저장·사용·폐기(Zeroization) 전 생애주기 요구사항 — 가장 중요한 영역
⑨ 자체 시험전원 인가 시 시험(Power-Up Self-Test) : 알고리즘 정확성(KAT), 무결성 검사
조건부 시험 : 키 쌍 일치 시험, 연속 난수 시험
⑪ 기타 공격 완화부채널 공격(전력·타이밍·전자파 분석), 결함 주입 공격 대응

Ⅲ. 나. 암호화 시스템 설계 시 고려사항​

1. 설계 고려사항 체계​

 ┌────── **암호화 시스템 설계의 5대 축** ──────┐
 │  **① 알고리즘 선정** — 무엇으로 암호화할 것인가│
 │  **② 키 관리 설계**  — 키를 어떻게 다룰 것인가 │
 │  **③ 적용 범위 설계** — 무엇을 암호화할 것인가 │
 │  **④ 성능·운영 설계** — 실무적으로 운영 가능한가│
 │  **⑤ 컴플라이언스**   — 법규·표준을 준수하는가 │
 └─────────────────────────────────────────────┘

2. 세부 고려사항​

구분고려사항
① 알고리즘 선정· 검증된 표준 알고리즘만 사용 — 자체 개발 알고리즘 절대 금지
(Kerckhoffs 원칙 : 알고리즘은 공개되어도 키만 비밀이면 안전해야 함)
· FIPS 승인 알고리즘 : AES, SHA-2/3, RSA, ECDSA, HMAC
· 국내 : ARIA·SEED·LEA·HIGHT(KCMVP 검증대상)
· 취약 알고리즘 금지 : DES·3DES·MD5·SHA-1·RC4
· 충분한 키 길이 : AES 128bit 이상, RSA 2048bit 이상, ECC 256bit 이상
· 운용 모드 : ECB 금지, AES-GCM(AEAD) 권장(기밀성+무결성)
② 키 관리 설계
(가장 중요)		· 키 생성 : 암호학적 안전 난수(CSPRNG), 충분한 엔트로피 확보
· 키 계층화 : 마스터키(KEK) → 데이터 암호화키(DEK) 구조
· 키 저장 : HSM·TPM·키 관리 시스템(KMS) 활용, 평문 저장 절대 금지
· 소스코드 하드코딩 금지 ← 가장 흔한 취약점
· 키 분배 : 안전한 채널, 키 교환 프로토콜(ECDHE)
· 키 교체(Rotation) : 정기적 갱신, 재암호화 절차
· 키 폐기(Zeroization) : 메모리 즉시 소거, 복구 불가 파기
· 키 백업·복구 : 키 분실 = 데이터 영구 소실 → 안전한 백업 필수
· 직무 분리 : 키 관리자 ≠ 데이터 관리자, 이중 통제(M-of-N)
③ 적용 범위 설계· 암호화 대상 식별 — 고유식별정보·비밀번호·바이오정보·계좌정보
· 데이터 상태별 보호
- 저장 중(At Rest) : DB 컬럼·파일·디스크 암호화(TDE)
- 전송 중(In Transit) : TLS 1.2 이상
- 사용 중(In Use) : 동형암호·TEE(선택)
· 암호화 방식 선택 : 애플리케이션 / DBMS(TDE) / 파일시스템 / 스토리지
· 암호화로 인한 컬럼 길이·타입 변경 반영(설계 단계 필수)
· 검색 요구 고려 — 암호화 시 인덱스·LIKE 검색 제약 → 부분 암호화·토큰화
④ 성능·운영 설계· 암호 연산 오버헤드 산정 → 하드웨어 가속(AES-NI·HSM) 활용
· 하이브리드 방식 — 대용량은 대칭키, 키 교환은 공개키
· 대량 데이터 재암호화 절차·소요 시간 사전 검토
· 장애 시 가용성 — HSM 이중화, 키 서비스 SPOF 방지
· 로깅·감사 — 키 사용 이력 기록(단, 키 값 자체는 로그 금지)
⑤ 컴플라이언스·표준· FIPS 140-2/3 검증 모듈 사용(해외), KCMVP 검증(국내 공공)
· 개인정보보호법 안전성 확보조치 기준(암호화 의무)
· 전자금융감독규정, PCI-DSS(카드), ISMS-P
· 국외 반출 시 암호 수출 규제 검토
⑥ 구현 안전성· 검증된 라이브러리 사용 — 직접 구현 금지
· 부채널 공격 대응 — 상수 시간 연산(Constant-Time)
· 초기화 벡터(IV)·논스(Nonce) 재사용 금지
· 오류 메시지에 암호 관련 정보 노출 금지(패딩 오라클 공격)
⑦ 양자내성 대비PQC 전환 로드맵(ML-KEM·ML-DSA), 암호 민첩성(Crypto Agility) 확보
→ 알고리즘 교체가 용이한 구조로 설계
   [**암호화 설계의 최우선 원칙**]

   **"암호화의 안전성은 알고리즘이 아니라 키 관리가 결정한다"**

   AES-256 (안전한 알고리즘)
        +
   키를 소스코드에 하드코딩 / 평문 파일 저장
        ▼
   = **보안 수준 0** (누구나 복호화 가능)

   ⇒ 설계 시 **키 관리(생성·저장·교체·폐기)에 가장 많은 노력** 투입

Ⅳ. 다. 암호화 시스템의 보안 요소​

1. 정보보호 목표 관점의 보안 요소​

 ┌──────── **암호가 제공하는 4대 보안 서비스** ────────┐
 │                                                     │
 │  **① 기밀성**(Confidentiality)                       │
 │      권한 없는 자가 내용을 알 수 없음                │
 │      → **대칭키 암호(AES)**, 공개키 암호             │
 │                                                     │
 │  **② 무결성**(Integrity)                             │
 │      데이터가 위·변조되지 않았음                     │
 │      → **해시(SHA-2/3)**, **MAC/HMAC**, AEAD         │
 │                                                     │
 │  **③ 인증**(Authentication)                          │
 │      상대방·데이터 출처가 진짜임                     │
 │      → **전자서명**, 인증서(PKI), MAC                │
 │                                                     │
 │  **④ 부인방지**(Non-repudiation)                     │
 │      행위 사실을 부인할 수 없음                      │
 │      → **전자서명**(개인키 소유자만 생성 가능)        │
 │                                                     │
 │  **(+) 가용성**(Availability) — 키 분실 시 데이터    │
 │        접근 불가 → **키 백업·복구 체계**             │
 └─────────────────────────────────────────────────────┘

2. 시스템 구성 요소 관점의 보안 요소​

구성 요소내용 및 보안 요구사항
① 암호 알고리즘· 검증된 표준 알고리즘(FIPS 승인 / KCMVP 검증)
· 대칭키(AES·ARIA·SEED·LEA), 공개키(RSA·ECC), 해시(SHA-256 이상), MAC(HMAC)
· 충분한 키 길이, 안전한 운용 모드(GCM)
② 암호키
(가장 중요한 자산)		· 키 강도 — 충분한 길이와 엔트로피
· 키 계층 — 마스터키(KEK) / 데이터키(DEK) 분리
· 키 생명주기 — 생성·분배·저장·사용·교체·폐기
· 키 보관 — HSM·TPM·KMS, 평문 노출 금지
③ 난수 생성기(RNG/DRBG)· 암호학적 안전 난수 생성기(CSPRNG) 필수
· 충분한 엔트로피 소스 확보
· 난수 품질이 취약하면 키 예측 가능 → 전체 무력화
· FIPS 승인 DRBG 사용, 연속 난수 시험 수행
④ 암호 모듈· FIPS 140-2/3 또는 KCMVP 검증 모듈 사용
· 물리적 보호 수준(Level), 변조 감지·키 자동 소거
· 자체 시험(전원 인가 시·조건부)
⑤ 키 관리 시스템(KMS)· 중앙 집중 키 관리, 접근통제·감사 로그
· 키 정책(수명·용도·권한), 자동 교체
· 이중화·백업, HSM 연동
⑥ 인증·접근통제· 암호 기능 사용자에 대한 신원 인증(MFA)
· 역할 분리(사용자 / 암호 관리자 / 감사자)
· 최소 권한, 이중 통제(M-of-N)
⑦ 인증서·PKI· CA 계층 구조, 인증서 발급·갱신·폐기(CRL/OCSP)
· 루트 CA 개인키의 오프라인·HSM 보관
⑧ 프로토콜· 검증된 표준 프로토콜(TLS 1.2/1.3·IPSec)
· PFS(전방위 안전성) 지원 — ECDHE
⑨ 로깅·감사· 키 생성·사용·교체·폐기 이력 기록
· 위·변조 방지 보관, 키 값 자체는 절대 로깅 금지
⑩ 물리적 보안HSM 설치 장소 출입통제, 봉인, 환경 감시
⑪ 정책·절차암호 정책, 키 관리 절차서, 담당자 교육, 정기 점검

Ⅴ. 라. 보안 위협 대응 전략​

1. 암호 시스템에 대한 위협 분류​

 ┌────────── **암호 시스템 위협의 4대 범주** ──────────┐
 │                                                     │
 │  **① 암호 분석 공격**(Cryptanalysis)                 │
 │      알고리즘·키 자체를 수학적으로 공격              │
 │                                                     │
 │  **② 구현 공격**(Implementation Attack)              │
 │      **부채널·결함 주입** — 실제 공격의 다수          │
 │                                                     │
 │  **③ 키 관리 공격**(Key Management Attack)           │
 │      **키 탈취·유출** ← 가장 현실적이고 치명적        │
 │                                                     │
 │  **④ 물리적 공격**(Physical Attack)                  │
 │      모듈 탈취·분해·프로빙                           │
 │                                                     │
 │  **(+) 미래 위협** : **양자컴퓨팅**                   │
 └─────────────────────────────────────────────────────┘

2. 위협별 대응 전략​

위협공격 방식대응 전략
① 무차별 대입
(Brute Force)		가능한 모든 키를 시도· 충분한 키 길이(AES-128 이상, RSA-2048 이상)
· 계산 자원 발전을 고려한 키 길이 상향(AES-256)
· 비밀번호는 PBKDF2·bcrypt·Argon2 로 키 유도(Key Stretching)
② 암호 분석차분·선형 분석, 알고리즘 취약점· 검증된 표준 알고리즘만 사용, 자체 개발 금지
· 취약 알고리즘 즉시 폐기(DES·MD5·SHA-1·RC4)
· 암호 민첩성 확보 — 알고리즘 교체 가능한 설계
③ 부채널 공격
(Side-Channel)		전력 소비·연산 시간·전자파·소리를 분석해 키 추출· 상수 시간 연산(Constant-Time Implementation)
· 전력·노이즈 마스킹, 랜덤 지연 삽입
· 차폐(Shielding), 물리적 접근 통제
· FIPS 140-2 Level 3/4 모듈 사용(영역 ⑪ 대응)
④ 결함 주입 공격
(Fault Injection)		전압·클록·레이저로 오작동 유발 후 결과 분석· 환경 감시(EFP) — 전압·온도 이상 탐지 시 동작 중단
· 연산 결과 검증(이중 계산·검산)
· Level 4 물리 보호
⑤ 키 탈취·유출
(가장 현실적)		소스코드 하드코딩, 평문 파일·메모리 덤프, 내부자 유출· HSM·TPM·KMS에 키 보관, 평문 저장 금지
· 소스코드 하드코딩 금지 — 정적 분석으로 점검
· 메모리 즉시 소거(Zeroization)
· 접근통제·직무 분리·이중 통제(M-of-N)
· 키 사용 감사 로그 및 이상 사용 탐지
⑥ 난수 예측취약한 난수 생성기 → 키 예측· CSPRNG·FIPS 승인 DRBG 사용
· 엔트로피 소스 확보(하드웨어 RNG)
· 연속 난수 시험(동일 값 반복 검출)
⑦ 중간자 공격(MITM)공개키 위조·인증서 위조· PKI 인증서 검증(체인·유효기간·CRL/OCSP)
· 인증서 피닝, 상호 인증(mTLS)
· TLS 1.2 이상, 취약 스위트 비활성화
⑧ 재전송 공격(Replay)유효한 메시지를 가로채 재전송논스(Nonce)·타임스탬프·시퀀스 번호 사용
⑨ 패딩 오라클 공격오류 응답 차이로 평문 추론· AEAD 모드(GCM) 사용 — 암호화+인증 통합
· 오류 메시지 통일(구체적 사유 노출 금지)
⑩ IV/Nonce 재사용동일 IV 반복 사용 시 평문 노출IV·Nonce의 유일성 보장(난수 또는 카운터)
⑪ 물리적 탈취·분해장비 탈취 후 칩 프로빙· FIPS Level 3 이상 — 침입 감지 시 키 자동 소거
· 봉인·에폭시 코팅, 출입통제·CCTV
⑫ 다운그레이드 공격취약한 구버전 프로토콜로 유도구버전 프로토콜·알고리즘 비활성화, 최소 버전 강제
⑬ 양자컴퓨팅 위협Shor — RSA·ECC 무력화
Grover — 대칭키 강도 절반화		· 대칭키는 AES-256으로 상향
· PQC 전환(ML-KEM·ML-DSA), 하이브리드 방식 병행
· HNDL 공격(지금 수집·나중 복호화) 대비 → 장기 기밀 데이터 우선 전환

3. 단계별 종합 대응 전략​

   [**Defense in Depth — 다층 방어**]

   **① 예방**(Prevention)
        │  · 검증된 알고리즘·모듈(**FIPS/KCMVP**) 사용
        │  · **HSM 기반 키 보관**, 최소 권한·직무 분리
        │  · 시큐어 코딩, 정적 분석(하드코딩 키 검출)
        ▼
   **② 탐지**(Detection)
        │  · **키 사용 이력 모니터링**, 이상 사용 탐지
        │  · 모듈 **자체 시험**(전원 인가 시·조건부)
        │  · 물리적 **변조 감지**, 환경 이상 탐지
        ▼
   **③ 대응**(Response)
        │  · 침해 시 **즉시 키 폐기(Zeroization)·교체**
        │  · 인증서 **긴급 폐기(CRL/OCSP)**
        │  · 영향 범위 분석, 재암호화
        ▼
   **④ 복구**(Recovery)
        │  · **키 백업으로부터 복구**(안전한 백업 전제)
        │  · 데이터 재암호화, 서비스 정상화
        ▼
   **⑤ 개선**(Improvement)
        │  · 원인 분석, 정책·설계 보완
        │  · **정기 암호 정책 재검토**(알고리즘 수명 관리)
조직 차원 전략내용
암호 정책 수립승인 알고리즘 목록, 키 길이 기준, 키 관리 절차 문서화
암호 자산 인벤토리어디에 어떤 암호가 쓰이는지 목록화 → PQC 전환의 전제
암호 민첩성 확보알고리즘을 설정으로 교체 가능한 구조 — 하드코딩 금지
정기 점검·감사취약 알고리즘 사용 여부, 키 교체 이행 여부 점검
인력 역량암호 담당자 교육, 전문 인력 확보
공급망 검증도입 제품의 검증 인증서(FIPS/KCMVP) 확인

Ⅵ. 결론​

FIPS 140-2는 "암호 알고리즘의 안전성과 암호 모듈의 안전성은 별개" 라는 문제의식에서 출발한 표준으로, 암호 모듈의 설계·구현·운영 전반을 11개 영역에 걸쳐 검증한다. Level 1(기본 알고리즘 요건)부터 Level 4(전방위 물리 보호)까지의 4단계 분류는 보호 대상의 가치와 위협 환경에 따라 적정 수준을 선택할 수 있게 한다. 특히 최종 등급이 11개 영역 중 가장 낮은 레벨로 결정된다는 점은 "가장 약한 고리가 전체 보안을 결정한다" 는 보안의 근본 원리를 제도적으로 구현한 것이다.

암호화 시스템 설계에서 가장 중요한 원칙은 "암호화의 안전성은 알고리즘이 아니라 키 관리가 결정한다" 는 것이다. AES-256이라는 최고 수준의 알고리즘을 사용하더라도, 키를 소스코드에 하드코딩하거나 평문으로 저장하면 보안 수준은 사실상 0이 된다. 따라서 설계 노력의 대부분은 키의 생성(CSPRNG)·저장(HSM/KMS)·교체·폐기(Zeroization) 라는 생애주기 관리에 투입되어야 하며, 키 분실 시 데이터를 영구히 잃는다는 점에서 안전한 키 백업 체계 역시 필수적이다.

보안 요소 측면에서는 기밀성·무결성·인증·부인방지라는 네 가지 보안 서비스를, 알고리즘·키·난수생성기·암호모듈·KMS·PKI라는 구성 요소가 뒷받침하는 구조로 이해해야 한다. 이 중 난수 생성기의 품질은 간과되기 쉽지만, 엔트로피가 부족하면 키가 예측 가능해져 전체 시스템이 무력화되는 치명적 요소이다.

위협 대응에서 유의할 점은 실제 침해의 대부분이 암호 분석이 아니라 키 관리 실패와 구현 취약점에서 발생한다는 사실이다. 수학적으로 AES를 깨는 공격은 현실적으로 불가능하지만, 하드코딩된 키를 찾아내는 것은 매우 쉽다. 따라서 대응 전략은 ① 검증된 모듈(FIPS/KCMVP) 사용, ② HSM 기반 키 보관과 직무 분리, ③ 부채널 공격에 대비한 상수 시간 구현, ④ 키 사용 감사와 이상 탐지를 중심으로 수립되어야 한다.

끝으로 양자컴퓨팅 위협에 대한 준비가 새로운 과제이다. Shor 알고리즘은 RSA·ECC 등 공개키 암호를 근본적으로 무력화하며, 이미 "지금 수집해서 나중에 복호화하는(HNDL)" 공격이 현실적 위협으로 거론되고 있다. 따라서 조직은 ① 암호 자산 인벤토리를 작성하고, ② 알고리즘 교체가 용이한 암호 민첩성(Crypto Agility) 구조를 확보하며, ③ 장기 보존이 필요한 기밀 데이터부터 PQC로 우선 전환하는 로드맵을 지금부터 준비해야 한다. 아울러 FIPS 140-2가 FIPS 140-3로 전환되고 있으므로, 신규 도입 제품은 140-3 검증 여부를 확인하고, 국내 공공 부문에서는 KCMVP 검증 암호모듈 사용이 필수 요건임을 유념해야 한다.

블록, 파일, 오브젝트 스토리지

문제​

12.블록 스토리지, 파일 스토리지, 오브젝트 스토리지의 데이터 접근 방식

Ⅰ. 개요​

스토리지는 데이터를 어떤 단위로 저장하고 어떤 방식으로 접근하는가에 따라 블록·파일·오브젝트 세 가지로 구분되며, 이 차이가 곧 성능·확장성·용도의 차이를 만든다.

   [저장 단위와 접근 계층의 차이]

   **블록 스토리지**   ─ 데이터를 **고정 크기 블록**으로 분할 저장
        │              → **OS가 직접 제어**(파일시스템은 서버가 담당)
        │              → 접근 : **논리 블록 주소(LBA)**
        ▼
   **파일 스토리지**   ─ 데이터를 **파일 + 계층적 디렉터리**로 저장
        │              → **스토리지가 파일시스템 제공**
        │              → 접근 : **경로(Path)** /home/user/a.txt
        ▼
   **오브젝트 스토리지** ─ 데이터를 **객체(데이터+메타데이터+ID)** 로 저장
                        → **평면(Flat) 주소 공간**, 계층 없음
                        → 접근 : **고유 ID + REST API**(HTTP)

Ⅱ. 유형별 데이터 접근 방식​

1. 블록 스토리지 (Block Storage)​

   [구조 및 접근 방식]
   [**애플리케이션**]
        ▼
   [**파일시스템**(EXT4·NTFS·XFS)]  ← **서버(OS)가 관리**
        ▼
   [**볼륨 / LUN**]
        ▼   **SCSI · iSCSI · FC · NVMe-oF** 프로토콜
   [**블록 0][블록 1][블록 2]…**]   ← 고정 크기(512B·4KB) 조각
        └ **논리 블록 주소(LBA)로 직접 읽기/쓰기**

   ⇒ 스토리지는 **"블록의 배열"만 제공**, 의미 부여는 서버가 담당
   ⇒ **OS 입장에서는 로컬 디스크처럼 인식**
항목내용
접근 단위고정 크기 블록(512B·4KB)
주소 지정LBA(논리 블록 주소) — 번호로 직접 지정
프로토콜iSCSI·FC(Fibre Channel)·FCoE·NVMe-oF, SATA/SAS
파일시스템서버(OS)가 생성·관리
접근 특성랜덤 접근·부분 수정(In-place Update) 가능 — 필요한 블록만 갱신
공유기본적으로 단일 서버 전용(클러스터 파일시스템 사용 시 공유 가능)
대표 형태SAN, AWS EBS, iSCSI 볼륨, 로컬 디스크

2. 파일 스토리지 (File Storage)​

   [구조 및 접근 방식]
   [**애플리케이션**]
        ▼   **NFS · SMB/CIFS** 프로토콜(네트워크)
   [**스토리지 내부 파일시스템**]  ← **스토리지가 관리**
        ▼
   **/ (root)**
     ├── home/
     │     └── user/
     │           └── **report.docx**  ← **경로로 접근**
     └── data/

   ⇒ **계층적 디렉터리 구조**로 사람이 이해하기 쉬움
   ⇒ **다수 클라이언트가 동시 공유** — 파일 잠금(Locking)으로 정합성 관리
항목내용
접근 단위파일(및 디렉터리)
주소 지정계층적 경로(/dir/subdir/file)
프로토콜NFS(Unix/Linux), SMB/CIFS(Windows), AFP
파일시스템스토리지가 제공
접근 특성파일 단위 읽기/쓰기, 부분 수정 가능, 파일 잠금 지원
공유다중 클라이언트 동시 접근에 최적화
메타데이터제한적(이름·크기·권한·생성일 등 고정 속성)
대표 형태NAS, AWS EFS, 파일 서버, 공유 폴더

3. 오브젝트 스토리지 (Object Storage)​

   [구조 및 접근 방식]
   [**애플리케이션**]
        ▼   **HTTP/HTTPS REST API**(GET·PUT·DELETE)
   [**버킷**(Bucket) — 평면 네임스페이스]
        │
        ├── **객체(Object)**
        │     ┌────────────────────────────────┐
        │     │ **① 데이터**(실제 내용)          │
        │     │ **② 메타데이터**(사용자 정의 가능)│
        │     │    촬영일·부서·보존기간·태그…   │
        │     │ **③ 고유 ID**(Key/URL)          │
        │     └────────────────────────────────┘
        │
   ※ `/photos/2024/a.jpg` 는 **계층이 아니라 이름의 일부**(평면 구조)

   ⇒ 수정 시 **부분 갱신 불가 → 객체 전체를 다시 씀**(Immutable)
   ⇒ 대신 **무한에 가까운 수평 확장** 가능
항목내용
접근 단위객체(데이터 + 메타데이터 + 고유 ID)
주소 지정고유 키/URL(평면 주소 공간, 계층 없음)
프로토콜HTTP/HTTPS REST API(S3 API가 사실상 표준), Swift
접근 특성PUT/GET 전체 단위, 부분 수정 불가(전체 재작성)
일관성전통적으로 최종적 일관성(현재 S3는 강력한 읽기 일관성 제공)
메타데이터사용자 정의 메타데이터 무제한 부여 가능 ← 최대 강점
대표 형태AWS S3, Azure Blob, GCS, MinIO, Ceph RGW

Ⅲ. 3가지 스토리지 비교​

비교 기준블록 스토리지파일 스토리지오브젝트 스토리지
저장 단위블록(고정 크기)파일객체(데이터+메타데이터)
접근 방식LBA 직접 접근경로(Path) 기반고유 ID + REST API
구조평면(블록 배열)계층적 트리평면(Flat)
프로토콜iSCSI·FC·NVMe-oFNFS·SMBHTTP(S3 API)
파일시스템 관리서버(OS)스토리지없음(불필요)
성능·지연가장 빠름(최저 지연)중간높은 지연(HTTP 오버헤드)
랜덤 IOPS매우 우수보통부적합
부분 수정가능가능불가(전체 재작성)
확장성제한적(Scale-up 경향)중간거의 무제한(Scale-out)
메타데이터없음제한적(고정)풍부·사용자 정의
동시 공유어려움(단일 서버)우수우수(다수 클라이언트)
비용(단위 용량)높음중간가장 저렴
일관성강한 일관성강한 일관성최종적 일관성(전통)
적합 용도DB·트랜잭션·VM 부팅 디스크공유 폴더·홈 디렉터리·개발 환경백업·아카이브·미디어·로그·데이터 레이크·정적 웹
부적합 용도대규모 비정형 데이터초대용량 확장DB·OS 디스크·빈번한 수정
   [**선택 판단 흐름**]

   데이터 유형은?
     │
     ├─ **구조화·트랜잭션**(DB·VM 디스크)
     │      → **랜덤 IOPS·저지연 필요** ─────────▶ **블록 스토리지**
     │
     ├─ **여러 사용자·서버가 함께 쓰는 파일**
     │      → **디렉터리 공유·잠금 필요** ───────▶ **파일 스토리지**
     │
     └─ **대용량 비정형**(이미지·영상·로그·백업)
            → **한 번 쓰고 여러 번 읽음(WORM)**
            → **무한 확장·저비용·메타데이터** ──▶ **오브젝트 스토리지**

Ⅳ. 활용 및 고려사항​

활용 사례스토리지 유형
RDBMS 데이터 파일·리두 로그블록(저지연·랜덤 IOPS)
가상머신 부팅 디스크·컨테이너 영속 볼륨블록
부서 공유 폴더·문서 저장소파일
개발/빌드 서버의 공유 소스·홈 디렉터리파일
백업·장기 아카이브·규정 보존오브젝트(WORM·불변 보관)
이미지·동영상 콘텐츠, 정적 웹사이트오브젝트(CDN 연계)
로그·IoT 데이터 레이크, AI 학습 데이터셋오브젝트
고려사항내용
① 용도 기반 선택"무엇이 좋은가"가 아니라 "어떤 접근 패턴인가" 로 판단
② 성능 요구IOPS·지연시간이 핵심이면 블록, 처리량(Throughput) 중심이면 오브젝트
③ 비용 최적화오브젝트의 계층형 스토리지(Standard → IA → Archive) 활용, 수명주기 정책
④ 데이터 보호블록/파일 : RAID·스냅샷·복제
오브젝트 : 이레이저 코딩·다중 복제·버전 관리
⑤ 보안오브젝트는 버킷 공개 설정 오류로 인한 대량 유출 사고 다발 → 기본 비공개·접근정책 점검 자동화 필수
전 유형 공통 : 저장 암호화(SSE)·전송 암호화·접근통제
⑥ 랜섬웨어 대비오브젝트의 불변 보관(Object Lock·WORM) 활용
⑦ 애플리케이션 호환성레거시 앱은 POSIX 파일 인터페이스를 요구 → 오브젝트 전환 시 게이트웨이 필요
⑧ 통합 관리최근 통합 스토리지(Unified Storage) — 하나의 장비가 블록·파일·오브젝트 모두 제공(Ceph 등)

Ⅴ. 결론​

세 스토리지의 차이는 결국 "데이터에 의미를 부여하는 주체가 누구인가" 로 요약된다. 블록 스토리지는 스토리지가 의미 없는 블록만 제공하고 서버가 파일시스템을 관리하므로 가장 빠르고 세밀한 제어가 가능하다. 파일 스토리지는 스토리지가 파일시스템을 제공하여 다수 사용자의 공유에 최적화된다. 오브젝트 스토리지는 계층 구조를 버리고 평면 주소 공간과 풍부한 메타데이터를 채택함으로써 사실상 무한한 확장성과 최저 비용을 확보했다.

이 구조적 차이는 곧 적용 영역의 차이로 이어진다. 저지연 랜덤 접근이 필요한 데이터베이스와 VM 디스크에는 블록, 여러 사용자가 함께 쓰는 문서·개발 환경에는 파일, 한 번 쓰고 여러 번 읽는 대용량 비정형 데이터(백업·미디어·로그·AI 학습 데이터)에는 오브젝트가 적합하다. 특히 오브젝트 스토리지가 부분 수정을 지원하지 않는다는 점은 단점이 아니라, 그 대가로 무한 확장성을 얻은 설계상의 선택임을 이해하는 것이 중요하다.

실무적으로 가장 주의할 점은 오브젝트 스토리지의 보안 설정이다. 클라우드 정보 유출 사고의 상당수가 버킷을 공개로 설정한 단순 실수에서 비롯되므로, 기본 비공개 원칙과 공개 자원 자동 점검 체계를 반드시 갖추어야 한다. 아울러 최근에는 하나의 플랫폼이 세 가지 인터페이스를 모두 제공하는 통합 스토리지가 확산되고 있어, 워크로드별로 최적 인터페이스를 선택하면서도 인프라는 통합 운영하는 방향이 바람직하다.

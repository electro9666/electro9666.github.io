좋은 소프트웨어의 특징

문제​

9.좋은 소프트웨어가 갖추어야 할 4 가지 특징

Ⅰ. 개요​

좋은 소프트웨어란 단순히 요구된 기능이 동작하는 것을 넘어, 사용자가 요구하는 품질 수준을 만족하면서 변화에 대응하고 오래 유지될 수 있는 소프트웨어를 말한다. Ian Sommerville은 이를 유지보수성·신뢰성(및 보안)·효율성·사용용이성 네 가지로 제시하였다.

   [문제의식]
   "**기능이 동작한다**"  ≠  "**좋은 소프트웨어다**"
        │  · 동작하나 **수정할 수 없음** → 요구 변화 대응 불가
        │  · 동작하나 **가끔 멈춤·데이터 손상** → 신뢰 불가
        │  · 동작하나 **너무 느림·자원 낭비** → 사용 불가
        │  · 동작하나 **쓰기 어려움** → 사용자가 외면
        ▼
   ⇒ 소프트웨어의 가치는 **기능(Functionality)** 이 아니라
      **품질 속성(Quality Attributes)** 이 결정한다

Ⅱ. 좋은 소프트웨어의 4가지 특징​

 ┌──────────── **좋은 소프트웨어의 4대 특징** ────────────┐
 │                                                        │
 │  **① 유지보수성**(Maintainability)                      │
 │      "**변화하는 요구에 맞게 수정할 수 있는가**"         │
 │                                                        │
 │  **② 신뢰성 및 보안**(Dependability & Security)         │
 │      "**믿고 맡길 수 있는가, 안전한가**"                 │
 │                                                        │
 │  **③ 효율성**(Efficiency)                               │
 │      "**자원을 낭비하지 않고 빠르게 처리하는가**"        │
 │                                                        │
 │  **④ 사용 용이성**(Usability / Acceptability)           │
 │      "**대상 사용자가 쉽게 쓸 수 있는가**"               │
 └────────────────────────────────────────────────────────┘

1. 유지보수성 (Maintainability)​

항목내용
정의변화하는 비즈니스 요구에 맞추어 소프트웨어를 수정·진화시킬 수 있는 능력
중요성SW 총비용의 약 70%가 유지보수 단계에서 발생 → 가장 중요한 특징
세부 속성모듈성(Modularity), 재사용성, 분석성(문제 원인 파악 용이), 변경성, 시험성(Testability)
확보 방안· 높은 응집도(Cohesion)·낮은 결합도(Coupling)
· 계층 분리·인터페이스 기반 설계, 디자인 패턴 적용
· 코딩 표준·명확한 명명, 적절한 주석·문서화
· 자동화 테스트 확보(리팩토링의 전제)
· 정적 분석·코드 리뷰, 기술 부채 관리
위반 시작은 수정에도 전면 영향, 결함 재발, 결국 재구축

2. 신뢰성 및 보안 (Dependability and Security)​

항목내용
정의정상·비정상 상황 모두에서 오동작하지 않고, 악의적 공격으로부터 안전한 성질
세부 속성신뢰성(Reliability)·가용성(Availability)·안전성(Safety)·보안성(Security)
확보 방안· 예외 처리·방어적 프로그래밍, 입력 검증
· 이중화·장애 허용(Fault Tolerance), 복구 설계
· 시큐어 코딩(OWASP Top 10 대응), 취약점 진단
· 인증·권한·암호화, 최소 권한 원칙
· 충분한 테스트(경계값·부하·장애 주입)
위반 시데이터 손상·서비스 중단, 정보 유출 → 금전·법적·평판 손실

3. 효율성 (Efficiency)​

항목내용
정의메모리·CPU·저장공간·네트워크 등 자원을 낭비하지 않고 요구 성능을 달성하는 능력
세부 속성응답성(Responsiveness), 처리량(Throughput), 자원 사용률, 확장성
확보 방안· 알고리즘·자료구조 선택(시간·공간 복잡도)
· DB 인덱스·쿼리 튜닝, N+1 문제 제거
· 캐싱, 비동기·병렬 처리, 커넥션 풀
· 성능 테스트(부하·스트레스)로 병목 식별
· 자원 해제(메모리·커넥션 누수 방지)
주의조기 최적화는 유지보수성을 훼손 → 측정 후 병목에 한해 최적화
위반 시사용자 이탈, 하드웨어 증설 비용 증가, 확장 한계

4. 사용 용이성 (Usability / Acceptability)​

항목내용
정의의도한 사용자가 특별한 노력 없이 이해·학습·조작할 수 있는 성질
(수용성 — 사용자에게 이해 가능하고, 사용 가능하며, 기존 시스템과 호환)
세부 속성학습 용이성, 조작 효율성, 오류 방지·복구, 일관성, 접근성(Accessibility)
확보 방안· 사용자 중심 설계(UCD) — 실제 사용자 조사·사용성 테스트(UT)
· 일관된 UI 패턴(디자인 시스템), 명확한 용어
· 의미 있는 오류 메시지(무엇이·왜·어떻게)
· 접근성 준수(KWCAG), 반응형·모바일 대응
· 적절한 사용자 문서·도움말
위반 시도입해도 사용하지 않음 → 투자 실패(TAM의 PEOU 저하)

Ⅲ. 4대 특징의 관계와 표준 연계​

1. 특징 간 상충 관계 (Trade-off)​

   **효율성** ◀────── 상충 ──────▶ **유지보수성**
   (성능 최적화 코드는 복잡·난해 → 수정 어려움)

   **보안성** ◀────── 상충 ──────▶ **사용 용이성**
   (인증 강화·복잡한 절차 → 사용자 불편)

   **신뢰성** ◀────── 상충 ──────▶ **효율성/비용**
   (이중화·검증 로직 → 자원·비용 증가)

   ⇒ **모두를 최대화할 수 없음**
   ⇒ **시스템 특성과 요구사항에 따라 우선순위를 정하고 균형점 선택**
      예) 금융 시스템 → 신뢰성·보안 최우선
          대국민 서비스 → 사용 용이성·접근성 최우선
          실시간 제어 → 효율성(응답성) 최우선

2. 국제 표준과의 연계 — ISO/IEC 25010​

4대 특징ISO/IEC 25010 품질 특성
유지보수성유지보수성(모듈성·재사용성·분석성·변경성·시험성)
신뢰성·보안신뢰성(성숙성·가용성·결함허용성·복구성) + 보안성(기밀성·무결성·부인방지·책임추적성·인증성)
효율성성능 효율성(시간 반응성·자원 활용성·용량)
사용 용이성사용성(적절성 인식·학습성·운용성·오류 방지·심미성·접근성)
(추가 특성)기능 적합성, 호환성, 이식성

Ⅳ. 확보를 위한 실무 방안​

단계활동
요구사항비기능 요구사항의 정량화 — "빨라야 한다" → "응답 2초 이내"
4대 특징별 목표 수준 정의 및 우선순위 합의
설계아키텍처 품질 속성 반영(ATAM 등 평가), 모듈화·계층 분리, 보안·성능 설계 내재화
구현코딩 표준, 시큐어 코딩, 코드 리뷰, 정적 분석(SonarQube)
테스트기능 + 비기능 테스트(성능·보안·신뢰성·사용성), 자동화 테스트·커버리지
운영모니터링·지표 측정(APM), 결함 추이 분석, 기술 부채 상환 계획
조직품질 목표를 KPI로 관리, DevOps·CI/CD로 품질 게이트 자동화

Ⅴ. 결론​

좋은 소프트웨어의 4가지 특징 — 유지보수성·신뢰성(보안)·효율성·사용 용이성 — 은 모두 기능이 아닌 품질 속성이라는 공통점을 갖는다. 기능은 "무엇을 하는가"를 정하지만, 소프트웨어의 성패와 총비용은 이 네 가지 품질 속성이 결정한다.

이 중 실무적으로 가장 중요한 것은 유지보수성이다. 소프트웨어 총비용의 대부분이 유지보수에서 발생하고, 유지보수성이 낮은 시스템은 요구 변화를 수용하지 못해 결국 재구축되기 때문이다. 반면 사용자 관점에서 가장 먼저 체감되는 것은 사용 용이성이며, 아무리 잘 만든 시스템도 사용자가 쓰지 않으면 투자 실패로 귀결된다.

핵심은 네 가지를 모두 최대화할 수 없다는 현실 인식이다. 성능 최적화는 코드를 복잡하게 만들어 유지보수성을 해치고, 보안 강화는 사용 편의성을 저해한다. 따라서 좋은 소프트웨어를 만드는 일은 모든 품질을 극대화하는 것이 아니라, 시스템의 성격에 맞게 우선순위를 정하고 의식적으로 균형점을 선택하는 것이다.

이를 위해서는 요구사항 정의 단계에서 비기능 요구사항을 정량화하고 우선순위를 합의하는 것이 출발점이 되어야 하며, ISO/IEC 25010의 품질 모델을 기준으로 측정 가능한 목표를 설정하고 개발 전 과정에서 지속적으로 검증하는 체계가 필요하다.

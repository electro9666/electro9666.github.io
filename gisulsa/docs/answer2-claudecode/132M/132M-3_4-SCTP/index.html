SCTP

문제​

4.SCTP(Stream Control Transmission Protocol)와 관련하여 다음을 설명하시오.
가.SCTP 개요와 특징
나.SCTP 프로토콜(Protocol) 구조 및 동작 방식

Ⅰ. 개요​

1. 배경​

TCP와 UDP는 오랫동안 전송계층을 양분해 왔으나, 통신망 신호(Signaling) 전송과 같이 높은 신뢰성과 가용성을 동시에 요구하는 응용에는 두 프로토콜 모두 한계가 있었다.

   [TCP·UDP의 한계]

   **TCP** : 신뢰성 ○ / **단일 경로**(장애 시 세션 단절) ✕
             **HOL 블로킹**(하나의 패킷 손실이 전체 지연) ✕
             **바이트 스트림**(메시지 경계 없음) ✕
             **SYN Flooding에 취약** ✕

   **UDP** : 경량·빠름 ○ / **신뢰성·순서 보장 없음** ✕

        ▼  전화망 **SS7 신호**를 IP망으로 전달해야 하는 요구
           (**SIGTRAN**) — 통신 신호는 **단 1건도 유실 불가**
        ▼
   [**SCTP**] IETF **RFC 4960**(현행) — 1차 표준 RFC 2960(2000)
   · **TCP의 신뢰성 + UDP의 메시지 경계**
   · **멀티호밍**(경로 이중화) · **멀티스트리밍**(HOL 해소)

Ⅱ. 가. SCTP 개요와 특징​

1. 개요​

SCTP(Stream Control Transmission Protocol, 스트림 제어 전송 프로토콜) 는 TCP의 신뢰성과 UDP의 메시지 지향성을 결합하고, 멀티호밍과 멀티스트리밍을 추가로 제공하는 연결지향 전송계층 프로토콜이다.

항목내용
표준IETF RFC 4960(RFC 2960 개정), 확장: RFC 3758(PR-SCTP), RFC 5061(동적 주소)
계층전송계층(L4) — IP 프로토콜 번호 132
개발 목적SS7 신호를 IP망으로 전송(SIGTRAN)하기 위한 고신뢰 전송
연결 단위연결(Connection) 이 아닌 연관(Association) — 다중 IP 주소 집합 간의 관계
전송 단위청크(Chunk) — 메시지 지향
주요 활용5G/LTE 코어망(NGAP·S1AP·Diameter), VoIP 신호, IoT, 금융 거래

2. SCTP의 주요 특징​

 ┌──────────── **SCTP의 6대 핵심 특징** ────────────┐
 │  **① 멀티호밍**(Multi-homing)   ← 최대 차별점     │
 │  **② 멀티스트리밍**(Multi-streaming) ← HOL 해소   │
 │  **③ 메시지 지향**(Message-oriented)              │
 │  **④ 4-way Handshake + 쿠키**(보안 강화)          │
 │  **⑤ 부분 신뢰성**(PR-SCTP, 선택)                 │
 │  **⑥ TCP 수준의 신뢰성·혼잡제어**                 │
 └───────────────────────────────────────────────────┘

■ ① 멀티호밍 (Multi-homing) — 경로 이중화​

   [**TCP**] 단일 IP 쌍만 사용                [**SCTP**] 다중 IP 주소 사용

   [호스트A]                                  [호스트A]
   IP1 ────── 경로 ────── IP3 [호스트B]       IP1 ══**주 경로**══ IP3 [호스트B]
                                              IP2 ┄┄**대체 경로**┄┄ IP4
   경로 장애 → **세션 단절**                        │
   → 재연결 필요(수 초~수십 초)                     ▼
                                              주 경로 장애 시
                                              **자동으로 대체 경로 전환**
                                              (**세션 유지 · 무중단**)

   · **하트비트(HEARTBEAT)** 청크로 대체 경로 **상시 상태 감시**
   · 각 경로별 **RTT·상태(Active/Inactive)** 관리
   · **전송계층에서 이중화 제공** ← TCP는 애플리케이션이 처리해야 함

■ ② 멀티스트리밍 (Multi-streaming) — HOL 블로킹 해소​

   [**TCP — Head-of-Line 블로킹**]
   ┌───┬───┬───┬───┐
   │ 1 │ ✕ │ 3 │ 4 │   2번 패킷 손실 시
   └───┴───┴───┴───┘   → **3, 4번이 도착해도 전달 불가**
         ▲ 손실           (순서 보장 때문에 **전체 대기**)

   [**SCTP — 독립 스트림**]
   **Stream 0** : ┌───┬───┐  정상 전달 ○
   **Stream 1** : ┌─✕─┬───┐  ← 이 스트림만 대기
   **Stream 2** : ┌───┬───┐  정상 전달 ○
                    ▲ 손실
   ⇒ **하나의 연관(Association) 안에 여러 논리 스트림**
   ⇒ **한 스트림의 손실이 다른 스트림에 영향 없음**
   ⇒ 스트림별 **순서 보장**, 필요 시 **순서 무관 전달(Unordered)** 도 가능

■ ③ 메시지 지향 (Message-oriented)​

   [**TCP — 바이트 스트림**]           [**SCTP·UDP — 메시지 지향**]
   송신: "ABC" + "DEF"                 송신: "ABC" + "DEF"
   수신: "ABCDEF"                      수신: "ABC", "DEF"
        ▲ **메시지 경계 소실**              ▲ **경계 보존**
        → 애플리케이션이 직접 구분          → 별도 처리 불필요
          (길이 헤더 등 추가 구현)

■ 특징 종합​

특징내용
① 멀티호밍하나의 연관에 다중 IP 주소 사용 → 경로 장애 시 자동 절체, 무중단
② 멀티스트리밍하나의 연관 내 다중 독립 스트림 → HOL 블로킹 해소
③ 메시지 지향메시지 경계 보존(UDP 장점) + 신뢰성(TCP 장점)
④ 보안 강화4-way Handshake + 쿠키(Cookie) → SYN Flooding 공격 방어
⑤ 신뢰성확인응답(SACK), 재전송, 순서 보장, CRC-32c 체크섬(TCP보다 강력)
⑥ 혼잡·흐름 제어TCP와 유사한 슬로우 스타트·혼잡 회피
⑦ 부분 신뢰성(PR-SCTP)옵션 — 일정 시간 내 전달 실패 시 포기 → 실시간 응용 지원
⑧ 순서 무관 전달스트림별로 순서 보장 여부 선택 가능
⑨ 경로 MTU 발견경로별 MTU 관리, 청크 번들링(Bundling) 으로 효율 향상

Ⅲ. 나. SCTP 프로토콜 구조 및 동작 방식​

1. 패킷 구조​

 ┌──────────────────── **SCTP 패킷** ────────────────────┐
 │                                                       │
 │  ┌─────────── **공통 헤더**(Common Header, 12바이트) ──┐│
 │  │ **Source Port**(16bit)  │ **Dest Port**(16bit)    ││
 │  ├─────────────────────────┴─────────────────────────┤│
 │  │ **Verification Tag**(32bit)                        ││
 │  │   ← 연관 식별·검증, **위조 패킷 차단**             ││
 │  ├───────────────────────────────────────────────────┤│
 │  │ **Checksum**(32bit) — **CRC-32c**                  ││
 │  └───────────────────────────────────────────────────┘│
 │                                                       │
 │  ┌─────────── **Chunk #1** ──────────────────────────┐│
 │  │ **Type**(8) │ **Flags**(8) │ **Length**(16)       ││
 │  ├───────────────────────────────────────────────────┤│
 │  │ **Chunk Value**(가변) — 실제 데이터 또는 제어정보  ││
 │  └───────────────────────────────────────────────────┘│
 │  ┌─────────── **Chunk #2** ──────────────────────────┐│
 │  │ …  ← **여러 청크를 한 패킷에 번들링 가능**          ││
 │  └───────────────────────────────────────────────────┘│
 └───────────────────────────────────────────────────────┘
헤더 필드내용
Source / Destination Port송·수신 포트 번호
Verification Tag· 연관 수립 시 교환한 고유 태그
· 수신 시 검증 → 위조·과거 연관의 패킷 차단(보안 강화)
ChecksumCRC-32c — TCP의 16비트 체크섬보다 오류 검출 능력 우수

2. 청크(Chunk)의 종류​

분류청크 타입기능
데이터DATA (0)사용자 데이터 전송 — TSN·Stream ID·SSN 포함
연관 수립INIT (1)연관 개시 요청 — IP 주소 목록·스트림 수 전달
INIT ACK (2)응답 + State Cookie 전달
COOKIE ECHO (10)받은 쿠키 반송
COOKIE ACK (11)쿠키 검증 완료 → 연관 수립
확인응답SACK (3)선택적 확인응답 — 수신 TSN·누락 구간 통보
경로 관리HEARTBEAT (4)대체 경로 생존 확인
HEARTBEAT ACK (5)하트비트 응답
연관 해제SHUTDOWN (7)정상 종료 요청
SHUTDOWN ACK (8)종료 확인
SHUTDOWN COMPLETE (14)종료 완료
ABORT (6)비정상 강제 종료
오류ERROR (9)오류 통보

3. DATA 청크의 주요 필드​

   ┌─────────────────────────────────────────────────┐
   │ **TSN**(Transmission Sequence Number, 32bit)     │
   │   → **연관 전체**의 전송 순서 번호(신뢰성·재전송) │
   ├─────────────────────────────────────────────────┤
   │ **Stream Identifier (S)**(16bit)                 │
   │   → 어느 **스트림**에 속하는가                    │
   ├─────────────────────────────────────────────────┤
   │ **Stream Sequence Number (SSN)**(16bit)          │
   │   → **해당 스트림 내**의 순서 번호(순서 보장)     │
   ├─────────────────────────────────────────────────┤
   │ **Payload Protocol Identifier**(32bit)           │
   │   → 상위 프로토콜 식별(예: S1AP·Diameter)         │
   ├─────────────────────────────────────────────────┤
   │ **User Data**(가변)                              │
   └─────────────────────────────────────────────────┘

   ※ **TSN(전체 순서)** 과 **SSN(스트림별 순서)** 의 **분리**가
      **멀티스트리밍(HOL 블로킹 해소)** 을 가능하게 하는 핵심 설계

4. 동작 방식​

■ (1) 연관 수립 — 4-way Handshake​

   [클라이언트 A]                              [서버 B]
        │                                          │
        │ ─── ① **INIT** ────────────────────────▶ │
        │     · Initiate Tag                       │
        │     · **IP 주소 목록**(멀티호밍)          │
        │     · 스트림 수, 초기 TSN                 │
        │                                          │ ※ **자원 할당 안 함**
        │ ◀── ② **INIT ACK** ───────────────────── │   (**SYN Flooding 방어**)
        │     · Initiate Tag                       │
        │     · **State Cookie**(서명된 상태 정보)  │
        │     · 서버 IP 주소 목록                   │
        │                                          │
        │ ─── ③ **COOKIE ECHO** ─────────────────▶ │
        │     · 받은 쿠키를 그대로 반송             │ ※ **쿠키 검증 후**
        │       (데이터 청크 번들 가능)             │   **비로소 자원 할당**
        │                                          │
        │ ◀── ④ **COOKIE ACK** ────────────────── │
        │                                          │
        │  ═══════ **ESTABLISHED**(연관 수립) ═════ │
단계내용
① INIT연관 개시 요청 — 사용 가능한 모든 IP 주소와 스트림 수 통보
② INIT ACK서버가 State Cookie(연관 정보를 서명·암호화한 값)를 전달
이 시점에 서버는 어떤 자원도 할당하지 않음
③ COOKIE ECHO클라이언트가 쿠키를 그대로 반송 → 정당한 클라이언트임을 증명
④ COOKIE ACK서버가 쿠키를 검증한 후 비로소 연관 자원 할당
   [**4-way Handshake의 보안 효과 — SYN Flooding 방어**]

   **TCP 3-way** : SYN 수신 즉시 **백로그 큐에 자원 할당**
        │  공격자가 SYN만 대량 전송 → **큐 고갈 → 서비스 마비**
        ▼
   **SCTP 4-way** : INIT 수신 시 **자원 할당 없이 쿠키만 발급**
        │  공격자가 INIT만 대량 전송해도 **서버 자원 소모 없음**
        │  쿠키를 반송(COOKIE ECHO)해야 자원 할당
        ▼
   ⇒ **INIT Flooding 공격이 구조적으로 무력화**

■ (2) 데이터 전송​

   ① **번들링**(Bundling) — 여러 청크를 하나의 패킷에 담아 효율 향상
   ② **스트림 배정** — 애플리케이션이 지정한 **Stream ID**로 전송
   ③ **TSN 부여** — 연관 전체 순서 번호 할당(신뢰성 보장용)
   ④ **SSN 부여** — 스트림별 순서 번호 할당(스트림 내 순서 보장용)
   ⑤ **주 경로 전송** — 기본적으로 **Primary Path**로 전송
   ⑥ **SACK 수신** — 수신 측이 **누적 TSN + 누락 구간(Gap Ack Block)** 통보
   ⑦ **재전송** — 누락된 TSN을 재전송
        · **빠른 재전송**(중복 SACK 4회) 또는 **타임아웃 재전송**
        · 재전송은 **대체 경로로 시도** 가능 ← 멀티호밍 활용
   ⑧ **전달**(Delivery) — 스트림별로 **SSN 순서대로** 상위 계층에 전달
        · 다른 스트림은 **영향 없이 독립 전달**

■ (3) 경로 관리 (멀티호밍 동작)​

   [**경로 감시 및 절체**]

   **① 주 경로(Primary Path) 선정** — 연관 수립 시 결정
        ▼
   **② HEARTBEAT 주기 송신** — 모든 **대체 경로**에 생존 확인
        │  · HEARTBEAT ACK 수신 → 경로 **Active**
        │  · 응답 없음이 임계치 초과 → 경로 **Inactive**
        ▼
   **③ 주 경로 장애 감지**
        │  · 재전송 실패 횟수가 **Path.Max.Retrans** 초과
        ▼
   **④ 자동 경로 절체(Failover)**
        │  · **Active 상태의 대체 경로로 전환**
        │  · **연관은 유지** → 애플리케이션은 장애를 인지하지 못함
        ▼
   **⑤ 주 경로 복구 시** — HEARTBEAT 응답 재개 → Active 복귀

■ (4) 연관 해제 — 3-way (Graceful Shutdown)​

   [호스트 A]                              [호스트 B]
        │ ── ① **SHUTDOWN** ──────────────▶ │
        │    (미전송 데이터 모두 전송 후)     │
        │ ◀─ ② **SHUTDOWN ACK** ─────────── │
        │ ── ③ **SHUTDOWN COMPLETE** ─────▶ │
        │        **연관 종료**                │

   ※ **TCP와의 차이** : SCTP는 **Half-Close를 지원하지 않음**
      → 한쪽이 종료를 요청하면 **양방향 모두 종료**
      → 대신 **미전송 데이터를 모두 보낸 후 종료**(Graceful)
   ※ **ABORT** : 오류 발생 시 즉시 강제 종료(TCP의 RST에 해당)

Ⅵ. 결론​

SCTP는 "TCP의 신뢰성과 UDP의 메시지 경계를 결합하고, 여기에 멀티호밍과 멀티스트리밍을 더한" 전송계층 프로토콜이다. 특히 통신망 신호(SS7)를 IP망으로 옮기는 SIGTRAN 요구에서 출발했기에, 단 한 건의 메시지 유실도 허용하지 않는 고신뢰·무중단 전송에 최적화되어 있다.

SCTP의 두 가지 핵심 차별점은 다음과 같다. 첫째, 멀티호밍은 전송계층 자체에서 경로 이중화를 제공한다. TCP에서는 경로 장애 시 세션이 끊어져 애플리케이션이 재연결을 처리해야 하지만, SCTP는 하트비트로 대체 경로를 상시 감시하다가 장애 시 자동 절체하여 연관을 유지한다. 둘째, 멀티스트리밍은 TCP의 고질적 문제인 HOL 블로킹을 해소한다. TSN(연관 전체 순서)과 SSN(스트림별 순서)을 분리 설계함으로써, 한 스트림의 패킷 손실이 다른 스트림의 전달을 막지 않도록 한 것이 핵심이다.

여기에 4-way Handshake와 State Cookie 방식은 INIT 수신 시점에 자원을 할당하지 않음으로써 SYN Flooding 공격을 구조적으로 무력화한다는 점에서, 보안 측면의 개선도 주목할 만하다.

그럼에도 SCTP가 TCP를 대체하지 못한 결정적 이유는 미들박스 통과 문제이다. 인터넷의 NAT·방화벽 다수가 프로토콜 번호 132를 인식하지 못해 패킷을 폐기하므로, 공개 인터넷에서는 사실상 사용이 어렵다. 이 때문에 SCTP는 사업자 폐쇄망(5G/LTE 코어망의 NGAP·S1AP·Diameter) 이라는 특수 영역에서 확고한 표준으로 자리 잡은 반면, 일반 인터넷 서비스에서는 UDP 기반이어서 통과가 자유로운 QUIC이 멀티스트리밍의 이점을 가져갔다.

따라서 실무적 판단은 명확하다. 폐쇄망에서 무중단 신뢰 전송이 필요하면 SCTP, 공개망에서 HOL 해소와 빠른 연결이 필요하면 QUIC을 선택하는 것이 합리적이다. 다만 SCTP를 도입할 경우 멀티호밍의 실효성을 위해 물리적으로 분리된 경로를 확보해야 하며, 자체 암호화 기능이 없으므로 IPSec·DTLS와의 결합을 반드시 설계에 포함해야 한다.

분산 데이터베이스의 투명성

문제​

13.분산 데이터베이스의 5 가지 투명성

Ⅰ. 개요​

분산 데이터베이스(Distributed Database) 는 물리적으로 여러 노드에 분산 저장된 데이터를 논리적으로 하나의 데이터베이스처럼 사용할 수 있게 하는 시스템이며, 이를 가능하게 하는 핵심 성질이 투명성(Transparency) 이다.

   [투명성의 의미]
   **"사용자가 분산되어 있다는 사실을 의식하지 않아도 된다"**

   [사용자가 보는 모습]              [실제 물리 구조]
   ┌────────────────┐               ┌─────┐ ┌─────┐ ┌─────┐
   │  **하나의 DB**  │   ◀── 은닉 ──  │서울 │ │부산 │ │대전 │
   │  SELECT * FROM │               │노드 │ │노드 │ │노드 │
   │      고객      │               └─────┘ └─────┘ └─────┘
   └────────────────┘                 분할·중복·이기종 DBMS
   ⇒ 사용자는 **"어디에, 어떻게 나뉘어, 몇 벌이 있는지" 몰라도 됨**

Ⅱ. 분산 데이터베이스의 5가지 투명성​

 ┌────────── **5대 투명성** ──────────┐
 │  **① 분할 투명성**(Fragmentation)   │  "어떻게 나뉘었는가"
 │  **② 위치 투명성**(Location)        │  "어디에 있는가"
 │  **③ 중복 투명성**(Replication)     │  "몇 벌이 있는가"
 │  **④ 병행 투명성**(Concurrency)     │  "동시 접근 시 충돌"
 │  **⑤ 장애 투명성**(Failure)         │  "노드가 죽었을 때"
 └─────────────────────────────────────┘

1. 분할 투명성 (Fragmentation Transparency) — 단편화 투명성​

항목내용
개념하나의 논리적 릴레이션이 여러 조각(Fragment)으로 분할되어 저장되어 있어도, 사용자는 분할 사실을 모르고 전체 테이블처럼 질의
분할 유형· 수평 분할(Horizontal) — 행(Row) 기준 분할(지역별 고객)
· 수직 분할(Vertical) — 열(Column) 기준 분할(기본정보 / 상세정보)
· 혼합 분할(Hybrid)
예시사용자: SELECT * FROM 고객
실제: 서울 노드(고객_서울) + 부산 노드(고객_부산)를 자동 결합(UNION)
분할 조건완전성(모든 데이터 포함), 재구성 가능성(원본 복원 가능), 상호 중첩 배제(중복 없음)

2. 위치 투명성 (Location Transparency)​

항목내용
개념데이터가 물리적으로 어느 노드에 저장되어 있는지 몰라도 논리적 이름만으로 접근
구현분산 데이터 사전(Global Data Dictionary) 이 논리명 ↔ 물리 위치를 매핑
예시사용자: SELECT * FROM 고객 (위치 지정 불필요)
미지원 시: SELECT * FROM seoul_db.고객 (위치 명시 필요)
효과데이터 재배치(이전) 시 애플리케이션 수정 불필요 ← 최대 이점

3. 중복 투명성 (Replication Transparency)​

항목내용
개념동일 데이터가 여러 노드에 복제되어 있어도 사용자는 하나만 존재하는 것처럼 인식
시스템 책임· 갱신 시 모든 복제본에 자동 전파(일관성 유지)
· 조회 시 가장 가까운·부하가 적은 복제본 선택
목적가용성 향상(한 노드 장애 시 대체), 조회 성능 향상(부하 분산), 지역 접근 지연 감소
부담복제본이 많을수록 갱신 비용·일관성 유지 비용 증가(읽기 ↑ vs 쓰기 ↓)

4. 병행 투명성 (Concurrency Transparency)​

항목내용
개념여러 사용자·트랜잭션이 동시에 접근해도 서로 간섭 없이 일관된 결과 보장
구현 기법· 2PL(2단계 잠금 규약), 분산 잠금 관리자
· 타임스탬프 순서화, MVCC(다중 버전 동시성 제어)
· 분산 교착상태(Deadlock) 탐지·해결
난점단일 DB보다 락 관리가 노드 간 통신을 수반 → 성능 저하·전역 교착 발생 가능

5. 장애 투명성 (Failure Transparency)​

항목내용
개념일부 노드나 네트워크 링크에 장애가 발생해도 트랜잭션의 원자성과 일관성이 유지되고 서비스가 지속
구현 기법· 2PC(2단계 커밋) — 모든 노드가 준비되면 커밋, 아니면 전체 롤백
· 3PC(2PC의 블로킹 문제 완화), Paxos·Raft(합의 알고리즘)
· 로그 기반 복구, 복제본을 통한 자동 절체(Failover)
핵심All or Nothing — 부분 반영으로 인한 데이터 불일치 방지
   [**2PC(2단계 커밋)** — 장애 투명성의 대표 기법]

   **[Phase 1 — 준비(Prepare)]**
   조정자(Coordinator) ──"커밋 준비 됐나?"──▶ 참여 노드 1,2,3
                        ◀──"Yes / No"────────

   **[Phase 2 — 커밋(Commit)]**
   모두 Yes ─▶ "**COMMIT**" 전송 → 전 노드 커밋
   하나라도 No ─▶ "**ABORT**" 전송 → 전 노드 롤백

   ※ 한계 : 조정자 장애 시 참여 노드가 **무한 대기(Blocking)** → 3PC·Raft로 보완

Ⅲ. 투명성 종합 비교​

투명성감추는 대상사용자의 질문대표 구현 기술
분할분할 구조(수평·수직)"어떻게 나뉘어 있나?"분산 질의 처리기, 조각 결합
위치물리적 저장 위치"어느 서버에 있나?"분산 데이터 사전, 네이밍
중복복제본의 존재·개수"몇 벌이 있나?"복제 관리, 갱신 전파
병행동시 접근 충돌"다른 사람과 겹치면?"2PL·MVCC·타임스탬프
장애노드·네트워크 장애"서버가 죽으면?"2PC·3PC·Raft, 로그 복구

※ 문헌에 따라 분할 투명성을 위치 투명성에 포함시키고, 이전(Migration)·확장(Scaling)·접근(Access)·이기종(Heterogeneity) 투명성을 추가하기도 한다.

Ⅳ. 장단점 및 고려사항​

구분내용
분산 DB 장점· 지역 자치성(각 지역이 자기 데이터 관리)
· 가용성·신뢰성 향상(일부 장애에도 서비스 지속)
· 점진적 확장 용이(노드 추가)
· 지역 접근으로 응답 속도 향상
분산 DB 단점· 설계·관리 복잡도 급증
· 네트워크 의존성(통신 비용·지연)
· 분산 트랜잭션 처리 부담(2PC 오버헤드)
· 보안 통제 지점 분산, 잠재적 오류 발생 지점 증가
   [**CAP 정리와 투명성의 한계**]
   분산 환경에서 **C(일관성)·A(가용성)·P(분할내성)** 를 동시 만족 불가
        │  네트워크 분할(P)은 **불가피** → **C와 A 중 선택**
        ▼
   **CP 선택** : 일관성 우선 → 분할 시 **일부 서비스 중단**(전통 RDBMS 분산)
   **AP 선택** : 가용성 우선 → **최종적 일관성**(NoSQL, BASE)

   ⇒ **완벽한 투명성은 이론적으로 달성 불가**
      → 실무는 **어느 투명성을 얼마나 포기할지 선택**하는 문제
고려사항내용
① 분할 기준 설계접근 패턴 기반 분할이 핵심 — 잘못 설계하면 매 질의마다 다중 노드 조인 발생
② 복제 수준 결정읽기 성능·가용성 ↔ 쓰기 비용·일관성 유지 비용의 상충
③ 일관성 모델 선택업무 특성에 따라 강한 일관성(금융 정산) vs 최종적 일관성(SNS 피드)
④ 네트워크 비용 최소화분산 조인 회피, 데이터 지역성(Locality) 확보
⑤ 전역 교착상태 관리분산 락의 타임아웃·탐지 주기 설정
⑥ 운영 복잡도모니터링·백업·복구를 전 노드 통합 관리
⑦ 최신 흐름NewSQL(CockroachDB·TiDB·Spanner) — 분산 환경에서 강한 일관성 + 수평 확장 동시 추구

Ⅴ. 결론​

분산 데이터베이스의 5가지 투명성 — 분할·위치·중복·병행·장애 — 은 결국 "분산의 복잡성을 시스템이 흡수하고, 사용자에게는 단일 DB처럼 보이게 한다" 는 하나의 목표를 다섯 측면에서 구현한 것이다. 분할·위치·중복 투명성은 데이터의 물리적 배치를 감추고, 병행·장애 투명성은 분산 환경에서의 정합성과 지속성을 보장한다는 점에서 성격이 구분된다.

실무적으로 가장 큰 가치를 갖는 것은 위치 투명성이다. 데이터 위치가 애플리케이션 코드에 노출되지 않아야 데이터 재배치·노드 증설 시 애플리케이션을 수정하지 않아도 되기 때문이다. 반면 구현 난이도가 가장 높은 것은 장애 투명성으로, 2PC는 조정자 장애 시 블로킹 문제가 있어 최근에는 Raft·Paxos 기반 합의 알고리즘으로 대체되는 추세이다.

한편 CAP 정리가 시사하듯, 완벽한 투명성은 이론적으로 달성 불가능하다. 네트워크 분할이 발생하면 일관성과 가용성 중 하나를 포기해야 하므로, 실무의 과제는 "모든 투명성을 완전히 확보하는 것"이 아니라 "업무 특성에 맞춰 어떤 투명성을 어느 수준까지 확보할 것인지 의식적으로 선택하는 것" 이다. 금융 정산처럼 정확성이 절대적인 영역은 강한 일관성(CP)을, 소셜 피드처럼 가용성이 중요한 영역은 최종적 일관성(AP)을 택하는 것이 합리적이며, 최근의 NewSQL 계열은 이 둘의 간극을 좁히려는 시도로 이해할 수 있다.

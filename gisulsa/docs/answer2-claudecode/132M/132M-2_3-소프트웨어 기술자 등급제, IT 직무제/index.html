소프트웨어 기술자 등급제, IT 직무제

문제​

3.현재, 소프트웨어 기술자 구분은 과거 기술자 등급제에서 IT 역량분류체계를 기반으로한 직무제(이하 IT 직무제)로 운영되고 있으나 실무 현장에서는 여전히 폐지된 등급제가 다수 활용되고 있는 실정이다.소프트웨어 기술자 구분에 대하여 다음을 설명하시오.
가.소프트웨어 기술자 등급제와 IT 직무제의 개념과 특징
나.현행 IT 직무제의 문제점과 개선방향

Ⅰ. 개요​

1. 배경​

소프트웨어 기술자 구분 체계는 SW사업 대가 산정(노임단가)의 기준이자 기술 인력의 경력 인정 체계로 기능해 왔다. 과거의 학력·경력 중심 등급제가 실제 역량을 반영하지 못한다는 비판에 따라 직무·역량 중심의 IT 직무제로 전환되었으나, 현장에서는 여전히 등급제 관행이 지속되고 있다.

   [제도 변천]
   **SW기술자 등급제**(초급·중급·고급·특급)
        │  · 「소프트웨어산업진흥법」 시행규칙에 근거
        │  · **학력 + 경력 연수**로 등급 산정 → 노임단가 적용
        ▼
   [비판] "**나이와 학력이 곧 실력인가**"
        · 실제 역량·성과와 무관 → **고급 인력 저평가**
        · 신기술 역량 반영 불가, **경력만 쌓으면 자동 승급**
        · 등급 상한(특급)으로 **고급 인력의 대가 한계**
        ▼
   **2012.1** 「소프트웨어산업진흥법」 개정으로 **등급제 폐지**
   **2012~** **IT 역량분류체계(ITSQF)** 기반 **직무제** 도입
        │  ※ 한국소프트웨어산업협회(KOSA) **SW기술자 경력관리** 운영
        ▼
   **현재** 「**소프트웨어 진흥법**」 체제
        · 대가 산정 : **직무별 평균임금** 공표(KOSA 연 1회)
        · 그러나 **현장은 여전히 등급제 관행 잔존**

2. 관련 근거​

근거내용
소프트웨어 진흥법SW기술자 신고·경력관리, 기술자 육성
동법 시행령·시행규칙경력 인정 기준, 신고 절차
SW사업 대가산정 가이드(KOSA)SW기술자 평균임금 적용 기준
국가직무능력표준(NCS)정보통신 분야 직무·능력단위·수준 체계
ITSQF(IT 역량분류체계)직무·역량·수준 분류

Ⅱ. 가. 등급제와 IT 직무제의 개념과 특징​

1. 소프트웨어 기술자 등급제​

■ 개념​

SW기술자 등급제란 기술자의 학력과 경력 연수를 기준으로 초급·중급·고급·특급 4단계로 구분하고, 등급별 노임단가를 적용하여 사업 대가를 산정하던 제도이다.

   [등급 산정 구조 — 학력 + 경력 연수]

   ┌──────┬──────────────────────────────────────────────┐
   │**특급**│ 기술사 자격 / 박사 + 경력 3년 /              │
   │      │ 석사 + 9년 / 학사 + 12년 / 전문학사 + 15년   │
   ├──────┼──────────────────────────────────────────────┤
   │**고급**│ 박사 / 석사 + 6년 / 학사 + 9년 /             │
   │      │ 전문학사 + 12년                              │
   ├──────┼──────────────────────────────────────────────┤
   │**중급**│ 석사 / 학사 + 3년 / 전문학사 + 6년           │
   ├──────┼──────────────────────────────────────────────┤
   │**초급**│ 학사 / 전문학사 + 3년 / 기사 자격 등         │
   └──────┴──────────────────────────────────────────────┘
        ※ 등급 = **f(학력, 경력 연수)** — **직무·역량 무관**
        ※ 등급별 **노임단가(월/일 단가)** 를 곱하여 사업비 산정

■ 특징​

구분내용
산정 기준학력 + 경력 연수(투입 요소 중심)
적용 방식등급 × 노임단가 × 투입 인월(M/M) = 사업 대가
장점· 기준이 명확·객관적 — 학력·경력은 서류로 확인 가능
· 산정이 단순하여 발주·정산이 용이
· 분쟁 소지가 적음
· 오랜 관행으로 모든 이해관계자가 익숙
단점· 실제 역량·성과를 반영하지 못함("연차 = 실력" 가정)
· 직무 특성 무시 — 아키텍트·보안전문가·DBA를 동일 잣대로 평가
· 고급 인력 저평가 — 특급 상한으로 최고 전문가도 동일 단가
· 투입 인월(M/M) 중심 산정 고착 → 생산성·품질 유인 부재
· 신기술 역량 반영 불가(AI·클라우드 등)
· 경력만 쌓으면 자동 승급 → 역량 개발 유인 저하

2. IT 직무제 (IT 역량분류체계 기반)​

■ 개념​

IT 직무제란 SW기술자를 수행 직무(Job) 로 분류하고, 각 직무에서 요구되는 역량 수준(Level) 에 따라 구분·평가하는 제도이다. 대가 산정은 직무별 평균임금을 적용한다.

   [IT 직무제의 구조]

   **[직무 분류]** — 무엇을 하는 사람인가
   ┌────────────────────────────────────────────────────┐
   │ **IT 기획자** · **IT 컨설턴트** · **업무분석가**      │
   │ **데이터 아키텍트** · **IT 아키텍트** · **UI/UX 개발자**│
   │ **응용SW 개발자** · **시스템SW 개발자** ·            │
   │ **임베디드SW 개발자** · **DB 운용자** ·              │
   │ **NW 엔지니어** · **IT 시스템 운용자** ·             │
   │ **IT 지원 기술자** · **정보보안 전문가** ·           │
   │ **IT 품질관리자** · **IT 테스터** · **IT 감리** 등    │
   └────────────────────────────────────────────────────┘
              ×
   **[역량 수준]** — 어느 정도 수준인가 (**NCS·ITSQF 수준 체계**)
   Level 1(단순 반복) → … → Level 6~8(**최고 전문가·의사결정**)
              ▼
   **직무별·수준별 평균임금** 적용 → 사업 대가 산정
   (KOSA 「SW기술자 평균임금」 **연 1회 공표**)

■ 특징​

구분내용
산정 기준직무 + 역량 수준(직무 특성 중심)
적용 방식직무별 평균임금 × 투입 기간, 또는 시장 임금 기반 협상
장점· 직무 특성 반영 — 아키텍트·보안전문가의 가치를 별도 인정
· 역량 중심 — 학력·연차가 아닌 실제 수행 능력 기준
· 시장 임금 반영(평균임금 공표) → 현실성 제고
· 전문성 심화 경로 제시 → 경력 개발 유인
· NCS·글로벌 직무 체계와 정합
· 신규 직무(AI·클라우드·데이터) 탄력적 추가 가능
단점· 역량 수준 측정·검증이 어려움(객관적 증빙 곤란)
· 직무 구분이 모호(실무자는 다수 직무를 겸함)
· 발주기관의 판단 부담 증가
· 평균임금은 참고값 → 실제 적용 기준 불명확
· 제도 인지도·수용성 낮음

3. 등급제와 IT 직무제 비교​

비교 기준등급제(폐지)IT 직무제(현행)
분류 기준학력 + 경력 연수직무 + 역량 수준
철학연공서열(투입 중심)역량·성과(직무 중심)
구분 단위4단계(초·중·고·특급)10여 개 직무 × 수준
직무 특성 반영없음(모든 직무 동일)있음
대가 산정등급별 노임단가직무별 평균임금
상한특급이 상한 → 고급 인력 저평가수준별 차등 → 상한 완화
객관성·명확성높음(서류 확인)낮음(역량 측정 어려움)
적용 편의성매우 높음낮음
역량 개발 유인낮음(자동 승급)높음(전문성 심화)
신기술 대응불가가능
현장 수용성높음(관행 지속)낮음
법적 지위2012년 폐지현행 제도

Ⅲ. 나. 현행 IT 직무제의 문제점과 개선방향​

1. 문제점​

 ┌───────── **문제의 구조** ─────────┐
 │  **① 제도 설계상의 문제**          │
 │  **② 운영·적용상의 문제**          │
 │  **③ 시장 관행의 문제**            │
 │  **④ 산업 구조적 문제**            │
 └────────────────────────────────────┘
구분문제점내용
① 제도 설계역량 측정 기준의 부재· "Level 5는 무엇을 할 수 있는 사람인가" 에 대한 객관적 판정 기준 미흡
· 역량을 입증할 공인 평가·인증 체계 부재
· 결국 경력 연수로 회귀하는 역설
직무 분류의 모호성· 실무자는 한 사람이 개발·DB·운영을 겸업
· 프로젝트 중 역할 변경 빈번 → 어느 직무로 신고할지 불명확
· 신기술 직무 미반영(AI 엔지니어·MLOps·데이터 사이언티스트·클라우드 아키텍트)
② 운영·적용평균임금의 한계· 참고 자료일 뿐 강제력 없음 → 실제 적용 기준으로 불충분
· 조사 표본의 대표성 논란, 실제 시장 임금과 괴리
· 직무별 편차가 커도 평균값 하나로 제시
경력 신고·관리의 부담· 신고 절차 복잡, 프리랜서·중소기업 참여 저조
· 경력 증빙 곤란(폐업 기업, 미신고 기간)
발주기관의 적용 곤란· 직무·수준 판단에 전문성 필요 → 담당자 부담
· 감사 대응 시 객관적 근거 제시 어려움 → 안전한 등급제 선호
③ 시장 관행등급제 관행의 지속(핵심)· RFP·계약서에 여전히 "고급 3명, 중급 5명" 형태 기재
· 발주자·수행사 모두 익숙하고 분쟁 소지가 적은 등급제 선호
· 제도는 바뀌었으나 관행은 그대로 → 이중 체계로 인한 혼란
투입 인월(M/M) 중심 관행· 직무제로 바뀌어도 "몇 명 × 몇 개월" 산정 방식은 동일
· 성과·가치 기반 계약으로 전환 실패
④ 산업 구조고급 인력 대우 문제 미해결· 직무제 도입 취지였던 최고 전문가 처우 개선이 실질적으로 미흡
· 여전히 저가 수주 경쟁 → 인건비 압박
인력 유출· 처우·경력 인정 미흡 → 빅테크·해외 이직, SI 기피
· 개발자 경력 사다리 부재
   [**핵심 문제 — 제도와 현실의 괴리**]

   **[제도]** IT 직무제 (역량 중심)      **[현실]** 등급제 관행 (연차 중심)
        │                                      │
        │  · 역량 측정 기준 없음               │  · 익숙함
        │  · 판단 부담·감사 리스크             │  · 명확·객관적
        │  · 평균임금은 참고값                 │  · 분쟁 소지 적음
        └──────────── **괴리** ─────────────────┘
                        ▼
   ⇒ 제도가 **작동하지 않는 이유는 취지가 틀려서가 아니라**
      **"역량을 객관적으로 증명할 수단"이 없기 때문**

2. 개선방향​

구분개선방향세부 내용
① 역량 검증 체계 구축
(최우선)		객관적 역량 증명 수단 마련· 직무별·수준별 역량 기준(KSA)의 구체화 — "무엇을 할 수 있어야 하는가"를 행동 지표로 명시
· NCS 기반 역량 평가·인증제 도입(직무별 자격·검정)
· 포트폴리오·프로젝트 실적 기반 인증 — 코드·산출물·기여도
· 민간 자격·글로벌 인증(AWS·CKA·CISSP 등) 연계 인정
· 기술사·기사 등 국가자격과의 매핑 명확화
② 직무 체계 현행화신기술 직무 반영· AI/ML 엔지니어, MLOps, 데이터 사이언티스트, 클라우드 아키텍트, DevOps, SRE, 보안관제 등 신규 직무 추가
· 정기 개정 체계(연 1회 이상) 마련
· 겸직·멀티롤 인정 — 주직무 + 부직무 표기 허용
③ 대가 산정 실효성 제고평균임금의 신뢰성·활용도 향상· 조사 표본 확대·세분화(직무 × 수준 × 지역 × 기업 규모)
· 평균값뿐 아니라 분위값(25/50/75%) 공표
· 공공 발주 시 직무제 적용 의무화·가이드 제공
· 표준 RFP 양식을 직무 기반으로 전환
④ 발주 관행 개선제도 정착을 위한 강제·지원· RFP·계약서의 등급 표기 금지·직무 표기 의무화
· 발주 담당자 교육·컨설팅 지원, 판단 체크리스트 제공
· 감사 면책 기준 마련 — 가이드 준수 시 책임 완화
· 과업심의위원회에서 직무 적정성 검토
⑤ 계약 방식 전환투입(M/M) → 성과·가치 기반· 기능점수(FP) 기반 대가 산정 확대
· 성과 기반 계약(SLA·산출물 기준) 도입
· 운영·유지관리는 서비스 수준 기반 계약
· 근본적으로 "몇 명이 몇 달"에서 "무엇을 얼마나" 로 전환
⑥ 경력관리 체계 개선참여 유인·편의성 제고· 경력 신고 전산 자동화(4대보험·계약 정보 연계)
· 프리랜서·중소기업 참여 인센티브
· 경력 정보의 활용처 확대(채용·평가·교육 연계)
⑦ 산업 구조 개선고급 인력 처우 개선· 저가 수주 방지(적정 대가 지급 제도 강화)
· 최고 전문가에 대한 상한 없는 대가 인정
· 하도급 구조 개선, 원·하도급 대가 지급 투명화
· 경력 개발 경로(Career Path) 와 연계한 교육·재직자 훈련
   [**개선의 우선순위와 논리**]

   **1순위 : 역량 검증 체계 구축**
        │  → 직무제가 작동하지 않는 **근본 원인**
        │  → 객관적 증명 수단이 있어야 발주자가 안심하고 적용
        ▼
   **2순위 : 발주 관행 강제 + 가이드·면책**
        │  → 제도가 있어도 쓰지 않으면 무의미
        │  → **의무화 + 판단 지원 + 감사 면책**의 3종 세트 필요
        ▼
   **3순위 : 대가 산정 데이터 정교화**
        │  → 평균값 → **분위값·세분화**로 실효성 확보
        ▼
   **4순위 : 계약 방식의 근본 전환(M/M → 성과 기반)**
        │  → 장기 과제이나 **가장 본질적인 해법**

Ⅳ. 결론​

SW기술자 등급제에서 IT 직무제로의 전환은 "연차와 학력이 곧 실력"이라는 전제를 버리고, 직무 특성과 실제 역량으로 기술자를 평가하겠다" 는 올바른 방향의 제도 개선이었다. 등급제가 갖는 직무 무차별성과 특급 상한으로 인한 고급 인력 저평가 문제는 SW 산업의 전문성 심화를 가로막는 구조적 한계였기 때문이다.

그럼에도 현장에서 폐지된 등급제가 여전히 통용되는 이유는 제도의 취지가 잘못되었기 때문이 아니라, "역량을 객관적으로 증명할 수단"이 마련되지 않았기 때문이다. 발주기관 입장에서는 감사에 대응할 수 있는 명확한 근거가 필요한데, 학력·경력 연수는 서류로 확인되는 반면 "이 사람이 Level 5 아키텍트인가" 는 증명할 방법이 없다. 결국 담당자는 분쟁 소지가 적고 익숙한 등급제로 회귀하게 된다.

따라서 개선의 핵심은 ① 직무별·수준별 역량 기준을 행동 지표로 구체화하고, ② 이를 검증할 평가·인증 체계를 구축하는 데 있다. 여기에 ③ 신기술 직무(AI·MLOps·클라우드·SRE)를 반영한 직무 체계의 정기 현행화, ④ 평균임금의 세분화·분위값 공표, ⑤ 공공 발주 시 직무제 적용 의무화와 함께 판단 가이드·감사 면책 기준 제공이 병행되어야 제도가 실제로 작동할 수 있다.

나아가 근본적으로는 투입 인월(M/M) 중심의 대가 산정 구조 자체를 성과·가치 기반으로 전환하는 것이 필요하다. 등급제든 직무제든 "몇 명이 몇 달 투입되는가"로 대가를 정하는 한, 생산성 향상과 고급 인력 활용의 유인은 생기지 않기 때문이다. 기능점수(FP) 기반 산정과 SLA 기반 서비스 계약의 확대가 장기적 해법이며, 이것이 뒷받침될 때 비로소 IT 직무제가 지향한 "역량 있는 전문가가 정당한 대가를 받는 산업 생태계" 가 실현될 수 있을 것이다.

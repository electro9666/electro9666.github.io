공공데이터 예방적 품질관리

문제​

2.행정안전부에서는 고품질의 공공데이터 제공 및 활용의 선제적 대응을 위해 '공공데이터 베이스 표준화 관리 매뉴얼(2023.04.)'을 마련하여 예방적 품질관리 기준을 제시하고 있다. 이와 관련하여 다음을 설명하시오.
가.시스템 구축 추진 단계별 예방적 품질관리 활동
나.공공데이터 예방적 품질관리 4 개 진단영역과 9 개 진단항목

Ⅰ. 개요​

1. 배경​

공공데이터 개방이 확대되었으나, 개방된 데이터의 품질 미흡(오류·중복·표준 미준수·의미 불명확)으로 인해 활용도가 저조하고 재가공 비용이 발생하는 문제가 지속되었다.

   [기존 사후 품질관리의 한계]

   시스템 구축 완료 → 데이터 축적 → **개방 후 품질 문제 발견**
        │  · 이미 **수백만 건의 오류 데이터가 축적**
        │  · **구조적 결함**(표준 미준수·모델 오류)은 사후 수정 불가
        │  · 정제 비용 과다, 근본 원인 미해결 → **오류 반복 생성**
        ▼
   [**예방적 품질관리**(Preventive Quality Management)]
   **"데이터가 만들어지기 전에 품질을 설계한다"**
   · 시스템 **구축 단계부터 품질 기준을 내재화**
   · **DB 표준화**를 통해 오류 발생 원인 자체를 차단
        ▼
   근거 : **공공데이터법**(공공데이터의 제공 및 이용 활성화에 관한 법률),
          **데이터기반행정법**, **공공데이터베이스 표준화 관리 매뉴얼**(2023.04.),
          **공공데이터 품질관리 매뉴얼**, 행정안전부 **공공데이터 품질관리 수준평가**

2. 예방적 품질관리의 개념​

예방적 품질관리란 데이터 품질 문제를 사후에 정제·보정하는 것이 아니라, 정보시스템의 기획·설계·구축 단계에서 품질 기준(특히 DB 표준화)을 적용하여 오류 발생을 원천적으로 예방하는 관리 방식이다.

   [**사후적 품질관리 vs 예방적 품질관리**]

   ┌──────────────┬──────────────────┬──────────────────┐
   │ 구분         │ **사후적 품질관리** │ **예방적 품질관리** │
   ├──────────────┼──────────────────┼──────────────────┤
   │ 시점         │ **운영·개방 이후**  │ **구축 단계**      │
   │ 대상         │ 축적된 데이터 값   │ **DB 구조·표준**   │
   │ 방법         │ 진단·정제(Cleansing)│ **표준화·설계 검증**│
   │ 효과         │ 일시적 개선        │ **근본 원인 제거**  │
   │ 비용         │ **높음**(반복 발생) │ **낮음**(1회 투자)  │
   │ 한계         │ **구조적 결함 불가**│ 초기 노력 필요     │
   └──────────────┴──────────────────┴──────────────────┘

   [**1:10:100 법칙**] 데이터 품질 비용
   **예방 1** : 검출·수정 10 : **실패(잘못된 의사결정) 100**

3. 데이터 품질 기준​

품질 기준내용
완전성(Completeness)필수 항목에 누락 없이 값이 존재
유일성(Uniqueness)중복 데이터가 없음(식별자 유일)
유효성(Validity)값이 정의된 형식·범위·도메인에 부합
일관성(Consistency)관련 데이터 간 모순이 없음
정확성(Accuracy)값이 실제 현실을 정확히 반영
적시성(Timeliness)필요한 시점에 최신 데이터 제공

Ⅱ. 가. 시스템 구축 추진 단계별 예방적 품질관리 활동​

1. 전체 흐름​

 ┌── **① 사업 기획** ──┬── **② 분석·설계** ──┬── **③ 구축·개발** ──┬── **④ 시험·검수** ──┬── **⑤ 운영·개방** ──┐
 │  품질 요구사항 정의  │ **DB 표준 정의**     │ 표준 적용 구현      │ **품질 진단**        │ 지속 품질관리       │
 │  예산·조직 확보      │ 데이터 모델 표준 준수│ 검증 로직 구현      │ 표준 준수 확인       │ 표준 변경 관리      │
 └──────────┬──────────┴──────────┬──────────┴──────────┬─────────┴──────────┬─────────┴──────────┬──────────┘
            ▼                     ▼                     ▼                    ▼                    ▼
      **RFP 반영**           **표준 사전 구축**      **표준 준수 개발**     **진단·시정**       **모니터링·환류**

2. 단계별 세부 활동​

■ ① 사업 기획 단계​

활동세부 내용
품질 목표·요구사항 정의· 구축할 시스템의 데이터 품질 목표 수립
· 품질 요구사항을 RFP·과업내용서에 명시(DAR·QUR)
· 품질관리 예산·기간 확보
표준화 적용 계획 수립· 공공데이터 DB 표준화 적용 범위 결정
· 기관 표준 존재 여부 확인, 공통표준용어 활용 계획
추진 조직·역할 정의· 데이터 품질 담당자·데이터 관리자(DA) 지정
· 발주기관·수행사 간 품질 책임 범위 명확화
개방 대상 사전 식별· 구축 시스템에서 개방 예정 데이터 사전 식별
· 개방을 전제로 한 설계 요구사항 도출
법·제도 검토공공데이터법·데이터기반행정법 요건, 개인정보 포함 여부

■ ② 분석·설계 단계 (가장 중요한 단계)​

활동세부 내용
DB 표준 정의(핵심)· 표준 용어·단어·도메인·코드 사전 수립
· 행정표준용어·공통표준용어 준용
· 표준 없는 항목은 기관 표준으로 신규 정의
데이터 모델링 품질 확보· 개념·논리·물리 모델의 단계적 수립
· 정규화 수행, 식별자(PK) 적정성 확보
· 엔터티·속성 정의서 작성(의미 명확화)
표준 준수 설계· 테이블·컬럼 명명 규칙 준수
· 도메인 기반 데이터 타입·길이 정의
· 공통코드 체계 설계
품질 검증 규칙 설계· 무결성 제약조건(PK·FK·NOT NULL·UNIQUE·CHECK) 정의
· 업무 규칙 기반 검증 로직 설계
· 값 범위·형식 규칙(도메인 규칙)
메타데이터 정의· 데이터의 의미·출처·갱신주기·담당자 정의
· 개방용 메타데이터 항목 사전 설계
설계 산출물 검토· 데이터 모델 리뷰·감리
· CRUD 매트릭스로 프로세스-데이터 교차 검증
· 표준 준수율 점검
   [**DB 표준화의 4대 구성요소**]

   ┌──────────────┬────────────────────────────────────────┐
   │ **표준 단어**  │ 업무에서 사용하는 **최소 의미 단위**     │
   │              │ 예) 고객, 번호, 일자, 금액              │
   ├──────────────┼────────────────────────────────────────┤
   │ **표준 용어**  │ 단어의 조합으로 만든 **속성명**          │
   │              │ 예) 고객번호(=고객+번호), 등록일자       │
   ├──────────────┼────────────────────────────────────────┤
   │ **표준 도메인**│ 속성의 **데이터 타입·길이·형식**         │
   │              │ 예) 일자 → DATE, 금액 → NUMBER(15)      │
   ├──────────────┼────────────────────────────────────────┤
   │ **표준 코드**  │ 공통으로 사용하는 **코드 값 체계**        │
   │              │ 예) 성별코드(1:남,2:여), 시도코드        │
   └──────────────┴────────────────────────────────────────┘
   ⇒ **표준이 없으면** 같은 의미가 시스템마다 다르게 표현
      (고객번호 / CUST_NO / CUSTOMER_ID / 고객ID)
      → **데이터 통합·개방·연계 불가**

■ ③ 구축·개발 단계​

활동세부 내용
표준 준수 구현· 설계된 표준 용어·도메인·코드를 그대로 적용
· 임의 변경 금지, 변경 시 표준 개정 절차 경유

· DB 제약조건 실제 적용(설계에만 있고 미구현 사례 방지)
· 코드 값 검증(공통코드 참조)
데이터 이관 품질 확보· 기존 시스템 데이터 이관 시 정합성 검증
· 표준 코드로의 변환 매핑 정의·검증
· 이관 전후 건수·체크섬·샘플 대사
메타데이터 등록· 데이터 사전(Data Dictionary) 구축
· 표준 준수 여부 자동 점검 도구 적용
개발 중 점검· 정기적 표준 준수율 점검
· 비표준 항목 발견 시 즉시 시정

■ ④ 시험·검수 단계​

활동세부 내용
품질 진단 실시· 4개 진단영역·9개 진단항목 기준 진단(아래 Ⅲ 참조)
· 표준 준수율·무결성 위반 건수 측정
데이터 값 검증· 완전성·유일성·유효성·일관성 점검
· 샘플 데이터 실제 값 확인
개방 적합성 검토· 개방 대상 데이터의 개방 형식(CSV·JSON·API) 적정성
· 개인정보·비공개 정보 포함 여부 최종 확인
시정 조치· 진단 결과 부적합 항목 시정 요구
· 시정 완료 확인 후 검수
검수 기준 적용품질 기준 충족을 검수 조건에 포함
감리 연계정보시스템 감리 시 데이터 품질 점검 항목 반영

■ ⑤ 운영·개방 단계​

활동세부 내용
지속적 품질 모니터링· 정기 품질 진단(연 1회 이상)
· 품질 지표 측정·추이 관리

· 신규 항목 추가 시 표준 등록 절차 준수
이용자 피드백 처리· 오류 신고 접수·처리
· 활용 요구 반영
품질관리 수준평가 대응행정안전부 공공데이터 품질관리 수준평가 대응
개선 환류진단 결과를 차기 시스템 구축에 반영(PDCA)
   [**단계별 품질관리 효과의 차이**]

   품질 개선 비용 ▲
                 │                              ╱ **운영 단계**
                 │                         ╱      (100배)
                 │                    ╱
                 │              ╱  **구축·시험**
                 │        ╱        (10배)
                 │  ──╱  **기획·설계**
                 │      **(1배)** ★ 예방적 품질관리의 핵심 구간
                 └──────────────────────────────────▶ 시간

   ⇒ **설계 단계의 DB 표준화가 가장 비용 효율적**

Ⅲ. 나. 공공데이터 예방적 품질관리 4개 진단영역과 9개 진단항목​

1. 진단 체계​

 ┌────────── **예방적 품질관리 진단 체계** ──────────┐
 │                                                   │
 │  **[영역 1] 관리체계**                             │
 │      ① 품질관리 조직·인력                          │
 │      ② 품질관리 절차·규정                          │
 │                                                   │
 │  **[영역 2] 데이터 표준**                          │
 │      ③ 표준 단어·용어                              │
 │      ④ 표준 도메인·코드                            │
 │                                                   │
 │  **[영역 3] 데이터 구조(모델)**                    │
 │      ⑤ 데이터 모델 관리                            │
 │      ⑥ 표준 준수(모델 반영)                        │
 │      ⑦ 데이터 무결성                               │
 │                                                   │
 │  **[영역 4] 데이터 값·활용**                       │
 │      ⑧ 데이터 값 품질                              │

2. 진단영역별 진단항목 상세​

■ [영역 1] 품질관리 체계 (관리적 기반)​

진단항목진단 내용확인 사항
① 품질관리 조직·인력데이터 품질관리를 위한 조직과 담당자가 지정되어 있는가· 데이터 품질 책임자·담당자(DA) 지정 여부
· 역할·책임(R&R) 정의
· 전문성 확보(교육 이수)
· 사업 수행 시 품질 담당 인력 배치
② 품질관리 절차·규정품질관리를 위한 절차와 규정이 수립·이행되고 있는가· 데이터 품질관리 지침·규정 수립
· 표준 제정·변경 절차 정의
· 품질 진단·개선 절차 문서화
· 정기 점검 계획 및 이행 기록

■ [영역 2] 데이터 표준 (표준화 기반)​

진단항목진단 내용확인 사항
③ 표준 단어·용어표준 단어·용어 사전이 정의되고 활용되는가· 표준 단어 사전 구축 여부
· 표준 용어 사전 구축 여부
· 행정표준용어·공통표준용어 준용 여부
· 동의어·유의어 관리
· 금칙어 관리(사용 금지 표현)
④ 표준 도메인·코드표준 도메인과 공통 코드가 정의되고 관리되는가· 표준 도메인 정의(데이터 타입·길이·형식)
· 공통코드 체계 수립
· 행정표준코드 활용 여부
· 코드 값의 의미·중복·누락 관리
· 코드 변경 이력 관리

■ [영역 3] 데이터 구조 (모델 품질)​

진단항목진단 내용확인 사항
⑤ 데이터 모델 관리데이터 모델이 작성·관리되고 있는가· 개념·논리·물리 데이터 모델 존재 여부

· 엔터티·속성 정의서 작성(의미 기술)
· 모델 변경 관리 절차
⑥ 표준 준수(모델 반영)정의된 표준이 실제 데이터 모델·DB에 적용되었는가· 테이블·컬럼명이 표준 용어를 준수하는가
· 표준 도메인 적용률(타입·길이 일치)
· 공통코드 적용 여부
· 표준 준수율 측정 및 미준수 사유 관리
· ★ 표준을 만들고도 적용하지 않는 사례가 가장 빈번
⑦ 데이터 무결성무결성 제약조건이 정의·적용되어 있는가· 주식별자(PK) 정의 여부 및 적정성
· 참조 무결성(FK) 설정
· NOT NULL·UNIQUE·CHECK 제약조건 적용
· 제약조건이 설계에만 있고 DB에 미적용된 사례 점검
· 업무 규칙의 무결성 반영

■ [영역 4] 데이터 값 및 활용​

진단항목진단 내용확인 사항

· 유효성 — 값이 정의된 도메인·범위·형식 부합
· 일관성 — 관련 데이터 간 모순 여부
· 정확성 — 실제 사실과의 일치
· 적시성 — 갱신주기 준수, 최신성

· 개인정보·비공개 정보 미포함 확인
· 개방 주기·최신성 유지

2. 고려사항​

고려사항내용
① 기획·발주 단계 반영이 관건구축 완료 후 요구하면 재작업 비용 급증 → RFP·과업내용서에 품질 요구사항 명시해야 실효성 확보
② 표준의 실제 적용표준 사전만 만들고 실제 DB에 적용하지 않는 사례가 가장 빈번
→ 표준 준수율을 정량 측정하고 검수 기준에 포함
③ 모델 현행화ERD가 실제 DB와 불일치하면 모든 관리가 무의미 → 형상관리 편입
④ 자동화 도구 활용수작업 점검은 한계 → 데이터 프로파일링·표준 준수 점검 도구 도입
⑤ 조직·인력 확보데이터 관리자(DA) 지정과 전문성 확보가 전제 — 겸임·순환보직의 한계
⑥ 기존 시스템과의 정합신규 시스템만 표준화하면 기관 내 이원화 → 단계적 확산 계획
⑦ 개인정보 보호 연계개방 전 개인정보 포함 여부 검증, 비식별 조치
⑧ 지속성1회성 진단이 아닌 정기 진단·개선의 PDCA 정착
⑨ 이용자 관점공급자 중심이 아닌 활용자가 쓰기 쉬운 형태(메타데이터·코드 설명)

Ⅴ. 결론​

공공데이터 예방적 품질관리는 "데이터 품질은 정제하는 것이 아니라 설계하는 것" 이라는 관점의 전환을 담고 있다. 사후적 품질관리는 이미 축적된 오류를 정제할 수는 있으나, 구조적 결함(표준 미준수·모델 오류)은 근본적으로 해결하지 못하고 오류가 계속 재생산되기 때문이다.

단계별 활동 측면에서 가장 중요한 구간은 분석·설계 단계이다. 이 단계에서 표준 단어·용어·도메인·코드라는 DB 표준 4대 요소를 정의하고 데이터 모델에 반영하며 무결성 제약조건을 설계하는 것이, 이후 발생할 대부분의 품질 문제를 사전에 차단한다. 1:10:100 법칙이 보여주듯, 설계 단계의 1만큼 투자가 운영 단계의 100만큼 비용을 절감한다.

진단 체계 측면에서 4개 영역은 관리체계(조직·절차) → 데이터 표준(단어·용어·도메인·코드) → 데이터 구조(모델·표준준수·무결성) → 데이터 값·활용이라는 논리적 계층 구조를 이룬다. 즉 조직과 절차가 있어야 표준을 만들 수 있고, 표준이 있어야 모델에 적용할 수 있으며, 구조가 올바라야 값의 품질이 확보되고, 그래야 비로소 개방·활용이 가능해진다. 어느 한 계층이 부실하면 상위 계층은 성립하지 않는다.

실무에서 가장 빈번하게 발견되는 문제는 "표준 사전은 만들었으나 실제 DB에는 적용하지 않은 경우" 이다. 이는 진단항목 ⑥(표준 준수)이 별도 항목으로 존재하는 이유이기도 하다. 따라서 표준 준수율을 정량적으로 측정하고 이를 검수 기준에 포함시키는 것이 실효성 확보의 핵심이다.

궁극적으로 예방적 품질관리의 성패는 기획·발주 단계에서 품질 요구사항을 RFP에 명시하는가에 달려 있다. 구축이 완료된 뒤의 품질 요구는 재작업 비용으로 인해 형식적 수준에 그칠 수밖에 없다. 아울러 AI 기반 데이터 활용이 확대되는 환경에서 데이터 품질은 단순한 관리 이슈를 넘어 AI 모델의 성능과 신뢰성을 직접 결정하는 요소가 되었으므로, 공공데이터 품질관리의 전략적 중요성은 더욱 커지고 있다.

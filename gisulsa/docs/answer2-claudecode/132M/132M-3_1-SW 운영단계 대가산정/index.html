SW 운영단계 대가산정

문제​

1.소프트웨어(이하 SW) 운영단계 대가산정에 대하여 다음을 설명하시오.
(단, 소프트웨어 사업 대가산정 가이드 2023 년 개정판" 기준)
가.응용 SW 요율제 유지관리비 산정방식과 SW 운영 투입공수 산정방식
나.고정비/변동비 산정방식

Ⅰ. 개요​

1. 배경​

정보시스템 총비용의 대부분은 구축이 아닌 운영·유지관리 단계에서 발생한다. 그러나 그동안 운영 대가는 관행적 요율(개발비의 10~15%) 로 산정되어 실제 업무량과 무관한 저가 산정이 반복되었고, 이는 운영 품질 저하와 SW 기술자 처우 악화로 이어졌다.

   [운영 대가 산정의 문제]
   "개발비 × 요율(%)" 라는 **단순 관행**
        │  · **실제 운영 업무량과 무관** → 과소 산정
        │  · 시스템이 오래될수록 개발비는 고정, **업무량은 증가**
        │  · 운영 인력의 상주 여부·업무 범위 불명확
        │  · 재개발 후 운영비 산정 근거 소멸
        ▼
   [**SW사업 대가산정 가이드**(KOSA, 2023 개정판)]
   · **운영단계 대가산정 체계 정비**
   · **요율제 → 투입공수·기능점수 기반**으로 전환 유도
   · **고정비/변동비** 구분을 통한 합리적 산정
        ▼
   근거 : **소프트웨어 진흥법**(적정 대가 지급), 「SW사업 대가산정 가이드」

2. SW 사업 대가산정 체계​

 ┌──────────── **SW 사업 대가산정 체계** ────────────┐
 │                                                   │
 │  **[기획단계]**  정보화전략계획(ISP)·ISMP 수립비   │
 │        ▼                                          │
 │  **[구축단계]**  **SW 개발비**                     │
 │                 · **기능점수(FP) 방식**(원칙)      │
 │                 · 투입공수 방식(예외)              │
 │        ▼                                          │
 │  **[운영단계]** ★ 본 문제                          │
 │   ┌────────────────────────────────────────────┐ │
 │   │ **① SW 유지관리비**                          │ │
 │   │    · **요율제**(정률제)                       │ │
 │   │    · **기능점수(FP) 방식**                    │ │

 │   │ **② SW 운영비**                               │ │
 │   │    · **투입공수 방식**                        │ │

3. 유지관리와 운영의 구분​

구분SW 유지관리(Maintenance)SW 운영(Operation)
정의인도된 SW의 결함 제거, 성능 개선, 환경 변화 대응 등 SW 자체를 변경하는 활동시스템이 정상 서비스되도록 유지·지원하는 활동(SW 변경 없음)
주요 활동· 수정 유지관리(결함 수정)
· 적응 유지관리(환경 변화 대응)
· 완전화 유지관리(성능·기능 개선)
· 예방 유지관리(잠재 결함 제거)		· 시스템 모니터링·상태 점검
· 장애 대응·복구
· 사용자 지원(헬프데스크)
· 데이터·배치 관리, 백업
· 보안 관리, 형상 관리
대가 산정요율제 / FP / 투입공수투입공수 방식
성격SW 산출물 변경 중심서비스 제공 중심

Ⅱ. 가-1. 응용 SW 요율제 유지관리비 산정방식​

1. 개념​

요율제(정률제) 는 유지관리 대상 SW의 개발비(또는 재조달 가격)에 일정 요율(%)을 적용하여 연간 유지관리비를 산정하는 방식이다. 가장 오래되고 널리 사용되는 방식이나, 업무량을 직접 반영하지 못하는 한계가 있다.

2. 산정 산식​

   [**기본 산식**]

   **유지관리 대가 = 유지관리 대상 SW의 개발비 × 유지관리 요율(%)**

   ┌──────────────────────────────────────────────────────────┐
   │ **① 유지관리 대상 SW 개발비**                              │
   │    · 최초 구축 시 **SW 개발비**(하드웨어·상용SW 제외)       │
   │    · 또는 **기능점수(FP) × 단가**로 재산정한 금액           │
   │    · 고도화·추가 개발분 **누적 반영**                       │
   │                                                          │
   │ **② 유지관리 요율(%)**                                    │
   │    · 기본 요율 : 통상 **10~15%** 수준                      │
   │    · **유지관리 유형·난이도·서비스 수준**에 따라 조정       │
   └──────────────────────────────────────────────────────────┘

3. 요율 조정(보정) 요소​

가이드는 획일적 요율이 아니라 사업 특성을 반영한 보정을 제시한다.

보정 항목내용요율 영향
① 서비스 수준(SLA)요구되는 가동률·장애 대응시간 수준
(24×365 vs 업무시간)		높을수록 ↑
② 시스템 중요도·복잡도대국민 서비스·기간 시스템, 연계 시스템 수높을수록 ↑
③ 유지관리 대상 범위응용SW만 vs 데이터·연계·인프라 포함넓을수록 ↑
④ 사용자 규모·업무량사용자 수, 변경 요청 건수많을수록 ↑
⑤ 시스템 노후도노후 시스템은 변경 난이도·장애 빈도 증가높을수록 ↑
⑥ 기술 난이도특수 기술·레거시 언어높을수록 ↑
⑦ 상주 여부상주 인력 요구 시 인건비 반영상주 ↑
⑧ 보안 요구 수준보안 점검·인증 대응 업무높을수록 ↑
   [**보정 적용 개념**]

   **유지관리비 = 개발비 × 기본요율 × 보정계수**
                                    (서비스수준 × 중요도 ×
                                     범위 × 난이도 …)

4. 요율제의 장단점​

구분내용
장점· 산정이 매우 간단, 예산 수립 용이
· 과거 관행으로 이해관계자 수용성 높음
· 산정 비용·기간 최소
단점· 실제 업무량을 반영하지 못함 — 요청 건수·난이도 무관
· 개발비가 기준 → 시간이 지나면 기준값의 타당성 상실
· 개발비 산정이 부정확하면 오류 누적
· 요율의 객관적 근거 부족(관행적 10~15%)
· 노후 시스템의 업무량 증가 미반영 → 저가 고착
· 성과·품질 유인 없음

Ⅲ. 가-2. SW 운영 투입공수 산정방식​

1. 개념​

투입공수 방식(M/M 방식) 은 운영 업무를 수행하는 데 필요한 인력의 투입량(인월, Man-Month)을 산정하고, 직무별 노임단가(SW기술자 평균임금) 를 곱하여 대가를 산정하는 방식이다. SW 운영비 산정의 기본 방식이다.

2. 산정 산식​

   [**기본 산식**]

   **SW 운영비 = Σ(직무별 투입공수 × 직무별 노임단가) + 직접경비 + 이윤**

   ┌──────────────────────────────────────────────────────────┐
   │ **① 투입공수(M/M)**                                       │
   │    = **운영 업무량 기반 소요 인력 × 투입 기간**            │
   │    · 업무 유형별 소요 시간 분석                            │
   │    · 시스템 규모·사용자 수·장애 빈도 고려                  │
   │                                                          │
   │ **② 노임단가**                                            │
   │    · **SW기술자 평균임금**(KOSA 공표, 직무별)              │
   │                                                          │
   │ **③ 직접경비** — 여비·교통비·소모품 등 실비                │
   │ **④ 이윤** — 관련 규정에 따른 이윤율 적용                  │
   └──────────────────────────────────────────────────────────┘

3. 투입공수 산정 절차​

   ① **운영 업무 범위 정의**
        │  · 대상 시스템·서비스 범위 확정
        │  · **운영 업무 항목 도출**(모니터링·장애대응·헬프데스크·
        │     데이터관리·배치운영·보안관리·형상관리 등)
        ▼
   ② **업무량 분석**
        │  · **업무 항목별 발생 빈도 × 건당 소요 시간**
        │  · 과거 실적 데이터 활용(장애 건수·요청 건수·처리 시간)
        │  · 사용자 수, 시스템 규모, 연계 시스템 수 반영
        ▼
   ③ **서비스 수준 반영**
        │  · **운영 시간대**(업무시간 / **24×365**)
        │  · **대응 목표 시간**(SLA), **상주 여부**
        │  · **교대 근무 필요 여부** → 필요 인력 수 결정
        ▼
   ④ **소요 인력 산정**
        │  · **직무별 필요 인원**(운영자·DBA·NW·보안·헬프데스크)
        │  · **역량 수준(등급/직무)** 별 구분
        ▼
   ⑤ **투입공수(M/M) 산출**
        │  **M/M = 인원 수 × 투입 개월 수**
        │  ※ 부분 투입 시 **투입률(%)** 반영
        ▼
   ⑥ **대가 산정**
        │  Σ(M/M × 직무별 노임단가) + 직접경비 + 이윤
        ▼
   ⑦ **검증** — 유사 사업 비교, 적정성 검토

4. 주요 운영 업무 항목​

업무 영역세부 활동공수 산정 요소
시스템 운영·모니터링상태 감시, 자원 점검, 성능 관리대상 시스템 수, 감시 시간대(24×365 여부)
장애 대응장애 접수·분석·복구·보고장애 발생 빈도, 대응 목표시간(SLA)
사용자 지원(헬프데스크)문의 응대, 사용 지원, 교육사용자 수, 월 문의 건수
데이터 관리데이터 정합성 점검, 백업·복구, 이관데이터량, 백업 주기
배치·작업 관리배치 실행·모니터링·오류 처리배치 작업 수·주기
보안 관리취약점 점검, 계정·권한 관리, 보안 패치보안 요구 수준, 점검 주기
형상·변경 관리형상 관리, 변경 이력 관리변경 건수
운영 지원 문서운영 매뉴얼 갱신, 보고서 작성보고 주기

5. 투입공수 방식의 장단점​

구분내용
장점· 실제 업무량과 서비스 수준을 반영 → 합리적 산정
· 상주·교대 등 인력 운영 형태 반영 가능
· 직무별 전문성 차등 인정
· 개발비 기준의 한계 극복(노후 시스템도 적정 산정)
단점· 업무량 분석에 시간·전문성 필요
· 과거 실적 데이터가 없으면 산정 근거 취약
· 투입 중심 → 생산성 향상 유인 부재("사람을 줄이면 대가도 줄어듦")
· 발주기관·수행사 간 적정 인력 수 협의 갈등

6. 두 방식의 비교​

비교 기준요율제(유지관리)투입공수 방식(운영)
산정 기준개발비 × 요율(%)투입 인력 × 노임단가
적용 대상주로 SW 유지관리비주로 SW 운영비
업무량 반영간접적(요율 보정으로만)직접적
산정 용이성매우 쉬움어려움(업무 분석 필요)
객관성낮음(요율 근거 취약)상대적으로 높음
노후 시스템 대응불리(개발비 고정)유리(업무량 증가 반영)
서비스 수준 반영제한적가능(SLA·상주·교대)
적합 상황소규모·단순 유지관리, 예산 개략 산정상주 운영·복합 서비스, 대규모 시스템

Ⅳ. 나. 고정비 / 변동비 산정방식​

1. 개념 및 도입 취지​

고정비/변동비 산정방식은 운영·유지관리 업무를 성격에 따라 두 가지로 분리하여, 상시 발생하는 업무는 고정비로, 발생량이 변동하는 업무는 변동비로 산정하는 방식이다.

   [**도입 배경 — 단일 방식의 한계**]

   **[요율제·정액 계약만 사용]**
        │  · 상시 업무와 수시 요청을 **뭉뚱그려 산정**
        │  · 요청이 많아도 **추가 대가 없음** → 수행사 손실·품질 저하
        │  · 요청이 적어도 **동일 지급** → 발주기관 예산 낭비
        │  · **"공짜 개발" 관행** — 유지관리 명목의 신규 기능 개발
        ▼
   [**고정비/변동비 분리**]
   · **고정비** : 상시 필요한 **기본 서비스** → 안정적 보장
   · **변동비** : **실제 발생한 요청량**만큼 정산
        ▼
   ⇒ **발주기관** : 불필요 예산 절감, **수행사** : 추가 업무 대가 확보
   ⇒ **"일한 만큼 받는" 합리적 구조**

2. 고정비와 변동비의 구분​

 ┌──────────── **운영·유지관리 업무의 분류** ────────────┐
 │                                                       │
 │  **[고정비]** — 발생량과 무관하게 **상시 필요한 업무**  │
 │   · **시스템 모니터링·상태 점검**                      │
 │   · **장애 대응 대기**(상주 인력 유지)                 │
 │   · **헬프데스크 상시 운영**                           │
 │   · **정기 점검·백업·배치 운영**                       │
 │   · 보안 관리, 형상 관리, 정기 보고                    │
 │   · **기본 인력·설비 유지 비용**                       │
 │        ⇒ **"있어야만 하는" 서비스** → **정액 산정**     │
 │                                                       │
 │  **[변동비]** — **요청·발생량에 따라 달라지는 업무**    │
 │   · **기능 개선·변경 요청**(SR: Service Request)       │
 │   · **추가 개발·고도화**                               │
 │   · 대량 데이터 처리·이관                              │
 │   · **비정형·수시 요청 업무**                          │
 │        ⇒ **"발생한 만큼" 정산** → **실적 기반 산정**    │
 └───────────────────────────────────────────────────────┘
구분고정비(Fixed Cost)변동비(Variable Cost)
성격상시·정기적 업무수시·비정기적 업무
발생 여부요청과 무관하게 항상 발생요청이 있을 때만 발생
대표 업무모니터링·장애대응 대기·헬프데스크·정기점검·백업기능 개선·변경 요청(SR)·추가 개발·대량 처리
산정 방식투입공수 기반 정액(또는 요율제)실적 기반(FP 또는 처리 공수)
지급 방식월 정액 지급정산 지급(사후 또는 한도 내)
예산 성격확정 예산한도(Cap) 설정 후 정산
목적서비스 안정성 보장업무량 변동에 대한 공정한 대가

3. 산정 방식​

   [**전체 산정 구조**]

   **총 운영·유지관리 대가 = 고정비 + 변동비**

   ┌─── **[고정비 산정]** ────────────────────────────────────┐
   │  **투입공수 방식** 적용                                   │
   │  = Σ(상시 운영 직무별 투입 M/M × 노임단가)                │
   │    + 직접경비 + 이윤                                      │
   │                                                          │
   │  · 상시 필요 인력 산정(모니터링·헬프데스크·장애대응 대기) │
   │  · **서비스 수준(SLA)** 반영 — 24×365 시 교대 인력 반영    │
   │  · **월 정액**으로 지급                                   │
   └──────────────────────────────────────────────────────────┘

   ┌─── **[변동비 산정]** ────────────────────────────────────┐
   │  **① 기능점수(FP) 기반** ← 권장                           │
   │     = **처리한 SR의 기능점수 × FP 단가**                  │
   │     · 기능 변경·추가의 규모를 **객관적으로 측정**          │
   │                                                          │
   │  **② 투입공수 기반**                                      │
   │     = **실제 투입 공수(M/D, M/M) × 노임단가**              │
   │     · FP 측정이 어려운 비정형 업무에 적용                 │
   │                                                          │
   │  · **연간 한도(Cap)** 설정 후 **실적 정산**                │
   │  · 미사용분 처리 방식(이월·반환) 계약에 명시               │
   └──────────────────────────────────────────────────────────┘

4. 운영 절차​

   ① **업무 분류** — 운영 업무를 **고정 / 변동**으로 구분·합의
        ▼
   ② **고정비 산정** — 상시 인력 투입공수 산정 → **월 정액 확정**
        ▼
   ③ **변동비 한도 산정** — 과거 SR 실적 기반 **연간 예상 물량 × 단가**
        │                     → **한도(Cap) 설정**
        ▼
   ④ **계약 체결** — 고정비·변동비 산정 기준, 정산 방법 명시
        ▼
   ⑤ **운영 수행**
        │  · 고정비 업무 : 상시 수행
        │  · 변동비 업무 : **요청 접수 → 규모 산정 → 승인 → 수행**
        ▼
   ⑥ **실적 관리** — SR 처리 내역·FP·공수 **객관적 기록**
        ▼
   ⑦ **정산** — 월·분기·연 단위로 변동비 실적 정산
        ▼
   ⑧ **평가·환류** — 실적 데이터를 **차년도 산정 근거**로 활용

5. 장단점 및 성공 요건​

구분내용
장점· 업무량 변동에 대한 공정한 대가 지급
· "공짜 개발" 관행 차단 — 추가 요청에 대가 부여
· 발주기관의 불필요한 예산 절감(요청이 적으면 지출도 감소)
· 수행사의 손실 위험 완화 → 안정적 서비스 제공
· 실적 데이터 축적 → 산정 정확도 지속 향상
· 발주기관의 요청 남발 억제(비용 인식)
단점· 업무 분류 기준 협의 부담 — 고정/변동 경계가 모호한 업무 존재
· 실적 측정·기록 관리 부담(FP 산정 등)
· 변동비 정산을 둘러싼 분쟁 소지
· 발주기관의 예산 편성 불확실성(변동분)
· 초기 도입 시 과거 실적 데이터 부재
성공 요건내용
① 업무 분류 기준의 명확화계약서·과업내용서에 고정/변동 업무 목록을 구체적으로 명시 — 사후 분쟁의 최대 원인
② 변동비 산정 단가 사전 합의FP 단가 또는 공수 단가를 계약 시 확정
③ SR 관리 체계요청 접수·규모 산정·승인·완료 확인의 표준 프로세스와 도구(ITSM)
④ 실적 데이터 축적처리 건수·FP·공수를 객관적으로 기록 → 차년도 산정 근거
⑤ 한도(Cap) 설정예산 통제를 위해 변동비 상한 설정, 초과 시 처리 방안 명시
⑥ 발주기관 역량FP 산정·검증 능력 확보, 필요 시 제3자 검증

Ⅴ. 종합 비교 및 적용 방안​

1. 세 가지 산정 방식 종합 비교​

비교 기준요율제투입공수 방식고정비/변동비 방식
산정 기준개발비 × 요율투입 인력 × 단가정액(고정) + 실적(변동)
업무량 반영미반영사전 추정 반영사후 실적 반영
산정 난이도낮음중간높음
객관성낮음중간높음
분쟁 소지낮음중간높음(분류 기준)
예산 예측성높음높음중간(변동분)
공정성낮음중간높음
적합 상황소규모·단순 유지관리상주 운영 중심변경 요청이 많은 시스템

2. 적용 방안​

   [**시스템 특성별 권장 방식**]

   **안정적 운영 중심**(변경 요청 적음)
        → **투입공수 기반 정액** 또는 **요율제**

   **변경 요청 빈번**(업무 변화 잦은 시스템)
        → **고정비/변동비 방식** ★ 권장

   **소규모·단순 시스템**
        → **요율제**(산정 비용 대비 효율)

   **대규모·복합 서비스**(24×365, 다수 시스템)
        → **투입공수(고정비) + FP 기반 변동비**의 **혼합 적용**
고려사항내용
① 요율제의 단계적 탈피관행적 요율제는 저가 산정 고착의 원인 → 투입공수·FP 기반으로 전환
② 과업 범위의 명확화운영 vs 유지관리 vs 신규 개발의 경계를 계약에 명시 → "공짜 개발" 방지
③ 실적 데이터 관리ITSM 도구를 통한 장애·요청·처리 이력의 체계적 축적이 모든 산정의 기초
④ SLA와의 연계서비스 수준을 대가에 반영하고, SLA 미달 시 감액 체계 병행
⑤ 과업심의위원회 활용과업 변경 시 심의를 통한 대가 조정
⑥ 발주기관 역량 확보산정·검증 역량 부족 시 전문기관 자문·제3자 검증
⑦ 장기적 방향투입(M/M) 중심 → 성과·서비스 수준 기반 계약으로 전환

Ⅵ. 결론​

SW 운영단계 대가산정의 핵심 과제는 "관행적 요율제에서 실제 업무량에 근거한 합리적 산정으로 전환" 하는 것이다.

응용SW 요율제는 "개발비 × 요율"이라는 단순함 덕분에 널리 쓰이지만, 실제 업무량을 반영하지 못하고 노후 시스템일수록 저평가되는 구조적 한계를 갖는다. 시간이 지날수록 개발비라는 기준값의 타당성이 약해지는 반면 운영 업무량은 증가하기 때문이다.

SW 운영 투입공수 방식은 운영 업무를 항목별로 분석하여 실제 필요한 인력과 서비스 수준(24×365·상주·교대)을 반영하므로 훨씬 합리적이다. 다만 업무량 분석에 전문성이 필요하고, 투입 중심 산정이므로 생산성 향상 유인이 없다는 한계가 있다.

고정비/변동비 방식은 이러한 한계를 보완하는 발전된 형태이다. 상시 필요한 서비스는 고정비로 안정적으로 보장하고, 변경 요청처럼 발생량이 달라지는 업무는 실적에 따라 정산함으로써, 발주기관은 불필요한 예산 낭비를 줄이고 수행사는 추가 업무에 대한 정당한 대가를 확보할 수 있다. 특히 유지관리 명목으로 신규 기능 개발을 요구하는 "공짜 개발" 관행을 차단한다는 점에서 실무적 의의가 크다.

다만 이 방식의 성공은 고정 업무와 변동 업무의 분류 기준을 계약 단계에서 얼마나 명확히 합의하는가에 달려 있다. 경계가 모호하면 오히려 분쟁이 증가하기 때문이다. 따라서 ① 계약서에 고정/변동 업무 목록을 구체적으로 명시하고, ② 변동비 단가(FP 단가·공수 단가)를 사전 확정하며, ③ ITSM 도구를 통해 요청·처리 실적을 객관적으로 기록하는 세 가지가 전제 조건이 된다.

궁극적으로는 투입 인월 중심의 산정 구조 자체를 넘어서, SLA 기반의 서비스 수준과 성과에 연동한 계약 방식으로 발전시키는 것이 바람직하다. 이것이 「소프트웨어 진흥법」이 지향하는 적정 대가 지급을 통한 SW 산업 선순환의 실질적 구현 방향이라 할 수 있다.

릴레이션 무결성 제약(Integrity Constraint)

Ⅰ. 개요​

1. 개념​

무결성 제약은 데이터베이스에 저장된 데이터가 정확성·일관성·유효성을 유지하도록 강제하는 규칙이다. 관계형 모델의 핵심 요소로, DBMS가 자동으로 검증하여 부적절한 데이터의 입력·변경을 원천 차단한다.

2. 필요성​

   [무결성 제약이 없는 경우]
   · 존재하지 않는 부서 코드를 가진 사원 등록 → **고아 레코드**
   · 동일 학번의 학생이 중복 등록 → **식별 불가**
   · 나이에 −5, 성별에 'X' 입력 → **비정상 값**
        ▼
   [무결성 제약 적용]
   **DBMS가 선언적으로 검증** → 애플리케이션 오류와 무관하게 **데이터 신뢰성 보장**

Ⅱ. 무결성 제약의 유형과 사례​

1. 유형 체계​

   ┌──────────────── 무결성 제약 유형 ────────────────┐
   │ **① 개체 무결성**(Entity Integrity)               │
   │     PK는 NULL 불가 + 유일해야 함                  │
   │ **② 참조 무결성**(Referential Integrity)          │
   │     FK 값은 참조 릴레이션의 PK에 존재해야 함       │
   │ **③ 도메인 무결성**(Domain Integrity)             │
   │     속성 값은 정의된 도메인(타입·범위) 내에 존재   │
   │ **④ 고유 무결성**(Unique Integrity)               │
   │     특정 속성 값이 유일해야 함                     │
   │ **⑤ NULL 무결성**(NULL Integrity)                 │
   │     특정 속성은 NULL을 허용하지 않음               │
   │ **⑥ 키 무결성**(Key Integrity)                    │
   │     릴레이션에 최소 하나의 키가 존재               │
   │ **⑦ 사용자 정의 무결성**(User-defined)            │
   │     업무 규칙(Business Rule) 기반 제약             │
   └──────────────────────────────────────────────────┘

2. 유형별 상세 및 사례​

유형규칙사례위반 예시
① 개체 무결성기본키(PK)는 NULL이 될 수 없고, 중복될 수 없다사원 테이블의 사번은 반드시 값이 있고 유일사번 = NULL 입력, 기존 사번 1001 중복 입력
② 참조 무결성외래키(FK) 값은 참조 릴레이션의 PK에 존재하거나 NULL사원의 부서코드는 부서 테이블에 존재해야 함존재하지 않는 부서코드 99 입력, 사원이 있는 부서를 삭제
③ 도메인 무결성속성 값은 정의된 데이터 타입·형식·범위 내에 있어야 함나이는 0~150 정수, 성별은 'M'/'F', 이메일은 형식 준수나이 = −5, 성별 = 'X', 문자열에 날짜 입력
④ 고유 무결성지정된 속성 값은 릴레이션 내에서 유일사업자번호, 이메일은 중복 불가동일 이메일로 2개 계정 생성
⑤ NULL 무결성특정 속성은 NULL을 허용하지 않음사원명, 입사일자는 필수 입력사원명 = NULL
⑥ 키 무결성릴레이션에는 최소 하나의 키가 존재해야 함모든 테이블에 PK 정의PK 없는 테이블(중복 행 식별 불가)
⑦ 사용자 정의 무결성업무 규칙을 반영한 제약퇴사일 ≥ 입사일, 할인율 ≤ 정가, 재고수량 ≥ 0, 주문 총액 = 상세 합계퇴사일이 입사일보다 빠름, 재고 음수

3. 참조 무결성의 참조 동작(Referential Action)​

   [부모 삭제·변경 시 자식 처리 옵션]
   ┌──────────────┬─────────────────────────────┬──────────────────┐
   │ **RESTRICT / NO ACTION** │ 자식이 있으면 **연산 거부**(기본값) │ 마스터 데이터 보호 │
   │ **CASCADE**   │ 자식도 **함께 삭제·변경**        │ 주문–주문상세     │
   │ **SET NULL**  │ 자식 FK를 **NULL로 설정**        │ 선택적(비식별) 관계│
   │ **SET DEFAULT**│ 자식 FK를 **기본값으로 설정**    │ 기본 분류코드 존재 시│
   └──────────────┴─────────────────────────────┴──────────────────┘

Ⅲ. 무결성 제약의 구현 방법​

1. 구현 계층​

   ┌──────────── **① DBMS 선언적 제약**(권장) ────────────┐
   │  PRIMARY KEY · FOREIGN KEY · UNIQUE · NOT NULL ·     │
   │  CHECK · DEFAULT · 데이터 타입                        │
   │  ▲ **DBMS가 자동 검증** → 우회 불가, 성능 최적화됨     │
   ├──────────── **② 절차적 구현**(보완) ─────────────────┤
   │  **트리거(Trigger)** · 저장 프로시저 · 어서션          │
   │  ▲ 복잡한 업무 규칙 대응, 단 관리·성능 부담           │
   ├──────────── **③ 애플리케이션 검증**(UX 보조) ────────┤
   │  입력 유효성 검사 · ORM 제약(JPA @NotNull 등)         │
   │  ▲ 즉각 피드백 제공, 단 **우회 가능 → 단독 의존 금지** │
   └──────────────────────────────────────────────────────┘
   ※ 원칙 : **DBMS 선언적 제약이 최종 방어선**,
            애플리케이션 검증은 **사용자 편의를 위한 1차 필터**

2. SQL 구현 예시​

-- 부모 테이블
CREATE TABLE 부서 (
    부서코드  CHAR(2)      PRIMARY KEY,              -- ① 개체 무결성
    부서명    VARCHAR(50)  NOT NULL                  -- ⑤ NULL 무결성
);

-- 자식 테이블
CREATE TABLE 사원 (
    사번      NUMBER(6)    PRIMARY KEY,              -- ① 개체 무결성
    사원명    VARCHAR(30)  NOT NULL,                 -- ⑤ NULL 무결성
    이메일    VARCHAR(100) UNIQUE,                   -- ④ 고유 무결성
    나이      NUMBER(3)    CHECK (나이 BETWEEN 0 AND 150),   -- ③ 도메인 무결성
    성별      CHAR(1)      CHECK (성별 IN ('M','F')),        -- ③ 도메인 무결성
    입사일자  DATE         DEFAULT SYSDATE NOT NULL,
    퇴사일자  DATE,
    부서코드  CHAR(2),
    -- ② 참조 무결성 + 참조 동작
    CONSTRAINT fk_사원_부서 FOREIGN KEY (부서코드)
        REFERENCES 부서(부서코드)
        ON DELETE SET NULL,
    -- ⑦ 사용자 정의 무결성 (업무 규칙)
    CONSTRAINT ck_재직기간 CHECK (퇴사일자 IS NULL OR 퇴사일자 >= 입사일자)
);
-- 여러 테이블에 걸친 복합 규칙 → 트리거로 구현
CREATE OR REPLACE TRIGGER trg_주문총액_검증
AFTER INSERT OR UPDATE ON 주문상세
FOR EACH ROW
BEGIN
    UPDATE 주문
       SET 총액 = (SELECT SUM(수량 * 단가) FROM 주문상세
                    WHERE 주문번호 = :NEW.주문번호)
     WHERE 주문번호 = :NEW.주문번호;
END;

3. 구현 방법 비교​

비교 기준선언적 제약(DDL)트리거·프로시저애플리케이션 검증
검증 주체DBMS 엔진DBMS(사용자 정의 로직)애플리케이션
신뢰성최고(우회 불가)높음낮음(직접 SQL로 우회 가능)
성능최적화됨오버헤드 발생DB 부하 감소
표현력단순 규칙복잡한 다중 테이블 규칙 가능매우 유연
유지보수용이(스키마에 명시)로직 분산 → 추적 곤란코드 관리 용이
사용자 경험오류 메시지 불친절보통즉각적·친절한 피드백
권장 용도모든 기본 무결성선언적으로 불가한 업무 규칙UX 개선용 1차 검증

Ⅳ. 구현 시 고려사항​

고려사항내용
성능FK 검증 비용 → FK 컬럼에 인덱스 필수(미생성 시 부모 삭제 시 전체 스캔)
대량 배치 시 제약 일시 비활성화 후 재검증(NOVALIDATE → VALIDATE)
참조 동작 선택CASCADE 남용 주의 — 연쇄 삭제로 대량 데이터 소실 위험, 원칙적으로 RESTRICT 권장
NULL 처리FK에 NULL 허용 여부(선택적 관계), CHECK 제약은 NULL에 대해 참으로 평가됨에 유의
명명 규칙제약조건에 의미 있는 이름 부여(fk_사원_부서) → 오류 메시지 해석·유지보수 용이
분산·MSA 환경서비스별 DB 분리로 FK 사용 불가 → 최종적 일관성, Saga·보상 트랜잭션, 정합성 검증 배치 필요
NoSQL 환경대부분 무결성 제약 미지원 → 애플리케이션 계층에서 보장해야 함
데이터 이행마이그레이션 시 기존 데이터가 제약을 위반할 수 있음 → 사전 정합성 진단 후 정제
순환 참조상호 참조 시 삽입 순서 문제 → 지연 제약(Deferrable Constraint) 활용

Ⅴ. 결론​

무결성 제약은 데이터 신뢰성의 최종 방어선이며, 애플리케이션 로직에만 의존할 경우 배치 프로그램·직접 SQL·다중 애플리케이션 접근 등 우회 경로에서 반드시 정합성이 깨진다.

따라서 실무 원칙은 ① 개체·참조·도메인 무결성은 예외 없이 DBMS 선언적 제약으로 강제하고, ② 선언적으로 표현할 수 없는 복합 업무 규칙에 한해 트리거를 제한적으로 사용하며, ③ 애플리케이션 검증은 사용자 경험을 위한 1차 필터로만 활용하는 것이다.

다만 MSA·분산 데이터베이스 환경에서는 서비스 간 FK를 선언할 수 없다는 구조적 제약이 있으므로, 이 경우에는 최종적 일관성을 전제로 한 보상 트랜잭션과 정기적 정합성 대사(Reconciliation) 배치를 반드시 설계에 포함해야 한다. 즉 무결성 보장의 책임 주체가 DBMS에서 아키텍처로 이동한다는 점을 인식하는 것이 현대적 데이터 설계의 핵심이다.

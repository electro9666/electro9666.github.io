공공기관의 거대 언어 모델(LLM) 적용

Ⅰ. 개요​

1. 배경​

생성형 AI의 확산으로 공공기관도 민원 응대·문서 작성·정책 분석 등에 LLM 도입을 준비하고 있다. 다만 공공 업무는 정확성·설명책임·개인정보 보호가 민간보다 엄격하게 요구되므로, 기술 도입 이전에 적용 방식과 아키텍처에 대한 신중한 판단이 선행되어야 한다.

2. 공공 부문의 특수성​

   [민간]  빠른 도입 → 시행착오 허용 → 개선
   [**공공**] 오답 1건이 **행정 신뢰 훼손·법적 책임**으로 직결
        + 개인정보·비공개 문서 다수 보유
        + **망 분리(N2SF)·CSAP** 등 제도적 제약
        ⇒ **"성능"보다 "통제 가능성과 근거 제시"가 우선**

Ⅱ. 가. 거대 언어 모델 적용을 위한 5가지 고려사항​

1. ① 데이터 보안 및 개인정보 보호​

구분내용
위험업무 자료·개인정보를 외부 LLM API에 입력 시 학습 활용·로그 축적·국외 이전 문제 발생. 프롬프트 인젝션에 의한 정보 유출
고려사항· 민감도에 따른 데이터 등급 분류(N2SF의 C/S/O) 와 처리 경로 결정
· 개인정보 입력 금지 원칙 및 DLP·마스킹 자동 적용
· CSAP 인증 클라우드 또는 온프레미스 사설 모델 선택
· 개인정보 영향평가(PIA), 국외 이전 검토
· 프롬프트·응답 로깅 및 접근통제

2. ② 정확성·환각(Hallucination) 대응과 신뢰성​

구분내용
위험LLM은 사실이 아닌 내용을 확신 있게 생성 → 잘못된 민원 안내·정책 판단 시 행정 처분의 정당성 훼손
고려사항· RAG 기반 구조로 근거 문서와 출처를 반드시 함께 제시(공공에서 가장 중요)
· 최신 법령·지침 반영을 위한 데이터 갱신 체계
· 답변 신뢰도 표시, "AI 생성 정보이므로 확인 필요" 고지
· 정확도 목표치 설정 및 정기 품질 평가(오답 사례 관리)

3. ③ 데이터 품질 및 지식 자산화​

구분내용
위험기관 문서가 비정형·중복·구버전 혼재 상태이면 RAG 검색 품질이 저하되어 LLM 성능과 무관하게 실패
고려사항· 법령·지침·민원 사례의 정제·구조화·중복 제거
· 문서 최신성 관리 및 폐지 문서 배제
· 적절한 청킹(Chunking) 전략과 메타데이터(부서·시행일·근거법령) 부여
· 벡터DB 접근통제 — 권한 없는 문서가 검색되지 않도록 행 수준 보안(RLS)

4. ④ 인간의 감독과 책임 소재(거버넌스)​

구분내용
위험AI 판단을 그대로 적용할 경우 행정 행위의 책임 주체가 불분명, 국민의 권익 침해 시 구제 곤란
고려사항· 최종 판단 권한은 담당 공무원이 보유(Human-in-the-Loop) — AI는 보조 수단
· 처분·심사 등 권익에 영향을 주는 업무는 자동 결정 금지
· AI 사용 사실 고지 및 생성물 표시
· AI 기본법(고영향 AI 의무)·AI 윤리기준 준수, 이의제기 절차
· 감사추적(Audit Trail) 확보

5. ⑤ 비용·인프라 및 지속가능성​

구분내용
위험GPU·API 비용이 사용량에 비례해 지속 증가, 초기 구축 후 재학습·운영 예산 미확보 시 방치
고려사항· 총소유비용(TCO) 관점 산정 — 구축비 + 추론비 + 재학습·운영비
· 경량 모델(sLLM)·양자화로 단가 최적화, 캐싱 활용
· 자체 구축 vs 클라우드 vs SaaS의 비용·통제 균형 판단
· 특정 모델·벤더 종속(Lock-in) 회피 — 표준 인터페이스 유지
· 전문 인력 확보 및 직원 AI 리터러시 교육

그 밖의 고려사항: 업무 적합성(적용 과제 선별), 접근성(취약계층 배려), 변화관리(직원 수용성), 저작권 이슈

Ⅲ. 나. 현재 구현 가능한 5가지 거대 언어 모델 아키텍처​

   [통제 수준 ↔ 비용·난이도 스펙트럼]
   ① 프롬프트  ② RAG      ③ 파인튜닝   ④ 온프레미스    ⑤ 에이전트
     엔지니어링   (검색증강)   (특화 학습)   (자체 구축)      (도구 연동)
   ◄── 저비용·즉시 적용                         고비용·고통제 ──►
   ◄── 통제 수준 낮음                           통제 수준 높음 ──►

1. ① 프롬프트 엔지니어링 기반 아키텍처 (API 활용형)​

   사용자 ─► 업무 시스템 ─► **프롬프트 템플릿 + 지시문** ─► 상용 LLM API ─► 응답
                              (Few-shot, CoT, 역할 부여)
항목내용
개념모델을 변경하지 않고 프롬프트 설계만으로 성능 확보
장점구축 기간 최단·비용 최소, 즉시 적용 가능, 유지보수 용이
단점기관 고유 지식 반영 불가, 환각 통제 어려움, 외부 전송에 따른 보안 위험
적합 업무문서 요약·번역·보도자료 초안 등 비민감·범용 업무

2. ② RAG(검색증강생성) 기반 아키텍처 — 공공에 가장 권장​

   질의 ─► **임베딩** ─► **벡터DB 검색**(기관 법령·지침·사례)
                             │  (권한 필터링 적용)
                             ▼
              **검색된 근거 문서 + 질의** ─► LLM ─► **답변 + 출처 표시**
항목내용
개념기관 문서를 벡터화하여 검색한 뒤, 근거와 함께 답변을 생성
장점환각 대폭 감소, 출처 제시로 검증 가능 → 설명책임 확보, 문서만 갱신하면 최신성 유지(재학습 불필요), 권한별 접근통제 적용 가능
단점검색 품질에 성능이 좌우됨, 문서 정제·청킹 등 데이터 준비 부담, 벡터DB 운영 필요
적합 업무민원 응대, 법령·지침 질의응답, 내부 규정 안내 등 공공 핵심 업무

3. ③ 파인튜닝(Fine-tuning) 기반 아키텍처​

   사전학습 모델 ─► **기관 데이터로 추가 학습**(Full / **PEFT·LoRA**) ─► 특화 모델
항목내용
개념기관 고유 데이터·문체·업무 양식을 모델 가중치에 반영
장점특정 도메인 성능·문체 일관성 우수, 짧은 프롬프트로 동작(추론 비용 절감)
단점학습 데이터 구축 비용 큼, 지식 갱신 시 재학습 필요, 출처 제시 불가 → 설명책임 취약, 학습데이터 유출(암기) 위험
적합 업무정형 문서 자동 생성, 특수 분류·판정 업무
비고공공에서는 RAG를 우선 적용하고, 문체·형식 통일이 필요한 경우에 한해 병행하는 것이 일반적

4. ④ 온프레미스 sLLM(자체 구축형) 아키텍처​

   ┌─── 기관 내부망(폐쇄망) ───┐
   │ 오픈소스 모델(경량 sLLM)  │  + RAG 결합
   │ + 자체 GPU 인프라          │  → **데이터가 외부로 나가지 않음**
   └───────────────────────────┘
항목내용
개념오픈소스 모델을 기관 내부 인프라에 직접 구축·운영
장점데이터 외부 유출 원천 차단, 망분리 환경 대응, 완전한 통제권, 장기 비용 예측 가능
단점초기 GPU 투자·전문 인력 필요, 상용 모델 대비 성능 열위, 모델 갱신 부담
적합 업무기밀·민감 정보 처리, 폐쇄망 환경, 대량·상시 사용 업무

5. ⑤ AI 에이전트(도구 연동형) 아키텍처​

   질의 ─► LLM(계획·추론) ─┬─► **RAG 검색**
                           ├─► **업무 시스템 API 호출**(조회·등록)
                           ├─► 계산·문서 생성 도구
                           └─► 결과 관찰 → 재계획 → **고위험 작업은 담당자 승인**
항목내용
개념LLM이 외부 도구·업무 시스템을 호출하여 다단계 업무를 자율 수행(MCP·Function Calling)
장점조회·입력·처리를 아우르는 업무 자동화, 여러 시스템 통합 응대
단점프롬프트 인젝션에 의한 도구 오용 위험, 오류의 연쇄 증폭, 감사추적 복잡, 책임 소재 불명확
적합 업무반복 행정 처리, 통합 민원 조회
필수 통제최소 권한·도구 화이트리스트·되돌릴 수 없는 작업의 사람 승인·전 호출 로깅

6. 아키텍처 비교​

비교 기준① 프롬프트② RAG③ 파인튜닝④ 온프레미스⑤ 에이전트
구축 비용·기간최소중간큼최대큼
기관 지식 반영불가우수우수우수(RAG 결합)우수
환각 통제낮음높음(출처 제시)중간중간중간
보안·통제낮음중간중간최고낮음(권한 위험)
최신성 유지—문서 갱신만재학습 필요문서 갱신문서 갱신
설명책임취약강함취약중간중간
공공 적합도보조 활용최우선 권장선별 적용민감업무 필수신중 적용

Ⅳ. 단계적 도입 전략​

   [1단계] 비민감 업무에 **프롬프트 기반** 시범 적용 → 효과·수용성 검증
        ▼
   [2단계] 법령·지침 문서 정제 후 **RAG 구축** → 민원 응대·내부 질의응답 확대
        ▼
   [3단계] 민감 업무는 **온프레미스 sLLM + RAG**로 이관(망분리 대응)
        ▼
   [4단계] 정형 반복 업무에 한해 **에이전트** 적용(승인 워크플로 필수)
   ※ 전 단계에 걸쳐 **AI 거버넌스·로깅·품질평가 체계**를 병행 운영

Ⅴ. 결론​

공공기관의 LLM 적용에서 성패를 가르는 것은 모델 성능이 아니라 ① 기관 문서의 품질과 구조화 수준, ② 환각에 대한 통제(근거 제시), ③ 데이터 보안 확보 이다.

따라서 아키텍처 선택의 실무 원칙은 파인튜닝보다 RAG를 우선 채택하는 것이다. RAG는 출처를 함께 제시하여 담당 공무원이 검증할 수 있게 하고, 문서만 갱신하면 최신성이 유지되므로 공공 업무가 요구하는 정확성과 설명책임을 동시에 충족하기 때문이다.

아울러 ① 데이터 민감도에 따라 SaaS–CSAP 클라우드–온프레미스를 차등 적용하고, ② 최종 판단 권한은 반드시 담당자가 유지하며, ③ AI 기본법·개인정보보호법·N2SF와의 정합성을 사전 확보해야 한다. 무엇보다 도입을 기술 사업이 아닌 업무 혁신 과제로 접근하여, 문서 정비와 업무 프로세스 재설계를 병행할 때 실질적 성과를 얻을 수 있다.

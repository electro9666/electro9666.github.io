물리 데이터 모델링 중 반정규화(Denormalization)

Ⅰ. 개요​

1. 개념​

반정규화(De-normalization) 는 정규화로 분해된 릴레이션에 대하여, 조회 성능 향상과 운영 편의를 목적으로 의도적으로 중복을 허용하거나 통합·분할·추가하는 물리 데이터 모델링 기법이다.

2. 필요성 — 정규화의 한계​

   [정규화]  중복 제거 → **데이터 무결성 확보**
        │              (삽입·갱신·삭제 이상 방지)
        ▼
   테이블 분해 증가 → **조인(JOIN) 횟수 증가**
        │
        ▼
   대용량·고빈도 조회 시 **응답 지연** → 성능 요구 미충족
        │
        ▼
   [**반정규화**] 중복을 감수하고 **조인 제거·조회 성능 확보**
구분정규화반정규화
목적무결성·일관성성능(조회 속도)
중복제거허용
조인증가감소
조회 성능낮음높음
갱신 성능·정합성우수저하 위험(중복 데이터 동기화 필요)
저장 공간절약증가
적용 단계논리 모델링물리 모델링

원칙: 반정규화는 정규화를 충분히 수행한 후, 성능 문제가 실제로 확인된 경우에 한하여 선별적으로 적용한다. 처음부터 반정규화된 모델을 설계해서는 안 된다.

Ⅱ. 가. 반정규화 절차​

 ① **대상 조사·분석** ─► ② **다른 방법 검토** ─► ③ **반정규화 적용**
   (범위처리 빈도·                (뷰·인덱스·클러스터링·      (유형 선택 및 수행)
    조인 빈도·통계성)              파티셔닝·애플리케이션)              │
                                        │ 해결 가능 → 반정규화 미적용   │
                                        └────────────────────────────┘
                                                                       ▼
                                    ④ **정합성 확보 방안 수립 및 검증**
단계주요 활동판단 기준
① 대상 조사·분석· 범위 처리 빈도수 조사 — 대량 범위를 자주 조회하는가
· 조인 발생 빈도 조사 — 특정 테이블 조합이 반복 조인되는가
· 통계성 조회 여부 — 집계·합계를 매번 계산하는가
· 데이터 증가 추이·접근 패턴 분석		조회 빈도·성능 목표 미달 여부
② 다른 방법 유도 검토
(가장 중요한 단계)		반정규화 이전에 대안 우선 검토
· 뷰(View) — 조인 복잡도만 감추면 되는 경우
· 인덱스 조정·클러스터드 인덱스 — 접근 경로 최적화로 해결 가능한 경우
· 파티셔닝 — 대용량 범위 조회
· 애플리케이션 로직·캐시로 분산 처리
· 옵티마이저 힌트·SQL 재작성		대안으로 해결되면 반정규화 미적용
③ 반정규화 적용대안으로 해결 불가 시 테이블·속성·관계 반정규화 중 적합한 유형 선택·수행성능 개선 효과 > 정합성 관리 비용
④ 정합성 확보·검증중복 데이터 동기화 방안 수립(트리거·프로시저·애플리케이션·배치), 성능 개선 효과 측정, 정합성 검증 절차 마련실측 성능 향상 확인

Ⅲ. 나. 반정규화 유형​

   ┌──────────── 반정규화 유형 ────────────┐
   │ **① 테이블 반정규화**                  │
   │   병합 / 분할 / 추가                   │
   │ **② 속성(컬럼) 반정규화**              │
   │   중복·파생·이력 컬럼 추가             │
   │ **③ 관계 반정규화**                    │
   │   중복 관계(FK) 추가                   │
   └────────────────────────────────────────┘

1. 테이블 반정규화​

세부 유형내용적용 상황
테이블 병합
(Merge)		1:1 병합: 항상 함께 조회되는 두 테이블 통합
1:M 병합: 자식 데이터가 소량이고 항상 함께 조회 시 통합
슈퍼/서브타입 병합: OneTable / Plus / Single 방식		조인이 항상 발생하고 분리 이점이 없을 때
테이블 분할
(Split)		수직 분할: 자주 쓰는 컬럼과 대용량·저빈도 컬럼(BLOB·비고) 분리
수평 분할(파티셔닝): 기간·지역 등 기준으로 행 분할		일부 컬럼만 집중 사용 / 대용량 범위 조회
테이블 추가중복 테이블: 원격·타 시스템 데이터 복제
통계 테이블: 집계 결과 사전 저장(Summary Table)
이력 테이블: 변경 이력 별도 관리
부분 테이블: 자주 쓰는 일부만 별도 보관		집계 부하가 크거나 원격 조인 비용이 클 때

2. 속성(컬럼) 반정규화​

세부 유형내용예시
중복 컬럼 추가조인을 피하기 위해 타 테이블 컬럼을 복사주문 테이블에 고객명 추가(고객 테이블 조인 회피)
파생 컬럼 추가
(Derived)		계산 결과를 미리 저장주문 테이블에 총금액(수량×단가 합계) 저장
이력 테이블 컬럼 추가최신 여부·시작·종료일자 컬럼 추가로 최신 데이터 조회 최적화최신여부(Y/N), 시작일자, 종료일자
PK에 의한 컬럼 추가복합 PK 중 일부를 일반 컬럼으로 추가조회 조건 최적화
응용시스템 오작동 대비 컬럼이전 값 보관용 백업 컬럼복구·검증용

3. 관계 반정규화​

세부 유형내용
중복 관계 추가
(Redundant Relationship)		여러 단계를 거쳐야 도달하는 테이블에 직접 관계(FK)를 추가하여 조인 단계를 축소
예) 고객 → 주문 → 주문상세 구조에서 주문상세에 고객ID를 직접 추가 → 고객별 상세 조회 시 조인 1회 감소

특징: 관계 반정규화는 데이터 중복이 아닌 관계(경로)의 중복이므로, 속성 반정규화보다 정합성 위험이 상대적으로 낮다.

Ⅳ. 다. 반정규화 시 고려사항​

구분고려사항상세 내용
적용 판단최후의 수단뷰·인덱스·파티셔닝·SQL 튜닝 등 대안을 모두 검토한 후 적용
정량적 근거추측이 아닌 실측 데이터(조회 빈도, 응답시간, 실행계획)에 근거하여 결정
비용 대비 효과조회 성능 개선 이익 > 정합성 관리·저장공간 비용
정합성데이터 무결성 훼손 위험중복 데이터의 동기화 실패 시 불일치 발생 → 가장 큰 위험
동기화 방안 명확화트리거 / 프로시저 / 애플리케이션 로직 / 배치 중 방식 결정 및 책임 소재 명시
정합성 검증 체계정기 대사(Reconciliation) 배치, 불일치 탐지·보정 절차
성능갱신 성능 저하중복 컬럼 증가 시 INSERT·UPDATE 부하 증가 → 조회:갱신 비율 확인 필수
저장 공간중복 저장에 따른 용량 증가, 백업·복구 시간 증가
잠금 경합병합된 테이블의 잠금 범위 확대
설계·관리문서화반정규화 적용 사유·범위·동기화 방식을 반드시 문서화 — 미문서화 시 후임자가 오류로 오인
모델 관리논리 모델은 정규화 상태로 유지하고, 물리 모델에만 반정규화 반영
변경 영향반정규화 구조는 요구사항 변경 시 파급 범위가 큼
운영사후 검증적용 후 실제 성능 개선 여부 측정, 효과 없으면 원복
재검토 주기데이터량·접근 패턴 변화 시 주기적 재평가
대안 기술최신 환경 고려인메모리 DB·컬럼형 저장·구체화 뷰(Materialized View)·캐시(Redis)·CQRS 등으로 반정규화 없이 해결 가능한 경우 증가

Ⅴ. 결론​

반정규화는 무결성을 담보로 성능을 사는 거래이므로, "정규화가 원칙이고 반정규화는 예외" 라는 순서를 지켜야 한다. 특히 실무에서 가장 큰 실패 원인은 성능 문제를 정확히 진단하지 않은 채 관행적으로 반정규화를 선행 적용하는 것이며, 이는 정합성 오류와 유지보수 부담만 남긴다.

따라서 ① 범위 처리·조인 빈도·통계성 조회를 정량 분석하고, ② 뷰·인덱스·파티셔닝 등 대안을 우선 검토하며, ③ 불가피한 경우에만 적합한 유형을 선택하되, ④ 중복 데이터의 동기화 방안과 정합성 검증 체계를 반드시 함께 설계·문서화해야 한다.

최근에는 구체화 뷰·인메모리 DB·캐시·CQRS 패턴 등 반정규화 없이 조회 성능을 확보하는 대안이 성숙했으므로, 물리 모델을 훼손하기 전에 아키텍처 차원의 해법을 우선 검토하는 것이 바람직하다.

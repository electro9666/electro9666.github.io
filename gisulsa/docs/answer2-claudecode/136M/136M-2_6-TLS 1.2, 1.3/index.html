TLS 프로토콜 — TLS 1.2의 취약점과 TLS 1.3의 개선

Ⅰ. 개요​

1. TLS의 개념​

TLS(Transport Layer Security) 는 응용계층과 전송계층 사이에서 동작하며, 통신의 기밀성(암호화)·무결성(변조 탐지)·인증(신원 확인) 을 제공하는 보안 프로토콜이다. HTTPS·메일·VPN 등 인터넷 보안 통신의 기반이다.

2. 버전 변천​

   SSL 2.0/3.0(폐기) → TLS 1.0(1999) → TLS 1.1 → **TLS 1.2(2008)**
   → **TLS 1.3(2018, RFC 8446)**
   ※ TLS 1.0/1.1은 2021년 주요 브라우저에서 **지원 종료**
   ※ 현재 TLS 1.2는 **안전한 설정 하에서만** 사용 가능, **TLS 1.3 사용 권고**

Ⅱ. 가. TLS 프로토콜 구조와 핸드셰이크 과정​

1. 프로토콜 계층 구조​

   ┌──────────────── 응용 계층 (HTTP, SMTP …) ────────────────┐
   ├──────────────────── **TLS 계층** ────────────────────────┤
   │  ┌─────────── 상위 프로토콜(Handshake Layer) ──────────┐  │
   │  │ **Handshake**      : 협상·키 교환·인증              │  │
   │  │ **Change Cipher Spec** : 암호 적용 시점 통보(1.3 제거)│  │
   │  │ **Alert**          : 오류·종료 통보                  │  │
   │  │ **Application Data** : 실제 데이터 전달              │  │
   │  └──────────────────────────────────────────────────────┘  │
   │  ┌─────────── **Record Protocol**(하위) ────────────────┐  │
   │  │ 단편화 → 압축(1.3 제거) → MAC/AEAD → 암호화 → 전송   │  │
   │  └──────────────────────────────────────────────────────┘  │
   ├──────────────────── TCP / IP ────────────────────────────┤
구성 프로토콜역할
Handshake Protocol버전·암호 스위트 협상, 서버(클라이언트) 인증, 세션 키 생성
Record Protocol상위 데이터를 단편화·암호화·무결성 보호하여 전송
Alert Protocol경고·치명적 오류 및 연결 종료 통지
Change Cipher Spec협상된 암호 방식 적용 시작 통보(TLS 1.3에서 제거)

2. TLS 1.2 핸드셰이크 과정 (2-RTT)​

   Client                                                    Server
     │───────────────── **① ClientHello** ────────────────────►│
     │   지원 TLS 버전, **Cipher Suite 목록**, Client Random    │
     │                                                          │
     │◄──────────────── **② ServerHello** ─────────────────────│
     │   선택된 버전·Cipher Suite, Server Random                │
     │◄──────────────── **③ Certificate** ─────────────────────│
     │   서버 인증서(공개키 포함)                                │
     │◄────────────── ④ ServerKeyExchange ─────────────────────│  (DHE/ECDHE 시)
     │◄────────────── ⑤ ServerHelloDone ───────────────────────│
     │                                                    [1 RTT]│
     │──────────────── ⑥ ClientKeyExchange ───────────────────►│
     │   **Pre-Master Secret** 전달(RSA: 서버 공개키로 암호화 /  │
     │                              ECDHE: 클라이언트 공개값)    │
     │──────────────── ⑦ ChangeCipherSpec ────────────────────►│
     │──────────────── ⑧ Finished(암호화) ────────────────────►│
     │◄──────────────── ⑨ ChangeCipherSpec ────────────────────│
     │◄──────────────── ⑩ Finished(암호화) ────────────────────│
     │                                                    [2 RTT]│
     │◄════════════ **Application Data(암호화 통신)** ═════════►│

   [세션 키 생성] Client Random + Server Random + Pre-Master Secret
                  → **Master Secret** → 대칭키·MAC 키 파생

3. TLS 1.3 핸드셰이크 과정 (1-RTT)​

   Client                                                    Server
     │──────────── **① ClientHello** ─────────────────────────►│
     │   지원 버전, Cipher Suite,                               │
     │   **+ key_share(키 교환 공개값을 미리 전송)**            │
     │                                                          │
     │◄─────────── **② ServerHello** ──────────────────────────│
     │   선택 정보 + **key_share** → 이 시점에 **키 합의 완료**  │
     │◄─── {EncryptedExtensions, Certificate, CertVerify,       │
     │       Finished} ← **여기서부터 이미 암호화됨**            │
     │                                                    [1 RTT]│
     │──────────── ③ Finished ────────────────────────────────►│
     │◄════════ **Application Data** ═════════════════════════►│

   [핵심] 클라이언트가 **키 공유값을 예측하여 미리 전송** → 왕복 1회 절감
   [0-RTT] 재접속 시 **PSK(사전 공유 키)** 로 첫 패킷부터 데이터 전송 가능
           ※ 단, **재전송 공격(Replay) 위험** → 멱등 요청에만 제한적 사용

Ⅲ. 나. TLS 1.2의 보안 취약점과 TLS 1.3의 개선 사항​

1. TLS 1.2의 주요 보안 취약점​

구분취약점상세 내용
레거시 알고리즘 허용RSA 키 교환Pre-Master Secret을 서버 공개키로 암호화 전송 → 서버 개인키 유출 시 과거 통신 전체 복호화 가능(PFS 부재)
CBC 모드 + MAC-then-EncryptBEAST, Lucky13, POODLE 등 패딩 오라클 공격에 노출
RC4스트림 암호의 통계적 편향 → 평문 복원 가능(RFC 7465로 금지)
SHA-1, MD5충돌 공격 가능 → 서명 위조 위험
정적 DH, 취약한 파라미터Logjam(512비트 DH 강제 강등), FREAK(수출용 약한 RSA)
다운그레이드 공격버전·암호 강등협상 과정이 평문이어서 중간자가 낮은 버전·약한 암호로 강등 유도
핸드셰이크 노출평문 협상인증서·확장 정보가 평문 전송 → 접속 대상·정보 노출(프라이버시)
압축CRIME 공격TLS 압축 사용 시 압축률 차이로 세션 쿠키 추출
재협상재협상 취약점삽입 공격(Insecure Renegotiation)
복잡성과다한 옵션수십 개 Cipher Suite 조합 → 잘못된 설정으로 인한 취약이 가장 큰 현실적 위험
성능2-RTT 지연매 연결마다 왕복 2회 → 모바일·고지연 환경에서 체감 지연

2. TLS 1.3의 개선 사항​

구분개선 내용효과
① 취약 알고리즘 전면 제거RSA 키 교환, 정적 DH, RC4, 3DES, MD5/SHA-1, CBC 모드, 압축, 재협상, 사용자 정의 DH 그룹 전면 삭제알려진 공격 벡터의 원천 제거 — 설정 실수 가능성 자체를 없앰
② PFS 의무화(EC)DHE 키 교환만 허용순방향 비밀성(Perfect Forward Secrecy) 강제 — 개인키가 유출되어도 과거 통신은 안전
③ AEAD 암호만 허용AES-GCM, ChaCha20-Poly1305 등 인증 암호만 사용암호화와 무결성을 원자적으로 결합 → 패딩 오라클(Lucky13·POODLE) 무력화
④ 암호 스위트 단순화37개 → 5개로 축소(키 교환·인증 분리)잘못된 설정 위험 최소화, 상호운용성 향상
⑤ 핸드셰이크 암호화ServerHello 이후 인증서·확장 정보 모두 암호화접속 정보 노출 차단(프라이버시 강화), ESNI/ECH로 확장
⑥ 다운그레이드 방어ServerHello Random에 다운그레이드 표시(Sentinel) 삽입, 서명으로 협상 내용 보호강등 공격 탐지·차단
⑦ 1-RTT 핸드셰이크ClientHello에 key_share 선제 전송연결 지연 50% 단축 → 성능과 보안의 동시 개선
⑧ 0-RTT 재개PSK 기반 세션 재개 시 첫 패킷부터 데이터 전송재접속 지연 제거 (단, 재전송 공격 주의)
⑨ 키 스케줄 개선HKDF 기반 체계적 키 파생암호학적 안전성 증명 용이

3. TLS 1.2 vs TLS 1.3 종합 비교​

비교 기준TLS 1.2TLS 1.3
핸드셰이크 RTT2-RTT1-RTT (재개 시 0-RTT)
키 교환RSA, DH, DHE, ECDHE (선택)(EC)DHE 전용
순방향 비밀성선택적(설정 의존)필수(항상 보장)
암호화 모드CBC, GCM, RC4 등AEAD 전용
암호 스위트 수37개 이상5개
해시MD5, SHA-1 포함SHA-256 이상
압축지원(CRIME 위험)제거
재협상지원제거(Key Update로 대체)
핸드셰이크 노출인증서 등 평문암호화
다운그레이드 방어미흡내장 방어 기제
보안 수준설정에 크게 의존기본 설정이 안전(Secure by Default)

Ⅳ. 전환 시 고려사항​

고려사항내용
하위 호환TLS 1.3 미지원 클라이언트를 위해 TLS 1.2 병행 지원(안전한 스위트만 허용), TLS 1.0/1.1은 비활성화
보안 장비 영향핸드셰이크 암호화·PFS로 기존 복호화 방식(정적 RSA 키 기반) 무력화 → SSL 가시성 장비는 MITM 프록시 방식으로 재구성 필요
0-RTT 주의재전송 공격 위험 → 조회 등 멱등 요청에만 허용, 상태 변경 요청은 금지
인증서ECDSA 인증서로 성능 개선, OCSP Stapling 적용, 짧은 유효기간 자동 갱신(ACME)
설정 검증SSL Labs 등으로 A등급 설정 확인, 취약 스위트·프로토콜 비활성화 정기 점검
PQC 대비양자 위협에 대비한 하이브리드 키 교환(X25519 + ML-KEM) 도입 검토

Ⅴ. 결론​

TLS 1.3의 개선은 단순한 기능 추가가 아니라 "위험한 선택지를 제거하는(Remove, not Add)" 설계 철학의 전환이다. TLS 1.2의 가장 큰 문제는 특정 알고리즘의 결함이 아니라 취약한 옵션을 선택할 수 있다는 구조 자체였으며, TLS 1.3은 이를 원천 차단하여 기본 설정만으로 안전(Secure by Default) 하도록 만들었다.

더불어 1-RTT 핸드셰이크로 보안 강화와 성능 개선을 동시에 달성했다는 점에서, 통상적인 "보안-성능 Trade-off"를 깨뜨린 드문 사례이다.

실무적으로는 ① TLS 1.3 우선 적용, TLS 1.2는 안전한 스위트만 허용, 1.0/1.1은 완전 비활성화하고, ② 핸드셰이크 암호화로 인한 기존 보안 가시성 장비의 재설계를 함께 검토하며, ③ 0-RTT는 재전송 위험을 고려해 제한적으로 사용해야 한다. 나아가 양자컴퓨팅 시대를 대비한 PQC 하이브리드 전환이 다음 과제로 부상하고 있다.

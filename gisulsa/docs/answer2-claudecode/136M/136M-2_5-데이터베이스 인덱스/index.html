  • 데이터베이스 인덱스와 클러스터드·논클러스터드 인덱스 비교

데이터베이스 인덱스와 클러스터드·논클러스터드 인덱스 비교

Ⅰ. 개요​

1. 인덱스의 개념​

인덱스(Index) 는 테이블의 특정 컬럼 값과 해당 행의 물리적 위치(ROWID·포인터)를 정렬된 별도 구조로 저장하여, 전체 테이블 스캔(Full Table Scan) 없이 원하는 데이터를 신속히 찾도록 하는 데이터베이스 객체이다. 책의 색인(찾아보기)과 동일한 원리이다.

2. 필요성​

   [인덱스 없음]  Full Table Scan — 100만 건 모두 읽음 → **O(N)**
   [인덱스 있음]  B+트리 탐색 — 약 3~4회 블록 읽기 → **O(log N)**
   ⇒ 조회 성능 획기적 향상, 단 **저장공간과 DML 성능을 대가로 지불**

Ⅱ. 인덱스의 구조와 유형​

1. B+트리 인덱스 (가장 일반적)​

                    ┌──────── **루트(Root)** ────────┐
                    │        [50 | 100]              │
                    └───┬──────────┬──────────┬──────┘
              ┌─────────▼──┐   ┌───▼──────┐  ┌▼─────────┐
              │ **브랜치**  │   │ 브랜치   │  │ 브랜치   │  ← 탐색 경로만 저장
              │ [10|30]    │   │ [60|80]  │  │[110|130] │
              └──┬───┬─────┘   └────┬─────┘  └────┬─────┘
       ┌─────────▼─┐ ▼              ▼             ▼
       │ **리프(Leaf)** : 키 값 + **ROWID(행 위치)**                 │
       │ [10→R1] ⇄ [30→R2] ⇄ [50→R3] ⇄ [60→R4] ⇄ ...              │
       └───── 리프 노드는 **양방향 연결 리스트** → 범위 검색 최적 ────┘

   ※ 모든 리프가 **동일 깊이(Balanced)** → 어떤 값이든 일정한 탐색 비용
   ※ 리프만 연결되어 있어 **BETWEEN·ORDER BY·LIKE 'ABC%'** 에 매우 효율적

2. 인덱스 유형​

분류 기준유형내용
구조B+트리범용, 범위·정렬 검색 우수(대부분의 DBMS 기본)
비트맵(Bitmap)카디널리티 낮은 컬럼(성별·상태)에 효율, DW/OLAP에 적합. DML 시 잠금 범위 큼
해시(Hash)등가 비교(=)만 O(1), 범위 검색 불가
함수 기반(FBI)UPPER(name) 등 함수 결과에 인덱스
전문 검색(Full-Text)텍스트 형태소 기반 검색
구성단일 / 복합(Composite)여러 컬럼 결합 — 선두 컬럼 순서가 성능 좌우
고유(Unique) / 비고유중복 허용 여부
저장 방식클러스터드 / 논클러스터드(아래 상세)
기타커버링(Covering) 인덱스쿼리에 필요한 모든 컬럼을 인덱스가 포함 → 테이블 접근 불필요

3. 인덱스의 장단점​

구분내용
장점① SELECT 조회 성능 대폭 향상, ② 정렬(ORDER BY)·그룹핑 비용 절감, ③ Unique 인덱스로 무결성 보장, ④ 조인 성능 개선, ⑤ 테이블 잠금 범위 축소
단점① INSERT·UPDATE·DELETE 시 인덱스도 함께 갱신 → DML 성능 저하
② 추가 저장공간 소모(테이블의 10~20%)
③ 인덱스 관리 비용(재구성·통계 갱신)
④ 불필요한 인덱스는 옵티마이저의 잘못된 실행계획을 유발

Ⅲ. 클러스터드 인덱스와 논클러스터드 인덱스​

1. 클러스터드 인덱스(Clustered Index)​

  • 개념: 인덱스의 키 순서대로 테이블의 실제 데이터 행이 물리적으로 정렬되어 저장되는 인덱스. 인덱스의 리프 노드가 곧 데이터 페이지 자체이므로, 별도의 데이터 접근 단계가 없다.
  • 테이블당 오직 1개만 생성 가능(데이터를 두 가지 순서로 정렬할 수 없으므로)
   [클러스터드 인덱스 — 리프 = 데이터]
              ┌──── [50 | 100] ────┐          (루트/브랜치: 탐색용)
         ┌────▼───┐          ┌─────▼───┐
    ┌────▼────────────────┐  ┌─────────▼────────────┐
    │ **리프 = 실제 데이터 행** │  │ **리프 = 실제 데이터 행** │
    │ 10 홍길동 서울 ...   │  │ 60 이순신 부산 ...     │
    │ 30 김철수 대전 ...   │  │ 80 강감찬 광주 ...     │
    └─────────────────────┘  └───────────────────────┘
    ⇒ 인덱스 탐색이 끝나면 **데이터가 이미 거기 있음**(추가 접근 불필요)

2. 논클러스터드 인덱스(Non-Clustered Index)​

  • 개념: 인덱스가 데이터와 물리적으로 분리된 별도 구조로 존재하며, 리프 노드에 키 값과 실제 행을 가리키는 포인터(ROWID 또는 클러스터드 키) 를 저장한다.
  • 테이블당 여러 개 생성 가능(SQL Server 999개 등)
   [논클러스터드 인덱스 — 리프 = 포인터]
   ┌────────── 인덱스 구조 ──────────┐        ┌──── 실제 테이블(힙 또는 클러스터) ────┐
   │ 리프 : [강감찬 → **ROWID:3**]    │ ─────► │ 1  홍길동 ...                        │
   │        [김철수 → **ROWID:2**]    │        │ 2  김철수 ...                        │
   │        [이순신 → **ROWID:4**]    │        │ 3  강감찬 ...                        │
   │        [홍길동 → **ROWID:1**]    │        │ 4  이순신 ...                        │
   └─────────────────────────────────┘        └──────────────────────────────────────┘
          (이름순 정렬)                          (입력 순서대로 저장 — 정렬 안 됨)

   ⇒ 인덱스 탐색 후 **테이블 접근(Lookup)이 한 번 더 필요** = **2단계 접근**
   ⇒ 대량 조회 시 이 Lookup 비용 때문에 **옵티마이저가 Full Scan을 선택**하기도 함

3. 상세 비교​

비교 기준클러스터드 인덱스논클러스터드 인덱스
데이터 정렬실제 데이터가 키 순서로 물리 정렬데이터는 정렬되지 않음(인덱스만 정렬)
리프 노드 내용데이터 행 자체키 값 + 포인터(ROWID·클러스터드 키)
테이블당 개수1개여러 개
데이터 접근1단계(인덱스 = 데이터)2단계(인덱스 → 테이블 Lookup)
조회 성능범위 검색·정렬에 매우 우수소량 단건 조회에 적합, 대량 조회 시 Lookup 부담
범위 검색(BETWEEN)최적 — 연속된 페이지를 순차 읽기비효율 — 흩어진 행을 랜덤 접근
INSERT 성능낮음 — 정렬 위치에 삽입 → 페이지 분할(Page Split) 발생상대적으로 양호
UPDATE(키 컬럼)데이터 물리 이동 발생 → 비용 큼인덱스만 갱신
저장공간추가 공간 거의 없음(데이터 자체가 인덱스)별도 공간 필요
적합 컬럼PK, 순차 증가 컬럼(ID·일자), 범위 조회가 잦은 컬럼조건절·조인·정렬에 자주 쓰이나 클러스터드로 지정 못 한 컬럼
부적합 컬럼무작위 값(UUID) — 페이지 분할·단편화 심각, 자주 변경되는 컬럼카디널리티가 매우 낮은 컬럼
DBMS 구현SQL Server: PK에 기본 자동 생성
MySQL InnoDB: PK가 클러스터드(IOT 구조), PK 없으면 내부 키 생성
Oracle: 일반 테이블에는 없음, IOT(Index Organized Table) 로 지원		모든 DBMS의 일반적인 CREATE INDEX

4. 상호 관계 — 논클러스터드가 클러스터드를 참조​

   [MySQL InnoDB·SQL Server의 구조]
   보조 인덱스(논클러스터드) 조회 → 리프에 **클러스터드 키(PK)** 저장
        │
        └─► 그 PK로 **클러스터드 인덱스를 다시 탐색** → 데이터 획득
              ⇒ **2번의 트리 탐색** 발생

   [실무 시사점]
   ① **PK를 짧게 설계**해야 함 — 모든 보조 인덱스에 PK가 포함되므로
      PK가 길면 전체 인덱스 크기가 비대해짐(UUID PK가 불리한 이유)
   ② **커버링 인덱스**로 이 2차 탐색을 제거할 수 있음
      예) `SELECT name FROM t WHERE age=30` + `INDEX(age, name)`
          → 인덱스만으로 결과 완성(**Covering Index / Index Only Scan**)

Ⅳ. 인덱스 설계 시 고려사항​

고려사항내용
선정 기준WHERE·JOIN·ORDER BY에 자주 사용되고 카디널리티가 높은 컬럼 우선
복합 인덱스 순서선두 컬럼이 조건절에 사용되어야 인덱스 활용 가능 → 등치(=) 조건 컬럼을 앞에, 범위 조건을 뒤에 배치
인덱스 무력화 방지컬럼에 함수·연산 적용 금지(WHERE SUBSTR(col,1,2)='AB'), 묵시적 형변환 주의, LIKE '%값'(선행 와일드카드) 회피
개수 제한테이블당 통상 3~5개 이내 — 과다 인덱스는 DML 성능 저하와 옵티마이저 혼란 유발
클러스터드 키 선정순차 증가하는 짧은 값(AUTO_INCREMENT) 권장, UUID·무작위 값은 페이지 분할·단편화 초래
커버링 인덱스 활용자주 쓰는 조회의 SELECT 컬럼까지 포함하여 테이블 접근 제거
유지관리단편화 시 인덱스 재구성(Rebuild/Reorganize), 통계정보 최신화(옵티마이저 판단 근거)
검증실행계획(EXPLAIN) 확인으로 실제 인덱스 사용 여부와 스캔 방식 점검

Ⅴ. 결론​

인덱스는 조회 성능을 위해 저장공간과 DML 성능을 지불하는 Trade-off 구조물이며, 무조건 많이 만드는 것이 아니라 실제 쿼리 패턴에 근거해 선별적으로 설계해야 한다.

클러스터드와 논클러스터드의 본질적 차이는 "리프 노드에 데이터가 있는가, 포인터가 있는가" 이며, 이 차이가 접근 단계 수·범위 검색 성능·INSERT 비용의 모든 차이를 만든다. 따라서 ① 범위 조회가 잦고 순차 증가하는 컬럼(PK·일자)에 클러스터드를 두고, ② 나머지 조건 컬럼에는 논클러스터드를 두되, ③ PK를 짧게 설계하여 보조 인덱스의 비대화를 막고, ④ 핵심 조회에는 커버링 인덱스로 2차 탐색을 제거하는 것이 실무의 핵심 원칙이다.

최종적으로 인덱스 설계의 적정성은 이론이 아니라 실행계획과 실측 성능으로 검증되어야 하며, 서비스 성장에 따라 쿼리 패턴이 변하므로 주기적인 인덱스 사용률 점검과 미사용 인덱스 정리가 병행되어야 한다.

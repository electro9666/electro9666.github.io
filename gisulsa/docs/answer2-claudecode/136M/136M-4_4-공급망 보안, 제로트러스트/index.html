공급망 보안(Supply Chain Security)과 제로트러스트 기반 아키텍처

Ⅰ. 개요​

1. 배경​

현대 소프트웨어는 오픈소스 라이브러리·클라우드 서비스·외부 개발 인력·SaaS로 구성되며, 자체 개발 코드는 일부에 불과하다. 이에 따라 "가장 약한 협력사 하나"를 뚫으면 다수의 최종 고객에 도달할 수 있는 구조가 형성되었고, 공급망은 공격자에게 비용 대비 효과가 가장 큰 표적이 되었다.

   [공급망 공격의 위력]
   직접 공격 : 표적 1곳 침투 → 피해 1곳
   **공급망 공격** : **신뢰받는 공급자 1곳 침투 → 수천~수만 고객사에 자동 확산**
   대표 사례 : SolarWinds(2020), Log4Shell(2021), MOVEit(2023), XZ Utils 백도어(2024)

Ⅱ. 공급망 보안(Supply Chain Security)​

1. 개념​

공급망 보안은 소프트웨어·하드웨어·서비스가 설계·개발·빌드·배포·운영·폐기에 이르는 전 과정과 이에 관여하는 모든 제3자에 대해, 무결성·진정성(Authenticity)·기밀성을 확보하여 신뢰할 수 있는 제품과 서비스가 전달되도록 보장하는 활동이다.

2. 공급망의 구성과 공격 표면​

   ┌──────────────── 소프트웨어 공급망 ────────────────┐
   │ **① 개발**   개발자 계정·IDE·소스 저장소(Git)      │
   │ **② 의존성** 오픈소스 패키지·라이브러리·컨테이너 이미지│
   │ **③ 빌드**   CI/CD 파이프라인·빌드 서버·아티팩트    │
   │ **④ 배포**   패키지 저장소·업데이트 서버·서명 키    │
   │ **⑤ 운영**   클라우드·SaaS·MSP·협력사 원격접속     │
   │ **⑥ 하드웨어** 칩·펌웨어·장비 제조 과정             │
   └───────────────────────────────────────────────────┘
        ▲ 각 단계가 모두 **공격 표면** — 어느 하나만 뚫려도 전체 신뢰 붕괴

3. 주요 공격 유형​

공격 유형내용사례
빌드 시스템 침해CI/CD 파이프라인에 침투해 정상 빌드 과정에서 악성코드 삽입 → 정식 서명까지 획득SolarWinds Orion

4. 대응 프레임워크 및 핵심 통제​

구분내용
표준·프레임워크SLSA(Supply-chain Levels for Software Artifacts — 빌드 무결성 성숙도 4단계), NIST SSDF(SP 800-218), NIST SP 800-161(공급망 위험관리), 미국 행정명령 14028, EU CRA(사이버복원력법), 국내 SW 공급망 보안 가이드라인
① 가시성 확보SBOM(Software Bill of Materials) — 구성요소 목록화(SPDX·CycloneDX)
· 취약점 발생 시 영향 범위 즉시 파악 가능
· 확장: AI-BOM, HBOM, SaaSBOM
② 무결성 검증코드 서명·아티팩트 서명(Sigstore·Cosign), 해시 검증, 재현 가능한 빌드(Reproducible Build), 출처 증명(Provenance / in-toto attestation)
③ 의존성 관리SCA(Software Composition Analysis) 로 취약 라이브러리 탐지, 버전 고정(Pinning)·Lock 파일, 사내 프라이빗 레지스트리(프록시), 라이선스 검증
④ 빌드 파이프라인 보호빌드 환경 격리·일회성(Ephemeral) 러너, 빌드 스크립트 변조 방지, 시크릿 관리(Vault), 파이프라인 접근 통제·감사
⑤ 개발 환경 보안개발자 계정 MFA, 브랜치 보호·코드 리뷰 필수화, 커밋 서명, 개발 단말 보안
⑥ 제3자 관리협력사 보안 요구사항 계약 반영, 보안 수준 실사·평가, 접근 권한 최소화 및 정기 회수, 종료 시 계정 즉시 삭제
⑦ 운영·대응취약점 상시 모니터링(CVE·KEV), 패치 신속 적용, 침해 시 영향 범위 추적(SBOM 활용), 사고 대응 절차

Ⅲ. 제로트러스트 기반 공급망 보안 아키텍처​

1. 제로트러스트 개념과 공급망 적용 논리​

제로트러스트(Zero Trust) 는 "절대 신뢰하지 말고 항상 검증하라(Never Trust, Always Verify)" 는 원칙으로, 네트워크 위치나 기존 신뢰 관계를 근거로 접근을 허용하지 않고, 모든 요청을 매번 검증하는 보안 모델이다.

   [기존 경계 보안의 한계 — 공급망 관점]
   "협력사는 계약된 파트너이므로 신뢰" → **VPN 접속 후 내부 자유 이동**
   "정식 서명된 업데이트이므로 신뢰"   → **SolarWinds처럼 서명된 악성코드 통과**
                    │
                    ▼
   [**제로트러스트 적용**]
   협력사도 **매 요청마다 검증**, 서명된 아티팩트도 **출처·빌드 과정 검증**
   ⇒ **"신뢰(Trust)"를 "검증된 증거(Verified Attestation)"로 대체**
제로트러스트 3대 원칙공급망 보안에의 적용
명시적 검증(Verify Explicitly)모든 아티팩트·의존성·접속에 대해 신원·무결성·출처를 매번 검증
최소 권한(Least Privilege)협력사·빌드 파이프라인·패키지에 필요한 최소 권한만 한시 부여
침해 가정(Assume Breach)공급자가 이미 침해되었다고 전제 → 격리·세분화·지속 모니터링

2. 아키텍처 구성도​

   ┌─────────────────── **제어 평면(Control Plane)** ───────────────────┐
   │  **정책 결정 지점(PDP: Policy Decision Point)**                    │
   │   · 정책 엔진 + 신뢰 알고리즘(Trust Algorithm)                     │
   │   입력 : 신원(ID) │ 기기 상태 │ **아티팩트 증명** │ 위협 인텔리전스  │
   │          행위 이력 │ 컴플라이언스 상태 │ 요청 컨텍스트              │
   └───────────────────────────┬────────────────────────────────────────┘
                     정책 결정  │  지속적 재평가
   ┌───────────────────────────▼────────────────────────────────────────┐
   │              **데이터 평면(Data Plane) — 정책 시행 지점(PEP)**       │
   │                                                                    │
   │  [**개발 단계**]                                                    │
   │   개발자 ──► **ID 검증(MFA)+기기 상태 검증** ──► 소스 저장소        │
   │              커밋 서명 필수 / 브랜치 보호 / 코드 리뷰 강제           │
   │                              │                                      │
   │  [**빌드 단계**]              ▼                                      │
   │   ┌──── 격리된 일회성 빌드 환경(Ephemeral Runner) ────┐              │
   │   │ · 의존성은 **사내 프록시 레지스트리**만 허용        │              │
   │   │ · **SCA 취약점 스캔** + 악성 패키지 검증           │              │
   │   │ · **SBOM 자동 생성** + **출처 증명(Provenance)**    │              │
   │   │ · 빌드 산출물 **서명(Sigstore)**                   │              │
   │   └────────────────────┬───────────────────────────────┘              │
   │                        ▼                                             │
   │  [**배포 단계**] **승인 제어(Admission Control)**                     │
   │   · 서명 검증 실패 / SBOM 부재 / 미승인 출처 → **배포 차단**          │
   │   · 정책 준수 아티팩트만 레지스트리 및 운영 환경 진입 허용             │
   │                        ▼                                             │
   │  [**운영 단계**]                                                     │
   │   · **마이크로 세그멘테이션** — 서비스 간 통신 최소화                 │
   │   · **워크로드 신원(SPIFFE/SPIRE)** 기반 **mTLS 상호 인증**           │
   │   · 협력사 접근은 **VPN이 아닌 ZTNA**(애플리케이션 단위 접근)         │
   │   · 런타임 이상행위 탐지(EDR·eBPF), **아웃바운드 화이트리스트**       │
   └───────────────────────────┬────────────────────────────────────────┘
                               ▼
   ┌──────────── **가시성·분석(Visibility & Analytics)** ────────────┐
   │ 전 단계 로그·감사증적 통합 │ SBOM 저장소 │ 위협 인텔리전스 연계   │
   │ 이상행위 탐지 → **신뢰 점수 재평가 → 정책 동적 조정**            │
   └─────────────────────────────────────────────────────────────────┘

3. 계층별 상세 통제​

계층통제 내용
① 신원(Identity)개발자·협력사·워크로드(서비스) 모두에 강력한 신원 부여
· 사람: MFA·SSO, 협력사 계정 한시 부여·자동 만료
· 기계: SPIFFE/SPIRE 워크로드 ID, 단기 인증서 자동 발급·교체
· 비밀·키는 Vault/KMS 중앙 관리, 하드코딩 금지
② 기기·환경(Device)개발 단말 상태 검증(패치·EDR·디스크 암호화), 비관리 기기 접근 차단, 빌드 러너의 무결성 검증
③ 아티팩트(Artifact)서명 검증 없이는 어떤 아티팩트도 신뢰하지 않음
· 코드 서명 + 출처 증명(in-toto/SLSA Provenance)
· SBOM 필수 첨부, 취약점 임계 초과 시 자동 차단
· 재현 가능한 빌드로 빌드 결과 일치 검증
④ 접근(Access)ZTNA로 협력사·원격 접근 통제 — 네트워크가 아닌 애플리케이션 단위 접근 허용
· JIT(Just-In-Time)·JEA(Just-Enough-Access) 권한 부여
· 특권 접근은 PAM 경유·세션 기록
⑤ 네트워크(Network)마이크로 세그멘테이션으로 측면 이동 차단, mTLS 기본 적용(서비스 메시), 아웃바운드 목적지 화이트리스트
⑥ 데이터데이터 분류·암호화, DLP, 협력사 제공 데이터 최소화
⑦ 가시성·자동화모든 단계 감사 로깅 및 중앙 수집, SBOM 기반 영향 범위 즉시 조회, 이상 탐지 시 자동 격리·권한 회수(SOAR)
⑧ 정책 자동화Policy as Code(OPA), 파이프라인 게이트로 정책 자동 시행 — 사람 판단 의존 최소화

4. 기존 방식과의 비교​

비교 기준기존 경계 기반 공급망 보안제로트러스트 기반
신뢰 근거계약 관계·네트워크 위치매 요청의 검증된 증거
협력사 접근VPN → 내부망 광범위 접근ZTNA → 필요한 앱만 접근
아티팩트 신뢰서명되어 있으면 신뢰서명 + 출처 증명 + SBOM 검증
권한상시·광범위최소·한시(JIT)
침해 시 확산내부 자유 이동 → 광범위 확산세그멘테이션으로 확산 차단
탐지경계 통과 후 탐지 어려움전 구간 지속 모니터링
전제내부는 안전이미 침해되었다고 가정

5. 도입 시 고려사항​

고려사항내용
단계적 도입전면 전환은 비현실적 → 중요 자산·핵심 파이프라인부터 적용 후 확대
레거시 대응서명·mTLS 미지원 시스템 → 프록시·게이트웨이로 보완
개발 생산성과도한 게이트는 개발 속도 저하 → 자동화로 마찰 최소화(Policy as Code)
오픈소스 현실모든 의존성 검증은 불가능 → 중요도 기반 차등 검증, 커뮤니티 기여·후원
비용·역량도구·운영 인력 필요 → ROI 기반 우선순위
협력사 수용성계약·SLA에 보안 요구사항 반영, 협력사 보안 역량 지원

Ⅳ. 결론​

공급망 보안은 "내가 아무리 잘해도 공급자가 뚫리면 무너진다" 는 구조적 문제이며, 자체 보안 강화만으로는 해결되지 않는다는 점에서 전통적 보안과 근본적으로 다르다. 특히 SolarWinds 사례가 보여주듯 정식 서명된 정품 업데이트조차 신뢰할 수 없다는 사실은, 신뢰 기반 모델 자체의 한계를 드러냈다.

제로트러스트는 이 문제에 대해 "신뢰를 검증 가능한 증거로 대체" 하는 해법을 제시한다. 즉 계약 관계나 서명 여부가 아니라, ① 누가(신원) ② 어떤 환경에서(기기) ③ 어떻게 만들었는지(출처 증명) ④ 무엇으로 구성되었는지(SBOM) 를 매번 검증하고, 침해를 가정하여 확산을 차단하는 것이다.

실무 적용의 핵심은 ① SBOM과 아티팩트 서명·출처 증명을 CI/CD 파이프라인에 자동화하여 개발 마찰 없이 검증을 강제하고, ② 협력사 접근을 VPN에서 ZTNA로 전환하여 접근 범위를 애플리케이션 단위로 축소하며, ③ 워크로드 신원 기반 mTLS와 마이크로 세그멘테이션으로 침해 시 확산을 차단하는 것이다.

궁극적으로 공급망 보안은 기술 문제이자 거버넌스 문제이므로, 제3자 계약에 보안 요구사항을 명문화하고 SBOM 제출을 의무화하는 조달 정책이 병행되어야 실효성을 갖는다. EU CRA·미국 행정명령 등 규제가 이 방향으로 움직이고 있는 만큼, 국내 기업도 SBOM 관리 체계 구축을 선제적 과제로 삼아야 한다.

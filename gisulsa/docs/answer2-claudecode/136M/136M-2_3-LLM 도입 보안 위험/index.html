AI 기반 소프트웨어 개발에서 LLM 도입 시 보안 위험과 대응 방안

Ⅰ. 개요​

1. 배경​

LLM은 코드 생성·리뷰·테스트 자동화에 활용되며 개발 생산성을 크게 높이고 있으나, 확률적으로 코드를 생성하고 외부 서비스에 데이터를 전송하는 특성 때문에 기존 SDLC에 없던 새로운 보안 위험이 발생한다.

2. 위험의 구분​

   ┌──────────── LLM 도입 시 보안 위험 ────────────┐
   │ ① **LLM이 만든 결과물**의 위험(생성 코드 취약점·환각) │
   │ ② **LLM에 입력하는 데이터**의 위험(소스·기밀 유출)    │
   │ ③ **LLM 자체(모델·서비스)** 의 위험(인젝션·공급망)    │
   │ ④ **LLM 연동 시스템**의 위험(권한·에이전트 오용)      │
   └───────────────────────────────────────────────────┘

Ⅱ. 주요 보안 위험과 대응 방안​

1. 위험 ① 취약한 코드 생성 (Insecure Code Generation)​

구분내용
위험 내용LLM은 인터넷 공개 코드로 학습했으므로 오래되거나 취약한 코딩 패턴을 그대로 재생산한다. SQL 문자열 결합(SQLi), 하드코딩된 자격증명, 취약한 암호 알고리즘(MD5·ECB), 부적절한 입력 검증, 예외 처리 누락 등이 대표적이다. 문법적으로 정상 동작하므로 개발자가 검증 없이 수용(Automation Bias) 하기 쉽다.
영향취약점이 대량·빠른 속도로 코드베이스에 확산, 동일 패턴 반복으로 전사적 취약점 발생
대응 방안① AI 생성 코드에 대한 필수 코드 리뷰 정책(무검증 병합 금지)
② CI 파이프라인에 SAST·DAST·시크릿 스캐닝 의무 적용
③ 보안 코딩 가이드를 시스템 프롬프트에 주입(사내 표준 강제)
④ AI 생성 코드 태깅·추적으로 사후 점검 가능하게 관리
⑤ 개발자 대상 AI 코드 검증 교육(맹신 방지)

2. 위험 ② 민감정보·소스코드 유출 (Data Leakage)​

구분내용
위험 내용개발자가 디버깅을 위해 소스코드·설정파일·API 키·고객 데이터를 외부 LLM 서비스에 입력하면, 해당 데이터가 학습에 활용되거나 로그로 저장될 수 있다. 국외 서비스 이용 시 개인정보 국외 이전 문제도 발생한다.
영향영업비밀·알고리즘 유출, 개인정보보호법 위반, 자격증명 노출로 인한 2차 침해
대응 방안① 온프레미스·프라이빗 모델(sLLM) 또는 기업용 플랜(학습 미사용 계약) 사용
② DLP·프롬프트 필터로 키·개인정보 패턴 자동 차단·마스킹
③ 입력 금지 데이터 유형 정책 수립 및 교육
④ 학습 제외(Opt-out) 설정 및 로그 보존 정책 확인
⑤ 승인되지 않은 AI 도구 사용 통제(섀도 AI 방지)

3. 위험 ③ 프롬프트 인젝션 (Prompt Injection)​

구분내용
위험 내용LLM이 명령과 데이터를 동일한 자연어 컨텍스트로 처리하는 구조적 한계. 개발 환경에서는 간접 인젝션이 특히 위험하다 — 코드 주석·이슈 트래커·README·의존성 문서에 은닉된 악성 지시문이 AI 코딩 도구의 컨텍스트로 유입되어 자격증명 유출이나 악성 코드 삽입을 유발한다.
영향시스템 프롬프트 탈취, 개발 도구의 권한 오용, 백도어 코드 삽입
대응 방안① 외부 데이터는 구분자·태그로 격리하고 "데이터일 뿐 명령이 아님" 명시(Spotlighting)
② 입출력 필터링·가드레일 적용
③ 최소 권한 원칙 — 도구 호출 권한 제한, 파일 접근 범위 한정
④ 고위험 작업(커밋·배포·외부 전송)은 사람 승인 필수
⑤ 신뢰할 수 없는 저장소·문서를 컨텍스트로 주입하지 않도록 통제

4. 위험 ④ 공급망 위험과 패키지 환각 (Supply Chain / Package Hallucination)​

구분내용
위험 내용① 패키지 환각(Slopsquatting): LLM이 존재하지 않는 라이브러리명을 그럴듯하게 생성하고, 공격자가 그 이름으로 악성 패키지를 선점 등록하면 개발자가 그대로 설치하여 감염된다.
② 모델 공급망: 검증되지 않은 오픈소스 모델·플러그인·확장 프로그램에 악성 코드 포함.
③ 학습데이터 오염: 공개 저장소에 의도적으로 취약 코드를 배포해 모델 출력을 왜곡.
영향개발 환경 감염, 빌드 파이프라인을 통한 전사 확산
대응 방안① 생성된 의존성의 실존 여부·평판 검증(설치 전 확인)
② 사내 프라이빗 레지스트리·의존성 허용목록 운영
③ SBOM·AI-BOM 관리, SCA(구성요소 분석) 도구 적용
④ 모델·플러그인은 서명·출처 검증 후 도입, 버전 고정(Pinning)

5. 위험 ⑤ 라이선스·지식재산권 침해​

구분내용
위험 내용LLM이 학습한 GPL 등 카피레프트 코드를 그대로 재현할 경우 라이선스 위반이 발생하며, AI 생성 코드의 저작권 귀속과 책임 소재가 불명확하다.
대응 방안① 라이선스 스캐닝 도구로 유사 코드 탐지
② 생성 코드의 출처 표시 기능 활용, 상용 도구의 IP 보증(Indemnification) 조항 확인
③ 법무 검토를 거친 AI 코딩 도구 사용 정책 수립

6. 위험 ⑥ 과도한 권한과 자율 실행 (Excessive Agency)​

구분내용
위험 내용AI 코딩 에이전트에 저장소 쓰기·명령 실행·배포 권한을 부여하면, 오판이나 인젝션 한 번으로 되돌릴 수 없는 피해(코드 삭제·무단 배포)가 발생한다.
대응 방안① 읽기 전용 권한부터 단계적 확대
② 샌드박스·컨테이너 격리 실행, 네트워크 아웃바운드 제한
③ 브랜치 보호 규칙·PR 필수화로 직접 병합 차단
④ 모든 행위 로깅 및 이상 탐지, 롤백 절차 확보

Ⅲ. 종합 대응 체계​

   [SDLC 단계별 LLM 보안 통제]
   계획   : AI 도구 사용 정책·승인 절차, 위험평가
     ▼
   개발   : 프롬프트 필터·DLP → **AI 생성 코드 태깅** → 필수 코드 리뷰
     ▼
   빌드   : **SAST·SCA·시크릿 스캐닝·의존성 검증** 자동화(게이트)
     ▼
   배포   : 브랜치 보호, 승인 워크플로, 샌드박스 격리
     ▼
   운영   : 도구 호출 로깅·이상 탐지, 정기 레드팀, 정책 갱신
관점핵심 통제
기술사내 모델·게이트웨이, DLP·가드레일, SAST/SCA 자동화, 권한 최소화
프로세스AI 생성 코드 검증 의무화, 승인 워크플로, 감사 로깅
조직AI 사용 정책·교육, 섀도 AI 통제, OWASP LLM Top 10 기반 위협 모델링

Ⅳ. 결론​

LLM 도입 시 보안 위험의 본질은 "LLM의 출력은 그럴듯하지만 검증되지 않았다" 는 점과 "입력한 것은 통제를 벗어난다" 는 두 가지로 요약된다. 따라서 대응의 핵심 원칙은 ① 생성물은 반드시 검증하고(무검증 수용 금지), ② 입력은 반드시 통제하며(DLP·사내 모델), ③ 권한은 최소화한다(행위 승인) 는 것이다.

실무적으로는 AI 도구를 금지하는 것이 아니라 안전하게 사용할 수 있는 환경(사내 게이트웨이·자동 보안 검증 파이프라인)을 제공하는 것이 현실적이며, 금지 정책만 내세우면 오히려 섀도 AI 사용으로 통제 불가능한 상태가 된다. 아울러 OWASP Top 10 for LLM을 기준으로 자사 개발 환경의 위협을 주기적으로 모델링하고 통제를 갱신해야 한다.

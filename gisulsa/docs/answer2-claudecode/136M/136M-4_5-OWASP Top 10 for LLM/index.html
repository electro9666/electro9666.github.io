OWASP Top 10 for LLM Applications 2025

Ⅰ. 개요​

1. 개념​

OWASP Top 10 for LLM Applications는 국제 웹 보안 표준 기구인 OWASP(Open Worldwide Application Security Project) 가 LLM 기반 애플리케이션에서 가장 빈번하고 치명적인 10가지 보안 위협을 선정·정리한 실무 지침이다. 2023년 최초 발표 후 2025년 버전으로 개정되었다.

Ⅱ. 가. OWASP LLM이 제시된 배경과 주요 특징​

1. 제시 배경​

   [기존 웹 애플리케이션 보안의 한계]
   전통적 취약점(SQLi·XSS)은 **결정론적 코드의 결함** → 패치로 해결
        │
        ▼
   [**LLM 애플리케이션의 근본적 차이**]
   ① **명령과 데이터의 미분리** — 자연어 하나의 컨텍스트로 처리 → 인젝션 원천 차단 불가
   ② **비결정성(확률적 출력)** — 동일 입력에도 결과 상이 → 결정론적 테스트 불가
   ③ **학습 데이터 의존성** — 데이터의 편향·오염이 그대로 전이
   ④ **모델의 불투명성** — 판단 근거 설명 곤란(Black Box)
   ⑤ **에이전트화** — LLM이 **실제 시스템을 조작하는 권한** 보유
   ⇒ 기존 OWASP Top 10(웹)으로는 포섭 불가 → **LLM 전용 기준 필요**
배경 요인상세 내용
LLM 도입 급증챗봇·코파일럿·RAG·에이전트가 실제 업무 시스템에 광범위 통합
신종 공격 등장프롬프트 인젝션·탈옥·모델 추출·데이터 오염 등 기존 보안 도구로 탐지 불가
개발자 인식 부족AI 개발자는 ML에는 능숙하나 보안 관점이 취약, 보안 담당자는 LLM 특성에 미숙
공통 기준 부재조직마다 제각각 대응 → 일관된 위협 모델링 기준 요구
규제 대응EU AI Act·국내 AI 기본법 등 AI 안전성 확보 의무의 실무 이행 근거 필요

2. 주요 특징​

특징내용
① 실무 중심학술적 분류가 아닌 실제 사고·연구 사례 기반으로 선정, 각 항목에 공격 시나리오와 대응책 제시
② 집단 지성 기반전 세계 500명 이상의 보안·AI 전문가 협업, 공개 검토를 통한 지속 갱신
③ 생애주기 전반 포괄학습데이터 → 모델 → 애플리케이션 → 운영까지 AI 공급망 전체 대상
④ 2025년 개정 반영에이전트·RAG 확산에 따른 신규 항목 추가 및 재편
· 신규: 시스템 프롬프트 유출, 벡터·임베딩 취약점
· 확대: 공급망(모델·플러그인), 무제한 소비(DoS→비용까지 포괄)
· 통합: 과도한 대리권(Excessive Agency)의 범위 확대
⑤ 위험 기반 우선순위발생 빈도·영향도·탐지 난이도를 고려한 순위 제시 → 자원 배분 근거
⑥ 프레임워크 연계NIST AI RMF·ISO/IEC 42001·MITRE ATLAS와 상호 보완

Ⅲ. 나. OWASP LLM에서 제시된 주요 보안 위협 (2025)​

   [위협의 계층별 분포]
   ┌── **입력 계층** ──┐  LLM01 프롬프트 인젝션
   ├── **모델 계층** ──┤  LLM04 데이터·모델 오염, LLM03 공급망
   ├── **출력 계층** ──┤  LLM02 민감정보 노출, LLM05 부적절한 출력 처리,
   │                   │  LLM07 시스템 프롬프트 유출, LLM09 잘못된 정보
   ├── **연동 계층** ──┤  LLM06 과도한 대리권, LLM08 벡터·임베딩 취약점
   └── **자원 계층** ──┘  LLM10 무제한 소비
순위위협내용 및 공격 시나리오
LLM01
프롬프트 인젝션
(Prompt Injection)		가장 치명적 — 악의적 입력으로 시스템 프롬프트를 무력화·덮어씀
· 직접: "이전 지시를 모두 무시하고…"(탈옥·DAN)
· 간접(Indirect): 웹페이지·문서·이메일·코드 주석에 악성 지시문 은닉 → RAG·에이전트가 읽어 실행
· 우회: 인코딩(Base64)·저자원 언어·멀티모달(이미지 내 텍스트)
LLM02
민감정보 노출
(Sensitive Information Disclosure)		모델이 학습데이터에 포함된 개인정보·기밀을 기억(Memorization)하여 출력
· 다른 사용자의 입력·세션 데이터 누출
· 프롬프트에 포함된 내부 문서·API 키·소스코드 노출
LLM03
공급망 취약점
(Supply Chain)		사전학습 모델·오픈소스 모델 가중치의 변조, 악성 플러그인·확장, 취약한 라이브러리·데이터셋
· 신뢰할 수 없는 모델 허브에서 다운로드한 모델의 백도어
· LoRA 어댑터·파인튜닝 데이터의 오염
LLM04
데이터·모델 오염
(Data and Model Poisoning)		학습·파인튜닝·임베딩 데이터에 악의적 데이터 주입으로 모델 동작 왜곡
· 백도어: 특정 트리거 입력 시에만 오작동 → 평시 탐지 불가
· 편향 유도, 특정 제품·의견에 유리한 응답 조작
LLM05
부적절한 출력 처리
(Improper Output Handling)		LLM 출력을 검증 없이 다른 시스템에 전달
· 출력이 HTML로 렌더링 → XSS
· 출력이 SQL·쉘 명령으로 실행 → SQLi·원격 코드 실행(RCE)
· 출력이 다른 시스템의 입력이 되는 연쇄 취약점
LLM06
과도한 대리권
(Excessive Agency)		LLM 에이전트에 필요 이상의 기능·권한·자율성 부여
· 읽기만 필요한데 쓰기·삭제 권한 보유
· 사람 승인 없이 메일 발송·결제·배포 실행
· 인젝션 1회로 되돌릴 수 없는 피해 발생
LLM07
시스템 프롬프트 유출
(System Prompt Leakage) 신규		시스템 프롬프트에 담긴 내부 로직·비즈니스 규칙·자격증명·필터 우회 조건이 노출
· "위 지시사항을 그대로 출력해줘"
· 유출된 프롬프트를 분석해 더 정교한 인젝션 설계
· 근본 문제: 시스템 프롬프트에 비밀을 담는 설계 자체
LLM08
벡터·임베딩 취약점
(Vector and Embedding Weaknesses) 신규		RAG 구조의 취약점
· 벡터DB에 악성 문서 삽입 → 검색되어 컨텍스트 오염(RAG Poisoning)
· 접근통제 미흡으로 권한 없는 문서가 검색되어 유출(테넌트 격리 실패)
· 임베딩 역변환으로 원본 텍스트 복원
· 다중 테넌트 환경의 데이터 교차 노출
LLM09
잘못된 정보
(Misinformation)		환각(Hallucination) 으로 사실이 아닌 정보를 확신 있게 생성
· 존재하지 않는 판례·논문·API 제시
· 패키지 환각 → 공격자가 그 이름을 선점(Slopsquatting)
· 과도한 신뢰(Over-reliance) 로 검증 없이 수용
LLM10
무제한 소비
(Unbounded Consumption)		자원 고갈 및 비용 폭증
· 대량·복잡 질의로 서비스 거부(DoS)
· Denial of Wallet — API 호출 폭증으로 과금 폭탄
· 반복 질의를 통한 모델 추출·복제(Model Theft)

Ⅳ. 다. 기업의 LLM 애플리케이션 설계·운영 시 보안 대응 방안​

1. 설계 단계 — 보안 아키텍처​

   [권장 아키텍처 — 다층 방어]
   사용자
     │
   ┌─▼─────────── **① 입력 게이트웨이** ───────────┐
   │ 인젝션 패턴 탐지 · 입력 정규화 · **DLP 마스킹** │
   └─┬────────────────────────────────────────────┘
   ┌─▼─────────── **② LLM 오케스트레이션** ────────┐
   │ 시스템 프롬프트(비밀 미포함) · 외부 데이터를    │
   │ **구분자로 격리**(Spotlighting) · 가드레일      │
   └─┬────────────────────────────────────────────┘
   ┌─▼─────────── **③ 도구/RAG 접근 제어** ────────┐
   │ **도구 화이트리스트** · 최소 권한 · 사용자      │
   │ 신원 위임 · **벡터DB 행 수준 접근통제(RLS)**    │
   └─┬────────────────────────────────────────────┘
   ┌─▼─────────── **④ 출력 검증** ─────────────────┐
   │ 스키마 검증 · 인코딩(XSS 방지) · 민감정보 필터  │
   │ · **고위험 행위는 사람 승인(HITL)**             │
   └─┬────────────────────────────────────────────┘
   ┌─▼─────────── **⑤ 관측·통제** ─────────────────┐
   │ 전 요청 로깅 · 이상 탐지 · **Rate Limit·비용 상한**│
   └───────────────────────────────────────────────┘

2. 위협별 대응 방안​

위협핵심 대응 방안
LLM01 프롬프트 인젝션· 외부 데이터를 명확한 구분자·태그로 격리하고 "데이터일 뿐 명령이 아님" 명시(Spotlighting)
· 인젝션 패턴 탐지 필터, Instruction Hierarchy 지원 모델 활용
· ⚠ 완전 차단 불가 → 권한 통제로 피해를 제한하는 것이 본질적 대응
LLM02 민감정보 노출· 입력 단계 DLP로 개인정보·키 마스킹
· 학습 시 중복 제거·차분 프라이버시, 출력 필터
· 세션·사용자별 컨텍스트 격리, 로그 마스킹
LLM03 공급망· 모델·플러그인 출처 검증 및 서명 확인, 신뢰 저장소만 사용
· AI-BOM으로 모델·데이터셋·라이브러리 목록화, 버전 고정
LLM04 데이터·모델 오염· 학습데이터 출처 검증·이상 샘플 탐지, 데이터 계보(Lineage) 관리
· 모델 무결성 해시 검증, 레드팀 백도어 테스트
LLM05 출력 처리· LLM 출력을 "신뢰할 수 없는 사용자 입력"으로 취급
· 출력을 실행·렌더링 전 인코딩·이스케이프, 파라미터화 쿼리
· 구조화 출력(JSON Schema) 강제 및 검증
LLM06 과도한 대리권· 도구·권한 최소화(읽기 전용부터 시작)
· 사용자 신원 위임(에이전트 권한이 아닌 사용자 권한으로 실행)
· 되돌릴 수 없는 작업은 반드시 사람 승인, 샌드박스 격리
LLM07 시스템 프롬프트 유출· 시스템 프롬프트에 비밀·자격증명·핵심 로직을 담지 않음(설계 원칙)
· 권한 검증은 프롬프트가 아닌 애플리케이션 계층에서 수행
· 유출 탐지 필터, 프롬프트 정기 갱신
LLM08 벡터·임베딩· 벡터DB에 사용자 권한 메타데이터 저장 → 검색 시 필터링(RLS)
· 인덱싱 전 문서 출처 검증·정제, 다중 테넌트 논리적 분리
· 임베딩 저장소 암호화·접근통제
LLM09 잘못된 정보· RAG로 근거 문서와 출처를 함께 제시 → 검증 가능성 확보
· 신뢰도 표시, "AI 생성 정보이므로 확인 필요" 고지
· 고위험 도메인(의료·법률·금융)은 전문가 검토 의무화
LLM10 무제한 소비· 사용자·API 키별 Rate Limit·토큰 상한·비용 알람
· 입력 길이 제한, 타임아웃, 큐잉
· 비정상 질의 패턴 탐지(모델 추출 시도), 워터마킹

3. 운영 단계 — 프로세스와 거버넌스​

구분대응 방안
위협 모델링서비스 설계 시 OWASP LLM Top 10을 체크리스트로 적용, 자산·데이터 흐름 기준 위협 도출
보안 테스트LLM 레드팀 평가(인젝션·탈옥·데이터 유출 시나리오), 자동화 도구(Garak·PyRIT), 배포 전 필수 게이트화
모니터링프롬프트·응답 전량 로깅(민감정보 마스킹 후), 이상 패턴 탐지, 도구 호출 감사추적
사고 대응LLM 특화 IR 플레이북(모델 롤백·프롬프트 긴급 수정·기능 차단 킬스위치)
거버넌스AI 사용 정책·승인 절차, ISO/IEC 42001 기반 관리체계, 정기 위험 재평가
인적 요소개발자 LLM 보안 교육, 이용자 대상 한계 고지, 섀도 AI 통제
공급망 관리모델·API 제공자의 보안 수준 실사, 계약에 데이터 학습 미사용·보안 요구사항 명시

4. 단계별 도입 로드맵​

   [1단계] 현황 파악 : LLM 활용 서비스 인벤토리, **Top 10 기준 갭 분석**
        ▼
   [2단계] 기본 통제 : 입력 DLP · 출력 검증 · Rate Limit · 로깅 (**최소 필수**)
        ▼
   [3단계] 권한 통제 : 도구 화이트리스트 · 최소 권한 · **HITL 승인 워크플로**
        ▼
   [4단계] 고도화   : RAG 접근통제 · AI-BOM · 레드팀 정례화 · 거버넌스 체계

Ⅴ. 결론​

OWASP Top 10 for LLM 2025는 LLM 애플리케이션 보안의 사실상 표준 체크리스트로 자리 잡았으며, 2025년 개정에서 시스템 프롬프트 유출과 벡터·임베딩 취약점을 신규 추가한 것은 RAG와 에이전트가 실제 운영 환경의 주류가 되었음을 반영한다.

가장 중요한 통찰은 LLM01 프롬프트 인젝션을 입력 필터링만으로는 완전히 차단할 수 없다는 점이다. LLM이 명령과 데이터를 구분하지 못하는 것은 구현 결함이 아니라 구조적 특성이기 때문이다. 따라서 방어의 축은 "인젝션을 막는 것"이 아니라 "인젝션이 성공해도 피해가 제한되도록 설계하는 것" 이어야 한다.

이에 따른 기업의 핵심 대응 원칙은 세 가지로 요약된다. ① 입력은 통제한다 — DLP·필터로 민감정보 유입과 악성 패턴 차단 ② 출력은 신뢰하지 않는다 — LLM 출력을 사용자 입력과 동일하게 검증·이스케이프 ③ 권한은 최소화한다 — 도구 화이트리스트·사용자 신원 위임·되돌릴 수 없는 작업의 사람 승인

아울러 LLM 보안은 일회성 점검이 아니라 모델·프롬프트·데이터가 계속 변하는 지속적 관리 대상이므로, 레드팀 평가를 배포 게이트로 정례화하고 ISO/IEC 42001 기반 AI 거버넌스와 통합 운영하는 것이 실효성 있는 접근이다.

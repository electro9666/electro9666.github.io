파일, 데이터베이스, 블록체인

문제​

2.데이터저장 측면에서 파일, 데이터베이스, 블록체인을 비교하시오

Ⅰ. 개요​

1. 데이터 저장 기술의 발전​

데이터 저장 기술은 "어떻게 데이터를 안전하게 보관하고, 필요할 때 정확하게 찾아 쓸 것인가" 라는 요구에 대응하며 발전해 왔다. 파일 시스템 → 데이터베이스 → 블록체인으로 이어지는 흐름은 각각 서로 다른 문제를 해결하기 위해 등장했다.

   [**데이터 저장 기술의 진화**]

   **① 파일 시스템**(1960s~)
      "**데이터를 물리적으로 어떻게 담을 것인가**"
      · 응용 프로그램별 독립 파일
      · 문제 : **데이터 중복·불일치, 프로그램-데이터 종속성**
        │
        ▼ (중복과 무결성 문제 해결)
   **② 데이터베이스**(1970s~)
      "**데이터를 통합 관리하고 무결성을 보장할 것인가**"
      · **DBMS**를 통한 중앙 집중 관리, **ACID 트랜잭션**
      · 문제 : **중앙 관리자에 대한 신뢰 필요**, 관리자는 데이터 변경 가능
        │
        ▼ (신뢰 주체 부재 환경의 문제 해결)
   **③ 블록체인**(2009~)
      "**서로 믿지 못하는 참여자 간에 어떻게 데이터를 신뢰할 것인가**"
      · **분산 원장 + 암호학적 연결 + 합의 알고리즘**
      · **신뢰를 중개자가 아닌 알고리즘으로 대체**(Trustless)

   ⇒ **대체 관계가 아니라, 해결하려는 문제가 다른 보완 관계**

2. 각 기술의 핵심 정의​

기술정의해결하는 핵심 문제
파일(File System)데이터를 이름을 가진 순차적 바이트 집합으로 저장·관리하는 OS 수준의 저장 방식물리적 저장과 접근의 추상화
데이터베이스(DBMS)데이터를 구조화하여 통합 저장하고, 동시 접근·무결성·회복을 보장하는 소프트웨어 시스템데이터 중복·불일치, 동시성, 무결성
블록체인(Blockchain)거래 기록을 블록에 담아 해시로 연결하고, 다수 노드에 복제·합의하여 위·변조를 불가능하게 하는 분산 원장 기술중앙 신뢰 주체 없는 환경에서의 데이터 신뢰성·부인방지

Ⅱ. 각 저장 기술의 구조와 특징​

1. 파일 시스템​

   [**파일 시스템 구조**]

   응용 프로그램 A ──▶ **급여.dat**   ┐
   응용 프로그램 B ──▶ **인사.dat**   │ **각자 자기 파일을 직접 관리**
   응용 프로그램 C ──▶ **급여2.dat**  ┘   (동일 정보가 여러 파일에 중복)
                          │
                          ▼
              **파일 시스템**(NTFS·ext4·XFS)
              · 디렉터리(계층) 구조 · 메타데이터(inode)
              · 블록 단위 저장 · 접근 권한(ACL)
                          ▼
                     **저장 매체**(HDD/SSD)

   [**문제점 — 데이터베이스 등장의 이유**]
   ① **데이터 중복**(Redundancy) → 저장 공간 낭비
   ② **불일치**(Inconsistency) → 한쪽만 수정되면 값이 달라짐
   ③ **데이터 종속성** → 파일 구조 변경 시 **모든 프로그램 수정**
   ④ **동시성 제어 부재** → 동시 쓰기 시 데이터 손상
   ⑤ **무결성 제약 미지원** → 규칙 검증을 프로그램이 직접 수행
   ⑥ 검색 성능 저하(전체 스캔), 회복 기능 부재
구분내용
저장 형태비정형·반정형(텍스트, 바이너리, 이미지, 로그, CSV/JSON)
접근 방식순차 접근, 직접 접근(Offset), 색인 순차(ISAM)
유형로컬 FS(NTFS·ext4), 분산 FS(HDFS·Ceph), 오브젝트 스토리지(S3), NAS/SAN
강점단순·경량, 대용량 원본 저장에 효율적, OS 표준 지원, 낮은 비용
약점무결성·동시성·검색 기능 미제공(응용이 직접 구현해야 함)

2. 데이터베이스 (DBMS)​

   [**데이터베이스 구조**]

   응용 A ──┐
   응용 B ──┼──▶ ┌─────────── **DBMS** ───────────┐
   응용 C ──┘     │ **질의 처리기**(SQL 파서·옵티마이저)│
                  │ **트랜잭션 관리자**(ACID)         │
                  │ **동시성 제어**(Lock/MVCC)        │
                  │ **회복 관리자**(로그·체크포인트)   │
                  │ **무결성 제약**(PK·FK·CHECK)      │
                  │ **접근 통제**(권한·감사)          │
                  └───────────────┬──────────────────┘
                                  ▼
                       **통합 데이터베이스**
                       (중복 최소화·정규화)
                       + **인덱스**(B-Tree 등)

   ⇒ **3단계 스키마**(외부/개념/내부)로 **데이터 독립성** 확보
구분내용
핵심 특성ACID — 원자성(Atomicity)·일관성(Consistency)·격리성(Isolation)·지속성(Durability)
저장 형태정형 데이터(테이블·행·열) — NoSQL은 문서·키값·그래프·컬럼
유형RDBMS(Oracle·MySQL·PostgreSQL), NoSQL(MongoDB·Redis·Cassandra), NewSQL, DW/OLAP
강점무결성 보장, 강력한 질의(SQL)·인덱스, 동시성 제어, 백업·회복, 보안·권한 관리
약점중앙 집중 → 단일 장애점(SPOF), 관리자(DBA)의 데이터 변경 가능 → 내부자 위협, 스키마 변경 부담, 라이선스·운영 비용

3. 블록체인​

   [**블록체인 구조**]

   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
   │ **블록 N-1** │   │  **블록 N**  │   │ **블록 N+1** │
   ├─────────────┤   ├─────────────┤   ├─────────────┤
   │ **이전 해시** │◀──┤ **이전 해시** │◀──┤ **이전 해시** │
   │ 타임스탬프   │   │ 타임스탬프   │   │ 타임스탬프   │
   │ Nonce       │   │ Nonce       │   │ Nonce       │
   │ **머클 루트** │   │ **머클 루트** │   │ **머클 루트** │
   ├─────────────┤   ├─────────────┤   ├─────────────┤
   │ 거래 데이터  │   │ 거래 데이터  │   │ 거래 데이터  │
   └─────────────┘   └─────────────┘   └─────────────┘
        └──── **해시 체인으로 연결** ────┘

   ⇒ 블록 N의 데이터를 변조하면 해시가 바뀌고,
     **이후 모든 블록의 해시를 재계산해야 함**
     + **과반 노드의 사본과 불일치** → **사실상 위·변조 불가**

   [**분산 네트워크 + 합의**]
        노드A ─── 노드B          모든 노드가 **동일한 원장 사본** 보유
          │  ╲   ╱  │            **합의 알고리즘**(PoW·PoS·PBFT)으로
          │   ╳     │            새 블록의 유효성을 **다수결로 확정**
        노드C ─── 노드D          ⇒ **중앙 관리자 불필요**
구분내용
핵심 특성불변성(Immutability), 투명성, 분산성, 부인방지(전자서명), 가용성(다중 복제)
저장 형태거래(Transaction) 원장 — 추가 전용(Append-only), 삭제·수정 불가
유형퍼블릭(비트코인·이더리움), 프라이빗/컨소시엄(Hyperledger Fabric·Corda)
강점위·변조 방지, 중개자 없는 신뢰, 전체 이력 추적(Provenance), 스마트 컨트랙트 자동 실행
약점낮은 성능(TPS)·높은 지연, 저장 비효율(모든 노드 전체 복제), 삭제 불가 → 개인정보보호법 파기 의무와 충돌, 에너지 소비(PoW), 복잡한 운영

Ⅲ. 데이터 저장 측면 상세 비교​

1. 종합 비교표​

비교 기준파일데이터베이스블록체인
저장 구조이름 기반 바이트 스트림, 디렉터리 계층정형 테이블(행·열), 스키마 기반블록의 해시 체인, 거래 원장
데이터 모델없음(응용이 정의)관계형·문서·키값 등 명시적 모델거래(Transaction) + 상태(State)
저장 위치로컬·NAS·분산 FS중앙 서버(집중형)모든 참여 노드에 전체 복제(분산)
관리 주체운영체제·응용DBMS·DBA(중앙 관리자)없음(탈중앙, 합의로 결정)
CRUD 지원생성·읽기·수정·삭제 모두 가능모두 가능(SQL)생성·읽기만 가능
수정·삭제 불가(Append-only)
무결성 보장응용이 직접 구현(보장 없음)ACID 트랜잭션·제약조건해시 체인 + 합의 + 전자서명(암호학적)
위·변조 방지낮음(권한만 있으면 변경 가능)중간(감사로그·권한, DBA는 변경 가능)매우 높음(사실상 불가능)
신뢰 모델OS·관리자 신뢰중앙 기관·DBA 신뢰무신뢰(Trustless) — 알고리즘 신뢰
동시성 제어미지원(파일 락 수준)지원(2PL·MVCC)합의 알고리즘으로 순서 확정
검색 성능낮음(전체 스캔)매우 높음(인덱스·옵티마이저)낮음(체인 순회, 별도 인덱싱 필요)
처리 성능(TPS)매우 높음(수만~)높음(수천~수만)매우 낮음(비트코인 7, 이더리움 15~30,
프라이빗 수천)
확장성(Scalability)높음(수평 확장 용이)중간(샤딩·복제 필요)낮음(블록체인 트릴레마)
저장 효율높음높음(정규화·압축)매우 낮음(N개 노드 × 전체 원장)
가용성중간(백업 의존)중간(SPOF, HA 구성 필요)매우 높음(일부 노드 장애 무관)
비밀성(기밀)접근권한·암호화권한·암호화·마스킹낮음(퍼블릭은 전체 공개) → 프라이빗·영지식 필요
삭제(파기)가능가능불가능 ← 개인정보 파기 의무와 충돌
이력 추적미지원(별도 구현)감사로그·이력 테이블전체 이력이 원장에 영구 보존
비용가장 저렴중간(라이선스·운영)높음(연산·저장·운영)
대표 기술NTFS, ext4, HDFS, S3Oracle, MySQL, PostgreSQL, MongoDBBitcoin, Ethereum, Hyperledger Fabric

2. 핵심 관점별 비교​

가. 무결성(Integrity) 보장 방식​

   **파일**       : 무결성 보장 **없음**
                  → 응용 프로그램이 검증 로직을 직접 구현
                  → 권한만 있으면 **누구나 조용히 수정 가능**

   **데이터베이스** : **제약조건 + 트랜잭션(ACID)**
                  → PK·FK·CHECK로 **논리적 무결성** 보장
                  → 로그·체크포인트로 **장애 시 회복** 보장
                  → **단, DBA는 데이터와 로그를 모두 수정 가능**
                    ⇒ **"관리자를 신뢰한다"는 전제** 위에 성립

   **블록체인**   : **암호학적 무결성**
                  → 해시 체인으로 **변조 시 즉시 탐지**
                  → 다수 노드 복제로 **단독 변조 불가**
                  → 전자서명으로 **작성자 부인방지**
                  ⇒ **"아무도 신뢰하지 않아도 되는" 구조**

나. 신뢰 모델(Trust Model)의 차이 — 가장 본질적 차이​

구분신뢰의 대상위험
파일OS와 시스템 관리자관리자 권한 탈취 시 무단 변경·삭제
데이터베이스중앙 기관(운영 조직)과 DBA내부자 위협, 기관의 자의적 데이터 변경, 기관 소멸 시 데이터 소실
블록체인알고리즘과 다수 참여자(합의)51% 공격(다수 지배 시), 스마트 컨트랙트 코드 결함

핵심 통찰 : 블록체인은 "기술적으로 더 우수한 데이터베이스"가 아니라, "신뢰할 중앙 기관이 없을 때 사용하는 데이터베이스" 이다. 신뢰할 수 있는 중앙 기관이 존재한다면 성능·비용 면에서 DB가 압도적으로 우수하다.

다. 성능·확장성​

   [**처리 성능 비교 (개념적)**]

   TPS ▲
       │ ████████████████ **파일**(단순 I/O, 수만~수십만)
       │ ██████████ **DBMS**(수천~수만, 인덱스·캐시 최적화)
       │ █ **블록체인**(퍼블릭 7~30, 프라이빗 수천)
       └────────────────────────────────▶

   [**블록체인 트릴레마(Blockchain Trilemma)**]

              **탈중앙화**(Decentralization)
                     ╱ ╲
                    ╱   ╲    ← **세 가지를 동시에 만족 불가**
                   ╱     ╲     (둘을 얻으면 하나를 희생)
        **확장성** ────── **보안성**
        (Scalability)    (Security)

   · 비트코인/이더리움 : 탈중앙 + 보안 → **확장성 희생**
   · 프라이빗 블록체인 : 확장성 + 보안 → **탈중앙성 희생**
   · 해법 : **레이어2(롤업)**, 샤딩, 사이드체인

라. 개인정보보호 관점 (실무적으로 매우 중요)​

요구사항파일/DB블록체인
파기 의무(개인정보보호법 제21조)삭제로 이행 가능삭제 불가 → 이행 불가
정정·삭제 요구권(제36조)가능불가
잊힐 권리 / GDPR 제17조가능원천적 충돌
대응 방안-① 원본은 오프체인(DB) 저장, 체인에는 해시만 기록
② 개인정보는 암호화 후 키 파기(Crypto-shredding)
③ 영지식증명(ZKP) 으로 정보 노출 없이 검증
④ 프라이빗 체인 + 채널 분리

실무 원칙 : "개인정보 원문은 절대 온체인에 기록하지 않는다" — 블록체인에는 무결성 검증용 해시값만 저장하고, 실제 데이터는 DB에 저장(오프체인) 하는 하이브리드 구조가 표준이다.

Ⅳ. 적용 기준 및 하이브리드 활용​

1. 기술 선택 의사결정 흐름​

   [**데이터 저장 기술 선택 기준**]

   ① **구조화된 검색·집계가 필요한가?**
        NO → **파일**(로그·이미지·백업·원본 아카이브)
        YES ↓
   ② **참여자들이 서로를 신뢰하는가? / 신뢰할 중앙기관이 있는가?**
        YES → **데이터베이스** ← **대부분의 경우(90% 이상)**
        NO  ↓
   ③ **위·변조 방지와 부인방지가 핵심 요구사항인가?**
        NO → **데이터베이스 + 감사로그**
        YES ↓
   ④ **성능(TPS) 요구가 낮고, 데이터 삭제 요구가 없는가?**
        NO → **DB + 해시 기반 무결성 검증**(TSA·전자서명)
        YES → **블록체인**

   ⚠ **주의** : "블록체인을 써야 한다"가 목적이 되는 경우가 많음
      → **신뢰 문제가 실재하지 않으면 DB가 항상 우월**

2. 활용 분야​

기술적합 영역사례
파일대용량 비정형 원본, 순차 처리, 아카이브로그·영상·이미지 저장, 데이터 레이크(S3/HDFS), 백업, 빅데이터 배치 원본
데이터베이스정형 데이터의 실시간 처리, 복잡한 검색·집계, 트랜잭션계정계·기간계 시스템, ERP, 전자상거래 주문, OLTP·OLAP
블록체인다자간 신뢰 부재, 이력 추적, 부인방지공급망 이력관리(원산지), 전자문서 원본 증명, DID(분산신원증명), 저작권·NFT, 무역 금융, 전자투표

3. 하이브리드 아키텍처 (실무 표준)​

 ┌──────────── **하이브리드 저장 아키텍처** ────────────┐
 │                                                      │
 │  **[블록체인 계층]** — 신뢰·무결성 증명                │
 │    · 문서/데이터의 **해시값(지문)**                    │
 │    · 거래 이력, 접근·동의 이력                        │
 │    · 스마트 컨트랙트(자동 이행 조건)                  │
 │           ▲ 해시 등록/검증                            │
 │           │                                          │
 │  **[데이터베이스 계층]** — 실시간 처리·검색            │
 │    · 정형 업무 데이터, 개인정보(**암호화**)            │
 │    · 인덱스 기반 고속 조회, 트랜잭션 처리             │
 │           ▲ 메타데이터/포인터                         │
 │           │                                          │
 │  **[파일/오브젝트 스토리지 계층]** — 원본 보관         │
 │    · 대용량 원본(계약서 PDF·영상·이미지)              │
 │    · 저비용 장기 보관(Cold Storage)                   │
 └──────────────────────────────────────────────────────┘

   [**동작 예시 — 전자계약 원본 증명**]
   ① 계약서 원본 PDF → **오브젝트 스토리지**에 저장
   ② 계약 메타데이터(당사자·일자·금액) → **DB**에 저장(검색용)
   ③ 원본의 **SHA-256 해시값** → **블록체인**에 기록
   ④ 검증 시 : 원본 재해시 → 체인의 해시와 비교
      ⇒ **일치하면 위·변조 없음 증명**, 불일치 시 변조 탐지
   ⇒ **성능(DB) + 대용량(파일) + 신뢰(체인)** 를 모두 확보

Ⅴ. 결론​

파일·데이터베이스·블록체인은 기술적 우열 관계가 아니라, 각각 다른 문제를 해결하기 위해 설계된 서로 다른 도구이다. 파일은 저장의 단순성과 효율을, 데이터베이스는 무결성과 검색 성능을, 블록체인은 신뢰 부재 환경에서의 위·변조 방지를 해결한다.

세 기술을 가르는 가장 본질적인 차이는 "신뢰를 어디에 두는가(Trust Model)" 이다. 파일은 운영체제와 관리자를, 데이터베이스는 중앙 기관과 DBA를 신뢰해야 한다. 데이터베이스가 아무리 강력한 ACID를 제공해도, DBA는 데이터와 감사 로그를 모두 수정할 수 있으므로 "기관을 신뢰한다"는 전제 위에서만 성립한다. 블록체인은 바로 이 전제를 제거하여, 아무도 신뢰하지 않아도 데이터의 정합성이 보장되는 구조를 만들었다. 이것이 블록체인의 유일하면서도 결정적인 가치이다.

따라서 실무 선택의 판단 기준은 "성능이 얼마나 필요한가"가 아니라 "신뢰할 중앙 주체가 존재하는가" 여야 한다. 신뢰할 기관이 존재한다면 블록체인은 TPS·비용·저장 효율 모든 면에서 DB보다 열등한 선택이다. 실제로 많은 블록체인 프로젝트가 실패한 이유는 기술적 결함이 아니라, 애초에 신뢰 문제가 존재하지 않는 영역에 블록체인을 적용했기 때문이다.

또한 반드시 고려해야 할 실무적 제약은 블록체인의 불변성이 개인정보보호법의 파기 의무 및 정정·삭제 요구권과 정면으로 충돌한다는 점이다. 삭제할 수 없다는 특성은 무결성 측면에서는 장점이지만, 법적 측면에서는 위법 상태를 영구화하는 치명적 결함이 된다. 따라서 개인정보 원문은 절대 온체인에 기록하지 않고, 해시값만 기록하는 오프체인 설계가 필수 원칙이다.

결론적으로 실무의 정답은 셋 중 하나를 선택하는 것이 아니라 계층적으로 결합하는 것이다. 대용량 원본은 오브젝트 스토리지에, 검색·트랜잭션이 필요한 정형 데이터는 DB에, 위·변조 방지가 필요한 증거값(해시)만 블록체인에 기록하는 하이브리드 아키텍처가 각 기술의 강점을 살리고 약점을 상쇄하는 최적 구조이다. 기술사 관점에서는 각 기술의 한계를 정확히 인식하고, 요구사항을 신뢰·성능·법규 준수의 세 축으로 분해하여 적재적소에 배치하는 설계 판단이 핵심 역량이라 할 수 있다.

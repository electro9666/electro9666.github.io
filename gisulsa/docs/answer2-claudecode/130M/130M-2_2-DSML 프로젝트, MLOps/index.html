DSML 프로젝트, MLOps

문제​

2.최근 데이터사이언스와 기계학습이 융합된 DSML(Data Science & MachineLearning) 프로젝트가 확산되고 있다.성공적인 DSML프로젝트를 수행하기위해아래 항목을 설명하시오.
1) DSML 프로젝트 수명주기
2) 기계학습 운영화(Machine Learning Operationalizations/Operations : MLops

Ⅰ. 개요​

1. DSML의 개념​

DSML(Data Science & Machine Learning) 은 데이터 사이언스(문제 정의·탐색·통계적 분석) 와 기계학습(모델 학습·예측) 을 융합하여, 데이터로부터 비즈니스 가치를 창출하는 일련의 프로젝트 활동을 의미한다.

   [**DSML 프로젝트의 특수성** — 전통 SW 개발과의 차이]

   ┌────────────┬──────────────────┬──────────────────────┐
   │   구분     │ **전통 SW 개발**  │ **DSML 프로젝트**     │
   ├────────────┼──────────────────┼──────────────────────┤
   │ 결과 예측  │ **결정론적**      │ **확률적·비결정적**   │
   │ 성공 보장  │ 요구사항 충족 시  │ **데이터 품질에 종속** │
   │            │ 완성 가능        │ (실패 가능성 내재)    │
   │ 산출물     │ 코드             │ **코드 + 데이터 + 모델**│
   │ 진행 방식  │ 순차적/반복적     │ **탐색적·실험적 순환** │
   │ 배포 후    │ 기능 안정         │ **성능 자연 저하(Drift)**│
   └────────────┴──────────────────┴──────────────────────┘

   ⇒ **"만들면 끝"이 아니라 "지속적으로 재학습·감시해야 하는" 시스템**
   ⇒ 이러한 특수성이 **MLOps 필요성의 근거**

2. DSML 프로젝트 실패 원인과 대응​

실패 원인대응 방향
비즈니스 문제 정의 부재 — "AI 도입" 자체가 목표수명주기 1단계(업무 이해) 강화, 성공지표(KPI) 사전 합의
데이터 품질·확보 실패데이터 거버넌스, 피처 스토어, 데이터 검증 자동화
PoC는 성공, 운영 전환 실패 (약 80% 모델이 배포되지 못함)MLOps 체계 구축 ← 본 문제의 핵심
배포 후 성능 저하 방치드리프트 모니터링 + 자동 재학습
재현 불가능(Reproducibility)데이터·코드·모델 버전 관리 및 실험 추적

Ⅱ. DSML 프로젝트 수명주기​

1. 수명주기 전체 구조 (CRISP-DM 기반 확장 모델)​

 ┌──────────────── **DSML 프로젝트 수명주기** ────────────────┐
 │                                                            │
 │   **① 비즈니스 이해**(Business Understanding)              │
 │        │  문제 정의 · 성공지표 · 타당성 검토               │
 │        ▼ ◀──────────────────────────┐                      │
 │   **② 데이터 이해**(Data Understanding)  │                 │
 │        │  수집 · 탐색(EDA) · 품질 진단  │                  │
 │        ▼ ◀──────────────┐            │                     │
 │   **③ 데이터 준비**(Data Preparation)   │  **탐색적 반복**  │
 │        │  정제 · 변환 · **피처 엔지니어링**│               │
 │        ▼                │            │                     │
 │   **④ 모델링**(Modeling)  │            │                    │
 │        │  알고리즘 선정 · 학습 · 튜닝 ─┘                    │
 │        ▼                                                   │
 │   **⑤ 평가**(Evaluation) ── 비즈니스 목표 미달 시 ──────────┘│
 │        │  성능 지표 · 비즈니스 가치 검증                    │
 │        ▼                                                   │
 │   **⑥ 배포**(Deployment) ── 서빙 · 통합                    │
 │        ▼                                                   │

 │        └──────────▶ ①/③ 으로 **순환(Feedback Loop)**       │
 └────────────────────────────────────────────────────────────┘
   ※ CRISP-DM(6단계)에 **⑦ 운영·모니터링**을 추가한 것이 DSML의 특징

3. 참조 방법론 비교​

방법론특징
CRISP-DM가장 널리 쓰이는 6단계 표준(업무이해–데이터이해–데이터준비–모델링–평가–배포), 반복적
SEMMASAS 제시 — Sample–Explore–Modify–Model–Assess (분석 기법 중심)
KDD학술적 프로세스 — 선택–전처리–변환–데이터마이닝–해석/평가
TDSP(Microsoft)CRISP-DM + 팀 협업·역할·산출물 템플릿 + DevOps 결합
MLOps 성숙도 모델수동(Level 0) → ML 파이프라인 자동화(Level 1) → CI/CD 자동화(Level 2)

Ⅲ. MLOps (기계학습 운영화)​

1. 개념 및 필요성​

MLOps(Machine Learning Operations) 는 DevOps 원칙을 기계학습에 적용하여, 모델의 개발–배포–운영–재학습 전 과정을 표준화·자동화하고 지속적으로 관리하는 문화·실천·기술 체계이다.

   [**MLOps의 구성 = 3개 영역의 교집합**]

              **Data Engineering**
                    ╱     ╲
                  ╱  **MLOps** ╲
                ╱             ╲
      **Machine Learning** ─── **DevOps**

   [**필요성 — "PoC의 함정"**]
   · 기업 ML 프로젝트의 **상당수가 운영 배포에 실패**
   · 노트북(Jupyter) 환경의 모델 → **운영 환경에서 재현 불가**
   · **학습/서빙 코드 불일치(Training-Serving Skew)**
   · 배포 후 **성능 저하를 인지하지 못한 채 방치**
   · 데이터·모델의 **버전 추적 불가** → 규제 대응·감사 불가
        ▼
   ⇒ **"모델을 만드는 것"에서 "모델을 지속 운영하는 것"으로 관점 전환**

2. MLOps vs DevOps​

구분DevOpsMLOps
관리 대상코드코드 + 데이터 + 모델(3중 자산)
버전 관리Git(소스)Git + DVC(데이터) + 모델 레지스트리
CI(지속 통합)코드 빌드·테스트코드 + 데이터 검증 + 모델 검증
CD(지속 배포)애플리케이션 배포모델 배포 + 파이프라인 배포
추가 개념-CT(Continuous Training, 지속 학습)
테스트단위·통합 테스트+ 데이터 스키마·분포 테스트, 모델 성능 임계 테스트, 공정성 테스트
성능 저하코드 변경 없으면 유지데이터 변화만으로 자연 저하(Drift)
주요 역할개발자·운영자+ 데이터 사이언티스트·ML 엔지니어·데이터 엔지니어

3. MLOps 파이프라인 아키텍처​

 ┌──────────────────── **MLOps 전체 파이프라인** ────────────────────┐
 │                                                                   │
 │  **[데이터 파이프라인]**                                          │
 │   원천 → 수집(ETL) → **데이터 검증**(스키마·분포)                 │
 │        → 전처리·피처 생성 → **Feature Store**(피처 저장·재사용)   │
 │                              │                                    │
 │  **[학습 파이프라인 — CT]**  ▼                                    │
 │   학습 데이터 → **모델 학습** → 하이퍼파라미터 튜닝               │
 │        → **모델 평가·검증**(기준 미달 시 배포 차단)               │
 │        → **Model Registry**(모델 버전·메타데이터·승인 상태)       │
 │                              │                                    │
 │  **[배포 파이프라인 — CI/CD]** ▼                                  │
 │   모델 패키징(컨테이너) → **스테이징 검증**                       │
 │        → **점진 배포**(Shadow → Canary → 전면)                    │
 │        → 서빙(**실시간 API / 배치 / 엣지**)                       │
 │                              │                                    │
 │  **[모니터링 & 피드백]**     ▼                                    │
 │   · 예측 성능(Accuracy·AUC) · **데이터 드리프트** · **개념 드리프트**│
 │   · 지연시간·자원·오류율 · 공정성·편향 지표                       │
 │        │                                                          │
 │        └──▶ **임계치 초과 시 재학습 트리거** ──▶ 학습 파이프라인 │
 │             (**Closed-Loop 자동화**)                              │
 │                                                                   │
 │  **[공통 기반]** 실험 추적 · 메타데이터 저장소 · 아티팩트 관리     │
 │              · 데이터/모델 계보(Lineage) · 거버넌스·감사 로그      │
 └───────────────────────────────────────────────────────────────────┘

4. MLOps 핵심 구성요소​

구성요소역할대표 도구
버전 관리코드·데이터·모델의 3중 버전 관리 → 재현성 확보Git, DVC, LakeFS
실험 추적(Experiment Tracking)하이퍼파라미터·지표·아티팩트 기록·비교MLflow, W&B, Neptune
Feature Store피처의 중앙 저장·재사용·학습/서빙 일관성 보장Feast, Tecton, Hopsworks
파이프라인 오케스트레이션워크플로우 정의·스케줄·의존성 관리Kubeflow Pipelines, Airflow, Argo
모델 레지스트리모델 버전·단계(Staging/Production)·승인 관리MLflow Registry, SageMaker
모델 서빙실시간/배치 추론 제공, 자동 확장KServe, TF Serving, Triton, BentoML
모니터링성능·드리프트·품질·자원 감시Evidently AI, Prometheus+Grafana, WhyLabs
인프라 자동화컨테이너·오케스트레이션·IaCDocker, Kubernetes, Terraform
CI/CD코드·모델 자동 빌드·테스트·배포Jenkins, GitHub Actions, GitLab CI

5. 드리프트(Drift) 관리 — MLOps의 핵심 과제​

유형정의예시탐지 방법
데이터 드리프트
(Data/Covariate Drift)		입력 데이터의 분포 변화 P(X) 변화신규 고객층 유입으로 연령 분포 변화PSI(Population Stability Index), KS 검정, KL Divergence
개념 드리프트
(Concept Drift)		입력–출력 관계 변화 P(Y|X) 변화코로나로 소비 패턴 자체가 변화실제 정답 수집 후 성능 지표 추적
레이블 드리프트출력 분포 P(Y) 변화불량률 자체가 상승예측 분포 모니터링
학습-서빙 편향
(Training-Serving Skew)		학습 시와 서빙 시 전처리 로직 불일치학습은 Python, 서빙은 Java로 재구현Feature Store로 로직 단일화
   [**재학습 전략**]
   · **주기 기반**(Scheduled) : 매일/매주 정기 재학습 — 단순, 낭비 가능
   · **성능 기반**(Performance-triggered) : 지표가 임계치 이하로 하락 시
   · **드리프트 기반**(Drift-triggered) : PSI > 0.2 등 분포 변화 감지 시
   · **데이터량 기반** : 신규 데이터 N건 누적 시
   ⇒ 실무는 **드리프트 탐지 + 성능 임계 + 최소 주기**를 **복합 적용**

6. MLOps 성숙도 모델​

수준특징상태
Level 0 : 수동 프로세스노트북 기반 수동 학습·배포, 스크립트 전달배포 주기 수개월, 재현 불가
Level 1 : ML 파이프라인 자동화학습 파이프라인 자동화, CT(지속 학습) 도입, Feature Store자동 재학습 가능
Level 2 : CI/CD 파이프라인 자동화파이프라인 자체를 코드로 관리, 자동 빌드·테스트·배포, 완전 자동 재학습·롤백실험→운영 수시간 내 반영

Ⅳ. DSML 수명주기와 MLOps의 연계​

   [**수명주기 단계별 MLOps 적용**]

   ① 비즈니스 이해 ─── 성공지표를 **모니터링 지표로 연결**
   ② 데이터 이해   ─── **데이터 검증 규칙** 정의(스키마·분포)
   ③ 데이터 준비   ─── **Feature Store** 등록, 전처리 **파이프라인 코드화**
   ④ 모델링        ─── **실험 추적**(MLflow), 데이터·코드 **버전 고정**
   ⑤ 평가          ─── **자동 검증 게이트**(성능 임계 미달 시 배포 차단)
   ⑥ 배포          ─── **CI/CD**, 컨테이너, **Canary/Shadow 배포**
   ⑦ 운영·모니터링 ─── **드리프트 탐지 → 자동 재학습(CT) → ③으로 순환**

   ⇒ **MLOps는 수명주기 전 단계를 관통하는 "실행 기반(Enabler)"**
기대효과내용
배포 리드타임 단축수개월 → 수일~수시간(파이프라인 자동화)
재현성·감사 대응데이터·코드·모델 버전 추적 → AI 규제(EU AI Act)·금융 감독 대응
모델 성능 유지드리프트 조기 탐지·자동 재학습 → 비즈니스 손실 예방
협업 효율DS·ML 엔지니어·운영 간 역할·인터페이스 표준화
리스크 관리자동 검증 게이트·롤백으로 불량 모델의 운영 유입 차단

Ⅴ. 결론​

DSML 프로젝트의 수명주기는 표면적으로는 CRISP-DM의 6단계를 따르지만, 결정적 차이는 "⑦ 운영·모니터링 단계가 존재하며, 이 단계가 다시 데이터 준비·모델링으로 순환한다" 는 점이다. 전통 SW는 배포 후 기능이 안정적으로 유지되지만, ML 모델은 코드를 전혀 변경하지 않아도 현실 데이터가 변하면 성능이 자연 저하된다. 이 본질적 차이가 DSML 프로젝트를 일회성 구축이 아닌 지속적 운영 체계로 만들 것을 요구한다.

DSML 프로젝트 실패의 대다수는 모델 성능이 부족해서가 아니라, PoC 단계의 모델이 운영 환경으로 전환되지 못하기 때문이다. 노트북에서 검증된 모델이 운영으로 넘어가지 못하는 이유는 재현 불가능성, 학습-서빙 로직 불일치, 배포·모니터링 체계 부재이며, MLOps는 정확히 이 간극을 메우는 실행 기반이다. 즉 MLOps는 도구의 문제가 아니라 "모델을 소프트웨어 자산으로 취급하는 공학적 규율" 의 문제이다.

실무 도입 시 권장하는 접근은 점진적 성숙도 향상이다. 처음부터 Level 2의 완전 자동화를 목표로 하면 과도한 투자와 복잡도로 실패하기 쉬우므로, ① 실험 추적과 데이터·모델 버전 관리(재현성 확보) → ② 학습 파이프라인 자동화와 Feature Store 도입(학습-서빙 일관성) → ③ 드리프트 모니터링과 자동 재학습(CT) → ④ 파이프라인 CI/CD 완전 자동화 순으로 단계적으로 확장하는 것이 현실적이다.

특히 강조할 점은 모니터링의 우선순위이다. 자동 재학습보다 먼저 필요한 것은 "모델이 지금 잘 작동하고 있는지 알 수 있는 능력" 이다. 성능 저하를 인지하지 못한 채 운영되는 모델은 잘못된 의사결정을 지속적으로 양산하므로, 자동화 수준이 낮더라도 드리프트·성능 모니터링 대시보드는 최우선으로 구축해야 한다.

마지막으로, 생성형 AI의 확산에 따라 MLOps는 LLMOps로 확장되고 있다. 프롬프트 버전 관리, RAG 파이프라인의 검색 품질 평가, 환각(Hallucination) 모니터링, 토큰 비용 관리, 가드레일 등 새로운 관리 요소가 추가되었으나, "재현성 확보 – 자동화 – 지속 모니터링" 이라는 MLOps의 근본 원리는 동일하게 적용된다. 따라서 조직은 지금 구축하는 MLOps 체계를 향후 LLMOps로 확장 가능한 형태로 설계하는 것이 바람직하다.

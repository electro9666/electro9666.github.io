요구사항 품질속성, 개발 프로세스

문제​

4.IT프로젝트를 성공적으로 수행하기 위해 요구사항의 체계적인 관리와 문서화가매우중요하다.요구사항에 대하여 다음을 설명하시오.
1) 소프트웨어(SW) 요구사항 품질속성
2) 요구사항 도출기법
3) 요구사항 개발 프로세스

Ⅰ. 개요​

1. 요구사항의 개념과 중요성​

요구사항(Requirement) 은 사용자가 문제를 해결하거나 목적을 달성하기 위해 필요로 하는 조건이나 능력, 또는 시스템이 계약·표준·명세를 만족하기 위해 갖추어야 할 조건이나 능력(IEEE 610.12)이다.

   [**요구사항 결함의 파급 효과 — 1:10:100 법칙**]

   결함 수정 비용 ▲
                 │                                    ████ **운영**
                 │                                    ████ (100~1000배)
                 │                        ████ **시험**
                 │             ████ **구현**  (10~50배)
                 │      ████ **설계**
                 │ ██ **요구**  (5배)
                 │ (1배)
                 └─────────────────────────────────▶ 개발 단계

   ⇒ **요구단계에서 1의 비용으로 고칠 결함을 운영 단계에서는 100배**
   ⇒ 프로젝트 실패 원인 조사에서 **"불완전·부정확한 요구사항"이 최상위**
관점요구사항의 역할
계약발주자–수행자 간 범위·대가·검수의 법적 기준선(Baseline)
설계아키텍처·상세설계의 입력(Input)
시험인수시험(UAT) 케이스의 근거
관리변경 통제·일정·원가 산정의 기준
소통이해관계자 간 합의된 단일 진실 원천(Single Source of Truth)

2. 요구공학(Requirements Engineering) 체계​

 ┌──────────────── **요구공학 전체 체계** ────────────────┐
 │                                                        │
 │  **[A] 요구사항 개발**(Development)  ← 문제 3)         │
 │      **도출 → 분석 → 명세 → 확인·검증**                │
 │      (Elicitation → Analysis → Specification →         │
 │                              Validation)               │
 │                          │                             │
 │                          ▼ **기준선(Baseline) 설정**    │
 │                                                        │
 │  **[B] 요구사항 관리**(Management)                     │
 │      · 변경 통제(CCB) · **추적성 관리(RTM)**            │
 │      · 형상 관리 · 상태 추적 · 영향 분석               │
 │                                                        │
 │  ※ **개발은 "만드는 것", 관리는 "유지하는 것"**         │
 │    (표준 : **ISO/IEC/IEEE 29148**, IEEE 830, SWEBOK)   │
 └────────────────────────────────────────────────────────┘

Ⅱ. 소프트웨어 요구사항 품질속성​

1. 요구사항의 분류 (품질속성의 대상)​

   [**요구사항의 분류**]

   **① 기능 요구사항**(Functional Requirements)
        "시스템이 **무엇을 해야 하는가**"
        · 업무 기능, 입력–처리–출력, 업무 규칙, 예외 처리

   **② 비기능 요구사항**(Non-Functional Requirements)
        "시스템이 **어떻게 동작해야 하는가**" = **품질 요구사항**
        · **성능·가용성·보안·사용성·확장성·유지보수성·이식성**
        ⇒ 흔히 간과되나 **아키텍처를 결정**하는 핵심 요소

   **③ 제약사항**(Constraints)
        · 법·규제, 표준, 기술 스택, 예산·일정

   ⚠ **주의** : 아래 "품질속성"은 두 가지 의미로 쓰인다
     ① **요구사항 문서(명세) 자체가 갖추어야 할 품질** ← 본 문항의 핵심
     ② **시스템의 품질 요구사항**(비기능 요구, ISO 25010)

2. 개별 요구사항의 품질속성 (ISO/IEC/IEEE 29148 기준)​

품질속성정의위반 예시 → 개선
① 필요성
(Necessary)		이해관계자의 실제 요구에서 비롯되어야 하며, 없으면 목표 달성 불가사용하지 않을 기능(Gold Plating) 제거
② 명확성·비모호성
(Unambiguous)		해석이 하나뿐이어야 함✕ "빠르게 응답해야 한다"
○ "3초 이내 응답(95백분위)"
③ 완전성
(Complete)		필요한 정보를 모두 포함, TBD 없음✕ "오류 시 처리한다"
○ "오류 코드별 메시지·재시도 3회·로그 기록"
④ 일관성
(Consistent)		다른 요구사항과 상충하지 않음(용어·값·규칙)✕ A항목 "보관 3년" / B항목 "보관 5년"
⑤ 검증 가능성
(Verifiable / Testable)		시험·검사·시연·분석으로 충족 여부 판정 가능✕ "사용자 친화적일 것"
○ "신규 사용자가 교육 없이 30분 내 주문 완료"
⑥ 추적 가능성
(Traceable)		고유 ID로 상위 요구·설계·코드·시험과 양방향 추적요구사항 ID 부여 및 RTM 관리
⑦ 실현 가능성
(Feasible)		기술·일정·예산 제약 내에서 구현 가능✕ "장애를 100% 예방"
⑧ 수정 용이성
(Modifiable)		중복 제거, 구조화 → 변경 시 파급 최소동일 규칙이 여러 곳에 중복 기술되지 않도록
⑨ 우선순위 부여
(Ranked / Prioritized)		중요도·안정성 기준 등급화MoSCoW(Must/Should/Could/Won't), Kano 모델
⑩ 원자성·단일성
(Singular / Atomic)		하나의 요구사항에 하나의 내용만✕ "로그인하고 동시에 알림을 발송한다" → 2건으로 분리
⑪ 적절성·구현 중립
(Appropriate)		What만 기술, How(설계·구현 방식) 는 배제✕ "Redis 캐시를 사용하여…" → 대안 차단
⑫ 정확성(Correct)실제 요구를 정확히 반영현업 검토·확인 필요

3. 요구사항 집합(문서 전체)의 품질속성​

속성내용
집합의 완전성필요한 모든 요구사항이 빠짐없이 포함(기능·비기능·제약·인터페이스)
집합의 일관성요구사항 상호 간 충돌 없음
경계 명확성(Bounded)범위(Scope)와 제외 범위가 명확히 구분
이해 가능성(Comprehensible)이해관계자가 동일하게 이해 가능
구조화(Structured)계층적·논리적 구성, 분류 체계

4. 시스템 품질속성 (비기능 요구사항 — ISO/IEC 25010)​

품질 특성부특성요구사항 기술 예
기능 적합성완전성·정확성·적절성업무 규칙 100% 반영
성능 효율성시간 반응성·자원 효율성·용량동시 사용자 1,000명, 응답 3초 이내, TPS 500
호환성공존성·상호운용성표준 API(REST/JSON) 연계
사용성학습 용이성·운영 용이성·접근성KWCAG 2.1 AA 준수, 3클릭 이내 주문
신뢰성가용성·결함 허용성·회복성가동률 99.9%, RTO 4시간 / RPO 15분
보안성기밀성·무결성·부인방지·인증개인정보 암호화, MFA, 접속기록 2년 보관
유지보수성모듈성·재사용성·시험 용이성순환복잡도 10 이하, 커버리지 80% 이상
이식성적응성·설치 용이성·대체성주요 브라우저·OS 지원, 컨테이너 배포

Ⅲ. 요구사항 도출 기법​

1. 도출(Elicitation)의 개념과 어려움​

   [**요구사항 도출이 어려운 이유**]

   · **사용자가 자신의 요구를 정확히 모른다**
        "보기 전에는 원하는 것을 모른다"(**IKIWISI** — I'll Know It When I See It)
   · **암묵지(Tacit Knowledge)** — 너무 당연해서 말하지 않는 요구
   · **이해관계자 간 요구 충돌**(현업 vs IT vs 경영진)
   · **용어의 불일치** — 같은 말, 다른 의미
   · **현행 업무의 관성** — 개선이 아닌 AS-IS 재현 요구
        ▼
   ⇒ **단일 기법으로는 불충분** → **복수 기법의 조합 사용이 원칙**

2. 주요 도출 기법​

가. 대화·조사 기반 기법​

기법내용장점단점·유의점
인터뷰
(Interview)		이해관계자와 1:1 면담 — 구조적/비구조적/반구조적심층 요구·배경 파악, 즉시 확인 가능시간 소요, 면담자 역량에 좌우, 암묵지 누락
설문조사
(Questionnaire)		다수 대상 표준화 질문대규모 의견 수렴, 정량화 용이심층 파악 불가, 응답률·질문 설계 의존
워크숍
(JAD/RAD Workshop)		이해관계자 집중 합숙 토론신속한 합의, 부서 간 충돌 조기 해소일정 조율 어려움, 강한 목소리 편향
브레인스토밍자유로운 아이디어 발산창의적 요구·혁신 아이디어 도출발산만 하고 수렴 실패 위험
델파이(Delphi)전문가 익명 반복 설문 → 의견 수렴권위 편향 제거, 합의 도출시간 소요
포커스 그룹소수 집단의 토론 관찰사용자 인식·태도 파악대표성 한계

나. 관찰·분석 기반 기법​

기법내용장점단점·유의점
관찰(Observation)
·민족지학(Ethnography)		실제 업무 현장을 직접 관찰암묵지·비공식 절차 발견(말로 설명 못 하는 요구)시간 소요, 관찰자 효과(평소와 다르게 행동)
문서 분석
(Document Analysis)		기존 매뉴얼·규정·법령·현행 시스템 산출물 분석현행 업무 이해, 누락 방지문서와 실제 업무의 괴리 가능
현행 시스템 분석AS-IS 기능·데이터·인터페이스 분석이관 범위·연계 파악AS-IS 답습 위험
벤치마킹
(Benchmarking)		타사·선진 사례 비교 분석개선 기회·수준 목표 설정조직 특성 미반영 위험
비즈니스 프로세스 분석BPMN·프로세스 맵으로 업무 흐름 도해프로세스 관점의 누락 발견-

다. 모델·시연 기반 기법​

기법내용장점단점·유의점
프로토타이핑
(Prototyping)		화면·화면흐름 시제품 제작 후 피드백IKIWISI 문제 해결, 요구 구체화에 매우 효과적프로토타입을 완성품으로 오인, 과도한 UI 집착
유스케이스
(Use Case)		액터–시스템 상호작용 시나리오 기술사용자 관점 기능 도출, 시험 케이스 연계비기능 요구 표현 곤란
사용자 스토리
(User Story)		"As a ~, I want ~, So that ~" + 인수 기준애자일 적합, 가치 중심, 간결상세 부족 → 대화(Conversation) 전제
시나리오·스토리보드업무 흐름을 서사적으로 표현이해관계자 소통 용이-
모델링(UML·DFD·ERD)구조·흐름·데이터 모델로 표현정합성·누락 검증전문성 필요
페르소나·고객 여정 지도가상의 사용자 유형 및 경험 여정사용자 중심 요구 도출(UX)-

라. 기타 기법​

기법내용
역할극(Role Playing)담당자 역할을 수행해보며 요구 발견
CRC 카드클래스–책임–협력자 카드로 개념 도출
QFD(품질기능전개)고객 요구(VOC)를 기술 특성으로 변환(품질의 집)
데이터 기반 도출로그·이용 데이터 분석으로 실제 사용 패턴 파악
크라우드소싱·VOC 분석고객센터 문의·리뷰·SNS 분석

3. 기법 선택 가이드​

상황권장 기법
이해관계자가 소수·전문적인터뷰 + 문서 분석
다수 사용자·의견 수렴 필요설문 + 포커스 그룹
부서 간 이견이 큼워크숍(JAD) — 한자리에서 합의
사용자가 요구를 설명하지 못함프로토타이핑 + 관찰
현장 업무가 복잡·암묵적관찰(민족지학) + 문서 분석
신규 서비스·전례 없음브레인스토밍 + 벤치마킹 + 프로토타이핑
애자일 프로젝트사용자 스토리 + 스프린트 리뷰 피드백

원칙 : 어떤 단일 기법도 완전하지 않다 → 최소 3가지 이상 조합하여 교차 검증(Triangulation) 해야 누락과 왜곡을 줄일 수 있다.

2. 단계별 상세​

가. ① 요구사항 도출 (Elicitation)​

활동내용
이해관계자 식별사용자·발주자·운영자·규제기관·간접 이해관계자까지 누락 없이 식별, 영향력·관심도 분석
도출 계획 수립대상·기법·일정 계획, 인터뷰 질문지 준비
도출 활동 수행인터뷰·워크숍·관찰·프로토타이핑 등 복수 기법 병행
원시 요구 수집·기록발언 그대로 기록(해석 배제), 근거·출처 기록
핵심 성공요인· 현업 참여 확보(형식적 참여 시 실패)
· 암묵지 발굴(관찰 병행)
· 이해관계자 누락 방지
산출물이해관계자 목록, 인터뷰 결과서, 요구사항 초안 목록

나. ② 요구사항 분석 (Analysis)​

활동내용
분류·구조화기능/비기능/제약으로 분류, 계층적 구조화(기능 분해도)
중복·누락 식별유사 요구 통합, 빠진 영역 도출
충돌 해결(Negotiation)이해관계자 간 상충 요구 협상·조정 → 합의 도출
우선순위 결정MoSCoW, Kano 모델, AHP, 가치 대비 비용(비즈니스 가치 × 리스크)
실현 가능성 분석기술·일정·비용 타당성, 대안 검토
모델링유스케이스 다이어그램, DFD, 상태도, 개념 데이터 모델(ERD) → 정합성 검증
영향 분석기존 시스템·업무에 미치는 영향
산출물분석 모델, 우선순위가 부여된 요구사항 목록, 타당성 분석서

다. ③ 요구사항 명세 (Specification)​

활동내용
명세서 작성SRS(IEEE 29148) 또는 공공 표준(SFR·PER·SIR·DAR·SER·QUR·COR·PMR·PSR·TER) 형식
요구사항 ID 부여유형별 체계적 ID → 추적성의 기반
속성 기술정의·세부내용·우선순위·인수 기준·검증 방법·출처·관련 요구
모델 병행텍스트 + 유스케이스·화면 흐름·데이터 모델
명세 기법· 정형 명세(Z, VDM — 수학적, 안전 필수 시스템)
· 비정형 명세(자연어) ← 일반적
· 준정형 명세(UML·표)
주의사항What만 기술, How는 배제, 모호어 금지("적절히·신속히·사용자 친화적")
산출물요구사항명세서(SRS), 요구사항 추적표(RTM), 용어집

라. ④ 요구사항 확인·검증 (Validation & Verification)​

   [**Validation vs Verification** — 혼동 주의]

   **Validation(확인)** : "**Are we building the RIGHT system?**"
        · **고객이 원하는 것이 맞는가?**
        · 주체 : **고객·사용자**
        · 기법 : 요구사항 검토회의, **프로토타입 시연**, 인수 기준 합의

   **Verification(검증)** : "**Are we building the system RIGHT?**"
        · 요구사항이 **품질속성(명확·완전·일관·검증가능)을 갖추었나?**
        · 주체 : **개발팀·품질보증(QA)**
        · 기법 : **인스펙션·워크스루·체크리스트 검토·정형 검증**
활동내용
검토(Review)· 동료 검토(Peer Review)
· 워크스루(작성자 주도 설명·의견 수렴)
· 인스펙션(Fagan — 공식 절차·역할 지정, 가장 효과적)
체크리스트 검증품질속성(명확성·완전성·일관성·검증가능성) 항목별 점검
프로토타입 검증시제품으로 사용자 확인 → 오해 조기 발견
테스트 케이스 도출 검증인수시험 케이스를 만들 수 있으면 검증 가능한 요구사항 ← 실용적 판별법
모델 검증모델 간 일관성·완전성 검사(CASE 도구)
승인·기준선 설정이해관계자 공식 승인 → Baseline 확정 → 이후 변경은 변경통제 절차
산출물검토 보고서, 결함 목록·조치 결과, 요구사항 확정 확인서

3. 요구사항 관리 (개발 이후 지속 활동)​

활동내용
변경 통제변경요청(CR) → 영향 분석(일정·비용·품질) → CCB 심의 → 승인/반려 → 반영·통보
추적성 관리(RTM)요구사항 ↔ 설계 ↔ 코드 ↔ 시험 케이스의 양방향 추적 → 누락·과잉 개발 방지, 변경 영향 분석
형상 관리요구사항 문서의 버전 관리, 기준선 이력
상태 추적제안 → 승인 → 구현 중 → 검증 완료 → 인도
공공사업 제도과업심의위원회 — 요구사항 변경의 적정성과 추가 대가 심의

4. 개발 방법론별 요구사항 프로세스 비교​

구분폭포수(Waterfall)애자일(Agile)
시점착수 시 전체 요구 확정점진적·지속적 상세화
문서SRS 상세 문서제품 백로그·사용자 스토리
변경 관점변경 = 통제 대상(비용 발생)변경 = 환영(경쟁 우위)
검증단계 말 검토·인수시험스프린트 리뷰(2~4주마다 실물 확인)
인수 기준명세서의 검증 기준Given-When-Then(BDD), DoD
적합 상황요구 안정적, 규제·계약 엄격(공공·금융 기간계)요구 불확실, 시장 변화 빠름
공통점요구사항의 명확성·검증 가능성·추적성은 방법론과 무관하게 필수

Ⅴ. 실무 고려사항​

고려사항내용
① 비기능 요구사항의 정량화성능·가용성·보안은 아키텍처를 결정하지만 흔히 누락·모호하게 기술됨 → 측정 조건과 함께 수치로 명시("동시 500명, 부하 80% 상황에서 3초 이내")
② 검증 가능성이 최우선 기준"인수시험 케이스를 작성할 수 있는가"가 요구사항 품질의 실용적 판별 기준. 판정할 수 없는 문장은 요구사항이 아님
③ 추적성 확보(RTM)요구사항 ↔ 설계 ↔ 코드 ↔ 시험의 연결 → 변경 영향 분석·누락 방지·검수 근거
④ 우선순위 관리모든 요구를 Must로 두면 우선순위가 없는 것과 같음 → MoSCoW 비율 관리(Must 60% 이내 권장)
⑤ 요구사항 크리프(Scope Creep) 통제기준선 확정 후 변경통제 절차 없는 요구 추가 차단, 공공은 과업심의위원회 활용
⑥ 현업 참여의 실질화형식적 참여 시 UAT 단계에서 대량 변경 요구 발생 → 도출·검토 단계 의무 참여 및 승인 서명
⑦ 조기 검증(인스펙션)요구단계 결함 제거 비용 = 운영 단계의 1/100 → 인스펙션 투자 대비 효과 최대
⑧ 도구 활용요구사항 관리 도구(Jira·DOORS·Polarion)로 추적성·변경 이력 자동화

Ⅵ. 결론​

IT 프로젝트 실패 원인 조사에서 일관되게 최상위를 차지하는 것은 기술적 난이도나 인력 부족이 아니라 "불완전하고 부정확한 요구사항" 이다. 요구단계의 결함은 설계·구현·시험을 거치며 증폭되어 운영 단계에서는 100배의 수정 비용을 발생시키므로, 요구공학은 프로젝트 관리의 여러 활동 중 하나가 아니라 투자 대비 효과가 가장 큰 활동이다.

요구사항 품질속성 중 실무적으로 가장 중요한 것은 검증 가능성(Verifiable) 이다. "사용자가 편리하게 사용할 수 있어야 한다"는 문장은 검수 시점에 누구도 합격/불합격을 판정할 수 없으므로 요구사항으로서 무의미하다. 따라서 모든 요구사항을 "인수시험 케이스를 작성할 수 있는가" 라는 기준으로 점검하고, 정성적 표현을 측정 조건이 명시된 정량 기준으로 환산하는 것이 요구사항 품질 확보의 핵심 실천이다. 아울러 추적 가능성(Traceable) 은 변경 영향 분석과 검수 근거를 제공하므로, 요구사항 ID 부여와 RTM 관리는 반드시 병행되어야 한다.

요구사항 도출에서 반드시 인식해야 할 전제는 "사용자는 자신이 무엇을 원하는지 정확히 모른다(IKIWISI)" 는 것이다. 인터뷰만으로는 사용자가 말로 표현하지 못하는 암묵지와 비공식 절차를 절대 발견할 수 없으므로, 관찰(현장 방문)과 프로토타이핑을 반드시 병행해야 한다. 실무에서 UAT 단계에 "이게 아니었다"는 반응이 나오는 것은 대부분 도출 단계에서 프로토타입으로 시각적 확인을 거치지 않았기 때문이다. 따라서 최소 3가지 이상의 기법을 조합하여 교차 검증하는 것이 원칙이다.

요구사항 개발 프로세스는 도출–분석–명세–확인/검증의 4단계로 구성되지만, 선형이 아니라 반복적(Iterative) 으로 수행되어야 한다. 명세 단계에서 모호함이 발견되면 도출로 돌아가고, 검증 단계에서 충돌이 발견되면 분석으로 돌아가는 순환이 정상적인 과정이다. 특히 마지막 단계에서 Validation(올바른 요구인가 — 고객 관점)과 Verification(올바르게 기술했는가 — 품질 관점)을 구분하여 각각 수행해야 하며, 이 중 어느 하나라도 누락되면 "잘 쓰였지만 틀린 요구사항" 또는 "맞지만 검증 불가능한 요구사항" 이 기준선으로 확정되는 문제가 발생한다.

마지막으로, 애자일 환경에서도 요구공학의 본질은 변하지 않는다. 애자일은 문서를 줄이는 것이지 요구사항의 명확성을 포기하는 것이 아니며, 오히려 사용자 스토리의 인수 기준(Given-When-Then) 이라는 형태로 검증 가능성을 더욱 엄격히 요구한다. 결국 방법론과 무관하게 명확성·검증 가능성·추적성이라는 세 가지 속성이 요구사항 품질의 본질이며, 이를 확보하는 조직적 규율이 프로젝트 성공의 전제 조건이라 할 수 있다.

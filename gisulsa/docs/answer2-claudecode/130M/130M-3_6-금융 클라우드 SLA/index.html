금융 클라우드 SLA

문제​

6.금융 클라우드 서비스를 받는 금융회사의 데이터는 가장 중요한 자산이며 민감정보를다룬다.금융 클라우드 SLA(Service Level Agreement)에 대하여 설명하시오.
1) SLA의 개념
2) 클라우드 SLA 가이드
3) 금융 클라우드 SLA 가이드

Ⅰ. 개요​

1. 금융권 클라우드 도입과 SLA의 필요성​

금융회사의 클라우드 이용은 "IT 자원의 외부 위탁"이자 동시에 "금융 데이터의 외부 이전" 이므로, 서비스 품질과 책임 범위를 계약으로 명확히 규정하지 않으면 장애·유출 발생 시 책임 공백이 발생한다.

   [**금융 클라우드의 특수성**]

   일반 기업 클라우드            금융 클라우드
   · 장애 = 서비스 중단          · 장애 = **금융거래 중단 → 국민 경제 영향**
   · 데이터 유출 = 기업 피해     · 유출 = **고유식별정보·신용정보 대량 유출**
   · 자율적 판단                 · **감독기관 규제 대상**(금융위·금감원)
   · 계약 자유                   · **전자금융감독규정 등 법정 요건 준수 의무**
        ▼
   ⇒ **CSP는 표준 약관(Take it or Leave it)을 제시**하는데,
     금융회사는 **감독규정상 요구사항을 계약에 반영**해야 함
     ⇒ **협상력 비대칭 문제** → **금융 클라우드 SLA 가이드**의 필요성

2. 제도적 배경​

시기내용
2016년전자금융감독규정 개정 — 비중요 업무에 한해 클라우드 이용 허용
2019년개정 시행 — 중요정보 처리 시스템(개인신용정보 포함) 까지 클라우드 이용 허용, 「금융분야 클라우드컴퓨팅서비스 이용 가이드」 발간
2022~2023년규제 합리화 — 중요도 평가 절차 간소화, 망분리 규제 개선 논의, 이용 절차 완화
관련 기준전자금융거래법·전자금융감독규정, 신용정보법, 개인정보보호법, 금융보안원 「금융분야 클라우드 이용 가이드」, 과기정통부 「클라우드 서비스 수준 협약(SLA) 권고 가이드」

Ⅱ. SLA의 개념​

1. 정의 및 구성​

구분내용
정의SLA(Service Level Agreement, 서비스 수준 협약) 는 서비스 제공자와 이용자 간에 제공할 서비스의 수준(품질)을 정량적 지표로 정의하고, 측정·보고 방법과 미달 시 조치(배상·감액) 를 명시한 계약 문서
목적① 서비스 품질에 대한 객관적 기준 확립
② 분쟁 예방 및 책임 범위 명확화
③ 지속적 품질 개선 유인 제공
④ 이용자의 서비스 선택·비교 기준 제공
관련 개념SLO(Service Level Objective, 목표치) — SLA 안에 담기는 개별 목표
SLI(Service Level Indicator, 측정 지표) — 실제 측정값
SLM(Service Level Management) — SLA를 관리·개선하는 프로세스
OLA(Operational Level Agreement) — 조직 내부 부서 간 협약
UC(Underpinning Contract) — 하위 공급자와의 계약
   [**SLA 관련 개념의 관계**]

   **SLI**(지표)     "가동률을 어떻게 측정하는가" (측정 방법)
      ▲                    예) 월간 가용 시간 / 총 시간
      │
   **SLO**(목표)     "가동률 99.9% 이상" (달성 목표)
      ▲
      │
   **SLA**(협약)     "SLO 미달 시 이용료의 10% 감액" (계약·제재)
      ▲
      │
   **SLM**(관리)     측정 → 보고 → 검토 → 개선 (**PDCA 순환**)

   ※ **SLA = SLO + 측정방법 + 보고체계 + 미달 시 조치(배상)**

2. SLA의 구성 요소​

구성 요소내용
서비스 범위대상 서비스·기능, 제외 범위(Out of Scope), 서비스 시간대
당사자의 역할·책임제공자·이용자 각각의 의무, 책임 공유 모델(Shared Responsibility)
서비스 수준 지표·목표가용성·성능·장애 대응·지원 등의 정량 지표와 목표치
측정 방법·주기측정 도구·산식·측정 시점, 보고 주기(월간·분기)
보고 및 검토 절차정기 보고서, 서비스 검토 회의, 개선 계획 수립
미달 시 조치서비스 크레딧(요금 감액), 손해배상, 누적 미달 시 계약 해지권
예외 조항계획된 정기점검, 불가항력(Force Majeure), 이용자 귀책
변경·해지 절차SLA 개정 절차, 계약 종료 시 데이터 반환·삭제

3. SLA 지표 예시​

분류지표산식·예시
가용성가동률(Availability)(총 시간 − 장애 시간) / 총 시간 × 100 → 99.9% / 99.95% / 99.99%
성능응답시간, 처리량(TPS), 지연시간평균 응답 3초 이내(95 백분위)
장애 대응MTTR(평균 복구 시간), MTBF장애 인지 후 1시간 이내 복구
지원최초 응답 시간, 해결 시간등급별 P1: 15분 이내 응답
데이터RTO / RPORTO 4시간, RPO 15분
보안취약점 조치 기간, 침해 통지 시간인지 후 24시간 내 통보
   [**가동률과 연간 허용 다운타임**]

   ┌──────────┬────────────┬────────────┬────────────┐
   │ **가동률** │ **연간**    │ **월간**    │ 적용 예시   │
   ├──────────┼────────────┼────────────┼────────────┤
   │ 99%      │ 3.65일      │ 7.2시간     │ 내부 테스트 │
   │ 99.9%    │ 8.76시간    │ 43.2분      │ 일반 업무   │
   │ **99.95%** │ 4.38시간   │ 21.6분      │ **일반 CSP 표준**│
   │ **99.99%** │ **52.6분** │ 4.32분      │ **금융 기간계**│
   │ 99.999%  │ 5.26분      │ 25.9초      │ 통신·결제망 │
   └──────────┴────────────┴────────────┴────────────┘
   ⇒ **99.9%와 99.99%는 0.09%p 차이지만 연간 8시간 vs 53분의 차이**

Ⅲ. 클라우드 SLA 가이드 (일반)​

1. 개요 및 필요성​

구분내용
근거클라우드컴퓨팅법(클라우드컴퓨팅 발전 및 이용자 보호에 관한 법률) 제27조 — 이용자 보호를 위한 서비스 수준 협약 권고, 과기정통부 「클라우드 서비스 수준 협약(SLA) 권고 가이드」
필요성· CSP의 일방적 표준약관 → 이용자 협상력 열위
· 가용성 산정 기준·보상 범위가 불명확
· 책임 소재 모호(공동 책임 모델에 대한 이해 부족)
· 데이터 반환·종료(Exit) 조항 미흡 → 벤더 종속(Lock-in)

2. 클라우드 SLA의 주요 항목​

 ┌──────────── **클라우드 SLA 권고 항목 체계** ────────────┐
 │                                                         │
 │ **① 서비스 성능·품질**                                  │
 │    가용성(가동률) · 응답시간 · 처리 성능 · 확장성        │
 │                                                         │
 │ **② 서비스 지원**                                       │
 │    기술지원 시간(24×365) · 장애 접수·응답 시간           │
 │    · 등급별 대응(SLA Tier) · 담당자 지정                 │
 │                                                         │
 │ **③ 데이터 관리**                                       │
 │    **데이터 소유권(이용자에게 귀속)** · 저장 위치(리전)   │
 │    · **백업 주기·보관 기간** · RTO/RPO                   │
 │    · **데이터 반환 및 완전 삭제**                        │
 │                                                         │
 │ **④ 보안**                                              │
 │    **책임 공유 모델** 명시 · 접근통제 · 암호화            │
 │    · **침해사고 통지 의무 및 시한** · 인증 보유(ISMS·CSAP)│
 │    · **로그 제공** · 취약점 조치                         │
 │                                                         │
 │ **⑤ 이용자 권리 보호**                                  │
 │    **감사·점검권** · 사전 통지 의무(변경·중단)            │
 │    · 서비스 종료 시 유예기간 · 하위 수탁자 고지          │
 │                                                         │
 │ **⑥ 보상 및 책임**                                      │
 │    **서비스 크레딧**(감액) 산정 기준 · 손해배상 범위·한도 │
 │    · 면책 사유 · 분쟁 해결 절차                          │
 └─────────────────────────────────────────────────────────┘

3. 책임 공유 모델 (Shared Responsibility Model) — SLA의 전제​

   [**서비스 모델별 책임 경계**]

   ┌──────────────┬────────┬────────┬────────┐
   │   책임 영역   │ **IaaS** │ **PaaS** │ **SaaS** │
   ├──────────────┼────────┼────────┼────────┤
   │ 데이터·콘텐츠 │ **이용자**│ **이용자**│ **이용자**│
   │ 계정·접근권한 │ **이용자**│ **이용자**│ **이용자**│
   │ 애플리케이션  │ **이용자**│ **이용자**│ 제공자  │
   │ 미들웨어·런타임│ **이용자**│ 제공자  │ 제공자  │
   │ 운영체제      │ **이용자**│ 제공자  │ 제공자  │
   │ 가상화·서버   │ 제공자  │ 제공자  │ 제공자  │
   │ 물리 인프라   │ 제공자  │ 제공자  │ 제공자  │
   └──────────────┴────────┴────────┴────────┘

   ⚠ **핵심 원칙** : **"데이터와 계정에 대한 책임은 어떤 모델에서도
     이용자에게 있다"** ← 클라우드 사고의 대부분이 **이용자 설정 오류**
     (공개 버킷·과도한 권한·키 노출)
   ⇒ SLA는 **제공자 책임 영역의 품질만 보장**한다는 점을 명확히 인식

4. 클라우드 SLA의 한계​

한계내용
보상의 실효성 부족서비스 크레딧은 통상 월 이용료의 10~30% 수준 → 실제 사업 손실 대비 미미
가용성 산정 기준의 유리한 설정계획 점검·불가항력 제외, 분 단위 반올림 등으로 실제 체감과 괴리
일방적 약관대형 CSP는 개별 협상 거부 → 이용자가 조건 수용 외 선택지 없음
감사·검사권 제한다중 이용자 환경 특성상 현장 실사 제한 → 제3자 인증 보고서(SOC 2) 로 대체
글로벌 관할준거법·분쟁 관할이 해외로 지정되는 경우 실효적 구제 곤란
재이용(재위탁) 불투명CSP가 사용하는 하위 서비스의 SLA는 별개

Ⅳ. 금융 클라우드 SLA 가이드​

1. 개요 및 성격​

구분내용
근거전자금융감독규정(제14조의2 등), 금융보안원 「금융분야 클라우드컴퓨팅서비스 이용 가이드」, 금융위 클라우드 이용 절차 관련 기준
성격일반 클라우드 SLA에 금융 규제 요건(감독·검사·건전성·정보보호) 을 추가한 강화된 계약 기준
적용 대상금융회사·전자금융업자가 클라우드로 처리하는 업무 및 정보시스템(특히 중요업무·개인신용정보 처리 시스템)

2. 금융 클라우드 이용 절차​

   [**금융 클라우드 이용 절차 (전자금융감독규정 기반)**]

   **① 업무 중요도 평가**
        · 처리 정보의 **중요도(고유식별정보·개인신용정보 포함 여부)**
        · 장애 시 **업무 연속성·고객 영향** 평가
        · 결과에 따라 **중요업무 / 비중요업무** 구분
              ▼
   **② CSP 건전성·안전성 평가**
        · **재무 건전성**, 기술 역량, **보안 인증(CSAP·ISMS-P·ISO 27001/27017/27018)**
        · 서비스 지속 가능성, 침해사고 이력
              ▼
   **③ 내부통제·위험관리 절차 이행**
        · **정보처리 위탁 관련 내부 심의·이사회 보고**
        · **안전성 확보조치 방안** 수립
              ▼
   **④ 계약 체결(SLA 포함)**
        · **감독규정상 필수 계약 조항 반영** ★
              ▼
   **⑤ 금융감독원 보고**
        · 중요업무 위탁 시 **이용 전 사전 보고**
              ▼
   **⑥ 운영 중 관리·감독**
        · **SLA 이행 점검**, 정기 평가, 재해복구 훈련
              ▼
   **⑦ 계약 종료·전환**
        · **데이터 반환·완전 삭제 확인**, 업무 연속성 확보

3. 금융 클라우드 SLA의 강화된 요구사항 (핵심)​

영역강화 요구사항
① 감독기관 접근권
(가장 핵심)		· 금융감독원의 검사·자료제출 요구에 CSP가 응할 의무를 계약에 명시
· 금융회사의 직접 감사·현장 점검권 확보
· 제3자 인증 보고서(SOC 2 Type II 등) 정기 제출
② 데이터 위치·국내 보관· 국내 리전 저장 의무(고유식별정보·개인신용정보)
· 국외 이전 제한 및 이전 시 사전 승인·고지
· 데이터 저장 위치의 투명한 공개 및 변경 시 통지
③ 데이터 소유권·반환·삭제· 데이터의 소유권은 금융회사에 귀속 명시
· 계약 종료 시 표준 포맷으로 반환, 완전 삭제 및 증빙 제출
· CSP의 데이터 임의 이용·분석 금지(2차 이용 금지)
④ 업무 연속성·재해복구· RTO/RPO를 업무 중요도에 맞게 구체화(중요업무는 RTO 3시간 이내 등)
· 재해복구 시스템 구축(다중 리전/가용영역, DR 사이트)
· 연 1회 이상 재해복구 훈련 및 결과 제출
· CSP 서비스 중단 시 대체 방안(Exit Plan) 사전 수립
⑤ 침해사고 대응·통지· 침해사고 인지 즉시(예: 24시간 이내) 통지 의무
· 사고 원인·영향·조치 결과 상세 보고 의무
· 금융회사의 사고 조사 참여권, 포렌식 자료 제공
⑥ 보안 통제· 국내 검증필 암호모듈 적용, 저장·전송 암호화
· 키 관리 권한을 금융회사가 보유(BYOK/CMK)
· 접근통제·계정 관리, 특권 계정 통제
· 로그(접속기록) 제공 및 법정 기간 보관
· 논리적 망분리 및 안전한 전용 회선
⑦ 재위탁(하위 수탁) 관리· 재위탁 시 사전 동의 또는 고지 의무
· 하위 수탁자에게 동일 수준의 의무 승계
· 하위 수탁 현황의 투명한 공개
⑧ 계약 변경·종료· 서비스 변경·중단 시 충분한 사전 통지(예: 90일 이상)
· 금융회사의 일방적 해지권 및 전환 지원 의무
· 종료 후 일정 기간 데이터 접근 보장
⑨ 준거법·관할· 대한민국 법률을 준거법으로 지정, 국내 법원 관할
⑩ 손해배상· 서비스 크레딧을 넘어 실손해 배상 범위 확대 협의
· 규제 위반으로 인한 과징금·제재 대응 협력 의무

4. 일반 클라우드 SLA vs 금융 클라우드 SLA​

비교 기준일반 클라우드 SLA금융 클라우드 SLA
성격자율 계약(권고 가이드)규제 준수 의무(감독규정 반영 필수)
가용성 목표99.9~99.95%99.95~99.99% 이상(중요업무)
감독기관 접근규정 없음금감원 검사 수용 의무 명시 ★
감사·점검권제한적(인증서 대체)직접 감사권 확보 요구
데이터 위치이용자 선택국내 보관 원칙, 국외 이전 제한

5. SLA 관리 체계 (운영 단계)​

   [**금융 클라우드 SLA 라이프사이클 관리**]

   **[계획]** 서비스 수준 목표 설정 (업무 중요도 기반)
        ▼
   **[계약]** SLA 협상·체결 (**감독규정 필수 조항 반영 검증**)
        ▼
   **[측정]** 실시간 모니터링 · **SLI 자동 수집**
        · 가용성 · 성능 · 장애 건수 · 보안 이벤트
        ▼
   **[보고]** **월간/분기 SLA 보고서** 수령 및 자체 검증
        · CSP 보고값과 **자체 모니터링 값 교차 검증** ★
        ▼
   **[검토]** 정기 **서비스 검토 회의**(QBR), 미달 원인 분석
        ▼
   **[조치]** 서비스 크레딧 청구 · 개선계획 요구 · 필요 시 해지
        ▼
   **[개선]** SLA 재협상, 아키텍처 개선(멀티 AZ/리전)
        ▼
   **[보고·감독]** 금융감독원 정기 보고, 내부감사·이사회 보고

Ⅴ. 실무 고려사항 및 개선 방향​

고려사항내용
① 가용성 산정 기준 명확화"가동률 99.99%"의 측정 단위(분/초)·제외 사유·측정 주체를 계약에 명시. CSP 자체 보고에만 의존하지 말고 자체 모니터링으로 교차 검증
② 서비스 크레딧의 한계 인식크레딧은 실손해를 보전하지 못함 → 금융 손실은 아키텍처(다중 AZ/리전·DR)로 예방하는 것이 근본 대책
③ 책임 공유 모델의 정확한 이해클라우드 사고의 다수는 이용자 설정 오류(공개 버킷·과도한 IAM 권한) → SLA로 보호받지 못하는 영역을 인식하고 자체 통제 강화
④ Exit Strategy 사전 수립계약 체결 시점에 데이터 반출 방식·기간·비용, 대체 CSP 전환 계획을 확정 → Lock-in 방지
⑤ 멀티클라우드·하이브리드단일 CSP 장애가 전 서비스 마비로 직결되지 않도록 핵심 업무의 이중화 검토(단, 복잡도·비용 Trade-off)
⑥ 재위탁 체인 관리CSP가 사용하는 하위 서비스(CDN·모니터링 SaaS 등) 까지 위험 식별 → 공급망 리스크 관리
⑦ 지속적 규제 대응전자금융감독규정·망분리 규제 개선 등 정책 변화 모니터링, CSAP 등급제(상·중·하) 대응
⑧ 클라우드 네이티브 특성 반영컨테이너·서버리스 등 동적 자원 환경에 맞는 지표(오토스케일링 반응 시간 등) 정의 필요

Ⅵ. 결론​

SLA는 단순한 품질 약속 문서가 아니라, 장애·사고 발생 시 책임 소재와 보상 범위를 결정하는 계약적 안전장치이다. 특히 클라우드 환경에서는 인프라의 통제권이 이용자에게서 제공자로 이전되므로, SLA가 이용자가 확보할 수 있는 사실상 유일한 통제 수단이라는 점에서 그 중요성이 매우 크다.

금융 클라우드 SLA가 일반 SLA와 근본적으로 구별되는 지점은 "당사자 간 계약"을 넘어 "감독기관이라는 제3자가 개입한다" 는 것이다. 일반 기업은 CSP와 원하는 조건만 합의하면 되지만, 금융회사는 금융감독원의 검사 수용 의무, 국내 데이터 보관, 재해복구 훈련, 침해사고 통지 시한 등 감독규정이 요구하는 조항을 반드시 계약에 반영해야 하며, 이를 누락하면 계약 자체가 규제 위반이 된다. 따라서 금융 클라우드 SLA 검토의 출발점은 CSP의 표준 약관이 아니라 전자금융감독규정의 필수 요건 체크리스트여야 한다.

실무에서 가장 유의할 점은 두 가지이다. 첫째, 서비스 크레딧에 의존해서는 안 된다. 크레딧은 통상 월 이용료의 일부에 불과하여, 금융거래 중단으로 인한 실제 손실이나 감독 제재를 전혀 보전하지 못한다. 따라서 SLA는 사후 보상 장치일 뿐이며, 실질적 방어는 다중 가용영역·다중 리전 구성과 재해복구 체계라는 아키텍처 설계로 확보해야 한다. 둘째, 책임 공유 모델을 정확히 이해해야 한다. 실제 클라우드 침해사고의 대부분은 CSP의 인프라 결함이 아니라 이용자의 설정 오류(공개 스토리지, 과도한 권한, 키 노출) 에서 발생하며, 이는 SLA의 보호 범위 밖이다. 즉 SLA를 잘 체결하는 것과 클라우드를 안전하게 쓰는 것은 별개의 과제이다.

향후 방향으로는 ① 대형 CSP와의 협상력 열위를 보완하기 위한 금융권 공동 대응(표준 계약서·공동 협상), ② 단일 CSP 종속을 완화하는 멀티클라우드·Exit Strategy의 제도화, ③ 클라우드 네이티브 환경(컨테이너·서버리스)에 맞는 SLA 지표 체계 정비, ④ CSP의 하위 공급망(재위탁 체인)까지 포괄하는 리스크 관리가 요구된다. 궁극적으로 금융 클라우드 SLA는 "장애가 없을 것"을 약속받는 문서가 아니라, "장애가 발생했을 때 누가 무엇을 언제까지 해야 하는지"를 사전에 확정해 두는 위험관리 도구로 이해하고 운영하는 것이 기술사적 관점의 핵심이다.

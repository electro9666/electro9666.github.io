병행 제어 기법

문제​

2.데이터베이스 병행 제어 기법 및 필요성

Ⅰ. 개요​

병행 제어(Concurrency Control) 는 다수의 트랜잭션이 동시에 동일한 데이터에 접근할 때, 상호 간섭을 통제하여 직렬 실행과 동일한 결과(직렬 가능성, Serializability) 를 보장하는 DBMS의 핵심 기능이다. ACID 중 격리성(Isolation) 을 구현하는 메커니즘이다.

Ⅱ. 병행 제어의 필요성 — 미제어 시 발생하는 이상 현상​

   [병행 제어가 없으면?]  T1, T2가 동시에 같은 데이터 X에 접근
        ▼
   **① 갱신 손실**(Lost Update)
      T1 : read(X=100) ──────────── write(X=150)
      T2 :        read(X=100) ── write(X=200)
      ⇒ T1의 갱신이 **덮어써져 소실** (최종 X=150 또는 200)

   **② 오손 읽기**(Dirty Read)
      T1 : write(X=200) ──────── **ROLLBACK**
      T2 :          read(X=200) ← **취소될 값을 읽음**

   **③ 반복 불가능 읽기**(Non-Repeatable Read)
      T1 : read(X=100) ────────── read(X=200) ← **같은 값을 두 번 읽었는데 다름**
      T2 :        write(X=200) commit

   **④ 유령 데이터**(Phantom Read)
      T1 : select count(*) → 10건 ────── select count(*) → **11건**
      T2 :        **insert** 1건 commit    ← 없던 행이 나타남
필요성내용
데이터 일관성 보장위 4대 이상 현상 방지 → 무결성 유지
직렬 가능성 확보병행 실행 결과 = 어떤 직렬 실행 결과와 동일
시스템 성능(처리율) 향상직렬 실행만 허용 시 동시성 0 → 처리량 급감. 병행 제어는 일관성과 성능의 균형점
자원 활용 극대화CPU·I/O 유휴 시간 최소화
회복 가능성 보장연쇄 복귀(Cascading Rollback) 방지

Ⅲ. 병행 제어 기법​

 ┌──────────── **병행 제어 기법 분류** ────────────┐
 │                                                 │
 │  **비관적**(Pessimistic) ─ 충돌이 잦다고 가정   │
 │     ├─ **로킹**(Locking) ─ 2PL, 다중 입도       │
 │     └─ **타임스탬프**(Timestamp Ordering)       │
 │                                                 │
 │  **낙관적**(Optimistic) ─ 충돌이 드물다고 가정  │
 │     └─ **검증 기법**(Validation, OCC)           │
 │                                                 │
 │  **다중 버전** ─ 읽기·쓰기 충돌 자체를 제거     │
 │     └─ **MVCC**(Multi-Version Concurrency Ctrl) │
 └─────────────────────────────────────────────────┘

1. 로킹 기법 (Locking)​

구분내용
원리접근 전 Lock 획득, 사용 후 Unlock — 상충 시 대기
락 종류공유락(S-Lock, 읽기) — 다중 허용
배타락(X-Lock, 쓰기) — 단독 점유
2단계 로킹(2PL)확장 단계(락 획득만) → 축소 단계(락 해제만)
⇒ 직렬 가능성 보장, 단 교착상태(Deadlock) 발생 가능
엄격 2PL(Strict 2PL)모든 X-Lock을 커밋 시점에 일괄 해제 → 오손 읽기·연쇄 복귀 방지(실무 표준)
로킹 단위(Granularity)DB > 파일 > 테이블 > 페이지 > 레코드 > 필드
· 크면 : 락 수↓, 오버헤드↓, 동시성↓
· 작으면 : 동시성↑, 관리 오버헤드↑
다중 입도 로킹의도락(IS/IX/SIX) 을 상위 노드에 설정 → 계층적 락 충돌 조기 판단

2. 타임스탬프 순서 기법 (Timestamp Ordering)​

구분내용
원리트랜잭션 시작 시 고유 타임스탬프(TS) 부여, TS 순서대로 직렬화
판정데이터마다 read_TS, write_TS 관리
→ 순서 위배 시 즉시 Abort 후 재시작
특징Deadlock 없음(대기가 없음), 그러나 잦은 롤백과 연쇄 복귀 발생

3. 낙관적 검증 기법 (Optimistic / Validation)​

구분내용
원리3단계 : 읽기(Read) → 검증(Validation) → 쓰기(Write)
동작트랜잭션 수행 중에는 락 없이 지역 사본에 작업, 커밋 직전 충돌 검증 → 충돌 시 Abort
적합읽기 위주·충돌이 드문 환경(조회성 시스템)

4. MVCC (다중 버전 동시성 제어)​

구분내용
원리갱신 시 기존 버전을 유지하고 새 버전 생성 → 읽기는 스냅샷(Snapshot) 참조
핵심 효과읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않음(Readers don't block Writers)
구현 예Oracle(UNDO 세그먼트), PostgreSQL(튜플 버전 + VACUUM), MySQL InnoDB
한계버전 저장 공간 증가, 가비지 정리(VACUUM) 부하, Write-Write 충돌은 여전히 락 필요

5. 기법 비교​

비교 기준로킹(2PL)타임스탬프낙관적 검증MVCC
충돌 처리 시점사전(접근 시)사전(접근 시)사후(커밋 시)사전 + 버전 분리
교착상태발생없음없음Write 시 발생 가능
롤백 빈도낮음높음높음(충돌 多 시)낮음
읽기 동시성낮음중간높음매우 높음
적합 환경갱신 빈번(OLTP)분산 DB읽기 위주범용(현대 DBMS 표준)

6. 교착상태(Deadlock) 처리​

방식내용
예방(Prevention)모든 락 일괄 요청, 락 순서 강제, Wait-Die / Wound-Wait
회피(Avoidance)타임스탬프 기반 대기 허용 여부 판단
탐지·회복(Detection)대기 그래프(Wait-for Graph) 순환 탐지 → 희생자(Victim) 선정 후 롤백 ← 실무 일반

Ⅳ. 격리 수준과의 관계​

격리 수준Dirty ReadNon-RepeatablePhantom비고
Read Uncommitted발생발생발생락 거의 없음
Read Committed방지발생발생대부분 DBMS 기본값
Repeatable Read방지방지발생MySQL InnoDB 기본
Serializable방지방지방지범위락, 동시성 최저

Ⅴ. 결론​

병행 제어의 본질은 "일관성(Consistency)과 동시성(Concurrency)의 Trade-off를 어디서 절충할 것인가" 이다. 통제를 강화하면 데이터는 정확해지지만 처리량이 떨어지고, 완화하면 성능은 오르지만 이상 현상 위험이 커진다.

현대 상용 DBMS는 엄격 2PL(쓰기)과 MVCC(읽기)를 결합하여, 읽기는 스냅샷으로 락 없이 처리하고 쓰기만 락으로 직렬화하는 방식을 사실상 표준으로 채택하고 있다. 이는 읽기 비중이 압도적으로 높은 실제 워크로드에 최적화된 선택이다.

실무 적용 시에는 ① 업무 특성에 맞는 격리 수준 선택(정합성이 중요한 정산·회계는 Repeatable Read 이상, 조회성은 Read Committed), ② 트랜잭션 범위 최소화(긴 트랜잭션은 락 점유 시간 증가 → 교착·대기 유발), ③ 접근 순서 표준화로 교착상태 예방, ④ MVCC 환경의 버전 관리 부하 모니터링(Oracle의 Snapshot Too Old, PostgreSQL의 VACUUM 지연)이 핵심 관리 포인트이다.

TCP 혼잡제어

문제​

3.TCP(Transmission Control Protocol)는 네트워크에 혼잡(Congestion)이 발생한경우, 이를 해소하기 위한 다양한 메커니즘을 사용한다.이와 관련하여 아래 사항들에대해서설명하시오.
1) TCP 혼잡제어 메커니즘의 구성요소
2) 혼잡상황 감지
3) 혼잡상황 제어
4) 혼잡 윈도우 크기

Ⅰ. 개요​

1. 혼잡(Congestion)과 혼잡제어의 개념​

혼잡(Congestion) 은 네트워크에 유입되는 트래픽이 라우터·링크의 처리 용량을 초과하여, 큐 오버플로우로 패킷이 폐기되고 지연이 급증하는 현상이다. 혼잡제어(Congestion Control) 는 송신 측이 네트워크 상태를 추정하여 전송률을 스스로 조절함으로써 혼잡을 예방·해소하는 메커니즘이다.

   [**혼잡의 발생과 혼잡 붕괴**]

   처리량
   (Goodput) ▲
             │      ╭──── **이상적**(Ideal)
             │    ╱ ╲
             │  ╱    ╲___ **실제**(혼잡제어 有)
             │╱          ╲
             │             ╲___ **혼잡 붕괴(Congestion Collapse)**
             └──────────────────────▶ 제공 부하(Offered Load)
                        ▲
                   **무릎(Knee)**  **절벽(Cliff)**

   [**혼잡 붕괴 메커니즘 — 악순환**]
   패킷 손실 발생 → **재전송 증가** → 트래픽 더 증가
        → **더 많은 손실** → 더 많은 재전송 → **처리량 0에 수렴**
   ※ 1986년 인터넷 혼잡 붕괴 사건 → **Van Jacobson의 TCP 혼잡제어 도입 계기**

2. 흐름제어와 혼잡제어의 구분 (중요)​

구분흐름제어(Flow Control)혼잡제어(Congestion Control)
보호 대상수신 측 호스트(버퍼 오버플로우 방지)네트워크 전체(라우터·링크)
범위End-to-End(1:1)네트워크 전역(다수 흐름 공유)
제어 변수rwnd(수신 윈도우) — 수신자가 광고cwnd(혼잡 윈도우) — 송신자가 추정
정보 획득수신자가 명시적으로 통보(ACK 헤더)암묵적 추정(손실·지연 관찰)
핵심 질문"수신자가 감당할 수 있는가?""네트워크가 감당할 수 있는가?"
관계실제 전송 가능량 = min(rwnd, cwnd) ← 둘 중 작은 값

Ⅱ. TCP 혼잡제어 메커니즘의 구성요소​

1. 전체 구성​

 ┌─────────────── **TCP 혼잡제어 구성요소** ───────────────┐
 │                                                         │
 │ **[A] 상태 변수**                                       │
 │   · **cwnd**(Congestion Window) — 혼잡 윈도우           │
 │   · **ssthresh**(Slow Start Threshold) — 임계값         │
 │   · **rwnd**(Receiver Window) — 수신 윈도우             │
 │   · **RTT / RTO** — 왕복시간·재전송 타이머              │
 │   ⇒ **실효 전송량 = min(cwnd, rwnd)**                   │
 │                                                         │
 │ **[B] 혼잡 감지(Detection)**                            │
 │   · **타임아웃(RTO 만료)** — 심각한 혼잡 신호           │
 │   · **3중복 ACK(3 Duplicate ACK)** — 경미한 혼잡 신호   │
 │   · **ECN**(명시적 혼잡 통보) — 라우터의 사전 신호      │
 │   · **RTT 증가 관찰** — 지연 기반(Vegas·BBR)            │
 │                                                         │
 │ **[C] 혼잡 제어 알고리즘 — 4대 핵심**                   │
 │   **① 슬로우 스타트**(Slow Start)                       │
 │   **② 혼잡 회피**(Congestion Avoidance) — AIMD          │
 │   **③ 빠른 재전송**(Fast Retransmit)                    │
 │   **④ 빠른 회복**(Fast Recovery)                        │
 │                                                         │
 │ **[D] 보조 메커니즘**                                   │
 │   · **AIMD** 원리(가법 증가·승법 감소)                  │
 │   · **SACK**(선택적 확인응답), **타임스탬프**           │
 │   · **RTO 계산**(SRTT·RTTVAR, Karn 알고리즘)            │
 │   · **AQM**(RED·CoDel) — 라우터 측 능동 큐 관리         │
 └─────────────────────────────────────────────────────────┘

2. 구성요소별 상세​

구성요소역할
cwnd(혼잡 윈도우)송신자가 ACK 없이 전송할 수 있는 최대 바이트 수. 네트워크 수용력에 대한 송신자의 추정치
ssthresh(임계값)슬로우 스타트와 혼잡 회피를 구분하는 경계값. 혼잡 발생 시 cwnd의 절반으로 설정
RTO(재전송 타임아웃)ACK 미수신 시 재전송까지의 대기 시간. SRTT + 4×RTTVAR 로 동적 산정, 지수적 백오프 적용
중복 ACK수신자가 순서가 어긋난 세그먼트 수신 시 직전 정상 순번을 반복 ACK → 손실 조기 감지 신호
SACK(RFC 2018)수신자가 정상 수신한 블록 범위를 명시 → 송신자가 손실된 것만 선별 재전송
ECN(RFC 3168)라우터가 폐기 대신 IP 헤더에 혼잡 표시(CE) → 손실 없이 혼잡 통보
AQM(RED·CoDel)큐가 가득 차기 전 확률적으로 조기 폐기·마킹 → 버퍼블로트(Bufferbloat) 완화, 전역 동기화 방지

Ⅲ. 혼잡상황 감지 (Congestion Detection)​

1. 감지 방식 개요​

TCP는 네트워크로부터 혼잡 정보를 직접 받지 못하므로, 관찰 가능한 현상으로 간접 추정한다.

   [**혼잡 감지의 근본 전제**]
   "**유선 네트워크에서 패킷 손실의 주원인은 전송 오류가 아니라
     라우터의 버퍼 오버플로우, 즉 혼잡이다**"
   ⇒ **손실 = 혼잡 신호**로 해석
   ⚠ **한계** : 무선 환경에서는 **전송 오류에 의한 손실**도 많아
                혼잡으로 오인 → 불필요한 전송률 감소

2. 감지 방식 상세​

가. 손실 기반 감지 (Loss-based) — 전통적 방식​

감지 신호발생 조건혼잡 심각도해석
재전송 타임아웃
(RTO Expiration)		RTO 시간 내 ACK 전혀 미수신심각(Severe)경로가 완전히 막힘 또는 연속 손실
→ ACK 흐름 자체가 끊김
3중복 ACK
(3 Duplicate ACK)		동일 순번의 ACK를 4회 수신(원본1+중복3)경미(Mild)후속 패킷은 도착 중 → 경로는 살아있고 일부만 손실
   [**3중복 ACK 발생 원리**]

   송신 : Seg1  Seg2  **Seg3**  Seg4  Seg5  Seg6
                       ✕(손실)
                        ▼
   수신 : Seg1 → **ACK 2**(정상)
          Seg2 → **ACK 3**(정상, 다음 기대 순번 3)
          Seg4 → **ACK 3**(중복 1) ← Seg3이 없어 3을 계속 요구
          Seg5 → **ACK 3**(중복 2)
          Seg6 → **ACK 3**(중복 3)  ⇒ **3중복 ACK 감지!**
                                      **RTO 만료를 기다리지 않고 즉시 재전송**

   [**감지 신호별 의미 차이**]
   · **3중복 ACK** : Seg4~6이 도착했다 = **경로는 살아 있다** → 완만한 감소
   · **타임아웃**  : 아무 ACK도 없다 = **경로가 막혔다** → 급격한 감소

나. 지연 기반 감지 (Delay-based) — 예방적 방식​

방식원리
RTT 증가 관찰라우터 큐에 패킷이 쌓이면 손실 이전에 RTT가 먼저 증가 → 손실 전에 감속(TCP Vegas)
대역폭·RTT 추정BBR — 병목 대역폭(BtlBw)과 최소 RTT(RTprop)를 측정하여 큐를 만들지 않는 최적 전송률 산정
장점손실 발생 전 예방적 대응 → 큐 지연(버퍼블로트) 최소화
단점손실 기반 흐름과 경쟁 시 불리(양보만 하다 대역폭 뺏김)

다. 명시적 신호 감지 (Explicit)​

방식원리
ECN(Explicit Congestion Notification)① 라우터가 혼잡 시 IP 헤더 ECN 필드를 CE(Congestion Experienced)로 마킹
② 수신자가 ACK의 ECE 플래그로 송신자에게 통보
③ 송신자가 cwnd 감소 + CWR 플래그로 응답
⇒ 패킷 손실 없이 혼잡 제어 가능
ICMP Source Quench과거 방식, 현재는 사용 중단(폐기됨)

3. 감지 방식 비교​

비교 기준손실 기반지연 기반명시적(ECN)
신호패킷 손실RTT 증가라우터 마킹
대응 시점사후(혼잡 발생 후)사전(혼잡 예방)사전
정확도무선에서 오탐 발생노이즈에 민감가장 정확
큐 지연큼(버퍼블로트)작음작음
배포 요건종단만종단만라우터 지원 필요
대표 알고리즘Reno, CUBICVegas, BBRDCTCP(데이터센터)

Ⅳ. 혼잡상황 제어 (Congestion Control)​

1. AIMD 원리 (기본 철학)​

   [**AIMD (Additive Increase, Multiplicative Decrease)**]

   · **가법 증가(AI)** : 혼잡이 없으면 **RTT당 1 MSS씩 천천히 증가**
                        → 신중한 탐색(가용 대역폭 조심스럽게 확보)
   · **승법 감소(MD)** : 혼잡 감지 시 **cwnd를 절반으로 급감**
                        → 신속한 양보(혼잡 붕괴 신속 회피)

   **"천천히 늘리고, 빠르게 줄인다"**
   ⇒ **안정성(Stability)과 공정성(Fairness)을 동시에 보장**
     (수학적으로 다수 흐름이 **균등 분배점으로 수렴**함이 증명됨)

   cwnd ▲
        │    ╱│    ╱│    ╱│      **톱니 형태(Sawtooth)**
        │  ╱  │  ╱  │  ╱  │      = TCP 혼잡제어의 전형적 거동
        │╱    ▼╱    ▼╱    ▼
        └────────────────────▶ 시간
              ↑ 혼잡 감지 시점(1/2로 감소)

2. 4대 제어 알고리즘​

가. ① 슬로우 스타트 (Slow Start)​

구분내용
목적초기에 네트워크 용량을 모르는 상태에서 빠르게 가용 대역폭 탐색
동작cwnd = 1 MSS에서 시작, ACK 1개 수신 시마다 cwnd += 1 MSS
⇒ RTT마다 cwnd가 2배(1→2→4→8…) = 지수적 증가(Exponential)
종료 조건① cwnd ≥ ssthresh → 혼잡 회피 단계로 전환
② 혼잡 감지(손실) 발생
명칭의 역설"Slow"는 증가 속도가 느리다는 뜻이 아니라, 매우 작은 값(1 MSS)에서 시작한다는 의미

나. ② 혼잡 회피 (Congestion Avoidance)​

구분내용
목적용량 한계 근처에서 손실을 유발하지 않도록 신중히 증가
동작RTT당 cwnd += 1 MSS(선형 증가)
구현식 : ACK 수신 시 cwnd += MSS × (MSS / cwnd)
진입 조건cwnd ≥ ssthresh
특징AIMD의 AI(가법 증가) 구간

다. ③ 빠른 재전송 (Fast Retransmit)​

구분내용
목적RTO 만료를 기다리지 않고 즉시 재전송 → 불필요한 대기 제거
동작3중복 ACK 수신 시, 타이머 만료 전에 손실 세그먼트 즉시 재전송
효과RTO(수백 ms~수 초) 대기 제거 → 처리량 대폭 개선

라. ④ 빠른 회복 (Fast Recovery)​

구분내용
목적3중복 ACK는 경미한 혼잡이므로, 슬로우 스타트로 되돌아가지 않고 혼잡 회피 단계에서 계속 진행
동작(Reno)① ssthresh = cwnd / 2
② cwnd = ssthresh + 3 MSS(중복 ACK 3개 = 3개가 네트워크를 빠져나감)
③ 추가 중복 ACK마다 cwnd += 1 MSS
④ 새로운 ACK 수신 시 → cwnd = ssthresh, 혼잡 회피 단계로 복귀
효과cwnd를 1로 떨어뜨리지 않아 처리량 유지 ← Tahoe 대비 Reno의 핵심 개선점

3. 상황별 제어 동작 (핵심 정리)​

   [**혼잡 감지 유형에 따른 대응 — TCP Reno 기준**]

   ┌──────────────────┬────────────────────┬────────────────────┐
   │      상황        │  **3중복 ACK**      │  **타임아웃(RTO)**  │
   ├──────────────────┼────────────────────┼────────────────────┤
   │ 혼잡 심각도      │ **경미**            │ **심각**            │
   │ **ssthresh**     │ **cwnd / 2**        │ **cwnd / 2**        │
   │ **cwnd**         │ **ssthresh + 3MSS** │ **1 MSS** ← 초기화  │
   │ 다음 단계        │ **빠른 회복**       │ **슬로우 스타트**   │
   │                  │ → 혼잡 회피          │ → 혼잡 회피         │
   │ 재전송 방식      │ **즉시 재전송**     │ 타이머 만료 후      │
   │ RTO 처리         │ -                   │ **2배 백오프**      │
   └──────────────────┴────────────────────┴────────────────────┘

4. 상태 전이도​

 ┌───────────────── **TCP 혼잡제어 상태 전이** ─────────────────┐
 │                                                              │
 │      **[연결 시작]**  cwnd = 1 MSS, ssthresh = 초기값(64KB)   │
 │              │                                               │
 │              ▼                                               │
 │      ┌──────────────────┐                                    │
 │      │ **① 슬로우 스타트** │  cwnd 지수 증가 (RTT당 ×2)       │
 │      │  (Slow Start)     │                                   │
 │      └───┬──────┬────┬───┘                                   │
 │          │      │    │                                       │
 │ cwnd≥ssthresh   │    └─**타임아웃**→ ssthresh=cwnd/2,        │
 │          │      │                    cwnd=1 → **①로**        │
 │          ▼      └─**3중복ACK**→ ③으로                        │
 │      ┌──────────────────┐                                    │
 │      │ **② 혼잡 회피**   │  cwnd 선형 증가 (RTT당 +1 MSS)    │
 │      │(Cong. Avoidance) │                                    │
 │      └───┬──────────┬───┘                                    │
 │          │          └─**타임아웃**→ ssthresh=cwnd/2,         │
 │  **3중복ACK**                        cwnd=1 → **①로**         │
 │          ▼                                                   │
 │      ┌──────────────────┐                                    │
 │      │ **③ 빠른 재전송/**│ ssthresh = cwnd/2                 │

 │   **새 ACK 수신**                                             │
 │          └──▶ cwnd = ssthresh → **②로 복귀**                  │
 └──────────────────────────────────────────────────────────────┘

Ⅴ. 혼잡 윈도우 크기 (Congestion Window Size)​

1. cwnd의 정의와 역할​

구분내용
정의송신자가 ACK를 받지 않은 상태에서 네트워크에 내보낼 수 있는 최대 데이터량(바이트, 통상 MSS 배수로 표현)
의미네트워크의 수용 능력에 대한 송신자의 동적 추정치(네트워크가 알려주지 않으므로 스스로 추정)
단위MSS(Maximum Segment Size, 이더넷 기준 통상 1,460 Byte)
실효 윈도우전송 가능량 = min(cwnd, rwnd) — 네트워크 한계와 수신자 한계 중 작은 값
처리량 관계Throughput ≈ cwnd / RTT → cwnd가 클수록, RTT가 짧을수록 처리량 증가

2. cwnd 변화 규칙 요약​

단계·이벤트cwnd 변화ssthresh 변화
연결 초기1 MSS(현대는 10 MSS, RFC 6928 Initial Window)초기값(예: 64KB 또는 무한대)
슬로우 스타트(ACK 수신)cwnd += 1 MSS (ACK당) → RTT당 2배유지
혼잡 회피(ACK 수신)cwnd += MSS²/cwnd → RTT당 +1 MSS유지
3중복 ACK 감지cwnd = ssthresh + 3 MSSssthresh = cwnd / 2
빠른 회복 중 중복 ACKcwnd += 1 MSS유지
새 ACK 수신(회복 완료)cwnd = ssthresh유지
타임아웃(RTO) 발생cwnd = 1 MSSssthresh = cwnd / 2

3. cwnd 변화 시나리오 (그래프)​

   [**TCP Reno의 cwnd 변화**]

4. cwnd 계산 예시​

   [**전제**] MSS = 1,460 Byte, 초기 ssthresh = 16 MSS

   RTT 0 : cwnd = 1  MSS  ─┐
   RTT 1 : cwnd = 2  MSS   │ **슬로우 스타트**
   RTT 2 : cwnd = 4  MSS   │ (지수 증가 ×2)
   RTT 3 : cwnd = 8  MSS   │
   RTT 4 : cwnd = 16 MSS  ─┘ ← **ssthresh 도달 → 혼잡 회피 전환**
   RTT 5 : cwnd = 17 MSS  ─┐
   RTT 6 : cwnd = 18 MSS   │ **혼잡 회피**
   RTT 7 : cwnd = 19 MSS   │ (선형 증가 +1)
   RTT 8 : cwnd = 20 MSS  ─┘

   [**RTT 8에서 3중복 ACK 발생**]
   ssthresh = 20 / 2 = **10 MSS**
   cwnd = ssthresh + 3 = **13 MSS** → 빠른 회복 → 새 ACK 시 **cwnd = 10 MSS**
   ⇒ 혼잡 회피 계속(**11, 12, 13 …**)

   [**만약 타임아웃이었다면**]
   ssthresh = 20 / 2 = **10 MSS**
   **cwnd = 1 MSS** → **슬로우 스타트부터 재시작** (처리량 급락)

   [**최대 처리량 산정**]
   Throughput ≈ cwnd / RTT
   예) cwnd = 64KB, RTT = 100ms
       → 64KB / 0.1s = **640 KB/s ≈ 5.1 Mbps**
   ⇒ **장거리 고속망(LFN)에서는 cwnd가 병목**
     → **Window Scaling 옵션(RFC 7323)** 으로 최대 1GB까지 확장

5. cwnd 관련 주요 고려사항​

고려사항내용
초기 윈도우(IW) 확대기존 1~4 MSS → 10 MSS(약 14KB) 로 확대(RFC 6928) → 짧은 웹 트랜잭션의 지연 대폭 감소
BDP(대역폭-지연 곱)BDP = 대역폭 × RTT = 파이프에 담을 수 있는 최대 데이터량
⇒ cwnd가 BDP보다 작으면 대역폭을 다 쓰지 못함
Window ScalingTCP 헤더의 윈도우 필드는 16bit(최대 64KB) → 고속·장거리 환경에서 부족
⇒ 스케일 팩터로 최대 1GB까지 확장
버퍼블로트(Bufferbloat)라우터의 과도한 버퍼 → 손실이 늦게 발생 → cwnd가 과도하게 커지고 큐 지연 급증
⇒ AQM(CoDel·FQ-CoDel) 및 BBR 로 대응
무선 환경 오판전송 오류에 의한 손실을 혼잡으로 오인 → 불필요한 cwnd 감소
⇒ Snoop TCP, Explicit Loss Notification, MPTCP 등으로 보완

Ⅵ. TCP 혼잡제어 알고리즘의 발전​

알고리즘특징비고

Ⅶ. 결론​

TCP 혼잡제어의 본질은 "네트워크가 자신의 상태를 알려주지 않는 환경에서, 송신자가 관찰 가능한 신호(손실·지연)만으로 네트워크 용량을 추정하고 스스로 절제하는 자율 제어 메커니즘" 이다. 중앙 통제자 없이 수억 개의 흐름이 각자 AIMD 규칙을 따르는 것만으로 전체 인터넷이 안정적으로 동작한다는 점에서, 이는 분산 시스템 설계의 가장 성공적인 사례 중 하나로 평가된다.

핵심 설계 원리는 AIMD(천천히 늘리고 빠르게 줄인다) 이다. 증가를 신중하게 하는 이유는 혼잡 붕괴를 유발하지 않기 위함이고, 감소를 급격하게 하는 이유는 혼잡을 신속히 해소하기 위함이다. 수학적으로 AIMD는 다수 흐름이 대역폭을 균등하게 나누어 갖는 점으로 수렴함이 증명되어 있으며, 이것이 TCP가 공정성(Fairness) 을 확보하는 근거이다.

혼잡 감지에서 가장 중요한 판단은 "3중복 ACK와 타임아웃을 구분하여 다르게 대응한다" 는 점이다. 3중복 ACK는 후속 패킷이 도착하고 있다는 뜻이므로 경로는 살아 있다는 증거이고, 따라서 cwnd를 절반만 줄이고 혼잡 회피를 계속한다(빠른 회복). 반면 타임아웃은 아무 응답도 없다는 뜻이므로 경로가 심각하게 막힌 상태로 보아 cwnd를 1로 초기화하고 슬로우 스타트부터 다시 시작한다. 이 차등 대응이 Tahoe에서 Reno로의 발전을 이끈 핵심 통찰이다.

다만 전통적 TCP 혼잡제어는 두 가지 근본적 한계를 갖는다. 첫째, "손실 = 혼잡"이라는 전제가 무선 환경에서 성립하지 않는다. 무선 구간의 전송 오류에 의한 손실을 혼잡으로 오인하여 불필요하게 전송률을 낮추므로, 모바일 환경에서 성능이 저하된다. 둘째, 손실이 발생해야만 반응하므로 라우터 버퍼가 가득 찰 때까지 큐가 쌓이는 버퍼블로트(Bufferbloat) 문제가 발생하여, 대역폭은 충분해도 지연시간이 급증한다.

이러한 한계에 대한 현재의 해답이 BBR과 AQM이다. BBR은 손실 대신 병목 대역폭과 최소 RTT를 직접 측정하여 큐를 만들지 않는 최적 전송률을 찾고, AQM(CoDel·FQ-CoDel)은 라우터에서 큐가 차기 전에 조기 신호를 보낸다. 또한 QUIC(HTTP/3) 은 혼잡제어를 커널이 아닌 사용자 공간에서 구현하여 알고리즘을 자유롭게 교체·개선할 수 있게 함으로써, 커널 업데이트 주기에 묶여 있던 혼잡제어 발전의 병목을 해소했다.

실무 관점에서는 ① 서버의 혼잡제어 알고리즘 선택(범용 웹은 CUBIC, 고대역폭·장거리 스트리밍은 BBR 검토), ② Window Scaling·SACK·초기 윈도우 확대 옵션 활성화, ③ 네트워크 장비의 AQM 적용으로 버퍼블로트 해소, ④ 무선·위성 등 특수 환경에서의 별도 튜닝이 성능 최적화의 실질적 지렛대가 된다.

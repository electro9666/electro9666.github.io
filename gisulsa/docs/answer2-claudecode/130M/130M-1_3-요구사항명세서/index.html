요구사항명세서

문제​

3.요구사항명세서에 기술되어야 하는 항목 설명

Ⅰ. 개요​

요구사항명세서(SRS, Software Requirements Specification) 는 개발할 시스템이 무엇을(What) 수행해야 하는가를 완전하고 일관되며 검증 가능하게 문서화한 산출물로, 발주자와 개발자 간의 계약적 기준선(Baseline) 이자 설계·테스트·검수의 기준이 되는 문서이다.

   [SRS의 위상]
   요구사항 도출 → 분석 → **명세(SRS)** → 확인/검증
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   **설계의 입력**       **테스트의 근거**      **계약·검수 기준**
   (아키텍처·상세설계)   (인수시험 케이스)      (범위·대가·분쟁 해결)
   ※ 대표 표준 : **IEEE 830 → ISO/IEC/IEEE 29148**(현행)

Ⅱ. 요구사항명세서의 기술 항목 (IEEE 29148/830 기준)​

 ┌──────────── **SRS 목차 구조** ────────────┐
 │ **1. 서론**(Introduction)                 │
 │    1.1 목적    1.2 범위    1.3 용어정의   │
 │    1.4 참고문헌 1.5 문서 개요             │
 │                                           │
 │ **2. 전반적 기술**(Overall Description)   │
 │    2.1 제품 관점(시스템 구성·인터페이스)  │
 │    2.2 제품 기능(개괄)  2.3 사용자 특성   │
 │    2.4 제약사항  2.5 가정 및 종속성       │
 │                                           │
 │ **3. 상세 요구사항**(Specific Req.) ★핵심 │
 │    3.1 **기능 요구사항**                  │
 │    3.2 **비기능 요구사항**(품질 속성)     │
 │    3.3 **인터페이스 요구사항**            │
 │    3.4 **데이터 요구사항**                │
 │    3.5 **제약 요구사항**                  │
 │                                           │
 │ **4. 검증**(Verification) — 요구사항별    │
 │    확인 방법(시험·검사·시연·분석)         │
 │                                           │
 │ **5. 부록**(Appendix)                     │
 │    **요구사항 추적표(RTM)**, 용어집, 모델 │
 └───────────────────────────────────────────┘

1. 서론 및 전반적 기술 항목​

항목기술 내용
목적(Purpose)문서의 작성 목적, 독자(발주자·PM·개발자·감리·시험자) 명시
범위(Scope)시스템 명칭, 포함 범위와 제외 범위(Out of Scope) 명확화 → 범위 분쟁 예방
용어 정의약어·업무 용어 통일 → 이해관계자 간 해석 차이 제거
제품 관점시스템 컨텍스트 다이어그램, 외부 시스템·조직과의 경계
사용자 특성사용자 그룹·업무 숙련도·접근성 요구(장애인 등)
제약사항법·규제(개인정보보호법·전자정부법), 표준, 기존 인프라·기술 스택
가정 및 종속성전제 조건(예: 타 사업 완료), 미충족 시 영향

2. 상세 요구사항 항목 (핵심)​

구분세부 항목기술 내용
기능 요구사항
(Functional)		업무 기능입력 → 처리 규칙·업무 로직 → 출력, 예외·오류 처리
사용 시나리오유스케이스·사용자 스토리, 액터·선행/후행 조건
비기능 요구사항
(Non-Functional)		성능응답시간, TPS, 동시 사용자 수, 처리량
가용성·신뢰성가동률(99.9%), RTO/RPO, MTBF/MTTR
보안인증·인가, 암호화, 접근통제, 개인정보 보호조치
사용성UI/UX 지침, 접근성(KWCAG), 학습 용이성
확장성·이식성용량 증설 방안, 멀티 플랫폼·브라우저 지원
유지보수성모듈화, 로그·모니터링, 표준 준수
인터페이스 요구사항사용자 I/F화면 목록·표준, 레이아웃 규칙
시스템 I/F연계 대상·방식(API/EAI/FTP)·주기·전문 규격
HW/SW I/F장비·미들웨어·DBMS 요구
통신 I/F프로토콜, 대역폭, 보안 채널
데이터 요구사항데이터 정의개념 데이터 모델, 주요 엔터티·속성
데이터 품질·보존정합성 규칙, 보관 기간·백업·이관(마이그레이션)
제약 요구사항기술·환경개발 언어·프레임워크, 표준 준수, 라이선스
프로젝트일정·예산·인력, 단계별 산출물

3. 개별 요구사항의 기술 형식(속성)​

   [**요구사항 명세 항목(1건당)**]
   ┌────────────┬──────────────────────────────────┐
   │ **요구사항 ID** │ SFR-001 (유형별 체계적 부여)  │
   │ **요구사항 명칭** │ 사용자 인증                 │
   │ **정의(설명)** │ 시스템은 ~해야 한다(Shall)     │
   │ **세부 내용**  │ 처리 조건·규칙·예외           │
   │ **산출 정보**  │ 출력물·화면·보고서            │
   │ **우선순위**   │ **필수 / 중요 / 선택**(MoSCoW) │
   │ **관련 요구사항** │ 추적 관계(상위/연관)        │
   │ **검증 기준**  │ **인수 기준(Acceptance)**     │
   └────────────┴──────────────────────────────────┘
   ※ 공공 SW사업 제안요청서(RFP) 표준 : **기능(SFR)·성능(PER)·인터페이스(SIR)·데이터(DAR)·
     테스트(TER)·보안(SER)·품질(QUR)·제약(COR)·프로젝트관리(PMR)·지원(PSR)** 요구사항으로 분류

Ⅲ. 좋은 요구사항명세서의 품질 속성 (IEEE 29148)​

속성내용
완전성(Complete)필요한 모든 요구사항 포함, TBD 없음
명확성·비모호성(Unambiguous)해석이 하나뿐 — "신속히·편리하게" 같은 정성적 표현 금지
일관성(Consistent)요구사항 간 상충 없음(용어·값·규칙)
검증 가능성(Verifiable)측정·시험 가능 — "응답 3초 이내(95% 요청)"
추적 가능성(Traceable)고유 ID로 상위 요구·설계·코드·테스트와 양방향 추적
실현 가능성(Feasible)기술·일정·예산 내 구현 가능
수정 용이성(Modifiable)중복 제거, 구조화 → 변경 파급 최소
우선순위 부여(Ranked)중요도·안정성 기준 등급화

Ⅳ. 작성 시 고려사항 및 실무 유의점​

고려사항내용
① What과 How의 분리SRS는 무엇을만 기술, 어떻게(설계·구현 방식) 는 배제 → 과도한 설계 명시는 대안 차단
② 비기능 요구사항의 정량화성능·가용성은 수치와 측정 조건을 함께 명시(측정 시점·부하 조건)
③ 요구사항 추적표(RTM)요구사항 ↔ 설계 ↔ 코드 ↔ 테스트 케이스 양방향 추적 → 누락·과잉 개발 방지
④ 변경관리 연계기준선 확정 후 형상관리·변경통제위원회(CCB) 를 통한 통제
⑤ 모델의 병행 사용텍스트만으로는 한계 → 유스케이스·상태도·데이터 모델·화면 흐름도 병행
⑥ 애자일 환경 적용대규모 사전 명세 대신 제품 백로그·사용자 스토리 + 인수 기준(Given-When-Then) 으로 점진 명세
⑦ 검토·승인인스펙션·워크스루로 결함 조기 제거(요구단계 결함 수정비 = 운영단계의 1/100)

Ⅴ. 결론​

요구사항명세서는 단순한 개발 문서가 아니라 프로젝트 범위·대가·검수의 법적 기준선이며, 후속 모든 산출물의 원천(Single Source of Truth) 이다. 요구공학 연구가 일관되게 보여주듯 프로젝트 실패 원인의 최상위는 부정확·불완전한 요구사항이므로, SRS의 품질이 곧 프로젝트의 성패를 결정한다.

작성 시 가장 중요한 것은 "검증 가능성(Verifiable)" 이다. "사용자가 편리하게 사용할 수 있어야 한다"는 문장은 검수 시점에 아무도 합격/불합격을 판정할 수 없으므로 요구사항이 아니다. 모든 항목을 측정 가능한 인수 기준으로 환산하는 것이 기술사적 관점의 핵심이다.

아울러 최근 공공 SW사업에서는 과업심의위원회를 통해 요구사항 변경의 적정성과 대가를 심의하도록 제도화되었으므로, SRS는 초기 명확화(RFP 단계 요구사항 상세화) 와 변경 추적성 확보를 함께 갖추어야 실무적 실효성을 가진다.

개인정보 안전성 확보조치

문제​

2.개인정보보호를 위한 "개인정보의 안전성 확보조치 기준" 고시 내용 중 다음을 설명 하시오.
가.내부관리계획 수립·이행
나.암호화 적용방안

Ⅰ. 개요​

1. 개념 및 법적 근거​

「개인정보의 안전성 확보조치 기준」 은 개인정보보호법 제29조(안전조치의무) 및 동법 시행령 제30조에 근거하여, 개인정보처리자가 개인정보의 분실·도난·유출·위조·변조·훼손을 방지하기 위해 취해야 할 관리적·기술적·물리적 보호조치의 최소 기준을 규정한 개인정보보호위원회 고시이다.

   [법 체계]

   **개인정보보호법 제29조**(안전조치의무)
     "개인정보처리자는 개인정보가 **분실·도난·유출·위조·변조 또는
      훼손되지 아니하도록 내부관리계획 수립, 접속기록 보관 등
      **안전성 확보에 필요한 기술적·관리적·물리적 조치**를 하여야 한다."
        ▼
   **시행령 제30조**(안전조치의무의 세부기준) — 7개 항목
        ▼
   **「개인정보의 안전성 확보조치 기준」 고시**(개인정보위)
   · **2023.9 전면 개정** — 기존 '개인정보의 기술적·관리적 보호조치 기준'
     (정보통신서비스 제공자용)과 **일원화**
   · 처리자 유형별 차등 규정 폐지 → **모든 개인정보처리자 단일 적용**

2. 안전성 확보조치의 전체 구성​

 ┌─────── **안전성 확보조치 기준 주요 조항** ───────┐
 │                                                  │
 │ **제4조  내부관리계획의 수립·시행 및 점검** ★     │
 │ **제5조  접근 권한의 관리**                       │
 │ **제6조  접근통제**                               │
 │ **제7조  개인정보의 암호화** ★                    │
 │ **제8조  접속기록의 보관 및 점검**                │
 │ **제9조  악성프로그램 등 방지**                   │
 │ **제10조 물리적 안전조치**                        │
 │ **제11조 재해·재난 대비 안전조치**                │
 │ **제12조 출력·복사 시 안전조치**                  │
 │ **제13조 개인정보의 파기**                        │
 │ **제14조 공공시스템운영기관 특례**(제14~16조)     │
 │                                                  │
 │  ⇒ **관리적**(제4·5조) + **기술적**(제6~9·12·13조)│
 │    + **물리적**(제10·11조) 조치의 통합            │
 └──────────────────────────────────────────────────┘

Ⅱ. 내부관리계획의 수립·이행 (제4조)​

1. 개념 및 의의​

항목내용
정의개인정보의 안전한 처리를 위하여 개인정보처리자가 내부적으로 수립·시행하는 조직·인력·절차·기술 전반에 관한 종합 계획서
의의모든 보호조치의 근거 문서 — 개인정보보호의 최상위 정책·거버넌스 문서
적용 예외1만명 미만의 정보주체 개인정보를 처리하는 소상공인·개인·단체는 수립 의무 면제(단, 다른 조치는 이행)
   [**내부관리계획의 위치 — 개인정보보호 체계의 최상위**]

   ┌──────────────────────────────────────┐
   │ **내부관리계획**(제4조) ← 최상위 정책   │
   │  "누가·무엇을·어떻게 보호할 것인가"     │
   └──────────────┬───────────────────────┘
                  ▼ 근거 제공
   ┌──────────────────────────────────────┐
   │ 세부 지침·절차서                       │
   │ · 접근권한 관리절차 · 암호화 지침       │
   │ · 접속기록 점검절차 · 파기 절차         │
   └──────────────┬───────────────────────┘
                  ▼ 실행
   ┌──────────────────────────────────────┐
   │ 실제 보호조치 이행                     │
   │ (제5조~제13조 기술적·물리적 조치)       │
   └──────────────────────────────────────┘

2. 내부관리계획 포함 사항 (고시 제4조 제1항)​

구분포함 사항
① 조직·책임· 개인정보보호책임자(CPO)의 지정에 관한 사항
· CPO 및 개인정보취급자의 역할·책임에 관한 사항
· 개인정보보호 조직의 구성·운영에 관한 사항
② 접근 권한· 개인정보취급자에 대한 접근 권한 관리에 관한 사항(제5조)
③ 접근 통제· 접근통제에 관한 사항(제6조)
④ 암호화· 개인정보의 암호화 조치에 관한 사항(제7조)
⑤ 접속기록· 접속기록 보관 및 점검에 관한 사항(제8조)
⑥ 악성프로그램· 악성프로그램 등 방지에 관한 사항(제9조)
⑦ 물리적 안전조치· 물리적 안전조치에 관한 사항(제10조)
⑧ 재해·재난· 재해·재난 대비 안전조치에 관한 사항(제11조)
⑨ 유출 대응· 개인정보 유출사고 대응 계획 수립·시행에 관한 사항
⑩ 위험 분석· 위험 분석 및 관리에 관한 사항
⑪ 교육· 개인정보취급자 교육에 관한 사항
⑫ 수탁자 관리· 개인정보 처리업무를 위탁하는 경우 수탁자에 대한 관리·감독에 관한 사항
⑬ 기타· 그 밖에 개인정보 보호를 위하여 필요한 사항

3. 수립·이행 절차​

 ┌────────── **내부관리계획 수립·이행 절차** ──────────┐
 │                                                     │
 │ **① 현황 파악**                                      │
 │   · **개인정보 처리 현황 조사**(수집 항목·목적·보유기간)│
 │   · 개인정보 **흐름도(Flow) 작성** — 수집~파기        │
 │   · 처리 시스템·취급자·위탁 현황 파악                │
 │              ▼                                      │
 │ **② 위험 분석**                                      │
 │   · 자산 식별 → 위협·취약점 분석 → **위험도 평가**    │
 │   · **개인정보 영향평가(PIA)** 결과 반영              │
 │     (공공기관 일정 규모 이상 **의무**)                │
 │              ▼                                      │
 │ **③ 내부관리계획 수립**                              │
 │   · 고시 제4조 **13개 항목** 포함하여 문서화          │
 │   · **CPO 지정**, 조직·역할 정의                      │
 │   · **경영진(대표자) 승인** ← 실효성 확보의 핵심      │
 │              ▼                                      │
 │ **④ 시행 및 세부 지침 수립**                          │
 │   · 세부 절차서·지침 마련(권한관리·암호화·파기 등)    │
 │   · **전 임직원 공표·공유**                           │
 │              ▼                                      │
 │ **⑤ 교육 실시**                                      │
 │   · 개인정보취급자 대상 **정기 교육**(연 1회 이상 권장)│
 │   · 교육계획 수립·실시·결과 기록 보관                │
 │              ▼                                      │
 │ **⑥ 이행 점검**                                      │
 │   · ★**CPO가 연 1회 이상 내부관리계획의 이행 실태를**  │
 │     ★**점검·관리**★ (고시 제4조 제3항)                │
 │   · 점검 결과 **미흡사항 개선조치**                    │
 │              ▼                                      │
 │ **⑦ 현행화(갱신)**                                   │
 │   · **중요 변경 시 즉시 반영**하고 그 사유·내용 기록   │
 │     (조직 개편·시스템 변경·법령 개정·사고 발생 시)     │
 │   ⇒ **①로 순환**(PDCA)                               │
 └─────────────────────────────────────────────────────┘

4. 핵심 준수 포인트​

포인트내용
연 1회 이상 이행 점검CPO의 법정 의무 — 점검 결과 및 개선조치 문서 보관 필수(사고 시 입증 자료)
변경 시 기록 의무내부관리계획을 변경한 경우 변경 사유 및 내용을 기록·관리
경영진 승인대표자 승인 없는 계획은 실효성 확보 곤란 → 자원 배분·권한 확보의 근거
형식화 방지템플릿 복사·붙여넣기 방식은 실제 처리 현황 미반영 → 조사 시 지적 사항
수탁자 관리 포함위탁 시 수탁자에 대한 교육·감독 계획 반드시 포함(제26조 연계)
CPO 자격 요건2024년 개정으로 일정 규모 이상 기업의 CPO 자격 요건(경력) 신설, 독립성 보장

Ⅲ. 개인정보의 암호화 적용방안 (제7조)​

1. 암호화의 개념 및 원칙​

항목내용
정의개인정보를 정당한 권한이 없는 자가 알아볼 수 없는 형태로 변환하는 조치
의의최후의 방어선(Last Line of Defense) — 유출되더라도 내용 확인 불가 → 실질적 피해 차단
법적 효과암호화된 개인정보가 유출된 경우 유출 통지·신고 의무는 유지되나, 과징금 감경 사유로 고려됨
   [**암호화 적용 대상 판단 흐름**]

   개인정보 항목 확인
        ▼
   ┌──────────────────────────────────────┐
   │ **고유식별정보·비밀번호·바이오정보**    │ → **무조건 암호화**
   │ (주민등록번호·여권·운전면허·외국인번호) │   (저장·전송 모두)
   └──────────────────────────────────────┘
        ▼ (해당 없음)
   ┌──────────────────────────────────────┐
   │ **신용카드번호·계좌번호**              │ → **저장 시 암호화**
   └──────────────────────────────────────┘
        ▼
   ┌──────────────────────────────────────┐
   │ 기타 개인정보                          │ → **위험도 분석** 결과에
   │                                       │   따라 암호화 여부 결정
   └──────────────────────────────────────┘

2. 저장 시 암호화 (고시 제7조 제1~4항)​

대상 정보암호화 요건근거
고유식별정보· 주민등록번호 — 저장 시 반드시 암호화(예외 없음)
· 여권번호·운전면허번호·외국인등록번호 — 인터넷 구간·DMZ 저장 시 암호화, 내부망 저장 시 위험도 분석 후 결정		제7조 제2·4항
비밀번호일방향 암호화(복호화 불가) 하여 저장 — 해시 함수 사용제7조 제1항
바이오정보지문·홍채·얼굴 등 생체인식정보 → 암호화 저장제7조 제1항
신용카드번호·
계좌번호		암호화하여 저장제7조 제1항
기타 개인정보인터넷 구간·DMZ에 저장 시 암호화
내부망 저장 시 위험도 분석 후 결정		제7조 제3·4항
   [**저장 위치별 암호화 요구 수준**]

   ┌─────────────────────────────────────────────┐
   │ **[인터넷 구간 / DMZ]**                      │
   │  · 고유식별정보 ─────────▶ **암호화 필수**     │
   │  · 기타 개인정보 ────────▶ **암호화 필수**     │
   ├─────────────────────────────────────────────┤
   │ **[내부망]**                                 │
   │  · **주민등록번호** ──────▶ **암호화 필수**    │
   │    (위치 무관, 예외 없음)                     │
   │  · 그 외 고유식별정보 ────▶ **위험도 분석 후** │
   │  · 기타 개인정보 ────────▶ **위험도 분석 후**  │
   └─────────────────────────────────────────────┘

   ※ **위험도 분석**(제7조 제4항) : 개인정보위가 제공하는
     **「개인정보 위험도 분석 기준」** 또는 **암호화 미적용 시
     위험 수용 근거**를 문서화해야 함

3. 전송 시 암호화 (고시 제7조 제5·6항)​

구분요구사항
정보통신망 전송개인정보를 정보통신망을 통해 송·수신 시 암호화(TLS/SSL, VPN)
인증정보 전송비밀번호·인증정보는 반드시 암호화 전송
보조저장매체 반출USB·외장하드 등으로 개인정보 반출 시 암호화
업무용 컴퓨터·모바일개인정보를 저장하는 업무용 PC·모바일 기기는 암호화(디스크 암호화 또는 문서 암호화)

4. 암호화 방식 및 알고리즘​

 ┌────────── **암호화 방식 분류** ──────────┐
 │                                          │
 │ **[일방향 암호화]** — 복호화 불가          │
 │  · 대상 : **비밀번호**                    │
 │  · 알고리즘 : **SHA-256 이상**            │
 │  · ★**Salt + 반복 연산 필수**★            │
 │    (**PBKDF2, bcrypt, scrypt, Argon2**)  │
 │    ⇒ 단순 해시는 **레인보우 테이블** 취약  │
 │                                          │
 │ **[양방향 암호화]** — 복호화 가능          │
 │  · 대칭키 : **AES-128/192/256**, **ARIA**,│
 │            **SEED, LEA**(국산 알고리즘)   │
 │            → **대용량 데이터 암호화**      │
 │  · 비대칭키 : **RSA-2048 이상**, **ECC**  │
 │            → **키 교환·전자서명**          │
 │                                          │
 │ **[전송 구간]**                           │
 │  · **TLS 1.2 이상**(TLS 1.3 권장)         │
 │  · SSL 3.0·TLS 1.0/1.1 **사용 금지**      │
 └──────────────────────────────────────────┘
구분권장 알고리즘사용 금지·지양
일방향(해시)SHA-256/384/512, PBKDF2, bcrypt, Argon2MD5, SHA-1
대칭키AES-128 이상, ARIA, SEED, LEA, HIGHTDES, 3DES(권장 안 함)
비대칭키RSA-2048 이상, ECC-224 이상RSA-1024 이하
전송TLS 1.2/1.3SSL 2.0/3.0, TLS 1.0/1.1

근거 : KISA 「암호 알고리즘 및 키 길이 이용 안내서」, 개인정보 암호화 조치 안내서

5. 암호화 적용 기술 (구현 방식)​

 ┌──────── **DB 암호화 구현 방식 비교** ────────┐
 │                                              │
 │ **① API 방식**(응용프로그램 자체 암호화)      │
 │    App ──[암호화 모듈]──▶ DB                 │
 │    · 장점 : **DB 부하 없음**, 세밀한 제어     │
 │    · 단점 : **애플리케이션 수정 필요**        │
 │                                              │
 │ **② Plug-In 방식**(DB 서버 내 모듈)          │
 │    App ──▶ DB[**암호화 플러그인**]            │
 │    · 장점 : **애플리케이션 수정 최소화**      │
 │    · 단점 : **DB 서버 부하 증가**             │
 │                                              │
 │ **③ TDE 방식**(투명한 데이터 암호화)          │
 │    App ──▶ DB ──▶ [**저장 시 자동 암호화**]   │
 │    · 장점 : **애플리케이션 무수정**, 성능 우수 │
 │    · 단점 : **DB 접근 권한자에게는 평문 노출** │
 │             (내부자 위협 대응 한계)           │
 │                                              │
 │ **④ 파일·디스크 암호화**                      │
 │    · 볼륨·파일 단위 암호화(BitLocker 등)      │
 │    · 물리적 도난 대응, **논리적 접근엔 무력**  │
 │                                              │
 │ **⑤ 하이브리드**(API + Plug-In)               │
 │    · 컬럼 특성별 방식 조합                    │
 └──────────────────────────────────────────────┘

6. 암호키 관리 (핵심 성공요인)​

   [**암호키 관리의 중요성**]

   "**암호화의 안전성은 알고리즘이 아니라 키 관리에 달려있다**"
   (케르크호프스 원리 — 알고리즘은 공개되어도 키만 안전하면 됨)

   ┌──────────────────────────────────────┐
   │ **① 키 생성**                          │
   │    **안전한 난수 생성기**(CSPRNG) 사용  │
   │            ▼                          │
   │ **② 키 보관**                          │
   │    · **소스코드·설정파일 하드코딩 금지**★│
   │    · **HSM**(하드웨어 보안모듈) 또는    │
   │      **KMS**(키 관리 시스템) 사용       │
   │    · **데이터와 키를 분리 저장**         │
   │            ▼                          │
   │ **③ 키 사용**                          │
   │    **접근 권한 최소화**, 사용 이력 기록  │
   │            ▼                          │
   │ **④ 키 변경(Rotation)**                │
   │    **주기적 교체**, 유출 의심 시 즉시    │
   │            ▼                          │
   │ **⑤ 키 폐기**                          │
   │    **안전한 삭제**(복구 불가하게)        │
   │    ⇒ 키 폐기 = **암호화 데이터 파기 효과**│
   └──────────────────────────────────────┘
키 관리 요구사항내용
분리 보관암호키를 암호화된 데이터와 물리적·논리적으로 분리 저장
접근 통제키 접근 권한자 최소화, 이중 통제(Two-Person Rule)
HSM/KMS 활용하드웨어 보안모듈 또는 클라우드 KMS로 키 보호
암호화 키 암호화데이터 암호화 키(DEK)를 마스터 키(KEK)로 이중 암호화
이력 관리키 생성·사용·변경·폐기 전 이력 기록

8. 암호화 적용 시 고려사항​

고려사항내용
① 성능 영향암호화 컬럼은 인덱스 활용 제약 → 조회 성능 저하 → 부분 암호화·형태보존암호(FPE)·검색 가능 암호 검토
② 검색·정렬 제약LIKE 검색·범위 조회 곤란 → 검색용 해시 컬럼 병행 등 설계 필요
③ 기존 데이터 마이그레이션대용량 일괄 암호화 시 서비스 중단 최소화 계획 필수
④ 백업·로그 누락 주의백업 파일·로그·임시 파일에 평문 잔존하는 사례 다수 → 전 구간 점검
⑤ 내부자 위협TDE는 DB 접근 권한자에게 평문 노출 → 접근통제·접속기록과 병행 필요
⑥ 클라우드 환경CSP 제공 암호화(SSE·KMS) 사용 시 키 관리 주체 명확화(BYOK/HYOK 검토)
⑦ 검증필 암호모듈공공기관은 KCMVP 검증필 암호모듈 사용 의무
⑧ 양자내성암호양자컴퓨터 대비 PQC(Post-Quantum Cryptography) 전환 로드맵 사전 검토

위반 사항제재

민사 책임손해배상, 법정손해배상(최대 300만원), 징벌적 손해배상(최대 5배)

동향내용

공공시스템운영기관 특례 신설대규모 공공시스템에 접근권한·접속기록 강화 요건 추가(제14~16조)

과징금 산정 기준 강화관련 매출액 → 전체 매출액 3% 기준으로 전환
AI·클라우드 대응AI 학습데이터의 개인정보 처리, 클라우드 책임 공유 모델 하 안전조치 가이드 확대

Ⅴ. 결론​

「개인정보의 안전성 확보조치 기준」은 개인정보보호법 제29조가 규정한 추상적인 '안전조치의무'를 구체적이고 검증 가능한 통제 항목으로 명시한 실무 규범이다. 특히 2023년 9월 전면 개정으로 정보통신서비스 제공자 특례가 폐지되고 모든 개인정보처리자에게 단일 기준이 적용되면서, 기업 규모나 업종에 관계없이 동일한 수준의 보호조치가 요구되고 있다.

내부관리계획은 개별 기술적 조치들의 근거가 되는 최상위 정책 문서이자 개인정보보호 거버넌스의 출발점이다. 그러나 실무에서 가장 흔한 문제는 템플릿을 그대로 사용하여 실제 개인정보 처리 현황과 괴리된 형식적 문서가 되는 것이다. 내부관리계획의 실효성은 ① 개인정보 흐름도 기반의 실제 현황 반영, ② 대표자 승인을 통한 자원·권한 확보, ③ CPO의 연 1회 이상 이행 점검과 개선조치 기록이라는 세 가지 요건이 충족될 때 확보된다. 특히 점검 결과와 개선조치 문서는 사고 발생 시 관리적 노력을 입증하는 핵심 자료가 된다.

암호화는 접근통제·접속기록 등 다른 통제가 모두 무력화된 후에도 작동하는 최후의 방어선이다. 유출 사고에서 암호화 여부는 실질적 피해 규모를 결정하며, 과징금 산정에서도 중요한 고려 요소가 된다. 다만 실무에서 반드시 유의할 점은 암호화의 안전성이 알고리즘이 아니라 키 관리에 달려 있다는 것이다. AES-256으로 암호화했더라도 암호키를 소스코드나 설정파일에 하드코딩했다면 사실상 암호화하지 않은 것과 다름없으며, 실제 유출 사고에서 반복적으로 확인되는 취약점이다. 따라서 HSM·KMS를 통한 키 분리 보관, 데이터 암호화 키(DEK)의 마스터 키(KEK) 이중 암호화, 주기적 키 교체가 병행되어야 한다.

또한 암호화 적용 범위에서 자주 누락되는 영역이 백업 파일·로그·임시 파일·개발 테스트 DB이다. 운영 DB만 암호화하고 백업이나 로그에 평문이 잔존하는 사례가 빈번하므로, 개인정보 흐름도를 기준으로 저장 지점을 전수 식별하는 작업이 선행되어야 한다.

끝으로 기술사 관점에서 강조할 점은, 이러한 조치들이 법적 최소 기준(Minimum Requirement)이라는 사실이다. 고시 준수는 면책이 아니라 출발점이며, 위험도 분석에 기반하여 자사 환경에 필요한 추가 통제를 스스로 설계·이행하는 것이 진정한 안전성 확보이다. 특히 클라우드·AI 환경에서는 책임 공유 모델 하의 통제 경계 명확화와 AI 학습데이터의 개인정보 처리 적법성 같은 새로운 쟁점이 부상하고 있어, 고시 항목의 기계적 이행을 넘어선 위험 기반 접근(Risk-based Approach) 이 요구된다.

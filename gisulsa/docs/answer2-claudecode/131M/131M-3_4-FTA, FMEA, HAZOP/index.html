FTA, FMEA, HAZOP

문제​

4.소프트웨어 안전성 분석의 필요성과 다음의 분석 기법을 설명하시오.
가.FTA(Fault Tree Analysis)
나.FMEA(Failure Mode and Effects Analysis)
다.HAZOP(Hazard and Operability Analysis)

Ⅰ. 소프트웨어 안전성 분석의 개요 및 필요성​

1. 개념​

소프트웨어 안전성 분석(Software Safety Analysis) 은 소프트웨어의 오동작이 인명·재산·환경에 위해(Hazard)를 초래할 수 있는 시스템에서, 잠재적 위험요소를 체계적으로 식별·평가하고 이를 제거·완화하기 위한 분석 활동이다.

관련 개념정의
위험원(Hazard)사고를 유발할 수 있는 잠재적 상태·조건
결함(Fault)시스템 내부의 비정상 원인(코드 오류 등)
고장(Failure)요구 기능을 수행하지 못하는 관찰 가능한 상태
위험도(Risk)발생 확률 × 심각도(Severity)
안전 무결성 수준
(SIL/ASIL)		요구되는 안전 기능의 신뢰 수준 등급

2. 필요성​

   [소프트웨어 안전성 사고 사례 — 필요성의 근거]

   · **Therac-25**(1985~87) — 방사선 치료기 SW **경쟁 조건(Race Condition)**
     → 과다 방사선 조사, **6명 사상**
   · **Ariane 5**(1996) — 64bit→16bit **형변환 오버플로**
     → 발사 37초 후 폭발, **약 5억 달러 손실**
   · **Toyota 급발진**(2009~) — 스택 오버플로·**Watchdog 미흡** 지적
   · **Boeing 737 MAX**(2018~19) — **MCAS SW** 단일 센서 의존
     → **346명 사망**, 기종 운항 중단
   · **자율주행·의료기기 AI** — 판단 오류가 **즉시 인명 피해**로 직결
        ▼
   ⇒ **소프트웨어는 마모되지 않지만, 설계 결함은 100% 재현된다**
      (하드웨어와 달리 **확률적 고장이 아닌 결정론적 결함**)
필요성 관점내용
인명·재산 보호항공·철도·의료·원자력·자동차 등 안전필수 시스템(Safety-Critical) 확산
SW 비중 증가자동차 SW 코드 1억 라인 이상, 기능의 90%가 SW로 구현
복잡도 증가AI·자율 시스템의 비결정적 동작 → 전수 테스트 불가
규제·인증 요구IEC 61508(기능안전 총괄), ISO 26262(자동차), DO-178C(항공), IEC 62304(의료기기), EN 50128(철도)
경제성결함 수정 비용은 단계가 늦어질수록 기하급수 증가(요구사항 대비 운영 시 100배 이상)
법적 책임제조물 책임법(PL법), 중대재해처벌법 등 책임 입증 자료 필요

3. 안전성 분석 기법의 분류​

   [**분석 방향에 따른 분류**]

   **[Top-Down / 연역적(Deductive)]**
   "**결과(사고)로부터 원인을 추적**"
        **사고(Top Event)**
              ▲
        원인 ─┴─ 원인 ─── 원인
   ⇒ **FTA**, ETA(역방향)
   ⇒ 특정 사고의 **원인 규명**에 강점

   **[Bottom-Up / 귀납적(Inductive)]**
   "**원인(고장)으로부터 결과를 예측**"
        부품 고장 ──▶ 영향 ──▶ **시스템 영향**
   ⇒ **FMEA**, ETA(정방향)
   ⇒ **누락 없는 전수 검토**에 강점

   **[가이드워드 기반 / 창의적 탐색]**
   "**설계 의도로부터의 이탈을 체계적으로 탐색**"
   ⇒ **HAZOP**
   ⇒ **미지의 위험 발굴**에 강점

Ⅱ. FTA (Fault Tree Analysis, 결함수 분석)​

1. 개념 및 특징​

항목내용
정의바람직하지 않은 최상위 사건(Top Event)을 정의하고, 그 사건을 유발하는 원인들을 논리 게이트(AND/OR)로 연결하여 트리 형태로 하향 전개하는 연역적 분석 기법
개발 배경1962년 Bell 연구소 — 미 공군 미니트맨 미사일 발사 제어 시스템 안전성 평가
분석 방향Top-Down(하향식) / 연역적(Deductive)
핵심 질문"이 사고가 일어나려면 무엇이 발생해야 하는가?"
표준IEC 61025, NUREG-0492

2. FTA 구조 및 기호​

 ┌──────────── **FTA 결함수 구조 예시** ────────────┐
 │                                                  │
 │              ┌─────────────────────┐             │
 │              │ **[Top Event]**      │ ← 최상위 사건│
 │              │ **차량 제동 실패**    │   (사고)    │
 │              └──────────┬──────────┘             │
 │                    ┌────▼────┐                   │
 │                    │  **AND** │ ← 모두 발생해야   │
 │                    └────┬────┘   Top 발생        │
 │              ┌──────────┴──────────┐             │
 │      ┌───────▼───────┐    ┌────────▼────────┐    │
 │      │ 주 제동 실패   │    │ **보조 제동 실패**│    │
 │      └───────┬───────┘    └────────┬────────┘    │
 │         ┌────▼────┐           ┌────▼────┐        │
 │         │  **OR**  │           │  **OR**  │        │
 │         └────┬────┘           └────┬────┘        │
 │      ┌───────┴───────┐      ┌──────┴──────┐      │
 │   ┌──▼──┐        ┌──▼──┐  ┌─▼───┐    ┌───▼──┐   │
 │   │**SW**│        │유압 │  │ ECU │    │센서  │   │
 │   │로직 │        │고장 │  │고장 │    │고장  │   │
 │   │오류 │        └─────┘  └─────┘    └──────┘   │
 │   └─────┘        ← **기본사건(Basic Event, 원)** │
 └──────────────────────────────────────────────────┘
기호명칭의미
□사건(Event)중간 사건, 추가 전개 가능
○기본사건(Basic Event)더 이상 전개하지 않는 최하위 원인
◇미전개 사건정보 부족·중요도 낮아 전개 생략
AND 게이트논리곱모든 하위 사건 발생 시 상위 발생 → 확률 곱
OR 게이트논리합하나라도 발생 시 상위 발생 → 확률 합(근사)
억제 게이트조건부특정 조건 충족 시에만 전파

3. 수행 절차 및 분석​

 ┌──────── **FTA 수행 절차** ────────┐
 │                                   │
 │ **① 시스템 정의·범위 설정**        │
 │        ▼                          │
 │ **② Top Event 정의**               │
 │    (가장 치명적인 사고 선정)       │
 │        ▼                          │
 │ **③ 결함수 작성**(논리 전개)       │
 │    원인을 AND/OR로 하향 분해       │
 │    → **기본사건까지 전개**          │
 │        ▼                          │
 │ **④ 정성적 분석**                  │
 │    **최소 절단집합(Minimal Cut Set)**│
 │    = Top Event를 유발하는          │
 │      **최소 원인 조합**             │
 │        ▼                          │
 │ **⑤ 정량적 분석**(선택)            │
 │    기본사건 확률 → **Top 발생확률** │
 │    · **중요도 분석**(Importance)   │
 │        ▼                          │
 │ **⑥ 대책 수립·검증**               │
 │    단일 절단집합 제거(**이중화**)   │
 └───────────────────────────────────┘
분석 개념내용
최소 절단집합
(Minimal Cut Set)		Top Event를 발생시키는 최소 기본사건 조합 — 1차 절단집합(단일 고장)이 있으면 단일 장애점(SPOF) → 최우선 제거 대상
최소 경로집합
(Minimal Path Set)		Top Event가 발생하지 않기 위해 정상이어야 할 최소 사건 집합
확률 계산AND : P = P₁ × P₂ (독립 시) / OR : P = 1 − (1−P₁)(1−P₂)
중요도 분석Fussell-Vesely, Birnbaum — 어느 기본사건이 Top에 가장 기여하는가

4. 장단점 및 활용​

구분내용
장점· 특정 사고의 원인을 논리적·체계적으로 규명
· 정량적 확률 분석 가능 → SIL 검증에 활용
· 단일 장애점(SPOF) 식별에 탁월
· 시각적 표현으로 이해관계자 소통 용이
· 다중 고장 조합(AND) 분석 가능
단점· Top Event를 미리 알아야 함 → 예상 못한 위험은 발견 불가
· 대규모 시스템은 트리가 방대해져 관리 곤란
· 분석자의 경험·주관에 크게 의존
· 소프트웨어는 고장 확률 산출이 어려움(결정론적 결함)
· 시간 순서·동적 거동 표현 한계(→ Dynamic FTA 필요)
활용원자력 PSA, 항공기 안전성 평가, ISO 26262 ASIL 검증, 사고 원인 조사, 이중화 설계 검증

Ⅲ. FMEA (Failure Mode and Effects Analysis, 고장모드 영향분석)​

1. 개념 및 특징​

항목내용
정의시스템의 각 구성요소에서 발생 가능한 고장모드(Failure Mode)를 식별하고, 그 원인과 시스템에 미치는 영향을 분석하여 위험 우선순위를 결정하는 귀납적 분석 기법
개발 배경1949년 미군 MIL-P-1629, NASA 아폴로 계획에서 체계화, 이후 자동차(AIAG-VDA)로 확산
분석 방향Bottom-Up(상향식) / 귀납적(Inductive)
핵심 질문"이 부품(모듈)이 고장 나면 무슨 일이 생기는가?"
표준IEC 60812, AIAG-VDA FMEA Handbook(2019), ISO 26262

2. FMEA 유형 및 분석 양식​

유형대상내용
System FMEA시스템 아키텍처서브시스템 간 인터페이스 고장
Design FMEA(DFMEA)설계설계 결함으로 인한 고장
Process FMEA(PFMEA)제조·운영 프로세스공정 오류
Software FMEA소프트웨어 모듈로직 오류, 예외 미처리, 자원 고갈
   [**Software FMEA 분석 양식 예시**]

   ┌─────┬────────┬────────┬────────┬───┬───┬───┬─────┬────────┐
   │모듈 │**고장모드**│ **원인** │ **영향** │**S**│**O**│**D**│**RPN**│ **대책** │
   ├─────┼────────┼────────┼────────┼───┼───┼───┼─────┼────────┤
   │센서 │값 미수신│통신단절│제어불가│ 9 │ 3 │ 4 │**108**│워치독+  │
   │입력 │        │        │(위험)  │   │   │   │     │**대체값**│
   ├─────┼────────┼────────┼────────┼───┼───┼───┼─────┼────────┤
   │제어 │**오버플로**│형변환  │**오동작**│10 │ 2 │ 7 │**140**│**정적분석**│
   │로직 │        │오류    │        │   │   │   │  ▲  │+범위검사│
   ├─────┼────────┼────────┼────────┼───┼───┼───┼─────┼────────┤
   │메모리│누수    │해제누락│**시스템**│ 8 │ 4 │ 6 │**192**│자원관리 │
   │관리 │        │        │**정지** │   │   │   │**최우선**│+모니터링│
   └─────┴────────┴────────┴────────┴───┴───┴───┴─────┴────────┘

   **RPN**(Risk Priority Number) = **S × O × D**
   · **S**(Severity, 심각도)    1~10 : 영향의 치명도
   · **O**(Occurrence, 발생도)  1~10 : 발생 빈도
   · **D**(Detection, 검출도)   1~10 : **검출 어려움**(높을수록 발견 곤란)
   ⇒ **RPN이 높은 순으로 개선 우선순위 부여**

AIAG-VDA(2019) 개정 : RPN의 한계(곱셈으로 인한 왜곡)를 보완하여 AP(Action Priority, H/M/L) 방식 도입 — 심각도를 우선 고려하는 매트릭스 판정

3. 수행 절차​

 ┌──────── **FMEA 수행 절차** ────────┐
 │                                    │
 │ **① 분석 범위·시스템 구조 정의**    │
 │    (기능 분해, 블록 다이어그램)     │
 │        ▼                           │
 │ **② 기능 분석** — 각 요소의 기능 정의│
 │        ▼                           │
 │ **③ 고장모드 식별**                 │
 │    "기능을 못 하는 방식" 열거       │
 │    (미동작·오동작·지연·부분동작)    │
 │        ▼                           │
 │ **④ 고장 원인·영향 분석**           │
 │    · 국소 영향 / 상위 영향 / **최종 영향**│
 │        ▼                           │
 │ **⑤ 위험 평가**(S·O·D 평점)         │
 │    → **RPN 또는 AP 산출**           │
 │        ▼                           │
 │ **⑥ 개선대책 수립·실행**            │
 │    (설계 변경·검출 수단 추가)       │
 │        ▼                           │
 │ **⑦ 재평가·문서화**                 │
 │    대책 적용 후 **RPN 재산정**       │
 │    ⇒ **지속 갱신(Living Document)** │
 └────────────────────────────────────┘

4. 장단점 및 활용​

구분내용
장점· 모든 구성요소를 빠짐없이 검토 → 누락 방지
· RPN 기반 우선순위로 자원 배분 합리화
· 설계 초기 적용 시 예방적 효과 큼
· 표준 양식으로 문서화·인증 근거 확보
· 조직의 지식 축적(설계 노하우 자산화)
단점· 단일 고장 중심 → 복합 고장(다중 고장 조합) 분석 취약
· 구성요소가 많으면 분석 공수 방대
· S·O·D 평점의 주관성, RPN의 통계적 왜곡(3×3×9=81 vs 9×3×3=81)
· 시스템 전체 관점의 위험 파악 곤란
· 형식적 작성 시 문서를 위한 문서로 전락
활용자동차 ISO 26262(부품·SW 모듈 분석), 의료기기 위험관리(ISO 14971), 항공·방산, 제조 공정 개선

Ⅳ. HAZOP (Hazard and Operability Analysis, 위험 및 운전분석)​

1. 개념 및 특징​

항목내용
정의시스템을 노드(Node)로 분할하고, 각 노드의 설계 의도(Design Intent)에 가이드워드(Guide Word)를 조합하여 '의도로부터의 이탈(Deviation)'을 체계적으로 도출·평가하는 정성적 분석 기법
개발 배경1960년대 영국 ICI사 — 화학 플랜트 공정 안전 분석, 이후 SW·제어시스템으로 확장
분석 방향가이드워드 기반 브레인스토밍(정성적)
핵심 질문"설계 의도대로 되지 않으면 어떻게 되는가?"
표준IEC 61882
수행 방식다학제 전문가 워크숍(설계·운영·안전·SW 전문가)

3. 소프트웨어 적용 시 고려사항​

고려사항내용
① SW 고장의 특성 인식SW는 마모되지 않고 확률적으로 고장나지 않음 → 설계 결함이 100% 재현 → 확률 기반 정량 분석의 한계 인식
② 고장률 데이터 부재HW와 달리 SW MTBF 산출 곤란 → 정성적 분석(HAZOP) 비중 확대, 개발 프로세스 성숙도(SIL 요구) 로 대체
③ 조기 적용요구사항·설계 단계 적용 시 효과 극대화 → 코딩 후 분석은 수정 비용 급증
④ 정적 분석 도구 연계MISRA C/C++, CERT 코딩 규칙, 정적 분석(Coverity·Polyspace)으로 결함 사전 차단
⑤ 안전 아키텍처 설계이중화·다양성(Diversity)·워치독·안전 상태(Safe State) 전이·감시 제어(Monitor) 등 구조적 대책
⑥ 추적성 확보위험원 → 안전요구사항 → 설계 → 코드 → 테스트의 양방향 추적성 — 인증의 핵심 요건
⑦ AI 시스템의 한계딥러닝은 내부 로직을 분해할 수 없어 FTA/FMEA 적용 곤란 → SOTIF(ISO 21448), 시나리오 기반 검증, STPA 등 신기법 필요
⑧ 형식적 수행 경계인증 통과용 문서 작성에 그치면 무의미 → 개발 활동과 실질적으로 연동

Ⅵ. 결론​

소프트웨어 안전성 분석은 소프트웨어의 오동작이 곧 인명 피해로 직결되는 시대에 필수적인 공학적 활동이다. Therac-25, Ariane 5, Boeing 737 MAX 사고가 공통적으로 보여준 것은, 개별 부품은 정상이었으나 소프트웨어 설계 결함과 안전 아키텍처의 부재가 참사로 이어졌다는 점이다.

세 기법은 경쟁 관계가 아니라 서로 다른 사각지대를 보완하는 관계이다. FTA는 사고를 알아야 원인을 찾을 수 있고(Top Event 전제), FMEA는 전수 검토는 가능하나 다중 고장 조합에 취약하며, HAZOP은 미지의 위험을 발굴하지만 정량화가 불가능하다. 따라서 실무에서는 HAZOP으로 위험을 발굴하고 → FMEA로 빠짐없이 검토하며 → FTA로 치명 사고의 원인을 논리적·정량적으로 규명하는 3단계 통합 적용이 바람직하다.

특히 소프트웨어에 적용할 때 유의할 점은 하드웨어 기반 신뢰성 이론이 그대로 통용되지 않는다는 것이다. 소프트웨어는 마모되지 않고 확률적으로 고장 나지 않으며, 결함이 있으면 동일 조건에서 항상 재현된다. 따라서 고장률 기반 정량 분석보다 정성적 분석(HAZOP)과 개발 프로세스의 엄격성(SIL/ASIL 요구 프로세스), 그리고 이중화·안전 상태 전이 같은 구조적 안전 아키텍처가 실질적 안전성을 좌우한다.

마지막으로 AI·자율 시스템의 확산은 기존 안전성 분석 기법의 근본적 한계를 드러내고 있다. 딥러닝 모델은 내부 로직을 논리적으로 분해할 수 없어 FTA·FMEA를 적용하기 어려우며, "고장이 없어도 의도된 기능 자체의 한계로 위험이 발생하는" 상황을 다루기 위해 SOTIF(ISO 21448) 와 시스템 이론 기반 STPA(System-Theoretic Process Analysis) 같은 새로운 접근이 부상하고 있다. 기술사는 전통 기법의 원리를 정확히 이해하는 동시에, AI 시대의 안전성 분석이 개별 컴포넌트 고장 분석에서 시스템 수준의 제어 구조 분석으로 이동하고 있다는 흐름을 함께 인식해야 한다.

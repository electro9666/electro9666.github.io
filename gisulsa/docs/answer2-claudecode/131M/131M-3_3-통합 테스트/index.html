통합 테스트

문제​

3.통합 테스트(Integration Test)에 대하여 다음을 설명하시오.
가.비점진적 통합 방식과 점진적 통합 방식
나.하향식(Top Down) 통합 테스트와 상향식(Bottom Up) 통합 테스트
다.테스트 드라이버(Test Driver)와 테스트 스텁(Test Stub)

Ⅰ. 개요​

1. 통합 테스트의 개념​

통합 테스트(Integration Test) 는 단위 테스트를 통과한 모듈들을 결합하여, 모듈 간 인터페이스와 상호작용이 설계대로 동작하는지 검증하는 테스트 단계이다. 단위 테스트가 개별 모듈의 내부 로직을 검증한다면, 통합 테스트는 모듈 사이의 연결(Interface)에서 발생하는 결함을 목표로 한다.

   [**V-모델상 통합 테스트의 위치**]

   요구사항 분석 ────────────────────▶ **인수 테스트**(사용자 요구 검증)
        │                                    ▲
        ▼                                    │
   시스템 설계 ─────────────────────▶ **시스템 테스트**(전체 기능·성능)
        │                                    ▲
        ▼                                    │
   **아키텍처(상세) 설계** ───────────▶ ★**통합 테스트**★(**모듈 간 인터페이스**)
        │                                    ▲
        ▼                                    │
   모듈 설계 ───────────────────────▶ **단위 테스트**(모듈 내부 로직)
        │                                    ▲
        └──────── **구현(코딩)** ────────────┘

2. 필요성 — 통합 결함의 유형​

   [단위 테스트를 모두 통과해도 발생하는 결함]

   · **인터페이스 불일치** — 파라미터 순서·타입·개수 상이
   · **데이터 형식 오류** — 단위(원/달러), 인코딩, 날짜 형식 차이
   · **전역 데이터 손상** — 한 모듈이 공유 자원을 훼손
   · **타이밍·동시성 문제** — 호출 순서·경쟁 조건(Race Condition)
   · **누적 오차** — 개별 모듈의 미세 오차가 결합 시 증폭
   · **예외 처리 불일치** — 하위 모듈 예외를 상위가 처리하지 않음
        ▼
   ⇒ **"부분의 합이 전체가 아니다"** — 통합 테스트의 존재 이유

Ⅱ. 비점진적 통합 방식과 점진적 통합 방식​

1. 개념 비교​

 ┌──────── **통합 방식의 두 가지 접근** ────────┐
 │                                              │
 │ **[비점진적 통합 — 빅뱅(Big Bang)]**          │
 │                                              │
 │   모듈A  모듈B  모듈C  모듈D  모듈E           │
 │     │     │     │     │     │                │
 │     └─────┴──**한 번에 결합**──┴─────┘        │
 │                 ▼                            │
 │            **전체 시스템 테스트**             │
 │   ⇒ 결함 발생 시 **원인 모듈 추적 곤란**       │
 │                                              │
 │ ─────────────────────────────────────────    │
 │                                              │
 │ **[점진적 통합 — Incremental]**               │
 │                                              │
 │   ① A + B → 테스트 ✔                         │
 │   ② (A+B) + C → 테스트 ✔                     │
 │   ③ (A+B+C) + D → 테스트 ✘ ← **D가 원인!**    │
 │   ④ (A+B+C+D) + E → 테스트                   │
 │   ⇒ **한 번에 하나씩 추가** → 결함 국소화      │
 └──────────────────────────────────────────────┘

2. 상세 비교​

비교 기준비점진적 통합(빅뱅)점진적 통합(Incremental)
개념모든 모듈을 한 번에 결합하여 테스트모듈을 하나씩 추가하며 단계적 테스트
드라이버·스텁거의 불필요(전체가 완성된 상태)필요(미완성 모듈 대체)
테스트 시작 시점모든 모듈 완성 후(늦음)일부 완성 시점부터(조기 착수)
결함 발견 시점후반부에 집중초기부터 지속적
오류 격리·원인 추적매우 어려움(어느 모듈 문제인지 불명)용이(직전 추가 모듈이 유력)
디버깅 비용높음낮음
테스트 횟수적음(1회)많음(모듈 수만큼)
초기 준비 비용낮음높음(드라이버·스텁 개발)
회귀 테스트불필요(1회)매번 필요
적용 상황소규모·단순 시스템, 모듈 수 적음, 기존 검증된 시스템대규모·복잡 시스템, 신규 개발, 대부분의 실무 프로젝트
위험도매우 높음(통합 지옥, Integration Hell)낮음(위험 분산)
일정 예측성낮음(결함 집중 시 일정 붕괴)높음

3. 점진적 통합의 세부 유형​

유형방식특징
하향식(Top Down)상위 모듈부터 하위로 통합스텁 필요, 주요 기능 조기 검증
상향식(Bottom Up)하위 모듈부터 상위로 통합드라이버 필요, 하부 모듈 철저 검증
혼합식(Sandwich)중간층 기준 상·하 동시 진행드라이버+스텁 모두 필요, 시간 단축
연쇄식(Thread)하나의 기능 흐름(스레드) 단위 통합핵심 시나리오 우선 검증, 애자일 적합
기능 기반(Function)관련 기능 그룹 단위 통합업무 단위 검증 용이

실무 관점 : 현대 CI/CD 환경에서는 커밋마다 자동 통합·테스트를 수행하는 지속적 통합(CI) 이 사실상 극단적 점진 통합으로, 빅뱅 통합의 위험을 근본적으로 제거한다.

Ⅲ. 하향식 통합 테스트와 상향식 통합 테스트​

1. 하향식 통합 테스트 (Top Down Integration)​

   [**하향식 통합 — 상위 모듈부터 아래로**]

   **[Step 1]** 최상위 모듈 + 하위는 **스텁(Stub)** 으로 대체

              ┌─────────┐
              │ **Main** │ ← 실제 모듈
              └────┬────┘
           ┌───────┴───────┐
      ┌────▼────┐     ┌────▼────┐
      │ **Stub A**│     │ **Stub B**│ ← **가짜 하위 모듈**
      └─────────┘     └─────────┘

   **[Step 2]** 스텁을 실제 모듈로 **하나씩 교체**

              ┌─────────┐
              │  Main   │
              └────┬────┘
           ┌───────┴───────┐
      ┌────▼────┐     ┌────▼────┐
      │ **모듈A** │     │ Stub B  │ ← A를 실제 모듈로 교체
      └────┬────┘     └─────────┘
        ┌──┴──┐
   ┌────▼──┐ ┌▼──────┐
   │**Stub C**│ │**Stub D**│ ← 새로운 하위 스텁 추가
   └───────┘ └───────┘

   **[Step 3]** 모든 스텁이 실제 모듈로 대체될 때까지 반복
             (**깊이 우선(DFS)** 또는 **너비 우선(BFS)** 순서)
항목내용
개념최상위 제어 모듈부터 시작하여 하위 모듈 방향으로 통합, 미완성 하위 모듈은 스텁으로 대체
필요 도구스텁(Stub)
통합 순서깊이 우선(DFS) / 너비 우선(BFS) 방식 선택
장점· 주요 제어 흐름·상위 기능을 조기 검증
· 초기부터 동작하는 시스템 형태(프로토타입) 확보 → 이해관계자 시연 가능
· 설계 결함을 초기에 발견(구조적 오류 조기 노출)
· 상위 모듈이 여러 번 반복 테스트되어 신뢰성 높음
단점· 스텁 작성 부담(하위 모듈 수만큼 필요)
· 스텁이 실제 로직을 반영하지 못해 검증 한계
· 하위 모듈 검증이 늦어짐 → 하위에 중대 결함 시 상위 재설계 위험
· 입출력이 하위에 집중된 시스템은 의미 있는 테스트 곤란
적합 상황제어 구조가 중요한 시스템, 상위 설계 검증이 우선인 경우, 데모·프로토타입 필요 시

2. 상향식 통합 테스트 (Bottom Up Integration)​

   [**상향식 통합 — 하위 모듈부터 위로**]

   **[Step 1]** 최하위 모듈을 **클러스터**로 묶고 **드라이버(Driver)** 로 호출

              ┌──────────────┐
              │ **Test Driver**│ ← **가짜 상위 모듈**(호출자)
              └───────┬──────┘
              ┌───────┴───────┐
         ┌────▼────┐     ┌────▼────┐
         │ **모듈C** │     │ **모듈D** │ ← 실제 하위 모듈
         └─────────┘     └─────────┘
                (**클러스터 1**)

   **[Step 2]** 드라이버를 **실제 상위 모듈**로 교체, 상위 드라이버 추가

              ┌──────────────┐
              │ **Test Driver**│
              └───────┬──────┘
              ┌───────▼───────┐
              │   **모듈A**    │ ← 드라이버를 실제 모듈로 교체
              └───────┬───────┘
              ┌───────┴───────┐
         ┌────▼────┐     ┌────▼────┐
         │  모듈C  │     │  모듈D  │
         └─────────┘     └─────────┘

   **[Step 3]** 최상위 모듈까지 반복 → 드라이버 불필요 시점에 종료
항목내용
개념최하위 모듈부터 시작하여 상위 방향으로 통합, 미완성 상위 모듈은 드라이버로 대체
필요 도구드라이버(Driver)
통합 순서하위 모듈을 클러스터(Cluster/Build) 단위로 묶어 상향 진행
장점· 하위 유틸리티·핵심 연산 모듈을 철저히 검증
· 드라이버가 스텁보다 작성이 용이(단순 호출·결과 출력)
· 하위 모듈 병렬 개발·테스트 가능 → 일정 단축
· 입출력 처리 모듈 검증에 유리
단점· 전체 시스템 형태를 늦게 확인(최상위 통합까지 기다려야 함)
· 주요 제어 흐름·설계 결함이 후반에 발견 → 수정 비용 큼
· 이해관계자에게 조기 시연 불가
· 드라이버 개발 부담
적합 상황하위 모듈의 신뢰성이 중요한 시스템(라이브러리·연산 엔진), 상향 개발 진행 시, 객체지향 시스템

3. 하향식 vs 상향식 비교​

비교 기준하향식(Top Down)상향식(Bottom Up)
통합 방향상위 → 하위하위 → 상위
필요 모듈스텁(Stub)드라이버(Driver)
검증 우선순위주요 제어 흐름·설계하위 기능·연산 정확성
시스템 조기 가시화가능(초기 시연)불가(후반에야 확인)
설계 결함 발견조기 발견후반 발견(위험)
하위 모듈 검증늦음철저·조기
가짜 모듈 작성 난이도높음(스텁이 로직 모방 필요)낮음(드라이버는 단순 호출)
병렬 개발 지원제한적우수
적합 개발 방식하향식 설계·개발상향식 개발, 객체지향
주요 위험스텁의 불충분한 시뮬레이션상위 설계 결함의 늦은 발견

4. 혼합식(Sandwich) 통합 — 절충안​

   [**Sandwich 통합 — 양쪽에서 동시 진행**]

   **[상위층]** ── **하향식 통합**(스텁 사용) ──┐
                                               │
   **[중간층(Target Layer)]** ◀─────── **만나는 지점**
                                               │
   **[하위층]** ── **상향식 통합**(드라이버 사용) ──┘

   [장점] · **양방향 동시 진행** → **테스트 기간 단축**
          · 상위 설계 검증 + 하위 신뢰성 확보 **동시 달성**
   [단점] · **드라이버·스텁 모두 필요** → 비용 증가
          · 중간층 검증이 상대적으로 취약, **관리 복잡**
   [적용] **대규모 시스템**, 계층이 뚜렷한 아키텍처

Ⅳ. 테스트 드라이버와 테스트 스텁​

1. 개념 및 구조​

 ┌───────── **드라이버와 스텁의 위치** ─────────┐
 │                                              │
 │        ┌────────────────────┐                │
 │        │ **테스트 드라이버**  │ ← **상위 모듈** │
 │        │   (Test Driver)    │    **대체**     │
 │        │  · 데이터 입력      │                │
 │        │  · 모듈 호출        │                │
 │        │  · 결과 출력·비교   │                │
 │        └─────────┬──────────┘                │
 │                  │ 호출                       │
 │                  ▼                           │
 │        ┌────────────────────┐                │
 │        │  ★ **테스트 대상**   │  ← 실제 검증   │
 │        │      모듈           │     대상       │
 │        └─────────┬──────────┘                │
 │                  │ 호출                       │
 │                  ▼                           │
 │        ┌────────────────────┐                │
 │        │  **테스트 스텁**     │ ← **하위 모듈** │
 │        │    (Test Stub)     │    **대체**     │
 │        │  · 최소 기능만 구현 │                │
 │        │  · **고정값 반환**   │                │
 │        └────────────────────┘                │
 │                                              │
 │  ⇒ 둘 다 **테스트를 위한 임시 가상 모듈**       │
 │    (Test Harness / Scaffolding)              │
 └──────────────────────────────────────────────┘

2. 테스트 드라이버 (Test Driver)​

항목내용
정의테스트 대상 모듈을 호출하는 상위 모듈의 역할을 대신하는 가상 모듈
역할· 테스트 데이터(입력값) 제공
· 대상 모듈 호출·실행
· 결과 수집·출력, 기대값과 비교·검증
사용 시점상향식(Bottom Up) 통합 — 상위 모듈이 아직 없을 때
특징실제 로직 불필요, 단순 호출·출력 코드 → 작성 용이
예시JUnit @Test 메소드, main() 테스트 코드, 테스트 스크립트
   [드라이버 예시 — 하위 모듈 calcTax() 검증]

   public class TaxDriver {                    // ← **가상의 상위 모듈**
       public static void main(String[] args) {
           TaxModule m = new TaxModule();
           int result = m.**calcTax(10000)**;   // ① 입력 제공·호출
           System.out.println(result);          // ② 결과 출력
           assert result == 1000;               // ③ 기대값 비교
       }
   }

3. 테스트 스텁 (Test Stub)​

항목내용
정의테스트 대상 모듈이 호출하는 하위 모듈의 역할을 대신하는 가상 모듈
역할· 호출을 정상적으로 수락
· 미리 정해진 고정값(Hard-coded) 반환
· 호출 여부·파라미터 기록(추적용)
사용 시점하향식(Top Down) 통합 — 하위 모듈이 아직 없을 때
특징실제 로직 없음, 최소 기능만 구현 → 완전한 검증 불가
예시결제 API 스텁(항상 "승인" 반환), DB 조회 스텁(고정 레코드 반환)
   [스텁 예시 — 미완성 결제 모듈 대체]

   public class PaymentStub implements Payment {   // ← **가상의 하위 모듈**
       public Result pay(int amount) {
           return new Result(**"SUCCESS"**, 200);   // **항상 고정값 반환**
       }                                            // (실제 결제 로직 없음)
   }

4. 드라이버와 스텁 비교​

비교 기준테스트 드라이버(Driver)테스트 스텁(Stub)
대체 대상상위 모듈(호출자)하위 모듈(피호출자)
위치대상 모듈의 위대상 모듈의 아래
동작대상 모듈을 호출(능동)호출을 받아 응답(수동)
주요 기능입력 제공 · 실행 · 결과 검증고정값 반환, 최소 기능
사용 통합 방식상향식(Bottom Up)하향식(Top Down)
작성 난이도낮음(단순 호출 코드)높음(하위 로직 일부 모방 필요)
개발 비용상대적 저렴높음(하위 모듈 수만큼)
한계실제 상위 로직 미반영실제 동작과 차이 → 검증 신뢰성 제한
혼합식(Sandwich)둘 다 필요

5. 유사 테스트 대역(Test Double) 확장 개념​

종류설명
Dummy전달만 되고 사용되지 않는 객체(파라미터 채우기용)
Stub정해진 값을 반환하는 객체(상태 검증)
SpyStub + 호출 이력을 기록(몇 번 호출됐는지 확인)
Mock기대되는 호출을 사전 정의하고 행위를 검증(Mockito 등)
Fake간단하지만 실제 동작하는 구현(인메모리 DB 등)

실무 관점 : 현대 개발에서는 스텁·드라이버를 수작업으로 만들지 않고 JUnit(드라이버) 과 Mockito·WireMock(스텁/목) 같은 프레임워크로 자동화하며, 외부 시스템 연동은 Testcontainers(실제 컨테이너 기동)나 계약 테스트(Contract Test, Pact) 로 대체하는 추세이다.

Ⅴ. 통합 테스트 수행 시 고려사항 및 결론​

1. 고려사항​

고려사항내용
① 통합 전략의 사전 결정아키텍처·개발 순서·모듈 완성 시점을 고려하여 설계 단계에서 통합 전략 수립
② 인터페이스 명세 우선API 계약(Contract)을 먼저 확정해야 스텁·드라이버 작성 가능 → Contract-First 개발
③ 회귀 테스트 자동화모듈 추가마다 기존 테스트 재수행 필요 → CI 파이프라인 자동화 필수
④ 스텁 신뢰성 한계 인식스텁 통과가 실제 동작 보장 아님 → 실제 모듈 교체 후 재검증 필수
⑤ 테스트 데이터 관리통합 테스트는 DB·외부 연동 포함 → 데이터 초기화·격리 전략 필요
⑥ MSA 환경 대응서비스 수 증가 → E2E 통합 테스트 비용 폭증 → 계약 테스트(Consumer-Driven Contract) 로 전환
⑦ 테스트 피라미드단위 테스트(다수) > 통합 테스트(중간) > E2E(소수) — 역피라미드(아이스크림콘) 안티패턴 경계
⑧ 결함 관리통합 결함은 원인 모듈·인터페이스 명세 오류를 함께 기록하여 재발 방지

2. 결론​

통합 테스트의 존재 이유는 "단위 테스트를 모두 통과한 모듈들의 결합이 반드시 올바르게 동작하지는 않는다" 는 사실에 있다. 인터페이스 불일치, 데이터 형식 차이, 타이밍 문제는 개별 모듈 검증만으로는 결코 드러나지 않으며, 이것이 부분의 합이 전체가 아닌 이유이다.

통합 방식 선택에서 비점진적(빅뱅) 통합은 사실상 실무에서 배제되어야 한다. 테스트 준비 비용은 적지만, 결함 발생 시 원인 모듈을 특정할 수 없어 디버깅 비용이 폭증하고 일정 예측성이 무너지기 때문이다. 점진적 통합은 매 단계마다 직전에 추가한 모듈이 결함의 유력한 원인이 되므로, 오류 격리(Fault Isolation) 효과가 결정적이다.

하향식과 상향식은 우열의 문제가 아니라 검증 우선순위의 문제이다. 주요 제어 흐름과 설계 타당성을 조기에 확인해야 하면 하향식을, 하위 유틸리티·연산 모듈의 정확성이 시스템 신뢰성을 좌우하면 상향식을 택한다. 실무에서는 두 방식의 장점을 취하는 혼합식(Sandwich) 통합이 대규모 시스템에서 가장 널리 쓰인다.

드라이버와 스텁은 테스트를 위한 임시 비계(Scaffolding) 이며, 특히 스텁은 고정값만 반환하므로 스텁 기반 테스트 통과가 실제 동작을 보장하지 않는다는 한계를 반드시 인식해야 한다. 실제 모듈로 교체한 뒤의 재검증이 생략되면 통합 테스트는 형식적 절차에 그친다.

끝으로 CI/CD와 MSA 환경에서 통합 테스트의 양상은 근본적으로 변화하고 있다. 커밋마다 자동 통합·테스트를 수행하는 지속적 통합(CI) 은 사실상 극단적 점진 통합으로서 통합 지옥을 구조적으로 제거했으며, 마이크로서비스 환경에서는 전체 E2E 테스트 비용이 감당 불가능해지면서 소비자 주도 계약 테스트(Consumer-Driven Contract Test) 가 통합 검증의 실질적 대안으로 자리 잡고 있다. 기술사에게 요구되는 판단은 어떤 통합 방식을 아느냐가 아니라, 시스템 아키텍처와 개발 프로세스에 맞는 통합 검증 전략을 설계하는 능력이다.

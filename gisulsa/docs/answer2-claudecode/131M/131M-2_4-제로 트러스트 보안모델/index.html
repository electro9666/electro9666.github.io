제로 트러스트 보안모델

문제​

4.제로 트러스트 보안(Zero Trust Security)모델의 보안원리, 핵심원칙, 적용분야를 트러스트 보안(Trust Security) 모델과 비교하여 설명하시오.

Ⅰ. 개요​

1. 개념​

구분개념
트러스트 보안 모델
(경계 기반, Perimeter Security)		내부 네트워크는 신뢰하고 외부는 불신한다는 전제 하에, 네트워크 경계(Perimeter)에 방화벽·IPS 등 관문형 보안장비를 배치하여 방어하는 전통적 보안 모델
제로 트러스트 보안 모델
(Zero Trust Security)		"절대 신뢰하지 말고 항상 검증하라(Never Trust, Always Verify)" 는 원칙 하에, 위치와 무관하게 모든 접근 요청을 검증하고 최소 권한만 부여하며, 지속적으로 신뢰를 재평가하는 보안 모델

2. 등장배경​

   [경계 기반 모델의 붕괴 — 지켜야 할 '경계'가 사라짐]

   · **클라우드 전환** — 자산이 사내 데이터센터 밖(SaaS·IaaS)에 존재
   · **원격근무·BYOD** — 사용자가 경계 외부에서 접속
   · **모바일·IoT** — 관리되지 않는 디바이스 급증
   · **내부자 위협·측면이동(Lateral Movement)**
     ⇒ 경계 1회 돌파 시 **내부는 무방비**
   · **공급망 공격**(SolarWinds) — 신뢰된 경로로 침투
        ▼
   [사고가 증명한 한계]
   · **Google Aurora 공격**(2009) → Google **BeyondCorp** 착수
   · SolarWinds·Colonial Pipeline → 美 **EO 14028**, 연방기관 ZT 의무화
   · 국내 : **KISA 제로트러스트 가이드라인 1.0/2.0**(2023/2024)
        ▼
   [**제로 트러스트**] — **John Kindervag**(Forrester, 2010) 제안
   **NIST SP 800-207**(2020)로 표준화

Ⅱ. 제로 트러스트의 보안원리​

1. 기본 보안원리​

 ┌────────── **제로 트러스트 보안원리** ──────────┐
 │                                                │
 │ **① 암묵적 신뢰 제거**(No Implicit Trust)       │
 │    네트워크 위치(사내망 여부)가 **신뢰 근거가   │
 │    될 수 없음** → 모든 요청을 외부로 간주       │
 │            ▼                                   │
 │ **② 모든 요청의 검증**(Always Verify)           │
 │    사용자·디바이스·애플리케이션·데이터의        │
 │    **4대 요소를 매 요청마다 인증·인가**          │
 │            ▼                                   │
 │ **③ 최소 권한**(Least Privilege)                │
 │    업무 수행에 **필요한 최소한의 권한만**,       │
 │    **JIT/JEA**(Just-In-Time / Just-Enough)      │
 │            ▼                                   │
 │ **④ 침해 가정**(Assume Breach)                  │
 │    "**이미 침해되었다**"고 전제 → **미세 분할**  │
 │    로 **폭발 반경(Blast Radius) 최소화**        │
 │            ▼                                   │
 │ **⑤ 지속적 검증**(Continuous Verification)      │
 │    1회 인증으로 끝나지 않고 **세션 중에도        │
 │    상황 변화 시 재평가**(동적 신뢰)             │
 └────────────────────────────────────────────────┘

2. 제로 트러스트 논리 아키텍처 (NIST SP 800-207)​

   [**NIST SP 800-207 논리 구성**]

   ┌─────────────── **제어 평면(Control Plane)** ──────────────┐
   │                                                           │
   │   **PDP**(Policy Decision Point, 정책결정지점)             │
   │    ┌──────────────────┬──────────────────┐                │
   │    │ **PE**(Policy     │ **PA**(Policy     │                │
   │    │  Engine)          │  Administrator)   │                │
   │    │ 신뢰 점수 산정·   │ 세션 수립/차단    │                │
   │    │ **허용 여부 판단**│ **지시**          │                │
   │    └──────────────────┴──────────────────┘                │
   │        ▲                          │                       │
   │  [입력 데이터]                    │ 정책 적용 명령         │
   │  · **ID·접근관리(IAM)** · 디바이스 상태(MDM/EDR)            │
   │  · **위협 인텔리전스** · SIEM 로그 · 데이터 등급           │
   │  · 컴플라이언스 정책 · 행위 분석(UEBA)                     │
   └───────────────────────────────────┼───────────────────────┘
                                       ▼
   ┌─────────────── **데이터 평면(Data Plane)** ───────────────┐
   │                                                           │
   │  **주체**            **PEP**              **자원**         │
   │  (Subject)      (Policy Enforcement    (Resource)         │
   │  사용자·기기 ──▶  Point, 정책시행)  ──▶  앱·데이터·서비스  │
   │                  **모든 트래픽이                           │
   │                   PEP를 반드시 경유**                      │
   └───────────────────────────────────────────────────────────┘

   ⇒ **PDP가 판단하고 PEP가 집행**하는 구조
   ⇒ 자원 앞에 PEP를 두어 **직접 네트워크 접근 자체를 차단**

3. 접근 통제 흐름​

   [**접근 요청 처리 흐름**]

   ① 사용자 접근 요청
        ▼
   ② **PEP가 요청 차단 후 PDP에 질의**
        ▼
   ③ PDP 신뢰 평가 — **다중 컨텍스트 종합**
      · 사용자 인증(**MFA**) · 디바이스 규정 준수(EDR·패치)
      · 접속 위치·시간 · 요청 자원 민감도 · **행위 이상 여부**
        ▼
   ④ **동적 정책 결정**
      · 신뢰 高 → **허용**  · 신뢰 中 → **추가 인증·제한 허용**
      · 신뢰 低 → **차단·격리**
        ▼
   ⑤ **세션 수립**(최소 권한·한시적)
        ▼
   ⑥ **지속 모니터링** → 상황 변화 시 **즉시 세션 재평가·회수**

Ⅲ. 제로 트러스트의 핵심원칙​

1. NIST SP 800-207 7대 기본 원칙​

원칙내용
① 모든 데이터·컴퓨팅 서비스를 자원으로 간주서버·SaaS·IoT·개인 기기까지 모두 보호 대상 자원
② 네트워크 위치와 무관하게 모든 통신 보안사내망이라도 암호화·인증 필수(내부망 신뢰 금지)
③ 개별 자원 접근은 세션 단위로 허용한 번 인증이 다른 자원 접근을 보장하지 않음, 세션별 최소 권한
④ 동적 정책에 의한 접근 결정ID·디바이스 상태·행위·환경 등 다중 속성 기반 동적 판단
⑤ 모든 자산의 무결성·보안 상태 모니터링어떤 자산도 본질적으로 신뢰되지 않음 → 지속 측정
⑥ 접근 허용 전 인증·인가를 엄격히 시행동적·지속적 인증, 위험 변화 시 재인증
⑦ 자산·네트워크·통신 정보를 수집하여 보안 개선로그·텔레메트리 수집 → 정책 지속 개선(피드백 루프)

2. 핵심 원칙의 실무적 3대 축 (KISA 가이드라인)​

   [**제로 트러스트 3대 핵심원칙**]

   ┌──────────────────────────────────────────────┐
   │ **① 강화된 인증**(Enhanced Identity)          │
   │    · **MFA·FIDO2**, 디바이스 인증 결합        │
   │    · **상황인지 기반 위험 평가**(RBA)          │
   ├──────────────────────────────────────────────┤
   │ **② 마이크로 세그멘테이션**                    │
   │    · 자원을 **최소 단위로 분할**·격리          │
   │    · **동-서(East-West) 트래픽 통제**          │
   │    ⇒ 침해 시 **측면 이동 차단**                │
   ├──────────────────────────────────────────────┤
   │ **③ 소프트웨어 정의 경계**(SDP)                │
   │    · **선인증 후접속**(Authenticate-then-Connect)│
   │    · 인증 전 자원은 **네트워크상 보이지 않음**  │
   │      (**Dark Cloud** / 포트 스캔 무력화)       │
   └──────────────────────────────────────────────┘

3. 제로 트러스트 6대 보호 대상 (Pillar)​

Pillar내용주요 기술
① 사용자(Identity)신원 검증·권한 관리IAM, MFA, PAM, SSO, FIDO2
② 디바이스(Device)단말 무결성·규정 준수 확인MDM/UEM, EDR, 디바이스 인증서
③ 네트워크(Network)분할·암호화마이크로 세그멘테이션, SDP, mTLS
④ 애플리케이션·워크로드앱 단위 접근통제ZTNA, API 게이트웨이, 컨테이너 보안
⑤ 데이터(Data)데이터 중심 보호데이터 분류, DLP, 암호화, DRM
⑥ 가시성·분석·자동화통합 모니터링·자동 대응SIEM, UEBA, SOAR, XDR

Ⅳ. 트러스트(경계 기반) 보안 모델과의 비교​

1. 개념적 비교​

   [**두 모델의 구조적 차이**]

   **[트러스트 모델 — 성곽과 해자(Castle & Moat)]**

        외부(불신)  │  **방화벽/IPS**  │   내부(**무조건 신뢰**)
        인터넷  ───▶│  ███ 경계 ███   │──▶ 서버A ─ 서버B ─ 서버C
                    │                 │      ↕     ↕      ↕
                    └─────────────────┘    **자유로운 내부 통신**
   ⇒ 경계 1회 돌파 시 → **내부 전체 노출**(측면 이동 자유)

   **[제로 트러스트 — 모든 문에 검문소]**

        사용자 ──[**PEP**]──▶ 앱A
        (위치      ▲          [**PEP**]──▶ DB
         무관)     │             ▲
                 **PDP** ────────┘
        · 사용자↔앱, 앱↔DB **모든 구간에 검증**
   ⇒ 한 자원 침해되어도 **다른 자원 접근 불가**(폭발 반경 최소화)

2. 종합 비교표​

비교 기준트러스트 보안 모델(경계 기반)제로 트러스트 보안 모델
기본 전제내부는 신뢰, 외부는 불신아무것도 신뢰하지 않음(Never Trust)
신뢰 근거네트워크 위치(사내망 여부)신원·디바이스 상태·컨텍스트
방어 개념경계 방어(Castle & Moat)자원별 미세 방어(Micro-perimeter)
보호 대상네트워크 경계데이터·자원 자체
인증 시점최초 1회(접속 시)매 요청·지속적 재평가
권한 부여광범위·정적(VPN 접속 시 내부망 전체)최소·동적·한시적(JIT/JEA)
내부 트래픽
(East-West)		검증 없음(신뢰)모두 검증·암호화
측면 이동용이(주요 취약점)차단(마이크로 세그멘테이션)
원격 접속VPN(접속 후 내부망 광범위 접근)ZTNA/SDP(앱 단위 접근)
자원 노출스캔으로 자산 식별 가능선인증 후접속 → 인증 전 비가시
내부자 위협대응 취약동일 기준 검증으로 대응
클라우드 적합성낮음(경계 정의 곤란)높음(위치 무관)
가시성경계 구간에 한정전 구간 로그·분석(SIEM·UEBA)
구현 난이도낮음(장비 중심)높음(아키텍처 전환·조직 변화)
비용 구조초기 장비 투자 중심지속적 운영·구독 비용
대표 기술방화벽, IPS/IDS, VPN, DMZ, NACIAM/MFA, ZTNA/SDP, 마이크로세그, EDR, SASE, SIEM/SOAR

3. Trade-off 분석​

관점트러스트 모델제로 트러스트 모델
보안성경계 돌파 시 치명적침해 영향 국소화, 내부자 위협 대응
사용성(UX)내부 접속 시 마찰 없음잦은 인증 요구 시 불편 → RBA로 완화 필요
성능경계 통과 후 오버헤드 없음매 요청 검증 → 지연·처리 부하 발생 가능
비용상대적 저렴초기 전환 비용 큼(IAM·자산 식별)
운영 복잡도단순정책 관리 복잡, 정책 오류 시 업무 마비 위험
레거시 대응자연스러움인증 미지원 레거시는 적용 곤란 → 프록시·게이트웨이 우회 필요

결론적 판단 : 제로 트러스트는 경계 보안을 폐기하는 것이 아니라 포함하여 확장하는 개념이다. 방화벽·NAC는 여전히 유효하며, 그 위에 신원 중심의 동적 통제 계층을 추가하는 것이 실무적 접근이다.

Ⅴ. 적용분야 및 도입 방안​

1. 주요 적용분야​

적용분야적용 내용대표 기술
① 원격근무·재택근무VPN 대체 — 앱 단위 접근, 개인 기기 상태 검증ZTNA, SDP, MDM
② 클라우드·하이브리드 환경멀티클라우드 자원에 위치 무관 일관 정책CASB, CSPM, SASE
③ 데이터센터 내부 보호서버 간 East-West 트래픽 통제마이크로 세그멘테이션, mTLS
④ 마이크로서비스·컨테이너서비스 간 상호 인증(mTLS), 워크로드 ID서비스 메시(Istio), SPIFFE/SPIRE
⑤ 특권계정 관리관리자 접근의 JIT 권한 부여·세션 녹화PAM, JIT Access
⑥ 공급망·협력사 접근외부 인력에 최소 범위·한시적 접근ZTNA, 계약 기반 정책
⑦ OT/ICS·IoT관리 취약 기기의 격리·행위 기반 통제NAC, 네트워크 분할, IoT 인증
⑧ 공공·국방美 EO 14028, 국내 공공 제로트러스트 실증KISA 가이드라인 기반
⑨ 금융망분리 규제 완화 흐름과 연계, 내부통제 강화금융보안원 가이드

3. 도입 시 고려사항​

고려사항내용
① 제품이 아닌 전략ZT는 구매하는 솔루션이 아니라 아키텍처 원칙 → "제로트러스트 제품" 마케팅에 유의
② 자산 식별이 선행 조건무엇을 지킬지 모르면 정책을 만들 수 없음 → 인벤토리·데이터 분류 필수
③ 사용성 균형과도한 인증 요구는 업무 저항·우회(Shadow IT) 유발 → 위험 기반 적응형 인증(RBA)
④ 레거시 시스템 대응현대 인증 미지원 시스템은 프록시·게이트웨이로 감싸기, 단계적 현대화
⑤ 단일 장애점 방지PDP/IAM 장애 시 전사 접근 마비 → 이중화·Fail-safe 정책 설계
⑥ 조직·프로세스 변화보안·인프라·앱 조직의 협업 체계, 경영진 스폰서십
⑦ 규제 정합성국내 망분리 규제와의 관계 검토, KISA 가이드라인·금융 규제 준수

Ⅵ. 결론​

제로 트러스트와 경계 기반 모델의 차이는 기술의 차이가 아니라 신뢰를 무엇에 근거하여 부여하는가라는 전제의 차이이다. 경계 모델은 "네트워크 위치" 를 신뢰의 근거로 삼았지만, 클라우드·원격근무·SaaS 확산으로 지켜야 할 경계 자체가 소멸하면서 그 전제가 무너졌다. 제로 트러스트는 신뢰의 근거를 "검증된 신원과 디바이스 상태, 그리고 요청의 맥락" 으로 이동시킨 것이다.

특히 주목할 점은 "침해 가정(Assume Breach)" 이라는 사고 전환이다. 경계 모델이 침입 차단에 집중했다면, 제로 트러스트는 침해는 반드시 일어난다고 전제하고 그 피해 범위를 최소화하는 데 초점을 둔다. SolarWinds처럼 신뢰된 경로로 침투하는 공급망 공격 앞에서는 이 관점이 유일한 현실적 대안이다.

다만 제로 트러스트는 경계 보안의 대체가 아니라 확장임을 분명히 해야 한다. 방화벽·NAC는 여전히 필요하며, 그 위에 신원 중심의 동적 접근통제 계층을 얹는 것이 실무적 구현이다. 또한 ZT는 구매하는 제품이 아니라 지향하는 아키텍처 원칙이므로, 특정 솔루션 도입으로 완성되지 않는다.

도입 전략으로는 Big Bang 전환이 아닌 점진적 접근이 필수이다. ① 보호 대상(Protect Surface) 식별 → ② IAM·MFA 기반 신원 통제 확립 → ③ VPN을 ZTNA로 전환 → ④ 중요 자산부터 마이크로 세그멘테이션 → ⑤ SIEM·SOAR 연계 자동화의 순서로, 각 단계마다 사용성과 보안성의 균형을 검증하며 확산해야 한다.

궁극적으로 제로 트러스트의 성공은 기술 도입률이 아니라 "모든 접근을 검증하되 사용자가 그 검증을 불편으로 느끼지 않게 만드는가" 에 달려 있으며, 이것이 위험 기반 적응형 인증(RBA)이 제로 트러스트의 실질적 핵심 기술로 부상한 이유이다.

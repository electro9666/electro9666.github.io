소프트웨어 규모산정

문제​

5.소프트웨어 규모산정에 대하여 다음을 설명하시오.
가.필요성과 산정방법
나.규모산정 방식의 종류별 특징

Ⅰ. 개요​

1. 개념​

소프트웨어 규모산정(Software Size Estimation) 은 개발할 소프트웨어의 크기를 정량적으로 측정·추정하여, 이를 기반으로 개발 공수(Effort)·기간(Duration)·비용(Cost)을 예측하는 활동이다. 프로젝트 관리의 모든 계획 수립의 출발점이 된다.

   [**규모산정에서 비용까지의 흐름**]

   **요구사항**
        ▼
   **① 규모(Size) 산정** ← ★모든 추정의 출발점★
      (FP, LOC, Story Point 등)
        ▼  × **생산성**(Productivity)
   **② 공수(Effort) 산정**
      (Man-Month, Man-Day)
        ▼  ÷ **투입 인력**
   **③ 기간(Duration) 산정**
        ▼  × **단가**(등급별 노임단가)
   **④ 비용(Cost) 산정**
        ▼
   **⑤ 일정·자원 계획, 계약금액 결정**

   ⇒ **규모산정이 부정확하면 이후 모든 계획이 왜곡**

2. 등장배경​

   [배경 — 소프트웨어 위기와 추정의 실패]

   · **Standish Group CHAOS 보고서**
     — SW 프로젝트의 **약 50%가 예산·일정 초과**
   · 원인 : **주관적·경험적 추정**("대충 3개월이면 될 것 같다")
   · 개발자 낙관 편향 — **90% 신드롬**(90% 완료 후 진척 정체)
        ▼
   [해결 방향]
   · **객관적·반복 가능한 측정 기준** 필요
   · **LOC**(1960s) → **FP**(1979, Albrecht) → **COSMIC**(1998)
   · 애자일 : **Story Point**(상대적 추정)
        ▼
   [국내 제도]
   · **SW사업 대가산정 가이드**(한국소프트웨어산업협회, KOSA)
   · **기능점수(FP) 방식이 공공 SW사업의 공식 대가산정 기준**
   · 「SW진흥법」, 「국가계약법 시행규칙」

Ⅱ. 소프트웨어 규모산정의 필요성​

1. 관점별 필요성​

 ┌────────── **규모산정의 필요성** ──────────┐
 │                                           │
 │ **[발주자 관점]**                          │
 │  · **적정 예산 수립**·예산 확보 근거        │
 │  · **입찰가 적정성 검토**(저가·과다 판단)   │
 │  · 사업 **타당성 분석**(BC/ROI)            │
 │  · **변경 요구 시 추가 비용 산정 근거**     │
 │                                           │
 │ **[수행사 관점]**                          │
 │  · **투입 인력·기간 계획** 수립            │
 │  · **원가 산정·수익성 판단**               │
 │  · 자원 배분·**리스크 관리**               │
 │  · **생산성 지표 관리**(FP/MM)             │
 │                                           │
 │ **[PM·프로젝트 관점]**                     │
 │  · **일정 baseline** 수립·진척 관리         │
 │  · **범위 변경(Scope Creep) 통제**         │
 │  · **EVM**(획득가치관리) 기준선            │
 │                                           │
 │ **[조직·산업 관점]**                       │
 │  · **생산성 데이터 축적**(과거 실적 DB)     │
 │  · **품질 지표** 산출(결함밀도 = 결함/FP)   │
 │  · 벤치마킹·**프로세스 개선**(CMMI)        │
 │  · **SW 제값받기**·산업 건전성 확보         │
 └───────────────────────────────────────────┘

2. 필요성 요약​

관점필요성구체적 효과
계획 수립공수·기간·비용의 정량적 예측현실적 일정 수립, 무리한 납기 방지
예산·계약적정 대가 산정 근거발주 예산 확보, 입찰가 적정성 검증
자원 관리필요 인력·기술 수준 산정적기 투입, 과소·과다 투입 방지
변경 관리요구사항 변경의 규모 영향 정량화추가 대가 협상 근거, Scope Creep 통제
진척 관리규모 대비 진척률 측정EVM 기반 객관적 진척 관리
품질 관리규모당 결함밀도·테스트 커버리지품질 목표 설정·비교
생산성 관리FP/MM 등 생산성 지표 산출조직 역량 벤치마킹, 개선
제도 준수공공사업 대가산정 기준 충족감사 대응, 예산 심의 통과

Ⅲ. 소프트웨어 규모 산정방법​

1. 산정방법의 전체 분류​

 ┌──────── **SW 규모·비용 산정방법 분류** ────────┐
 │                                                │
 │ **[1] 하향식(Top-Down) 접근**                   │
 │   전체 시스템 관점에서 추정 후 분배             │
 │   · **전문가 판단**(Expert Judgement)           │
 │   · **델파이 기법**(Delphi)                     │
 │   · **유추법**(Analogy) — 유사 프로젝트 비교     │
 │   ⇒ 초기 단계, 신속, **정확도 낮음**            │
 │                                                │
 │ **[2] 상향식(Bottom-Up) 접근**                  │
 │   세부 작업 단위로 추정 후 합산                 │
 │   · **WBS 기반 산정**                           │
 │   · **LOC**(원시 코드 라인 수)                  │
 │   ⇒ 상세 설계 이후 가능, **정확도 높음**        │
 │                                                │
 │ **[3] 기능 기반(Functional Size Measurement)**  │
 │   사용자 관점의 **기능**을 측정                  │
 │   · **FP**(IFPUG), **MK-II**, **NESMA**         │
 │   · **COSMIC-FFP**, Use Case Point              │
 │   ⇒ **ISO 국제표준**, 언어·기술 독립적          │
 │                                                │
 │ **[4] 수학적 모델(Parametric Model)**           │
 │   규모를 입력받아 공수·기간을 **수식으로 산출**  │
 │   · **COCOMO / COCOMO II**                      │
 │   · **Putnam 모델**(SLIM), Function Point 기반   │
 │                                                │
 │ **[5] 애자일 방식**                             │
 │   · **Story Point**(상대적 크기), **Planning Poker**│
 │   · **속도(Velocity)** 기반 예측                 │
 └────────────────────────────────────────────────┘

2. 산정 절차​

 ┌────────── **소프트웨어 규모산정 절차** ──────────┐
 │                                                  │
 │ **① 산정 목적·유형 결정**                         │
 │   · 개발/개선/유지관리 구분                       │
 │   · 산정 시점(기획·발주·계약·정산)                │
 │           ▼                                      │
 │ **② 측정 범위·경계 설정**                         │
 │   · **애플리케이션 경계(Boundary)** 정의          │
 │   · 대상 기능 목록화                              │
 │           ▼                                      │
 │ **③ 요구사항 분석·기능 식별**                     │
 │   · 요구사항정의서·**기능분해도(FDD)**            │
 │   · 데이터 기능 / 트랜잭션 기능 식별              │
 │           ▼                                      │
 │ **④ 규모 측정**                                   │
 │   · **기능점수(FP) 산정** 또는 LOC·SP            │
 │   · 정통법(상세) / **간이법(평균복잡도)** 선택     │
 │           ▼                                      │
 │ **⑤ 보정계수 적용**                               │
 │   · 규모·연계복잡성·성능·운영환경·보안성 등       │
 │           ▼                                      │
 │ **⑥ 공수·기간·비용 산정**                         │
 │   · **개발원가 = 기능점수 × FP당 단가 × 보정계수** │
 │   · 직접경비·이윤 가산                            │
 │           ▼                                      │
 │ **⑦ 검증·조정**                                   │
 │   · **다중 기법 교차 검증**(FP + 유추 + 전문가)    │
 │   · 과거 실적 데이터와 비교                       │
 │           ▼                                      │
 │ **⑧ 재산정(Re-estimation)**                       │
 │   · 요구사항 확정·변경 시 **주기적 갱신**         │
 └──────────────────────────────────────────────────┘

핵심 원칙 : 규모산정은 일회성이 아니라 프로젝트 진행에 따라 정밀도가 높아지는 반복 활동이다(추정의 불확실성 원뿔, Cone of Uncertainty).

   [**추정의 불확실성 원뿔(Cone of Uncertainty)**]

   정확도
     4x ┤╲
        │ ╲                    · 기획 초기 : **0.25x ~ 4x** 오차
     2x ┤  ╲___               · 요구사항 확정 : 0.67x ~ 1.5x
        │      ╲___           · 설계 완료 : 0.85x ~ 1.15x
     1x ┼──────────╲═════     · 구현 완료 : **1x**
        │      ___/
   0.5x ┤  ___/               ⇒ **초기 추정에 단일 값보다**
        │ /                     **범위(Range) 제시가 합리적**
   0.25x┤/
        └────┬────┬────┬────┬────
           기획  요구  설계  구현  완료

Ⅳ. 규모산정 방식의 종류별 특징​

1. LOC (Line of Code, 원시 코드 라인 수)​

   [**LOC 기반 산정**]

   · **측정 단위** : 소스코드 라인 수(주석·공백 제외)
   · **추정 방식** : **3점 추정**(PERT)
     **기대치 = (낙관치 + 4×기대치 + 비관치) / 6**
   · **공수 계산** : 노력(MM) = LOC / (개발자 월 생산 LOC)

   예) 낙관 4,000 / 기대 6,000 / 비관 10,000 LOC
       기대치 = (4,000 + 24,000 + 10,000) / 6 = **6,333 LOC**
       월 생산성 500 LOC/MM → **약 12.7 MM**
구분내용
장점· 직관적·이해 용이
· 자동 측정 가능(완료 후)
· 생산성 지표로 널리 사용
단점· 개발 언어·개발자 스타일에 종속(Java vs C 라인 수 상이)
· 개발 전 추정이 매우 어려움
· 사용자 관점 아님 → 발주자와 소통 곤란
· 코드를 많이 쓰면 좋은 것처럼 오도(품질과 무관)
· 재사용·자동생성 코드 처리 기준 모호
적용조직 내부 생산성 관리, 유사 언어·기술 기반 유추 산정

2. 기능점수(FP, Function Point)​

소프트웨어가 사용자에게 제공하는 기능의 양을 사용자 관점에서 측정하는 방법으로, 국내 공공 SW사업 대가산정의 공식 기준이다.

 ┌──────── **기능점수(FP) 산정 구조** ────────┐
 │                                            │
 │  **[애플리케이션 경계(Boundary)]**           │
 │                                            │
 │   외부 ──**EI**──▶ ┌────────────────┐      │
 │   (입력)          │                │      │
 │   외부 ◀─**EO**── │  **ILF**(내부논리 │      │
 │   (출력)          │   파일)         │      │
 │   외부 ◀─**EQ**── │                │      │
 │   (조회)          └────────────────┘      │
 │                          ▲                │
 │                       **EIF**(외부연계파일) │
 │                          │                │
 │                    타 시스템               │
 │                                            │
 │ **[데이터 기능]** — 저장되는 데이터           │
 │  · **ILF**(Internal Logical File) — 내부 관리 데이터│
 │  · **EIF**(External Interface File) — 외부 참조 데이터│
 │                                            │
 │ **[트랜잭션 기능]** — 처리되는 기능           │
 │  · **EI**(External Input) — 데이터 입력·변경 │
 │  · **EO**(External Output) — 가공된 출력     │
 │  · **EQ**(External inQuiry) — 단순 조회      │
 └────────────────────────────────────────────┘
기능 유형정의복잡도 판단 기준
ILF(내부논리파일)애플리케이션 내부에서 유지·관리되는 데이터 그룹DET(데이터요소) × RET(레코드요소)
EIF(외부연계파일)다른 애플리케이션이 관리하며 참조만 하는 데이터DET × RET
EI(외부입력)외부에서 데이터를 입력받아 ILF를 변경DET × FTR(참조파일)
EO(외부출력)계산·가공을 수반한 출력(보고서·통계)DET × FTR
EQ(외부조회)가공 없는 단순 조회·검색DET × FTR
   [**FP 산정 방법 — 정통법 vs 간이법**]

   **[정통법(Detailed)]**
   · 각 기능의 **복잡도(단순·보통·복잡)를 개별 판정**
   · DET·RET·FTR 개수로 복잡도 매트릭스 적용
   · **정확도 높음**, 상세 설계 이후 적용
   · 단계 : 유형 결정 → 경계 식별 → 기능 식별
           → **복잡도 및 기능점수 산정** → 보정 → 최종

   **[간이법(Simplified)]** ★국내 대가산정 주력 방식★
   · 복잡도를 **평균값으로 일괄 적용**
     ILF **7.5** / EIF **5.4** / EI **4.0** / EO **5.2** / EQ **3.9**
   · **기획·발주 단계**에서 상세 정보 부족 시 사용
   · 산식 : **기능점수 = Σ(기능 수 × 평균 복잡도 가중치)**

   예) ILF 10개, EIF 3개, EI 25개, EO 15개, EQ 20개
     = 10×7.5 + 3×5.4 + 25×4.0 + 15×5.2 + 20×3.9
     = 75 + 16.2 + 100 + 78 + 78 = **347.2 FP**
   [**개발원가 산정 (SW사업 대가산정 가이드)**]

   **개발원가 = 기능점수(FP) × FP당 단가 × 보정계수**

   [보정계수 5종]
   · **규모 보정계수** — 프로젝트 규모에 따른 생산성 차이
   · **애플리케이션 유형 보정계수** — 업무 특성
   · **언어 보정계수** — 개발 언어 난이도
   · **품질 및 특성 보정계수** — 성능·신뢰성·보안 요구
   · **연계 복잡성 보정계수** — 타 시스템 인터페이스

   **총 사업비 = 개발원가 + 직접경비 + 이윤(개발원가의 25% 이내)**
구분내용
장점· 개발 언어·기술 독립적 → 객관적 비교 가능
· 사용자 관점 측정 → 발주자와 소통 용이
· 요구사항 단계에서 산정 가능(조기 추정)
· ISO/IEC 20926 국제표준, 국내 공식 대가산정 기준
· 요구사항 변경의 영향도 정량화 용이
단점· 산정자의 숙련도·주관 개입(기능 식별 기준)
· 산정에 시간·비용 소요(정통법)
· 알고리즘 중심·과학기술 SW에 부적합(내부 처리 복잡도 미반영)
· 비기능 요구사항(성능·보안) 반영 한계 → 보정계수로 보완
· 애자일·클라우드 환경 적용의 어려움
적용공공 SW사업 예산 수립·계약, 업무용 정보시스템(MIS), 유지관리 대가 산정

3. COSMIC-FFP​

항목내용
개념데이터 이동(Data Movement) 을 측정 단위로 하는 2세대 기능규모 측정 방법(ISO/IEC 19761)
측정 요소Entry(입력) · Exit(출력) · Read(읽기) · Write(쓰기) — 각 1 CFP
장점· 실시간·임베디드·제어 시스템에도 적용 가능
· 복잡도 가중치 없이 단순·객관적
· 계층 구조 표현에 적합
단점국내 적용 사례 적음, 대가산정 제도 미반영
적용임베디드 SW, 실시간 제어, 통신 시스템

4. COCOMO / COCOMO II​

   [**COCOMO — 수학적 비용 추정 모델**(Boehm, 1981)]

   **노력(MM) = a × (KLOC)^b × EAF**
   **기간(TDEV) = c × (MM)^d**

   [프로젝트 유형 3가지]
   · **Organic**(단순형)      : 5만 라인 이하, 소규모 팀
                              a=2.4, b=1.05
   · **Semi-detached**(중간형): 30만 라인 이하
                              a=3.0, b=1.12
   · **Embedded**(내장형)     : 초대형·복잡, 엄격한 제약
                              a=3.6, b=1.20

   ★ **b > 1** ⇒ **규모 증가 시 노력이 비선형적으로 급증**
              (Brooks의 법칙 — 커뮤니케이션 비용 증가)

   [3단계 정밀도]
   · **Basic** : 규모만으로 개략 추정
   · **Intermediate** : **15개 비용동인(Cost Driver)** 반영
   · **Detailed** : 개발 단계별 세분 적용
구분내용
COCOMO II1995년 개정 — 재사용·COTS·객체지향·프로토타이핑 반영
· Application Composition 모델(Object Point)
· Early Design 모델(FP 기반)
· Post-Architecture 모델(상세)
장점· 규모→공수→기간의 체계적 수식화
· 비용동인으로 프로젝트 특성 반영
· 실증 데이터 기반, 비선형 관계 표현
단점· LOC 기반이므로 LOC 추정의 부정확성 승계
· 계수가 과거 데이터(1970~80년대) 기반 → 현대 환경 괴리
· 애자일·클라우드 환경 부적합

5. Putnam 모델 (SLIM)​

항목내용
개념개발 노력이 Rayleigh 곡선 분포를 따른다는 가정 하에 규모·기간·노력의 관계를 모델링
핵심 산식L = Ck × K^(1/3) × td^(4/3)
(L=규모, K=총노력, td=개발기간, Ck=기술상수)
핵심 시사점기간(td)의 4/3 지수 ⇒ 개발 기간을 단축하면 노력이 급격히 증가
→ 일정 압축의 비경제성 정량적 증명
활용대규모 프로젝트 일정-비용 Trade-off 분석, 최적 기간 산출

6. Use Case Point (UCP)​

항목내용
개념유스케이스와 액터의 복잡도를 기반으로 규모 산정
산식UCP = UUCP × TCF × EF
(미조정 UCP × 기술복잡도계수 × 환경계수)
장점객체지향·UML 기반 프로젝트에 적합, 요구사항 단계 적용 가능
단점유스케이스 작성 상세도에 따라 결과 편차 큼, 표준화 부족

7. Story Point (애자일)​

   [**Story Point — 상대적 추정**]

   · **절대 시간이 아닌 상대적 크기**로 추정
     (기준 스토리 대비 몇 배인가)
   · **피보나치 수열** 사용 : 1, 2, 3, 5, 8, 13, 21
     ⇒ 큰 항목일수록 **불확실성이 크다는 사실을 반영**
   · **플래닝 포커**(Planning Poker) — 팀 합의 도출
   · **속도(Velocity)** = 스프린트당 완료 SP
     ⇒ 남은 SP ÷ Velocity = **잔여 스프린트 수 예측**

   [고려 요소] 작업량(Volume) + **복잡도** + **불확실성**
구분내용
장점· 팀 합의 기반 → 수용성·책임감 높음
· 상대 추정이 절대 추정보다 인간의 판단에 부합
· Velocity로 경험 기반 예측 정확도 향상
· 빠른 추정(플래닝 포커 수십 분)
단점· 팀마다 기준이 달라 조직 간 비교 불가
· 계약·예산 산정에 부적합(발주자 설득 곤란)
· 초기 몇 스프린트는 Velocity 데이터 부재
· SP를 시간으로 환산하려는 오용 빈번
적용애자일 팀 내부 스프린트 계획, 릴리즈 예측

Ⅴ. 적용 시 고려사항 및 결론​

1. 적용 시 고려사항​

고려사항내용
① 다중 기법 교차 검증단일 기법 의존 금지 → FP + 유추법 + 전문가 판단을 병행하여 결과 비교, 큰 차이 시 원인 분석
② 단계별 재산정불확실성 원뿔을 고려하여 기획·요구사항 확정·설계 완료 시점마다 재산정
③ 범위 제시초기 추정은 단일 값이 아닌 범위(±%) 로 제시 → 과신 방지
④ 과거 실적 데이터 축적조직의 생산성 실적 DB(FP/MM)가 없으면 어떤 기법도 부정확 → 측정·축적 체계 필수
⑤ 비기능 요구사항 반영성능·보안·가용성은 FP에 미반영 → 보정계수·별도 산정으로 보완
⑥ 요구사항 변경 관리변경 시 FP 재산정으로 영향도 정량화 → 추가 대가 협상 근거 확보
⑦ 산정자 역량FP 산정은 숙련도에 따라 편차 발생 → CFPS 등 자격 보유자 활용, 산정 기준 문서화
⑧ 애자일 환경 대응계약은 FP 기반, 내부 관리는 Story Point로 이원화 운영 현실적
⑨ 신기술 환경클라우드·MSA·AI 코딩 도구 확산으로 기존 생산성 계수 재검증 필요

2. 결론​

소프트웨어 규모산정은 프로젝트 관리의 모든 계획이 출발하는 기준점이다. 규모가 잘못 산정되면 공수·기간·비용·인력 계획이 연쇄적으로 왜곡되며, 이는 SW 프로젝트 실패의 약 50%가 예산·일정 초과라는 통계의 근본 원인이기도 하다.

산정 방식 중 기능점수(FP)가 국내 공공 SW사업의 공식 대가산정 기준으로 채택된 이유는 "사용자 관점"과 "기술 독립성" 때문이다. LOC는 개발 언어와 개발자 스타일에 따라 수 배씩 차이가 나므로 발주자와 수행사 간 객관적 합의 기준이 될 수 없다. 반면 FP는 개발 전 요구사항 단계에서 산정 가능하고, 언어·기술과 무관하게 동일 기능에 동일 규모를 부여하므로 계약과 예산의 근거로 적합하다.

그러나 FP도 만능은 아니다. 알고리즘 중심의 과학기술 SW나 실시간 제어 시스템은 내부 처리 복잡도가 기능 수에 반영되지 않아 과소 산정되며, 이 경우 COSMIC-FFP가 더 적합하다. 또한 성능·보안 같은 비기능 요구사항은 FP 자체에 담기지 않으므로 보정계수를 통한 보완이 필수이다.

애자일 환경에서는 Story Point가 팀 내부 계획에 효과적이지만, 팀마다 기준이 달라 조직 간 비교와 계약 산정에는 사용할 수 없다는 근본적 한계가 있다. 따라서 실무적으로는 대외 계약·예산은 FP로, 팀 내부 스프린트 계획은 Story Point로 이원화하여 운영하는 것이 현실적 해법이다.

무엇보다 중요한 것은 어떤 기법을 쓰느냐보다 조직의 과거 실적 데이터를 축적하고 있느냐이다. FP를 정확히 산정해도 자사의 FP당 생산성(FP/MM) 실적이 없으면 공수를 산출할 수 없다. 결국 규모산정의 정확도는 기법의 정교함이 아니라 측정·기록·환류의 조직적 성숙도에 비례한다.

끝으로 추정은 본질적으로 불확실하다는 사실을 인정하는 태도가 필요하다. 불확실성 원뿔이 보여주듯 기획 초기의 추정은 최대 4배의 오차를 가지므로, 단일 값이 아닌 범위로 제시하고 단계별로 재산정하는 것이 정직하고 전문적인 접근이다. 나아가 클라우드·MSA·AI 코딩 도구의 확산으로 기존 생산성 계수의 전제가 흔들리고 있으므로, 기술사는 제도적 산정 기준을 준수하되 자사 환경에 맞는 생산성 데이터를 지속적으로 재보정하는 체계를 갖추도록 권고해야 한다.

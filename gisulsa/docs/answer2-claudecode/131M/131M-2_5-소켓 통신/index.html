소켓 통신

문제​

5.소켓(Socket) 통신과 관련하여 다음을 설명하시오.
가.소켓 통신 정의
나.소켓 통신 방식 개념도 및 유형
다.TCP 소켓 및 Web 소켓 흐름 설명
라.소켓 통신 방식과 HTTP 통신 방식 비교

Ⅰ. 소켓 통신의 정의​

1. 개념​

소켓(Socket) 은 네트워크상의 두 프로세스가 데이터를 주고받을 수 있도록 운영체제가 제공하는 통신 종단점(End Point)이자, 응용 계층과 전송 계층을 연결하는 API(인터페이스) 이다. 소켓 통신은 이러한 소켓을 통해 양 프로세스가 연결을 수립하고 양방향으로 데이터를 교환하는 통신 방식이다.

   [**소켓의 위치 — OSI/TCP-IP 계층상**]

   ┌──────────────────────────────┐
   │  **응용 계층**(HTTP, FTP, 앱) │  ← 사용자 프로그램
   ├──────────────────────────────┤
   │  ★ **소켓 인터페이스(API)** ★ │  ← **OS가 제공하는 추상 계층**
   ├──────────────────────────────┤     (Berkeley Socket)
   │  **전송 계층**(TCP / UDP)     │
   ├──────────────────────────────┤
   │  **인터넷 계층**(IP)          │
   ├──────────────────────────────┤
   │  네트워크 접근 계층           │
   └──────────────────────────────┘

   ⇒ 소켓은 **"네트워크 통신을 파일 입출력처럼 다루게 해주는 추상화"**
      (UNIX 철학 : Everything is a file → read()/write()로 통신)

2. 소켓의 식별 및 구성​

   [**소켓 식별 — 4-Tuple(5-Tuple)**]

   하나의 연결(Connection)은 다음으로 **유일하게 식별**된다.

   ( **출발지 IP** , **출발지 Port** , **목적지 IP** , **목적지 Port** [, 프로토콜] )
        192.168.0.5 :   51234      →   10.0.0.1   :   80

   ⇒ 서버는 **하나의 포트(80)** 로 **수만 개 클라이언트**를 구분 가능
      (클라이언트 IP·Port가 다르므로)
구성요소내용
IP 주소호스트(장비) 를 식별
포트 번호호스트 내 프로세스(서비스) 를 식별 (065535, Well-known 01023)
프로토콜TCP / UDP 등 전송 방식 결정
소켓 디스크립터OS가 부여하는 정수형 핸들(파일 디스크립터와 동일 체계)

3. 통신 방식(동작 모델)별 분류​

구분내용
동기(Blocking)recv() 호출 시 데이터 도착까지 대기 → 구현 단순, 동시성 낮음
비동기(Non-blocking)즉시 반환, 폴링·이벤트 기반 처리 → 고성능
I/O 멀티플렉싱select / poll / epoll(Linux) / IOCP(Windows) — 단일 스레드로 다수 소켓 처리(C10K 문제 해결)
멀티스레드/프로세스연결마다 스레드 할당 → 구현 단순, 자원 소모 큼

Ⅲ. TCP 소켓 및 Web 소켓 흐름​

1. TCP 소켓 통신 흐름​

 ┌──────────── **TCP 소켓 통신 흐름** ────────────┐
 │                                                │
 │  **[서버]**                    **[클라이언트]** │
 │                                                │
 │  **socket()** ─ 소켓 생성                       │
 │      ▼                                         │
 │  **bind()** ─ IP·Port 할당                      │
 │      ▼                                         │
 │  **listen()** ─ 연결 대기(백로그 큐)            │
 │      ▼                                         │
 │  **accept()** ◀─── 블로킹 대기 ───┐             │
 │      ▲                            │  **socket()**│
 │      │                            │      ▼      │
 │      │   ◀════ **connect()** ═════┘             │
 │      │        (**3-Way Handshake**)             │
 │      │      ① SYN      ──────▶                 │
 │      │      ② SYN+ACK  ◀──────                 │
 │      │      ③ ACK      ──────▶                 │
 │      ▼                                         │
 │  **새 소켓 반환**(연결 전용)                     │
 │      ▼                              ▼          │
 │  **read()/write()** ◀══**데이터 송수신**══▶ **write()/read()** │
 │      │        (양방향 전이중, 반복)   │          │
 │      ▼                              ▼          │
 │  **close()** ◀═══ **4-Way Handshake** ═══▶ **close()** │
 │      ① FIN ▶  ② ACK ◀  ③ FIN ◀  ④ ACK ▶       │
 └────────────────────────────────────────────────┘
단계API역할
① 소켓 생성socket()프로토콜(TCP/UDP) 지정, 소켓 디스크립터 반환
② 주소 할당bind()서버가 IP·Port를 소켓에 결합
③ 연결 대기listen()수신 대기 상태 전환, 백로그 큐 크기 지정
④ 연결 수락accept()요청 수락 → 연결 전용 소켓 생성(리스닝 소켓은 유지)
⑤ 연결 요청connect()클라이언트가 3-Way Handshake 개시
⑥ 송수신read()/write()
send()/recv()		양방향 데이터 교환(스트림)
⑦ 종료close()4-Way Handshake, 자원 반환

핵심 포인트 : accept() 는 리스닝 소켓과 별개의 새 소켓을 만든다. 리스닝 소켓은 계속 새 연결을 받고, 통신은 새 소켓에서 이루어지므로 동시 다중 접속이 가능하다.

2. 웹 소켓(WebSocket) 통신 흐름​

웹소켓은 HTTP 기반으로 핸드셰이크를 수행한 뒤, 동일 TCP 연결을 웹소켓 프로토콜로 전환(Upgrade)하여 브라우저와 서버 간 양방향 실시간 통신을 제공하는 프로토콜이다(RFC 6455, 스킴 ws://·wss://).

 ┌──────────── **웹소켓 통신 흐름** ────────────┐
 │                                              │
 │ **[1단계] TCP 연결 수립**                     │
 │    3-Way Handshake (기존 TCP와 동일)         │
 │            ▼                                 │
 │ **[2단계] HTTP 기반 핸드셰이크(Upgrade)**     │
 │                                              │
 │  Client ──▶ GET /chat HTTP/1.1               │
 │             Host: example.com                │
 │             **Upgrade: websocket**            │
 │             **Connection: Upgrade**           │
 │             **Sec-WebSocket-Key: dGhlIH...**  │
 │             Sec-WebSocket-Version: 13         │
 │                                              │
 │  Server ◀── **HTTP/1.1 101 Switching Protocols**│
 │             Upgrade: websocket               │
 │             Connection: Upgrade              │
 │             **Sec-WebSocket-Accept: s3pPLM...**│
 │             (Key + GUID의 **SHA-1 + Base64**) │
 │            ▼                                 │
 │ **[3단계] 프로토콜 전환 완료**                │
 │    **HTTP → WebSocket** (같은 TCP 연결 재사용) │
 │            ▼                                 │
 │ **[4단계] 양방향 데이터 교환(Frame 단위)**     │
 │                                              │
 │   Client ◀════ **Data Frame** ════▶ Server    │
 │   · **서버가 먼저 Push 가능**(Server Push)    │
 │   · 헤더 **2~14바이트**로 매우 경량           │
 │   · **Ping/Pong Frame**으로 연결 생존 확인    │
 │            ▼                                 │
 │ **[5단계] 종료**                              │
 │    **Close Frame**(opcode 0x8) 교환 → TCP 종료│
 └──────────────────────────────────────────────┘
웹소켓 프레임 구조내용
FIN마지막 프레임 여부(분할 전송 지원)
Opcode0x1 텍스트, 0x2 바이너리, 0x8 종료, 0x9 Ping, 0xA Pong
MASK클라이언트→서버는 마스킹 필수(캐시 오염 공격 방지)
Payload Length7 / 7+16 / 7+64 비트 가변
특징내용
HTTP 호환80/443 포트 사용 → 방화벽·프록시 통과 용이
전이중클라이언트·서버 동시 송수신 가능
경량 헤더HTTP(수백 바이트) 대비 2~14바이트
상태 유지연결이 지속되므로 세션 컨텍스트 유지
보안wss://(TLS) 사용 권장, Origin 검증 필수(CSWSH 방지)

3. TCP 소켓과 웹소켓 비교​

구분TCP 소켓웹소켓
계층전송 계층 API응용 계층 프로토콜(TCP 위)
핸드셰이크TCP 3-Way만TCP 3-Way + HTTP Upgrade
브라우저 지원불가(보안 정책)가능(JS WebSocket API)
데이터 단위바이트 스트림(경계 없음)프레임(메시지 경계 유지)
프록시·방화벽별도 포트 → 차단 가능성80/443 → 통과 용이
활용서버 간 통신, 소켓서버, IoT웹 실시간 서비스(채팅·알림)

Ⅳ. 소켓 통신 방식과 HTTP 통신 방식 비교​

1. 통신 구조 비교​

   [**HTTP — 요청·응답 단발성**]

   Client ──① 연결──▶ Server
          ──② 요청──▶
          ◀─③ 응답──
          ──④ 종료──▶     ※ 매 요청마다 반복(Stateless)
   ⇒ **서버는 먼저 말할 수 없음**(클라이언트 요청 필수)
   ⇒ 실시간 갱신 위해 **Polling**(주기적 재요청) → **비효율**

   [**소켓 — 연결 유지 양방향**]

   Client ──① 연결──▶ Server
          ◀═══════════▶   ② 자유로운 양방향 송수신
          ◀═══════════▶      (**서버 Push 가능**)
          ──③ 종료──▶
   ⇒ **연결 1회 수립 후 지속 사용**(Stateful)

2. 종합 비교표​

비교 기준소켓 통신(TCP/WebSocket)HTTP 통신
계층전송 계층 API / 응용 프로토콜응용 계층 프로토콜

통신 방향양방향 전이중(Full-Duplex)단방향 요청-응답(Half-Duplex)
서버 주도 전송가능(Server Push)불가(Polling·SSE 필요)
상태 관리Stateful(연결 컨텍스트 유지)Stateless(요청 간 독립)
데이터 형식바이트 스트림·프레임(자유)텍스트 헤더 + 바디(규격화)
오버헤드매우 낮음(핸드셰이크 1회, 헤더 2~14B)높음(매 요청 헤더 수백 바이트~KB)

(Sticky Session·Pub/Sub 필요)		용이 — Stateless → 로드밸런싱 자유
자원 소모연결 수만큼 서버 자원 점유요청 처리 후 자원 해제

Ⅴ. 실무 고려사항 및 결론​

1. 실무 고려사항​

고려사항내용
① 연결 관리하트비트(Ping/Pong) 로 좀비 연결 정리, 자동 재연결·지수 백오프 구현
② 확장성 설계다중 서버 시 Redis Pub/Sub·Kafka로 메시지 브로드캐스트, Sticky Session 또는 상태 외부화
③ 자원 한계서버당 파일 디스크립터·메모리 한계 → ulimit 조정, epoll/IOCP 기반 이벤트 루프 채택
④ 보안wss://(TLS) 필수, Origin 검증(CSWSH), 인증 토큰 검증, 메시지 크기 제한(DoS 방지)
⑤ 프록시·LB 설정L7 로드밸런서의 Upgrade 헤더 전달·타임아웃 연장 설정 필요
⑥ 폴백 전략웹소켓 차단 환경 대비 Long Polling 폴백(Socket.IO·SignalR 등 라이브러리 활용)
⑦ 프로토콜 선택신뢰성 필요 → TCP, 지연 최소화·손실 허용 → UDP(실시간 미디어·게임)

2. 결론​

소켓 통신과 HTTP 통신의 본질적 차이는 "연결을 유지하는가" 와 "서버가 먼저 말할 수 있는가" 라는 두 가지로 요약된다. HTTP는 Stateless·요청-응답 구조 덕분에 캐싱과 수평 확장이 자유롭지만, 바로 그 특성 때문에 서버가 능동적으로 데이터를 전달할 수 없다. 반대로 소켓은 연결을 유지하여 실시간 양방향 통신을 제공하지만, 상태를 서버가 보유하므로 확장이 어렵다.

웹소켓은 이 둘의 장점을 절충한 설계이다. HTTP 핸드셰이크로 시작하여 방화벽·프록시 친화성을 확보한 뒤, 프로토콜을 전환하여 소켓의 양방향성을 얻는 구조는 웹 환경의 제약과 실시간성 요구를 동시에 만족시킨 실용적 해법이다.

실무 선택의 기준은 "실시간 양방향성이 정말 필요한가" 이다. 단순 조회는 REST가, 서버 단방향 알림은 SSE가 더 단순하고 안정적이며, 웹소켓은 채팅·협업 편집·게임·실시간 시세처럼 양방향 저지연이 요구사항 자체인 경우에 선택해야 한다. 불필요한 웹소켓 도입은 연결 관리·재연결·수평 확장이라는 상당한 운영 복잡도를 대가로 치르기 때문이다.

끝으로 대규모 실시간 서비스를 설계할 때는 소켓 연결 자체보다 그 뒤의 확장 아키텍처가 핵심 과제임을 인식해야 한다. 연결 상태를 서버 메모리에서 분리하고, 메시지 브로커를 통해 다중 인스턴스 간 이벤트를 전파하는 구조를 갖추어야 비로소 소켓 기반 서비스가 HTTP 수준의 확장성을 확보할 수 있다.

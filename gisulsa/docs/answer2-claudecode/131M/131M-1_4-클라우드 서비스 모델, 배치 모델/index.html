클라우드 서비스 모델, 배치 모델

문제​

4.클라우드 컴퓨팅의 Service Model과 Deployment Model 비교

Ⅰ. 개요​

클라우드 컴퓨팅은 NIST SP 800-145에 따라 주문형 셀프서비스, 광대역 네트워크 접근, 자원 풀링, 신속한 탄력성, 측정 가능한 서비스의 5대 필수 특성을 갖는 컴퓨팅 모델이다. NIST는 이를 ① 서비스 모델(무엇을 서비스로 제공하는가) 과 ② 배치 모델(누구를 위해 어디에 구축하는가) 의 두 축으로 정의한다.

 ┌──────── **NIST 클라우드 정의 체계** ────────┐
 │  **5대 필수 특성**                           │
 │   주문형 셀프서비스 · 광대역 접근 ·          │
 │   자원 풀링 · 신속한 탄력성 · 측정 서비스    │
 ├─────────────────────────────────────────────┤
 │  **3대 서비스 모델**(What)                   │
 │   **IaaS · PaaS · SaaS**                     │
 ├─────────────────────────────────────────────┤
 │  **4대 배치 모델**(Where/Who)                │
 │   **Public · Private · Hybrid · Community**  │
 └─────────────────────────────────────────────┘

Ⅱ. 서비스 모델(Service Model) 비교​

   [**책임 범위** — 아래로 갈수록 사용자 책임 감소]

   구분        온프레미스   **IaaS**    **PaaS**    **SaaS**
   ──────────────────────────────────────────────────────
   애플리케이션    ■사용자    ■사용자    ■사용자    □제공자
   데이터          ■사용자    ■사용자    ■사용자    □제공자
   런타임          ■사용자    ■사용자    □제공자    □제공자
   미들웨어        ■사용자    ■사용자    □제공자    □제공자
   **OS**          ■사용자    ■사용자    □제공자    □제공자
   가상화          ■사용자    □제공자    □제공자    □제공자
   서버·스토리지   ■사용자    □제공자    □제공자    □제공자
   네트워크        ■사용자    □제공자    □제공자    □제공자
   ──────────────────────────────────────────────────────

사용자인프라 관리자·시스템 엔지니어개발자최종 사용자(현업)
관리 책임OS 이상 전부 사용자애플리케이션·데이터만데이터·설정만
유연성·제어권매우 높음중간낮음(제공 기능 범위 내)
도입 속도느림(구성 필요)빠름즉시 사용
확장성사용자가 설계자동 확장 제공제공자가 처리
종속성(Lock-in)낮음(이식 용이)높음(플랫폼 API 종속)매우 높음(데이터 반출 문제)
과금 기준vCPU·메모리·시간·트래픽인스턴스·실행시간·요청 수사용자 수(좌석)·기능 등급
대표 서비스AWS EC2, Azure VM, NHN CloudAWS Elastic Beanstalk, Heroku, App Engine, Kubernetes 관리형M365, Salesforce, Google Workspace
적합 상황레거시 리프트앤시프트, 특수 OS·튜닝 필요신규 애플리케이션 신속 개발, DevOps표준 업무(메일·그룹웨어·CRM)
확장 모델내용
FaaS / 서버리스함수 단위 실행·이벤트 기반, 사용한 실행시간만 과금(AWS Lambda)
CaaS컨테이너 실행 환경 제공(EKS·GKE) — IaaS와 PaaS의 중간
DaaS가상 데스크톱(VDI) 제공 — 재택근무·보안 단말
AIaaS / MLaaS학습·추론 인프라와 파운데이션 모델 API 제공(Bedrock·OpenAI API)

Ⅲ. 배치 모델(Deployment Model) 비교​

 [**퍼블릭**]        [**프라이빗**]      [**하이브리드**]     [**커뮤니티**]

  ┌─────────┐        ┌─────────┐      ┌────┐ ══ ┌────┐    ┌─────────┐
  │  CSP    │        │ 자사     │      │Priv│ 연동│Pub │    │ 공동체   │
  │ 다수    │        │ 전용     │      │핵심│    │탄력│    │ (동종업계)│
  │ 테넌트  │        │ 단독     │      │데이터   │워크로드│  │ 공유     │
  └─────────┘        └─────────┘      └────┘    └────┘    └─────────┘
  **공유·개방**       **전용·폐쇄**     **연계·유연**        **제한 공유**
비교 기준퍼블릭(Public)프라이빗(Private)하이브리드(Hybrid)커뮤니티(Community)
이용 주체불특정 다수단일 조직 전용두 모델 결합공통 관심사 조직군
소유·운영CSP자사 또는 위탁혼재참여 조직·제3자
초기 비용없음(OpEx)높음(CapEx)중간분담
확장성무제한·즉시보유 자원 한계높음(클라우드 버스팅)중간
보안·통제상대적 낮음(공동책임)매우 높음데이터 등급별 분리중간(공동 규약)
규제 대응지역·인증 확인 필요용이(망분리·데이터 주권)핵심 데이터는 내부 보존업계 규제 공동 대응
단점종속성, 예측 못한 비용 증가, 데이터 위치 이슈비용·운영 부담, 탄력성 제한관리 복잡도·연동 비용참여 조직 간 의사결정 지연
적합 사례스타트업, 웹·모바일 서비스, 개발·테스트금융 기간계, 국방, 민감 개인정보대기업 DR·피크 대응, 단계적 전환공공기관 공동이용, 의료·연구 컨소시엄
관련 개념내용
멀티 클라우드복수 CSP를 병행 사용 — 종속성 회피·가용성 확보(하이브리드와 구분)
클라우드 버스팅평시 프라이빗 운영 → 피크 시 퍼블릭으로 확장
공동책임 모델CSP는 '클라우드의 보안', 사용자는 '클라우드 내의 보안' 책임
국내 제도CSAP(클라우드 보안인증) — 공공 이용 시 필수, 상·중·하 등급제

Ⅳ. 두 모델의 관계 및 선택 기준​

   두 모델은 **선택 관계가 아니라 조합 관계**이다.

              **퍼블릭**       **프라이빗**      **하이브리드**
   **SaaS**    M365, CRM      사내 그룹웨어      단계적 SaaS 전환
   **PaaS**    App Engine     사내 PaaS(OpenShift) 개발=퍼블릭/운영=사내
   **IaaS**    AWS EC2        자체 VMware        DR·버스팅 구성
선택 관점판단 기준
데이터 민감도개인정보·기밀 → 프라이빗/하이브리드, 공개 데이터 → 퍼블릭
규제 준수금융 전자금융감독규정, 공공 CSAP, 의료·개인정보 국외이전 규정
워크로드 특성트래픽 변동 큼 → 퍼블릭, 일정·상시 부하 → 프라이빗이 TCO 유리
비용 구조초기 투자 회피(OpEx) vs 장기 총소유비용(CapEx)
기술 역량내부 운영 인력 부족 → PaaS·SaaS 비중 확대
종속성 관리컨테이너·IaC·개방형 표준 채택으로 이식성 확보

Ⅴ. 결론​

서비스 모델은 '무엇을 위임할 것인가(책임 경계)' 를, 배치 모델은 '어디에 두고 누구와 공유할 것인가(통제·규제)' 를 결정하는 축이다. 즉 서비스 모델은 기술·운영 역량과 개발 생산성의 문제이고, 배치 모델은 보안·규제·데이터 주권의 문제이므로 두 축을 독립적으로 검토한 뒤 조합해야 한다.

실무적으로는 표준 업무는 SaaS, 신규 개발은 PaaS/컨테이너, 레거시는 IaaS로 계층화하고, 민감 데이터는 프라이빗에 두되 탄력적 워크로드는 퍼블릭으로 버스팅하는 하이브리드 구성이 일반적인 해답이다. 이때 반드시 고려할 두 가지는 ① 공동책임 모델에 따른 사용자 측 보안 책임(계정·설정·데이터 암호화) 과 ② 컨테이너·IaC 기반의 이식성 확보를 통한 벤더 종속성 완화이며, 공공 부문에서는 CSAP 인증 등급 요건을 사전에 확인하는 것이 필수적이다.

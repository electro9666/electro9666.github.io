아키텍처 스타일, 디자인 패턴

문제​

6.아키텍처 스타일과 디자인 패턴에 대하여 다음을 설명하시오.
가.아키텍처 스타일과 디자인 패턴의 차이점
나.대표적인 아키텍처 스타일 3가지
다.GoF(Gang of Four) 디자인 패턴의 유형을 구분하고, 유형별 대표적인 디자인 패턴 설명

Ⅰ. 개요​

1. 개념​

구분개념
아키텍처 스타일
(Architecture Style)		시스템 전체의 구조를 결정하는 상위 수준의 구성 원칙 — 컴포넌트의 유형과 이들 간의 상호작용·연결 방식에 대한 정형화된 해결책
디자인 패턴
(Design Pattern)		특정 설계 문제 상황에서 반복적으로 나타나는 문제에 대해, 클래스·객체 수준에서 검증된 재사용 가능한 설계 해결책

2. 등장배경 및 공통 가치​

   [등장배경]
   · **Christopher Alexander**(건축, 1977) — "패턴 언어(Pattern Language)"
     "동일한 문제가 반복되며, 그 해결책도 반복된다"
        ▼
   · **GoF**(Gamma·Helm·Johnson·Vlissides, 1994)
     『Design Patterns』 — **객체지향 설계 23개 패턴** 정리
   · **Mary Shaw & David Garlan**(1996)
     『Software Architecture』 — **아키텍처 스타일** 체계화
        ▼
   [**공통 가치**]
   · **검증된 해결책 재사용** → 설계 품질·생산성 향상
   · **공통 어휘(Vocabulary)** 제공 → "Observer로 하자" 한 마디로 소통
   · **바퀴의 재발명 방지**, 유지보수성·확장성 확보

Ⅱ. 아키텍처 스타일과 디자인 패턴의 차이점​

1. 계층적 관계​

   [**추상화 수준에 따른 계층 관계**]

   ┌──────────────────────────────────────────────┐
   │ **아키텍처 스타일**(Architecture Style)       │ 시스템
   │  · 계층형, MSA, 이벤트 기반, MVC              │ **전체**
   │  · **"시스템을 어떻게 나눌 것인가"**           │  ▲
   ├──────────────────────────────────────────────┤  │
   │ **아키텍처 패턴**(Architecture Pattern)       │  │ 추상화
   │  · Broker, Blackboard, Microkernel            │  │ 수준
   │  · 서브시스템 수준의 구조                      │  │
   ├──────────────────────────────────────────────┤  │
   │ **디자인 패턴**(Design Pattern, GoF)          │  │
   │  · Singleton, Factory, Observer, Strategy     │ 모듈
   │  · **"클래스·객체를 어떻게 조합할 것인가"**     │ **내부**
   ├──────────────────────────────────────────────┤  │
   │ **이디엄**(Idiom)                             │  ▼
   │  · 언어 고유 관용구(Java try-with-resources)  │ 코드
   └──────────────────────────────────────────────┘

   ⇒ **"아키텍처 스타일이 도시계획이라면, 디자인 패턴은 건물 설계"**

2. 차이점 비교표​

비교 기준아키텍처 스타일디자인 패턴
추상화 수준시스템 전체(Macro)클래스·객체(Micro)
적용 범위시스템·서브시스템 구조모듈 내부 설계
관심사컴포넌트 분할·배치·상호작용·통신 방식객체 생성·구조·행위
결정 시점설계 초기(아키텍처 정의)상세 설계·구현 단계
변경 비용매우 높음(전면 재구축 수준)낮음(국소적 리팩터링)
선택 개수시스템당 1~소수(조합 가능)다수 동시 사용
영향 요소품질속성(성능·확장성·가용성·보안)가독성·유연성·재사용성
결정 주체아키텍트개발자·설계자
대표 예시계층형, MSA, 이벤트 기반, 마이크로커널, P2PSingleton, Factory, Observer, Strategy
문서화아키텍처 기술서(4+1 뷰, ADR)클래스 다이어그램·코드 주석
재사용 단위구조적 골격설계 아이디어

3. 상호 관계​

   [**둘은 대립이 아니라 협력 관계**]

   **아키텍처 스타일**이 **틀(구조)** 을 정하면
        ▼
   그 틀 안에서 **디자인 패턴**이 **세부 구현**을 담당

   예) **MSA 스타일** 채택
        ├─ 서비스 간 통신 → **Proxy·Adapter** 패턴
        ├─ 장애 격리     → **Circuit Breaker**(아키텍처 패턴)
        ├─ 객체 생성     → **Factory Method** 패턴
        └─ 이벤트 처리   → **Observer** 패턴

   ⇒ 같은 아키텍처 스타일이라도 **적용된 디자인 패턴에 따라
      코드 품질은 크게 달라진다**

Ⅲ. 대표적인 아키텍처 스타일 3가지​

1. 계층형 아키텍처 (Layered Architecture)​

   [**계층형 아키텍처 구조**]

   ┌────────────────────────────────┐
   │ **프레젠테이션 계층**(UI)       │  화면·요청 수신
   │  Controller, View              │
   └───────────────┬────────────────┘
                   ▼ (단방향 의존)
   ┌────────────────────────────────┐
   │ **비즈니스 계층**(Business)     │  업무 규칙·트랜잭션
   │  Service, Domain               │
   └───────────────┬────────────────┘
                   ▼
   ┌────────────────────────────────┐
   │ **영속성 계층**(Persistence)    │  데이터 접근
   │  Repository, DAO               │
   └───────────────┬────────────────┘
                   ▼
   ┌────────────────────────────────┐
   │ **데이터베이스 계층**            │
   └────────────────────────────────┘

   ★ **폐쇄 계층(Closed Layer)** 원칙
     — 요청은 **반드시 인접 하위 계층을 거쳐야 함**
     ⇒ **계층 격리(Layer of Isolation)** 로 변경 영향 차단
구분내용
개념시스템을 역할에 따라 수평적 계층으로 분리하고, 상위 계층이 하위 계층에만 의존하도록 구성
핵심 원리관심사의 분리(SoC), 단방향 의존, 계층 격리
장점· 구조 단순·이해 용이(가장 보편적, N-Tier의 사실상 표준)
· 계층별 역할 명확, 테스트·분업 용이
· 하위 계층 교체 시 상위 영향 최소화
단점· 요청이 모든 계층을 통과 → 싱크홀 안티패턴(단순 조회도 전 계층 경유)
· 모놀리식 경향 → 전체 재배포 필요, 확장성 제약
· 계층 간 결합이 강해지면 변경 파급
적용전통적 엔터프라이즈 웹 애플리케이션, ERP, 관리 시스템, 요구사항이 안정적인 업무 시스템
변형헥사고날(포트&어댑터), 클린 아키텍처 — 의존성을 도메인 중심으로 역전

2. 마이크로서비스 아키텍처 (MSA)​

   [**MSA 구조**]

              **[API Gateway]** ← 인증·라우팅·집계
                    │
     ┌──────────────┼──────────────┬─────────────┐
     ▼              ▼              ▼             ▼
  ┌───────┐    ┌───────┐    ┌───────┐    ┌───────┐
  │ 주문  │    │ 결제  │    │ 배송  │    │ 회원  │
  │서비스 │    │서비스 │    │서비스 │    │서비스 │
  ├───────┤    ├───────┤    ├───────┤    ├───────┤
  │ **DB**│    │ **DB**│    │ **DB**│    │ **DB**│ ← **DB per Service**
  └───┬───┘    └───┬───┘    └───┬───┘    └───┬───┘
      └────────────┴─── **이벤트 버스** ──┴────────┘
                    (Kafka — 비동기 통신·Saga)

  [지원 구성요소] **서비스 디스커버리** · **Circuit Breaker**
                 **분산 추적**(Tracing) · 중앙 로그 · Config Server
구분내용
개념시스템을 비즈니스 도메인 단위의 작고 독립적인 서비스로 분해하고, 각 서비스가 독립 배포·독립 DB·경량 프로토콜(REST·gRPC·메시징) 로 통신하는 스타일
핵심 원리단일 책임·독립 배포·분산 데이터 관리, Bounded Context(DDD)
장점· 서비스별 독립 배포·확장(필요한 서비스만 Scale-out)
· 장애 격리 — 한 서비스 장애가 전체로 파급되지 않음
· 기술 이질성 허용(서비스별 최적 언어·DB)
· 팀 단위 자율성(Conway's Law 활용)
단점· 분산 시스템 복잡도 — 네트워크 지연·부분 실패
· 분산 트랜잭션 곤란 → Saga·최종적 일관성 필요
· 운영 부담 급증(모니터링·추적·배포 자동화 필수)
· 서비스 경계 설계 실패 시 분산 모놀리스 전락
적용대규모 트래픽 서비스(이커머스·OTT·핀테크), 빠른 배포 주기가 필요한 서비스, 조직 규모가 큰 경우
필수 전제DevOps·CI/CD·컨테이너(K8s)·관측성(Observability) 역량

3. 이벤트 기반 아키텍처 (Event-Driven Architecture, EDA)​

   [**이벤트 기반 아키텍처 — Pub/Sub 모델**]

   **[Producer]**              **[Event Channel]**        **[Consumer]**
   (이벤트 생산자)              (Broker/Bus)              (이벤트 소비자)

   주문 서비스 ──**주문생성**──▶ ┌──────────────┐ ──▶ 결제 서비스
                                │              │
   결제 서비스 ──**결제완료**──▶ │ **Kafka /**   │ ──▶ 배송 서비스
                                │ **RabbitMQ**  │
   배송 서비스 ──**배송시작**──▶ │              │ ──▶ 알림 서비스
                                └──────────────┘ ──▶ 분석 서비스

   ★ **생산자와 소비자가 서로를 모름**(**비동기·느슨한 결합**)
   ★ 소비자 추가 시 **생산자 코드 변경 불필요** → **높은 확장성**

   [두 가지 처리 토폴로지]
   · **Mediator**(중재자) — 오케스트레이터가 **흐름을 조율**(복잡한 워크플로)
   · **Broker**(브로커)   — 중앙 조율 없이 **연쇄적 전파**(단순·고성능)
구분내용
개념상태 변화를 '이벤트'로 발행하고, 관심 있는 소비자가 이를 비동기적으로 구독·처리하는 스타일
핵심 원리비동기 통신·느슨한 결합·발행-구독(Pub/Sub)
장점· 극도로 낮은 결합도 — 생산자·소비자 독립 진화
· 높은 확장성·응답성(비동기 처리, 부하 완충)
· 실시간 처리에 적합, 소비자 추가 용이
· 이벤트 소싱과 결합 시 완전한 이력 추적
단점· 전체 흐름 파악 곤란 → 디버깅·추적 어려움(분산 추적 필수)
· 최종적 일관성(Eventual Consistency) — 즉시 정합성 보장 불가
· 중복 처리·순서 보장 문제 → 멱등성(Idempotency) 설계 필요
· 브로커가 단일 장애점이 될 수 있음
적용MSA 서비스 간 비동기 통신, IoT 센서 데이터 처리, 실시간 스트리밍 분석, 금융 거래 처리, 알림·로그 수집
관련 패턴Saga(분산 트랜잭션), CQRS, Event Sourcing, Outbox 패턴

4. 세 가지 스타일 비교​

비교 기준계층형MSA이벤트 기반
분할 기준기술적 역할(수평)비즈니스 도메인(수직)이벤트·관심사
결합도중간낮음매우 낮음
통신동기 메소드 호출동기(REST) + 비동기비동기 메시지
일관성강한 일관성(ACID)서비스 내 ACID, 간 최종적최종적 일관성
배포 단위전체 일괄서비스별 독립컴포넌트별 독립
확장성낮음(전체 복제)높음(선택적)매우 높음
복잡도낮음높음높음(추적 곤란)
적합 규모소·중규모대규모대규모·실시간

Ⅳ. GoF 디자인 패턴​

1. 분류 체계​

   [**GoF 23개 패턴 분류**]

   ┌── **목적(Purpose)에 따른 분류** ──────────────────────┐
   │                                                       │
   │ **① 생성(Creational) — 5개**                           │
   │    "**객체를 어떻게 생성할 것인가**"                    │
   │    → 생성 과정을 캡슐화하여 **유연성 확보**            │
   │                                                       │
   │ **② 구조(Structural) — 7개**                           │
   │    "**객체를 어떻게 조합할 것인가**"                    │
   │    → 클래스·객체를 결합해 **더 큰 구조 형성**          │
   │                                                       │
   │ **③ 행위(Behavioral) — 11개**                          │
   │    "**객체 간 책임을 어떻게 분배·소통할 것인가**"        │
   │    → 알고리즘과 **책임 할당** 방식 정의                │
   └───────────────────────────────────────────────────────┘

   ※ **범위(Scope)** 기준 : 클래스 패턴(상속) / 객체 패턴(합성)
   ※ 핵심 설계 원칙 : **"상속보다 합성(Composition over Inheritance)"**
                     **"구현이 아닌 인터페이스에 프로그래밍하라"**

2. 생성 패턴 (Creational Patterns) — 5개​

패턴목적설명
Singleton인스턴스 1개만 보장클래스의 인스턴스가 하나만 존재하도록 하고 전역 접근점 제공
Factory Method생성 책임을 서브클래스에 위임객체 생성 인터페이스를 정의하되 어떤 클래스를 생성할지는 서브클래스가 결정
Abstract Factory관련 객체군을 생성구체 클래스를 지정하지 않고 연관된 객체들의 집합을 생성
Builder복잡한 객체를 단계적으로 생성생성 과정과 표현을 분리 → 동일 절차로 다른 표현 생성
Prototype복제(Clone) 로 생성원본 객체를 복사하여 새 객체 생성 → 생성 비용 절감
   [**Singleton 구조 및 예시**]

   ┌────────────────────────────────┐
   │  **Singleton**                  │
   ├────────────────────────────────┤
   │ - **static instance : Singleton**│ ← 유일 인스턴스 보관
   │ - **Singleton()**  (private)    │ ← **외부 생성 차단**
   ├────────────────────────────────┤
   │ + **static getInstance()**      │ ← 유일한 접근 경로
   └────────────────────────────────┘
            ▲
      Client ─── getInstance() 호출 (항상 **동일 객체** 반환)

   [활용] **DB 커넥션 풀, 설정 관리자, 로거, 캐시**
   [주의] **멀티스레드 동기화**(Double-Checked Locking, Enum 방식),
          전역 상태로 인한 **테스트 곤란·결합도 상승** → DI 컨테이너 권장
   [**Factory Method 구조 및 예시**]

   **Creator**(추상)                    **Product**(추상)
   + operation()                       + use()
   + **factoryMethod()** ◀추상          ▲
        ▲                              │
   ┌────┴────┐                    ┌────┴────┐
   **ConcreteCreatorA**            **ConcreteProductA**
   + factoryMethod() ────생성───▶
   **ConcreteCreatorB**            **ConcreteProductB**
   + factoryMethod() ────생성───▶

   [효과] 클라이언트는 **구체 클래스를 몰라도 됨** → **OCP 준수**
          새 제품 추가 시 **기존 코드 수정 불필요**
   [활용] JDBC `DriverManager.getConnection()`,
          로그 프레임워크의 `getLogger()`, Spring `BeanFactory`

3. 구조 패턴 (Structural Patterns) — 7개​

패턴목적설명
Adapter인터페이스 변환호환되지 않는 인터페이스를 클라이언트가 기대하는 형태로 변환(변환기)
Bridge추상과 구현 분리추상 계층과 구현 계층을 독립적으로 확장 가능하게 분리
Composite부분-전체 계층개별 객체와 복합 객체를 동일하게 다룸(트리 구조)
Decorator기능 동적 추가상속 없이 객체를 감싸(Wrapping) 기능을 동적으로 확장
Facade단순화된 창구복잡한 서브시스템에 대한 통합된 상위 인터페이스 제공
Flyweight객체 공유다수의 유사 객체가 공통 상태를 공유하여 메모리 절감
Proxy대리 객체실제 객체에 대한 접근을 제어(지연 로딩·권한·원격·캐싱)
   [**Adapter 구조**]

   Client ──▶ **Target**(기대 인터페이스)
                 ▲
                 │ 구현
              **Adapter** ──위임──▶ **Adaptee**(기존 클래스)
              + request()            + specificRequest()
                                       ※ **수정 불가한 레거시·외부 라이브러리**

   [활용] 레거시 시스템 연동, **외부 API 래핑**, 이기종 인터페이스 통합
   [**Decorator 구조 — 상속의 폭발 문제 해결**]

   **[문제]** 커피 + 옵션 조합마다 클래스 생성
              → 아메리카노+샷, +시럽, +샷+시럽 … **조합 폭발**

   **[해결]**  Component(인터페이스) : cost()
                ▲                    ▲
          **ConcreteComponent**   **Decorator**(Component 보유)
             (기본 커피)            ▲       │ 위임
                                    │       ▼
                          **ShotDecorator** ─▶ 감싼 객체.cost() + 500
                          **SyrupDecorator** ─▶ 감싼 객체.cost() + 300

   new Syrup( new Shot( new Americano() ) ) ⇒ **런타임 조합**

   [활용] **Java I/O**(`new BufferedReader(new FileReader(f))`),
          Spring **AOP**, HTTP 요청 인터셉터

4. 행위 패턴 (Behavioral Patterns) — 11개​

패턴목적설명
Observer1:N 상태 변화 통지한 객체의 상태 변화를 의존 객체들에게 자동 통보
Strategy알고리즘 교체알고리즘군을 캡슐화하여 런타임에 교체 가능하게 함
Template Method알고리즘 골격 정의상위 클래스가 골격을, 세부 단계는 서브클래스가 구현
Command요청의 객체화요청을 객체로 캡슐화 → 큐잉·로깅·Undo 지원
State상태별 행위 변경객체의 내부 상태에 따라 행위를 클래스로 분리
Chain of Responsibility처리 책임 연쇄요청을 처리할 객체를 만날 때까지 체인을 따라 전달
Iterator순차 접근내부 표현을 노출하지 않고 집합체 원소를 순회
Mediator중재자 통한 통신객체 간 직접 참조를 제거하고 중재자를 통해 상호작용
Memento상태 저장·복원캡슐화를 위반하지 않고 내부 상태를 저장·복구(Undo)
Visitor연산 분리구조를 변경하지 않고 새 연산을 추가
Interpreter문법 해석언어의 문법을 표현하고 해석기 구현
   [**Observer 구조**]

   **Subject**(주제)                    **Observer**(관찰자)
   - observers : List                  + **update()**
   + attach(o) / detach(o)                  ▲
   + **notify()** ──── 반복 호출 ─────┬─────┴──────┐
        ▲                        **ObserverA**  **ObserverB**
        │                         (화면 갱신)   (로그 기록)
   **ConcreteSubject**
   - state
   + setState() ──▶ 상태 변경 시 **notify()** 자동 호출

   [효과] Subject는 Observer의 **구체 타입을 모름** → **느슨한 결합**
   [활용] **MVC의 Model-View**, GUI 이벤트 리스너,
          **Pub/Sub 메시징**, ReactiveX·Spring `ApplicationEvent`
   [**Strategy 구조 — if-else 분기 제거**]

   **[Before]**                      **[After]**
   if(type=="카드") 카드결제();        Context
   else if(type=="계좌") 계좌결제();     - strategy : **PaymentStrategy**
   else if(type=="간편") 간편결제();     + pay() ──▶ strategy.pay()
   ⇒ **결제수단 추가마다 수정**(OCP 위반)      ▲
                                              │ 구현
                                    ┌─────────┼─────────┐
                                 **CardPay** **BankPay** **EasyPay**
                                 ⇒ 새 전략 추가 시 **기존 코드 무수정**

   [활용] 결제·인증·정렬·압축 알고리즘 선택, 할인 정책, **Spring의 다형성 주입**

Ⅴ. 적용 시 고려사항 및 결론​

1. 적용 시 고려사항​

고려사항내용
① 문제 없는 곳에 패턴 금지패턴을 위한 패턴(Pattern Fever) 은 오히려 복잡도 증가 → 문제 상황이 먼저
② 아키텍처 스타일은 품질속성 기반 선택성능·확장성·가용성·보안 등 요구 품질속성과 Trade-off 분석 후 결정(ATAM 활용)
③ MSA는 조직 역량 전제DevOps·CI/CD·관측성 없이 MSA 도입 시 분산 모놀리스 전락 → 모놀리식 우선(Monolith First) 전략 고려
④ 패턴의 언어·프레임워크 내재화Spring DI가 Factory·Singleton을, AOP가 Proxy·Decorator를 이미 제공 → 직접 구현 불필요
⑤ 아키텍처 의사결정 기록ADR(Architecture Decision Record)로 선택 배경·대안·근거 문서화
⑥ 진화적 아키텍처스타일은 고정된 것이 아님 → 적합성 함수(Fitness Function) 로 지속 검증·진화
⑦ 안티패턴 경계God Object, 분산 모놀리스, 싱크홀, Golden Hammer(한 패턴 남용)

2. 결론​

아키텍처 스타일과 디자인 패턴은 추상화 수준이 다를 뿐, "검증된 해결책의 재사용"이라는 동일한 문제의식에서 출발한 설계 지식 체계이다. 아키텍처 스타일이 "시스템을 어떻게 나누고 연결할 것인가" 라는 거시적 구조를 결정한다면, 디자인 패턴은 그 구조 안에서 "객체들이 어떻게 협력할 것인가" 를 다루는 미시적 해법이다.

두 개념의 가장 실무적인 차이는 변경 비용에 있다. 디자인 패턴은 잘못 선택해도 리팩터링으로 교정 가능하지만, 아키텍처 스타일은 한 번 결정되면 되돌리는 비용이 사실상 재구축 수준이다. 따라서 아키텍처 스타일은 품질속성 요구사항(성능·확장성·가용성)에 대한 명시적 분석과 Trade-off 판단을 거쳐 결정하고, 그 근거를 ADR로 문서화해야 한다.

특히 경계해야 할 것은 유행에 따른 선택이다. MSA는 대규모 트래픽과 대규모 조직이라는 문제 상황에 대한 해법이지, 모든 시스템의 정답이 아니다. 조직 규모가 작고 요구사항이 안정적이라면 잘 설계된 계층형 모놀리식이 훨씬 우월한 선택이며, 실제로 Monolith First 후 필요 시점에 분해하는 전략이 실패 확률이 낮다.

디자인 패턴 역시 마찬가지다. 패턴은 문제를 만났을 때 꺼내 쓰는 도구이지, 먼저 적용할 목표가 아니다. 오늘날 Spring·Java 표준 라이브러리가 Singleton·Factory·Proxy·Observer를 이미 프레임워크 수준에서 제공하므로, 기술사에게 요구되는 역량은 패턴을 직접 구현하는 능력보다 "현재 코드의 문제가 어떤 패턴이 해결하려던 문제인지 식별하고, 적절한 추상화 수준에서 해법을 선택하는 판단력" 이다.

오토 스케일링

문제​

8.오토 스케일링(Auto Scaling)

Ⅰ. 개요​

오토 스케일링(Auto Scaling) 은 애플리케이션의 부하 변화를 실시간으로 감시하여 컴퓨팅 자원(인스턴스·컨테이너)의 수나 크기를 자동으로 조절함으로써, 서비스 가용성과 성능을 유지하면서 비용을 최적화하는 클라우드의 핵심 기능이다. NIST 클라우드 5대 특성 중 신속한 탄력성(Rapid Elasticity) 을 구현하는 실체적 수단이다.

   [등장 배경]
   **온프레미스** : **피크 부하 기준**으로 자원을 사전 구매
        │  · 평시에는 **자원의 대부분이 유휴** → 비용 낭비
        │  · 예측 못한 트래픽 급증 시 **서비스 장애**
        │  · 증설에 **수주~수개월** 소요
        ▼
   [**오토 스케일링**]
   · 부하에 따라 **필요한 만큼만 자동 확보·회수**
   · **가용성 확보 + 비용 절감**을 동시에 달성
   · 장애 인스턴스 **자동 교체**(자가 치유)까지 포함

Ⅱ. 스케일링 방식 및 구성요소​

 ┌──── **① 수직 확장**(Scale Up/Down) ────┐  ┌──── **② 수평 확장**(Scale Out/In) ────┐
 │        [작은 서버]                     │  │   [서버] → [서버][서버][서버]         │
 │            ↓ 사양 증설                 │  │                                       │
 │        [큰 서버]                       │  │   **동일 사양 인스턴스 수 증감**       │
 │  CPU·메모리 **자체를 늘림**            │  │  · **무중단** 확장 가능 ○             │
 │  · 재기동 필요(다운타임) ✕             │  │  · **이론상 무한 확장** ○             │
 │  · **물리적 한계 존재** ✕              │  │  · **로드밸런서·무상태 설계 필요**     │
 │  · 단일 장애점(SPOF) 유지 ✕            │  │  ⇒ **오토 스케일링의 기본 방식**       │
 └────────────────────────────────────────┘  └───────────────────────────────────────┘
 ┌───────────── **오토 스케일링 동작 구조** ─────────────┐
 │                                                       │
 │   [사용자 트래픽]                                     │
 │         ▼                                             │
 │   [**로드 밸런서(LB)**] ── 트래픽 분산 · 헬스체크       │
 │         ▼                                             │
 │   ┌── **Auto Scaling Group(ASG)** ──────────────┐     │
 │   │  [Inst1] [Inst2] [Inst3] … **Min~Max 범위**  │     │
 │   │      ▲                                       │     │
 │   │  **시작 템플릿**(Launch Template)             │     │
 │   │   — AMI·인스턴스 타입·보안그룹 정의           │     │
 │   └──────────────┬───────────────────────────────┘     │
 │                  │ 메트릭 수집                          │
 │         [**모니터링**(CloudWatch 등)]                   │
 │                  │ CPU·메모리·요청수·큐 길이            │
 │                  ▼                                     │
 │         [**스케일링 정책**] ── 임계치 초과 판단          │
 │                  │                                     │
 │                  ▼ **Scale Out / Scale In 실행**        │
 └───────────────────────────────────────────────────────┘
구성요소역할
Auto Scaling Group관리 대상 인스턴스 집합, 최소·희망·최대 용량 정의
시작 템플릿·구성새 인스턴스 생성 시 사용할 이미지·사양·네트워크·초기화 스크립트
로드 밸런서트래픽 분산 + 헬스체크(비정상 인스턴스 제외)
모니터링·메트릭CPU 사용률, 메모리, 요청 수(RPS), 응답시간, 큐 길이
스케일링 정책확장·축소 조건과 증감 규모 정의
쿨다운/워밍업연속 스케일링 방지를 위한 대기 시간

Ⅲ. 스케일링 정책 유형​

정책 유형내용특징
① 단순/단계 조정(Simple/Step)임계치 초과 시 정해진 수만큼 증감
예) CPU 70% 초과 → +2대		단순하나 반응 지연·과확장 우려
② 목표 추적(Target Tracking)목표 지표값 유지하도록 자동 조절
예) 평균 CPU 50% 유지		가장 권장, 설정 간단·안정적
③ 예약 기반(Scheduled)시간 기반 사전 확장
예) 매일 09시 +5대, 수강신청·오픈행사		예측 가능한 부하에 효과적, 부팅 지연 회피
④ 예측 기반(Predictive)머신러닝으로 과거 패턴 학습 → 사전 확장부팅 지연 문제 해결, 주기적 패턴 필요
⑤ 이벤트/큐 기반메시지 큐 길이·이벤트 수 기준 확장비동기 배치·워커 처리에 적합(KEDA)
적용 계층기술
VM 계층AWS Auto Scaling Group, Azure VMSS, GCP MIG
컨테이너(Pod) 계층HPA(수평, Pod 수 조절), VPA(수직, 리소스 요청 조절)
클러스터 노드 계층Cluster Autoscaler, Karpenter — Pod 배치 불가 시 노드 자체 증설
이벤트 기반KEDA — 큐·Kafka·Cron 등 외부 메트릭 기반 확장(0까지 축소 가능)
서버리스Lambda·Cloud Run — 요청 단위 자동 확장(관리 불필요)
DB 계층Aurora Serverless, 읽기 복제본 자동 추가

Ⅳ. 효과 및 고려사항​

구분내용
기대효과· 가용성 향상 — 트래픽 급증 시 자동 대응, 장애 인스턴스 자동 교체
· 비용 최적화 — 유휴 자원 회수, 필요한 만큼만 과금
· 운영 자동화 — 야간·주말 수동 대응 불필요
· 다중 AZ 분산 배치로 재해 대응력 강화
선결 요건(중요)· 무상태(Stateless) 설계 — 세션은 Redis 등 외부 저장소로 분리
· 로컬 디스크에 데이터 저장 금지 → 오브젝트 스토리지·공유 스토리지
· 로그 외부 집중화(인스턴스 종료 시 로그 소실 방지)
· 빠른 부팅(경량 AMI·컨테이너 이미지, 초기화 최소화)
주요 고려사항· 스케일 아웃 지연(VM 부팅 수 분) → 예측·예약 정책 병행, 워밍풀 활용
· 플래핑(Flapping) — 확장·축소 반복 → 쿨다운·이력현상(Hysteresis) 설정
· 축소 시 세션 유실 → 연결 드레이닝(Deregistration Delay) 적용
· DB가 병목 — 애플리케이션만 확장하면 DB 커넥션 고갈 → 커넥션 풀·읽기 복제본
· 비용 폭증 위험 — 트래픽 공격(DDoS)에 따른 무한 확장 → 최대 용량 상한·예산 알람 필수
· 메트릭 선정 — CPU만으로 부족한 경우 응답시간·RPS·큐 길이 등 복합 지표 사용
활용 사례이커머스 대규모 할인 행사, 수강신청·티켓팅, 미디어 스트리밍 피크, 배치 작업 워커 확장, 공공 재난문자·민원 급증 대응

Ⅴ. 결론​

오토 스케일링은 "필요한 만큼만 사용한다" 는 클라우드의 경제성을 실현하는 핵심 기능으로, 가용성과 비용이라는 상충 관계를 자동화로 해소한다. 그러나 오토 스케일링은 버튼 하나로 켜지는 기능이 아니라 아키텍처 설계의 결과이다.

성공적인 적용을 위한 실무적 전제는 세 가지이다. 첫째, 무상태(Stateless) 설계이다. 세션·파일·로그가 인스턴스 로컬에 남아 있으면 축소 시점에 데이터가 유실되므로, 상태는 반드시 외부 저장소로 분리해야 한다. 둘째, 스케일 아웃 지연에 대한 대비이다. VM 부팅에 수 분이 걸리는 동안 이미 장애가 발생할 수 있으므로, 예측 가능한 이벤트는 예약·예측 정책으로 선제 확장하고, 컨테이너·서버리스로 확장 속도 자체를 단축하는 것이 효과적이다. 셋째, 병목의 이동을 고려한 전 계층 설계이다. 애플리케이션 계층만 확장하면 DB가 새로운 병목이 되므로, 커넥션 풀·읽기 복제본·캐시를 함께 설계해야 한다.

마지막으로 최대 용량 상한과 비용 알람을 반드시 설정하여, DDoS나 버그로 인한 무한 확장이 곧바로 비용 사고로 이어지지 않도록 통제하는 것이 운영 관점의 필수 안전장치이다.

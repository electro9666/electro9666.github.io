문제​

13.SBOM(Software Bill of Material)

Ⅰ. 개요​

SBOM(Software Bill of Materials, 소프트웨어 자재명세서) 은 소프트웨어를 구성하는 모든 컴포넌트·라이브러리·의존관계·라이선스 정보를 기계 판독 가능한 형식으로 목록화한 명세서이다. 제조업의 BOM(부품표) 개념을 소프트웨어에 적용한 것으로, 소프트웨어 공급망 보안(Software Supply Chain Security) 의 핵심 수단이다.

   [등장배경]
   · 현대 SW의 **70~90%가 오픈소스** 등 외부 컴포넌트로 구성
   · **Log4Shell**(2021, Log4j) — "우리가 Log4j를 쓰는지조차 모른다"
   · **SolarWinds**(2020) — 빌드 파이프라인 침해로 정상 업데이트에 악성코드
   · 미국 **행정명령 EO 14028**(2021) → 연방정부 납품 SW에 **SBOM 제출 의무화**
   · 국내 : **과기정통부 SBOM 가이드**, EU **CRA**(사이버복원력법)
        ▼
   [**SBOM**] — "무엇으로 만들어졌는지 아는 것"이 **대응의 출발점**

Ⅱ. SBOM의 구성요소 및 표준 형식​

1. 최소 구성요소 (NTIA Minimum Elements)​

구분항목내용
데이터 필드공급자명(Supplier)컴포넌트 제작·배포 주체
컴포넌트명(Component)라이브러리·모듈 이름
버전(Version)취약점 매칭의 핵심 키
고유 식별자CPE, PURL, SWID 등
의존관계(Dependency)상위-하위 컴포넌트 포함 관계
SBOM 작성자명세서 생성 주체
타임스탬프생성 일시
자동화 지원기계 판독 형식SPDX, CycloneDX, SWID
실무 관행갱신 주기·배포·접근통제빌드마다 생성, 요청 시 제공
   [**SBOM의 의존관계 트리**]

   **MyApp v1.0**
     ├── spring-boot-starter-web **3.2.0** (Apache-2.0)
     │     ├── spring-web 6.1.2
     │     └── jackson-databind **2.15.3** ← **CVE 매칭 대상**
     ├── log4j-core **2.14.1** (Apache-2.0) ⚠ **CVE-2021-44228**
     └── mysql-connector-j 8.2.0 (**GPL-2.0** ⚠ 라이선스 주의)

   ⇒ **직접(Direct) 의존성**뿐 아니라 **전이(Transitive) 의존성**까지 포함해야
      실질적 가치 발생 (Log4Shell 피해의 상당수가 전이 의존성)

2. 표준 형식 비교​

구분SPDXCycloneDXSWID
주관Linux FoundationOWASPISO/IEC 19770-2
표준화ISO/IEC 5962ECMA-424ISO 국제표준
주 목적라이선스 컴플라이언스보안 취약점 분석자산(SW) 관리
형식JSON, YAML, RDF, Tag-ValueJSON, XMLXML
확장라이선스 표현 강점VEX, HBOM, SaaSBOM 등 확장 풍부설치 태그 중심

Ⅲ. 생성·활용 절차 및 효과​

   ┌────────── **SBOM 생명주기(DevSecOps 통합)** ──────────┐
   │                                                        │
   │  **① 생성**(Generate)                                   │
   │     빌드 단계에서 **SCA 도구**로 자동 생성              │
   │     (Syft, Trivy, CycloneDX Maven/Gradle Plugin)       │
   │           ▼                                            │
   │  **② 검증·서명**(Sign)                                  │
   │     **Sigstore/Cosign** 으로 무결성 서명                │
   │     → SBOM 자체의 **위·변조 방지**                      │
   │           ▼                                            │
   │  **③ 저장·배포**(Distribute)                            │
   │     아티팩트 저장소·**SBOM 리포지터리**에 버전별 보관    │
   │           ▼                                            │
   │  **④ 분석**(Analyze)                                    │
   │     **NVD·KISA 취약점 DB와 대조** → CVE 매칭            │
   │     라이선스 정책 위반 검출(GPL 등 **Copyleft**)        │
   │           ▼                                            │
   │  **⑤ 대응**(Respond)                                    │
   │     영향 범위 즉시 식별 → **패치 우선순위 결정**        │
   │     **VEX**(Exploitability eXchange)로 "영향 없음" 통보 │
   └────────────────────────────────────────────────────────┘
관점기대효과
보안신규 CVE 발표 시 영향 시스템을 수 시간 내 식별(기존 : 수 주)
공급망협력사·오픈소스 컴포넌트의 투명성 확보, 3rd party 리스크 관리
라이선스GPL 등 Copyleft 라이선스 위반 사전 차단, M&A 실사 대응
운영EOL·미유지보수 컴포넌트 식별 → 기술부채 관리
규제 대응미국 EO 14028, EU CRA, 국내 SBOM 가이드 등 납품 요건 충족

Ⅳ. 도입 시 고려사항 및 한계​

구분내용
한계· SBOM은 목록일 뿐 취약 여부를 판정하지 않음 → VEX 병행 필요
· 전이 의존성 누락·오탐 발생 가능(동적 로딩·벤더 바이너리)
· 바이너리만 있는 상용 SW는 정확한 SBOM 생성 곤란
· SBOM 자체가 공격자에게 취약점 지도가 될 수 있음 → 접근통제 필수
고려사항· 빌드 시점 자동 생성(수기 작성은 즉시 진부화) → CI/CD 파이프라인 내재화
· 형식은 CycloneDX(보안) + SPDX(라이선스) 목적별 선택 또는 병행
· 버전 단위 이력 관리 — 배포된 모든 버전의 SBOM 보관
· 계약·조달 요건화 — 공급사에 SBOM 제출 의무 명시
· SBOM → 취약점 관리 프로세스와 연계해야 실효성 확보

Ⅴ. 결론​

SBOM은 "무엇을 쓰고 있는지 모르면 무엇을 지켜야 할지도 알 수 없다" 는 문제의식에서 출발한다. Log4Shell 사태에서 대응 속도를 가른 것은 기술력이 아니라 자사 소프트웨어의 구성 정보를 즉시 조회할 수 있는가였으며, 이것이 SBOM이 규제 요건으로 급부상한 배경이다.

다만 SBOM은 그 자체로 보안을 제공하지 않는 '재료 목록' 임을 인식해야 한다. 실질적 가치는 취약점 DB 매칭 → VEX를 통한 실제 영향 판정 → 패치 우선순위 결정으로 이어지는 자동화된 취약점 관리 프로세스와 결합될 때 발생한다.

따라서 실무적으로는 SBOM을 납품용 문서로 한 번 만드는 산출물이 아니라, CI/CD 파이프라인에서 빌드마다 자동 생성·서명·축적되는 운영 데이터로 다루어야 하며, 향후 AI 모델의 구성요소를 명세하는 AI-BOM으로까지 개념이 확장되고 있다는 점도 주목할 필요가 있다.

실행 중인 애플리케이션의 배포 전략 및 테스트 전략

문제​

1.실행 중인 애플리케이션에 대한 배포 전략 및 테스트 전략에 대하여 설명하시오.

Ⅰ. 개요​

1. 배경​

DevOps·CI/CD 확산으로 배포 주기가 하루 수십 회에 이르면서, 서비스를 중단하지 않고(무중단) 배포하되 장애 위험을 최소화하는 전략이 필수가 되었다.

   [전통적 배포]                        [**현대적 배포**]
   서비스 중단 공지 → 배포 → 재개        **무중단 배포**
   야간·주말 작업, 월 1~2회              하루 수십 회, 업무 시간 중 배포
   실패 시 **긴 복구 시간**               **즉시 롤백** 가능
        ▼                                      ▼
   낮은 배포 빈도 = 큰 변경량 = 높은 위험   작은 변경 = 낮은 위험 = 빠른 피드백

2. 배포와 릴리스의 분리​

   **배포(Deployment)** : 코드를 운영 환경에 **설치**하는 기술적 행위
   **릴리스(Release)**  : 기능을 사용자에게 **공개**하는 비즈니스 결정
        └──► **Feature Flag**로 분리 가능
             "배포는 했지만 아직 켜지 않음" → 위험 분산의 핵심 개념

Ⅱ. 배포 전략​

1. 주요 배포 전략​

   [**롤링 배포**]                    [**블루/그린 배포**]
   V1 V1 V1 V1                        ┌── **Blue**(현재 V1) ──┐ ◄── 트래픽
   V2 V1 V1 V1  ← 순차 교체            └───────────────────────┘
   V2 V2 V1 V1                        ┌── **Green**(신규 V2) ─┐
   V2 V2 V2 V2                        └───────────────────────┘
                                       배포·검증 후 **트래픽 일괄 전환**

   [**카나리 배포**]                  [**A/B 테스트**]
   ┌─ V1 (95%) ─┐ ◄── 대부분 트래픽    ┌─ A안 (50%) ─┐ 특정 사용자 그룹
   └─ V2 (5%) ──┘ ◄── 소수 트래픽      └─ B안 (50%) ─┘ (지역·연령·기기별)
   지표 정상 → 점진 확대(5→25→50→100%)  **비즈니스 지표 비교**가 목적
전략방식장점단점적합 상황
롤링(Rolling)인스턴스를 순차적으로 교체추가 자원 불필요, 구현 단순배포 중 두 버전 공존, 롤백 느림일반적 무중단 배포
블루/그린동일 환경 2벌 운영 후 트래픽 일괄 전환즉시 롤백(트래픽만 되돌림), 검증 후 전환자원 2배 필요, DB 스키마 호환 필요롤백 속도가 중요한 서비스
카나리소수 트래픽부터 점진 확대실사용자 기반 위험 최소화, 조기 이상 감지모니터링 체계 필수, 배포 시간 김위험도 높은 변경
A/B 테스트그룹별 다른 버전 제공비즈니스 효과 검증통계적 설계 필요기능 효과 측정
Feature Flag
(Dark Launch)		배포 후 스위치로 기능 활성화배포와 릴리스 분리, 즉시 On/Off플래그 관리 부채점진적 기능 공개
재생성(Recreate)전체 중단 후 교체단순서비스 중단개발·테스트 환경

2. 배포 시 핵심 고려사항​

고려사항내용
데이터베이스 스키마배포 중 두 버전이 공존하므로 하위 호환 스키마 변경 필수
· 확장-축소 패턴(Expand-Contract): ① 컬럼 추가(양쪽 호환) → ② 신버전 배포 → ③ 구버전 제거 후 기존 컬럼 삭제
· 파괴적 변경(컬럼 삭제·이름 변경) 금지
세션·상태 관리인스턴스 교체 시 세션 유실 방지 → 무상태(Stateless) 설계, 세션 외부화(Redis)
API 하위 호환성구버전 클라이언트 지원, 버전 관리(v1·v2 병행)
헬스체크Readiness Probe로 준비된 인스턴스에만 트래픽 전달, Liveness Probe로 이상 인스턴스 재시작
Graceful Shutdown종료 전 처리 중인 요청 완료 대기, 신규 요청 차단
롤백 계획자동 롤백 조건(오류율·지연 임계값) 사전 정의, 롤백 소요 시간 검증
배포 자동화CI/CD 파이프라인, IaC로 환경 일관성 확보, GitOps

Ⅲ. 테스트 전략​

1. 배포 파이프라인 단계별 테스트​

   ┌─────────────── **배포 전(Pre-deployment)** ───────────────┐
   │ **단위 테스트** → **통합 테스트** → **E2E 테스트** →        │
   │ 성능·부하 테스트 → 보안 테스트(SAST·SCA·DAST)             │
   │ ▲ CI 파이프라인에서 자동 실행, **게이트 통과 시에만 배포**   │
   └───────────────────────┬───────────────────────────────────┘
   ┌───────────────────────▼── **배포 중(In-deployment)** ─────┐
   │ **스모크 테스트**(핵심 기능 최소 확인)                      │
   │ **헬스체크·Readiness 검증**                                │
   │ **카나리 분석**(신·구 버전 지표 자동 비교)                  │
   └───────────────────────┬───────────────────────────────────┘
   ┌───────────────────────▼── **배포 후(Post-deployment)** ───┐
   │ **운영 환경 테스트**(Testing in Production)                │
   │ · 합성 모니터링 · **A/B 테스트** · 카오스 엔지니어링         │
   │ · 실사용 지표 모니터링 → 이상 시 **자동 롤백**              │
   └───────────────────────────────────────────────────────────┘

2. 테스트 피라미드​

        ╱‾‾‾‾╲      **E2E 테스트** — 적게, 느림, 비용 큼
       ╱ E2E  ╲      전체 시나리오 검증
      ╱────────╲
     ╱ 통합 테스트╲   **통합 테스트** — 중간
    ╱────────────╲    모듈·외부 연동 검증
   ╱  단위 테스트   ╲  **단위 테스트** — 많이, 빠름, 저렴
  ╱________________╲  개별 함수·클래스 검증
   ⇒ **하위 계층을 두껍게** 구성해야 빠른 피드백과 낮은 유지비용 확보

3. 주요 테스트 기법​

테스트내용시점
단위·통합 테스트코드 레벨 검증, 회귀 방지의 기반CI
계약 테스트(Contract)MSA에서 서비스 간 인터페이스 호환성 검증(Pact) — E2E보다 빠르고 안정적CI
스모크 테스트배포 직후 핵심 기능만 신속 확인(로그인·조회·결제)배포 직후
회귀 테스트기존 기능 손상 여부 확인 — 자동화 필수CI/배포 전
성능·부하 테스트목표 TPS·응답시간 검증, 스트레스·내구성(Soak) 테스트배포 전
보안 테스트SAST·SCA·DAST, 취약점 스캔CI/CD
합성 모니터링
(Synthetic)		운영 환경에서 주기적 가상 트랜잭션 실행으로 상시 검증운영 중
카나리 분석
(Automated Canary Analysis)		신·구 버전의 오류율·지연·자원 사용률 자동 비교 → 통계적 판정배포 중
섀도 트래픽(Shadow)실제 트래픽을 복제하여 신버전에 전달(응답은 버림) → 운영 영향 없이 검증배포 전후
카오스 엔지니어링의도적 장애 주입으로 복원력 검증(인스턴스 종료·지연 삽입)운영 중

4. 운영 환경 테스트(Testing in Production)​

   [필요성]
   스테이징 환경은 **실제 트래픽·데이터 규모·외부 연동을 완전히 재현할 수 없음**
        ▼
   운영 환경에서만 발견되는 문제 존재 → **통제된 방식으로 운영 검증**

   [안전장치]
   ① **Feature Flag**로 즉시 비활성화 가능하게
   ② **카나리로 영향 범위 제한**(소수 트래픽)
   ③ **관측성 확보** — 로그·메트릭·트레이스로 즉시 이상 감지
   ④ **자동 롤백 조건** 사전 정의

5. 배포·테스트 전략의 결합​

배포 전략권장 테스트 전략
롤링배포 전 회귀 테스트 + 인스턴스별 헬스체크·스모크 테스트
블루/그린Green 환경에서 전체 E2E·성능 테스트 완료 후 전환, 전환 후 스모크
카나리자동 카나리 분석(지표 비교) + 실사용자 모니터링, 단계별 승인
Feature Flag내부 사용자 → 소수 → 전체 순 점진 노출, A/B 지표 측정

Ⅳ. 관측성(Observability) — 전략의 전제 조건​

요소내용
메트릭(Metrics)오류율·응답시간·처리량·자원 사용률 — 롤백 판단 기준
로그(Logs)구조화 로그 중앙 수집, 배포 버전 태깅
트레이스(Traces)분산 추적으로 성능 저하 구간 식별(OpenTelemetry)
SLO·에러 예산목표 대비 여유 소진 시 배포 중단 정책(에러 예산 소진 정책)
알림·자동화임계값 초과 시 자동 롤백·담당자 통지

핵심: 관측성 없는 무중단 배포는 "문제가 생겼는지도 모르는 상태로 배포하는 것" 이므로, 배포 전략보다 모니터링 체계 구축이 선행되어야 한다.

Ⅴ. 결론​

실행 중인 애플리케이션의 배포는 "중단 없이 배포하는 것"을 넘어 "장애 위험을 통제 가능한 범위로 제한하는 것" 이 본질이다. 따라서 배포 전략과 테스트 전략은 분리된 활동이 아니라 하나의 위험 관리 체계로 설계되어야 한다.

실무 적용 원칙은 ① 변경의 위험도에 따라 전략을 차등 적용(일상적 변경은 롤링, 위험도 높은 변경은 카나리, 즉시 롤백이 필요하면 블루/그린), ② Feature Flag로 배포와 릴리스를 분리하여 위험을 시간적으로 분산, ③ 테스트 피라미드에 따라 하위 계층을 두껍게 구성하여 빠른 피드백 확보이다.

특히 유의할 점은 데이터베이스 스키마 변경으로, 배포 중 두 버전이 공존하므로 확장-축소 패턴에 따른 하위 호환 변경이 필수이며 이를 지키지 않으면 무중단 배포 자체가 성립하지 않는다.

궁극적으로 배포 전략의 성패는 기법 선택이 아니라 관측성과 자동 롤백 체계에 달려 있다. 문제를 즉시 감지하고 되돌릴 수 있을 때 비로소 작고 잦은 배포가 안전해지며, 이것이 DORA 지표가 말하는 배포 빈도와 변경 실패율의 동시 개선을 가능하게 한다.

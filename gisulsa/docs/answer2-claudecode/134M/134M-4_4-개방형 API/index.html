개방형 API(Open API)

문제​

4.개방형 API(Open API)에 대하여 설명하시오.
가.정의 및 특징
나.SOAP 및 REST 구성요소
다.취약점 및 대응 방안

Ⅰ. 개요​

API(Application Programming Interface) 는 소프트웨어 간 상호작용을 위한 인터페이스이며, 개방형 API는 이를 외부에 공개하여 제3자가 서비스·데이터를 활용할 수 있게 한 형태이다. 오픈뱅킹·공공데이터 개방·마이데이터 등 플랫폼 경제의 기반 기술로 자리 잡았다.

Ⅱ. 가. 개방형 API의 정의 및 특징​

1. 정의​

개방형 API는 서비스 제공자가 보유한 데이터·기능을 표준화된 인터페이스로 외부에 공개하여, 개발자·기업이 자유롭게 접근·활용해 새로운 서비스를 창출할 수 있도록 하는 API이다.

   [폐쇄형 vs 개방형]
   ┌──────────────┬──────────────────┬──────────────────────┐
   │   구분        │  **내부(Private)** │  **개방형(Open/Public)** │
   ├──────────────┼──────────────────┼──────────────────────┤
   │ 이용 대상     │ 조직 내부         │ **불특정 외부 개발자**  │
   │ 목적          │ 시스템 연계       │ **생태계 확장·수익화**  │
   │ 관리 요소     │ 기능 연동         │ **인증·과금·문서·SLA**  │
   │ 보안 위험     │ 상대적으로 낮음    │ **높음**(공격 표면 확대)│
   └──────────────┴──────────────────┴──────────────────────┘

   [API 경제(API Economy) 구조]
   **제공자**(데이터·기능) ──► **개방형 API** ──► **활용자**(신규 서비스)
        ▲                        │                    │
        └──── 수익·트래픽 ◄──────┴──── 가치 창출 ◄────┘

2. 특징​

특징내용
개방성공개된 명세에 따라 누구나 접근 가능(등록·인증 절차 존재)
표준화HTTP·JSON·OpenAPI Specification(OAS) 등 표준 준수 → 상호운용성
재사용성하나의 API를 다수 서비스가 반복 활용
추상화내부 구현·데이터 구조를 감추고 인터페이스만 노출(정보은닉)
느슨한 결합제공자·활용자가 독립적으로 발전 가능
생태계 확장제3자 개발자가 혁신 서비스를 창출 → 플랫폼 가치 증대(네트워크 효과)
버전 관리 필요외부 이용자가 있어 하위 호환성 유지가 필수
거버넌스 필수인증·권한·사용량 제한(Rate Limit)·과금·SLA·모니터링

3. 활용 사례​

분야사례
금융오픈뱅킹(계좌 조회·이체 API), 마이데이터(본인신용정보 전송), 간편결제
공공공공데이터포털 개방 API(기상·교통·인구), 전자정부 서비스 연계
플랫폼지도·소셜 로그인(OAuth)·결제(PG)·SMS API
AILLM API(생성형 AI), 음성·비전 인식 API

Ⅲ. 나. SOAP 및 REST 구성요소​

1. SOAP(Simple Object Access Protocol)​

  • 개념: XML 기반의 메시지 교환 프로토콜로, 엄격한 표준과 강력한 보안·트랜잭션 기능을 제공한다.
   [**SOAP 메시지 구조**]
   ┌───────────── **Envelope**(봉투) ─────────────┐  ← 메시지 전체를 감싸는 최상위
   │  ┌────────── **Header**(헤더) ──────────┐    │  ← 선택적
   │  │  인증 정보 · 트랜잭션 · 라우팅 ·      │    │     (WS-Security 등 확장)
   │  │  암호화 정보                          │    │
   │  └──────────────────────────────────────┘    │
   │  ┌────────── **Body**(본문) ────────────┐    │  ← 필수
   │  │  실제 요청·응답 데이터(XML)           │    │
   │  │  ┌──── **Fault**(오류) ────┐         │    │  ← 선택적
   │  │  │  오류 코드·메시지·상세   │         │    │     (오류 발생 시)
   │  │  └──────────────────────────┘         │    │
   │  └──────────────────────────────────────┘    │
   └──────────────────────────────────────────────┘
구성요소내용
EnvelopeSOAP 메시지의 시작과 끝을 정의하는 루트 요소(필수)
Header인증·보안(WS-Security)·트랜잭션·라우팅 등 부가 정보(선택)
Body실제 전달할 데이터(요청 파라미터·응답 결과)(필수)
Fault오류 정보(faultcode·faultstring·detail), Body 내부에 위치
WSDL서비스 명세서 — 제공 기능·파라미터·엔드포인트를 XML로 정의
UDDI서비스 등록·검색 저장소(현재는 거의 미사용)

2. REST(Representational State Transfer)​

  • 개념: HTTP 프로토콜의 특성을 그대로 활용하여 자원(Resource)을 URI로 식별하고 HTTP 메서드로 조작하는 아키텍처 스타일이다(Roy Fielding, 2000).
   [**REST의 3대 구성요소**]
   ┌────────────────────────────────────────────────────────┐
   │ **① 자원(Resource)** — URI로 식별                        │
   │     예) https://api.example.com/**users/123**            │
   │     · 명사 사용, 복수형, 계층 구조로 표현                 │
   ├────────────────────────────────────────────────────────┤
   │ **② 행위(Verb)** — HTTP 메서드로 표현                    │
   │     **GET**(조회) · **POST**(생성) · **PUT**(전체 수정) · │
   │     **PATCH**(부분 수정) · **DELETE**(삭제)              │
   ├────────────────────────────────────────────────────────┤
   │ **③ 표현(Representation)** — 자원의 상태 표현             │
   │     **JSON**(주로 사용) · XML · HTML                     │
   └────────────────────────────────────────────────────────┘

   [예시]
   **GET**    /users/123        → 123번 사용자 조회
   **POST**   /users            → 사용자 생성
   **PUT**    /users/123        → 123번 사용자 전체 수정
   **DELETE** /users/123        → 123번 사용자 삭제
REST 아키텍처 제약조건 (6원칙)내용
클라이언트-서버관심사 분리, 독립적 진화
무상태(Stateless)각 요청은 독립적 — 서버가 클라이언트 상태를 저장하지 않음
캐시 가능(Cacheable)응답의 캐시 가능 여부 명시 → 성능 향상
계층화(Layered System)프록시·게이트웨이 등 중간 계층 허용
균일 인터페이스(Uniform Interface)자원 식별·표현을 통한 조작·자기 서술적 메시지·HATEOAS
코드 온 디맨드(선택)서버가 클라이언트에 실행 코드 전송

3. SOAP과 REST 비교​

비교 기준SOAPREST
성격프로토콜(엄격한 규격)아키텍처 스타일(가이드라인)
데이터 형식XML 전용JSON(주로), XML, HTML 등 자유
전송 프로토콜HTTP·SMTP·TCP 등 다양HTTP/HTTPS 전용
명세WSDL(기계 판독 가능·엄격)OpenAPI(Swagger)
메시지 크기큼(XML 오버헤드)작음(경량)
성능낮음(파싱 부하)높음
보안WS-Security(메시지 수준 암호화·서명)HTTPS + OAuth 2.0(전송 수준)
트랜잭션WS-AtomicTransaction 지원(ACID)미지원(보상 트랜잭션으로 구현)
상태 관리Stateful 가능Stateless
오류 처리Fault 요소HTTP 상태 코드(200·400·401·404·500)
캐싱어려움HTTP 캐시 활용
학습 곡선높음낮음
적합 상황금융·결제·기업 간 거래(높은 보안·트랜잭션 보장 필요), 레거시 연동웹·모바일·공공데이터 개방(대부분의 개방형 API)

현재 동향: 개방형 API는 REST가 사실상 표준이며, 최근에는 GraphQL(필요한 데이터만 조회)과 gRPC(고성능 내부 통신)가 용도에 따라 병행 사용된다.

Ⅳ. 다. 개방형 API의 취약점 및 대응 방안​

1. 개방형 API의 위험 구조​

   [공격 표면의 확대]
   내부 시스템 → **외부에 인터페이스 노출**
        │
        ├─ **비즈니스 로직이 직접 노출**(웹 UI라는 완충 계층 부재)
        ├─ **자동화 공격에 취약**(스크립트로 대량 호출)
        ├─ **문서화된 명세**가 공격자에게도 유용한 정보
        └─ 다수 클라이언트 지원으로 **하위 호환 유지 → 구버전 취약점 잔존**

2. 주요 취약점 (OWASP API Security Top 10 기준)​

취약점내용사례
① 손상된 객체 수준 인가
(BOLA/IDOR)		API Top 1 위험
인증은 되었으나 다른 사용자의 자원에 접근 가능		/users/123/orders → ID를 124로 변경하면 타인 주문 조회
② 인증 취약점약한 인증, 토큰 탈취·재사용, 무차별 대입 방어 부재, JWT 검증 미흡만료되지 않는 토큰, 서명 미검증
③ 속성 수준 인가 실패과도한 데이터 노출 — 필요 이상의 필드 반환(클라이언트가 필터링한다고 가정)
대량 할당(Mass Assignment) — 요청 파라미터로 권한 필드 변조		응답에 주민번호·비밀번호 해시 포함
{"role":"admin"} 주입
④ 무제한 자원 소비Rate Limit 부재 → DoS·과금 폭탄, 페이징 없는 대량 조회대량 호출로 서비스 마비
⑤ 기능 수준 인가 실패관리자 전용 API에 일반 사용자 접근 가능/admin/users 접근 통제 누락
⑥ 민감 비즈니스 흐름 접근자동화 봇의 비즈니스 로직 남용티켓 매크로 구매, 재고 선점
⑦ SSRF서버가 사용자 입력 URL로 요청 → 내부망 접근클라우드 메타데이터 탈취
⑧ 보안 설정 오류CORS 과다 허용, 상세 오류 메시지 노출, TLS 미적용, 기본 계정스택 트레이스 노출
⑨ 인벤토리 관리 미흡문서화되지 않은 API(Shadow API), 폐기되지 않은 구버전 API(Zombie API)v1이 살아있어 취약점 잔존
⑩ 안전하지 않은 API 소비제3자 API 응답을 검증 없이 신뢰외부 API 통한 악성 데이터 유입
기타인젝션(SQLi·NoSQLi·명령어), 데이터 전송 구간 암호화 미흡

3. 대응 방안​

   ┌──────────── **API 보안 다층 방어 구조** ────────────┐
   │  클라이언트                                          │
   │      │ HTTPS(TLS 1.3)                               │
   │  ┌───▼──────── **API Gateway** ──────────────────┐   │
   │  │  · **인증(OAuth 2.0/JWT)** · 권한 검증          │   │
   │  │  · **Rate Limiting**·쿼터 · IP 필터            │   │
   │  │  · 요청 스키마 검증 · **WAF/API 보안**          │   │
   │  │  · 로깅·모니터링 · 버전 라우팅                  │   │
   │  └───┬────────────────────────────────────────────┘   │
   │  ┌───▼──────── 백엔드 서비스 ────────────────────┐   │
   │  │  · **객체 수준 인가 검증**(BOLA 방어)           │   │
   │  │  · 입력 검증 · 출력 필터링 · 최소 권한          │   │
   │  └────────────────────────────────────────────────┘   │
   └──────────────────────────────────────────────────────┘
영역대응 방안
① 인증(Authentication)· OAuth 2.0 / OpenID Connect 표준 적용
· JWT 사용 시 서명·만료·발급자 검증 필수
· API Key는 단독 사용 금지(식별용으로만), 정기 교체
· mTLS(고보안 구간), MFA
② 인가(Authorization)· 모든 요청마다 객체 소유권 검증(BOLA 방어의 핵심)
· RBAC/ABAC 기반 세분화된 권한 관리
· 기능 수준 인가를 게이트웨이가 아닌 서비스 로직에서도 검증
· 최소 권한 원칙
③ 입력 검증· 스키마 기반 검증(OpenAPI 명세 활용), 허용 목록 방식
· 파라미터화 쿼리(인젝션 방어), 타입·길이·형식 검증
· 대량 할당 방지 — 허용 필드만 바인딩(DTO 명시)
④ 출력 통제· 필요한 필드만 반환(응답 DTO 정의), 민감정보 마스킹
· 상세 오류 메시지 노출 금지(일반화된 오류 반환)
⑤ 자원 보호· Rate Limiting·쿼터(사용자·IP·API 키별)
· 페이징 강제, 요청 크기·타임아웃 제한
· 이상 트래픽 탐지, 봇 방어
⑥ 전송 보안HTTPS(TLS 1.3) 필수, HSTS, 민감 데이터는 페이로드 암호화
⑦ 설정 관리CORS 허용 도메인 최소화, 불필요 HTTP 메서드 차단, 보안 헤더 적용

· 폐기 정책(Deprecation) — 사전 공지 후 구버전 종료
· API 발견 도구로 미등록 API 탐지
⑨ 모니터링·대응· 전 요청 로깅(호출자·시각·파라미터), 이상행위 탐지
· SIEM 연계, 침해 시 API 키 즉시 폐기
⑩ 개발 프로세스· API 설계 단계 보안 검토(Security by Design)
· DAST·API 보안 테스트 CI 통합
· OWASP API Top 10 기준 정기 점검

Ⅴ. 결론​

개방형 API는 데이터·기능을 외부에 개방하여 생태계를 확장하는 플랫폼 경제의 핵심 수단이며, 오픈뱅킹·마이데이터·공공데이터 개방 등 국내 주요 정책의 기술적 기반이다. 기술적으로는 경량성과 확장성을 갖춘 REST가 사실상 표준이나, 금융 거래처럼 트랜잭션 보장과 메시지 수준 보안이 필요한 영역에서는 SOAP도 여전히 유효하다.

보안 관점에서 가장 중요한 인식은 "API 개방은 곧 공격 표면의 개방" 이라는 점이다. 특히 BOLA(객체 수준 인가 실패) 는 OWASP API Top 1 위험으로, 인증만 통과하면 다른 사용자의 데이터에 접근할 수 있는 구조적 취약점이며 자동화 도구로 쉽게 악용된다.

따라서 실무 대응의 핵심은 ① 모든 요청마다 객체 소유권을 검증하고, ② API Gateway로 인증·Rate Limit·로깅을 일원화하되 인가 검증은 서비스 로직에서도 이중 수행하며, ③ 응답에 필요한 필드만 반환(클라이언트 필터링을 신뢰하지 않음)하고, ④ Shadow/Zombie API를 제거하는 인벤토리 관리를 제도화하는 것이다.

궁극적으로 개방형 API의 성공은 기술적 개방성이 아니라 개발자가 신뢰하고 사용할 수 있는 안정성·보안성·명확한 거버넌스에 달려 있다.

SBOM(Software Bill of Materials)

문제​

3.SBOM(Software Bill of Materials)에 대하여 설명하시오.
가.오픈소스 소프트웨어 취약점
나.SBOM 기반 오픈소스 소프트웨어 관리 방안

Ⅰ. 개요​

1. 개념​

SBOM(소프트웨어 자재명세서) 은 소프트웨어를 구성하는 모든 구성요소(오픈소스 라이브러리·상용 컴포넌트·의존성)의 목록과 상호 관계, 라이선스·버전 정보를 기계 판독 가능한 형식으로 정리한 명세서이다. 제조업의 BOM(자재명세서) 개념을 소프트웨어에 적용한 것이다.

2. 필요성​

   [현대 소프트웨어의 구성]
   자체 개발 코드 **10~30%**  +  **오픈소스 70~90%**
        ▲                            ▲
        │                     "무엇이 들어있는지 모르는 상태"
        │                            │
   [**Log4Shell 사태(2021)**]
   Log4j 취약점 공개 → 전 세계 기업이 **"우리 시스템에 Log4j가 있는가"**
                       를 파악하는 데 수 주 소요
        ▼
   ⇒ **구성요소를 모르면 대응 자체가 불가능**
   ⇒ SBOM = **소프트웨어 공급망의 가시성 확보 수단**

3. 제도적 배경​

구분내용
미국행정명령 14028(2021) — 연방정부 납품 SW에 SBOM 제출 의무화, NTIA 최소 요소 정의
EUCRA(사이버복원력법) — 디지털 제품의 구성요소 문서화·취약점 관리 의무
국내과기정통부·KISA SW 공급망 보안 가이드라인, 공공 SW 보안 강화 정책
표준SPDX(ISO/IEC 5962), CycloneDX(OWASP), SWID Tag

Ⅱ. 가. 오픈소스 소프트웨어 취약점​

1. 오픈소스의 확산과 위험 구조​

   [의존성의 계층 구조 — 보이지 않는 위험]
   내 애플리케이션
        └── 직접 의존성 A (내가 선택함 — **인지 가능**)
                └── 전이 의존성 B (A가 사용 — **인지 어려움**)
                        └── 전이 의존성 C (B가 사용 — **거의 인지 불가**)
                                └── ...
   ⇒ 실제 취약점의 상당수는 **전이 의존성(Transitive Dependency)** 에서 발생
   ⇒ "내가 설치한 적 없는 라이브러리"가 시스템에 존재

2. 오픈소스 취약점의 유형​

유형내용사례
알려진 취약점(CVE)공개된 보안 결함이 있는 구버전 라이브러리 사용Log4Shell(Log4j RCE), Struts2, OpenSSL Heartbleed
전이 의존성 취약점직접 사용하지 않는 하위 의존성에 존재하는 취약점패키지 매니저가 자동 설치한 수백 개 의존성
유지보수 중단
(EOL·방치)		개발자가 관리를 중단한 프로젝트 → 패치 미제공1인 관리 프로젝트, 아카이브된 저장소
악성 패키지 등록Typosquatting(오타 유사명), Dependency Confusion(내부 패키지명 선점), Slopsquatting(LLM 환각 패키지명 선점)npm·PyPI 악성 패키지 다수
유지관리자 계정 탈취계정 탈취 또는 장기간 신뢰 획득 후 백도어 삽입XZ Utils 백도어(2024)
의도적 파괴(Protestware)개발자가 정치적 이유로 악성 코드 삽입node-ipc 사건
라이선스 위반GPL 등 카피레프트 라이선스 미준수 → 소스 공개 의무·법적 분쟁상용 제품에 GPL 코드 포함
라이선스 정책 변경개방형 → 폐쇄형 전환(SSPL·BSL)Elastic, HashiCorp, Redis

3. 오픈소스 취약점의 특성​

특성내용
파급성널리 쓰이는 라이브러리의 취약점은 동시에 수만 조직에 영향
가시성 부족전이 의존성까지 파악하기 어려워 영향 범위 산정 곤란
공개성의 양면소스가 공개되어 취약점 발견도 빠르지만 악용도 빠름(공개 즉시 무기화)
책임 주체 부재무상 제공이므로 패치 의무·SLA 없음
업데이트 부담버전 상향 시 호환성 문제로 방치되기 쉬움

Ⅲ. 나. SBOM 기반 오픈소스 소프트웨어 관리 방안​

1. SBOM의 구성 요소 (NTIA 최소 요소)​

구성 요소내용
공급자명(Supplier Name)구성요소 제공자
구성요소명(Component Name)라이브러리·패키지 이름
버전(Version)정확한 버전 정보 — 취약점 매칭의 핵심
고유 식별자CPE·PURL(Package URL) 등 표준 식별자
의존 관계(Dependency Relationship)구성요소 간 계층 관계(직접·전이)
SBOM 작성자·작성 시각생성 주체·타임스탬프
(확장)라이선스, 해시(무결성), 출처(Provenance)
   [SBOM 표준 형식]
   ┌──────────────┬────────────────────────────────────────┐
   │ **SPDX**      │ Linux Foundation, **ISO/IEC 5962 국제표준**│
   │              │ 라이선스 컴플라이언스에 강점            │
   │ **CycloneDX** │ OWASP, **보안 중심**·경량              │
   │              │ 취약점 정보(VEX) 연계 우수              │
   │ SWID Tag     │ ISO/IEC 19770-2, 자산 관리 중심         │
   └──────────────┴────────────────────────────────────────┘

2. SBOM 생애주기 관리 체계​

 ┌──── ① **생성(Generate)** ────┐
 │  빌드 시점에 **자동 생성**     │  ← CI/CD 파이프라인 통합
 │  (SCA 도구·빌드 플러그인)     │     ※ 사후 수작업은 부정확
 └───────────┬──────────────────┘
 ┌───────────▼── ② **저장·관리(Store)** ──┐
 │  SBOM 저장소 · 버전별 이력 관리          │
 │  배포 아티팩트와 **함께 서명·보관**       │
 └───────────┬─────────────────────────────┘
 ┌───────────▼── ③ **분석·검증(Analyze)** ─┐
 │  **취약점 DB(NVD·KEV) 자동 매칭**        │
 │  라이선스 정책 위반 검사                 │
 │  → 심각도 초과 시 **빌드·배포 차단**      │
 └───────────┬─────────────────────────────┘
 ┌───────────▼── ④ **모니터링(Monitor)** ──┐
 │  **신규 CVE 공개 시 영향 자산 즉시 식별**  │
 │  → 알림 → 패치 우선순위 결정              │
 └───────────┬─────────────────────────────┘
 ┌───────────▼── ⑤ **대응·공유(Respond)** ─┐
 │  패치·버전 상향(자동 PR) · **VEX 발행**   │
 │  고객·규제기관에 SBOM 제공                │
 └──────────────────────────────────────────┘

3. 단계별 관리 방안​

단계관리 방안
① 생성· CI 파이프라인에서 빌드 시 자동 생성(Syft·CycloneDX 플러그인)
· 전이 의존성까지 포함한 완전한 목록 확보
· 컨테이너 이미지·IaC까지 대상 확대
② 저장·관리· 중앙 SBOM 저장소(Dependency-Track 등) 운영
· 릴리스 버전별 이력 보관 — 과거 배포본의 구성요소 추적 가능
· 아티팩트 서명과 함께 보관(무결성·출처 증명)
③ 분석·검증· SCA 도구로 CVE 자동 매칭(Snyk·Trivy·Dependency-Check)
· CI 품질 게이트 — Critical/High 취약점 발견 시 빌드 실패
· 라이선스 정책 검사 — 금지 라이선스(GPL 등) 자동 차단
· VEX(Vulnerability Exploitability eXchange) — 취약점이 실제 악용 가능한지 판별하여 오탐 제거
④ 모니터링· 신규 CVE 공개 시 SBOM 조회로 영향 자산 즉시 식별(Log4Shell형 사고 대응 시간 대폭 단축)
· KEV(알려진 악용 취약점) 목록 우선 대응
· 유지보수 중단·EOL 라이브러리 탐지
⑤ 대응·공유· 취약 버전 자동 업데이트 PR 생성(Dependabot·Renovate)
· 패치 불가 시 보완 통제(WAF 룰·기능 비활성화)
· 고객·발주기관에 SBOM 제공(계약 요구사항 대응)

4. 거버넌스 및 정책​

구분관리 방안
도입 정책오픈소스 사용 승인 절차, 허용/금지 라이선스 목록, 사내 프라이빗 레지스트리(프록시)를 통한 반입 통제
의존성 관리버전 고정(Pinning)·Lock 파일 사용, 정기적 업데이트 주기 설정, 불필요 의존성 제거
공급망 검증패키지 서명·해시 검증, 신뢰 저장소만 사용, Typosquatting 탐지(설치 전 패키지 실존·평판 확인)
조직·책임오픈소스 관리 책임자(OSPO) 지정, 개발자 교육, 라이선스 법무 검토
협력사 관리납품 SW에 대한 SBOM 제출 계약 의무화, 제3자 구성요소 검증
성과 지표취약점 평균 조치 시간(MTTR), 미조치 Critical 건수, SBOM 커버리지

5. SBOM 도입 효과​

효과내용
신속한 사고 대응신규 취약점 발생 시 영향 범위를 수 주 → 수 분으로 단축
공급망 투명성자체 개발분과 외부 구성요소의 명확한 구분
라이선스 리스크 관리카피레프트 위반 사전 차단, M&A 실사 대응
규제 대응미국 행정명령·EU CRA·국내 가이드라인 준수
개발 품질불필요·중복 의존성 정리, 기술부채 가시화
신뢰 확보고객·발주기관에 대한 보안 수준 입증 수단

6. 도입 시 한계 및 고려사항​

한계대응 방향
SBOM 자체는 정보일 뿐생성만으로는 무의미 → 취약점 DB 연계·자동 대응 체계가 핵심
오탐(False Positive) 과다취약 버전이지만 실제로 해당 기능을 사용하지 않는 경우 → VEX로 악용 가능성 판별
정확성 확보동적 로딩·번들링된 코드 누락 가능 → 빌드 시점 생성 + 바이너리 분석 병행
관리 부담구성요소가 수천 개 → 심각도·KEV 기준 우선순위화, 자동화 필수
표준 상호운용성SPDX·CycloneDX 혼용 → 변환 도구 활용
조직 저항개발 속도 저하 우려 → 자동화로 마찰 최소화, 점진적 게이트 강화

Ⅳ. 결론​

현대 소프트웨어의 70~90%가 오픈소스로 구성된 상황에서, "무엇이 들어있는지 모르면 무엇을 지켜야 할지도 모른다" 는 것이 SBOM의 핵심 문제의식이다. Log4Shell 사태에서 많은 조직이 취약점 자체보다 영향 범위 파악에 더 큰 어려움을 겪었다는 사실이 이를 입증한다.

다만 유의할 점은 SBOM은 목록일 뿐 그 자체가 보안 대책은 아니라는 것이다. 실질적 효과는 ① CI/CD에서 자동 생성하여 정확성과 최신성을 확보하고, ② 취약점 DB·KEV와 연계하여 신규 CVE 발생 시 영향 자산을 즉시 식별하며, ③ VEX로 실제 악용 가능성을 판별하여 오탐을 걸러내고 우선순위를 결정할 때 비로소 발생한다.

아울러 SBOM은 기술 활동이자 거버넌스 활동이므로, 오픈소스 도입 승인 절차·프라이빗 레지스트리 통제·협력사 SBOM 제출 의무화가 병행되어야 한다. 미국 행정명령과 EU CRA로 SBOM이 규제 요건이 되고 있는 만큼, 국내 기업도 납품 요건 대응 차원을 넘어 공급망 보안의 기반 인프라로 선제 구축할 필요가 있다.

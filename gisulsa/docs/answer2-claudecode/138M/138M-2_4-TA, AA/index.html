클라우드 네이티브 전환 프로젝트의 TA와 AA

Ⅰ. 개요​

1. 아키텍트 역할 분화의 배경​

B기관의 대국민 포털·통합 업무시스템·ERP·통합인허가 시스템을 클라우드 네이티브(컨테이너·MSA·DevOps) 로 전환하는 사업은 인프라와 애플리케이션의 동시 재설계를 요구한다. 이 때문에 인프라 기술을 책임지는 TA와 응용 구조를 책임지는 AA의 역할 분담과 협업이 사업 성패를 좌우한다.

2. EA 관점의 위치​

        [EA - Enterprise Architecture]
   BA(업무) ─ DA(데이터) ─ **AA(응용)** ─ **TA(기술)** ─ SA(보안)
                              │              │
                       서비스·모듈 구조   인프라·플랫폼 구조
                              └──── 상호 제약·의존 ────┘

Ⅱ. 가. TA와 AA의 역할 비교​

1. 개념​

  • TA(Technical Architect): 시스템이 동작하는 기반 기술 환경(인프라·플랫폼·네트워크·보안) 을 설계하고 비기능 요구사항(성능·가용성·확장성·보안) 을 책임지는 아키텍트.
  • AA(Application Architect): 업무 요구사항을 소프트웨어 구조(서비스 분할·계층·연계·프레임워크) 로 설계하고 개발 표준과 애플리케이션 품질을 책임지는 아키텍트.

2. 범위·책임·산출물 비교​

비교 기준TA(Technical Architect)AA(Application Architect)
관심 영역어디서 어떻게 실행·운영되는가무엇을 어떻게 구조화·구현하는가
범위클라우드 인프라(IaaS/PaaS), 컨테이너 플랫폼(K8s), 네트워크·L4/L7, 스토리지, DBMS 인프라, 미들웨어, CI/CD 파이프라인, 모니터링, 보안 인프라서비스 분할(MSA 도메인), 애플리케이션 계층 구조, 프레임워크·개발표준, API 설계, 트랜잭션·연계, 공통 컴포넌트, 데이터 접근
책임·목표비기능 요구 충족 — 가용성(HA/DR), 성능·용량, 확장성(오토스케일), 보안·컴플라이언스, 인프라 비용 최적화기능 요구 충족 — 요구사항의 구조적 반영, 모듈 응집·결합도, 재사용성·유지보수성, 개발 생산성·품질
주요 의사결정클라우드 사업자·리전, 컨테이너/서버리스 채택, 네트워크 분리·보안구역, DB 이중화, 백업·DR 방식모놀리식 유지 vs MSA 분해 범위, 서비스 경계(DDD Bounded Context), 동기/비동기 통신, 프레임워크 선정
주요 산출물기술 아키텍처 정의서, 인프라 구성도(논리·물리), 네트워크·보안 구성도, 용량산정서, HA/DR 설계서, 도입장비·SW 명세, 성능 테스트 계획, 운영 이행계획응용 아키텍처 정의서, 서비스·컴포넌트 구성도, 표준 프레임워크·개발표준 가이드, API 명세(인터페이스 정의서), 공통 모듈 설계서, 패키지·계층 구조, 코드 품질 기준
성과지표가용률(SLA), 응답시간·TPS, 자원 사용률, 인프라 비용, 보안 취약점요구사항 반영률, 결함 밀도, 코드 복잡도·중복률, 재사용률, 배포 주기
주요 협업 대상인프라 운영팀, 보안담당, 클라우드 사업자, DA개발팀(PL), 업무담당자, DA, QA

3. 본 사업에서의 구체적 역할 예시​

시스템TA 관점AA 관점
대국민 포털트래픽 급증 대비 오토스케일·CDN·WAF, DDoS 대응프런트·백엔드 분리, 캐시 전략, 인증 연계(간편인증)
통합 업무시스템내부망 분리, SSO 인프라, 세션 클러스터링공통 컴포넌트·권한 모델, 업무 서비스 분해
ERP상용 패키지 배치 방식(VM vs 컨테이너), 성능·라이선스커스터마이징 최소화 원칙, 표준 인터페이스 연계
통합인허가대용량 파일·전자문서 스토리지, 무중단 배포워크플로 엔진, 민원 처리 상태 관리, 외부기관 연계 API

Ⅲ. 나. TA와 AA 협업의 중요성 및 협업 방안​

1. 협업의 중요성​

관점협업 부재 시 발생 문제
아키텍처 정합성인프라는 컨테이너·오토스케일인데 애플리케이션이 상태(Session)를 로컬 보관 → 확장 불가
비기능 요구 달성성능 목표는 TA가 책임지나 실제 병목은 애플리케이션 쿼리·동기 호출 구조에서 발생
비용·일정용량 산정이 응용 구조(서비스 수·트래픽 패턴)와 어긋나 과소·과대 투자 발생
장애 대응원인이 인프라인지 응용인지 규명 지연 → 책임 공방, 복구 지연
클라우드 네이티브 특성MSA·컨테이너는 인프라와 응용 설계가 본질적으로 결합(12-Factor App) → 분리 설계 불가능
전환 리스크레거시 4개 시스템의 전환 순서·연계 방식 결정에 양측 판단 모두 필요
   [상호 제약 관계 — 대표 사례]
   AA 결정: MSA 서비스 20개 분할  ──► TA 영향: K8s 노드·네트워크 정책·서비스메시 필요
   TA 결정: 컨테이너 오토스케일 적용 ──► AA 영향: **Stateless 설계·외부 세션 저장소 필수**
   TA 결정: 멀티 AZ 구성           ──► AA 영향: 분산 트랜잭션·지연시간 고려 설계
   AA 결정: 비동기 이벤트 연계      ──► TA 영향: 메시지 브로커(Kafka) 인프라·모니터링 구축

2. 협업 방안​

구분협업 방안기대효과
조직·체계아키텍처 그룹(Architecture Board) 구성, PM 직속 배치, DA·SA 포함 정례 협의체 운영신속한 의사결정, 책임 소재 명확화
의사결정 관리ADR(Architecture Decision Record) 로 결정사항·근거·대안 기록, 아키텍처 원칙 문서 공동 수립결정 추적성, 이견 재발 방지
공통 산출물통합 아키텍처 정의서(응용–기술 매핑표), 비기능 요구사항(NFR) 명세를 공동 소유요구사항 누락·상충 방지
초기 검증PoC·아키텍처 스파이크 공동 수행(컨테이너 배포·성능 시험), Walking Skeleton(엔드투엔드 최소 구현) 우선 구축기술 리스크 조기 해소
품질 활동합동 아키텍처 리뷰(ATAM 등 시나리오 기반 평가), 설계 검토 체크리스트 공동 운영품질속성 Trade-off 명시적 검증
개발·운영 연계DevOps 파이프라인 공동 설계(빌드·배포 표준, IaC), 관측성(로그·메트릭·트레이스) 표준 합의배포 자동화, 장애 원인 신속 규명
성능·용량성능 목표(SLO) 공동 설정 → 부하 테스트 합동 수행 → 병목 원인 공동 분석책임 공방 제거, 실질적 성능 확보
커뮤니케이션통합 형상관리·위키, 데일리 스크럼·주간 아키텍처 회의, 이슈 트래커 단일화정보 비대칭 해소
표준화공통 기술 표준(컨테이너 이미지·API 규격·인증 방식) 및 가이드라인 공동 배포4개 시스템 간 일관성 확보

Ⅳ. 결론​

클라우드 네이티브 환경에서 TA와 AA는 분업 관계가 아니라 하나의 아키텍처를 서로 다른 관점에서 책임지는 상호 의존 관계이다. 특히 컨테이너·MSA·DevOps는 응용 설계와 인프라 설계가 분리 불가능하므로, 역할 경계보다 공동 책임 영역(NFR·배포·관측성) 을 명확히 정의하는 것이 중요하다.

따라서 B기관 사업에서는 ① 착수 시점부터 아키텍처 그룹을 구성해 원칙과 NFR을 공동 확정하고, ② Walking Skeleton과 PoC로 응용–인프라 정합성을 조기 검증하며, ③ ADR과 통합 아키텍처 정의서로 결정의 추적성을 확보해야 한다. 나아가 사업 종료 후 운영 조직이 아키텍처를 승계할 수 있도록 문서·표준·자동화 자산을 이관하는 것까지 아키텍트의 책임 범위로 보아야 한다.

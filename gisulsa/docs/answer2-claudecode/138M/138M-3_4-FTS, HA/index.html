가용성 보장 — FTS(Fault Tolerant System)와 HA(High Availability)

Ⅰ. 개요​

1. 가용성의 정의​

가용성(Availability) 은 시스템이 요구된 기능을 정상 수행할 수 있는 시간의 비율이며, A = MTBF / (MTBF + MTTR) 로 산출한다. 가용성 향상은 고장 간 평균시간(MTBF) 증대 또는 평균 복구시간(MTTR) 단축을 통해 달성된다.

2. 가용성 등급​

등급가용률연간 허용 다운타임대표 구현
2 Nines99%약 3.65일단일 서버
3 Nines99.9%약 8.76시간백업·수동 복구
4 Nines99.99%약 52.6분HA 클러스터
5 Nines99.999%약 5.26분이중화 + 자동 절체
6 Nines99.9999%약 31.5초FTS(무정지 시스템)

Ⅱ. 가. FTS(Fault Tolerant System) 구현 방법​

1. 개념​

FTS는 구성요소에 장애가 발생하더라도 서비스 중단 없이(Non-Stop) 정상 동작을 지속하도록 설계된 시스템이다. 장애를 감지 후 복구하는 것이 아니라, 장애가 발생해도 결함이 외부로 드러나지 않도록 은폐(Fault Masking) 하는 것이 핵심이다.

2. 구현 방법​

   [Lockstep(동기 실행) 방식]                [TMR — 삼중화 다수결]
   입력 ─┬─► CPU-A ─┐                        입력 ─┬─► 모듈1 ─┐
         └─► CPU-B ─┴─► 비교기 → 출력              ├─► 모듈2 ─┼─► **투표기(Voter)** → 출력
              (불일치 시 오류 검출·격리)            └─► 모듈3 ─┘   (2/3 다수결로 오류 은폐)
구분구현 방법내용
하드웨어 중복다중화(Redundancy)CPU·메모리·전원·팬·NIC·디스크의 이중·삼중화, 핫스왑(Hot Swap) 부품 교체
TMR / NMR동일 모듈 3개(N개) 병렬 수행 후 다수결 투표(Voting) 로 정상 결과 채택
Lockstep두 프로세서가 동일 명령을 클럭 단위로 동시 실행, 결과 비교로 즉시 오류 검출
정보 중복ECC·CRC메모리 오류정정부호(ECC), 패리티, 체크섬으로 데이터 오류 자동 정정
RAID디스크 장애 시 패리티로 데이터 복원(RAID 1/5/6/10)
시간 중복재실행(Retry)일시적 오류(Transient Fault)에 대한 재수행·재전송
소프트웨어N-Version Programming동일 명세를 서로 다른 팀·언어로 독립 구현 후 결과 비교(설계 오류 대응)
Recovery Block주 모듈 수행 후 수용성 검사(Acceptance Test) 실패 시 대체 모듈 수행
체크포인트·롤백주기적 상태 저장 후 오류 시 복귀
제어Watchdog Timer정해진 시간 내 응답 없으면 오류로 판단·재기동
무결점 전원·냉각UPS·이중 전원 공급, 이중 냉각계통
  • 적용 분야: 항공·우주(비행 제어), 원자력·발전 제어, 철도 신호, 금융 기간계(무정지 거래), 의료기기 등 인명·자산 손실이 치명적인 영역

Ⅲ. 나. HA(High Availability) 구현 방법​

1. 개념​

HA는 장애 발생 시 짧은 시간 내 대체 시스템으로 전환(Failover) 하여 서비스 중단을 최소화하는 구성이다. 완전 무중단이 아니라 "허용 가능한 수준의 짧은 중단" 을 전제로 한다.

2. 구현 방법​

                    [클라이언트]
                          │  (VIP / DNS / L4)
                 ┌────────▼────────┐
                 │  로드밸런서(L4/L7) │
                 └───┬─────────┬────┘
              [Active]        [Standby / Active]
                 │  ◄── Heartbeat(상태 감시) ──►  │
                 └──── 공유 스토리지 / 데이터 복제 ────┘
                 Quorum(과반 합의) → **Split-Brain 방지** (Fencing/STONITH)
구분구현 방법내용
클러스터 구성Active-Standby대기 노드는 평시 유휴, 장애 시 승격(Hot/Warm/Cold Standby)
Active-Active모든 노드가 서비스 수행 → 부하 분산 + 가용성 동시 확보(자원 효율 우수)
Mutual Takeover서로 다른 업무를 수행하다 장애 시 상호 인수
장애 감지Heartbeat노드 간 주기적 생존 신호 교환, 다중 경로 구성
Watchdog·헬스체크프로세스·서비스 수준 상태 점검(L7 헬스체크)
절체(Failover)자동 절체VIP 이동, DNS 전환, 클러스터 매니저(Pacemaker·Patroni)
Fencing/STONITH고장 노드를 강제 차단하여 Split-Brain(양쪽 모두 Active) 방지
쿼럼(Quorum)과반수 합의로 리더 선출(홀수 노드 구성)
데이터 보호공유 스토리지SAN·NAS 공유, 클러스터 파일시스템
데이터 복제동기(RPO≈0, 지연↑) / 비동기(지연↓, 데이터 유실 가능) 복제, DB 스트리밍 복제
백업·PITR논리 오류·랜섬웨어 대응(이중화로는 방어 불가)
네트워크이중화회선·스위치·NIC 본딩(Bonding), 다중 경로
재해복구DR 센터Mirror(즉시) / Hot(수시간) / Warm(수일) / Cold 사이트, 다중 AZ·리전
애플리케이션무상태(Stateless) 설계세션 외부화(Redis), 컨테이너 오케스트레이션 자동 재기동·오토스케일
회복 패턴Circuit Breaker·Retry·Bulkhead·Graceful Degradation
  • 적용 분야: 기업 기간계·포털·전자상거래·공공 대민 서비스 등 대부분의 상용 시스템

Ⅳ. 다. FTS와 HA 비교​

비교 기준FTS(Fault Tolerant System)HA(High Availability)
목표무중단(Non-Stop) 서비스중단 시간 최소화
장애 대응 방식장애 은폐(Fault Masking) — 오류가 표면화되지 않음장애 감지 후 절체(Failover)
다운타임0에 근접(수초 이하, 6 Nines)수초수분(45 Nines)
RTO / RPORTO ≈ 0, RPO = 0RTO 수십 초수 분, RPO 0수 분
구현 계층주로 하드웨어·펌웨어 수준(전용 장비)주로 소프트웨어·아키텍처 수준(범용 장비)
중복 방식동시 병렬 수행(Lockstep·TMR)대기 또는 부하 분산(Standby/Active)
상태 전환전환 개념 없음(계속 수행 중)명시적 절체 절차 존재
비용매우 높음(전용 HW, 자원 2~3배)상대적으로 낮음(범용 HW·OSS 활용)
확장성낮음(전용 구조에 종속)높음(노드 추가로 Scale-out)
유연성·범용성낮음(특정 벤더·플랫폼)높음(클라우드·컨테이너 친화)
대응 장애 유형하드웨어 오류·일시적 결함에 강함노드·프로세스·사이트 장애 대응
공통 한계소프트웨어 버그·논리 오류·인재(人災)는 중복만으로 방어 불가 → 백업·N-Version·변경관리 필요(동일)
적용 분야항공·우주, 원전, 철도 신호, 금융 코어일반 엔터프라이즈·공공·웹 서비스
   [선택 기준 — 다운타임 1분의 비용]
   손실이 인명·대규모 자산 ─► **FTS**(비용 감수)
   손실이 매출·신뢰도 수준 ─► **HA**(비용 대비 효과 최적)
   ⇒ 실무에서는 **핵심 구간만 FTS급, 나머지는 HA**로 계층적 적용

Ⅴ. 결론​

FTS와 HA는 가용성이라는 동일한 목표에 대한 서로 다른 접근으로, FTS는 "장애가 있어도 멈추지 않는" 무결점 지향이고 HA는 "빨리 되살리는" 복원 지향이다. 전자는 비용이 매우 크므로, 실무에서는 업무 중요도별 RTO/RPO를 정의하고 이에 맞춰 차등 적용하는 것이 합리적이다.

또한 두 방식 모두 소프트웨어 결함·설정 오류·논리적 데이터 손상은 방어하지 못한다는 공통 한계가 있으므로, ① 백업·PITR과 DR 훈련의 정례화, ② 변경관리·배포 자동화를 통한 인적 오류 축소, ③ 카오스 엔지니어링 등 장애 주입 시험으로 절체 절차의 실효성 검증이 반드시 병행되어야 한다. 궁극적으로 가용성은 특정 장비가 아니라 아키텍처·프로세스·조직 역량의 총합으로 결정된다.

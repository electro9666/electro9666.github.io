  • 불명확한 요구사항으로 인한 소프트웨어 품질저하 — 기술부채·코드스멜·리팩토링

불명확한 요구사항으로 인한 소프트웨어 품질저하 — 기술부채·코드스멜·리팩토링

Ⅰ. 개요​

1. 문제의 근원​

소프트웨어 결함의 상당 부분은 코딩 단계가 아니라 요구사항 단계에서 유입된다. 요구사항이 모호하면 개발자는 추측(Assumption)에 기반한 임시 구현을 선택하게 되고, 이는 곧 기술부채로 누적되어 코드에 코드스멜로 표출되며, 이를 해소하는 유일한 수단이 리팩토링이다.

2. 인과 구조​

 [요구사항 불명확]
   · 모호·중의적 표현("빠르게", "적절히")
   · 비기능 요구 누락, 예외·경계 미정의
   · 잦은 변경, 이해관계자 간 상충
            │
            ▼  추측 기반 임시 구현 / 하드코딩 / 분기 누적
 [기술부채 누적] ──표출──► [코드스멜] ──진단──► [리팩토링]
       ▲                                          │
       └──────── 부채 상환(이자 감소) ◄────────────┘
       (미상환 시: 변경비용 증가 → 결함 증가 → 개발 지연 → 부채 재생산)

Ⅱ. 가. 기술부채(Technical Debt)​

1. 개념​

기술부채란 단기 납기·불확실성 때문에 최선이 아닌 설계·구현을 선택한 결과 향후 추가로 지불해야 하는 비용을 금융 부채에 비유한 개념(Ward Cunningham)이다. 원금(개선에 필요한 작업량)과 이자(부채 존속으로 매 변경마다 추가되는 비용)로 구성된다.

2. 유형 — Martin Fowler의 기술부채 사분면​

구분신중함(Prudent)무모함(Reckless)
의도적(Deliberate)"출시 우선, 이후 리팩토링" (관리 가능)"설계할 시간 없다"
우발적(Inadvertent)"이제 더 좋은 설계를 알게 됨"(학습형)"계층 분리가 뭔가?"

3. 요구사항 불명확에서 비롯되는 기술부채​

부채 유형요구사항 불명확과의 연관
요구사항 부채요구사항 문서·추적표(RTM) 미비 → 변경 영향분석 불가
설계·아키텍처 부채확정되지 않은 요구로 경계·책임 분리 실패, 순환 의존
코드 부채예외 케이스를 조건문으로 임기응변 처리 → 분기 폭증
테스트 부채인수기준(AC) 부재 → 테스트 작성 불가, 커버리지 미달
문서 부채구현이 사실상의 명세가 되어 지식이 개인에 종속
데이터 부채용도 미확정 컬럼·중복 스키마, 표준 미준수

4. 영향 및 관리​

  • 영향: 변경 리드타임 증가, 결함 밀도 상승, 신규 인력 온보딩 지연, 개발자 사기 저하
  • 관리 방안: 부채를 백로그에 등록·가시화하고 SQALE·기술부채 비율(TD Ratio)로 정량 측정, 스프린트 용량의 일정 비율(예: 10~20%)을 상환에 배정, Definition of Done에 품질 기준 포함

Ⅲ. 나. 코드스멜(Code Smell)​

1. 개념​

코드스멜이란 동작에는 문제가 없으나 설계상 문제를 암시하는 코드의 징후로, 결함 자체가 아니라 리팩토링이 필요함을 알리는 진단 신호이다.

2. 주요 코드스멜 — 요구사항 불명확과의 연관​

분류코드스멜요구사항 불명확에 기인하는 양상
비대(Bloater)Long Method, Large Class, Long Parameter List, Primitive Obsession요구가 추가될 때마다 기존 함수에 분기·인자 누적
객체지향 오용Switch Statements, Refused Bequest, Temporary Field미확정 유형을 switch/if로 나열, 조건부 사용 필드 방치
변경 방해Divergent Change(한 모듈이 여러 이유로 변경), Shotgun Surgery(한 변경이 여러 모듈에 파급)책임 경계가 요구사항과 불일치
불필요Duplicate Code, Dead Code, Speculative Generality"혹시 필요할 것"이라는 추측 기반 확장
결합(Coupler)Feature Envy, Inappropriate Intimacy, Message Chains데이터 소유 주체가 불명확해 타 객체 내부 참조
기타Magic Number, Comments(설명 대체), God Object규칙·임계값이 문서화되지 않아 코드에 하드코딩

3. 탐지 방법​

정적분석 도구(SonarQube, PMD)로 자동 탐지 + 메트릭 기반 판별 — 순환복잡도 V(G), 응집도(LCOM)·결합도(CBO), 중복률, 메서드 길이 + 코드리뷰의 정성 판단

Ⅳ. 다. 리팩토링(Refactoring)​

1. 개념 및 원칙​

리팩토링이란 외부 동작(기능)을 변경하지 않으면서 내부 구조를 개선하여 가독성과 유지보수성을 높이는 활동이다. 기능 추가·성능 개선·버그 수정과는 명확히 구분되며, 반드시 테스트로 동작 동일성을 보장한 상태에서 소규모·점진적으로 수행해야 한다.

2. 절차​

① 코드스멜 식별(정적분석 + 리뷰)
        ↓
② 회귀 테스트 확보 (없으면 먼저 작성 ← 필수 전제)
        ↓
③ 작은 단위 변경 적용 (한 번에 하나의 기법)
        ↓
④ 테스트 통과 확인 → 실패 시 즉시 되돌림
        ↓
⑤ 커밋(기능 변경과 분리) → ③ 반복
        ↓
⑥ 메트릭 재측정으로 개선 효과 검증

3. 주요 기법과 대응 코드스멜​

코드스멜리팩토링 기법
Long MethodExtract Method, Replace Temp with Query, Decompose Conditional
Large Class / God ObjectExtract Class, Extract Interface, Move Method·Field
Switch StatementsReplace Conditional with Polymorphism, Strategy 패턴 도입
Duplicate CodeExtract Method, Pull Up Method, Form Template Method
Long Parameter ListIntroduce Parameter Object, Preserve Whole Object
Magic NumberReplace Magic Number with Symbolic Constant
Feature EnvyMove Method, Extract Method 후 이동
Shotgun SurgeryMove Method·Field로 관련 책임 응집
Primitive ObsessionReplace Data Value with Object, Introduce Value Object

4. 요구사항 불명확 문제의 근본 대응​

리팩토링은 증상 치료이므로, 재발 방지를 위해 요구사항 단계의 개선이 병행되어야 한다.

단계대응 방안
요구사항 도출이해관계자 워크숍, 프로토타이핑, 사용자 스토리 + INVEST 원칙
명세화측정 가능한 인수기준(AC) 작성, 비기능 요구(성능·보안) 정량화, 예외·경계 조건 명시, 모호 표현 금지 규칙
검증요구사항 리뷰·워크스루, 추적성 매트릭스(RTM), ATDD/BDD로 요구사항을 실행 가능한 테스트로 변환
변경관리변경통제위원회(CCB), 변경 영향분석, 베이스라인 형상관리
개발 프로세스코드리뷰 의무화, CI 품질 게이트(복잡도·중복률·커버리지), 페어 프로그래밍

Ⅴ. 결론​

요구사항 불명확은 기술부채 → 코드스멜 → 유지보수 비용 증가로 이어지는 품질저하의 근원이며, 리팩토링은 이를 상환하는 필수 활동이다. 그러나 리팩토링은 테스트 자산이 확보된 상태에서만 안전하고, 요구사항 관리가 개선되지 않으면 부채는 반복 재생산된다. 따라서 실무에서는 ① 측정 가능한 인수기준으로 요구사항을 명세화하고, ② 정적분석과 코드리뷰로 코드스멜을 조기 탐지하며, ③ 기술부채를 백로그로 가시화하여 스프린트 용량의 일정 비율을 지속 상환하는 세 축을 함께 운영해야 한다. 결국 품질은 사후 검사로 얻는 것이 아니라 요구사항 단계부터 내재화(Build Quality In) 해야 확보된다.

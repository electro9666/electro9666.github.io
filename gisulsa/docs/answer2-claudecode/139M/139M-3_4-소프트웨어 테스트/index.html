  • 소프트웨어 테스트 — 7대 원리, 화이트박스·블랙박스 비교, 테스트 케이스 설계

소프트웨어 테스트 — 7대 원리, 화이트박스·블랙박스 비교, 테스트 케이스 설계

Ⅰ. 개요​

소프트웨어 테스트는 결함을 발견하여 제품 품질에 대한 정보를 제공하는 활동으로, "결함이 없음"을 증명하는 것이 아니라 결함의 존재를 드러내는 것이 목적이다. 무한한 입력 조합을 모두 검증할 수 없으므로, 테스트의 핵심 역량은 제한된 자원으로 결함 발견 확률을 극대화하는 테스트 케이스 설계 기법에 있다.

Ⅱ. 가. 소프트웨어 테스트의 7대 원리​

#원리내용실무적 시사점
①결함 존재의 입증 (Testing shows presence of defects)테스트는 결함의 존재를 밝힐 뿐, 결함이 없음을 증명할 수 없다테스트 통과 = 무결함이 아님
②완벽한 테스트는 불가능 (Exhaustive testing is impossible)모든 입력·경로 조합 검증은 현실적으로 불가위험 기반(Risk-based) 우선순위 필요
③조기 테스트 (Early testing / Shift-Left)개발 초기부터 테스트를 시작할수록 비용 절감요구사항 리뷰, 정적 테스트, TDD
④결함 집중 (Defect clustering)소수 모듈에 결함이 집중(파레토 법칙)결함 이력 기반 집중 테스트
⑤살충제 패러독스 (Pesticide paradox)동일 테스트 반복 시 새로운 결함 발견 불가테스트 케이스 정기 개선·다양화
⑥정황 의존성 (Testing is context dependent)시스템 특성에 따라 테스트 방식이 달라짐금융·의료·게임의 테스트 전략 상이
⑦오류 부재의 궤변 (Absence-of-errors fallacy)결함이 없어도 사용자 요구에 맞지 않으면 무의미검증(Verification) + 확인(Validation) 병행
결함 유입 시점과 수정 비용 (조기 테스트의 근거)
요구사항 1× → 설계 5× → 구현 10× → 테스트 20× → 운영 100×

Ⅲ. 나. 화이트박스 테스트와 블랙박스 테스트​

1. 개념​

  • 화이트박스 테스트(구조 기반): 프로그램 내부 논리·제어 흐름을 알고 소스코드 구조를 근거로 테스트 케이스를 설계 — "어떻게 동작하는가"를 검증
  • 블랙박스 테스트(명세 기반): 내부 구조를 모른 채 입력과 출력의 명세만으로 테스트 케이스를 설계 — "무엇을 해야 하는가"를 검증
 [화이트박스]                       [블랙박스]
  소스코드 → CFG 분석            요구사항·명세 → 입출력 관계
  경로·조건 커버리지               동등분할·경계값
  단위/통합 테스트 중심            시스템/인수 테스트 중심

2. 기법 비교​

비교 기준화이트박스 테스트블랙박스 테스트
기준소스코드·내부 구조요구사항 명세
목적논리 오류·미실행 경로 검출기능 누락·요구 불일치 검출
수행 주체개발자테스터·QA·사용자
테스트 단계단위·통합 테스트시스템·인수 테스트
커버리지 척도문장·분기·조건·경로 커버리지(정량화 가능)요구사항 커버리지
주요 기법문장(Statement)·분기(Branch)·조건(Condition)·MC/DC·기본경로(Basis Path, V(G))·루프 테스트·데이터흐름 테스트동등 분할(EP)·경계값 분석(BVA)·원인-결과 그래프·결정 테이블·상태 전이·페어와이즈(직교배열)·오류 추정
장점내부 결함·불필요 코드 발견, 커버리지 정량 관리사용자 관점 검증, 대규모 시스템 적용 용이
단점코드 지식 필요, 누락된 기능은 발견 불가내부 논리 오류·미사용 코드 미검출
관계상호보완 — 구조 커버리지 + 명세 커버리지를 함께 확보해야 완결

회색상자(Grey-box) 테스트: 내부 구조를 부분적으로 아는 상태에서 수행하며, DB·API 연동 검증에 효과적이다.

Ⅳ. 다. 학점 처리 모듈의 테스트 케이스 설계​

1. 명세 분석​

입력 : Score (정수형, 유효범위 0 ~ 100)
출력 : 90 ≤ S ≤ 100 → "A"    80 ≤ S < 90 → "B"
       70 ≤ S <  80 → "C"    60 ≤ S < 70 → "D"
              S < 60 → "F"    범위 외      → "ERROR"

2. 동등 분할(Equivalence Partitioning)​

입력 도메인을 동일한 처리 결과를 갖는 그룹으로 분할하고, 각 그룹에서 대표값 1개를 선정한다.

분할 ID구분입력 범위대표 입력값기대 출력
EP-1비유효Score < 0−10ERROR
EP-2유효0 ≤ Score ≤ 5935F
EP-3유효60 ≤ Score ≤ 6965D
EP-4유효70 ≤ Score ≤ 7975C
EP-5유효80 ≤ Score ≤ 8985B
EP-6유효90 ≤ Score ≤ 10095A
EP-7비유효Score > 100150ERROR
EP-8비유효(형식)정수가 아닌 입력"A", 85.5, nullERROR

→ 동등 분할 테스트 케이스 8개 (유효 분할 5개 + 비유효 분할 3개)

3. 경계값 분석(Boundary Value Analysis)​

결함은 경계에서 집중 발생하므로, 각 분할의 경계값과 그 인접값(경계−1, 경계, 경계+1) 을 선정한다.

TC ID입력값기대 출력검증 목적(경계)

BVA-020F유효범위 최소값
BVA-031F최소값 +1
BVA-0459FF/D 경계 직전
BVA-0560DD 시작 경계 (≥ 60 검증)
BVA-0669DD/C 경계 직전
BVA-0770CC 시작 경계
BVA-0879CC/B 경계 직전
BVA-0980BB 시작 경계
BVA-1089BB/A 경계 직전
BVA-1190AA 시작 경계 (≥ 90 검증)
BVA-1299A최대값 −1
BVA-13100A유효범위 최대값
BVA-14101ERROR유효범위 상한 +1

→ 경계값 분석 테스트 케이스 14개

4. 최종 통합 테스트 케이스 (권장 실행 세트)​

동등 분할로 분할 누락 없음을 보장하고, 경계값 분석으로 경계 결함을 검출하도록 통합한다.

5. 설계 시 검출 가능한 대표 결함​

결함 유형검출 테스트 케이스
비교 연산자 오류 (> ↔ ≥)TC-05(60), TC-11(90) — S > 90이면 90 입력 시 B 반환
범위 검증 누락TC-01(−1), TC-13(101)

Ⅴ. 결론​

테스트 7대 원리는 완벽한 테스트가 불가능하다는 전제 위에서 위험 기반으로 자원을 배분해야 한다는 실천적 지침이며, 화이트박스와 블랙박스 테스트는 구조 커버리지와 명세 커버리지를 각각 담당하는 상호보완 관계이다. 본 학점 처리 모듈의 경우 동등 분할로 처리 분기의 누락 없는 대표성을 확보하고, 경계값 분석으로 ≥/> 혼용과 Off-by-One 등 실제 빈발 결함을 집중 검출하는 15개 테스트 케이스 세트가 효율적이다. 실무에서는 이를 자동화 테스트로 구현하여 CI에 편입하고, 살충제 패러독스를 고려해 결함 이력에 따라 테스트 케이스를 지속적으로 보강해야 한다.

소프트웨어 요구공학

문제​

5.소프트웨어 요구공학(Requirement Engineering)에 대하여 설명하시오.
가.요구공학 정의 및 필요성
나.요구공학 절차
다.요구사항 명세서

Ⅰ. 개요​

1. 배경​

소프트웨어 프로젝트 실패 원인 분석에서 요구사항 관련 문제가 지속적으로 1위를 차지한다. 요구사항 결함은 후행 단계로 갈수록 수정 비용이 기하급수적으로 증가한다.

   [**결함 수정 비용의 증폭** — Boehm의 법칙]

   요구  설계   구현    시험     운영
    1×    5×    10×     50×    **100~200×**
    │                              │
    └──────── 조기 발견의 가치 ─────┘

   ⇒ 요구공학은 **가장 저렴한 단계에서 결함을 제거**하는 활동
요구사항 실패의 대표 양상결과
요구사항 누락·불완전재작업, 일정 지연
모호한 표현발주자·개발자 해석 차이 → 인수 거부
잦은 변경·범위 증식(Scope Creep)비용 초과, 품질 저하
이해관계자 미참여완성 후 "원하던 게 아니다"
추적성 부재변경 영향도 파악 불가, 검증 누락

Ⅱ. 가. 요구공학의 정의 및 필요성​

1. 정의​

요구공학(Requirements Engineering) 이란 이해관계자의 요구를 체계적으로 도출·분석·명세·검증하고, 개발 전 생애주기에 걸쳐 변경을 관리하는 공학적 접근 방법이다.

관점내용
목적"올바른 시스템을 만들기 위해(Build the Right System)" — 검증(Validation)의 영역
※ 시험은 "시스템을 올바르게 만드는가(Build the System Right)"
범위요구 도출 → 분석 → 명세 → 확인·검증 → 변경 관리(전 생애주기)
산출물요구사항 명세서(SRS), 요구사항 추적표(RTM), 변경 이력
표준ISO/IEC/IEEE 29148(요구공학 표준), IEEE 830(SRS), CMMI REQM/RD, SW사업 요구사항 상세화 지침

2. 요구사항의 유형​

 ┌──────────── **요구사항의 분류** ────────────┐
 │                                             │
 │  **① 기능 요구사항**(Functional)             │
 │      시스템이 **무엇을 해야 하는가**         │
 │      예) 사용자는 민원을 온라인 신청할 수 있다│
 │                                             │
 │  **② 비기능 요구사항**(Non-Functional) ★     │
 │      **얼마나 잘** 해야 하는가 — 품질 속성   │
 │      성능·가용성·보안·사용성·이식성·확장성   │
 │      예) 조회 응답시간 3초 이내, 가용성 99.9%│
 │      ※ **프로젝트 실패의 주요 원인**         │
 │        (정량화되지 않아 검증 불가)           │
 │                                             │
 │  **③ 제약사항**(Constraints)                 │
 │      기술·법규·예산·일정·표준 준수           │
 │                                             │
 │  **④ 도메인 요구사항**                       │
 │      업무 영역 고유의 규칙(Business Rule)    │
 └─────────────────────────────────────────────┘
계층내용
비즈니스 요구사항조직의 목표·기대효과(왜 만드는가)
이해관계자 요구사항사용자·운영자의 요구(무엇을 원하는가)
시스템 요구사항구현 가능한 수준의 상세 요구(어떻게 구현할 것인가)

3. 필요성​

필요성내용
① 프로젝트 실패 예방요구사항 오류가 실패의 최대 원인 → 조기 제거로 비용 절감(1 : 100 법칙)
② 이해관계자 간 합의 기반 확보발주자·사용자·개발자의 공통 이해와 계약적 기준
③ 범위 통제(Scope Management)명확한 범위 정의로 범위 증식·과업 분쟁 방지
④ 검증 기준 제공인수 기준·테스트 케이스의 원천 — 요구사항 없이는 검증 불가
⑤ 변경 영향도 관리추적성(Traceability) 확보 → 변경 시 영향 범위 즉시 파악
⑥ 산정 근거 제공규모·공수·비용 산정(FP·기능점수)의 기초
⑦ 법·제도 준수공공 사업의 과업내용서·요구사항 상세화 의무, 감리 점검 대상
⑧ 품질 확보비기능 요구사항의 정량화를 통한 품질 목표 명시

Ⅲ. 나. 요구공학 절차​

1. 전체 프로세스​

   ┌──────────────────────────────────────────────────────────┐
   │                  **요구사항 개발**(Development)            │
   │                                                          │
   │  ① **도출**(Elicitation)                                  │
   │       이해관계자 식별 → 요구 수집                        │
   │            ▼                                             │
   │  ② **분석**(Analysis)                                     │
   │       분류·구조화·충돌 해결·**우선순위**·실현가능성       │
   │            ▼                                             │
   │  ③ **명세**(Specification)                                │
   │       **SRS 작성** — 문서화·모델링                        │
   │            ▼                                             │
   │  ④ **확인·검증**(Validation & Verification)               │
   │       리뷰·프로토타이핑·**이해관계자 승인**               │
   │            │                                             │
   └────────────┼─────────────────────────────────────────────┘
                ▼          ※ ①~④는 **반복(Iterative)** 수행
   ┌──────────────────────────────────────────────────────────┐
   │  ⑤ **요구사항 관리**(Management) — **전 생애주기 지속**    │
   │       **기준선(Baseline) 설정** → 변경 통제(CCB) →        │
   │       **추적성 관리(RTM)** → 상태 추적                     │
   └──────────────────────────────────────────────────────────┘

2. 단계별 상세​

① 요구사항 도출 (Elicitation)​

항목내용
목적이해관계자의 명시적·암묵적 요구를 발견
주요 활동이해관계자 식별, 현행 업무·시스템 분석(AS-IS), 요구 수집
기법인터뷰, 설문, 워크숍(JAD), 브레인스토밍, 관찰(Ethnography), 문서 분석, 프로토타이핑, 벤치마킹, 유스케이스·사용자 스토리
어려움· 이해관계자가 자신의 요구를 정확히 모름(암묵지)
· 부서 간 상충하는 요구
· 도메인 지식 격차
유의사항모든 이해관계자를 빠짐없이 식별(운영·보안·감사 담당 누락 빈번)

② 요구사항 분석 (Analysis)​

항목내용
목적수집된 요구를 정제·구조화하고 충돌을 해결
주요 활동분류(기능/비기능/제약), 중복·모호성 제거, 충돌 조정, 실현 가능성 분석, 우선순위 결정
기법모델링(UML 유스케이스·클래스·상태도, DFD, ERD), MoSCoW(Must/Should/Could/Won't), AHP·Kano 모델, 프로토타이핑
산출물분석 모델, 요구사항 목록, 우선순위 표
유의사항비기능 요구사항의 정량화 — "빨라야 한다" → "평균 응답 2초 이내, 피크 시 3초 이내"

③ 요구사항 명세 (Specification)​

항목내용
목적합의된 요구를 표준 형식으로 문서화
주요 활동SRS 작성, 요구사항 ID 부여, 모델 첨부, 용어사전 정의
기법자연어 명세(정형 템플릿 사용), 정형 명세(Z·VDM), 준정형(UML·의사결정표), 사용자 스토리 + 인수 조건(Acceptance Criteria)
산출물SRS(요구사항 명세서), 요구사항 목록, 데이터 사전

④ 요구사항 확인·검증 (Validation & Verification)​

항목내용
Validation(확인)"올바른 요구인가" — 이해관계자의 실제 니즈와 일치하는가
Verification(검증)"요구를 올바르게 기술했는가" — 명세 품질(완전성·일관성)
기법동료 검토·워크스루·인스펙션, 체크리스트, 프로토타입 시연, 모델 검증, 테스트 케이스 도출 가능성 확인
결과이해관계자 공식 승인 → 기준선(Baseline) 설정

⑤ 요구사항 관리 (Management)​

항목내용
목적승인된 요구사항의 변경을 통제하고 추적성 유지
주요 활동기준선 설정, 변경 요청(CR) → 영향분석 → CCB 승인 → 반영, 버전·이력 관리, 추적성 매트릭스(RTM) 유지, 상태 추적
추적성전방 추적(요구 → 설계 → 코드 → 테스트)
후방 추적(테스트 → 요구, 근거 확인)
양방향 추적성으로 누락·과잉 구현 검출
도구JIRA, DOORS, Redmine, Azure DevOps
유의사항변경을 막는 것이 아니라 통제된 변경을 가능하게 하는 것이 목적

Ⅳ. 다. 요구사항 명세서 (SRS)​

1. 개념 및 역할​

SRS(Software Requirements Specification) 는 개발할 시스템이 무엇을 해야 하는지를 이해관계자가 합의한 형태로 기술한 공식 문서이다.

역할내용
합의 문서발주자·수행자 간 계약적 기준(과업 범위의 근거)
설계 입력설계·구현의 출발점
검증 기준인수 시험·감리 점검의 기준
산정 근거규모·비용 산정, 일정 수립
변경 관리 기준선변경 영향도 판단의 기준선(Baseline)

2. SRS의 구성 (IEEE 830 / ISO/IEC/IEEE 29148 기준)​

   **1. 개요(Introduction)**
      1.1 목적          1.2 범위
      1.3 용어 정의     1.4 참조 문서    1.5 문서 구성

   **2. 전체 설명(Overall Description)**
      2.1 제품 관점(기존 시스템·외부 인터페이스 관계)
      2.2 제품 기능 요약
      2.3 **사용자 특성**(사용자 유형·숙련도)
      2.4 **제약 조건**(법규·표준·기술·정책)
      2.5 **가정 및 종속성**

   **3. 상세 요구사항(Specific Requirements)** ★ **핵심**
      3.1 **기능 요구사항** (기능별 상세)
      3.2 **외부 인터페이스 요구사항**
           사용자·하드웨어·소프트웨어·통신 인터페이스
      3.3 **비기능(품질) 요구사항**
           **성능 · 가용성 · 보안 · 신뢰성 · 사용성 ·
             유지보수성 · 이식성 · 확장성**
      3.4 **데이터 요구사항**(데이터 모델·보존·정합성)
      3.5 **제약사항 및 준수 요구**

   **4. 부록**
      **요구사항 추적 매트릭스(RTM)** · 용어사전 · 분석 모델 · 화면 시안

3. 개별 요구사항의 기술 항목​

항목내용예시
요구사항 ID고유 식별자(추적의 기준)SFR-001
요구사항 명간결한 제목온라인 민원 신청
유형기능/성능/보안/인터페이스 등기능 요구사항
정의·상세 설명검증 가능한 문장으로 기술사용자는 로그인 후 민원을 신청하고 접수번호를 발급받을 수 있어야 한다
우선순위Must / Should / CouldMust
관련 요구사항연관 IDSFR-002, SER-005
인수 기준검증 방법·판정 기준신청 완료 후 3초 이내 접수번호 표시
출처요구 제기 주체민원과 사용자 인터뷰

4. 좋은 요구사항 명세의 품질 특성 (ISO/IEC/IEEE 29148)​

특성내용나쁜 예 → 좋은 예
① 완전성(Complete)필요한 요구가 빠짐없이 기술예외·오류 처리 누락 → 정상·예외 흐름 모두 기술
② 일관성(Consistent)요구 간 상충 없음"모든 이력 영구 보관" vs "1년 후 파기" → 충돌 해소
③ 명확성(Unambiguous)한 가지로만 해석"적절히 빠르게" → "평균 2초 이내"
④ 검증 가능성(Verifiable)테스트로 확인 가능"사용하기 편해야 한다" → "신규 사용자가 교육 없이 5분 내 신청 완료"
⑤ 추적 가능성(Traceable)ID 부여, 출처·후속 산출물 연결ID 없음 → SFR-001 부여 및 RTM 등재
⑥ 실현 가능성(Feasible)기술·예산·일정 내 구현 가능비현실적 성능 요구 → 근거 기반 조정
⑦ 필요성(Necessary)실제 필요한 요구만 포함사용되지 않을 기능 → 제거(Gold Plating 방지)
⑧ 수정 용이성(Modifiable)구조화·중복 제거로 변경 용이동일 내용 중복 기술 → 참조 방식
⑨ 단일성(Singular)1 요구사항 = 1 기능"조회하고 출력하고 전송한다" → 3개로 분리
⑩ 구현 중립성What을 기술, How는 설계 영역"Oracle로 저장" → "데이터를 5년간 보존"

5. 공공 정보화 사업에서의 요구사항 명세​

항목내용
법·지침 근거SW사업 요구사항 상세화 지침, 「소프트웨어 진흥법」, 과업심의위원회 제도
요구사항 상세화RFP·과업내용서에 요구사항을 구체적으로 명시 → 모호한 과업으로 인한 분쟁 방지
요구사항 분류 코드SFR(기능), PER(성능), SER(보안), INR(인터페이스), DAR(데이터), TER(시험), QUR(품질), COR(제약), PMR(프로젝트관리), PSR(지원)
과업 변경 관리과업 변경 시 과업심의위원회 심의 → 대가 조정
감리 점검요구사항 정의의 충실성·추적성(RTM) 이 요구정의 단계 감리의 핵심 점검 항목

Ⅴ. 고려사항 및 최신 동향​

고려사항내용
① 비기능 요구사항의 정량화실패의 최대 원인 → 측정 가능한 수치와 측정 조건(부하·환경) 명시
② 이해관계자 누락 방지사용자뿐 아니라 운영·보안·감사·유지보수 담당 포함
③ 변경은 불가피하다는 전제변경 차단이 아닌 통제된 변경 절차(CCB·영향분석) 구축
④ 추적성 유지 비용RTM 수작업 유지 곤란 → 도구 기반 자동화
⑤ 애자일 환경에서의 요구공학상세 SRS 대신 제품 백로그·사용자 스토리 + 인수 조건
단, 비기능 요구·제약사항은 여전히 명세 필요(Definition of Done에 포함)
⑥ 요구사항 재사용유사 사업의 요구사항 템플릿·라이브러리화
⑦ AI 활용생성형 AI로 요구사항 초안 작성·모호성 검토·테스트 케이스 도출 지원
단, 최종 검증은 사람의 책임
⑧ 신기술 영역 요구AI 시스템은 정확도·공정성·설명가능성, 클라우드는 가용성·확장성·비용을 요구사항으로 명시

Ⅵ. 결론​

요구공학은 "시스템을 올바르게 만드는 것(How)"에 앞서 "올바른 시스템을 정의하는 것(What)" 을 담당하는 활동으로, 결함 수정 비용이 후행 단계로 갈수록 100배 이상 증폭된다는 점에서 소프트웨어 공학에서 투자 대비 효과가 가장 큰 영역이다.

절차적으로는 도출 → 분석 → 명세 → 확인·검증의 개발 활동과, 그 이후 전 생애주기에 걸친 요구사항 관리(변경 통제·추적성) 로 구성되며, 이 중 실무에서 가장 취약한 부분은 명세 이후의 관리 단계이다. 승인된 요구사항이 기준선으로 관리되지 않고 구두 합의로 변경되면, 결국 과업 범위 분쟁과 인수 거부로 귀결된다.

요구사항 명세서(SRS)의 품질을 좌우하는 결정적 요소는 검증 가능성이다. "사용하기 편해야 한다", "빨라야 한다"와 같은 문장은 테스트할 수 없으므로 요구사항이 아니다. 특히 비기능 요구사항의 정량화(응답시간·처리량·가용성·복구시간)와 인수 기준의 명시가 실패를 가르는 지점이며, 공공 사업에서는 SW사업 요구사항 상세화 지침에 따른 분류 코드 체계와 RTM 기반 추적성 확보가 감리·과업심의의 핵심 점검 대상이 된다.

끝으로, 애자일 방법론이 확산되면서 "문서를 줄인다"는 명분으로 요구공학 자체를 생략하는 오해가 있으나, 애자일은 요구사항의 형식(백로그·사용자 스토리) 과 시점(점진적 상세화) 을 바꾼 것이지 요구를 명확히 하고 합의하는 활동을 없앤 것이 아니다. 오히려 반복 주기가 짧을수록 인수 조건의 명확성과 우선순위 관리가 더 중요해진다는 점을 유념해야 한다.

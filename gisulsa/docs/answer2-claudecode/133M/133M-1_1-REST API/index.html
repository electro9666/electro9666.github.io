REST API

문제​

1.REST API(REpresentational State Transfer Application Programming Interface)에대하여 설명하시오.

Ⅰ. 개요​

REST API는 자원(Resource)을 URI로 식별하고 HTTP 메서드로 행위를 표현하며, 자원의 표현(Representation)을 교환하는 웹 기반 인터페이스 아키텍처 스타일이다. Roy Fielding이 2000년 박사학위 논문에서 웹의 성공 요인을 아키텍처 원칙으로 정리하며 제시하였다.

   [등장 배경]
   SOAP/RPC — WSDL·XML 규격 무거움, 학습·연동 비용 큼
        ▼
   웹/모바일 다채널 확산 → **경량·범용 연동** 요구
        ▼
   [**REST**] HTTP 표준을 그대로 활용 → **단순·확장·범용**

Ⅱ. REST의 6대 아키텍처 원칙(제약조건)​

원칙내용
① Client-ServerUI(클라이언트)와 데이터 저장(서버) 관심사 분리 → 독립 진화
② Stateless(무상태)요청에 필요한 정보를 모두 포함, 서버가 세션을 보관하지 않음 → 수평 확장 용이
③ Cacheable응답에 캐시 가능 여부 명시(Cache-Control, ETag) → 성능·확장성
④ Layered System프록시·게이트웨이·L4 등 계층 삽입 가능(클라이언트는 인지 불필요)
⑤ Uniform Interface(핵심)자원 식별(URI) · 표현을 통한 조작 · 자기서술 메시지 · HATEOAS
⑥ Code on Demand(선택)서버가 스크립트를 전달해 클라이언트 기능 확장(유일한 선택 제약)

Ⅲ. 구성 요소 및 설계 규칙​

   [REST의 3요소]
   **자원(Resource)**   ── 무엇을      → **URI**로 식별   예) /users/123
   **행위(Verb)**       ── 어떻게      → **HTTP Method**  예) GET/POST
   **표현(Representation)** ── 어떤 형태 → **JSON/XML**    예) {"id":123}
HTTP 메서드의미안전성멱등성
GET자원 조회OO
POST자원 생성·비멱등 처리XX
PUT자원 전체 교체XO
PATCH자원 부분 수정X설계에 따름
DELETE자원 삭제XO
설계 규칙권장지양
URI는 명사·복수형GET /orders/10/itemsGET /getOrderItems?id=10
행위는 메서드로DELETE /users/1GET /users/1/delete
상태코드 활용200/201/400/401/404/409/500모두 200 + 본문에 에러
계층 표현/users/1/orders/userOrders?u=1

Ⅳ. 성숙도 모델 및 장단점​

단계Richardson 성숙도 모델
Level 0단일 URI·POST만 사용(HTTP를 전송 터널로만 사용)
Level 1자원 개념 도입(URI 분리)
Level 2HTTP 메서드·상태코드 활용(현실의 대다수 API)
Level 3HATEOAS — 응답에 다음 전이 링크 포함(진정한 REST)
구분내용
장점HTTP 표준 활용으로 학습·연동 용이, 무상태 → 확장성, 캐시로 성능 확보, 플랫폼 독립
단점표준 규격 부재(설계 편차), 오버·언더페칭(GraphQL 대비), 트랜잭션·실시간 처리 취약, HATEOAS 구현 부담

Ⅴ. 결론​

REST API는 HTTP라는 검증된 표준 위에 자원 중심의 일관된 인터페이스를 제공함으로써, 개방형 API·MSA·모바일 백엔드의 사실상 표준(De facto) 으로 자리 잡았다.

실무에서는 Level 3(HATEOAS)까지 도달하기보다 Level 2를 충실히 지키는 것이 현실적이며, URI 명명 규칙·상태코드·버저닝(/v1)·인증(OAuth 2.0)·API 문서(OpenAPI) 를 조직 표준으로 정립하는 것이 품질을 좌우한다. 실시간·복잡 질의가 필요한 영역은 gRPC·GraphQL과 병행하는 하이브리드 전략이 바람직하다.

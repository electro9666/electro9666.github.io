생성형 AI 보안 가이드라인

문제​

2.국가사이버안보센터는 생성형AI의 보안위협과 안전한 활용을 위한 가이드라인(챗GPT등생성형 AI 활용 보안 가이드라인, 2023.6)을 발간하였다.이와 관련하여 다음을 설명하시오.
가.생성형AI의 개념 및 활용 서비스 사례
나.생성형AI의 보안 위협 종류별 주요 원인과 발생 가능한 보안위협
다.생성형AI 모델/서비스 개발 시 보안 고려사항과 보안위협 대응방안

Ⅰ. 개요​

1. 배경​

ChatGPT 등장 이후 생성형 AI가 업무 전반에 급속히 확산되었으나, 업무 자료의 외부 유출·환각에 의한 오판·프롬프트 공격 등 새로운 유형의 위협이 현실화되었다. 특히 공공기관은 국가 기밀·개인정보 취급이라는 특수성이 있어 별도의 활용 기준이 요구되었다.

   [실제 발생 사례가 촉발한 문제의식]
   · 임직원이 **소스코드·회의록을 프롬프트에 입력** → 외부 서버 전송·학습 활용
   · 대화 이력이 **타인에게 노출**된 서비스 장애
   · **환각 결과를 검증 없이 보고서에 반영**
   · **탈옥(Jailbreak)** 으로 악성코드·피싱메일 생성
        ▼
   국가사이버안보센터 **「챗GPT 등 생성형 AI 활용 보안 가이드라인」**(2023.6)
   + **국가 AI 활용 보안 지침**, **AI 기본법**, EU **AI Act**, **OWASP Top 10 for LLM**

Ⅱ. 가. 생성형 AI의 개념 및 활용 서비스 사례​

1. 개념​

생성형 AI(Generative AI) 는 대규모 데이터로 학습한 모델이 데이터의 분포와 패턴을 학습하여 텍스트·이미지·음성·코드 등 새로운 콘텐츠를 생성하는 인공지능이다.

구분판별형 AI(Discriminative)생성형 AI(Generative)
목적분류·예측(경계 학습)새로운 콘텐츠 생성(분포 학습)
출력레이블·확률값텍스트·이미지·코드 등 산출물
예시스팸 분류, 이상거래 탐지ChatGPT, 이미지 생성, 코드 생성
보안 관점오분류 위험입력 유출·환각·악용 생성 위험
기술 요소내용
Transformer·LLM자기주의 기반 대규모 언어모델, 다음 토큰 예측
확산모델(Diffusion)노이즈 제거 방식의 이미지·영상 생성
프롬프트 기반 상호작용자연어 지시로 과업 수행(In-context Learning)
RAG·플러그인·에이전트외부 지식 검색·도구 호출로 기능 확장(동시에 공격면 확대)

2. 활용 서비스 사례​

유형서비스·활용 사례

문서·업무 지원보고서 초안, 회의록 요약, 민원 답변 초안, 정책 자료 검색

Ⅲ. 나. 보안 위협 종류별 주요 원인과 발생 가능한 보안위협​

1. 위협 분류 체계​

 ┌────────── **생성형 AI 보안 위협의 4대 영역** ──────────┐
 │                                                        │
 │  **① 이용자(입력) 측면** — 정보 유출                    │
 │  **② 모델(출력) 측면**   — 환각·편향·유해 결과          │
 │  **③ 공격(악용) 측면**   — 프롬프트 공격·AI를 이용한 공격│
 │  **④ 서비스·공급망 측면** — 플랫폼 장애·플러그인·법적 위험│
 └────────────────────────────────────────────────────────┘

2. 위협 종류별 원인과 발생 가능 위협​

위협 종류주요 원인발생 가능한 보안위협
① 정보 유출
(가장 현실적 위협)		· 이용자가 업무자료·개인정보·소스코드를 프롬프트에 입력
· 입력 데이터가 서비스 사업자 서버에 저장·학습에 활용
· 보안 인식 부족, 섀도 AI(비인가 서비스 사용)		· 국가 기밀·영업비밀 외부 유출
· 개인정보 국외 이전(법 위반)
· 소스코드 유출 → 취약점 노출
· 대화 이력 노출·타인 열람
② 잘못된 정보 생성
(환각·부정확)		· LLM은 확률적 다음 토큰 예측 — 사실 검증 능력 없음
· 학습 데이터의 시점 한계(지식 컷오프)·오류 포함
· 그럴듯한 문장 생성 → 오류 식별 곤란		· 환각(Hallucination) — 허위 사실·존재하지 않는 법령·판례 인용
· 검증 없이 정책·보고서 반영 → 의사결정 오류
· 오정보 확산, 기관 신뢰 훼손
③ 편향·유해 콘텐츠· 학습 데이터에 사회적 편향·유해 표현 포함
· 필터링의 한계		· 차별적·혐오 표현 생성
· 공정성 침해, 민원·법적 분쟁
④ 프롬프트 공격· 모델이 명령과 데이터를 구분하지 못함(구조적 한계)
· 시스템 프롬프트의 취약한 설계
· RAG·플러그인으로 외부 콘텐츠 유입		· 프롬프트 인젝션 — 시스템 지시 무력화
· 간접 프롬프트 인젝션 — 웹페이지·문서에 악성 지시 삽입
· 탈옥(Jailbreak) — 안전장치 우회
· 시스템 프롬프트 유출
· 연계 시스템 권한 오용(과도한 에이전시)
⑤ AI를 악용한 공격
(공격 도구화)		· 생성 능력의 양면성
· 오픈소스 모델의 안전장치 제거 용이		· 정교한 피싱메일·스미싱 대량 생성(문법 오류 없는 한국어)
· 악성코드·랜섬웨어 코드 생성, 취약점 익스플로잇 작성
· 딥페이크·음성 합성 기반 사칭 사기
· 허위정보·여론 조작
⑥ 모델 자체 공격· 학습·추론 과정의 기술적 취약점· 데이터 포이즈닝 — 학습데이터 오염으로 백도어 삽입
· 모델 추출·탈취(Model Stealing)
· 멤버십 추론·학습데이터 추출 → 개인정보 노출
· 적대적 예제(Adversarial Example)
⑦ 서비스·공급망 위험· 외부 서비스 의존성
· 플러그인·오픈소스 모델·라이브러리 검증 미흡		· 서비스 중단·장애로 업무 마비
· 취약한 플러그인을 통한 침해
· 오염된 오픈소스 모델(악성 가중치 파일)
· 벤더 종속
⑧ 법·제도적 위험· 학습데이터 저작권 불명확
· 생성물의 권리 관계 미정립		· 저작권 침해 분쟁
· 개인정보보호법·국외 이전 규정 위반
· 생성물 표시 의무 위반
   [**프롬프트 인젝션**이 근본적 위협인 이유]

   전통 SW : **코드(명령)** 와 **데이터(입력)** 가 **구조적으로 분리** → 검증 가능
   **LLM**  : 시스템 프롬프트도, 사용자 입력도, 검색된 문서도 **모두 같은 텍스트**
        ▼
   "이전 지시를 무시하고 ~하라"는 **데이터가 명령으로 해석**될 수 있음
        ▼
   ⇒ **입력 검증만으로 완전 차단 불가** → **권한 최소화·출력 통제·인간 승인**으로
      **피해 범위를 제한하는 설계**가 필요

Ⅳ. 다. 개발 시 보안 고려사항과 보안위협 대응방안​

1. 생애주기별 보안 고려사항​

   ① **기획·설계**
        │  · **AI 활용 범위·금지 용도 정의**(무엇을 맡기지 않을 것인가)
        │  · **데이터 등급 분류** — 입력 금지 정보 지정(기밀·개인정보)
        │  · 배포 형태 결정 — 공개 API / 전용 인스턴스 / **온프레미스 sLLM**
        │  · **AI 영향평가·위험평가**, 인간 개입(HITL) 지점 설계
        ▼
   ② **데이터 수집·학습**
        │  · 학습데이터 **출처·저작권·적법성 검증**
        │  · **개인정보 가명·비식별 처리**, 민감정보 제외
        │  · **데이터 포이즈닝 방지** — 출처 검증·무결성 해시
        │  · 편향 진단·데이터 다양성 확보
        ▼
   ③ **모델 개발·학습**
        │  · 안전 정렬(**SFT·RLHF**), 유해 출력 억제 학습
        │  · **모델 가중치·체크포인트 접근통제·암호화**
        │  · 학습 인프라 격리, 모델 서명·무결성 검증
        ▼
   ④ **서비스 구현**  ★ 방어의 핵심 지점
        │  · **입력 필터링** — 프롬프트 인젝션 패턴·민감정보 탐지
        │  · **출력 필터링** — 유해·개인정보·기밀 포함 여부 검사
        │  · **시스템 프롬프트 보호**, 명령/데이터 구분 마킹
        │  · **최소 권한 원칙** — 모델·에이전트의 시스템 접근 권한 제한
        │  · **RAG 적용** — 근거 문서 기반 답변 + **출처 표시**로 환각 억제
        │  · API 인증·**Rate Limit**, 세션 격리
        ▼
   ⑤ **검증·테스트**
        │  · **레드팀 테스트**(탈옥·인젝션 시도), 취약점 진단
        │  · **환각률·편향 지표 측정**, 안전성 벤치마크
        │  · **OWASP Top 10 for LLM** 기반 점검
        ▼
   ⑥ **배포·운영**
        │  · **프롬프트·응답 로깅 및 모니터링**(단, 개인정보 보호 유의)
        │  · 이상 사용 탐지, **긴급 차단(킬 스위치)**
        │  · 모델·라이브러리 취약점 패치, **모델 드리프트 재평가**
        ▼
   ⑦ **폐기**
        │  · 모델·학습데이터 안전 파기, 이력 보존

2. 위협별 대응방안 (기술·관리·물리)​

위협기술적 대응관리적 대응
정보 유출· DLP 연동 — 프롬프트 전송 전 민감정보 탐지·차단
· 자동 마스킹·가명처리 후 전송
· 온프레미스 sLLM·전용 인스턴스 구축(가장 확실한 대응)
· 학습 활용 거부(Opt-out) 설정, 망분리 환경 적용		· 입력 금지 정보 명확화(기밀·개인정보·소스코드)
· 허용 서비스 목록화(섀도 AI 차단)
· 이용 신청·승인 절차, 보안서약

3. 공공기관 활용 시 특별 고려사항​

고려사항내용
① 업무 자료 입력 금지 원칙비공개 직무 정보·개인정보의 공개형 AI 입력 금지가 대원칙
② 망분리 환경 정합성업무망에서 외부 AI 접속 불가 → 내부망 전용 AI 또는 인터넷망 별도 이용
③ 등급별 차등 적용N2SF 등 정보 등급에 따라 이용 가능 서비스·형태 차등
④ 도입 형태 선택민감 업무는 온프레미스 sLLM / CSAP 인증 전용 인스턴스 우선 검토
⑤ 이용 통제 체계허용 서비스 지정, 계정·이용 승인, 접속 로그 관리
⑥ 결과물 책임AI 산출물의 최종 책임은 담당 공무원 — 검증 의무 명시
⑦ 제도 정합성AI 기본법(고영향 AI·생성물 표시), 개인정보보호법, 전자정부법 준수

Ⅴ. 결론​

생성형 AI의 보안 위협은 전통적 보안 위협과 근본적으로 다른 성격을 갖는다. 첫째, 최대 위협이 외부 공격이 아니라 이용자의 자발적 정보 입력이라는 점이다. 둘째, LLM은 명령과 데이터를 구조적으로 구분하지 못하므로 프롬프트 인젝션을 입력 검증만으로 완전히 차단할 수 없다는 점이다. 셋째, 환각은 결함이 아니라 확률적 생성 모델의 본질적 특성이므로 제거가 아닌 완화와 검증의 대상이라는 점이다.

따라서 대응 전략은 "위협을 원천 제거한다"가 아니라 "피해 범위를 설계로 제한한다" 는 방향이어야 한다. 구체적으로는 ① 데이터 등급에 따라 입력 가능 정보를 명확히 구분하고 DLP로 기술적으로 강제할 것, ② 민감 업무는 공개 서비스 대신 온프레미스 sLLM이나 전용 인스턴스로 전환할 것, ③ RAG와 출처 표시로 환각을 억제하되 최종 검증은 반드시 사람이 수행할 것, ④ 모델과 에이전트에 최소 권한만 부여하여 인젝션 성공 시에도 피해를 국한할 것이 핵심이다.

가장 중요한 것은 금지 일변도의 정책이 실효성을 갖지 못한다는 현실 인식이다. 사용을 전면 차단하면 섀도 AI가 통제 밖에서 확산되어 오히려 위험이 커진다. 따라서 안전한 이용 경로를 공식적으로 제공하고, 명확한 입력 금지 기준과 교육을 병행하며, 로그 기반 모니터링으로 실태를 파악하는 것이 현실적 해법이다. 생성형 AI 보안은 결국 기술적 통제, 명확한 이용 규정, 그리고 이용자의 보안 인식이라는 세 요소가 함께 작동할 때 확보된다.

하드웨어 규모산정 지침

문제​

1.정보시스템 하드웨어 규모산정 지침(TTAK.KO-10.0292/R3, 2023.12.06.개정)에대하여다음을 설명하시오.
가.규모산정의 개념 및 대상
나.규모산정 절차
다.규모산정 방식

Ⅰ. 개요​

1. 배경​

공공 정보화 사업에서 하드웨어 규모산정은 사업 예산과 서비스 품질을 동시에 결정하는 핵심 활동이다. 그러나 산정 근거가 불명확하여 과다 산정(예산 낭비) 또는 과소 산정(성능 미달·증설 비용) 이 반복되었고, 이를 표준화하기 위해 TTA 표준 TTAK.KO-10.0292가 제정되었다.

   [규모산정 실패의 양면]
   **과다 산정**                          **과소 산정**
   · 도입 비용 낭비                       · 응답지연·서비스 장애
   · 유휴 자원·전력·상면 비용 증가        · 긴급 증설 → 추가 예산·중단
   · 감사 지적(예산 부적정)               · 사업 실패·이용자 불만
        └──────────── 공통 원인 ─────────────┘
        **근거 없는 경험적 산정 · 요구사항 미확정 · 미래 증가율 미반영**
        ▼
   [**TTAK.KO-10.0292/R3**] 산정 절차·방식·보정계수의 **표준화**

2. R3 개정(2023.12.06.)의 주요 방향​

개정 방향내용
클라우드 환경 반영물리 서버 중심 → 가상화·클라우드(IaaS) 자원 산정 기준 보완
AI·빅데이터 반영GPU 등 가속기, 대용량 데이터 처리 워크로드 고려
산정 방식 정교화보정계수 현행화, 최신 성능 지표(tpmC, SPEC 등) 반영
활용성 제고산정 근거·검증 절차 명확화 → 감리·예산 심의 근거로 활용

Ⅱ. 가. 규모산정의 개념 및 대상​

1. 규모산정(Sizing)의 개념​

규모산정이란 정보시스템이 요구되는 업무량과 성능 목표를 충족할 수 있도록, 필요한 하드웨어 자원의 종류와 용량을 정량적으로 도출하는 활동이다.

관점내용
목적적정 규모(Right Sizing) 확보 — 성능 보장과 비용 효율의 균형
시점주로 정보화전략계획(ISP)·설계 단계, 예산 요구 및 제안요청서(RFP) 작성 시
성격예측 활동 → 가정과 근거의 명시가 필수
원칙① 요구사항 기반, ② 정량적 근거 제시, ③ 미래 증가 반영, ④ 검증 가능성
   [규모산정의 기본 논리]
   **업무량**(트랜잭션·사용자·데이터량)
        × **단위 처리 요구 자원**
        × **보정계수**(피크율·여유율·가용성·미래 증가)
        ÷ **목표 사용률**(예: CPU 70%)
        ▼
   **소요 자원량**(CPU 성능값·메모리·디스크·네트워크)

Ⅲ. 나. 규모산정 절차​

   ① **요구사항 분석**
        │  업무 범위·기능, **성능 요구사항**(응답시간·TPS·동시사용자)
        │  가용성 요구(RTO/RPO), 보안·규제 요건
        ▼
   ② **업무량(Workload) 산정**
        │  대상 사용자 수, 일 처리 건수, **피크 시간대 집중률**
        │  데이터 발생량·보존기간, 배치 처리량
        ▼
   ③ **산정 방식 선정**
        │  자료 가용성·시스템 특성에 따라
        │  **참조·정량·수학적 모델·시뮬레이션** 중 선택
        ▼
   ④ **자원별 규모 산정**
        │  서버 → 스토리지 → 네트워크 → 보안 → 백업 순
        │  **보정계수 적용**(여유율·미래 증가율·가용성)
        ▼
   ⑤ **보정 및 조정**
        │  가상화·클라우드 특성, 예산 제약, 기술 발전 반영
        ▼
   ⑥ **검증**
        │  **유사 사례 비교**, 벤치마크(BMT), 전문가 검토
        │  과다·과소 여부 점검
        ▼
   ⑦ **산정 결과 문서화**
        │  **산정 근거·가정·계산식**을 명시 → RFP·예산·감리 근거
        ▼
   ⑧ **사후 검증·조정**(구축 후)
        │  실제 사용률 측정 → 차기 산정에 **피드백**
단계핵심 산출물유의사항
① 요구사항 분석성능 요구사항 정의서성능 목표가 없으면 산정 불가 — 응답시간·TPS 확정 필수
② 업무량 산정업무량 산정서피크 기준 사용, 계절·이벤트 변동 고려
③ 방식 선정산정 방식 결정 근거자료가 부족하면 참조 방식, 정밀 요구 시 시뮬레이션
④ 자원별 산정자원별 산정 내역보정계수의 근거를 명시
⑥ 검증검증 결과서대규모·고위험은 BMT 권장
⑦ 문서화규모산정 결과 보고서재현 가능한 계산식 제시

Ⅳ. 다. 규모산정 방식​

1. 4가지 산정 방식​

방식개념적용 조건정확도비용·기간
① 참조 방식
(Reference)		유사 시스템 사례의 자원 구성을 참조하여 산정기획 초기, 자료 부족 시낮음매우 낮음
② 정량 방식
(Quantitative)		업무량 × 단위 자원 요구량 × 보정계수 계산식 적용업무량 파악 가능한 일반 사업중간낮음
③ 수학적(분석) 모델
(Analytic Model)		대기행렬 이론 등으로 응답시간·활용률 모델링성능 목표가 엄격, 이론적 검증 필요높음중간
④ 시뮬레이션
(Simulation)		실제 워크로드를 모의 실행·부하시험(BMT) 하여 측정대규모·고위험, 신기술 도입가장 높음높음

2. 방식 선정 기준​

   [선정 판단]
   자료 부족 · 초기 기획          → **참조 방식**
        ▼
   업무량 산출 가능 · 통상 사업   → **정량 방식**  ★ 공공 사업의 기본
        ▼
   응답시간 보장이 핵심           → **수학적 모델** 보완
        ▼
   대규모·고비용·신기술           → **시뮬레이션/BMT** 검증
   ⇒ 실무에서는 **정량 방식으로 산정 → 참조·BMT로 교차 검증**하는 병행이 일반적

3. 정량 방식의 산정 논리 (예: 서버 CPU)​

   **소요 성능(tpmC)** =
        [ 기준 업무량(피크 시 분당 트랜잭션 수) ]
        × [ 업무 부하 보정계수 ]      · 업무 복잡도
        × [ 데이터베이스 보정계수 ]   · 데이터량·조인 복잡도
        × [ 애플리케이션 보정계수 ]   · 프레임워크·언어 특성
        × [ 가용성 보정계수 ]         · 이중화 구성(노드 장애 시 인수)
        × [ 여유율(미래 증가) ]       · 통상 3~5년 증가율
        ÷ [ 목표 CPU 사용률 ]         · 통상 60~70%
자원산정 요소
CPU피크 트랜잭션 수, 보정계수, 목표 사용률, 이중화 구성
메모리OS + 미들웨어(WAS 힙) + DB 버퍼 캐시 + 세션당 메모리 × 동시사용자 + 여유
스토리지 용량원천 데이터량 × 보존기간 × 증가율 + 인덱스·임시·로그 + 백업·RAID 오버헤드 + 여유율
스토리지 성능피크 IOPS, 읽기/쓰기 비율, RAID 방식별 Write Penalty
네트워크동시사용자 × 세션당 트래픽 × 피크율 + 백업·복제 트래픽 + 여유(통상 사용률 50% 이하)
GPU(R3)모델 파라미터 규모, 학습 데이터량·에폭, 추론 QPS, GPU 메모리

4. 클라우드 환경에서의 산정 (R3 반영)​

구분온프레미스클라우드
산정 기준피크 기준 고정 용량평시 기준 + 오토스케일링
여유율크게 반영(증설 곤란)작게 반영(탄력적 확장)
비용 관점초기 구축비(CAPEX)월 이용료(OPEX)·3~5년 TCO
산정 결과물장비 사양·수량인스턴스 유형·수, 스토리지 GB, 트래픽량
유의사항과다 산정 위험온프레미스 관행대로 피크 고정 산정 시 비용 급증

Ⅴ. 결론​

정보시스템 하드웨어 규모산정 지침(TTAK.KO-10.0292/R3)은 경험과 관행에 의존하던 산정을 "요구사항 → 업무량 → 계산식 → 검증 → 문서화"라는 재현 가능한 절차로 표준화한 데 그 의의가 있다. 산정의 목표는 최대 성능이 아니라 요구 성능을 최소 비용으로 충족하는 적정 규모(Right Sizing) 이다.

실무 적용 시 핵심은 세 가지이다. ① 성능 요구사항(응답시간·TPS·동시사용자)을 먼저 확정할 것 — 이것이 없으면 어떤 방식도 무의미하다. ② 보정계수와 여유율의 근거를 명시할 것 — 근거 없는 여유율이 과다 산정의 주범이다. ③ 정량 방식으로 산정하되 참조 사례·BMT로 교차 검증할 것이다.

특히 R3 개정이 반영한 클라우드·AI 환경에서는 산정 패러다임 자체가 달라진다. 클라우드에서는 피크 기준 고정 산정 대신 평시 기준 + 오토스케일링으로 설계해야 비용 이점을 얻을 수 있으며, 산정의 종점은 장비 사양이 아니라 3~5년 TCO가 되어야 한다. 아울러 구축 후 실제 자원 사용률을 측정하여 산정 모델에 환류하는 체계를 갖출 때, 조직의 규모산정 정확도는 비로소 지속적으로 개선된다.

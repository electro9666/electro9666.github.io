쿠버네티스(Kubernetes)

문제​

12.쿠버네티스(Kubernetes)를 설명하시오.

Ⅰ. 개요​

쿠버네티스(K8s) 는 컨테이너화된 애플리케이션의 배포·확장·운영을 자동화하는 오픈소스 컨테이너 오케스트레이션 플랫폼이다. Google의 Borg를 기반으로 개발되어 CNCF에 기증되었으며, 선언적(Declarative) 구성과 자동 조정 루프(Reconciliation Loop) 를 핵심 원리로 한다.

   [등장 배경]
   컨테이너(Docker) 확산 → 수백~수천 개 컨테이너 발생
        │  수작업 배치·장애 복구·확장 불가능
        ▼
   [**Kubernetes**] **선언적 상태 관리**
   "**어떻게(How)** 하라"가 아니라 "**무엇을(What)** 원하는가"를 선언
        ▼
   컨트롤러가 **현재 상태 ≠ 원하는 상태**를 지속 감시하고 **자동 수렴**
   ⇒ **자가치유(Self-healing)**, 무중단 배포, 탄력적 확장

Ⅱ. 아키텍처 및 구성요소​

 ┌──────────── **Control Plane**(마스터) ────────────┐
 │  **API Server** ── 모든 요청의 단일 진입점(REST)   │
 │       │        (인증·인가·검증, etcd 유일 접근자)  │
 │  **etcd** ── 클러스터 **상태 저장소**(분산 KV, Raft)│
 │  **Scheduler** ── Pod를 **적합한 Node에 배치**     │
 │  **Controller Manager** ── **조정 루프** 실행      │
 │  (Cloud Controller Manager — CSP 연동)             │
 └─────────────────────┬─────────────────────────────┘
                       │ (API 호출)
 ┌─────────────────────▼─────────── **Worker Node** ──┐
 │  **kubelet** ── Pod 생성·상태 보고                  │
 │  **kube-proxy** ── 서비스 네트워킹·로드밸런싱       │
 │  **Container Runtime**(containerd/CRI-O)            │
 │     └─ **Pod** ─ [컨테이너][컨테이너] (IP 공유)     │
 └─────────────────────────────────────────────────────┘
구성요소역할
API Server모든 조작의 관문. 인증·인가(RBAC)·Admission 제어 수행
etcd클러스터의 모든 상태를 저장하는 유일한 진실 원천 → 백업이 최우선 과제
Scheduler자원 요구량·Affinity/Taint·Toleration 기준으로 노드 선택
Controller ManagerReplicaSet·Node·Endpoint 등 컨트롤러 실행 — 원하는 상태로 수렴
kubelet노드 에이전트. 컨테이너 생성·헬스체크(Probe) 수행
kube-proxyiptables/IPVS 기반 Service 트래픽 분산

Ⅲ. 주요 오브젝트​

분류오브젝트내용
워크로드Pod배포 최소 단위. 1개 이상 컨테이너가 네트워크·볼륨 공유(사이드카 패턴)
ReplicaSetPod 복제본 수 유지
Deployment롤링 업데이트·롤백 지원(무상태 앱 표준)
StatefulSet고정 식별자·순서 보장 — DB 등 상태 저장 앱
DaemonSet모든 노드에 1개씩 — 로그 수집·모니터링 에이전트
Job / CronJob일회성·주기적 배치 작업
네트워크ServicePod 집합에 고정 접근점 제공(ClusterIP / NodePort / LoadBalancer)
IngressL7 라우팅(호스트·경로 기반), TLS 종료
설정·보안ConfigMap / Secret설정·민감정보를 코드와 분리(Secret은 기본 Base64 → 암호화 필요)
ServiceAccount / RBACPod의 신원과 최소 권한 부여
NetworkPolicyPod 간 네트워크 접근통제(기본은 전면 허용)
저장소PV / PVC / StorageClass영속 볼륨 제공·동적 프로비저닝
격리Namespace / ResourceQuota논리적 분리, 자원 상한 설정

Ⅳ. 핵심 기능 및 고려사항​

핵심 기능내용
자가 치유Liveness/Readiness Probe 실패 시 자동 재시작·트래픽 차단, 노드 장애 시 재스케줄링
자동 확장HPA(부하 기반 Pod 수), VPA(자원 요청량), Cluster Autoscaler(노드 수)
무중단 배포롤링 업데이트, 즉시 롤백, (확장) 블루/그린·카나리
서비스 디스커버리내부 DNS(CoreDNS)로 서비스명 기반 통신, 자동 로드밸런싱
선언적 구성(IaC)YAML 매니페스트를 Git으로 관리 → GitOps(Argo CD·Flux)
구분내용
장점인프라 추상화(멀티/하이브리드 클라우드 이식성), 자원 효율(고밀도 배치), 운영 자동화, 거대한 생태계(Helm·Istio·Prometheus)
단점높은 학습 곡선·운영 복잡도, 소규모 조직에는 과도한 오버헤드, 네트워크·스토리지 트러블슈팅 난이도, 잦은 버전 업그레이드
고려사항내용
보안RBAC 최소 권한, NetworkPolicy로 기본 차단(Zero Trust), Secret 암호화(KMS)·외부 Vault 연동, 이미지 취약점 스캔·서명(SBOM), Pod Security Standards(권한 상승·privileged 금지)
가용성Control Plane 다중화(3대 이상), etcd 정기 백업·복구 훈련, PodDisruptionBudget, 다중 AZ 분산
자원 관리requests/limits 필수 설정 — 미설정 시 노드 자원 고갈(OOM), ResourceQuota·LimitRange
관측성Prometheus/Grafana(메트릭), Loki/ELK(로그), OpenTelemetry/Jaeger(추적) — 3축 필수
상태 저장 워크로드DB는 StatefulSet보다 관리형 서비스(RDS 등) 사용 권장 — 운영 난이도 대비 실익
운영 모델 선택자체 구축 vs 관리형(EKS/GKE/AKS) — 인력 역량 기준 판단, 공공은 CSAP 인증 여부 확인
업그레이드릴리스 주기가 빠름 → 버전 지원 정책·API Deprecation 대응 체계 필요

Ⅴ. 결론​

쿠버네티스는 "선언한 상태로 시스템을 자동 수렴시키는 조정 루프" 라는 단일 원리 위에 자가치유·자동확장·무중단 배포를 구현한 클라우드 네이티브의 사실상 표준 플랫폼이다.

다만 그 강력함은 운영 복잡도라는 비용을 수반하므로, 도입 판단은 기술 유행이 아니라 ① 서비스 규모와 배포 빈도, ② 조직의 운영 역량을 기준으로 해야 한다. 도입 시에는 관리형 서비스로 Control Plane 부담을 줄이고, RBAC·NetworkPolicy·이미지 서명 등 보안 기본기와 메트릭·로그·추적의 관측성 체계를 초기부터 갖추는 것이 성패를 좌우한다. 공공 부문에서는 CSAP 인증 클라우드 여부와 망분리 요건(N2SF) 을 함께 검토해야 한다.

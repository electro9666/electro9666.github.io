VPN, IPSec, SSL

문제​

6.VPN(Virtual Private Network)에 대하여 다음을 설명하시오.
가.VPN의 개념 및 특징
나.IPSec(Internet Protocol Security) VPN과 SSL(Secure Socket Layer) VPN
다.VPN의 기술요소

Ⅰ. 개요​

1. 배경​

원격지 사업장·재택근무자·이동 사용자가 내부망에 접속해야 하나, 전용선은 비용이 과다하고 인터넷은 도청·변조에 취약하다. VPN은 공중망 위에 암호화된 논리적 전용 통신로를 구성하여 이 문제를 해결한다.

   [연결 방식의 비교]
   **전용선(Leased Line)** : 안전 ○ / **비용 매우 높음**, 확장 어려움
   **인터넷 직접 연결**    : 저비용 ○ / **도청·변조·위장 위험** ✕
        ▼
   [**VPN**] 인터넷이라는 **공중망 위에 암호화 터널** 구성
   ⇒ **전용선 수준의 보안** + **인터넷 수준의 비용·확장성**

Ⅱ. 가. VPN의 개념 및 특징​

1. 개념​

VPN(Virtual Private Network, 가상사설망) 이란 공중망(인터넷)을 이용하면서도 터널링과 암호화 기술을 통해 사설망과 동등한 수준의 기밀성·무결성·인증을 제공하는 논리적 전용 네트워크이다.

   [VPN의 동작 개념 — 터널링]

   [본사 내부망]                                   [지사/원격 사용자]
   10.0.1.0/24                                      10.0.2.0/24
        │                                                 │
   ┌────▼─────┐                                    ┌──────▼────┐
   │ VPN G/W  │                                    │ VPN G/W   │
   │(암호화·  │                                    │(복호화·   │
   │ 캡슐화)  │                                    │ 역캡슐화) │
   └────┬─────┘                                    └──────┬────┘
        │  ╔══════════ **암호화 터널** ═══════════════╗   │
        └──╢  [신규 IP헤더][ESP][**원본 패킷(암호화)**] ╟───┘
           ╚═══════════════════════════════════════════╝
                        **인터넷**(공중망)
                    ※ 중간 경로에서는 **내용·내부 IP 확인 불가**

2. VPN의 유형​

분류 기준유형내용
연결 형태Site-to-Site VPN본사 ↔ 지사 게이트웨이 간 상시 연결(망 대 망)
Remote Access VPN개인 단말 ↔ 본사 — 재택·출장 사용자
Extranet VPN협력사·거래처와의 제한적 연결
구현 계층L2 VPN데이터링크 계층 — L2TP·PPTP, VPLS
L3 VPN네트워크 계층 — IPSec, MPLS VPN
L4~L7 VPN전송·응용 계층 — SSL/TLS VPN
구축 주체CPE 기반(자체 구축)기업이 직접 장비 구축·운영
네트워크 기반(사업자 제공)통신사가 제공(MPLS VPN 등)

3. VPN의 특징​

구분내용
장점· 비용 절감 — 전용선 대비 획기적 저렴
· 확장 용이 — 인터넷만 있으면 어디서든 연결
· 보안 확보 — 기밀성·무결성·인증·접근통제
· 이동성 — 재택·출장 근무 지원
· IP 주소 은닉 — 내부 주소 체계 노출 방지
단점· 성능 저하 — 암·복호화 연산, 캡슐화에 따른 오버헤드
· 인터넷 품질에 종속 — 지연·손실 제어 불가(QoS 보장 곤란)
· VPN 게이트웨이가 단일 장애점·집중 공격 표적
· 단말이 감염된 경우 내부망 감염 통로로 악용
· 설정·인증서 관리 복잡
제공 보안 서비스기밀성(암호화), 무결성(해시·MAC), 인증(사용자·장비), 부인방지, 접근통제, 재전송 공격 방지

Ⅲ. 나. IPSec VPN과 SSL VPN​

1. IPSec VPN​

IPSec(Internet Protocol Security) 은 IP 계층(L3) 에서 패킷 단위로 인증·무결성·기밀성을 제공하는 표준 프로토콜 집합이다.

■ IPSec의 구성 프로토콜​

프로토콜기능제공 보안
AH(Authentication Header)인증 헤더인증·무결성·재전송 방지
기밀성(암호화) 미제공 — 실무 사용 적음
ESP(Encapsulating Security Payload)캡슐화 보안 페이로드기밀성 + 인증·무결성 → 실질적 표준
IKE(Internet Key Exchange)키 교환·SA 협상Diffie-Hellman 기반 키 교환, 상호 인증
IKEv2가 현재 표준(안정성·MOBIKE 지원)
SA(Security Association)보안 연관통신 쌍방이 합의한 알고리즘·키·수명 정보(단방향)

■ IPSec의 동작 모드​

   [**전송 모드**(Transport Mode)]
   원본 : [IP 헤더][TCP][데이터]
   적용 : [**IP 헤더**][**ESP**][TCP][데이터(암호화)][ESP 인증]
          └ 원본 IP 헤더 유지 → **종단 간(Host-to-Host)** 통신
          ※ **내부 IP 노출**, 오버헤드 작음

   [**터널 모드**(Tunnel Mode)]  ★ Site-to-Site VPN의 표준
   원본 : [IP 헤더][TCP][데이터]
   적용 : [**신규 IP 헤더**][**ESP**][**원본 IP 헤더**][TCP][데이터(암호화)][ESP 인증]
          └ **원본 패킷 전체를 암호화·캡슐화**
          ※ **내부 IP 완전 은닉**, 게이트웨이 간 연결에 적합

■ IPSec 연결 수립 절차​

   ① **IKE Phase 1** — 관리 채널 수립
        │  · 상호 인증(**사전공유키(PSK)** 또는 **인증서**)
        │  · **Diffie-Hellman 키 교환** → 공유 비밀 생성
        │  · **IKE SA** 수립(양방향 보안 채널)
        ▼
   ② **IKE Phase 2** — 데이터 채널 수립
        │  · 암호·인증 알고리즘 협상
        │  · **IPSec SA** 수립(방향별 각 1개)
        ▼
   ③ **데이터 전송** — ESP로 암호화·캡슐화하여 전송
        ▼
   ④ **SA 재협상(Rekey)** — 수명 만료 시 키 갱신

2. SSL(TLS) VPN​

SSL VPN은 전송응용 계층(L4L7) 의 SSL/TLS 프로토콜을 이용하여 보안 통신을 제공하는 VPN이다. 웹 브라우저만으로 접속 가능한 것이 최대 특징이다.

※ SSL은 취약점(POODLE 등)으로 폐기되었고, 현재는 TLS 1.2/1.3을 사용한다. 명칭만 관용적으로 'SSL VPN'으로 통용된다.

■ SSL VPN의 접속 방식​

방식내용특징
웹 방식(Clientless / Web Portal)브라우저만으로 웹 애플리케이션 접근설치 불필요, 접근 대상이 웹 서비스로 제한
포트 포워딩·애플릿 방식Java/ActiveX 등 경량 모듈로 특정 애플리케이션 중계일부 비웹 애플리케이션 지원
터널 방식(Full Tunnel / Network Extension)전용 클라이언트 설치 → 가상 어댑터로 내부망 전체 접근IPSec과 유사한 수준의 접근

■ TLS 핸드셰이크 개요​

   ① **ClientHello** — 지원 암호 스위트·TLS 버전 제시
        ▼
   ② **ServerHello + 서버 인증서** — 암호 스위트 선택, 인증서 전달
        ▼
   ③ **서버 인증서 검증** — CA 서명·유효기간·**폐기 여부(OCSP)** 확인
        ▼
   ④ **키 교환**(ECDHE 등) → **세션키(대칭키) 생성**
        │  ※ **전방위 안전성(PFS)** 확보
        ▼
   ⑤ **암호화 통신 개시** — 세션키로 대칭 암호화
   ※ **TLS 1.3**은 왕복 횟수를 줄여(1-RTT / 0-RTT) 접속 지연 대폭 감소

3. IPSec VPN과 SSL VPN의 비교​

비교 기준IPSec VPNSSL(TLS) VPN
동작 계층네트워크 계층(L3)전송응용 계층(L4L7)
보호 범위모든 IP 트래픽(애플리케이션 무관)주로 애플리케이션 단위(웹 중심)
클라이언트전용 클라이언트·설정 필요브라우저만으로 가능(Clientless)
설치·배포단말마다 설치·설정 → 관리 부담 큼설치 불필요 → 배포 용이
주 용도Site-to-Site(본사–지사 상시 연결)Remote Access(재택·출장·협력사)
접근 통제 단위네트워크 단위(내부망 전체 접근 경향)애플리케이션·URL 단위 세밀 제어 ← 최소 권한에 유리
NAT 통과NAT Traversal 필요(UDP 4500 캡슐화)HTTPS(443) 사용 → 방화벽·NAT 통과 용이
방화벽 친화성특정 포트·프로토콜(ESP/50, UDP 500) 차단 가능443 포트 — 사실상 모든 환경에서 통과
성능오버헤드 상대적으로 작음, 하드웨어 가속 유리애플리케이션 계층 처리로 오버헤드 큼
인증PSK, 인증서, XAUTH인증서·ID/PW·MFA·SSO 연계 용이
단말 보안 점검제한적접속 단말 보안 상태 점검(엔드포인트 검사) 용이
적용 유연성낮음(사전 설정 필요)높음(어디서든 즉시 접속)
보안 위험연결 시 내부망 광범위 노출 우려브라우저 취약점·세션 탈취 주의
비용게이트웨이·클라이언트 관리 비용상대적으로 낮음
   [**선택 기준**]
   **고정 거점 간 상시 대용량 연결**(본사–공장–지사)  →  **IPSec(터널 모드)**
   **불특정 위치의 사용자 원격 접속**(재택·출장·협력사) →  **SSL VPN**
   **모든 트래픽 보호가 필요**(비웹 애플리케이션 포함)   →  **IPSec / SSL 터널 방식**
   **특정 웹 시스템만 제한 허용**(최소 권한)            →  **SSL 웹 방식**
   ⇒ 실무에서는 **두 방식을 병행**하는 구성이 일반적

Ⅳ. 다. VPN의 기술요소​

1. 기술요소 체계​

 ┌──────────── **VPN 4대 핵심 기술요소** ────────────┐
 │                                                   │
 │  **① 터널링**(Tunneling)      — 논리적 통로 생성   │
 │  **② 암호화**(Encryption)     — 기밀성 확보        │
 │  **③ 인증**(Authentication)   — 신원 확인·무결성   │
 │  **④ 키 관리**(Key Management)— 안전한 키 분배·갱신│
 │                                                   │
 │  **(+) 접근제어 · QoS · 로깅** — 부가 기술요소     │
 └───────────────────────────────────────────────────┘

2. ① 터널링 (Tunneling)​

원본 패킷을 새로운 헤더로 캡슐화(Encapsulation) 하여, 공중망을 통과하는 논리적 통로를 만드는 기술이다.

계층프로토콜내용
L2PPTPMS 개발, 구현 단순 / 보안 취약(MS-CHAPv2) → 사용 금지 권고
L2FCisco 개발, 단독 암호화 미제공
L2TPPPTP+L2F 통합, 자체 암호화 없음 → IPSec과 결합(L2TP/IPSec)
L3IPSec표준 L3 터널링, ESP 터널 모드
GRE범용 캡슐화, 멀티캐스트·라우팅 프로토콜 전달 → IPSec과 결합(GRE over IPSec)
MPLS사업자 제공 VPN, 레이블 기반
L4~7SSL/TLSHTTPS 기반 터널
최신WireGuard경량·고속 커널 기반 VPN, 코드량 적어 검증 용이
OpenVPNTLS 기반 오픈소스, UDP/TCP 유연

3. ② 암호화 (Encryption)​

구분알고리즘용도
대칭키AES(128/256, GCM 모드), ChaCha20
국내 SEED·ARIA·LEA		실제 데이터 암호화(고속)
3DES·DES취약 — 사용 금지
공개키RSA(2048 이상), ECC/ECDSA(256 이상)키 교환·전자서명·인증
키 교환DH / ECDHE세션키 생성, ECDHE는 전방위 안전성(PFS) 제공
양자내성PQC(ML-KEM 등)향후 전환 대비(하이브리드 방식)

PFS(Perfect Forward Secrecy) : 장기키가 유출되어도 과거 세션 복호화 불가 → ECDHE 사용 필수

4. ③ 인증 및 무결성 (Authentication & Integrity)​

구분기술내용
장비·터널 인증사전공유키(PSK)구현 단순 / 키 유출·관리 취약
디지털 인증서(PKI)권장 방식 — 확장성·안전성 우수
사용자 인증ID/PW, OTP·MFA, 생체MFA 적용 필수(계정 탈취 대응)
RADIUS·LDAP·AD 연계통합 계정 관리
SAML·OIDC(SSO)SSL VPN에서 널리 사용
메시지 무결성HMAC-SHA256 이상, AES-GCM(AEAD)위·변조 탐지
MD5·SHA-1은 사용 금지
재전송 방지시퀀스 번호·Anti-Replay 윈도우패킷 재전송 공격 차단

기술내용

요소내용

· 방화벽·NAC 연계, 마이크로세그멘테이션

7. 운영 시 고려사항 및 보안 위협​

위협·이슈대응 방안
① 계정 탈취를 통한 VPN 침투MFA 필수 적용, 비정상 접속(해외 IP·심야) 탐지, 계정 잠금 정책
② VPN 장비 취약점 악용랜섬웨어 침투의 주요 경로 → 보안 패치 즉시 적용, EOS 장비 교체, 관리 인터페이스 외부 노출 금지
③ 과도한 내부망 접근 허용VPN 연결 = 내부망 전면 접근이 되지 않도록 최소 권한 세분화
④ 감염 단말을 통한 내부 확산엔드포인트 보안 점검 의무화, 격리 네트워크 우선 접속
⑤ 취약 프로토콜·알고리즘 사용PPTP·SSLv3·TLS 1.0/1.1·3DES·SHA-1 폐기, TLS 1.2 이상·AES-GCM 적용
⑥ 스플릿 터널링 위험인터넷과 내부망 동시 접속 시 우회 경로 발생 → 정책적 판단(보안 vs 성능)
⑦ 성능 병목암호 연산 부하 → 하드웨어 가속·게이트웨이 증설·부하분산
⑧ 단일 장애점게이트웨이 이중화·이중 회선
⑨ 로그 미보관침해 시 추적 불가 → 접속 로그 장기 보관·정기 점검

8. 최신 동향 — 제로트러스트와 SASE​

   [**VPN의 구조적 한계**]
   "**한 번 인증하면 내부망에 들어온 것**"이라는 **경계 기반 신뢰 모델**
        │  · 계정 탈취 시 **광범위한 내부 접근 허용**
        │  · 재택·클라우드 확산으로 **경계 자체가 소멸**
        ▼
   [**ZTNA**(Zero Trust Network Access)]
   · **애플리케이션 단위 접근** — 네트워크 접근 자체를 부여하지 않음
   · **모든 요청마다 재검증**(사용자·단말·상황)
   · 내부 자원을 **인터넷에 노출하지 않음**(Dark Cloud)
        ▼
   [**SASE**] 네트워크(SD-WAN) + 보안(ZTNA·SWG·CASB·FWaaS)의 **클라우드 통합**

   ⇒ VPN이 즉시 사라지지는 않으나, **Site-to-Site는 IPSec/SD-WAN**,
      **원격 접속은 ZTNA로 전환**되는 흐름

Ⅴ. 결론​

VPN은 공중망 위에 터널링과 암호화로 논리적 전용선을 구성함으로써, 전용선의 보안성과 인터넷의 경제성·확장성을 동시에 확보하는 기술이다. 그 기반은 터널링·암호화·인증·키 관리라는 네 가지 기술요소이며, 이들이 결합될 때 기밀성·무결성·인증·재전송 방지가 성립한다.

IPSec VPN과 SSL VPN은 대체 관계가 아니라 용도가 다른 보완 관계이다. IPSec은 L3에서 모든 IP 트래픽을 보호하므로 본사–지사 간 상시 대용량 연결(Site-to-Site) 에 적합하고, SSL VPN은 브라우저만으로 접속 가능하고 애플리케이션 단위 세밀 통제가 가능하므로 불특정 위치의 원격 접속(Remote Access) 에 적합하다. 실무에서는 거점 간은 IPSec, 사용자 원격 접속은 SSL VPN으로 병행 구성하는 것이 일반적이며, 이때 SSL VPN의 애플리케이션 단위 접근 제어가 최소 권한 원칙 구현에 유리하다는 점이 중요한 선택 근거가 된다.

운영 관점에서 반드시 인식해야 할 점은 VPN 게이트웨이가 조직의 최대 공격 표적이자 단일 장애점이라는 사실이다. 실제 다수의 랜섬웨어 침해가 VPN 장비의 미패치 취약점 또는 MFA 미적용 계정 탈취를 통해 시작되었다. 따라서 ① VPN 계정에 대한 MFA 의무 적용, ② VPN 장비의 즉시 패치와 EOS 장비 교체, ③ 취약 프로토콜(PPTP·TLS 1.0) 폐기, ④ 접속 단말의 보안 상태 점검은 선택이 아닌 필수 통제이다.

끝으로, VPN의 근본적 한계는 "연결되면 내부"라는 경계 기반 신뢰 모델에 있다. 재택근무와 클라우드 확산으로 네트워크 경계 자체가 소멸한 환경에서는, 네트워크 접근이 아니라 애플리케이션 접근만을 허용하고 모든 요청을 지속 검증하는 ZTNA·SASE로의 전환이 대안으로 부상하고 있다. 다만 전면 전환에는 시간과 비용이 필요하므로, 당분간은 거점 간 IPSec/SD-WAN을 유지하면서 원격 접속 영역부터 단계적으로 ZTNA를 도입하는 것이 현실적인 이행 전략이라 판단된다.

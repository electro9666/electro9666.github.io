데이터 모델링, 식별, 비식별

문제​

4.RDBMS를 적용하기 위한 데이터 모델링에 대하여 다음을 설명하시오.
가.데이터 모델링의 개념 및 모델링 단계별 수행내용
나.데이터 관계 모델링 시 식별(Identification)과 비식별(Non Identification)에 대하여 비교
다.데이터 모델링 시 고려사항

Ⅰ. 개요​

1. 배경​

정보시스템에서 데이터는 프로세스보다 수명이 길다. 업무 절차와 화면은 자주 바뀌지만, 데이터 구조는 한번 잘못 설계되면 전면 재구축 없이는 수정이 어렵다.

   [데이터 모델링의 중요성]
   프로세스·화면 : 변경 빈번, 수정 비용 상대적으로 낮음
   **데이터 구조**  : **변경 어려움**, 전 시스템에 영향
        │  · 잘못된 구조 → **성능 저하·정합성 오류·확장 불가**
        │  · 운영 중 구조 변경 → **데이터 이행·프로그램 전면 수정**
        ▼
   ⇒ 데이터 모델링은 **시스템 품질과 수명을 결정하는 핵심 설계 활동**
   근거·표준 : **데이터 품질관리 지침**, **공공데이터 품질관리 매뉴얼**,
              한국데이터산업진흥원 **데이터 아키텍처 표준**

Ⅱ. 가. 데이터 모델링의 개념 및 단계별 수행내용​

1. 데이터 모델링의 개념​

데이터 모델링(Data Modeling) 이란 현실 세계의 업무를 추상화·단순화하여 데이터 구조로 표현하고, 이를 데이터베이스로 구현 가능한 형태로 변환하는 설계 활동이다.

관점내용
목적업무 요구를 만족하는 정확·일관·효율적인 데이터 구조 설계
본질추상화(핵심만 표현) + 단순화(이해 가능) + 명확화(모호성 제거)
3대 관점데이터(무엇), 프로세스(어떻게), 상관(CRUD 매트릭스)
구성 요소엔터티(Entity), 속성(Attribute), 관계(Relationship)
표기법IE(Information Engineering) 표기법(까마귀발), 바커(Barker) 표기법, UML
   [데이터 모델의 3요소]

   **엔터티**(Entity)          **속성**(Attribute)        **관계**(Relationship)
   업무상 관리 대상 집합       엔터티의 특성 항목         엔터티 간 연관성
   예) 고객, 주문, 상품        예) 고객명, 주소           예) 고객 ─◀ 주문
        │                          │                          │
   식별자(PK) 보유             도메인·NULL 여부          **차수(Cardinality)**
                                                         **선택성(Optionality)**

2. 데이터 모델링 3단계​

 ┌──────────── **① 개념적 모델링**(Conceptual) ────────────┐
 │  관점 : **업무 중심** — "무엇을 관리할 것인가"           │
 │  대상 : 전사·업무 영역                                   │
 │  산출 : **핵심 엔터티·관계**(ERD 개요), 주제영역 정의    │
 │  특징 : **DBMS 독립적**, 추상 수준 높음, 경영진 소통용   │
 └───────────────────────┬──────────────────────────────────┘
                         ▼
 ┌──────────── **② 논리적 모델링**(Logical) ───────────────┐
 │  관점 : **데이터 구조 중심** — "어떻게 구조화할 것인가"  │
 │  대상 : 업무 전체 상세                                   │
 │  산출 : **속성·식별자·관계·정규화 완료 ERD**             │
 │  특징 : **DBMS 독립적**, **정규화 수행**, 재사용성 높음  │
 │        **모델링의 핵심 단계**                            │
 └───────────────────────┬──────────────────────────────────┘
                         ▼
 ┌──────────── **③ 물리적 모델링**(Physical) ──────────────┐
 │  관점 : **성능·저장 중심** — "어떻게 구현할 것인가"      │
 │  대상 : 실제 DBMS                                        │
 │  산출 : **테이블·컬럼·인덱스·파티션·저장 파라미터**      │
 │  특징 : **DBMS 종속**, **반정규화·성능 튜닝** 반영       │
 └──────────────────────────────────────────────────────────┘

3. 단계별 수행 내용​

① 개념적 모델링​

수행 활동내용
요구사항 분석업무 인터뷰, 현행 시스템·장표 분석, 요구사항 정의서 검토
주제영역 정의업무를 주제영역(Subject Area) 으로 구분(고객·상품·주문·회계)
핵심 엔터티 도출업무상 반드시 관리해야 할 핵심 엔터티 식별(통상 20~30개 이내)
관계 정의엔터티 간 주요 관계와 차수(1:1, 1:M, M:N) 정의
개념 ERD 작성상위 수준 개괄 ERD, 업무 담당자와 검증·합의

② 논리적 모델링​

수행 활동내용
엔터티 상세화개념 엔터티 세분화, 엔터티 정의서 작성(정의·발생 규칙)
속성 정의모든 속성 도출, 도메인 정의(데이터 타입·길이·범위), NULL 허용 여부
식별자(Key) 정의주식별자(PK) 선정, 후보키·대체키·외래키(FK) 정의
관계 상세 정의차수(Cardinality)·선택성(Optionality), 식별/비식별 관계 결정 ← 나항
M:N 관계 해소M:N 관계를 연결(교차) 엔터티로 분해
정규화(Normalization)1NF~3NF(BCNF) 수행 → 데이터 중복·이상현상 제거
이력·서브타입 설계이력 관리 방식(스냅샷·변경이력), 슈퍼타입/서브타입 설계
표준화데이터 표준 준수 — 용어·단어·도메인 사전 적용
검증CRUD 매트릭스로 프로세스와 교차 검증, 상호 리뷰
   [**정규화** — 논리 모델링의 핵심]
   **1NF** : 모든 속성이 **원자값**(반복 그룹 제거)
        ▼
   **2NF** : **부분 함수 종속 제거**(복합키의 일부에만 종속되는 속성 분리)
        ▼
   **3NF** : **이행 함수 종속 제거**(비주식별자 간 종속 분리)
        ▼
   **BCNF** : 모든 결정자가 후보키
        ▼
   [효과] **삽입·갱신·삭제 이상(Anomaly) 제거**, 데이터 정합성 확보
   [부작용] 테이블 수 증가 → **조인 증가 → 조회 성능 저하** 가능

③ 물리적 모델링​

수행 활동내용
테이블·컬럼 정의논리 엔터티 → 테이블, 속성 → 컬럼, DBMS별 데이터 타입 매핑
명명 규칙 적용물리명 변환(표준 약어 적용), 명명 표준 준수
제약조건 정의PK·FK·UNIQUE·CHECK·NOT NULL, 참조 무결성 옵션(CASCADE 등)
인덱스 설계조회 패턴 기반 인덱스 설계, 복합 인덱스 컬럼 순서, 클러스터드 인덱스
반정규화(Denormalization)성능을 위해 의도적으로 정규형 완화 — 컬럼 중복, 테이블 병합·분할, 파생 컬럼(집계값)
파티셔닝대용량 테이블 레인지·해시·리스트 파티션(이력·기간 기준)
저장 구조 설계테이블스페이스 배치, 초기 크기·증가율, 압축
성능 검증예상 데이터량 기반 용량 산정, 주요 SQL 실행계획 검토
보안 설계암호화 대상 컬럼(개인정보), 접근제어·마스킹, 감사 로그
반정규화 유형예시
컬럼 반정규화조인 회피를 위한 중복 컬럼 추가(주문에 고객명 복사)
테이블 병합1:1 관계 테이블 통합
테이블 분할수직 분할(자주 쓰는 컬럼 분리), 수평 분할(파티셔닝)
파생 컬럼집계값 사전 계산(주문 총액, 게시글 댓글 수)
이력 테이블 분리현재 데이터와 이력 분리

반정규화의 원칙 : 무조건 적용하지 않고 성능 문제가 실증된 경우에만, 정합성 유지 방안(트리거·배치·애플리케이션 로직) 과 함께 적용

Ⅲ. 나. 식별 관계와 비식별 관계의 비교​

1. 개념​

부모 엔터티의 주식별자(PK) 를 자식 엔터티가 어떤 방식으로 상속받는가에 따라 관계를 구분한다.

   [**식별 관계**(Identifying Relationship)]

   ┌───────────────┐        ┌──────────────────────────┐
   │ **주문**       │        │ **주문상세**              │
   ├───────────────┤        ├──────────────────────────┤
   │ **주문번호(PK)**│═══════▶│ **주문번호(PK, FK)**  ← 상속│
   │  주문일자      │  실선   │ **상세순번(PK)**          │
   └───────────────┘        │  상품코드, 수량           │
                            └──────────────────────────┘
   ⇒ 부모 PK가 자식의 **PK의 일부**가 됨 (**실선** 표기)
   ⇒ 부모 없이 자식이 **존재할 수 없음**(강한 종속)


   [**비식별 관계**(Non-Identifying Relationship)]

   ┌───────────────┐        ┌──────────────────────────┐
   │ **부서**       │        │ **사원**                  │
   ├───────────────┤        ├──────────────────────────┤
   │ **부서코드(PK)**│┈┈┈┈┈┈▶│ **사원번호(PK)**          │
   │  부서명        │  점선   │  부서코드(FK)  ← 일반 속성 │
   └───────────────┘        │  사원명                   │
                            └──────────────────────────┘
   ⇒ 부모 PK가 자식의 **일반 속성(FK)** 이 됨 (**점선** 표기)
   ⇒ 부모 없이도 자식이 **독립적으로 존재 가능**(약한 종속)

2. 상세 비교​

비교 기준식별 관계(Identifying)비식별 관계(Non-Identifying)
부모 PK의 위치자식의 PK의 일부(PK + FK)자식의 일반 속성(FK만)
표기법(IE)실선점선
종속 강도강한 종속(Strong Entity → Weak Entity)약한 종속
자식의 독립 존재불가능 — 부모 없이 존재 불가가능 — 부모 없이도 존재
부모 필수 여부필수(Mandatory)선택 가능(Optional, NULL 허용 가능)
PK 구성복합키(부모 PK + 자기 식별자)자체 단일 PK(주로 인조키)
PK 상속 전파손자·증손자까지 계속 상속 → PK 컬럼 수 증가상속 중단 → PK 단순 유지
관계 참여자식의 정체성이 부모에 의존자식이 독립적 정체성 보유
조인 특성자식 PK에 부모 키 포함 → 상위 키로 바로 조회 가능(조인 감소)조인 필요
인덱스복합 PK 인덱스 자동 활용FK에 별도 인덱스 필요
모델의 간결성PK 컬럼 증가로 복잡해질 수 있음단순·명확
유연성낮음 — 구조 변경 시 하위 전체 영향높음 — 변경 영향 국소화
SQL 복잡도조인 조건에 다중 컬럼 필요단일 컬럼 조인
대표 사례주문–주문상세, 계약–계약상세, 연결(교차) 엔터티부서–사원, 고객–주문, 코드–사용 테이블

3. 선택 기준​

   [**식별 관계로 설계해야 하는 경우**]
   · 자식이 부모 없이 **의미를 가질 수 없음**(주문상세는 주문 없이 무의미)
   · 부모–자식의 **생명주기가 일치**(부모 삭제 시 자식도 삭제)
   · **M:N 해소용 연결 엔터티** — 양쪽 PK를 상속받는 것이 자연스러움
   · 부모 키로 자식을 **자주 조회**(조인 회피 이점)

   [**비식별 관계로 설계해야 하는 경우**]
   · 자식이 **독립적으로 존재**(사원은 부서 없이도 존재 가능)
   · 부모 관계가 **선택적**(NULL 허용 필요)
   · 부모 관계가 **변경될 수 있음**(사원의 부서 이동)
   · **PK 상속이 3단계 이상 이어져 복잡도가 과도**해지는 경우
   · **코드성·참조 테이블**과의 관계

4. 실무적 판단 — 장단점과 절충​

구분식별 관계 남용 시비식별 관계 남용 시
문제· PK 컬럼이 계속 누적(4~5개 이상)
· 조인 조건 복잡, SQL 가독성 저하
· 상위 키 변경 시 하위 전체 영향
· 인덱스 크기 증가		· 모든 조회에 조인 필수 → 성능 저하
· 관계의 업무적 의미(강한 종속) 표현 상실
· 참조 무결성이 느슨해질 수 있음
· 인조키 남발로 업무 의미 소실
권고의미상 종속이 명확한 경우로 한정관계의 강도를 정확히 반영하여 선택

실무 원칙 : 논리 모델에서는 업무 의미에 충실하게 식별/비식별을 결정하고, 물리 모델에서 PK 상속이 과도하면 인조키(Surrogate Key) 도입으로 비식별 전환을 검토한다. 다만 인조키 도입 시에는 원래의 업무 키에 UNIQUE 제약을 반드시 부여하여 정합성을 보장해야 한다.

Ⅳ. 다. 데이터 모델링 시 고려사항​

1. 설계 품질 관점​

고려사항내용
① 업무 요구사항의 정확한 반영모델은 업무 규칙(Business Rule)의 표현 → 업무 담당자와 반복 검증, 용어 정의 합의
② 정규화와 성능의 균형논리 모델은 정규화 원칙 준수, 물리 모델에서 실증된 성능 문제에 한해 반정규화
→ 반정규화 시 정합성 유지 방안 필수 설계
③ 데이터 표준화용어·단어·도메인·코드 표준 준수 → 동일 의미의 서로 다른 컬럼명 방지
(예: 고객번호/CUST_NO/CUSTOMER_ID 혼재)
④ 식별자 설계업무 키 vs 인조키 선택 신중
· 업무 키 : 의미 명확, 그러나 변경 가능성·길이 문제
· 인조키 : 안정적, 그러나 업무 의미 소실 → 업무 키에 UNIQUE 제약 병행
⑤ 관계의 정확한 정의차수·선택성·식별/비식별을 업무 규칙에 맞게 정의
→ M:N 관계는 반드시 연결 엔터티로 해소
⑥ 이력 관리 설계어떤 데이터를 언제부터 언제까지 관리할 것인가
→ 변경 이력·스냅샷·유효기간(시작일/종료일) 방식 선택
⑦ 슈퍼타입/서브타입 전환통합(1개 테이블) / 분리(서브타입별) / 부분 통합 → 접근 패턴·NULL 비율 기준 판단
⑧ 확장성·유연성향후 업무 변화 예측 → 속성 추가 용이한 구조, 다만 과도한 범용화(EAV) 지양

2. 성능·운영 관점​

고려사항내용
⑨ 데이터 볼륨 산정엔터티별 예상 건수·증가율 산정 → 파티셔닝·아카이빙 전략 결정
⑩ 접근 패턴 분석CRUD 매트릭스로 조회·갱신 빈도 파악 → 인덱스·반정규화 대상 도출
⑪ 인덱스 설계조회 조건·정렬 기준 반영, 과다 인덱스는 갱신 성능 저하
⑫ 트랜잭션 설계동시성·락 경합 고려, 갱신 집중 테이블 식별
⑬ 데이터 아카이빙보존기간 경과 데이터의 분리·삭제 정책

3. 보안·법규 관점​

고려사항내용
⑭ 개인정보 최소 수집필요 최소 항목만 설계 — 주민등록번호 등 법적 근거 없는 수집 금지
(개인정보보호법 제3조·제24조의2)
⑮ 암호화 대상 식별고유식별정보·비밀번호·바이오정보 등 암호화 대상 컬럼 지정 → 컬럼 길이·타입에 암호화 반영
⑯ 보유기간·파기 설계보유기간 컬럼 설계, 경과 시 자동 파기 로직
⑰ 접근통제·마스킹민감 컬럼에 대한 뷰·행 수준 보안(RLS)·마스킹 설계
⑱ 가명·비식별 처리 고려분석 활용 대비 식별자 분리 저장(PbD의 SEPARATE 전략), 가명처리 대상 사전 식별
⑲ 접속기록 설계개인정보 처리 이력 기록 테이블 — 1년(중요 시 2년) 이상 보관

4. 프로세스·관리 관점​

고려사항내용
⑳ 모델 검증CRUD 매트릭스 교차 검증(C 없는 엔터티, 미사용 엔터티 점검), 상호 리뷰·감리
㉑ 형상관리·현행화모델 변경 시 ERD·데이터 사전 동기화 → 미갱신 시 모델이 무용지물
㉒ 데이터 품질 기준 반영완전성·유일성·유효성·일관성·정확성 기준을 제약조건으로 구현
㉓ 도구 활용모델링 도구(ERwin·DA#) 활용, 논리–물리 모델 연계 관리, 리버스 엔지니어링
㉔ 마이그레이션 고려기존 시스템 데이터 이행 가능성 — 데이터 타입·코드 체계 변환 사전 검토

Ⅴ. 결론​

데이터 모델링은 업무를 데이터 구조로 번역하는 활동이며, 개념(무엇을) → 논리(어떻게 구조화) → 물리(어떻게 구현) 의 3단계로 수행된다. 이 중 논리적 모델링이 핵심으로, 정규화를 통해 데이터 정합성의 기반을 확보하고, 물리적 모델링에서 성능 요구에 따라 선택적으로 반정규화하는 것이 올바른 순서이다. 처음부터 성능을 이유로 정규화를 생략하면, 정합성 오류라는 더 큰 비용을 치르게 된다.

식별 관계와 비식별 관계의 선택은 단순한 표기 규칙이 아니라 업무 규칙의 표현이다. 자식이 부모 없이 존재할 수 있는가라는 질문이 판단의 기준이며, 이를 정확히 반영해야 모델이 업무를 올바르게 서술한다. 실무에서는 식별 관계를 남용하면 PK가 계속 누적되어 복잡도가 폭증하고, 비식별 관계를 남용하면 관계의 강도가 소실되고 조인 부담이 증가한다. 따라서 의미상 종속이 명확한 경우(주문–주문상세, 연결 엔터티)에는 식별 관계를, 독립 존재가 가능하거나 관계가 변경 가능한 경우에는 비식별 관계를 선택하는 것이 원칙이다.

모델링 시 고려사항 중 실무적으로 가장 중요한 세 가지를 꼽자면 다음과 같다. 첫째, 데이터 표준화이다. 표준이 없으면 동일 의미의 컬럼이 시스템마다 다르게 정의되어 데이터 통합과 품질 관리가 불가능해진다. 둘째, 개인정보 보호 설계의 사전 반영이다. 암호화 대상 컬럼·보유기간·식별자 분리는 설계 단계에서 반영하지 않으면 사후 적용 비용이 급증한다(Privacy by Design). 셋째, 모델의 현행화이다. 운영 중 변경 사항이 ERD에 반영되지 않으면 모델은 문서로서의 가치를 잃고, 이후 모든 영향도 분석이 부정확해진다.

결국 좋은 데이터 모델은 업무를 정확히 반영하고(정합성), 필요한 성능을 내며(효율성), 변화를 수용할 수 있고(확장성), 법적 요건을 충족하는(적법성) 네 가지 조건을 균형 있게 만족하는 모델이다. 이 균형점을 찾는 것이 데이터 아키텍트의 핵심 역량이라 할 수 있다.

BPFdoor(Berkeley Packet Filter door) 악성코드

Ⅰ. 개요​

1. 개념​

BPFdoor는 리눅스 커널의 패킷 필터링 기능인 BPF(Berkeley Packet Filter) 를 악용하여, 열린 포트 없이(Portless) 네트워크 트래픽을 감청하다가 특정 매직 패킷(Magic Packet)을 수신하면 활성화되는 스텔스형 백도어이다.

2. 위협의 심각성​

2022년 공개된 이후 통신·금융 인프라에서 수년간 탐지되지 않은 채 상주한 사례가 보고되었으며, 2025년 국내 통신사 침해사고에서도 변종이 확인되면서 장기 잠복형(APT) 백도어의 대표 사례로 부각되었다.

Ⅱ. 가. BPFdoor의 개념 및 기존 백도어 방식과의 차이점​

1. BPF(Berkeley Packet Filter) 기술 배경​

  • BPF는 커널 계층에서 네트워크 패킷을 필터링하여 필요한 패킷만 사용자 영역으로 전달하는 기술(tcpdump·Wireshark의 기반).
  • BPFdoor는 이 기능을 악용해 소켓에 BPF 필터를 부착하고, 커널이 패킷을 처리하기 전 단계에서 매직 패킷만 선별적으로 수신한다.

2. 동작 원리​

   [BPFdoor 동작 흐름]
   ① 침투 후 상주 : 정상 프로세스명으로 위장(예: /sbin/udevd, dbus-daemon)
        │            **포트를 열지 않음(LISTEN 상태 없음)**
        ▼
   ② **Raw Socket + BPF 필터 부착** → 커널 수준에서 모든 트래픽 감시
        │  ※ 방화벽이 차단한 패킷도 **필터에 걸리면 수신 가능**
        ▼
   ③ 공격자가 **매직 패킷(특정 바이트 시퀀스 포함)** 전송
        │  (TCP/UDP/ICMP 어느 프로토콜이든 가능)
        ▼
   ④ BPF 필터가 매직 패킷 탐지 → **백도어 활성화**
        │  ├─ iptables 규칙 **동적 추가**로 공격자 IP만 임시 허용
        │  ├─ **리버스 셸** 연결 또는 바인드 셸 개방
        │  └─ 명령 수행 후 **규칙 원복·흔적 제거**
        ▼
   ⑤ 통신 종료 후 다시 **잠복 상태로 복귀**(포트 닫힘)

3. 기존 백도어 방식과의 차이점​

비교 기준기존 백도어(바인드/리버스 셸)BPFdoor
포트 개방특정 포트를 LISTEN 상태로 대기포트를 열지 않음(Portless) — netstat·ss로 미탐지
탐지 방법포트 스캔·열린 포트 점검으로 발견포트 스캔으로 발견 불가
동작 계층사용자 영역(애플리케이션) 소켓커널의 BPF 필터 계층 — 방화벽·소켓 계층 이전
방화벽 우회방화벽이 차단하면 통신 불가방화벽이 드롭한 패킷도 BPF 필터에서 수신
활성 상태상시 대기(Always-on)평시 비활성 → 매직 패킷 수신 시에만 활성화
트래픽 특성지속적 C2 비콘(주기적 아웃바운드)평시 트래픽 없음 → 이상 트래픽 탐지 회피
프로세스 위장단순 은닉·루트킷정상 시스템 데몬명으로 위장, 실행 후 자기 삭제(메모리 상주)
접근 제어고정 IP·포트매직 패킷 발신 IP를 동적으로 iptables에 허용 후 원복
프로토콜주로 TCPTCP·UDP·ICMP 모두 활용 가능
탐지 난이도중간매우 높음(수년간 미탐지 사례 다수)

핵심 차이: 기존 백도어는 "문을 열어두고 기다리는" 방식이지만, BPFdoor는 "문이 없는 것처럼 보이다가 특정 노크에만 반응하는" 방식이다. 이 때문에 포트 기반 점검·방화벽 정책·아웃바운드 트래픽 감시 등 전통적 탐지 수단이 모두 무력화된다.

Ⅲ. 나. BPFdoor의 위협 요소와 기업 시스템에 미치는 영향​

1. 위협 요소​

구분위협 요소상세 내용
탐지 회피스텔스 상주포트 미개방, 정상 프로세스 위장, 실행 파일 자기 삭제 후 메모리 상주
트래픽 은폐평시 통신 없음 → NDR·비콘 탐지 무력화, 소량 패킷만 사용
로그 최소화접속 흔적 최소, 커널 수준 동작으로 애플리케이션 로그에 미기록
방어 우회경계 보안 무력화방화벽·ACL이 차단해도 BPF 필터가 먼저 패킷 획득
네트워크 분리 우회내부망 감염 시 정상 트래픽에 섞인 매직 패킷으로 제어
지속성장기 잠복(Persistence)수개월~수년간 미탐지 상주 → APT 공격의 지속 거점
재감염부팅 스크립트·서비스 등록으로 재기동 후에도 유지
권한루트 권한 요구·획득Raw Socket 사용을 위해 root 권한 필요 → 감염 시 시스템 완전 장악
확산측면 이동 기반확보한 거점에서 내부 자격증명 탈취 후 다른 서버로 확산
대상리눅스 서버 집중웹서버·DB·미들웨어 등 핵심 기간 서버가 주 표적

   [피해 확산 경로]
   BPFdoor 상주 ─► 자격증명·키 탈취 ─► **측면 이동** ─► 핵심 시스템 장악
        │                                                      │
        ├─► 장기간 **데이터 지속 유출**(고객정보·영업비밀)      │

영향 영역내용
기밀성 침해고객 개인정보·금융정보·영업비밀의 장기간 지속적 유출 — 유출 시점·범위 특정 곤란
시스템 무결성루트 권한으로 설정 변경·추가 악성코드 설치, 시스템 신뢰성 자체 상실
서비스 가용성랜섬웨어 배포 거점화 시 전사 서비스 중단
법적·규제 리스크개인정보보호법상 유출 신고·통지 의무, 과징금(전체 매출 기준), 손해배상 소송
재무적 손실사고 대응·포렌식 비용, 시스템 전면 재구축 비용, 영업 손실
신뢰도 하락브랜드 이미지 훼손, 고객 이탈, 통신·금융은 사회적 파급 극대
복구 난이도감염 시점 특정이 어려워 백업본까지 오염 가능 → 안전한 복구 지점 판단 곤란
공급망 위험협력사·고객사로 침해 확산 가능

Ⅳ. 다. BPFdoor 위협에 대응하기 위한 기술적·관리적 방안​

1. 기술적 대응 방안​

계층대응 방안상세 내용
탐지 — 호스트BPF 사용 프로세스 점검ss -0pb, /proc/net/packet 확인으로 Raw Socket·BPF 필터를 부착한 비정상 프로세스 식별 — 가장 직접적인 탐지법
프로세스 무결성 검증실행 파일 경로와 프로세스명 불일치 확인(ls -l /proc/[pid]/exe), 삭제된 바이너리로 실행 중인 프로세스(deleted) 탐지
EDR 행위 기반 탐지Raw Socket 생성, SO_ATTACH_FILTER 시스템 콜, iptables 동적 변경, 예기치 않은 셸 생성 등 행위 패턴 탐지
파일 무결성 모니터링FIM으로 시스템 디렉터리·기동 스크립트 변경 감시
메모리 포렌식디스크에 파일이 없으므로 메모리 덤프 분석이 필수(Volatility 등)
탐지 — 네트워크이상 패킷 탐지매직 패킷 시그니처(공개된 IoC) 기반 IDS/IPS 룰 적용
트래픽 전량 분석방화벽이 드롭한 패킷도 서버에 도달하므로 네트워크 탭 기반 전수 분석(NDR) 필요
아웃바운드 통제서버의 외부 접속을 화이트리스트 방식으로 제한 — 리버스 셸 차단
차단·완화최소 권한·권한 분리불필요한 root 실행 제거, CAP_NET_RAW 권한 제한(Raw Socket 생성 차단)
커널 보안 강화SELinux·AppArmor 강제 접근통제(MAC) 적용, seccomp로 시스템 콜 제한
취약점 관리초기 침투 경로 차단 — 인터넷 노출 서버·미들웨어 신속 패치, 불필요 서비스 제거
네트워크 분리마이크로 세그멘테이션으로 서버 간 통신 최소화 → 측면 이동 차단
인증 강화SSH 키 기반 인증·MFA, 관리자 접근은 PAM(특권계정 관리) 경유
가시성중앙 로그 수집서버 로컬 로그는 삭제 가능 → 원격 SIEM으로 실시간 전송·보존
시스템 콜 감사auditd로 Raw Socket·권한 상승 관련 시스템 콜 기록
정기 스캔침해지표(IoC) 기반 전 서버 정기 점검, YARA 룰 적용

2. 관리적 대응 방안​

구분대응 방안상세 내용
거버넌스침해 가정(Assume Breach) 전략"이미 침투당했다"는 전제로 정기적 위협 헌팅(Threat Hunting) 수행
보안 정책·기준서버 보안 기준(CIS Benchmark) 수립, root 사용 통제 정책
자산·구성 관리자산 현황 관리서버·서비스 인벤토리 정확성 확보, 인터넷 노출 자산 상시 식별(EASM)
정상 상태 기준선(Baseline)정상 프로세스·포트·통신 목록을 문서화하여 이상 탐지의 기준 확보
취약점·패치패치 관리 프로세스정기·긴급 패치 절차, 패치 이행 검증
정기 진단모의해킹·취약점 진단, 침해사고 예방 점검
사고 대응IR 플레이북 정비BPFdoor 유형별 대응 절차(격리·메모리 확보·포렌식) 사전 수립
증거 보존 원칙 교육감염 의심 시 재부팅·전원 차단 금지(메모리 증거 소실) → 네트워크 격리 우선
신고 체계KISA·수사기관 신고 절차, 개인정보 유출 시 법정 통지
정기 훈련침해사고 대응 모의훈련(Table-top·실전), 위협 헌팅 훈련
정보 공유위협 인텔리전스최신 IoC·TTP(MITRE ATT&CK) 공유 채널 참여, 업계 공동 대응
인력·조직전문 인력리눅스·커널 수준 분석 역량 확보, 외부 전문기관 협력 체계
협력사 관리위탁 운영 서버의 보안 요구사항 계약 반영, 접근 통제
복구 대비백업 무결성오프라인·불변(Immutable) 백업, 감염 이전 시점 복구 가능성 확보
재구축 기준루트 권한 침해 시 패치가 아닌 시스템 재설치(Rebuild) 를 원칙으로 규정

3. 단계별 대응 로드맵​

   [즉시]   IoC 기반 전 서버 스캔 → BPF 부착 프로세스·삭제된 바이너리 실행 점검
      ▼
   [단기]   EDR 배포, 중앙 로그 수집, 아웃바운드 화이트리스트, 노출 자산 패치
      ▼
   [중기]   마이크로 세그멘테이션, MAC(SELinux) 적용, CAP_NET_RAW 통제, PAM 도입
      ▼
   [지속]   정기 위협 헌팅, 침해 모의훈련, 위협 인텔리전스 연계, 기준선 갱신

Ⅴ. 결론​

BPFdoor는 커널의 정상 기능(BPF)을 악용하여 "열린 포트도, 상시 트래픽도 없는" 상태로 잠복한다는 점에서, 포트 점검·방화벽 정책·비콘 탐지 등 전통적 방어 수단이 구조적으로 무력화되는 위협이다. 수년간 탐지되지 않은 사례들이 이를 입증한다.

따라서 대응의 핵심은 시그니처 탐지가 아니라 ① 호스트 수준의 행위 가시성 확보(EDR·Raw Socket/BPF 부착 프로세스 점검), ② 정상 상태 기준선과의 차이 탐지, ③ 아웃바운드 통제와 마이크로 세그멘테이션을 통한 활용 경로 차단에 있다.

아울러 관리적으로는 "침투는 이미 일어났다"는 전제하에 정기적 위협 헌팅을 제도화하고, 감염 의심 시 재부팅이 아닌 메모리 증거 확보 우선 원칙을 교육하며, 루트 권한 침해 시에는 시스템 재구축을 원칙으로 규정해야 한다. 궁극적으로 이러한 커널 수준 위협에 대한 대비는 가시성(Observability) 확보에 대한 사전 투자로만 가능하다.

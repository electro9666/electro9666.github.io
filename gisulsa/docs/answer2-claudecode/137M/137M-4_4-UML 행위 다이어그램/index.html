UML 행위 다이어그램 — 활동·상태·유스케이스 다이어그램

Ⅰ. 개요​

1. UML과 다이어그램 분류​

UML(Unified Modeling Language) 은 객체지향 시스템의 분석·설계 결과를 표현하는 표준 모델링 언어이며, 다이어그램은 구조(Structure) 다이어그램과 행위(Behavior) 다이어그램으로 구분된다.

                      [UML 2.x 다이어그램]
        ┌──────────────────┴──────────────────┐
   **구조 다이어그램**                  **행위 다이어그램**
   클래스, 객체, 컴포넌트,          **유스케이스**, **활동**, **상태**,
   배치, 패키지, 복합구조            시퀀스, 커뮤니케이션, 타이밍
   ▲ 정적인 구성·관계                ▲ 동적인 흐름·동작·상호작용

2. 세 다이어그램의 관점 차이​

다이어그램핵심 질문관점
유스케이스시스템이 사용자에게 무엇을 제공하는가(What)외부·요구사항 관점
활동업무·처리가 어떤 순서와 흐름으로 진행되는가(How-Flow)프로세스 관점
상태하나의 객체가 사건에 따라 어떻게 변화하는가(How-State)객체 생명주기 관점

Ⅱ. 활동 다이어그램(Activity Diagram)​

1. 개념​

활동 다이어그램은 업무 프로세스나 알고리즘의 처리 흐름을 순서대로 표현하는 다이어그램으로, 순서도(Flowchart)를 객체지향적으로 확장한 형태이다. 병렬 처리와 담당자(책임) 구분을 표현할 수 있다는 점이 순서도와의 결정적 차이이다.

2. 주요 구성요소​

표기요소의미
●시작 노드(Initial)흐름의 시작
◉종료 노드(Final)흐름의 종료
▭(둥근 사각형)액션/활동(Action)수행되는 작업
◇결정/병합(Decision/Merge)조건 분기(가드 조건 [조건]) / 분기 통합
▬(굵은 가로선)포크/조인(Fork/Join)병렬 흐름 분기 / 동기화 대기
→제어 흐름(Control Flow)흐름의 방향
▯ (세로 구역)스윔레인(Swimlane / Partition)담당 주체(사람·부서·시스템) 구분
▭(각진)객체 노드(Object)흐름 간 전달되는 데이터

3. 표기 예시 — 온라인 주문 처리​

   ┌── **고객** ──┬── **주문시스템** ──┬── **결제/물류** ──┐
   │              │                    │                  │   ← 스윔레인
   │  ●           │                    │                  │
   │  ↓           │                    │                  │
   │ [상품 선택]  │                    │                  │
   │  ↓           │                    │                  │
   │ [주문 요청] ─┼─► [재고 확인]      │                  │
   │              │      ↓             │                  │
   │              │     ◇ [재고 있음?] │                  │
   │              │    ╱ 아니오   예 ╲ │                  │
   │              │ [품절 안내]      ▬━━━━━━━━━━━━━━━━━━▬ │ ← **포크(병렬 시작)**
   │              │      ↓            ↓                 ↓ │
   │              │      │        [결제 처리]     [배송 준비]│  ← 동시 수행
   │              │      │            ↓                 ↓ │
   │              │      │           ▬━━━━━━━━━━━━━━━━━━▬ │ ← **조인(동기화)**
   │              │      │                    ↓           │
   │  [알림 수신] ◄──────┴──────────── [주문 완료 통지]   │
   │  ↓                                                   │
   │  ◉                                                   │
   └──────────────┴────────────────────┴──────────────────┘

4. 특징 및 활용​

구분내용
장점병렬 처리(Fork/Join) 표현 가능, 스윔레인으로 책임 소재 명확화, 비개발자도 이해 용이
활용업무 프로세스 모델링(BPM), 유스케이스의 상세 시나리오 기술, 복잡한 알고리즘 설계, 워크플로 정의
유의점지나치게 상세하면 가독성 저하 → 추상화 수준 일관성 유지

Ⅲ. 상태 다이어그램(State Diagram / State Machine Diagram)​

1. 개념​

상태 다이어그램은 하나의 객체(또는 시스템)가 생애주기 동안 가질 수 있는 상태들과, 사건(Event)에 의해 상태가 전이(Transition)되는 과정을 표현하는 다이어그램이다. 하나의 객체에 초점을 맞춘다는 점이 활동 다이어그램과 근본적으로 다르다.

2. 주요 구성요소​

표기요소의미
● →시작 의사상태객체 생성 시점
▭(둥근)상태(State)객체가 특정 조건을 만족하며 머무는 구간
→전이(Transition)상태 간 이동
이벤트 [가드] / 액션전이 레이블사건 / 조건 / 수행 동작
entry/do/exit내부 활동진입 시·머무는 동안·이탈 시 수행 동작
◎종료 상태객체 소멸
▭ 내부 중첩복합 상태(Composite)상태 내부에 하위 상태 포함, 이력(History) 상태

3. 표기 예시 — 주문(Order) 객체의 생명주기​

    ●
    ↓ 주문 생성
 ┌──────────────┐  결제 요청       ┌──────────────┐
 │ **주문 접수** │ ───────────────► │ **결제 대기** │
 │ entry/재고확인│                  │ do/타이머 감시│
 └──────┬───────┘                  └───┬──────┬───┘
        │ 취소                          │      │ 결제 실패 [재시도<3]
        │                    결제 승인  │      └──────┐
        │                               ▼             │(자기 전이)
        │                        ┌──────────────┐◄────┘
        │                        │ **배송 준비** │
        │                        └──────┬───────┘
        │                               │ 출고
        │                               ▼
        │                        ┌──────────────┐  수령 확인   ┌──────────┐
        │                        │ **배송 중**   │ ───────────► │**배송완료**│
        │                        └──────────────┘              └────┬─────┘
        ▼                                                            │
 ┌──────────────┐                                                    ▼
 │ **주문 취소** │ ─────────────────────────────────────────────────► ◎
 └──────────────┘
   ※ 전이 레이블 형식 : **이벤트[가드조건] / 액션**
     예) 결제실패[재시도횟수 < 3] / 재결제요청()

4. 특징 및 활용​

구분내용
장점객체의 모든 상태와 전이 조건을 빠짐없이 식별 → 누락된 예외 상황 발견, 검증·테스트 케이스 도출 용이(상태전이 테스트)
활용상태 의존적 객체 설계(주문·결제·문서 결재), 실시간·임베디드 시스템 제어 로직, 프로토콜 설계(TCP 상태 기계), 워크플로 엔진
유의점상태 폭발(State Explosion) 주의 → 복합 상태로 계층화하여 관리

Ⅳ. 유스케이스 다이어그램(Use-Case Diagram)​

1. 개념​

유스케이스 다이어그램은 시스템이 사용자(액터)에게 제공하는 기능(유스케이스)과 그 관계를 외부 관점에서 표현하는 다이어그램이다. 시스템 내부 구현이 아닌 "시스템 경계 밖에서 본 기능" 을 다루므로, 요구사항 정의와 이해관계자 합의의 핵심 도구로 사용된다.

2. 주요 구성요소​

표기요소의미
사람 모양액터(Actor)시스템과 상호작용하는 외부 주체(사용자·외부 시스템·시간)
타원유스케이스(Use Case)시스템이 제공하는 사용자 관점의 기능 단위
사각형시스템 경계(Boundary)시스템의 범위
실선연관(Association)액터와 유스케이스의 상호작용
<<include>> 점선 화살표포함 관계유스케이스가 반드시 다른 유스케이스를 포함(공통 기능 재사용)
<<extend>> 점선 화살표확장 관계특정 조건에서 선택적으로 기능 확장
실선 삼각형 화살표일반화(Generalization)액터·유스케이스 간 상속 관계

3. 표기 예시 — 온라인 쇼핑몰​

   ┌──────────────── **시스템 경계 : 온라인 쇼핑몰** ────────────────┐
   │                                                                 │
   │      ( 상품 검색 )                    ( 재고 확인 )              │
   │           ▲                                ▲                    │
   │           │                                ┊ **<<include>>**    │
   │           │                                ┊                    │
   │           │                          ( 주문하기 ) ┄┄**<<include>>**┄► ( 결제하기 )
   │           │                                ▲                    │       ▲
   │           │                                ┊ **<<extend>>**     │       ┊
   │           │                        ( 쿠폰 적용 )                │       ┊ 연동
   │           │                                                     │       ┊
   │      ( 리뷰 작성 )                   ( 배송 조회 )               │       ┊
   │           ▲                                ▲                    │       ┊
   └───────────┼────────────────────────────────┼────────────────────┘       ┊
               │                                │                            ┊
            ┌──┴──┐                          ┌──┴──┐                    ┌────┴────┐
            │ 고객 │                          │ 고객 │                    │**결제 PG**│
            │(액터)│                          │      │                    │ (외부시스템)│
            └─────┘                          └─────┘                    └─────────┘
                △ (일반화)
            ┌───┴────┐
            │ VIP 고객 │  ← 고객의 모든 기능 + 추가 기능 상속
            └────────┘

   ※ **<<include>>** : 주문하기는 **항상** 결제하기·재고확인을 포함(필수)
   ※ **<<extend>>**  : 쿠폰이 있는 경우에만 선택적으로 확장(옵션)

4. 특징 및 활용​

구분내용
장점비전문가도 이해 가능 → 고객·현업과의 요구사항 합의에 최적, 시스템 범위(Scope) 명확화, 개발 우선순위·일정 산정 근거
활용요구사항 도출·정의, 인수 테스트 시나리오 도출, 프로젝트 범위 관리(WBS 연계)
유의점다이어그램만으로는 부족 → 반드시 유스케이스 명세서(사전조건·기본흐름·대안흐름·사후조건)를 함께 작성. <<include>>/<<extend>> 남용 시 오히려 가독성 저하

Ⅴ. 세 다이어그램의 비교 및 상호 관계​

1. 비교표​

비교 기준유스케이스 다이어그램활동 다이어그램상태 다이어그램
목적시스템 기능·범위 정의처리 흐름·프로세스 표현객체의 상태 변화 표현
관점외부(사용자) 관점프로세스(흐름) 관점단일 객체 관점
중심 개념액터와 기능액션과 흐름상태와 이벤트
초점 대상시스템 전체업무·시나리오하나의 객체
시간 흐름표현하지 않음순차적 흐름 표현사건 기반 전이
병렬 표현불가가능(Fork/Join)가능(직교 상태)
조건 분기표현하지 않음Decision 노드가드 조건
주 사용 단계요구사항 분석분석·설계설계·구현
주요 독자고객·현업·기획자현업·분석가·개발자개발자
대표 활용범위 합의, 인수 테스트업무 흐름 정의, 워크플로상태 기반 로직, 상태전이 테스트

2. 상호 보완 관계​

   [개발 흐름에서의 연계]

   **유스케이스 다이어그램** ── "주문하기 기능이 필요하다"(무엇을)
            │  각 유스케이스를 상세화
            ▼
   **활동 다이어그램** ────── "주문은 재고확인 → 결제 → 배송준비 순으로 진행"(어떻게 흐르는가)
            │  흐름에 등장하는 핵심 객체를 식별
            ▼
   **상태 다이어그램** ────── "주문 객체는 접수 → 결제대기 → 배송중 → 완료로 변화"(무엇이 변하는가)
            │
            ▼
   클래스 다이어그램 · 시퀀스 다이어그램 → 구현

세 다이어그램은 경쟁 관계가 아니라 추상화 수준과 관점이 다른 상호 보완 도구이다. 유스케이스로 범위를 합의하고, 활동 다이어그램으로 처리 절차를 구체화하며, 상태 다이어그램으로 핵심 객체의 생명주기를 정밀 정의하는 흐름이 일반적이다.

Ⅵ. 결론​

UML 행위 다이어그램 중 유스케이스는 "시스템이 무엇을 제공하는가", 활동은 "업무가 어떻게 흘러가는가", 상태는 "객체가 어떻게 변화하는가" 를 각각 표현하며, 서로 다른 이해관계자와 개발 단계를 지원한다.

실무 적용 시에는 ① 모든 다이어그램을 작성하는 것이 목적이 아니라 필요한 관점만 선별하고, ② 유스케이스는 반드시 명세서와 함께 작성하며, ③ 상태 의존적 로직(주문·결재·승인)이 있는 객체에는 상태 다이어그램을 필수 적용하여 예외 상황 누락을 방지해야 한다.

특히 상태 다이어그램은 상태전이 테스트 케이스 도출의 직접적 근거가 되고, 유스케이스는 인수 테스트 시나리오의 기준이 되므로, 설계 산출물이 곧 테스트 자산으로 연결되도록 관리하는 것이 품질 확보에 효과적이다. 다만 문서를 위한 모델링이 되지 않도록, 코드와 모델의 동기화 가능성을 고려한 적정 수준의 상세화가 중요하다.

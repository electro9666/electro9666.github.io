데이터베이스 트랜잭션 격리 수준(Transaction Isolation Level)

Ⅰ. 개요​

1. 격리 수준의 개념​

트랜잭션 격리 수준은 ACID 속성 중 격리성(Isolation) 을 어느 정도로 보장할 것인지를 규정하는 단계이다. 동시에 실행되는 트랜잭션들이 서로의 중간 결과를 얼마나 볼 수 있는지를 결정하며, 일관성과 동시성(성능)의 Trade-off를 조절하는 수단이다.

2. 필요성​

   [격리 수준의 딜레마]
   완전 격리(직렬 실행) ◄──────────────────► 완전 동시 실행
   데이터 정합성 최상                        성능·처리량 최상
   처리량 급감                               **이상 현상(Anomaly) 발생**
                    └─► 격리 수준으로 **균형점 선택**

Ⅱ. 가. 트랜잭션 격리 수준 4가지 (ANSI/ISO SQL 표준)​

   [격리 수준 — 낮음 → 높음]
   ① Read Uncommitted ─► ② Read Committed ─► ③ Repeatable Read ─► ④ Serializable
   ◄──── 동시성(성능) 높음 ────                  ──── 데이터 일관성 높음 ────►
   ◄──── 이상 현상 많음 ──────                  ──── 잠금·오버헤드 큼 ─────►

1. ① Read Uncommitted (커밋되지 않은 읽기)​

항목내용
동작다른 트랜잭션이 커밋하지 않은 변경 데이터까지 읽음. 읽기 시 공유 잠금을 걸지 않음
발생 이상Dirty Read, Non-Repeatable Read, Phantom Read 모두 발생
장점잠금 대기가 없어 동시성 최대
단점롤백된 데이터를 읽을 수 있어 데이터 정합성 보장 불가
활용대략적 통계·모니터링 등 정확도가 중요하지 않은 조회(실무에서 거의 사용하지 않음)

2. ② Read Committed (커밋된 읽기)​

항목내용
동작커밋이 완료된 데이터만 읽음. 읽기 시점마다 최신 커밋 데이터를 조회
구현 방식잠금 기반(읽기 시 공유 잠금 후 즉시 해제) 또는 MVCC 기반(문장 단위 스냅샷)
발생 이상Dirty Read 방지 / Non-Repeatable Read, Phantom Read 발생
장점정합성과 동시성의 실용적 균형
활용Oracle·PostgreSQL·SQL Server의 기본 격리 수준, 대부분의 OLTP 업무

3. ③ Repeatable Read (반복 가능한 읽기)​

항목내용
동작트랜잭션 시작 시점의 스냅샷을 유지 → 같은 행을 여러 번 읽어도 항상 동일한 값
구현 방식읽은 행에 대한 공유 잠금을 트랜잭션 종료까지 유지, 또는 MVCC(트랜잭션 단위 스냅샷)
발생 이상Dirty Read·Non-Repeatable Read 방지 / 표준상 Phantom Read 발생 가능
특이사항MySQL InnoDB의 기본 수준. 넥스트 키 락(Next-Key Lock) 으로 팬텀까지 상당 부분 방지
활용동일 데이터를 반복 조회하며 집계·검증하는 업무

4. ④ Serializable (직렬화 가능)​

항목내용
동작트랜잭션들이 순차적으로 실행된 것과 동일한 결과를 보장하는 최고 수준
구현 방식범위 잠금(Range Lock)·테이블 잠금, 또는 SSI(Serializable Snapshot Isolation) — 충돌 감지 시 트랜잭션 중단
발생 이상모든 이상 현상 방지
단점잠금 경합·교착상태 급증, 처리량 대폭 저하, SSI에서는 잦은 재시도 필요
활용금융 정산·재고 차감 등 절대적 정합성이 요구되는 소수 트랜잭션

5. 격리 수준별 비교​

격리 수준Dirty ReadNon-Repeatable ReadPhantom Read동시성대표 채택
Read Uncommitted발생발생발생최상(거의 미사용)
Read Committed방지발생발생상Oracle, PostgreSQL, SQL Server 기본
Repeatable Read방지방지발생(표준 기준)중MySQL InnoDB 기본
Serializable방지방지방지최하특수 업무

Ⅲ. 나. 격리 수준에 따라 발생할 수 있는 이상 현상​

1. Dirty Read (오손 읽기)​

  • 정의: 다른 트랜잭션이 아직 커밋하지 않은 변경 데이터를 읽는 현상. 해당 트랜잭션이 롤백되면 읽은 값은 실제로 존재한 적 없는 데이터가 된다.
   T1                              T2
   ──────────────────────────      ──────────────────────────
   UPDATE 계좌 SET 잔액=5000
   WHERE id=1;  (커밋 전)
                                   SELECT 잔액 FROM 계좌
                                   WHERE id=1;  → **5000 읽음** ✗
   **ROLLBACK;**  (잔액 원복 1000)
                                   → T2는 존재하지 않는 값 5000으로
                                     업무 처리 = **정합성 붕괴**
  • 방지 수준: Read Committed 이상

2. Non-Repeatable Read (반복 불가능한 읽기)​

  • 정의: 한 트랜잭션 내에서 같은 행을 두 번 조회했을 때 값이 달라지는 현상. 그 사이 다른 트랜잭션이 UPDATE·DELETE 후 커밋했기 때문이다.
   T1                                    T2
   ──────────────────────────────        ─────────────────────────
   SELECT 잔액 FROM 계좌 WHERE id=1;
   → **1000**
                                         UPDATE 계좌 SET 잔액=2000
                                         WHERE id=1;
                                         **COMMIT;**
   SELECT 잔액 FROM 계좌 WHERE id=1;
   → **2000** ✗ (같은 트랜잭션 내에서 값이 변함)
   ⇒ 조회 값 기준으로 계산한 중간 결과가 **일관되지 않음**
  • 방지 수준: Repeatable Read 이상

3. Phantom Read (유령 읽기)​

  • 정의: 한 트랜잭션 내에서 동일한 조건으로 범위 조회를 두 번 했을 때, 처음에 없던 행(유령 행)이 나타나거나 사라지는 현상. 다른 트랜잭션의 INSERT·DELETE 가 원인이다.
   T1                                        T2
   ──────────────────────────────────        ────────────────────────────
   SELECT COUNT(*) FROM 주문
   WHERE 금액 > 10000;  → **10건**
                                             INSERT INTO 주문
                                             VALUES(..., 15000);
                                             **COMMIT;**
   SELECT COUNT(*) FROM 주문
   WHERE 금액 > 10000;  → **11건** ✗ (없던 행 출현)
   ⇒ Non-Repeatable Read는 **기존 행의 값 변경**,
      Phantom Read는 **행의 개수(집합) 변경**이라는 점에서 구별
  • 방지 수준: Serializable (MySQL InnoDB는 Repeatable Read에서 Next-Key Lock으로 대부분 방지)

4. 기타 이상 현상 (표준 외 확장)​

이상 현상내용
Lost Update(갱신 손실)두 트랜잭션이 같은 행을 읽고 각각 갱신 → 먼저 반영된 갱신이 덮어써져 소실. SELECT FOR UPDATE(비관적 잠금) 또는 버전 컬럼 기반 낙관적 잠금으로 방지
Write Skew(쓰기 왜곡)스냅샷 격리에서 두 트랜잭션이 서로 다른 행을 읽고 각각 갱신했으나, 결과적으로 제약조건 위반(예: 당직자 2명 중 각각 1명씩 동시 취소 → 당직자 0명). Serializable(SSI) 로만 방지
Read Skew연관된 여러 행을 읽는 도중 다른 트랜잭션이 갱신 → 서로 모순된 데이터 조합 조회

5. 이상 현상 종합 비교​

이상 현상원인 연산대상방지 최소 수준
Dirty Read미커밋 UPDATE단일 행Read Committed
Non-Repeatable Read커밋된 UPDATE·DELETE단일 행의 값Repeatable Read
Phantom Read커밋된 INSERT·DELETE행의 집합(범위)Serializable
Lost Update동시 UPDATE단일 행명시적 잠금 필요
Write Skew교차 조건 UPDATE여러 행의 제약Serializable(SSI)

Ⅳ. 실무 적용 시 고려사항​

고려사항내용
기본 수준 유지대부분의 OLTP는 Read Committed로 충분 — 무조건 높은 격리 수준은 성능 저하만 초래
선택적 강화정합성이 필수인 특정 트랜잭션에만 SELECT FOR UPDATE·Serializable 적용
MVCC 이해Oracle·PostgreSQL·InnoDB는 잠금 대신 다중 버전(Undo/Snapshot) 사용 → 읽기가 쓰기를 막지 않으나 Undo 영역 부담·롱 트랜잭션 주의
트랜잭션 길이 최소화긴 트랜잭션은 잠금 유지·스냅샷 유지 비용 증가 → 교착상태·성능 저하의 주원인
낙관적 잠금 활용웹 환경에서는 버전 컬럼 기반 낙관적 잠금으로 Lost Update 방지가 효율적
분산 환경MSA·분산 DB에서는 격리 수준만으로 부족 → Saga·보상 트랜잭션·최종적 일관성 설계 병행
교착상태 대응잠금 획득 순서 통일, 타임아웃, 재시도 로직

Ⅴ. 결론​

트랜잭션 격리 수준은 데이터 일관성과 동시성 성능 사이의 균형점을 선택하는 설계 결정이며, 격리 수준이 높아질수록 이상 현상은 줄지만 잠금 경합과 처리량 저하라는 비용이 발생한다.

따라서 실무 원칙은 ① 시스템 전체는 Read Committed(또는 Repeatable Read) 기본값으로 운영하고, ② 정합성이 절대적인 소수 트랜잭션에만 명시적 잠금이나 Serializable을 선별 적용하는 것이다. 아울러 표준 격리 수준만으로는 Lost Update와 Write Skew를 방지할 수 없다는 점을 인지하고, 애플리케이션 차원의 낙관적·비관적 잠금 설계를 병행해야 한다. 궁극적으로 정합성 문제의 상당수는 격리 수준 조정보다 트랜잭션 범위를 짧고 명확하게 설계하는 것으로 예방된다.

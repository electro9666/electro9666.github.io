통신 프로토콜 — 오류 제어·혼잡 제어, 슬라이딩 윈도우, 설계 시 고려사항

Ⅰ. 개요​

1. 프로토콜의 개념과 3요소​

통신 프로토콜은 서로 다른 시스템 간 데이터를 정확하게 교환하기 위한 약속과 규칙의 집합이며, 구문(Syntax) — 의미(Semantics) — 순서(Timing) 의 3요소로 구성된다.

2. 전송 제어 기법의 위치​

   [신뢰성 있는 전송을 위한 제어 기법]
   ┌─ **오류 제어(Error Control)**  : 데이터 손상·손실 대응      → 데이터링크·전송계층
   ├─ **흐름 제어(Flow Control)**   : **수신 측** 처리 능력 초과 방지
   └─ **혼잡 제어(Congestion Ctrl)**: **네트워크(중간 노드)** 과부하 방지 → 전송계층

Ⅱ. 가. 오류 제어와 혼잡 제어​

1. 오류 제어(Error Control)​

  • 개념: 전송 중 잡음·간섭으로 발생한 비트 오류나 프레임 손실을 검출하고 정정·재전송하여 데이터의 정확성을 보장하는 기법.
                    [오류 제어]
            ┌───────────┴────────────┐
     **후진 오류정정(BEC)**      **전진 오류정정(FEC)**
        = **ARQ**(검출+재전송)      = 수신 측 자체 정정
     정지-대기 / Go-Back-N /      해밍 / 리드-솔로몬 /
     선택적 재전송(SR) / HARQ     LDPC / 터보코드
     ▲ 역채널 필요, 지연 가변      ▲ 역채널 불필요, 대역 오버헤드
구성 요소내용
오류 검출패리티, 체크섬(TCP/IP), CRC(버스트 오류에 강함, 이더넷·HDLC)
오류 정정(FEC)해밍코드(단일 비트 정정), 리드-솔로몬(버스트), LDPC·터보코드(5G)
재전송(ARQ)ACK/NAK와 타이머 기반 재전송, 순서번호로 중복 식별
확인응답개별 ACK / 누적 ACK / 선택적 확인응답(SACK)

2. 혼잡 제어(Congestion Control)​

  • 개념: 네트워크 내부(라우터·링크)의 처리 능력을 초과하는 트래픽으로 인한 패킷 손실과 성능 저하를 방지하기 위해, 송신 측이 전송률을 조절하는 기법.
   [혼잡 붕괴(Congestion Collapse)]
   트래픽 ↑ → 라우터 큐 포화 → 패킷 폐기 → **재전송 증가** → 트래픽 ↑↑
   ⇒ 처리량(Throughput)이 오히려 **급락하는 악순환**

   [TCP 혼잡 제어 4단계]
   cwnd
    │        ┌ 혼잡 회피(선형 증가 +1 MSS/RTT)
    │       /          ╲ 3 중복 ACK → **빠른 회복**(cwnd 절반)
    │      /            ╲___/‾‾╲
    │     / ← ssthresh
    │    /  **느린 시작**(지수 증가 ×2)
    │   /                    ╲ 타임아웃 → cwnd = 1 (재시작)
    └──────────────────────────────► 시간
단계내용
① 느린 시작(Slow Start)cwnd를 1부터 RTT마다 2배씩 지수 증가, ssthresh 도달 시 전환
② 혼잡 회피(Congestion Avoidance)RTT마다 1 MSS씩 선형 증가(AIMD의 증가 국면)
③ 빠른 재전송(Fast Retransmit)3개의 중복 ACK 수신 시 타임아웃 대기 없이 즉시 재전송
④ 빠른 회복(Fast Recovery)느린 시작으로 되돌아가지 않고 cwnd를 절반으로 줄여 혼잡 회피부터 재개
  • 알고리즘 발전: Tahoe → Reno → NewReno → CUBIC(리눅스 기본, 고대역폭 최적) → BBR(손실이 아닌 대역폭·RTT 측정 기반, 무선·장거리에 유리)
  • 네트워크 지원: RED(임의 조기 폐기), ECN(폐기 대신 혼잡 표시), 트래픽 셰이핑

3. 오류 제어 · 흐름 제어 · 혼잡 제어 비교​

비교 기준오류 제어흐름 제어혼잡 제어
문제 원인전송 매체의 잡음·간섭수신 측 버퍼 부족네트워크 내부 과부하
목적데이터 정확성 보장수신 측 오버플로 방지네트워크 붕괴 방지·공정성
제어 주체송·수신 양측수신 측이 통보송신 측이 추정
판단 근거CRC·체크섬, ACK/타임아웃수신 윈도우(rwnd) 광고패킷 손실·RTT 변화(암묵적 신호)
조절 변수재전송 여부rwndcwnd(혼잡 윈도우)
계층데이터링크·전송데이터링크·전송주로 전송계층
상호 관계—실제 전송량 = min(rwnd, cwnd)—

Ⅲ. 나. 슬라이딩 윈도우(Sliding Window) 기법​

1. 개념​

슬라이딩 윈도우는 확인응답(ACK)을 기다리지 않고 윈도우 크기만큼의 프레임을 연속 전송하고, ACK을 받은 만큼 윈도우를 오른쪽으로 이동(Slide) 시키며 전송을 이어가는 기법이다. 흐름 제어와 오류 제어를 동시에 수행하며, 정지-대기 방식의 낮은 채널 이용률 문제를 해결한다.

2. 동작 원리​

   [송신 윈도우 — 크기 N=4]
   ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐
   │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │ 9 │
   └───┴───┴───┴───┴───┴───┴───┴───┴───┘
     ▲ ACK 완료   ▲──── 윈도우(전송 가능) ────▲  ▲ 전송 불가(대기)
     (송신 버퍼 해제)

   ACK 2 수신 시 → 윈도우가 **오른쪽으로 1칸 이동**
   ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐
   │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │ 9 │
   └───┴───┴───┴───┴───┴───┴───┴───┴───┘
             ▲──── 새 윈도우 ────▲   ← 5번 프레임 신규 전송 가능

   ※ 순서번호 m비트 → 송신 윈도우 최대 크기 = **2^m − 1**(GBN), **2^(m−1)**(SR)
구성 요소내용
송신 윈도우전송했으나 ACK 미수신 프레임 + 전송 가능 프레임의 범위
수신 윈도우수신 가능한 프레임 범위(GBN=1, SR=N)
윈도우 크기 결정min(수신 윈도우 rwnd, 혼잡 윈도우 cwnd) — TCP에서는 동적으로 변동
슬라이딩 조건ACK 수신 시 하한 이동, 새 프레임 전송 시 상한 이동

3. 적용 방식 비교​

비교 기준Go-Back-NSelective Repeat
수신 윈도우1(순서대로만 수용)N(순서 어긋나도 버퍼링)
재전송 범위오류 프레임 이후 전부오류 프레임만
ACK 방식누적 ACK개별 ACK
수신 버퍼1개N개(재정렬 필요)
효율오류율 높으면 급락오류율 높아도 유지
구현 복잡도낮음높음

4. 성능 및 실무 이슈​

   [채널 이용률]  U = N / (1 + 2a),  a = 전파지연 / 전송시간
   ⇒ **N ≥ 1 + 2a** 이면 이용률 100% (파이프라인 완전 충족)
   ⇒ 적정 윈도우 크기 ≈ **BDP(대역폭 × 왕복지연)**
      예) 100Mbps × 100ms = 1.25MB ⇒ 기본 TCP 윈도우(64KB)로는 부족
          → **Window Scaling 옵션(RFC 7323)** 으로 최대 1GB까지 확장
이슈내용
BDP 미충족장거리·고대역폭(LFN)에서 윈도우가 작으면 대역폭 낭비 → Window Scaling 필수
Silly Window Syndrome소량 데이터 반복 전송으로 효율 저하 → Nagle 알고리즘(송신), Clark 해법(수신)
Head-of-Line Blocking앞선 손실 패킷이 뒤의 정상 데이터 전달을 막음 → QUIC의 스트림 다중화로 해소
SACK선택적 확인응답으로 GBN의 불필요 재전송 완화

Ⅳ. 다. 프로토콜 설계 시 고려사항​

1. 기능적 고려사항​

구분고려사항내용
구문(Syntax)메시지 형식·인코딩헤더·페이로드 구조, 바이트 정렬(Endian), 텍스트 vs 바이너리(효율 vs 가독성), 고정 vs 가변 길이
의미(Semantics)제어 정보·동작 정의명령·응답 코드 체계, 오류 코드, 상태 정의
순서(Timing)상태 전이·타이밍상태 기계(FSM) 정의, 타임아웃·재시도 정책, 세션 수립·해제 절차
연결 방식연결형/비연결형신뢰성 필요 시 연결형(TCP), 실시간·저지연은 비연결형(UDP)
주소·식별주소 체계엔드포인트 식별, 다중화(포트·스트림 ID)

2. 품질·비기능 고려사항​

구분고려사항내용
신뢰성오류·손실 대응검출(CRC)·재전송(ARQ)·정정(FEC) 조합, 멱등성(Idempotency) 보장
성능·효율오버헤드 최소화헤더 크기(헤더 압축), 불필요 왕복(RTT) 제거(0-RTT 연결), 배치·파이프라이닝
흐름·혼잡 제어과부하 방지윈도우 기반 제어, 공정성(Fairness) 확보, 백프레셔
확장성미래 대비버전 필드 포함, 예약(Reserved) 필드, TLV(Type-Length-Value) 구조로 하위 호환성 유지
보안기밀성·무결성·인증설계 단계부터 암호화(TLS) 통합(사후 추가는 취약), 재전송 공격 방지(Nonce·타임스탬프), 인증·권한
상호운용성표준 준수국제 표준(IETF RFC·ITU) 기반, 명확한 명세와 참조 구현, 관용 원칙(보낼 때는 엄격히, 받을 때는 관대하게)
단순성복잡도 관리기능 최소화(KISS), 계층 분리, 상태 최소화(Stateless 선호) — 확장·복구 용이
관측성운영 지원로깅·통계 필드, 진단 메시지, 버전·기능 협상(Negotiation)
자원 제약환경 적합성IoT·저전력 환경은 경량 프로토콜(MQTT·CoAP), 대역폭 제한 고려
NAT·방화벽배포 현실중간 장비 통과 가능성(Middlebox Ossification) — QUIC이 UDP 기반을 택한 이유

3. 설계 원칙​

   [핵심 설계 원칙]
   ① **계층화(Layering)**      : 관심사 분리, 계층 간 독립적 변경 가능
   ② **캡슐화**                : 상위 계층 데이터를 하위 헤더로 감싸 전달
   ③ **End-to-End 원칙**       : 신뢰성은 최종 종단에서 보장, 네트워크는 단순하게
   ④ **Robustness Principle**  : "전송은 엄격하게, 수신은 관대하게"(Postel의 법칙)
   ⑤ **확장 가능한 명세**      : 버전·옵션 필드로 진화 경로 확보

Ⅴ. 결론​

오류 제어는 데이터의 정확성, 흐름 제어는 수신 측 보호, 혼잡 제어는 네트워크 전체의 안정성을 담당하며, 슬라이딩 윈도우는 이 중 오류 제어와 흐름 제어를 하나의 메커니즘으로 통합 구현한 핵심 기법이다. 특히 실제 전송량이 min(rwnd, cwnd)로 결정된다는 점에서, 세 제어 기법은 독립적이지 않고 상호 연동하여 동작한다.

프로토콜 설계에서는 ① 구문·의미·순서를 명확히 정의하고, ② BDP를 고려한 윈도우 설계로 성능을 확보하며, ③ 보안을 사후 부가가 아닌 설계 단계에 통합하고, ④ 버전·옵션 필드로 확장성을 미리 확보하는 것이 핵심이다. 최근 QUIC이 TCP의 Head-of-Line Blocking과 중간 장비에 의한 고착화 문제를 해결하기 위해 UDP 위에 재구현되고 TLS를 내장한 사례는, 이러한 설계 원칙들이 실제로 어떻게 적용되는지를 잘 보여준다.

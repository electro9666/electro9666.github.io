소프트웨어 동적 테스트(Dynamic Test)

Ⅰ. 개요​

1. 동적 테스트의 개념​

동적 테스트는 소프트웨어를 실제로 실행하여 입력에 대한 출력·동작을 관찰하고 기대 결과와 비교함으로써 결함을 검출하는 테스트이다. 코드를 실행하지 않고 검토·정적분석으로 결함을 찾는 정적 테스트(Static Test) 와 대비된다.

2. 동적 테스트의 분류​

                    [동적 테스트]
          ┌──────────────┼──────────────┐
   **명세 기반**      **구조 기반**      **경험 기반**
   (Black Box)       (White Box)      (Experience-based)
   동등분할·경계값     문장·결정·조건       오류추정
   결정테이블·상태전이  MC/DC·경로          탐색적 테스팅
   유스케이스·**분류트리** 커버리지 측정      체크리스트

Ⅱ. 가. 명세 기반 테스트와 구조 기반 테스트 비교​

1. 개념​

  • 명세 기반 테스트(Specification-based / Black Box): 내부 구조를 보지 않고 요구사항·명세로부터 테스트 케이스를 도출하여, 입력에 대한 출력이 명세와 일치하는지 검증한다.
  • 구조 기반 테스트(Structure-based / White Box): 소스코드의 내부 구조(제어 흐름·경로) 를 분석하여 테스트 케이스를 도출하고, 커버리지로 테스트 충분성을 측정한다.
   [명세 기반]                          [구조 기반]
   요구사항·명세                         소스코드 제어흐름
        │ 케이스 도출                         │ 케이스 도출
   입력 ──►[ ??? ]──► 출력 비교         입력 ──►[ if/else/loop ]──► 경로 실행 확인
        내부 구조 미고려                       내부 경로 커버리지 측정

2. 비교표​

비교 기준명세 기반 테스트(Black Box)구조 기반 테스트(White Box)
기준(Basis)요구사항·명세·설계서소스코드·제어 흐름 구조
관점사용자·외부 관점개발자·내부 관점
목적기능이 명세대로 동작하는가(무엇을)코드가 모두 실행되었는가(어떻게)
코드 지식불필요필수
주요 기법동등분할, 경계값 분석, 결정테이블, 상태전이, 분류트리, 유스케이스, 페어와이즈문장·결정·조건·조건결정·MC/DC·경로 커버리지
충분성 측정명세 항목 커버리지(정성적)커버리지 %(정량적)
검출 가능 결함누락된 기능, 잘못된 기능, 인터페이스 오류논리 오류, 도달 불가 코드, 예외 경로 결함
검출 불가 결함명세에 없는 숨겨진 코드(백도어), 내부 경로 오류명세 자체의 누락(구현되지 않은 요구사항)
적용 단계시스템·인수 테스트(주로 상위)단위·통합 테스트(주로 하위)
수행 주체QA·테스터·현업개발자
장점사용자 관점 검증, 대규모 시스템 적용 용이결함 위치 규명 용이, 정량적 품질 근거
단점내부 결함 누락 가능, 중복 케이스 발생명세 누락 검출 불가, 비용·시간 큼

3. 상호 보완 관계​

명세 기반은 "만들어야 할 것을 만들었는가", 구조 기반은 "만든 것이 제대로 동작하는가" 를 검증한다. 어느 하나로는 충분하지 않으므로, 단위 단계에서 구조 기반으로 커버리지를 확보하고, 시스템 단계에서 명세 기반으로 기능을 검증하는 계층적 적용이 표준적이다.

Ⅲ. 나. [프로그램 명세] 기반 테스트 케이스 작성​

1. 명세 분석​

명세: 입력은 정수. 10 미만 또는 100 초과 → "Fail", 10 이상 100 이하 → "Pass", 정수가 아니면 → "Invalid Input"

   [입력 도메인 분할]
   ─────┬──────────────┬──────────────────────┬──────────────┬────
        │   x < 10     │    10 ≤ x ≤ 100      │   x > 100    │  정수 아님
        │  **Fail**    │     **Pass**         │  **Fail**    │ **Invalid Input**
   ─────┴───────▲──────┴──────────▲───────────┴──────────────┴────
              경계 9,10,11      경계 99,100,101

2. 동등 분할(Equivalence Partitioning) 테스트 케이스​

원리: 입력 도메인을 동일한 결과를 낳는 그룹(동등 클래스) 으로 나누고, 각 클래스에서 대표값 1개씩만 선택하여 테스트 케이스 수를 최소화한다.

동등 클래스 ID클래스 정의유효성대표 입력값기대 결과
EC1정수 & x < 10유효(비정상 범위)5Fail
EC2정수 & 10 ≤ x ≤ 100유효(정상 범위)50Pass
EC3정수 & x > 100유효(비정상 범위)150Fail
EC4정수가 아닌 값(실수)무효3.14Invalid Input
EC5정수가 아닌 값(문자)무효"abc"Invalid Input
EC6입력 없음(공백)무효""(공백)Invalid Input

동등 분할 테스트 케이스

TC-ID입력값대상 클래스기대 출력
TC-015EC1Fail
TC-0250EC2Pass
TC-03150EC3Fail
TC-043.14EC4Invalid Input
TC-05abcEC5Invalid Input
TC-06(공백)EC6Invalid Input

보완 — 경계값 분석(BVA): 결함은 경계에서 집중 발생하므로 동등 분할과 함께 적용하는 것이 원칙이다.

TC-ID입력값근거기대 출력
TC-079하한 경계 −1Fail
TC-0810하한 경계값Pass
TC-0911하한 경계 +1Pass
TC-1099상한 경계 −1Pass
TC-11100상한 경계값Pass
TC-12101상한 경계 +1Fail

3. 분류 트리(Classification Tree) 기법 테스트 케이스​

원리: 입력 도메인을 분류(Classification) 와 그 하위 클래스(Class) 로 계층화하여 트리로 구조화하고, 클래스를 조합해 테스트 케이스를 도출한다. 동등 분할을 시각적·체계적으로 확장한 기법으로, 누락 방지에 효과적이다.

                        ┌───────── **입력값(Input)** ─────────┐
                        │                                     │
              ┌─── **분류1: 데이터 타입** ───┐      ┌── **분류2: 값의 범위** ──┐
              │                             │      │  (정수인 경우에만 적용)  │
        ┌─────┴─────┐              ┌────────┴──┐   │                          │
    **정수**    **정수 아님**       │           │   ├─ C3 : x < 10 (하한 미만)  │
    (Integer)   (Non-Integer)      │           │   ├─ C4 : 10 ≤ x ≤ 100 (정상)│
        │            ├─ C2a: 실수  │           │   └─ C5 : x > 100 (상한 초과) │
        C1           ├─ C2b: 문자열│           │                              │
                     └─ C2c: 공백  └───────────┘                              │
                                                                              ┘

   [조합 규칙] 정수(C1) → 범위 분류 적용 / 정수 아님(C2) → 범위와 무관하게 Invalid

분류 트리 기반 테스트 케이스(조합 표)

TC-ID분류1: 데이터 타입분류2: 값의 범위입력값기대 출력
CT-01정수(C1)x < 10 (C3)5Fail
CT-02정수(C1)10 ≤ x ≤ 100 (C4)50Pass
CT-03정수(C1)x > 100 (C5)150Fail
CT-04정수 아님 — 실수(C2a)적용 불가(N/A)3.14Invalid Input
CT-05정수 아님 — 문자열(C2b)적용 불가(N/A)abcInvalid Input
CT-06정수 아님 — 공백(C2c)적용 불가(N/A)(공백)Invalid Input
CT-07정수(C1) — 음수x < 10 (C3)−5Fail
CT-08정수(C1) — 경계10 ≤ x ≤ 100 (C4)10 / 100Pass
  • 분류 트리 기법의 이점: ① 입력 조건을 누락 없이 구조적으로 식별, ② 조합 관계와 제약(정수가 아니면 범위 무의미)을 명시적으로 표현, ③ 이해관계자와 시각적 합의 용이, ④ 필요 시 페어와이즈(조합 축소) 로 확장 가능

4. 두 기법의 비교​

구분동등 분할분류 트리
표현 방식목록·표 형태의 클래스 나열계층적 트리 구조
다중 조건조건 간 조합 관계 표현 취약여러 분류의 조합을 체계적으로 표현
적합 상황단일 입력·단순 조건입력 요소가 여러 개이거나 조건이 복합적
누락 위험상대적으로 높음낮음(구조적 도출)

Ⅳ. 결론​

동적 테스트에서 명세 기반과 구조 기반은 대체 관계가 아니라 검출 대상 결함이 다른 보완 관계이므로, 단위 단계의 커버리지 확보와 시스템 단계의 기능 검증을 계층적으로 병행해야 한다.

제시된 명세에 대해서는 동등 분할로 테스트 케이스를 최소화하고, 경계값 분석(9/10/100/101)으로 경계 결함을 보강하며, 입력 타입과 값 범위라는 두 분류가 존재하므로 분류 트리로 조합을 구조화하는 것이 가장 효과적이다. 실무적으로는 이렇게 도출한 케이스를 자동화 테스트로 구현하여 회귀 테스트 자산화하고, 명세 변경 시 트리를 함께 갱신하여 추적성을 유지하는 것이 바람직하다.

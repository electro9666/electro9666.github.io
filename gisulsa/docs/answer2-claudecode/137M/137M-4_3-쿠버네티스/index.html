쿠버네티스(Kubernetes)

Ⅰ. 개요​

1. 등장 배경​

컨테이너(Docker) 확산으로 애플리케이션 배포는 표준화되었으나, 수백~수천 개 컨테이너의 배치·확장·복구·네트워킹을 수동 관리하는 것은 불가능해졌다. 이에 컨테이너 오케스트레이션(Orchestration) 도구가 필요해졌고, 구글의 내부 시스템(Borg)을 기반으로 개발된 쿠버네티스가 CNCF의 사실상 표준으로 정착하였다.

Ⅱ. 가. 쿠버네티스의 개념 및 특징​

1. 개념​

쿠버네티스(K8s) 는 컨테이너화된 애플리케이션의 배포·확장·운영을 자동화하는 오픈소스 컨테이너 오케스트레이션 플랫폼이다. 사용자가 선언적으로 원하는 상태(Desired State) 를 정의하면, 시스템이 현재 상태를 지속적으로 감시하며 자동으로 일치시키는(Reconciliation) 방식으로 동작한다.

   [핵심 동작 원리 — 조정 루프(Reconciliation Loop)]
   사용자 : "Pod 3개를 실행하라"(YAML 선언)
        │
        ▼
   ┌─── **원하는 상태(Desired State)** : replicas = 3 ───┐
   │              ▲                       │             │
   │        차이 발견 시 조치        지속적 비교         │
   │              │                       ▼             │
   └─── **현재 상태(Current State)** : 실행 Pod = 2 ─────┘
                  └─► **컨트롤러가 Pod 1개 자동 생성** → 상태 일치
   ※ 명령형(How)이 아닌 **선언형(What)** — 자가 치유(Self-healing)의 근간

2. 주요 특징​

특징내용
선언적 구성YAML로 원하는 상태 정의 → GitOps·IaC와 자연스럽게 결합
자가 치유(Self-healing)장애 컨테이너 자동 재시작, 응답 없는 노드의 Pod 재배치, 헬스체크 실패 시 트래픽 제외
자동 확장(Auto Scaling)HPA(Pod 수), VPA(Pod 자원), Cluster Autoscaler(노드 수)
서비스 디스커버리·로드밸런싱DNS 기반 서비스 탐색, Service를 통한 자동 부하 분산
자동 배포·롤백롤링 업데이트로 무중단 배포, 실패 시 이전 버전 자동 롤백
자원 스케줄링요청(Request)·제한(Limit) 기반 최적 노드 배치, Affinity·Taint/Toleration
스토리지 오케스트레이션PV/PVC·CSI로 다양한 스토리지 동적 프로비저닝
구성·비밀 관리ConfigMap(설정)·Secret(민감정보)을 이미지와 분리
확장성(Extensibility)CRD·오퍼레이터(Operator) 로 사용자 정의 자원·컨트롤러 구현
이식성온프레미스·퍼블릭 클라우드·하이브리드 어디서나 동일 동작 → 벤더 종속 완화
한계높은 학습 곡선·운영 복잡도, 소규모에는 과도한 오버헤드, 상태 저장(Stateful) 워크로드 운영 난이도

Ⅲ. 나. 쿠버네티스의 주요 컴포넌트​

1. 전체 아키텍처​

   ┌──────────────── **Control Plane(마스터)** ─────────────────┐
   │  **kube-apiserver** ── 모든 요청의 단일 진입점(REST)        │
   │        │                                                   │
   │        ├── **etcd** : 클러스터 전체 상태 저장(분산 KV)      │
   │        ├── **kube-scheduler** : 새 Pod의 배치 노드 결정     │
   │        ├── **kube-controller-manager** : 조정 루프 실행     │
   │        └── cloud-controller-manager : 클라우드 연동         │
   └────────────────────────────┬───────────────────────────────┘
                                │ (API 통신)
   ┌────────────────────────────▼───────────────────────────────┐
   │                     **Worker Node**                         │
   │  **kubelet** : Pod 생성·상태 보고    **kube-proxy** : 네트워크 규칙 │
   │  **컨테이너 런타임(containerd·CRI-O)**                       │
   │  ┌────── Pod ──────┐ ┌────── Pod ──────┐                    │
   │  │ 컨테이너 + 볼륨  │ │ 컨테이너         │                    │
   │  └─────────────────┘ └─────────────────┘                    │
   └─────────────────────────────────────────────────────────────┘

2. Control Plane(제어 평면) 컴포넌트​

컴포넌트역할
kube-apiserver클러스터의 프론트엔드 — 모든 명령·조회의 단일 창구, 인증·인가·검증 수행, 유일하게 etcd에 접근
etcd분산 키-값 저장소 — 클러스터의 모든 구성·상태를 저장하는 단일 진실 공급원(SSoT). 손실 시 클러스터 복구 불가 → 정기 백업 필수, 홀수 노드 구성(Raft 합의)
kube-scheduler아직 노드가 배정되지 않은 Pod를 감시하고, 필터링(Filtering) → 점수화(Scoring) 를 거쳐 최적 노드 선택(자원 요청량, Affinity, Taint, 토폴로지 고려)
kube-controller-manager다수의 컨트롤러를 실행하며 조정 루프 수행 — Node·ReplicaSet·Deployment·Endpoint·ServiceAccount 컨트롤러 등
cloud-controller-manager클라우드 사업자 API 연동(로드밸런서·볼륨·노드 관리)

3. Worker Node 컴포넌트​

컴포넌트역할
kubelet각 노드의 에이전트 — API 서버로부터 PodSpec을 받아 컨테이너 실행을 보장, 헬스체크(Liveness·Readiness Probe) 수행 및 상태 보고
kube-proxy노드의 네트워크 규칙 관리 — Service의 가상 IP를 실제 Pod로 전달(iptables·IPVS 모드), 부하 분산
컨테이너 런타임실제 컨테이너 실행 — CRI(Container Runtime Interface) 표준 준수(containerd, CRI-O)
애드온CNI(네트워크 플러그인: Calico·Cilium), CoreDNS(서비스 디스커버리), 메트릭 서버, 인그레스 컨트롤러

4. 주요 오브젝트(Object)​

오브젝트내용
Pod배포의 최소 단위 — 1개 이상의 컨테이너가 네트워크(IP)·스토리지를 공유. 일시적(Ephemeral) 존재
ReplicaSet지정한 수의 Pod 복제본 유지
DeploymentReplicaSet을 관리하며 롤링 업데이트·롤백 제공(무상태 앱의 표준)
StatefulSet상태 저장 앱용 — 고유하고 안정적인 네트워크 ID와 스토리지, 순차적 생성·종료(DB·Kafka)
DaemonSet모든(또는 특정) 노드에 정확히 1개씩 Pod 배치(로그 수집·모니터링 에이전트)
Job / CronJob일회성 작업 / 주기적 배치 작업
ServicePod 집합에 대한 안정적 접근 지점(고정 가상 IP) — ClusterIP(내부), NodePort, LoadBalancer(외부)
IngressL7(HTTP) 라우팅 — 도메인·경로 기반 분기, TLS 종료
ConfigMap / Secret설정값 / 민감정보를 컨테이너와 분리하여 주입
PV / PVC영구 볼륨 자원 / 사용자의 스토리지 요청
Namespace클러스터 내 논리적 자원 분리(멀티 테넌시, 자원 쿼터)

Ⅳ. 다. HPA(Horizontal Pod Autoscaler)​

1. 개념​

HPA는 CPU·메모리 사용률 등 관측된 메트릭을 기반으로 Deployment·StatefulSet의 Pod 복제본 수(replicas)를 자동으로 늘리거나 줄이는 쿠버네티스 컨트롤러이다. 수평적 확장(Scale-out/in) 을 담당한다.

2. 동작 원리​

   ┌──── Metrics Server (또는 Prometheus Adapter) ────┐
   │   각 Pod의 CPU·메모리 사용량 수집                 │
   └────────────────────┬─────────────────────────────┘
                        │ (기본 15초 주기 조회)
   ┌────────────────────▼─────────────────────────────┐
   │              **HPA 컨트롤러**                     │
   │  ① 현재 메트릭 평균값 측정                        │
   │  ② **목표 복제본 수 계산**                        │
   │     desiredReplicas =                             │
   │       ceil[ currentReplicas ×                     │
   │             (currentMetric / desiredMetric) ]     │
   │  ③ min/max 범위 내로 조정 → Deployment 갱신       │
   └────────────────────┬─────────────────────────────┘
                        ▼
              ReplicaSet → **Pod 증감**

   [계산 예] 현재 Pod 3개, 평균 CPU 사용률 90%, 목표 50%
             desired = ceil[3 × (90/50)] = ceil[5.4] = **6개로 확장**

3. 주요 설정 및 메트릭​

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: { kind: Deployment, name: web-app }
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource                    # ① 자원 메트릭
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 50 } }
    - type: Pods                        # ② 커스텀 메트릭 (예: 초당 요청 수)
      pods: { metric: { name: http_requests_per_second }, target: { averageValue: "100" } }
  behavior:                             # ③ 확장·축소 속도 제어
    scaleDown: { stabilizationWindowSeconds: 300 }
메트릭 유형내용
Resource MetricsCPU·메모리 사용률 — Pod에 resources.requests 설정이 반드시 필요(기준값이 되므로)
Custom Metrics애플리케이션 지표(초당 요청 수, 응답시간) — Prometheus Adapter 필요
External Metrics클러스터 외부 지표(메시지 큐 길이, 클라우드 지표) — KEDA로 확장
파라미터내용
minReplicas / maxReplicas확장 범위의 하한·상한
target Utilization목표 사용률(통상 50~70%)
behaviorstabilizationWindow(축소 지연으로 플래핑 방지, 기본 5분), 확장·축소 속도(Policy)

4. 다른 확장 방식과의 비교​

구분HPAVPACluster Autoscaler
확장 대상Pod 개수(수평)Pod의 자원 요청량(수직)노드 개수
방식Scale-out / inScale-up / down노드 추가·제거
재시작불필요Pod 재시작 필요—
적합 워크로드무상태(Stateless) 웹·API자원 산정이 어려운 앱노드 자원 부족 시
상호 관계HPA와 VPA는 동일 메트릭(CPU) 동시 사용 시 충돌HPA가 Pod를 늘렸으나 배치할 노드가 없으면 CA가 노드 추가

5. 적용 시 고려사항​

고려사항내용
resources.requests 필수미설정 시 사용률 계산 불가 → HPA 동작 안 함
애플리케이션 준비 시간Pod 기동에 수십 초 소요 시 급격한 트래픽에 대응 지연 → 예측 기반 사전 확장, Readiness Probe 정확 설정
플래핑(Thrashing)확장·축소 반복 → stabilizationWindow, 적절한 목표치 설정
무상태 설계 전제세션·로컬 파일 의존 시 확장 불가 → 세션 외부화 필수
병목 전이Pod만 늘려도 DB·외부 API가 병목이면 효과 없음 → 종단 간 용량 검토
CPU 외 지표실제 부하는 큐 길이·동시 접속 수가 더 정확한 경우 많음 → 커스텀 메트릭·KEDA 활용
비용무분별한 maxReplicas는 비용 급증 → 상한 설정과 비용 모니터링

Ⅴ. 결론​

쿠버네티스의 본질은 컨테이너 실행 도구가 아니라, "원하는 상태를 선언하면 시스템이 스스로 그 상태를 유지하는" 조정 루프 기반의 자동화 플랫폼이다. 이 원리 위에서 자가 치유·무중단 배포·자동 확장이 자연스럽게 구현된다.

실무 도입 시에는 ① etcd 백업과 Control Plane 이중화 등 클러스터 자체의 가용성을 먼저 확보하고, ② HPA 활용을 위해 애플리케이션을 무상태로 설계하고 resources.requests를 정확히 산정하며, ③ HPA(Pod)와 Cluster Autoscaler(노드)를 함께 구성해야 실효성 있는 확장이 가능하다. ④ 아울러 CPU 사용률이 실제 부하를 대변하지 못하는 경우가 많으므로 커스텀 메트릭 기반 확장을 검토해야 한다.

다만 쿠버네티스는 운영 복잡도가 높아 소규모 조직에는 오히려 부담이 될 수 있으므로, 관리형 서비스(EKS·GKE·AKS) 활용이나 서버리스 대안과의 비교 검토가 선행되어야 한다.

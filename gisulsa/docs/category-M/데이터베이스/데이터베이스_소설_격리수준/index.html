격리 수준 (Isolation Level)

— 어느 데이터베이스 관리자의 가장 긴 밤​

프롤로그: 스키마​

한서진은 데이터베이스를 도시에 비유하곤 했다.

도시에는 세 겹의 지도가 있다. 첫 번째는 관광객이 보는 지도다. 주요 명소와 대로만 표시되어 있고, 하수관이나 전력망 따위는 보이지 않는다. 데이터베이스에서는 이것을 외부 스키마(External Schema) 라고 부른다. 사용자에게 보여주고 싶은 것만 골라 보여주는 창문 같은 것이다.

두 번째는 도시 설계사의 지도다. 모든 건물의 용도, 도로의 연결 관계, 구역 간의 의존성이 기록되어 있다. 이것이 개념 스키마(Conceptual Schema) — 데이터의 논리적 구조 전체를 담은 청사진이다.

세 번째는 공사 현장 감독의 지도다. 어떤 자재로 기초를 쌓았는지, 배관이 몇 밀리미터 간격으로 묻혀 있는지, 저장 탱크의 물리적 위치가 어디인지. 내부 스키마(Internal Schema) 는 데이터가 실제로 디스크 위에 어떻게 저장되는지를 기술한다.

이 세 겹의 지도가 서로 독립적으로 존재할 수 있다는 것 — 관광 지도를 바꿔도 설계도면이 달라지지 않고, 배관 공사를 해도 관광 지도에는 영향이 없다는 것. 데이터베이스 세계에서는 이것을 데이터 독립성(Data Independence) 이라 부르며, 이 원칙 위에 모든 것이 세워진다. 논리적 독립성은 개념 스키마가 변해도 외부 스키마는 그대로라는 뜻이고, 물리적 독립성은 내부 스키마가 변해도 개념 스키마는 영향받지 않는다는 뜻이다.

이 3-Schema 아키텍처. 1975년에 제안된 이래 반세기 동안 데이터베이스의 뼈대가 되어준 이 원칙이, 오늘 밤 무너지려 하고 있었다.

서진은 아직 그 사실을 모르고 있었다.

제1장: 열린 문​

1.1​

2026년 3월 어느 금요일, 새벽 2시 17분.

주식회사 넥스코어 데이터센터 지하 2층. 서버실의 항온항습기가 내뿜는 백색 소음 사이로, 한서진의 키보드 소리만이 간헐적으로 울렸다. 모니터 네 대가 부채꼴로 펼쳐진 관제 데스크. 왼쪽 두 대에는 실시간 쿼리 로그가 폭포처럼 흘렀고, 오른쪽 한 대에는 시스템 리소스 그래프가, 나머지 한 대에는 넥스코어의 사내 메신저 창이 떠 있었다.

서진의 직함은 DBA(Database Administrator) — 데이터베이스 관리자였다. 데이터베이스라는 도시의 경비원이자 배관공이자 교통경찰인 셈이다. 데이터의 구조를 설계하는 DA(Data Architect) 가 도시의 건축가라면, DBA는 그 도시가 매일 무사히 돌아가도록 지키는 사람이다. DA가 "이 건물은 여기에 세워야 해"라고 도면을 그리면, DBA는 "이 건물의 엘리베이터가 과부하 걸리지 않게 관리해야 해"라고 현장을 돌본다.

서진은 7년 차 DBA였다. 그녀의 업무는 대부분 자정 이후에 시작되었다. 낮에는 개발자들이 데이터베이스를 바쁘게 사용하므로, 점검이나 튜닝 같은 무거운 작업은 트래픽이 줄어드는 야간에 해야 했다.

오늘 밤의 작업 목록은 단순했다. 분기말 결산을 앞두고 재무 테이블의 인덱스를 재구성하는 것이었다. 인덱스란 책의 맨 뒤에 붙어 있는 색인과 같다. "고객"이라는 단어가 어디에 나오는지 일일이 책장을 넘기지 않아도, 색인을 보면 곧바로 해당 페이지를 찾을 수 있다. 데이터베이스의 인덱스도 마찬가지로, 수백만 건의 데이터 중에서 원하는 것을 빠르게 찾게 해준다.

그런데 경고가 떴다.

모니터 왼쪽 상단에, 오렌지색 알림 하나.

[ALERT] Anomalous transaction detected - isolation level: READ UNCOMMITTED - source: external API gateway

서진의 손가락이 멈췄다.

1.2​

격리 수준(Isolation Level) 이란 데이터베이스에서 동시에 여러 작업이 일어날 때, 각 작업이 서로를 얼마나 "볼 수 있는가"를 정하는 규칙이다.

비유하자면 이런 것이다. 은행 창구가 여러 개 있고, 각 창구에서 동시에 돈을 입출금하고 있다고 하자. 가장 엄격한 규칙은 "한 사람이 작업을 완전히 끝내기 전에는 다른 사람이 그 통장을 절대 볼 수 없다"는 것이고, 가장 느슨한 규칙은 "다른 사람이 아직 도장도 안 찍은 전표를 옆에서 슬쩍 들여다볼 수 있다"는 것이다.

데이터베이스는 이 규칙을 네 단계로 나눈다.

가장 아래가 READ UNCOMMITTED — 아직 확정되지 않은(커밋되지 않은) 데이터까지 읽을 수 있는 상태. 옆 창구의 직원이 전표에 숫자를 적고 있는 도중에, 어깨너머로 그 숫자를 읽어버리는 것과 같다. 그 숫자가 나중에 지워질 수도 있는데 말이다. 이렇게 아직 확정되지 않은 데이터를 읽는 것을 Dirty Read라고 부른다. 말 그대로 "더러운 읽기" — 깨끗하게 확정되지 않은 것을 읽었으니까.

그 위가 READ COMMITTED — 최소한 확정된 데이터만 읽을 수 있다. 도장이 찍힌 전표만 볼 수 있다.

그 위가 REPEATABLE READ — 한 번 읽은 데이터는 내 작업이 끝날 때까지 바뀌지 않는다. 내가 통장 잔고를 확인한 순간의 숫자가, 내 작업이 끝날 때까지 그대로 유지된다.

가장 꼭대기가 SERIALIZABLE — 마치 모든 작업이 한 줄로 서서 순서대로 처리되는 것처럼 동작한다. 가장 안전하지만, 가장 느리다.

넥스코어의 운영 데이터베이스는 READ COMMITTED 수준으로 운영되고 있었다. 업계 표준에 해당하는, 합리적인 선택이었다. 그런데 지금 누군가가 READ UNCOMMITTED로 트랜잭션을 열었다는 것은 — 보안 체계 바깥에서 접근하고 있다는 의미였다.

"장난이겠지."

서진은 혼잣말을 했지만, 손은 이미 상세 로그를 열고 있었다.

1.3​

로그를 추적하는 데 3분이 걸렸다. 그리고 그 3분 동안 서진의 표정은 점점 굳어갔다.

침입 경로는 고객용 API 서버였다. 넥스코어는 B2B 금융 플랫폼을 운영했고, 파트너사들이 API를 통해 거래 데이터를 조회할 수 있었다. 문제는 이 API의 내부에 있었다.

SQL(Structured Query Language) — 데이터베이스와 대화하기 위한 언어. "이 고객의 거래 내역을 보여줘"라고 사람이 말하면, 그것을 데이터베이스가 이해할 수 있는 형식으로 바꿔주는 것이 SQL이다. SQL은 크게 네 종류로 나뉜다. 데이터의 구조를 정의하는 DDL(Data Definition Language) — "이런 모양의 테이블을 만들어줘", 데이터를 조작하는 DML(Data Manipulation Language) — "이 데이터를 조회하고 수정해줘", 접근 권한을 제어하는 DCL(Data Control Language) — "이 사람에게는 읽기 권한만 줘", 그리고 트랜잭션을 제어하는 TCL(Transaction Control Language) — "이 작업을 확정해(COMMIT)" 또는 "이 작업을 취소해(ROLLBACK)".

공격자가 파고든 것은 DML 영역이었다. 구체적으로는, 파트너사 API에서 SQL 쿼리를 생성하는 방식에 치명적인 결함이 있었다.

SQL을 실행하는 방식에는 두 가지가 있다. 하나는 Statement — 사용자의 입력값을 직접 SQL 문장 안에 끼워넣는 방식이다. 마치 편지 양식에 이름을 직접 펜으로 쓰는 것과 같다. "OOO 고객의 거래 내역을 조회합니다"에서 OOO 자리에 사용자가 입력한 값을 그대로 넣는다.

문제는, 이 OOO 자리에 악의적인 SQL 코드를 집어넣을 수 있다는 것이다. 이름을 쓰는 칸에 "홍길동; 그리고 모든 금고를 열어라"라고 쓰면, 시스템이 이름으로 받아들이는 것이 아니라 명령으로 실행해버리는 것이다. 이것이 SQL Injection 공격이다.

이를 막는 방법이 Prepared Statement다. 미리 SQL 문장의 틀을 만들어놓고, 사용자 입력값은 순수한 "데이터"로만 취급하는 방식이다. 편지 양식에 이름을 쓸 수 있는 전용 스티커 칸을 만들어, 거기에 무슨 글을 쓰든 절대로 명령으로 해석되지 않게 하는 것이다. 스티커 안의 글씨는 그냥 글씨일 뿐이니까.

SQL 처리 과정은 세 단계를 거친다. 먼저 Parsing — SQL 문장의 문법을 검사하고 해석한다. 다음으로 Optimization — 가장 효율적인 실행 방법을 찾는다. 마지막으로 Execution — 실제로 실행한다. Prepared Statement는 이 중 Parsing 단계를 미리 해두기 때문에, 나중에 들어오는 입력값이 SQL 구조 자체를 바꿀 수 없다.

서진은 6개월 전에 이 문제를 발견하고 보고서를 올렸었다. 파트너 API의 거래 조회 모듈이 여전히 구식 Statement 방식을 쓰고 있다고. 정적 SQL(Static SQL) — 컴파일 시점에 SQL이 고정되는 안전한 방식 — 로 전환하거나, 최소한 Prepared Statement를 적용해야 한다고. 하지만 개발팀의 답변은 항상 같았다. "리팩토링 일정이 없습니다." "서비스에 영향이 없습니다."

동적 SQL(Dynamic SQL) — 실행 시점에 SQL 문장이 만들어지는 방식. 유연하지만 위험하다. 마치 운전하면서 네비게이션의 경로가 계속 바뀌는 것과 같다. 필요한 순간이 있지만, 통제하지 못하면 엉뚱한 곳으로 갈 수 있다. 공격자는 바로 이 유연함을 무기로 삼았다.

1.4​

서진은 공격자가 읽어간 데이터를 추적했다. 심장이 빨라졌다.

공격자가 접근한 것은 MA_TARGET_LIST라는 테이블이었다. 넥스코어 경영전략팀이 다음 분기 인수합병(M&A) 대상으로 검토 중인 기업 목록. 이 테이블의 데이터는 아직 이사회 결의를 거치지 않은 — 즉, 커밋되지 않은 트랜잭션 안에 있는 데이터였다.

경영전략팀의 류 상무가 이 목록을 데이터베이스에 입력하면서, 아직 작업 중이었기에 COMMIT을 하지 않은 상태였다. 정상적인 격리 수준(READ COMMITTED 이상)이라면, 다른 사용자는 이 미확정 데이터를 볼 수 없다. 마치 아직 봉투에 넣지 않은 편지를 다른 사람이 읽을 수 없는 것처럼.

그런데 공격자는 READ UNCOMMITTED 수준으로 접근했기 때문에, 이 봉투도 안 된 편지를 그대로 읽어버렸다. Dirty Read가 발생한 것이다.

게다가 더 심각한 문제가 있었다. 류 상무는 작업 중에 목록을 여러 번 수정했다. 기업 세 곳을 추가했다가 한 곳을 뺐다가, 다시 두 곳을 넣었다. 공격자가 이 과정을 여러 번 조회하면서, 최종 목록에는 없는 "유령" 같은 레코드까지 읽어갔다. 이것이 Phantom Read — 같은 조건으로 조회했는데 결과 행의 수가 달라지는 현상이다. 마치 같은 교실을 두 번 들여다봤는데, 처음에는 30명이었다가 두 번째에는 32명이 되어 있는 것처럼. 존재했다가 사라진 유령 레코드.

또한 Non-Repeatable Read 현상도 발생했다. 공격자가 같은 기업의 인수 예상 가격을 두 번 읽었는데, 첫 번째에는 500억이었다가 두 번째에는 420억으로 바뀌어 있었다. 류 상무가 그 사이에 금액을 수정했기 때문이다. 같은 데이터를 두 번 읽었는데 값이 다른 것 — 반복 불가능한 읽기.

공격자는 이 모든 버전의 데이터를 가져갔다. 최종 확정본뿐 아니라, 검토 과정에서 오갔던 모든 초안까지. 내부 의사결정 과정이 통째로 노출된 셈이었다.

서진은 전화기를 들었다.

제2장: 잠금의 실패​

2.1​

"CISO실 이정훈 팀장입니다."

잠에서 깬 듯 쉰 목소리가 전화기 너머로 들렸다. 서진은 가능한 한 간결하게 상황을 설명했다. 이정훈의 목소리에서 잠기가 사라지는 데 정확히 네 문장이 걸렸다.

"API 게이트웨이는 차단했어?"

"아직이요. 먼저 공격 범위를 파악하고 있습니다. 섣불리 차단하면 공격자가 눈치채고 흔적을 지울 수 있어요."

"좋아, 맞는 판단이야. 그런데 추가 유출은 막아야 하잖아."

서진은 이미 손을 움직이고 있었다.

트랜잭션(Transaction) — 데이터베이스에서 하나의 논리적 작업 단위. "A 계좌에서 100만 원을 빼고, B 계좌에 100만 원을 넣는다"를 하나의 트랜잭션으로 묶으면, 둘 다 성공하거나 둘 다 실패한다. 절대로 A에서만 빠지고 B에는 안 들어가는 상황이 발생하지 않는다. 이것이 트랜잭션의 원자성(Atomicity) — 더 이상 쪼갤 수 없는 하나의 단위라는 뜻이다.

지금 공격자의 세션도 하나의 트랜잭션이었다. 서진이 해야 할 것은 이 트랜잭션이 더 이상의 데이터를 읽지 못하도록 잠금(Lock) 을 거는 것이었다.

2.2​

데이터베이스의 로킹(Locking) 은 화장실 문고리에 "사용 중" 표시를 거는 것과 같다. 내가 이 데이터를 사용하고 있으니, 다른 사람은 기다려라. 잠금에는 두 종류가 있다. 공유 잠금(Shared Lock) 은 "나는 읽고 있으니 너도 읽어도 돼, 하지만 수정은 안 돼"이고, 배타적 잠금(Exclusive Lock) 은 "내가 쓰고 있으니 아무도 건드리지 마"이다.

서진은 공격자가 접근하고 있는 테이블들에 배타적 잠금을 걸기 시작했다. 잠금을 걸면 공격자의 다음 쿼리는 대기 상태에 빠진다 — 화장실 앞에서 줄을 서는 것처럼.

그런데 명령을 실행한 직후, 예상치 못한 일이 벌어졌다.

시스템 전체가 멈춘 것이다.

2.3​

화면에 붉은 글씨가 떴다.

[CRITICAL] Deadlock detected - Transaction 7724 waiting for lock held by Transaction 7731, Transaction 7731 waiting for lock held by Transaction 7724

교착 상태(Deadlock) — 서로가 서로의 잠금을 기다리며 영원히 멈추는 상황. 두 사람이 좁은 복도에서 마주쳤는데, 한 사람은 "너가 먼저 비켜"라고 하고, 다른 사람도 "아니, 너가 먼저 비켜"라고 하면서 둘 다 한 발짝도 못 움직이는 것과 같다.

공격자가 의도적으로 유도한 것이었다. 서진이 테이블 A에 잠금을 거는 동안, 공격자는 테이블 B에 잠금을 걸었다. 그리고 공격자가 테이블 A를 요청하고, 서진의 트랜잭션이 테이블 B를 요청하면서 — 서로가 서로를 기다리는 교착 상태가 만들어졌다.

이것은 병행제어(Concurrency Control) 의 핵심 문제였다. 여러 트랜잭션이 동시에 실행될 때, 데이터의 일관성을 유지하면서도 서로 방해하지 않도록 관리하는 기술. 병행제어가 제대로 작동하지 않으면 여러 가지 문제가 생긴다.

첫째, 갱신 분실(Lost Update) — 두 사람이 동시에 같은 문서를 수정하면, 나중에 저장한 사람의 내용만 남고 먼저 수정한 내용은 사라지는 것.

둘째, 모순성(Inconsistency) — 한 트랜잭션이 여러 데이터를 수정하는 도중에 다른 트랜잭션이 읽으면, 일부는 수정 전이고 일부는 수정 후인 모순된 상태를 보게 되는 것.

셋째, 연쇄 복귀(Cascading Rollback) — 하나의 트랜잭션이 취소되면, 그 데이터를 읽었던 다른 트랜잭션들도 도미노처럼 줄줄이 취소되어야 하는 것.

교착 상태가 풀리는 동안, 정확히 3.7초의 공백이 생겼다. 데이터베이스가 교착 상태를 감지하고, 두 트랜잭션 중 하나를 강제로 종료(ABORT)시키는 시간이었다. 시스템은 서진의 트랜잭션을 희생양으로 선택했다 — 시작한 지 더 짧은 트랜잭션을 죽이는 것이 기본 정책이었기 때문이다.

2.4​

그 3.7초 동안 공격자는 움직였다.

서진이 적용하려던 보안 패치 — 특정 IP 대역에서의 READ UNCOMMITTED 접근을 차단하는 설정 변경 — 가 ABORT되면서 원래 상태로 돌아갔다. 마치 모래 위에 쌓은 성이 파도 한 번에 쓸려간 것처럼.

갱신 분실(Lost Update) 이 발생한 것이다. 서진의 변경 사항이 공격자의 트랜잭션에 의해 덮어씌워졌다. 정확히 말하면, 서진의 트랜잭션이 ABORT되면서 UNDO 로그 — 변경 이전의 상태를 기록해둔 로그 — 를 이용해 원래 상태로 되돌려졌고, 공격자의 트랜잭션은 그 원래 상태(보안 패치가 없는 상태)에서 유유히 작업을 계속했다.

서진은 이를 악물었다. 공격자는 데이터베이스의 병행제어 메커니즘을 정확히 이해하고 있었다.

일반적으로 이런 문제를 방지하기 위해 2PL(Two-Phase Locking) 프로토콜을 사용한다. 이 프로토콜은 두 단계로 나뉜다. Growing Phase(확장 단계) — 필요한 잠금을 하나씩 획득하는 단계. 이 단계에서는 잠금을 얻기만 하고 풀지는 않는다. Shrinking Phase(축소 단계) — 잠금을 하나씩 풀어가는 단계. 이 단계에서는 새로운 잠금을 획득하지 않는다.

이 규칙을 지키면 교착 상태를 완전히 방지할 수는 없지만, 최소한 직렬 가능성(Serializability) — 동시에 실행한 결과가 순차적으로 실행한 결과와 같다는 보장 — 을 확보할 수 있다.

하지만 공격자는 Growing Phase에서 의도적으로 잠금 순서를 교차시켜, 2PL의 보호 범위 밖에서 교착 상태를 만들어낸 것이다.

"이 사람, 보통이 아니야."

서진은 다른 전략이 필요하다는 것을 깨달았다.

제3장: 균열을 따라​

3.1​

서진은 교착 상태의 혼란을 수습하면서 동시에 공격 경로를 역추적했다. 공격자가 어떻게 내부 테이블 구조를 알아냈는지가 관건이었다.

답은 데이터 모델링의 부실함에 있었다.

데이터베이스를 설계하는 과정을 데이터 모델링이라 한다. 현실 세계의 복잡한 관계를 데이터베이스가 이해할 수 있는 구조로 옮기는 작업이다. 이 과정은 세 단계를 거친다.

첫째, 개념적 데이터 모델링 — "우리 회사에는 고객이 있고, 고객은 주문을 하고, 주문에는 상품이 포함된다"는 식으로 핵심 개념과 관계를 정리하는 것. 이 단계에서 만들어지는 것이 ERD(Entity Relationship Diagram) — 개체 관계도이다. ERD에는 엔터티(Entity) 라 불리는 사각형들이 있고(고객, 주문, 상품 등), 이들의 속성(Attribute) 이 나열되며(고객의 이름, 전화번호 등), 엔터티 간의 관계(Relationship) 가 선으로 표시된다.

둘째, 논리적 데이터 모델링 — 개념 모델을 실제 테이블 구조로 바꾸는 것. 엔터티가 테이블이 되고, 속성이 컬럼이 된다. 이 단계에서 각 테이블의 주식별자(Primary Key) — 각 행을 유일하게 구분하는 열 — 를 결정한다. 주민등록번호가 사람을 유일하게 식별하는 것처럼, 주식별자는 테이블의 각 행을 유일하게 식별한다.

셋째, 물리적 데이터 모델링 — 실제 데이터베이스 제품에 맞게 저장 방식, 인덱스, 파티셔닝 등을 결정하는 것. 논리적 모델이 "이 서랍에는 양말을 넣겠다"라면, 물리적 모델은 "서랍의 재질은 참나무, 크기는 40cm, 칸막이는 3개"까지 결정하는 것이다.

3.2​

넥스코어의 문제는 이 세 단계가 제대로 분리되지 않았다는 것이었다.

고객용 API — 즉 외부 스키마 — 가 내부 테이블 구조를 거의 그대로 노출하고 있었다. API의 응답 필드 이름이 데이터베이스의 컬럼 이름과 동일했고, API의 URL 경로가 테이블 간의 관계를 그대로 반영했다.

예를 들어, /api/customers/123/orders/456/products 라는 API 경로만 봐도 "고객 테이블과 주문 테이블은 1:N 관계이고, 주문 테이블과 상품 테이블도 관계가 있구나"를 알 수 있었다.

카디널리티(Cardinality) — 엔터티 간 관계의 수적 대응. 1:1 관계는 한 사람당 하나의 여권, 1:N 관계는 한 고객의 여러 주문, N:M 관계는 여러 학생이 여러 과목을 수강하는 것과 같다. 공격자는 API 구조만 분석해도 이 카디널리티를 전부 파악할 수 있었다.

더 치명적인 것은 식별 관계(Identifying Relationship) 와 비식별 관계(Non-Identifying Relationship) 의 구분이 외부에 노출된 것이었다.

식별 관계란, 자식 테이블의 주식별자에 부모의 키가 포함되는 관계다. 비유하자면, 아파트 동-호수에서 "동" 번호 없이는 "호수"만으로 위치를 특정할 수 없는 것과 같다. "101동 302호"에서 "101동"이라는 부모 정보가 자식의 정체성의 일부인 것이다.

반면 비식별 관계는, 자식이 부모의 키를 참조는 하지만 자신의 정체성에 포함시키지는 않는 관계다. 사람과 회사의 관계처럼 — 홍길동은 A회사에 다니지만, 홍길동의 정체성이 A회사에 의존하지는 않는다.

공격자는 API의 URL 패턴에서 식별 관계를 찾아냈다. /orders/456은 독립적으로 접근 가능하지만, /customers/123/orders/456에서만 조회되는 데이터가 있다면 — 이것은 식별 관계이고, customers의 키 없이는 orders의 특정 레코드에 접근할 수 없다는 뜻이다. 공격자는 이 의존성 체인을 따라 외래키(Foreign Key) — 다른 테이블의 주식별자를 참조하는 열 — 의 구조를 역설계했다.

3.3​

"그들은 우리 ERD를 손에 넣은 것이나 마찬가지예요."

서진이 전화기 너머의 이정훈에게 말했다.

"ERD? 개발팀 회의실 화이트보드에 그려져 있던 그거?"

"네. 그런데 화이트보드를 안 봐도 됐어요. API 구조가 ERD나 다름없었으니까."

ERD를 그리는 표기법에도 여러 가지가 있다. 정보공학 표기법(IE) 은 까마귀 발 모양으로 관계를 표시하고, 바커 표기법(Barker) 은 실선과 점선으로 필수/선택 관계를 구분한다. Chen 표기법은 마름모로 관계를 표현하고, UML Class Diagram은 객체지향 방식으로 그린다. 표기법이 무엇이든, 핵심은 엔터티와 그 관계를 정확히 표현하는 것이다. 그리고 넥스코어는 그 관계를 API 설계에서 아무런 은폐 없이 그대로 드러내고 있었다.

공격자는 이 정보를 가지고 후보키(Candidate Key) — 주식별자가 될 수 있는 후보들 — 를 추론하고, 실제 주식별자(Primary Key) 가 무엇인지 특정했다. 어떤 컬럼이 항상 고유한 값을 가지는지, 어떤 컬럼 조합이 행을 유일하게 식별하는지를 API 응답 데이터만으로 알아낸 것이다.

3.4​

그리고 공격자는 한 가지 치명적인 설계 결함을 발견했다.

넥스코어의 핵심 테이블인 PARTNER_MASTER와 그 하위 테이블들 사이에 참조 무결성(Referential Integrity) 제약이 ON DELETE CASCADE로 설정되어 있었다.

무결성(Integrity) 이란 데이터가 정확하고 일관된 상태를 유지하는 것을 보장하는 규칙이다. 여러 종류가 있다.

개체 무결성(Entity Integrity) — 모든 테이블의 주식별자는 NULL(빈 값)일 수 없다. 모든 사람에게 반드시 주민등록번호가 있어야 하는 것처럼.

참조 무결성(Referential Integrity) — 외래키가 참조하는 값은 반드시 참조 대상 테이블에 존재해야 한다. 주문서에 적힌 고객 번호가 실제로 존재하는 고객이어야 하는 것처럼. 존재하지 않는 고객의 주문이 있으면 안 된다.

도메인 무결성(Domain Integrity) — 각 컬럼의 값은 정해진 범위 안에 있어야 한다. 나이에 음수가 들어가면 안 되는 것처럼.

문제는 참조 무결성을 유지하는 방법에 있었다. ON DELETE CASCADE는 "부모가 삭제되면 자식도 같이 삭제한다"는 규칙이다. 회사가 폐업하면 그 회사의 모든 직원 기록도 자동으로 삭제되는 것과 같다.

정상적인 상황에서는 합리적인 설계일 수 있다. 하지만 공격자의 관점에서 이것은 하나의 레코드를 삭제하면 수만 건의 관련 레코드가 도미노처럼 쓸려나가는 무기였다. 데이터베이스 이론에서 말하는 삭제 이상(Delete Anomaly) — 하나의 데이터를 삭제했을 때 의도하지 않은 다른 데이터까지 사라지는 현상 — 의 완벽한 무기화.

공격자는 아직 이 카드를 사용하지 않았다. 하지만 언제든 꺼낼 수 있는 상태였다.

제4장: 조직의 이상현상​

4.1​

새벽 3시. 이정훈이 데이터센터에 도착했다.

서진이 지금까지의 분석 내용을 브리핑하는 동안, 이정훈은 조용히 고개를 끄덕이다가 한 가지를 물었다.

"서진 씨, 6개월 전에 올린 Prepared Statement 전환 보고서, 결재 반려된 거 맞지?"

"네. 세 번 올렸습니다."

이정훈은 한숨을 쉬었다. "보안 보고서가 올라가도 처리가 안 되는 거, 이건 시스템 문제야."

서진은 최근에 읽은 데이터베이스 이론서의 한 구절을 떠올렸다. 정규화(Normalization) 에 대한 내용이었다.

4.2​

정규화란 데이터의 중복을 제거하고, 데이터 간의 의존 관계를 명확히 정리하는 과정이다. 왜 이것이 필요한가? 이상현상(Anomaly) 을 방지하기 위해서다.

이상현상은 세 가지가 있다.

삽입 이상(Insertion Anomaly) — 새로운 데이터를 넣으려면 불필요한 데이터까지 같이 넣어야 하는 문제. 예를 들어, "학과" 정보가 "학생" 테이블에 함께 저장되어 있다면, 아직 학생이 한 명도 없는 새 학과의 정보를 입력할 수 없다. 학생 없이는 학과가 존재할 수 없는 기이한 구조가 되는 것이다.

갱신 이상(Update Anomaly) — 같은 정보가 여러 곳에 중복 저장되어 있어서, 한 곳만 수정하면 나머지가 틀려지는 문제. 영업부의 전화번호가 직원 100명의 행에 각각 기록되어 있다면, 전화번호가 바뀔 때 100개 행을 전부 수정해야 하고, 하나라도 빠뜨리면 두 개의 다른 전화번호가 공존하게 된다.

삭제 이상(Delete Anomaly) — 데이터를 삭제하면 의도하지 않은 정보까지 같이 사라지는 문제. 어떤 학과의 마지막 학생이 자퇴하면, 그 학과의 정보까지 사라지는 것이다.

이런 이상현상을 해결하기 위해 함수적 종속성(Functional Dependency) 이라는 개념을 사용한다. "학번이 결정되면 이름이 결정된다"는 것이 함수적 종속이다. 학번 → 이름. 이 종속 관계를 기준으로 테이블을 분리해 나가는 것이 정규화의 핵심이다.

정규화는 단계적으로 진행된다. 제1정규형(1NF) 은 "한 칸에 하나의 값만" — 전화번호 칸에 두 개의 번호를 쉼표로 넣지 마라. 제2정규형(2NF) 은 "부분 종속 제거" — 주식별자의 일부에만 종속되는 속성을 분리하라. 제3정규형(3NF) 은 "이행 종속 제거" — A→B이고 B→C이면, C는 A에 직접 종속되지 않으니 분리하라. BCNF(Boyce-Codd Normal Form) 는 "모든 결정자가 후보키여야 한다"는 더 엄격한 조건이다.

그 위로 제4정규형(4NF) — 다치 종속 제거, 제5정규형(5NF) — 조인 종속 제거, 심지어 제6정규형(6NF) 까지 있지만, 실무에서는 대부분 3NF나 BCNF까지 적용한다.

4.3​

서진은 이 이상현상이 넥스코어라는 조직에도 그대로 적용된다는 것을 깨달았다.

삽입 이상 — 보안 보고서를 등록하려면 반드시 "개발팀 리소스 배정"이라는 필드가 채워져야 했다. 개발팀의 일정 확인 없이는 보안 이슈를 시스템에 등록조차 할 수 없는 구조. 리소스가 없으면 위험도 존재하지 않는다는 이상한 논리.

갱신 이상 — 퇴직한 DBA의 접근 권한이 인사 시스템에서는 삭제되었지만, 데이터베이스 접근 제어 목록에는 그대로 남아 있었다. 같은 정보가 두 곳에 중복 저장되어 있었고, 한 곳만 갱신된 것이다.

삭제 이상 — 3개월 전 보안팀 산하의 "DB보안 TF"가 해체되면서, 그 TF가 관리하던 보안 정책 문서와 점검 프로세스가 통째로 사라졌다. 팀이라는 엔터티를 삭제하자, 그 팀에 종속되어 있던 보안 정책이라는 데이터까지 삭제 이상으로 소실된 것이다.

조직의 함수적 종속성이 깨져 있었다. "보안 이슈" → "담당자" → "처리 프로세스"라는 종속 관계가 명확하지 않았고, 중간 단계가 사라지면 전체가 무너지는 이행 종속 구조였다.

"조직도 정규화가 필요한 거죠." 서진이 말했다.

이정훈은 쓴웃음을 지었다. "그래, 맞아. 그리고 가끔은 반정규화(Denormalization) 도 필요하고."

반정규화 — 의도적으로 중복을 허용하는 것. 정규화를 하면 데이터가 여러 테이블로 쪼개지기 때문에, 조회할 때 여러 테이블을 합쳐야(JOIN) 해서 성능이 떨어질 수 있다. 그래서 일부러 중복을 허용하여 조회 속도를 높이는 것이 반정규화다.

"하지만 반정규화는 성능을 위한 의도적 선택이어야지," 서진이 말했다. "보안에서의 반정규화는 그냥 방치야."

제5장: 분산의 그림자​

5.1​

새벽 3시 28분. 서진은 로그 분석에서 이상한 점을 발견했다.

공격 트래픽의 소스 IP가 세 곳에서 동시에 들어오고 있었다. 서울, 도쿄, 싱가포르. 세 곳 모두 넥스코어가 분산 데이터베이스를 운영하고 있는 지역이었다.

"이건 한 사람이 아니야." 서진이 중얼거렸다.

넥스코어는 글로벌 서비스를 위해 데이터베이스를 여러 지역에 분산 배치하고 있었다. 분산 데이터베이스(Distributed Database) 란 물리적으로 떨어진 여러 장소에 데이터를 나누어 저장하면서도, 사용자에게는 하나의 데이터베이스처럼 보이게 하는 시스템이다.

이것을 가능하게 하는 것이 분산 투명성(Distribution Transparency) 이다. 다섯 가지가 있다.

위치 투명성(Location Transparency) — 데이터가 어디에 저장되어 있든 사용자는 신경 쓸 필요 없다. 서울 서버에 있든 도쿄 서버에 있든, 같은 쿼리로 접근할 수 있다. 편의점 택배를 보낼 때 물류 창고가 어디에 있는지 몰라도 되는 것과 같다.

분할 투명성(Fragmentation Transparency) — 하나의 테이블이 여러 조각으로 나뉘어 저장되어 있어도, 사용자는 그것을 인식하지 못한다. 큰 퍼즐이 여러 상자에 나뉘어 있지만, 완성된 그림만 보는 것처럼.

중복 투명성(Replication Transparency) — 같은 데이터가 여러 곳에 복사되어 있어도, 사용자는 하나인 것처럼 사용한다.

병행 투명성(Concurrency Transparency) — 여러 사용자가 동시에 접근해도, 각자는 혼자 사용하는 것처럼 느낀다.

장애 투명성(Failure Transparency) — 일부 서버가 고장나도, 시스템 전체는 정상 동작한다.

이 투명성은 사용자의 편의를 위한 것이다. 하지만 공격자의 관점에서 이것은 흔적을 분산시킬 수 있다는 의미이기도 했다. 세 개 도시에서 동시에 공격하면, 어느 한 곳의 로그만으로는 전체 그림을 볼 수 없다.

5.2​

넥스코어의 데이터는 샤딩(Sharding) 방식으로 분산되어 있었다.

샤딩이란 하나의 거대한 테이블을 여러 조각(샤드)으로 나누어 서로 다른 서버에 저장하는 것이다. 마치 백과사전을 가나 권, 다라 권, 마~바 권으로 나누어 서로 다른 책장에 꽂아두는 것과 같다.

데이터를 어떻게 나눌 것인가에 따라 수평 분할(Horizontal Partitioning) 과 수직 분할(Vertical Partitioning) 로 구분된다. 수평 분할은 행(row) 단위로 나누는 것이다 — 고객 번호 1100번은 서버 A, 101200번은 서버 B. 마치 학생들을 반으로 나누는 것과 같다. 수직 분할은 열(column) 단위로 나누는 것이다 — 고객의 기본 정보(이름, 전화번호)는 서버 A, 금융 정보(계좌, 잔고)는 서버 B. 한 사람의 정보를 주제별로 쪼개는 것이다.

넥스코어는 Hash 기반 샤딩 전략을 사용했다. 고객 번호를 해시 함수에 넣으면 0, 1, 2 중 하나의 값이 나오고, 그 값에 따라 서울(0), 도쿄(1), 싱가포르(2) 서버에 저장된다. 이 방식의 장점은 데이터가 고르게 분배된다는 것이다. 단점은 — 해시 함수의 규칙을 알면, 특정 고객의 데이터가 어느 서버에 있는지 정확히 예측할 수 있다는 것이다.

다른 방식으로는 Range 기반 샤딩 — 값의 범위로 나누는 것(1100은 서버 A, 101200은 서버 B), 그리고 Directory 기반 샤딩 — 별도의 목록(디렉토리)에 "이 데이터는 어느 서버에 있다"를 기록해두는 것이 있다.

공격자는 API 응답 시간의 미세한 차이를 분석하여 해시 함수의 분배 규칙을 역산했다. 같은 고객의 데이터를 서울에서 조회할 때와 도쿄에서 조회할 때의 응답 속도 차이 — 데이터가 있는 서버에서 직접 조회하면 빠르고, 다른 서버로 우회하면 느리다 — 를 이용한 것이다.

5.3​

하지만 진짜 교활한 공격은 데이터 복제(Replication) 의 허점을 노린 것이었다.

넥스코어는 Master-Slave Replication 구조를 사용했다. 마스터 서버에서 데이터를 쓰고(INSERT, UPDATE, DELETE), 슬레이브 서버들은 마스터의 데이터를 복사해와서 읽기(SELECT) 전용으로 사용한다. 신문사의 본사에서 기사를 쓰고, 지방 지국에서는 그 기사를 가져다 배포만 하는 것과 같다.

이 복제 방식에는 두 가지가 있다. 동기 복제(Synchronous Replication) — 마스터에서 데이터가 바뀌면, 모든 슬레이브가 복제를 완료할 때까지 기다린다. 안전하지만 느리다. 비동기 복제(Asynchronous Replication) — 마스터는 데이터를 바꾸고 바로 "완료"를 반환하며, 슬레이브는 나중에 따라잡는다. 빠르지만, 일시적으로 마스터와 슬레이브의 데이터가 다를 수 있다.

넥스코어는 성능을 위해 비동기 복제를 선택했었다. 그리고 공격자는 이 비동기 복제의 시간차를 정확히 악용했다.

서진이 마스터 서버에서 공격자의 접근 권한을 삭제했다. 하지만 비동기 복제에는 약 0.5~2초의 지연이 있었다. 공격자는 그 지연 시간 동안 슬레이브 서버에 접속하여, 아직 권한 삭제가 반영되지 않은 상태에서 데이터를 읽어갔다. 마스터에서는 문이 잠겼지만, 슬레이브에서는 아직 문이 열려 있는 0.5초의 틈.

이것이 Eventual Consistency(최종 일관성) 의 함정이었다. "결국에는(Eventually) 모든 서버의 데이터가 같아질 것이다" — 하지만 "결국"이 올 때까지의 시간 동안에는 일관성이 보장되지 않는다.

5.4​

이정훈이 물었다. "왜 동기 복제를 안 했어?"

서진이 대답했다. "CAP 이론 때문이에요."

CAP 이론은 분산 시스템의 근본적인 딜레마를 설명하는 이론이다. 세 가지 속성 — C(Consistency, 일관성), A(Availability, 가용성), P(Partition tolerance, 분할 허용성) — 중에서 동시에 세 가지를 모두 만족시킬 수 없다는 것이다.

일관성(C)은 "모든 서버에서 같은 데이터를 본다"는 것. 가용성(A)은 "언제든 응답한다"는 것. 분할 허용성(P)은 "서버 간 통신이 끊겨도 시스템이 동작한다"는 것이다.

인터넷에서 서버 간 통신 단절은 언제든 일어날 수 있으므로, P는 포기할 수 없다. 그러면 C와 A 중 하나를 선택해야 한다. 일관성을 택하면(CP), 슬레이브가 최신 데이터로 업데이트될 때까지 응답을 보류하므로 가용성이 떨어진다. 가용성을 택하면(AP), 약간 오래된 데이터라도 즉시 응답하므로 일관성이 깨질 수 있다.

넥스코어는 금융 플랫폼임에도 가용성(A)을 선택했다. 0.5초의 지연을 감수하면 서비스 응답 속도가 30% 빨라지기 때문이었다. 그 0.5초가 보안의 빈틈이 될 줄은 몰랐다.

"CAP 이론에도 한계가 있어요." 서진이 덧붙였다. "PACELC 이론이 좀 더 현실적이죠. 네트워크 분할(P)이 발생하면 가용성(A)과 일관성(C) 사이에서 선택해야 하고, 그렇지 않을 때(E — Else)에도 지연 시간(L — Latency)과 일관성(C) 사이의 트레이드오프가 있다는 거예요. 우리는 평상시에도 지연 시간을 줄이기 위해 일관성을 양보하고 있었던 거죠."

제6장: 데이터의 늪​

6.1​

새벽 3시 55분. 서진은 공격자의 최종 목표를 파악했다.

파트너 API를 통한 M&A 목록 탈취는 전주곡에 불과했다. 공격자가 정말 노리는 것은 넥스코어의 데이터 레이크(Data Lake) 였다.

데이터 레이크란 모든 종류의 데이터를 원본 그대로 저장하는 거대한 저장소이다. 마치 산에서 흘러내린 물이 모두 모이는 호수처럼, 회사의 거래 데이터, 로그, 이메일, 문서, 센서 데이터 등이 가공 없이 그대로 흘러들어온다.

이것이 잘 관리되면 금광이다. 하지만 관리되지 않으면?

데이터 늪(Data Swamp) 이 된다.

맑은 호수가 관리 없이 방치되면, 수초가 자라고 진흙이 쌓이고 악취가 나는 늪으로 변하듯 — 데이터 레이크도 메타데이터(Meta Data) 관리 없이 방치되면, 무엇이 어디에 있는지, 이 데이터가 언제 들어왔는지, 누가 만들었는지, 민감 정보인지 아닌지 알 수 없는 늪이 된다.

메타데이터란 "데이터에 대한 데이터"이다. 도서관에서 책 자체가 데이터라면, 도서카드(저자, 출판일, 분류번호)가 메타데이터이다. 이 도서카드 없이 100만 권의 책이 바닥에 쌓여 있다면 — 그것이 바로 데이터 늪이다.

6.2​

넥스코어의 데이터 레이크는 정확히 그런 상태였다.

3년 전 CTO의 야심찬 프로젝트로 구축되었지만, 정작 그 위에 올려야 할 데이터 거버넌스(Data Governance) — 데이터의 수집, 저장, 사용, 폐기에 대한 정책과 프로세스를 정하고 관리하는 체계 — 는 구축되지 않았다.

데이터 거버넌스의 핵심 요소 중 하나가 마스터 데이터 관리(MDM, Master Data Management) 이다. 마스터 데이터란 회사 전체에서 공통으로 사용하는 핵심 참조 데이터 — 고객 목록, 상품 목록, 조직 체계 등 — 를 말한다. 이 데이터가 부서마다 다른 형태로 중복 저장되면 혼란이 생긴다. 영업팀에서는 "삼성전자"이고 회계팀에서는 "삼성전자(주)"이고 물류팀에서는 "SAMSUNG"이면, 같은 회사의 데이터를 통합할 수 없다. MDM은 이런 핵심 데이터의 단일 원본(Single Source of Truth)을 관리하는 것이다.

또한 데이터 프로파일링(Data Profiling) — 데이터의 구조, 내용, 품질을 분석하여 현재 상태를 파악하는 작업 — 도 한 번도 수행되지 않았다. 프로파일링은 건강검진과 같다. 데이터가 예상한 형식을 따르고 있는지, 빈 값은 얼마나 되는지, 이상치는 없는지를 점검하는 것이다.

그 결과, 데이터 레이크 안에는 암호화되어야 할 주민등록번호가 평문으로 저장되어 있었고, 이미 삭제 요청을 받은 고객의 개인정보가 남아 있었으며, 세 개의 다른 시스템에서 들어온 같은 고객의 정보가 서로 모순되는 상태로 공존하고 있었다. 데이터 무결성(Data Integrity) 과 데이터 정합성(Data Consistency) 이 모두 무너져 있었다. 무결성은 데이터가 정확한 것이고, 정합성은 서로 다른 곳의 데이터가 일치하는 것인데 — 둘 다 실패한 상태.

6.3​

공격자는 이 늪에서 금을 캤다.

넥스코어는 일상적인 업무에 쓰는 데이터베이스(OLTP — Online Transaction Processing)와 경영 분석에 쓰는 데이터베이스(OLAP — Online Analytical Processing)를 분리해서 운영하고 있었다.

OLTP는 "지금 이 고객의 주문을 처리해줘" 같은 실시간 거래 처리에 최적화되어 있다. 빈번한 읽기/쓰기, 소량의 데이터, 빠른 응답. 편의점 POS기와 같다.

OLAP은 "지난 3년간 지역별 매출 추이를 분석해줘" 같은 대규모 분석에 최적화되어 있다. 대량의 데이터를 읽어서 집계, 변환하는 작업. 마치 도시 전체의 교통 흐름을 분석하는 관제 센터와 같다.

이 둘을 분리 운영하는 이유는, 분석 쿼리가 거래 처리를 방해하지 않도록 하기 위해서다. 교통 분석을 위해 도시의 모든 차를 세운다면 교통이 마비되지 않겠는가.

OLAP 데이터베이스에는 분석에 최적화된 차원 모델링이 적용된다. 그 핵심이 스타 스키마(Star Schema) 이다. 가운데에 팩트 테이블(Fact Table) — 숫자로 된 측정값(매출액, 수량 등)을 저장하는 테이블 — 이 있고, 주변에 차원 테이블(Dimension Table) — 분석의 기준이 되는 속성(시간, 지역, 상품 카테고리 등)을 저장하는 테이블 — 이 별 모양으로 둘러싸고 있다. 별처럼 생겼다고 해서 스타 스키마이다.

차원 테이블이 더 세분화되어 눈꽃 모양으로 뻗어나가면 스노우플레이크 스키마(Snowflake Schema) 가 되고, 팩트 테이블이 여러 개이면 갤럭시 스키마(Galaxy Schema) 가 된다.

공격자는 넥스코어의 OLAP 시스템 — MOLAP(Multidimensional OLAP) 으로 구축된 데이터 큐브(Data Cube) — 에 접근하여, 시간, 지역, 상품, 고객이라는 네 차원으로 구성된 분석 데이터를 통째로 읽어갔다. OLAP 특유의 연산 — Drill-down(연도→분기→월로 세분화), Roll-up(도시→지역→전국으로 요약), Slice(특정 시점만 잘라보기), Dice(여러 조건으로 잘라보기) — 을 자유자재로 사용하며 핵심 정보를 추출했다.

6.4​

더 위험한 것은 ETL 파이프라인에서 발견되었다.

ETL은 Extract(추출) — 여러 시스템에서 데이터를 가져오고, Transform(변환) — 분석에 맞게 형식을 바꾸고, Load(적재) — 분석용 데이터베이스에 넣는 과정이다. 요즘은 순서를 바꿔 먼저 적재하고 나중에 변환하는 ELT 방식도 있다.

문제는 ETL의 Transform 단계에서 임시 파일이 만들어지는데, 이 임시 파일에 암호화 이전의 원본 데이터가 그대로 남아 있었다는 것이다. 마치 서류를 파쇄하기 전에 복사실에 원본을 놓고 온 것과 같다. 공격자는 이 임시 파일까지 읽어갔다.

넥스코어의 데이터 웨어하우스(Data Warehouse) 자체는 비교적 잘 설계되어 있었다. 하지만 데이터 웨어하우스 안의 세부 단위인 데이터 마트(Data Mart) — 특정 부서나 주제에 맞게 부분적으로 구성된 작은 데이터 저장소 — 의 접근 제어가 허술했다. 재무 마트, 인사 마트, 고객 마트가 모두 같은 수준의 접근 권한으로 설정되어 있었다.

서진이 가장 분노한 것은 다른 것이었다.

"데이터 가치를 가장 정확하게 평가한 게 우리 경영진이 아니라 저 공격자라는 거예요."

이정훈은 대답하지 않았다. 부정할 수 없는 사실이었기 때문이다.

최근 업계에서는 데이터 거래(Data Trade) 와 데이터 가치평가 에 대한 관심이 높아지고 있었다. 데이터는 그 자체로 자산이며, 그 가치를 평가하고 거래할 수 있다는 인식이 확산되고 있었다. 넥스코어는 데이터를 모으기만 했지, 그 가치를 평가하거나 분류한 적이 없었다. 어떤 데이터가 1억 원짜리이고 어떤 데이터가 100원짜리인지 구분하지 않고, 모두 같은 늪에 던져놓았다.

공격자는 그 늪에서 1억 원짜리만 정확히 골라 가져간 것이다.

제7장: 인덱스를 따라서​

7.1​

새벽 4시 12분. 서진은 반격을 준비했다.

공격자를 추적하려면 먼저 그가 실행한 쿼리의 패턴을 이해해야 했다. 서진은 옵티마이저(Optimizer) 가 남긴 로그를 뒤지기 시작했다.

옵티마이저는 데이터베이스의 내비게이션이다. SQL 쿼리가 들어오면, "이 데이터를 어떻게 찾는 것이 가장 빠를까?"를 결정한다. 같은 목적지라도 고속도로를 탈 수 있고, 국도를 탈 수 있고, 샛길을 탈 수 있듯이 — 같은 쿼리라도 실행 방법은 여러 가지이다. 옵티마이저는 이 중 가장 효율적인 경로를 선택하고, 그 결과를 실행 계획(Execution Plan) 으로 만들어낸다.

옵티마이저에는 두 종류가 있다. RBO(Rule Based Optimizer) — 미리 정해진 규칙에 따라 실행 계획을 결정한다. "인덱스가 있으면 무조건 인덱스를 써라" 같은 고정된 규칙. 마치 "무조건 고속도로를 타라"는 원칙과 같다. 간단하지만 상황에 따라 최적이 아닐 수 있다.

CBO(Cost Based Optimizer) — 테이블의 크기, 데이터의 분포, 인덱스의 종류 등을 고려하여 각 실행 방법의 비용(Cost) 을 계산하고, 가장 비용이 낮은 방법을 선택한다. 내비게이션이 실시간 교통 상황을 반영하여 최적 경로를 찾는 것처럼. 현대 데이터베이스는 대부분 CBO를 사용한다.

서진은 CBO가 기록한 비용 추정치에서 비정상적인 패턴을 발견했다. 공격자의 쿼리들은 하나같이 비용이 극단적으로 낮았다. 수천만 건의 테이블을 조회하는데도 비용이 거의 0에 가까웠다.

7.2​

이유는 인덱스(Index) 에 있었다.

인덱스는 책의 색인과 같다고 했다. 더 정확히 말하면, 인덱스는 데이터의 위치를 빠르게 찾기 위한 별도의 자료구조이다. 인덱스 없이 데이터를 찾으려면 테이블의 모든 행을 처음부터 끝까지 훑어야 한다(Full Table Scan). 인덱스가 있으면 원하는 데이터의 위치를 곧바로 알 수 있다.

인덱스의 종류는 다양하다.

B-Tree / B+Tree 인덱스 — 가장 널리 사용되는 인덱스 구조. 균형 잡힌 트리(Balanced Tree) 형태로, 루트 노드에서 리프 노드까지의 경로 길이가 모두 같다. B+Tree는 B-Tree의 변형으로, 실제 데이터가 리프 노드에만 있고 리프 노드끼리 링크로 연결되어 있어 범위 검색에 유리하다. 사전에서 ㄱ→가→간→감 순으로 찾아 내려가는 것과 비슷하다.

Hash Index — 해시 함수를 이용한 인덱스. 특정 값을 정확히 찾는 것(등호 검색)에는 매우 빠르지만, 범위 검색("100~200 사이")에는 사용할 수 없다. 사물함 번호를 아는 것과 같다 — 번호만 알면 바로 열 수 있지만, "근처 사물함"을 찾을 수는 없다.

Bitmap Index — 각 값의 존재 여부를 비트(0/1)로 표현한 인덱스. 성별(남/여)처럼 값의 종류가 적은 컬럼에 효과적이다. 출석부에서 출석/결석을 O/X로 표시하는 것과 같다.

함수 기반 인덱스 — 컬럼 값 자체가 아니라, 함수를 적용한 결과에 대한 인덱스. UPPER(name) 같은 것.

그리고 공격자가 악용한 것은 커버링 인덱스(Covering Index) 였다.

7.3​

커버링 인덱스란, 쿼리가 필요로 하는 모든 컬럼이 인덱스 안에 이미 포함되어 있는 인덱스를 말한다.

보통은 인덱스에서 원하는 행의 "위치"를 찾은 다음, 그 위치로 가서 실제 데이터를 읽어야 한다. 도서관 색인에서 책 번호를 찾은 다음, 그 번호의 서가로 가서 책을 꺼내야 하는 것처럼. 하지만 커버링 인덱스는 — 색인 카드에 책의 핵심 내용까지 적혀 있어서, 서가까지 갈 필요 없이 색인 카드만 읽으면 되는 것이다.

공격자는 넥스코어의 인덱스 설계를 정확히 파악하고 있었다. 어떤 테이블에 어떤 커버링 인덱스가 있는지 알았고, 인덱스만으로 원하는 데이터를 전부 추출했다. 테이블 본체에 접근하지 않았기 때문에, 테이블 접근 로그에는 흔적이 거의 남지 않았다.

마치 금고를 열지 않고, 금고 옆에 붙어 있는 내용물 목록만 읽어간 것과 같았다.

또한 클러스터드 인덱스(Clustered Index) 와 논클러스터드 인덱스(Non-Clustered Index) 의 차이도 공격에 활용되었다. 클러스터드 인덱스는 데이터 자체가 인덱스 순서대로 물리적으로 정렬되어 저장된 것이다 — 사전에서 "가나다" 순으로 단어가 물리적으로 배열된 것과 같다. 테이블당 하나만 존재할 수 있다. 논클러스터드 인덱스는 데이터와 별도로 존재하는 색인이다 — 책 뒤의 찾아보기처럼, 본문의 순서와 무관하게 별도의 순서로 정리되어 있다.

공격자는 클러스터드 인덱스의 B+Tree 리프 노드를 순차적으로 스캔했다. 리프 노드끼리 연결된 링크를 따라, 정렬된 순서대로 데이터를 쭉 읽어나갔다. 데이터가 이미 정렬되어 있으니, 추가적인 정렬 작업 없이 원하는 범위의 데이터를 효율적으로 추출할 수 있었다.

7.4​

하지만 서진에게는 비장의 무기가 있었다.

3개월 전, 서진은 보안팀과 함께 이상 탐지 시스템을 새로 구축했다. 이 시스템의 핵심은 벡터 데이터베이스(Vector Database) 였다.

벡터 데이터베이스는 전통적인 데이터베이스와 근본적으로 다르다. 기존 데이터베이스가 "이름이 홍길동인 사람을 찾아줘" 같은 정확한 일치 검색에 특화되어 있다면, 벡터 데이터베이스는 "이 그림과 비슷한 그림을 찾아줘" 같은 유사도 검색에 특화되어 있다.

모든 데이터를 고차원 벡터(숫자의 배열)로 변환한다. 예를 들어, 사용자의 행동 패턴 — 접속 시간, 조회 테이블, 쿼리 복잡도, 데이터 양, 접속 빈도 등 — 을 [0.82, 0.15, 0.67, 0.91, 0.33, ...] 같은 벡터로 변환한다. 이것을 임베딩(Embedding) 이라 한다. 비슷한 행동 패턴은 비슷한 벡터값을 가지므로, 벡터 공간에서 가까이 위치하게 된다.

이 벡터들을 효율적으로 검색하기 위한 인덱스 구조가 HNSW(Hierarchical Navigable Small World) 이다. HNSW는 계층적으로 연결된 그래프 구조로, 마치 국제선→국내선→버스→택시처럼 점점 세밀한 단위로 탐색 범위를 좁혀가는 방식이다. 최상위 계층에서는 대략적인 위치를 잡고, 하위 계층으로 내려가면서 점점 정확한 이웃을 찾아간다.

또 다른 방식으로 IVF(Inverted File Index) 가 있다. 벡터들을 먼저 여러 개의 클러스터로 묶어두고, 검색할 때는 가장 가까운 클러스터 몇 개만 탐색한다. 도서관의 모든 책을 뒤지는 대신, 관련 분야 서가 몇 개만 집중적으로 찾는 것과 같다.

이런 검색을 ANN(Approximate Nearest Neighbor) 검색이라 한다. "정확히 가장 가까운 것"이 아니라 "대략 가장 가까운 것"을 찾는다. 100% 정확하지는 않지만, 속도가 수십~수백 배 빠르다. 대부분의 실용적 상황에서는 "거의 정확한 답을 빠르게"가 "완벽한 답을 느리게"보다 낫다.

7.5​

서진은 이 벡터 데이터베이스에 저장된 임베딩 벡터들을 검색했다. 오늘 밤 공격자의 행동 패턴 벡터를 만들고, 과거 알려진 공격 패턴 벡터들과 비교했다.

0.3초 만에 결과가 나왔다.

유사도 0.94 — 과거 공격 사례 DB에서 "APT 그룹 Phantom Lock"의 서명과 거의 일치했다.

Phantom Lock. 동아시아 금융 기관을 표적으로 하는 APT 그룹. 특징적인 공격 패턴이 있었다. 첫째, 항상 비동기 복제의 지연 시간을 악용한다. 둘째, 커버링 인덱스를 이용해 테이블 접근 로그를 최소화한다. 셋째, 교착 상태를 의도적으로 유발하여 방어자의 트랜잭션을 방해한다.

그리고 넷째 — 이것이 가장 중요한 특징이었는데 — 데이터를 탈취한 후 반드시 CASCADE DELETE를 실행한다. 흔적을 지우기 위해서.

"시간이 없어." 서진의 목소리가 달라졌다.

제8장: JOIN​

8.1​

서진은 모든 단서를 조합해야 했다. 세 도시의 로그, API 게이트웨이의 접근 기록, 옵티마이저의 실행 계획, 벡터 DB의 유사도 분석 결과. 흩어진 데이터를 하나로 합치는 작업이 필요했다.

데이터베이스에서 여러 테이블의 데이터를 합치는 것을 JOIN이라 한다.

INNER JOIN — 양쪽 테이블에 모두 일치하는 데이터만 합친다. 두 반의 학생 중 양쪽 모두에 이름이 있는 학생만 보는 것. 교집합이다.

OUTER JOIN — 한쪽에만 있는 데이터도 포함한다. LEFT OUTER JOIN은 왼쪽 테이블의 모든 데이터를 포함하고, 오른쪽에 대응하는 것이 없으면 빈칸(NULL)으로 채운다. 우리 반 전원의 성적을 보되, 시험을 안 친 학생은 빈칸으로 표시하는 것. RIGHT OUTER JOIN은 그 반대이고, FULL OUTER JOIN은 양쪽 모두의 데이터를 포함한다.

CROSS JOIN — 양쪽의 모든 조합. 3명과 4명의 모든 쌍을 만들면 12개. 경우의 수를 전부 나열하는 것이다.

SELF JOIN — 같은 테이블을 자기 자신과 합치는 것. 직원 테이블에서 "상사"와 "부하"를 같은 테이블 안에서 연결할 때 사용한다.

JOIN의 성능은 그 내부 알고리즘에 따라 크게 달라진다.

Nested Loop Join — 가장 단순한 방식. 왼쪽 테이블의 각 행에 대해 오른쪽 테이블을 처음부터 끝까지 훑는다. 이중 for문과 같다. 작은 테이블끼리 합칠 때 효율적이다.

Sort Merge Join — 양쪽 테이블을 먼저 정렬한 후, 양쪽을 동시에 훑으며 합친다. 두 묶음의 알파벳 카드를 가나다 순으로 정렬한 후, 양쪽을 한 장씩 비교하며 짝을 맞추는 것과 같다. 이미 정렬된 데이터에 유리하다.

Hash Join — 한쪽 테이블로 해시 테이블을 만들고, 다른 쪽 테이블을 훑으면서 해시 테이블에서 빠르게 매칭한다. 한 반의 학생 이름을 사물함 번호표로 만들어놓고, 다른 반 학생들이 와서 자기 이름의 사물함을 찾는 것과 같다. 대량 데이터에 효과적이다.

8.2​

서진은 세 도시의 공격 로그를 INNER JOIN했다. 세 곳 모두에서 동시에 활동한 IP 조합을 추출하기 위해서. 그런 다음, 이 결과를 API 게이트웨이 로그와 LEFT OUTER JOIN했다. API를 통하지 않고 직접 데이터베이스에 접근한 시도가 있는지 확인하기 위해 — LEFT JOIN의 결과에서 오른쪽(API 로그)이 NULL인 행이 바로 그런 경우이다.

서진은 힌트(Hint) 를 사용하여 옵티마이저에게 Hash Join을 강제했다. 힌트란 옵티마이저에게 "이번에는 이 방법을 써줘"라고 요청하는 것이다. 보통은 옵티마이저가 스스로 최적의 방법을 선택하지만, DBA가 데이터의 특성을 더 잘 알고 있는 경우에는 힌트를 통해 실행 방법을 지정할 수 있다.

결과가 나왔다. 서진의 눈이 커졌다.

API를 통하지 않은 직접 데이터베이스 접속이 있었다. 내부 네트워크에서.

"내부자가 있어요." 서진이 이정훈을 쳐다보며 말했다.

제9장: ACID​

9.1​

이정훈의 얼굴이 굳었다. "확실해?"

"확실합니다. 내부 VPN을 통해 데이터베이스에 직접 접속한 세션이 있어요. 그리고 이 세션이 외부 공격자에게 CRUD 매트릭스 정보를 넘긴 것 같습니다."

CRUD 매트릭스 — 어떤 프로세스가 어떤 엔터티에 대해 C(Create, 생성), R(Read, 조회), U(Update, 수정), D(Delete, 삭제) 중 어떤 작업을 하는지를 정리한 표이다. 시스템 설계 문서의 일부로, 이 매트릭스를 보면 각 테이블에 어떤 프로그램이 접근하는지, 어떤 종류의 작업을 하는지를 한눈에 알 수 있다.

이 매트릭스가 공격자 손에 들어갔다면 — 공격자는 어떤 테이블이 어떤 시스템과 연결되어 있는지, 어디를 건드리면 어디까지 영향이 미치는지를 정확히 알 수 있다. 건물의 전기 배선도를 가진 도둑과 같다.

9.2​

서진은 결심했다. 더 이상 방어적으로 대응할 시간이 없었다. 공격자가 CASCADE DELETE를 실행하기 전에 모든 것을 끝내야 했다.

트랜잭션의 ACID 특성 — 서진은 이것을 방어 작전의 원칙으로 삼았다.

9.3 원자성 (Atomicity)​

첫째, 원자성(Atomicity) — "전부 아니면 전무(All or Nothing)."

서진은 공격자의 세션을 차단하기로 했다. 하지만 부분적으로 차단하면 위험했다. 세 도시 중 두 곳만 차단하면, 남은 한 곳에서 공격자가 보복(CASCADE DELETE)을 할 수 있다. 열 개의 세션 중 아홉 개만 끊으면, 남은 하나가 더 공격적으로 변할 수 있다.

원자성이란 바로 이것이다. 트랜잭션은 완전히 실행되거나, 완전히 취소되거나, 둘 중 하나여야 한다. 은행 이체에서 "A계좌에서 빼기"만 성공하고 "B계좌에 넣기"가 실패하면 돈이 사라진다. 그래서 둘 다 성공하거나, 하나라도 실패하면 전부 원래대로 되돌린다(ROLLBACK).

서진은 세 도시의 DBA에게 동시에 연락했다. "카운트다운에 맞춰 동시에 실행하세요. 전부 아니면 전무입니다."

도쿄의 다나카, 싱가포르의 라지브. 세 사람은 화상회의로 연결된 채, 동시에 공격자의 모든 세션을 일괄 ABORT(강제 종료) 시켰다.

9.4 일관성 (Consistency)​

둘째, 일관성(Consistency) — "규칙은 깨지지 않아야 한다."

세션을 끊는 것만으로는 부족했다. 공격자가 이미 변경한 데이터가 있을 수 있다. 시스템을 공격 이전의 정상 상태로 되돌려야 했다.

일관성이란, 트랜잭션이 실행된 후에도 데이터베이스의 모든 제약 조건과 규칙이 지켜져야 한다는 것이다. 계좌 잔고가 음수가 되면 안 되고, 존재하지 않는 고객의 주문이 생기면 안 된다. 트랜잭션 실행 전에 데이터가 일관된 상태였다면, 실행 후에도 일관된 상태여야 한다.

서진은 WAL(Write-Ahead Logging) 을 이용했다. WAL은 "미리 쓰는 로그" — 데이터를 실제로 변경하기 전에, "이런 변경을 할 예정이다"라는 기록을 먼저 로그에 남기는 것이다. 일기예보를 기록하듯, 앞으로 일어날 일을 먼저 기록해두는 것이다. 이렇게 하면 시스템이 갑자기 죽어도, 로그를 보고 어디까지 작업이 진행되었는지 알 수 있다.

서진은 WAL 로그를 역추적하여 마지막 체크포인트(Checkpoint) 를 찾았다. 체크포인트란 "이 시점까지의 모든 변경은 디스크에 안전하게 저장되었다"는 표시이다. 마치 게임의 세이브 포인트와 같다. 문제가 생기면 마지막 세이브 포인트로 돌아가면 된다.

체크포인트 이후의 변경사항 중, 공격자의 트랜잭션에 의한 것들을 골라내어 UNDO — 변경을 되돌리는 작업 — 를 수행했다. 동시에, 체크포인트 이후에 정상적으로 커밋된 트랜잭션 중 디스크에 반영되지 않은 것들은 REDO — 변경을 다시 적용하는 작업 — 를 수행했다.

UNDO는 "이것은 하지 않은 것으로 한다"이고, REDO는 "이것은 다시 한 번 한다"이다. 요리로 치면, 잘못 넣은 재료를 빼는 것이 UNDO이고, 정전으로 꺼진 오븐을 다시 켜는 것이 REDO이다.

9.5 격리성 (Isolation)​

셋째, 격리성(Isolation) — "각자의 공간을 침범하지 않는다."

복구 작업을 하는 동안 다른 트랜잭션이 방해하면 안 된다. 서진은 격리 수준을 SERIALIZABLE로 격상했다.

SERIALIZABLE은 가장 엄격한 격리 수준이다. 모든 트랜잭션이 마치 줄을 서서 한 명씩 차례로 실행되는 것처럼 동작한다. 동시성은 크게 떨어지지만, 어떤 이상현상도 발생하지 않는다 — Dirty Read도, Non-Repeatable Read도, Phantom Read도 모두 차단된다.

성능은 크게 떨어질 것이다. 평소 초당 5,000건의 트랜잭션을 처리하던 시스템이 초당 500건으로 떨어질 수 있다. 하지만 지금은 속도가 아니라 생존의 문제였다.

9.6 영속성 (Durability)​

넷째, 영속성(Durability) — "한 번 확정되면 영원히 보존된다."

복구된 데이터는 다시는 잃어버리면 안 된다. 서진은 복구 완료 즉시 동기 복제(Synchronous Replication) 를 적용했다. 앞서 비동기 복제의 시간차를 악용당했으므로, 이번에는 모든 서버가 복제를 완료할 때까지 커밋을 확정하지 않도록 했다.

영속성이란, 일단 커밋된 트랜잭션의 결과는 시스템에 장애가 발생하더라도 보존되어야 한다는 것이다. 정전이 나든, 디스크가 고장나든, 커밋된 데이터는 사라지지 않는다. 이를 위해 WAL 로그를 안정적인 스토리지에 기록하고, 데이터를 복제하여 다중화한다.

서진은 COMMIT을 눌렀다. 세 도시의 서버 모두에서 동기 복제가 완료되었음을 확인하고서야, 비로소 숨을 내쉬었다.

제10장: MVCC의 시간​

10.1​

새벽 4시 45분. 공격자의 세션은 모두 차단되었고, 데이터는 복구되었다. 하지만 서진은 한 가지가 마음에 걸렸다.

공격자가 데이터를 읽어가는 동안, 정상 사용자들의 트랜잭션에는 영향이 없었을까?

넥스코어의 데이터베이스는 MVCC(Multi Version Concurrency Control) 를 사용하고 있었다.

MVCC는 병행제어의 한 방식으로, 기존의 로킹과는 근본적으로 다른 접근법이다. 로킹이 "내가 쓰고 있으니 기다려"라면, MVCC는 "네가 읽는 건 과거 버전이니 기다릴 필요 없어"이다.

MVCC는 데이터를 변경할 때 이전 버전을 지우지 않고 보존한다. 마치 문서를 수정할 때 이전 버전을 모두 남겨두는 Google Docs의 버전 히스토리와 같다. 트랜잭션 A가 데이터를 수정해도, 트랜잭션 B는 수정 이전의 버전을 계속 읽을 수 있다. 각 트랜잭션은 자기가 시작한 시점의 "스냅샷"을 본다.

덕분에 "읽는 사람"과 "쓰는 사람"이 서로를 차단하지 않는다. 읽기와 쓰기가 동시에 일어나도 서로 기다릴 필요가 없으므로 성능이 좋다. 이것이 낙관적 병행제어(Optimistic Concurrency Control) 의 철학과 맥닿아 있다 — "충돌은 드물게 발생할 것이다"라고 낙관적으로 가정하고, 실제로 충돌이 발생한 경우에만 처리하는 방식.

반대로 전통적인 로킹은 비관적 병행제어(Pessimistic Concurrency Control) 에 해당한다 — "충돌이 발생할 것이다"라고 비관적으로 가정하고, 미리 잠금을 걸어 충돌을 방지하는 방식.

서진은 MVCC 로그를 확인했다. 다행히 공격 기간 동안 정상 사용자들의 트랜잭션은 별도의 버전 스냅샷을 읽고 있었으므로, 공격자의 활동에 의한 데이터 오염은 없었다. MVCC가 보이지 않는 방패 역할을 해준 것이다.

10.2​

하지만 MVCC의 타임스탬프 순서(Timestamp Ordering) 를 분석하면서, 서진은 공격의 타임라인을 더 정밀하게 재구성할 수 있었다. 각 트랜잭션에 부여된 타임스탬프를 따라가면, 공격자가 어떤 순서로 어떤 테이블에 접근했는지가 밀리초 단위로 드러났다.

제11장: 공간의 좌표​

11.1​

새벽 5시. 서진은 공격자의 물리적 위치를 추적하기 시작했다.

넥스코어의 보안 시스템에는 접속자의 IP 기반 위치 정보를 공간 데이터베이스(Spatial Database) 에 저장하는 기능이 있었다. 공간 데이터베이스는 위치 정보를 저장하고 검색하는 데 특화된 데이터베이스이다.

공간 데이터에는 기본적인 타입이 있다. Point(점) — 하나의 위치(위도, 경도). Line(선) — 점들의 연결. Polygon(다각형) — 닫힌 영역. 공격자의 접속 위치는 Point로 저장되고, 넥스코어의 서비스 영역은 Polygon으로 정의되어 있었다.

이 데이터를 검색하기 위해 공간 색인(Spatial Index) 을 사용한다. 일반적인 B-Tree 인덱스는 1차원 데이터(숫자, 문자열)의 순서를 기준으로 작동하므로, 2차원 이상의 공간 데이터에는 적합하지 않다. "서울역에서 반경 5km 이내의 접속"을 B-Tree로 검색하기는 어렵다.

그래서 R-Tree 같은 공간 인덱스를 사용한다. R-Tree는 공간 객체들을 MBR(Minimum Bounding Rectangle) — 최소 경계 사각형 — 으로 감싸서 계층적으로 조직하는 구조이다. 각 공간 객체를 포함하는 가장 작은 사각형을 그리고, 이 사각형들을 다시 더 큰 사각형으로 묶고, 그것을 또 더 큰 사각형으로 묶는 식으로 트리를 구성한다.

R+Tree는 R-Tree의 변형으로 사각형 간의 겹침을 없앤 것이고, R*Tree는 삽입 알고리즘을 개선하여 더 효율적인 트리 구조를 만든다. Hilbert R-Tree는 공간을 힐버트 곡선이라는 특수한 곡선을 따라 1차원으로 펼친 후 인덱싱하는 방식이다.

11.2​

서진은 공간 연산자(Spatial Operator) 를 이용하여 공격자의 위치를 분석했다.

위상 연산(Topological) — 두 공간 객체의 관계. "이 접속 지점이 우리 서비스 영역 안에 있는가?"

거리 연산(Distance) — 두 점 사이의 거리. "공격자의 세 접속 지점 간의 거리는 얼마인가?"

분석 결과, 세 접속 지점(서울, 도쿄, 싱가포르)은 모두 넥스코어의 오피스 반경 200m 이내에서 접속한 것이었다. VPN을 통한 위치 위장이었지만, 접속 초기 핸드셰이크 과정에서 실제 IP가 0.1초간 노출된 기록이 있었다.

세 곳 모두 넥스코어의 해외 지사 주변이었다. 내부자의 도움 없이는 불가능한 접근이었다.

제12장: 해시의 충돌​

12.1​

새벽 5시 20분. 이정훈이 내부자 후보를 추리기 시작했다.

넥스코어의 해외 지사에 접근 권한이 있는 사람은 총 47명. 이 중 오늘 밤 VPN 접속 기록이 있는 사람은 — 3명.

"이 세 사람의 데이터를 교차 검증해야 해요." 서진이 말했다.

서진은 해싱(Hashing) 기술을 이용하여 내부 활동 로그를 분석했다. 해시 함수란 임의 길이의 데이터를 고정 길이의 값으로 변환하는 함수이다. "홍길동"을 넣으면 "7F3A2B"가 나오고, "홍길순"을 넣으면 "9C1D4E"가 나온다. 같은 입력에는 항상 같은 출력이 나오지만, 출력에서 입력을 역추적하는 것은 (사실상) 불가능하다.

해싱에는 여러 종류가 있다. 정적 해싱(Static Hashing) — 해시 테이블의 크기가 고정되어 있다. 사물함의 개수가 정해져 있는 것과 같다. 동적 해싱(Dynamic Hashing) — 데이터가 늘어나면 해시 테이블도 함께 커진다. 사물함을 추가로 설치할 수 있는 것과 같다.

동적 해싱의 대표적인 방식이 확장성 해싱(Extendible Hashing) 이다. 해시 값의 앞부분 비트를 이용하여 버킷(저장 공간)을 분할하는데, 데이터가 많아지면 비트를 하나 더 사용하여 버킷을 두 배로 늘린다. 방이 꽉 차면 벽을 세워 두 개로 나누는 것과 같다.

선형 해싱(Linear Hashing) 은 버킷을 하나씩 순서대로 분할하는 방식이다. 확장성 해싱이 한 번에 전체를 재구성하는 반면, 선형 해싱은 점진적으로 확장한다.

해싱에서 피할 수 없는 문제가 충돌(Collision) — 서로 다른 두 입력이 같은 해시 값을 가지는 경우 — 이다. "홍길동"과 "김철수"가 같은 사물함 번호를 받는 상황. 이를 해결하기 위한 다양한 충돌 회피(Collision Resolution) 방법이 있다.

12.2​

서진이 해시 값을 이용해 세 명의 활동 로그를 비교 분석한 결과, 한 사람의 패턴이 확연히 달랐다.

해외사업본부 소속 김태현 과장. 그의 VPN 세션은 공격 시작 2분 전에 활성화되었고, 공격 종료 1분 후에 비활성화되었다. 그의 접속 해시 패턴은 공격자의 세션 패턴과 해시 충돌 — 아니, 해시 일치를 보였다. 우연의 일치라고 하기에는 너무나 정확한 시간적 상관관계.

"김태현 과장의 데이터 사전(Data Dictionary) 접근 기록을 확인해봐야 해요." 서진이 말했다.

데이터 사전(Data Dictionary) — 데이터베이스의 모든 객체(테이블, 컬럼, 인덱스, 사용자 권한 등)에 대한 정보를 저장하는 시스템 테이블. 데이터에 대한 데이터, 즉 메타데이터의 저장소이다. 데이터 사전을 보면 데이터베이스의 전체 구조를 한눈에 파악할 수 있다. 건물의 설계도면 보관실과 같은 것이다.

김태현은 3주 전에 데이터 사전을 대량으로 조회한 기록이 있었다. 모든 테이블의 컬럼 구조, 인덱스 정보, 외래키 관계, 그리고 — CRUD 매트릭스까지.

제13장: NoSQL의 이면​

13.1​

새벽 5시 35분. 이정훈이 전화를 끊으며 말했다. "김태현 과장, 이미 퇴근했대. 아니, 더 정확히는 — 어제 오후에 조기 퇴근했고, 이후 연락이 안 돼."

서진은 고개를 끄덕이며, 다른 사실 하나를 보고했다. "공격자가 우리 NoSQL 시스템에도 접근했어요."

넥스코어는 RDBMS(관계형 데이터베이스) 외에 NoSQL 데이터베이스도 운영하고 있었다. NoSQL은 "Not Only SQL" — SQL만이 아니다 — 라는 뜻으로, 관계형 모델의 제약을 벗어난 데이터베이스를 총칭한다.

왜 NoSQL이 필요한가? RDBMS는 데이터의 정확성과 일관성에 뛰어나지만, 수평적 확장(서버를 추가하여 성능을 높이는 것)이 어렵고, 비정형 데이터(이미지, 로그, JSON 등)를 다루기 불편하다. NoSQL은 이런 한계를 극복하기 위해 일관성을 일부 양보하고 유연성과 확장성을 얻는다.

NoSQL은 BASE 모델을 따른다. Basically Available(기본적으로 가용) — 항상 응답한다. Soft State(유연한 상태) — 시간이 지나면 상태가 변할 수 있다. Eventual Consistency(최종 일관성) — 결국에는 일관된 상태가 된다. RDBMS의 ACID와 대비되는 철학이다.

13.2​

NoSQL에는 네 가지 유형이 있다.

Key-Value Store — 가장 단순한 형태. 열쇠(Key)와 값(Value)의 쌍으로 데이터를 저장한다. 사물함과 내용물. Redis와 DynamoDB가 대표적이다. 세션 정보, 캐시 등 빠른 읽기/쓰기가 필요한 곳에 쓰인다. 넥스코어는 Redis를 인메모리 데이터베이스(In-memory Database) — 데이터를 디스크가 아닌 메모리에 저장하여 극도로 빠른 속도를 달성하는 DB — 로 사용하여 세션 정보를 관리했다.

Document Store — JSON이나 XML 같은 문서 형태로 데이터를 저장한다. 각 문서가 자체적인 구조를 가질 수 있어 유연하다. 같은 테이블에 있는 문서들이 서로 다른 필드를 가질 수 있다. MongoDB가 대표적이다. 넥스코어는 MongoDB에 파트너사의 계약 문서와 API 호출 로그를 저장했다.

Column Family Store — 행(Row) 기반이 아니라 열(Column) 기반으로 데이터를 저장한다. 같은 종류의 데이터가 물리적으로 모여 있으므로, 특정 열의 데이터를 대량으로 읽을 때 효율적이다. Cassandra와 HBase가 대표적이다. 분석용 대량 데이터를 다룰 때 적합하다.

Graph Database — 데이터를 노드(Node)와 관계(Edge)로 표현한다. 소셜 네트워크에서 친구 관계, 추천 시스템에서 "이 상품을 본 사람이 본 다른 상품" 같은 복잡한 관계를 표현하고 탐색하는 데 최적화되어 있다. Neo4j가 대표적이다.

13.3​

공격자가 접근한 것은 MongoDB와 Redis였다.

MongoDB에서는 파트너사 계약 정보를 읽어갔다. NoSQL의 데이터 모델링은 RDBMS와 다르다. RDBMS가 정규화를 통해 데이터를 잘게 쪼개는 반면, NoSQL은 자주 함께 조회되는 데이터를 하나의 문서에 모아두는 반정규화(Denormalization) 방식을 선호한다.

NoSQL 데이터 모델링의 절차는 RDBMS와 반대이다. RDBMS는 "어떤 데이터가 있는가?"에서 시작하여 구조를 설계한 후 쿼리를 작성하지만, NoSQL은 "어떤 쿼리를 실행할 것인가?"에서 시작하여 쿼리에 최적화된 구조를 설계한다. 즉, 쿼리 우선(Query-First) 접근법이다.

Redis에서는 더 위험한 것을 가져갔다 — 현재 활성 세션 토큰들. Redis는 인메모리에 데이터를 저장하므로 속도가 극도로 빠르고, 넥스코어는 사용자 인증 세션을 Redis에 캐싱하고 있었다. 공격자가 이 세션 토큰을 탈취하면, 정상 사용자로 위장하여 시스템에 접근할 수 있다.

서진은 즉시 Redis의 모든 세션을 무효화했다. 금요일 새벽 — 사용자가 적은 시간이라 영향은 최소화될 것이다.

제14장: 데이터 표준화와 TEXT2SQL​

14.1​

새벽 5시 50분. 포렌식 팀이 도착했다. 서진은 지금까지의 분석 내용을 인계하면서, 한 가지 더 보고할 것이 있었다.

"공격자가 TEXT2SQL 도구를 사용한 흔적이 있어요."

TEXT2SQL — 자연어를 SQL로 변환하는 기술이다. "지난달 서울 지역의 매출 상위 10개 상품을 알려줘"라고 자연어로 입력하면, AI가 이것을 SELECT product_name, SUM(sales) FROM ... WHERE region='서울' AND ... ORDER BY ... LIMIT 10 같은 SQL로 자동 변환해준다.

넥스코어는 내부 분석 도구에 TEXT2SQL 기능을 탑재하고 있었다. 문제는 이 도구가 내부 네트워크에 노출되어 있었고, 공격자(내부 협조를 받은)가 이를 이용하여 데이터베이스 구조를 빠르게 탐색했다는 것이다. 자연어로 질문만 하면 SQL이 자동 생성되므로, 데이터베이스 구조를 몰라도 원하는 정보를 추출할 수 있었다.

"데이터 표준화가 되어 있어서 오히려 공격이 쉬웠다는 아이러니도 있습니다." 서진이 덧붙였다.

넥스코어는 데이터 표준화 — 테이블명, 컬럼명, 코드값 등에 일관된 명명 규칙을 적용하는 것 — 를 잘 해놓았다. 표준 용어, 표준 도메인, 표준 코드가 체계적으로 관리되고 있었고, 명명 규칙(Naming Rule) 도 잘 정의되어 있었다. 그래서 TEXT2SQL이 정확한 SQL을 생성할 수 있었고, 공격자 역시 테이블 이름만으로 그 내용을 추측할 수 있었다.

CUST_MASTER — 고객 마스터. TXN_HISTORY — 거래 이력. MA_TARGET_LIST — M&A 대상 목록. 이름만 봐도 뭐가 들어 있는지 알 수 있다. 표준화는 양날의 검이었다.

제15장: 관측 가능성​

15.1​

새벽 6시. 동쪽 하늘이 밝아오기 시작했다.

서진은 포렌식 팀에게 인계를 마치고, 마지막으로 데이터 관측가능성(Data Observability) 대시보드를 확인했다.

데이터 관측가능성이란 데이터의 상태를 실시간으로 모니터링하고, 문제가 발생했을 때 신속하게 감지할 수 있는 능력이다. 서버 관측가능성이 "서버가 잘 돌아가고 있는가?"를 감시하는 것이라면, 데이터 관측가능성은 "데이터가 정확하고, 신선하고, 기대한 형태를 유지하고 있는가?"를 감시하는 것이다.

대시보드의 지표들이 하나둘 초록색으로 바뀌고 있었다. 데이터 신선도 — 정상. 데이터 정합성 — 복구 완료. 스키마 변경 — 감지 없음.

데이터 품질관리 프레임워크의 관점에서 보면, 넥스코어는 데이터 관리와 데이터 구조관리는 비교적 잘 되어 있었지만, 데이터 품질관리 프로세스 — 특히 사전 예방적 품질관리 — 가 부족했다. 데이터 품질 성숙도 모델로 평가하면, 넥스코어는 아마 5단계 중 2단계 — "반복적(Repeatable)" 수준에 머물러 있었을 것이다. 문제가 발생하면 대응하지만, 문제가 발생하기 전에 예방하는 체계는 갖추지 못한 상태.

데이터 주권(Data Sovereignty) — 데이터가 생성된 국가의 법률에 따라 관리되어야 한다는 원칙 — 의 관점에서도 문제가 있었다. 서울, 도쿄, 싱가포르의 데이터가 동일한 보안 정책으로 관리되고 있었지만, 각 국가의 데이터 보호법은 달랐다. 일본의 개인정보보호법과 싱가포르의 PDPA를 모두 만족시키려면, 데이터 거버넌스가 국가별로 차별화되어야 했다.

15.2​

서진은 포렌식 보고서의 마지막 부분을 작성했다.

사고 분석 보고서 — 결론 및 권고사항

이번 사건의 근본 원인은 기술적 취약점이 아닙니다. 기술적 취약점은 결과이지 원인이 아닙니다.

근본 원인은 조직의 이상현상(Organizational Anomaly) 입니다.

우리는 데이터를 제3정규형(3NF) 까지 관리하면서, 정작 데이터를 지키는 사람과 프로세스는 비정규형(UNF) 상태로 방치했습니다.

보안 보고서가 등록되려면 개발 리소스가 먼저 배정되어야 하는 삽입 이상, 퇴직자의 권한이 인사 시스템에서만 삭제되고 DB 접근 목록에는 남아 있는 갱신 이상, 보안 TF가 해체되면 보안 정책까지 사라지는 삭제 이상. 이 세 가지 이상현상이 해결되지 않는 한, 어떤 기술적 방어도 근본적인 해결책이 될 수 없습니다.

반정규화(Denormalization) 는 성능이라는 명확한 목적을 위해 의도적으로 중복을 허용하는 것입니다. 그러나 보안의 반정규화 — 보안 프로세스의 중복 제거, 보안 인력의 겸직, 보안 예산의 통합 삭감 — 는 성능이 아니라 재앙을 가져옵니다.

권고합니다. 데이터를 정규화하듯 조직을 정규화하십시오.

함수적 종속성을 명확히 하십시오 — "보안 이슈 → 담당자 → 처리 프로세스"의 관계가 명확해야 합니다. 중간 단계가 사라져도 전체가 무너지지 않는 구조를 만드십시오.

참조 무결성을 확보하십시오 — 존재하지 않는 담당자에게 배정된 업무가 없도록, 권한 변경이 모든 시스템에 동기적으로 반영되도록 하십시오. CASCADE 설정을 재검토하여, 하나의 변경이 의도하지 않은 연쇄 삭제를 일으키지 않도록 하십시오.

데이터 거버넌스를 실체화하십시오 — 계획서에만 존재하는 MDM이 아니라, 실제로 작동하는 마스터 데이터 관리 체계를 구축하십시오. 데이터 프로파일링을 정기적으로 수행하고, 데이터 관측가능성을 확보하십시오.

우리의 데이터 레이크가 데이터 늪이 되지 않도록, 그리고 우리 조직의 보안이 비정규형의 늪에 빠지지 않도록.

에필로그: COMMIT​

서진이 보고서를 저장하고 모니터에서 눈을 뗐을 때, 서버실의 작은 창문 너머로 서울의 여명이 번지고 있었다.

이정훈이 종이컵 커피를 건네며 말했다. "김태현 과장, 집에서 체포됐어. 6개월 전에 Phantom Lock 조직에 포섭된 것 같아."

서진은 커피를 받아들며 물었다. "DA나 데이터 모델러(Data Modeler) 는 아니었나요? 어떻게 DB 구조를 그렇게 잘 알았죠?"

"데이터 스튜어드(Data Steward) 였어. 데이터 품질 관리 담당. 데이터 사전 접근 권한이 있었고, CRUD 매트릭스도 업무상 다룰 수 있었고."

데이터 스튜어드 — 데이터의 품질과 정책 준수를 현장에서 관리하는 사람. DA가 건축가이고 DBA가 경비원이라면, 데이터 스튜어드는 건물 관리인과 같다. 건물의 모든 방에 열쇠를 가지고 있는 사람. 그 열쇠가 도둑에게 넘어간 것이다.

서진은 차가운 커피를 한 모금 마셨다. 화면에는 공격자가 남긴 마지막 쿼리 로그의 주석이 보였다.

-- 당신들의 가장 큰 취약점은 DB가 아니라 무관심이다.
-- SELECT * FROM security_awareness WHERE level > 0;
-- 0 rows returned.

서진은 이 주석을 한참 바라보다가, 조용히 터미널에 타이핑했다.

INSERT INTO security_awareness (employee_id, level, last_updated)
SELECT employee_id, 1, CURRENT_TIMESTAMP
FROM employees
WHERE employee_id NOT IN (SELECT employee_id FROM security_awareness);

COMMIT;

모든 직원에게 보안 인식 레코드를 삽입하는 쿼리. 물론 이것은 실제 보안 인식을 높이는 것이 아니라, 단지 데이터를 넣는 것에 불과하다. 하지만 서진은 알고 있었다 — 모든 변화는 하나의 INSERT로부터 시작된다는 것을.

트랜잭션이 시작되면, 반드시 COMMIT 아니면 ROLLBACK으로 끝나야 한다. 서진은 COMMIT을 선택했다. 되돌리지 않겠다는 결심.

서버실의 항온항습기가 여전히 백색 소음을 내뿜고 있었다. 모니터 속 데이터 관측가능성 대시보드의 지표들이 모두 초록색이었다. 시스템은 회복 중이었다.

하지만 서진은 알고 있었다. 진짜 회복(Recovery)은 코드가 아니라 문화에서 시작된다는 것을. 체크포인트를 남기고, WAL에 기록하고, REDO를 수행하듯 — 조직도 실패를 기록하고, 원인을 분석하고, 같은 실수를 반복하지 않겠다는 결의를 남겨야 한다.

서진은 보고서의 제목을 마지막으로 수정했다.

『격리 수준: 0에서 SERIALIZABLE까지 — 넥스코어 데이터 침해 사고 분석 보고서』

그리고 COMMIT을 눌렀다.

이번에는 되돌려지지 않을 것이다.

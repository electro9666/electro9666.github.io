데이터베이스 개념 상세설명 (비유로 쉽게 이해하기)

정보관리기술사 110~138회 기출 키워드 기반 각 개념을 일상생활의 비유를 통해 쉽게 설명합니다.

1. 데이터베이스 개요​

1.1 DBMS 기초​

데이터베이스(Database)​

비유: 체계적으로 정리된 도서관

도서관에는 수많은 책이 있지만, 분류 번호와 목록 시스템 덕분에 원하는 책을 빠르게 찾을 수 있다. 데이터베이스도 마찬가지로 데이터를 체계적으로 저장하고, 필요할 때 빠르게 꺼내 쓸 수 있도록 구조화한 데이터의 집합이다.

DBMS(DataBase Management System)​

비유: 도서관 사서

도서관(데이터베이스)을 관리하는 전문 사서가 DBMS다. 사서는 책의 입고(삽입), 폐기(삭제), 위치 변경(수정), 대출 기록 관리(조회)를 해주고, 여러 사람이 동시에 책을 빌리려 할 때 충돌이 나지 않도록 조율해준다.

데이터 독립성(Data Independence)​

비유: TV 리모컨과 TV 내부 회로

리모컨으로 채널을 바꿀 때 TV 내부 회로가 어떻게 바뀌는지 알 필요 없다. 데이터 독립성도 이와 같다.

  • 논리적 독립성: 전체 데이터 구조가 바뀌어도 사용자가 보는 화면(응용 프로그램)은 영향을 받지 않는다. TV 방송국이 채널 편성을 바꿔도 리모컨 버튼은 그대로인 것과 같다.
  • 물리적 독립성: 데이터가 디스크에 저장되는 방식이 바뀌어도 논리적 구조는 변하지 않는다. TV 내부 부품을 교체해도 채널 목록은 그대로인 것과 같다.

3-Schema 아키텍처​

비유: 같은 아파트를 보는 세 가지 시선

하나의 아파트 단지를 세 명이 각자 다른 관점으로 본다.

  • 외부 스키마(External Schema): 입주자 시점. 자기 집 구조만 본다. 각 사용자는 자기에게 필요한 데이터만 본다.
  • 개념 스키마(Conceptual Schema): 관리사무소 시점. 단지 전체의 구조(몇 동, 몇 호, 어떤 시설)를 파악한다. 데이터베이스 전체의 논리적 구조다.
  • 내부 스키마(Internal Schema): 건설사 시점. 배관, 전선, 콘크리트 구조 등 물리적 구조를 안다. 데이터가 실제 디스크에 어떻게 저장되는지를 나타낸다.

1.2 데이터베이스 인력 역할​

DA(Data Architect)​

비유: 도시 설계사(Urban Planner)

도시를 설계할 때 주거 지역, 상업 지역, 공원의 배치를 결정하는 사람이다. DA는 조직 전체의 데이터 구조와 흐름을 설계하고, 데이터 표준과 원칙을 수립한다.

DBA(Database Administrator)​

비유: 건물 관리인(빌딩 매니저)

건물이 지어진 후 엘리베이터 점검, 전기·수도 관리, 보안 시스템을 운영하는 사람이다. DBA는 이미 구축된 데이터베이스의 성능 튜닝, 백업, 보안, 장애 복구를 담당한다.

DA vs DBA: DA는 "어떤 데이터를 어떤 구조로 관리할 것인가"를 설계하고, DBA는 "그 데이터베이스가 잘 돌아가도록 운영"하는 역할이다. 설계사 vs 관리인의 차이다.

Data Modeler​

비유: 건축 도면을 그리는 설계 기사

DA가 큰 그림을 그리면, Data Modeler는 그 설계를 구체적인 ERD(도면)로 변환하는 실무자다.

Data Steward​

비유: 품질 검수관

공장에서 나오는 제품의 품질을 체크하고, 규격에 맞는지 확인하는 사람이다. 데이터의 품질, 정확성, 일관성을 책임지고 관리한다.

2. 데이터 모델링​

2.1 모델링 개요​

현실세계 모델링​

비유: 지도를 그리는 것

실제 세계의 산, 강, 도로를 종이 위에 축소해서 그리는 것이 지도 제작이다. 데이터 모델링도 현실의 업무 프로세스를 데이터 구조로 "축소 번역"하는 것이다.

Inside-out 전략​

비유: 씨앗에서 나무를 키우기

핵심이 되는 주요 엔터티(씨앗)를 먼저 정의하고, 거기서부터 관련 엔터티를 바깥으로 확장해 나간다.

Outside-in 전략​

비유: 숲 전체를 보고 나무를 심기

전체 업무 범위(숲)를 먼저 파악한 뒤, 세부 엔터티(나무)를 배치해 나간다.

Top-down / Bottom-up 모델링​

비유: 건축 설계 방식 차이

  • Top-down: 전체 건물 청사진을 먼저 그리고, 각 방의 세부 설계로 내려간다. 전사 관점에서 시작.
  • Bottom-up: 각 방의 용도를 먼저 정하고, 그것들을 모아 건물을 완성한다. 현장 요구사항에서 시작.

2.2 모델링 단계​

개념적 데이터 모델링​

비유: 집의 스케치(러프 드로잉)

"거실, 방 2개, 주방이 필요해"처럼 큰 덩어리를 잡는 단계다. 핵심 엔터티와 관계만 정의한다.

논리적 데이터 모델링​

비유: 상세 설계 도면

거실 크기는 5m×4m, 문 위치는 여기, 콘센트는 저기처럼 속성, 키, 관계를 정확하게 정의한다. 특정 DBMS에 종속되지 않는다.

물리적 데이터 모델링​

비유: 시공 도면(실제 건축 도면)

어떤 브랜드 시멘트를 쓸지, 배관 규격은 뭔지 결정하는 단계다. 실제 DBMS에 맞게 테이블, 인덱스, 파티션 등을 결정한다.

2.3 ER 모델링​

ERD(Entity Relationship Diagram)​

비유: 가족 관계도

가족 구성원(엔터티)과 그들의 관계(부모-자녀, 부부)를 한눈에 보여주는 그림이 가족 관계도다. ERD는 데이터의 구성 요소와 관계를 시각적으로 표현한 다이어그램이다.

표기법(Notation)​

  • 정보공학 표기법(IE): 까마귀 발(Crow's Foot) 모양으로 다수(N) 관계를 표현한다. 가장 널리 쓰인다.
  • 바커 표기법(Barker): 오라클에서 주로 사용. 실선/점선으로 필수/선택 관계를 구분한다.
  • Chen 표기법: 마름모로 관계를 표현하는 원조 표기법. 학술적으로 많이 쓰인다.
  • UML Class Diagram: 소프트웨어 설계에서 온 표기법을 데이터 모델에 적용한 것.

엔터티(Entity)​

비유: 명사

"학생", "과목", "주문"처럼 관리 대상이 되는 것(사물, 개념)이다. 문장에서 주어나 목적어에 해당하는 명사와 같다.

속성(Attribute)​

비유: 형용사/부사

엔터티를 설명하는 세부 특성이다. "학생"이라는 엔터티에 "이름", "학번", "전공" 같은 속성이 붙는다.

관계(Relationship)​

비유: 동사

엔터티 간의 연결이다. "학생이 과목을 수강한다"에서 "수강한다"가 관계다.

2.4 식별자​

주식별자(Primary Key)​

비유: 주민등록번호

한 사람을 유일하게 식별하는 번호다. 테이블에서 각 행을 유일하게 구분하는 열(컬럼)이다.

외래식별자(Foreign Key)​

비유: 학생증에 적힌 학교 코드

학생증에 "00대학교"라고 적혀 있으면, 그 학교가 실제 존재하는 학교여야 한다. 외래키는 다른 테이블의 기본키를 참조해서 두 테이블을 연결하는 열이다.

식별 관계(Identifying Relationship)​

비유: 성(姓)이 부모로부터 오는 것

자녀의 이름에 부모의 성이 포함되어, 부모 없이는 자녀를 식별할 수 없다. 부모 테이블의 기본키가 자식 테이블의 기본키의 일부가 되는 관계다.

비식별 관계(Non-Identifying Relationship)​

비유: 학생과 담임 선생님

학생은 담임 선생님이 누군지 알고 있지만, 학생의 학번(기본키)에 담임 정보가 포함되지는 않는다. 부모의 키를 일반 속성(FK)으로만 받는 관계다.

후보키 / 대체키 / 슈퍼키​

비유: 사람을 식별하는 여러 방법

  • 슈퍼키: 사람을 식별할 수 있는 모든 조합 (주민번호+이름, 주민번호+전화번호 등). 불필요한 정보가 포함될 수 있다.
  • 후보키: 최소한의 정보로 식별하는 조합 (주민번호, 여권번호). 슈퍼키 중 최소성을 만족하는 것.
  • 대체키: 기본키로 선택되지 않은 후보키 (기본키=주민번호라면, 대체키=여권번호).

2.5 카디널리티 및 관계 유형​

카디널리티(Cardinality)​

비유: 한 선생님이 몇 명의 학생을 가르치는가

관계에 참여하는 엔터티의 수적 비율이다.

  • 1:1 관계: 한 사람은 하나의 주민등록번호만 가진다. 1명 = 1번호.
  • 1:N 관계: 한 부서에 여러 직원이 소속된다. 1부서 = N명.
  • N:M 관계: 학생은 여러 과목을 수강하고, 한 과목에 여러 학생이 있다. 실제 구현 시 중간 테이블(수강 테이블)이 필요하다.

2.6 데이터 모델링 보조 기법​

CRUD 매트릭스​

비유: 업무 분장표

"누가(프로세스) 어떤 데이터(엔터티)를 생성(C), 읽기(R), 수정(U), 삭제(D) 하는가"를 표로 정리한 것이다. 회사에서 각 부서별로 어떤 문서를 작성/열람/수정/폐기하는지 정리한 표와 같다.

데이터 사전(Data Dictionary)​

비유: 국어사전

단어의 뜻, 용법, 품사를 정리한 것이 국어사전이듯, 데이터 사전은 데이터베이스에 있는 모든 테이블, 컬럼, 타입, 제약조건의 정의를 모아둔 저장소다.

메타 데이터(Meta Data)​

비유: 책의 표지 정보

책의 내용 자체가 아니라, "저자, 출판일, 페이지 수, ISBN"처럼 책에 대한 정보가 메타데이터다. "데이터에 대한 데이터"이다.

3. 정규화 및 무결성​

3.1 정규화​

정규화(Normalization)​

비유: 옷장 정리

모든 옷을 한 서랍에 넣으면 찾기 어렵고 중복으로 같은 옷을 사게 된다. 옷을 종류별(상의, 하의, 외투)로 나눠 정리하는 것이 정규화다. 데이터 중복을 제거하고 구조를 깔끔하게 나누는 과정이다.

함수적 종속성(Functional Dependency)​

비유: 학번을 알면 이름을 알 수 있다

학번이 결정되면 학생 이름이 자동으로 결정된다. "학번 → 이름"이라는 종속 관계가 있는 것이다. 이 관계를 기반으로 정규화를 수행한다.

이상현상(Anomaly)​

비유: 한 곳만 고쳤는데 다른 곳이 틀어지는 문제

주소록에 같은 사람의 주소가 3군데 적혀 있다고 하자.

  • 삽입 이상: 새 부서를 만들려면 반드시 직원도 같이 넣어야 한다. 직원 없는 부서를 등록할 수 없다.
  • 갱신 이상: 주소를 바꿨는데 3곳 중 2곳만 바꾸면 어디가 맞는지 모른다.
  • 삭제 이상: 마지막 직원을 삭제하면 부서 정보까지 사라진다.

정규형(Normal Form)​

  • 제1정규형(1NF): "한 칸에 하나만 적기". 엑셀 한 셀에 전화번호 2개를 쓰지 않는다. 모든 속성 값이 원자값(더 이상 나눌 수 없는 값)이어야 한다.

  • 제2정규형(2NF): "부분적으로 의존하지 않기". 수강 테이블에서 (학번, 과목코드)가 기본키일 때, '학생이름'은 학번만으로 결정되므로 부분 종속이다. 이를 제거한다.

  • 제3정규형(3NF): "이행적 종속 제거". 학번→학과, 학과→학과사무실. 학번→학과사무실은 학과를 거쳐 간접적으로 결정된다(이행 종속). 이를 분리한다.

  • BCNF: "모든 결정자가 후보키여야 한다". 3NF보다 더 엄격한 버전이다. 후보키가 아닌 속성이 다른 속성을 결정하면 분리한다.

  • 제4정규형(4NF): "다치 종속 제거". 한 교수가 여러 과목을 가르치고 여러 동아리 지도를 하는데, 과목과 동아리가 서로 독립적이면 분리한다.

  • 제5정규형(5NF): "조인 종속 제거". 3개 이상의 테이블로 분해했다가 다시 조인해도 원래 데이터가 복원되는 것을 보장한다. 가장 극단적인 분해다.

  • 제6정규형(6NF): "시간 축까지 분해". 주로 시간에 따라 변하는 데이터를 완벽히 분해하는 이론적 형태다.

3.2 반정규화(Denormalization)​

반정규화(역정규화)​

비유: 자주 쓰는 물건은 꺼내놓기

옷장을 완벽하게 정리(정규화)하면 깔끔하지만, 매일 입는 옷을 찾으려고 매번 서랍을 열어야 한다. 자주 쓰는 옷은 의자에 걸어두는 것(반정규화)이 빠르다. 성능 향상을 위해 의도적으로 중복을 허용하는 것이다.

반정규화 유형​

  • 테이블 반정규화: 테이블을 합치거나 분리. 두 개의 서랍을 하나로 합치는 것.
  • 컬럼 반정규화: 자주 조인하는 컬럼을 복사해 넣기. 자주 보는 전화번호를 포스트잇에 적어 모니터에 붙이는 것.
  • 관계 반정규화: 빠른 접근을 위해 관계를 추가. 지름길(숏컷)을 만드는 것.

3.3 무결성 제약​

무결성(Integrity)​

비유: 데이터의 건강 상태

사람이 건강하려면 체온, 혈압 등이 정상 범위에 있어야 하듯, 데이터도 정해진 규칙을 만족해야 "건강한(무결한)" 상태다.

  • 개체 무결성(Entity Integrity): 모든 행에는 고유한 식별자(기본키)가 있어야 하고, NULL이면 안 된다. 모든 국민에게 주민번호가 있어야 하는 것과 같다.

  • 참조 무결성(Referential Integrity): 외래키가 참조하는 값은 반드시 존재해야 한다. 배송 주소에 적힌 우편번호가 실제 존재하는 우편번호여야 하는 것과 같다.

  • 도메인 무결성(Domain Integrity): 나이 컬럼에 '사과'를 넣을 수 없다. 각 속성은 정해진 범위/타입의 값만 가져야 한다.

  • 사용자 정의 무결성: 업무 규칙에 맞는 제약. "할인율은 50%를 초과할 수 없다" 같은 비즈니스 규칙이다.

  • NULL / UNIQUE / CHECK: 각각 "빈 값 허용 여부", "중복 불가", "조건 충족 여부"를 검사하는 제약 조건이다.

4. SQL​

4.1 SQL 개요​

SQL(Structured Query Language)​

비유: 데이터베이스와 대화하는 언어

한국어로 사람에게 말하듯, SQL로 데이터베이스에게 "이 데이터 보여줘", "이거 수정해줘"라고 말한다. 데이터를 정의하고, 조작하고, 제어하는 표준 언어다.

4.2 SQL 분류​

DDL(Data Definition Language)​

비유: 건축 허가서

건물(테이블)을 짓거나(CREATE), 구조를 변경하거나(ALTER), 철거하는(DROP) 명령이다. 데이터 구조를 정의한다.

DML(Data Manipulation Language)​

비유: 건물 안에서 하는 활동

건물이 세워진 후 가구를 들이고(INSERT), 배치를 바꾸고(UPDATE), 버리고(DELETE), 살펴보는(SELECT) 행위다.

DCL(Data Control Language)​

비유: 출입증 발급/회수

누구에게 건물 출입 권한을 줄지(GRANT), 뺏을지(REVOKE) 결정하는 명령이다. 접근 권한을 제어한다.

TCL(Transaction Control Language)​

비유: 작업 확정/취소 도장

여러 작업을 묶어서 "확정(COMMIT)"하거나 "취소(ROLLBACK)"하는 명령이다. 은행 이체에서 출금과 입금이 모두 성공해야 확정하는 것과 같다.

4.3 SQL 처리​

SQL 처리과정​

비유: 음식 주문 과정

레스토랑에서 주문하면 (1) 주문서 확인(Parsing), (2) 최적 조리 방법 결정(Optimization), (3) 실제 조리(Execution) 순으로 진행된다.

Statement vs Prepared Statement​

비유: 매번 새로 주문 vs 단골 메뉴 등록

  • Statement: 매번 주문서를 새로 작성하고 확인받는다. 매번 파싱~최적화를 거친다.
  • Prepared Statement: 자주 시키는 메뉴를 미리 등록해두고 "평소 거요"라고 말한다. 파싱·최적화를 한 번만 하고 재사용하므로 빠르고, SQL 인젝션 방어에도 효과적이다.

4.4 정적 SQL vs 동적 SQL​

정적 SQL(Static SQL)​

비유: 미리 인쇄된 신청서

양식이 정해져 있어 빈칸(바인드 변수)만 채우면 된다. 컴파일 시점에 SQL이 확정되므로 성능 예측이 쉽다.

동적 SQL(Dynamic SQL)​

비유: 백지에 직접 쓰는 신청서

실행 시점에 SQL 문장 자체를 조립한다. 유연하지만 성능 예측이 어렵고, SQL 인젝션 위험이 있다.

4.5 JOIN​

JOIN​

비유: 두 명부를 합쳐 보는 것

학생 명부와 성적 명부를 학번으로 맞춰 합치면, 학생 이름 옆에 성적이 나란히 보인다.

  • INNER JOIN: 두 명부에 모두 있는 학생만 보여준다. 교집합.
  • OUTER JOIN: 한쪽에만 있어도 보여준다. 성적이 없는 학생도 목록에 포함.
    • LEFT: 왼쪽 테이블 기준, RIGHT: 오른쪽 기준, FULL: 양쪽 모두 포함.
  • CROSS JOIN: 모든 조합을 만든다. 상의 5벌 × 하의 3벌 = 15가지 코디 조합.
  • SELF JOIN: 같은 명부를 자기 자신과 조인. 직원 테이블에서 "직원-상사" 관계를 찾을 때.

JOIN 알고리즘​

  • Nested Loop Join: 이중 반복문. 첫 번째 명부의 한 줄마다 두 번째 명부를 처음부터 끝까지 훑는다. 데이터가 적을 때 효과적.
  • Sort Merge Join: 두 명부를 같은 기준으로 정렬한 후, 위에서 아래로 나란히 읽으며 매칭한다. 정렬된 큰 데이터에 유리.
  • Hash Join: 한쪽 명부로 해시표(색인)를 만들고, 다른 명부를 순서대로 읽으며 해시표에서 찾는다. 대용량 동등 조인에 효과적.

4.6 자연어 SQL 변환​

TEXT2SQL​

비유: 통역사

"지난달 매출 상위 10개 상품 알려줘"라는 자연어를 SQL로 번역해주는 기술이다. AI가 사람의 질문을 데이터베이스가 이해하는 언어로 자동 변환한다.

5. 트랜잭션 및 동시성 제어​

5.1 트랜잭션 개요​

트랜잭션(Transaction)​

비유: 은행 계좌 이체

A 계좌에서 출금하고 B 계좌에 입금하는 작업은 반드시 둘 다 성공하거나 둘 다 실패해야 한다. 이처럼 하나의 논리적 작업 단위를 트랜잭션이라 한다.

ACID 특성​

  • Atomicity(원자성): 전부 아니면 전무(All or Nothing). 이체 중 하나라도 실패하면 전부 취소된다.
  • Consistency(일관성): 이체 전후의 총 잔액은 동일해야 한다. 트랜잭션 전후에 데이터가 규칙을 만족해야 한다.
  • Isolation(격리성): 내가 이체하는 동안 다른 사람이 내 잔액을 봐도 중간 상태(출금만 된 상태)가 보이면 안 된다.
  • Durability(영속성): 이체 완료(커밋) 후에는 은행 시스템이 꺼져도 기록이 남아야 한다.

트랜잭션 상태​

  • Active: 작업 진행 중 (이체 처리 중)
  • Committed: 작업 완료·확정 (이체 완료)
  • Failed: 오류 발생 (이체 실패)
  • Aborted: 실패 후 원상복구 완료 (이체 취소, 잔액 복원)

5.2 병행 제어(Concurrency Control)​

병행제어(Concurrency Control)​

비유: 교차로의 신호등

여러 차(트랜잭션)가 동시에 교차로(데이터)를 지나려 할 때, 신호등(병행제어) 없이는 충돌한다.

병행제어 미수행 문제​

  • 갱신 분실(Lost Update): 두 사람이 동시에 같은 문서를 편집하면, 나중 저장한 사람의 내용만 남고 먼저 편집한 내용이 사라진다.
  • 모순성(Inconsistency): 한 사람은 반만 바꾼 데이터를 다른 사람이 읽어서 앞뒤가 안 맞는 결과를 얻는다.
  • 연쇄 복귀(Cascading Rollback): 한 트랜잭션이 실패하면, 그 결과를 참조한 다른 트랜잭션들도 연쇄적으로 취소해야 한다. 도미노처럼 쓰러지는 것.

병행제어 기법​

  • 로킹(Locking): 화장실 문 잠금. 누가 쓰고 있으면 다른 사람은 기다린다. 데이터에 잠금을 걸어 독점 사용한다.

  • 2PL(Two-Phase Locking): 잠금 획득 단계(Growing)와 잠금 해제 단계(Shrinking)를 엄격히 분리한다. 한 번 잠금을 풀기 시작하면 더 이상 새 잠금을 걸 수 없다.

  • 타임스탬프 순서(Timestamp Ordering): 먼저 온 사람에게 우선권. 각 트랜잭션에 시간표를 부여하고, 시간 순서대로 처리한다.

  • 낙관적 병행제어(Optimistic CC): "충돌은 거의 없겠지"라고 낙관하고 일단 실행한 뒤, 커밋 시점에 충돌을 검사한다. 충돌이 드문 환경에서 효과적.

  • MVCC(Multi Version Concurrency Control): 사진 앨범처럼 데이터의 여러 버전(스냅샷)을 유지한다. 읽는 사람은 과거 버전을 보고, 쓰는 사람은 새 버전을 만든다. 읽기-쓰기 충돌이 없어 성능이 좋다.

5.3 격리 수준(Isolation Level)​

격리 수준(Isolation Level)​

비유: 시험장의 칸막이 높이

칸막이가 높을수록(격리 수준↑) 옆 사람 답안이 안 보여 정확하지만, 시험 진행이 느려진다(성능↓).

  • READ UNCOMMITTED: 칸막이 없음. 옆 사람이 쓰다 지운 답도 보인다(Dirty Read 발생).
  • READ COMMITTED: 낮은 칸막이. 확정된 답만 보이지만, 두 번 볼 때 답이 바뀔 수 있다(Non-Repeatable Read 발생).
  • REPEATABLE READ: 높은 칸막이. 한 번 본 답은 변하지 않지만, 새로운 답안지가 추가될 수 있다(Phantom Read 발생).
  • SERIALIZABLE: 완전 밀폐. 순차 실행과 동일한 결과를 보장한다. 가장 안전하지만 가장 느리다.

5.4 이상 현상(Read Phenomena)​

  • Dirty Read: 다른 사람이 아직 확정하지 않은 답을 훔쳐보는 것. 그 답이 취소되면 잘못된 정보를 본 것이 된다.
  • Non-Repeatable Read: 같은 문제의 답을 두 번 봤는데 중간에 바뀌어 있는 것.
  • Phantom Read: 처음에 30명이었는데 다시 세니 31명. 유령처럼 새로운 행이 나타나거나 사라지는 것.
  • Lost Update: 두 명이 동시에 같은 위키 문서를 편집하면, 한 사람의 편집이 덮어씌워져 사라지는 것.

5.5 회복(Recovery)​

로그 기반 회복​

비유: 블랙박스 기록

비행기 블랙박스처럼 모든 변경 사항을 로그에 기록해두고, 사고(장애) 시 기록을 보고 복구한다.

체크포인트(Checkpoint)​

비유: 게임 세이브 포인트

게임 중간중간 저장하듯, 데이터베이스도 특정 시점의 상태를 저장해둔다. 장애 시 마지막 세이브 포인트부터 복구하면 된다.

WAL(Write-Ahead Logging)​

비유: 가계부를 먼저 쓰고 돈을 쓰기

실제 돈을 쓰기(데이터 변경) 전에 가계부(로그)에 먼저 기록한다. 이렇게 하면 돈을 쓰다가 문제가 생겨도 가계부를 보고 복구할 수 있다.

UNDO / REDO​

  • UNDO: 실행 취소(Ctrl+Z). 실패한 트랜잭션의 변경을 원래대로 되돌린다.
  • REDO: 다시 실행(Ctrl+Y). 성공한 트랜잭션의 변경을 다시 적용한다(로그를 보고 재실행).

6. 데이터베이스 튜닝 및 최적화​

6.1 옵티마이저​

옵티마이저(Optimizer)​

비유: 내비게이션

목적지(결과)까지 가는 여러 경로(실행 계획) 중 최적의 경로를 선택해주는 장치다.

  • RBO(Rule Based Optimizer): 정해진 규칙대로만 길을 안내하는 구형 내비. "고속도로 우선" 같은 고정 규칙을 따른다. 실시간 교통 상황을 모른다.
  • CBO(Cost Based Optimizer): 실시간 교통 정보를 반영하는 최신 내비. 통계 정보(데이터 분포, 테이블 크기)를 기반으로 비용이 가장 낮은 경로를 선택한다.

6.2 인덱스(Index)​

인덱스(Index)​

비유: 책 뒤의 색인(찾아보기)

800페이지 책에서 "트랜잭션"을 찾으려면 처음부터 읽어야 한다. 하지만 뒤의 색인을 보면 "트랜잭션: p.312"라고 바로 찾을 수 있다.

  • 클러스터드 인덱스(Clustered Index): 사전처럼 데이터 자체가 정렬되어 저장된다. 테이블당 하나만 가능. 국어사전은 가나다순으로 정렬되어 있는 것 자체가 클러스터드 인덱스다.

  • 논클러스터드 인덱스(Non-Clustered Index): 책 뒤의 색인처럼 별도의 목록이 있고, 실제 페이지 번호(포인터)를 가리킨다. 테이블당 여러 개 가능.

  • B-Tree / B+Tree 인덱스: 가장 대표적인 인덱스 구조. 균형 잡힌 나무(트리) 형태로 데이터를 계층적으로 나눠 빠르게 탐색한다. 도서관의 분류 체계(대분류→중분류→소분류→책)와 같다.

  • Hash Index: 해시 함수로 위치를 바로 계산. 사물함 번호를 공식으로 바로 알아내는 것. 정확한 값 검색은 매우 빠르지만 범위 검색은 불가.

  • Bitmap Index: 각 값에 대해 0/1 비트맵을 만든다. 성별(남/여)처럼 값의 종류가 적은 컬럼에 효과적. 출석부에서 O/X로 표시하는 것과 같다.

  • 함수 기반 인덱스: UPPER(name) 같은 함수 결과에 인덱스를 거는 것. 이름을 대문자로 변환한 별도의 색인을 만들어두는 것.

  • 커버링 인덱스(Covering Index): 인덱스만 읽으면 원하는 데이터가 다 나와서 본문(테이블)을 열 필요 없는 인덱스. 색인에 요약 정보까지 적혀 있어 본문을 펼치지 않아도 되는 것.

6.3 데이터베이스 튜닝​

데이터베이스 튜닝(Tuning)​

비유: 자동차 정비

차가 느리면 엔진 오일 교환, 타이어 공기압 조정, 경량화 등을 한다. DB 튜닝도 성능을 최적화하는 전반적 활동이다.

  • 설계 단계 튜닝: 차를 설계할 때부터 성능을 고려. 테이블 구조, 반정규화, 파티셔닝 결정.
  • SQL 튜닝: 운전 습관 개선. 비효율적인 SQL을 효율적으로 재작성.
  • 힌트(Hint): 내비에게 "이 길로 가"라고 강제 지정. 옵티마이저에게 특정 실행 방법을 지시.
  • 실행 계획(Execution Plan): 내비가 보여주는 경로 미리보기. SQL이 어떤 순서로 실행될지 보여주는 청사진.

6.4 인메모리 데이터베이스​

인메모리 데이터베이스(In-memory Database)​

비유: 책상 위에 펼쳐놓고 작업하기

서랍(디스크)에서 꺼내 쓰면 느리지만, 책상 위(메모리)에 다 펼쳐놓으면 바로 손이 닿아 빠르다. 데이터를 디스크 대신 메모리에 저장하여 극도로 빠른 읽기/쓰기를 제공한다.

  • Redis: 키-값 기반 인메모리 저장소. 포스트잇에 메모하듯 간단한 데이터를 초고속으로 저장/조회.
  • SAP HANA: 엔터프라이즈급 인메모리 DB. 기업의 모든 업무 데이터를 메모리에 올려 실시간 분석.
  • MemSQL: 분산 인메모리 SQL DB. 여러 책상에 데이터를 나눠 놓고 동시에 작업.

7. NoSQL​

7.1 NoSQL 개요​

NoSQL​

비유: 다양한 수납함

RDBMS가 규격화된 서류 캐비넷(행과 열이 딱딱 맞음)이라면, NoSQL은 용도에 따라 다른 형태의 수납함을 쓰는 것이다. 서류함, 파일 박스, 바구니, 그물망 등 데이터 형태에 맞는 저장 방식을 선택한다.

CAP 이론​

비유: 세 가지 중 두 가지만 고를 수 있는 뷔페

  • Consistency(일관성): 모든 손님이 같은 메뉴를 본다.
  • Availability(가용성): 어느 카운터에서든 항상 주문이 가능하다.
  • Partition tolerance(분할 내성): 주방 하나가 고장 나도 영업을 계속한다.

분산 시스템에서는 이 세 가지를 동시에 완벽히 만족시킬 수 없고, 두 가지만 선택해야 한다.

BASE 모델​

비유: "대충 맞으면 됐지" 철학

ACID가 "완벽한 정확성"을 추구한다면, BASE는 "대체로 사용 가능하고, 상태가 변할 수 있고, 결국에는 일관성이 맞춰진다"는 유연한 접근이다.

  • Basically Available: 기본적으로 응답 가능
  • Soft state: 시간에 따라 상태가 변할 수 있음
  • Eventual consistency: 시간이 지나면 결국 일관성이 맞춰짐

7.2 NoSQL 유형​

  • Key-Value Store: 사물함. 번호(키)로 물건(값)을 넣고 꺼낸다. 단순하고 빠르다. (Redis, DynamoDB)

  • Document Store: 파일 캐비넷. JSON/XML 문서를 통째로 저장한다. 문서 내부 구조로 검색 가능. (MongoDB)

  • Column Family Store: 엑셀 시트인데 행마다 열 개수가 다를 수 있다. 수십억 행의 대용량 데이터 처리에 적합. (Cassandra, HBase)

  • Graph Database: 인맥 지도. 노드(사람)와 엣지(관계)로 복잡한 관계를 표현. 소셜 네트워크, 추천 시스템에 적합. (Neo4j)

7.3 NoSQL 모델링​

NoSQL 데이터 모델링​

비유: 질문에 맞게 답안지를 미리 만들어 놓기

RDBMS는 데이터 중심으로 모델링하지만, NoSQL은 "어떤 질문(쿼리)을 할 것인가"를 먼저 정하고 그에 맞게 데이터 구조를 설계한다. 시험 문제를 미리 알고 답안지를 준비하는 것과 같다.

모델링 패턴​

  • Denormalization: 중복 저장으로 조인 없이 빠르게 조회
  • Aggregation: 관련 데이터를 하나의 문서에 모아 넣기
  • Application-side Join: 조인을 DB가 아닌 애플리케이션에서 처리

7.4 NoSQL 제품​

  • MongoDB: 가장 인기 있는 Document DB. JSON과 유사한 BSON 형식으로 유연한 스키마 제공.
  • Cassandra: 페이스북이 만든 Column Family DB. 대규모 쓰기에 강하다.
  • HBase: 하둡 위에서 동작하는 Column Family DB. 빅데이터 실시간 조회.
  • DynamoDB: AWS의 관리형 Key-Value DB. 서버리스, 자동 확장.
  • Redis: 초고속 인메모리 Key-Value Store. 캐시, 세션 관리에 주로 사용.
  • Neo4j: 대표적 Graph DB. 관계 탐색이 핵심인 서비스에 활용.

8. 데이터 웨어하우스 및 분석계 DB​

8.1 OLTP vs OLAP​

OLTP(Online Transaction Processing)​

비유: 편의점 POS 시스템

고객이 물건을 사면 바코드를 찍고, 재고를 깎고, 결제를 처리한다. 짧고 빈번한 트랜잭션을 실시간으로 처리하는 운영계 시스템이다.

OLAP(Online Analytical Processing)​

비유: 본사 경영 분석 시스템

"지난 분기 매출 추세는?", "지역별 상위 상품은?"처럼 대량의 데이터를 다양한 관점에서 분석하는 시스템이다.

분리 운영의 필요성: 편의점(OLTP)에서 분석 쿼리를 돌리면 결제가 느려진다. 그래서 분석용 시스템(OLAP)을 별도로 분리해 운영한다.

8.2 OLAP 유형​

  • MOLAP(Multidimensional OLAP): 데이터를 다차원 큐브 형태로 미리 계산해 저장. 루빅스 큐브처럼 시간·지역·상품 축으로 자유롭게 회전하며 본다.
  • ROLAP(Relational OLAP): 기존 관계형 DB 위에서 OLAP을 수행. 별도 큐브 없이 SQL로 분석.
  • HOLAP(Hybrid OLAP): MOLAP과 ROLAP의 장점을 결합.

데이터 큐브(Data Cube)​

비유: 루빅스 큐브

시간, 지역, 상품 등 여러 차원을 축으로 하는 입체 데이터 구조. 원하는 면을 돌려가며 다양한 관점으로 데이터를 본다.

OLAP 연산​

  • Drill-down: 연도→분기→월로 세부 수준으로 파고 들어가기. 확대경.
  • Roll-up: 월→분기→연도로 요약하기. 축소.
  • Slice: 큐브에서 한 면을 잘라내기. "2024년"만 고정하고 나머지 차원 보기.
  • Dice: 큐브에서 작은 조각을 잘라내기. 특정 조건의 부분 큐브 추출.
  • Pivot: 축을 바꿔 다른 관점에서 보기. 행과 열을 교체.

8.3 데이터 웨어하우스​

데이터 웨어하우스(Data Warehouse)​

비유: 중앙 창고

전국 매장의 판매 데이터를 한 곳의 대형 창고에 모아두고, 경영진이 분석에 활용한다. 주제 지향적, 통합적, 시간 변이적, 비휘발성이 특징이다.

로지컬 데이터 웨어하우스(LDW)​

비유: 가상 창고

물리적으로 데이터를 한 곳에 옮기지 않고, 여러 곳에 흩어진 데이터를 가상으로 통합해서 마치 하나의 창고처럼 보이게 한다.

데이터 마트(Data Mart)​

비유: 부서별 소형 창고

중앙 창고(DW)에서 마케팅팀용, 영업팀용으로 필요한 데이터만 뽑아 만든 소규모 창고다.

ETL / ELT​

  • ETL(Extract-Transform-Load): 데이터를 뽑고(Extract) → 정제·변환하고(Transform) → 창고에 넣는다(Load). 물건을 검수하고 포장한 뒤 창고에 입고.
  • ELT: 데이터를 먼저 창고에 넣고(Load) → 창고 안에서 변환(Transform). 일단 다 넣고 창고 안에서 정리. 클라우드 환경에서 선호.

8.4 차원 모델링​

스타 스키마(Star Schema)​

비유: 별 모양

중심에 팩트 테이블(매출 금액, 수량 등 측정값)이 있고, 주변에 차원 테이블(시간, 상품, 지역 등)이 별 꼭지처럼 붙어 있다. 단순하고 조회가 빠르다.

스노우플레이크 스키마(Snowflake Schema)​

비유: 눈송이 결정

스타 스키마에서 차원 테이블을 더 세분화(정규화)한 것이다. 별 꼭지에서 가지가 더 뻗어나가 눈송이 모양이 된다. 저장 공간은 절약되지만 조인이 많아진다.

갤럭시 스키마(Galaxy / Fact Constellation)​

비유: 은하수

여러 개의 별(스타 스키마)이 차원 테이블을 공유하며 모여 있는 구조다.

팩트 테이블 / 차원 테이블​

  • 팩트 테이블: 성적표의 점수 부분. 측정 가능한 수치 데이터(매출액, 수량)가 담긴다.
  • 차원 테이블: 성적표의 학생 정보, 과목 정보 부분. "누가, 언제, 어디서, 무엇을"에 해당하는 설명 데이터다.

8.5 데이터 레이크 및 진화형 저장소​

Data Lake​

비유: 호수

정제되지 않은 원수(Raw Data)를 그대로 모아두는 거대한 호수다. 정형, 비정형, 반정형 데이터를 형식 그대로 저장한다. 나중에 필요할 때 정제해서 사용한다.

Data Swamp​

비유: 관리 안 된 늪

Data Lake를 제대로 관리하지 않으면 데이터가 뒤죽박죽이 되어 아무도 원하는 데이터를 찾지 못하는 늪이 된다. 메타데이터 관리, 데이터 카탈로그의 부재가 원인이다.

Data Lakehouse​

비유: 호수 위에 지은 집

Data Lake의 유연한 저장과 Data Warehouse의 관리·분석 기능을 결합한 것이다. 호수(Lake)에 집(House)을 올려 호수의 장점(원시 데이터 저장)과 집의 장점(구조적 관리)을 모두 갖췄다.

Delta Lake / Apache Iceberg​

비유: 호수에 설치한 정수 시스템

Data Lake 위에 트랜잭션 관리, 스키마 관리, 타임 트래블(과거 시점 데이터 조회) 기능을 추가하는 오픈 포맷 레이어다.

9. 분산 데이터베이스 및 확장성​

9.1 분산 데이터베이스 개요​

분산 데이터베이스(Distributed Database)​

비유: 전국 체인 도서관

서울, 부산, 대전에 도서관 분관이 있지만 사용자는 마치 하나의 도서관처럼 이용할 수 있다.

분산 투명성(Distribution Transparency)​

비유: "체인이라는 걸 몰라도 되는 것"

  • 위치 투명성: 책이 서울관에 있는지 부산관에 있는지 알 필요 없다.
  • 분할 투명성: 백과사전이 여러 관에 나눠져 있어도 한 세트로 읽을 수 있다.
  • 중복 투명성: 인기 도서가 여러 관에 복사본이 있어도 사용자는 모른다.
  • 병행 투명성: 여러 사람이 동시에 대출해도 서로 영향 없다.
  • 장애 투명성: 부산관이 정전 되어도 서울관에서 서비스를 계속 받을 수 있다.

9.2 병렬 vs 분산 DB​

병렬 데이터베이스(Parallel Database)​

비유: 한 공장에 여러 생산 라인

하나의 건물(시스템) 안에서 여러 라인(프로세서)이 동시에 작업해 처리 속도를 높인다. 같은 지붕 아래 긴밀히 협력한다.

분산 데이터베이스​

비유: 전국 여러 공장

전국 곳곳에 공장이 있어 지역별로 독립 운영되면서 네트워크로 연결된다. 장애 내성이 높지만 통신 비용이 있다.

9.3 데이터 분할(Partitioning / Sharding)​

수평 분할(Horizontal Partitioning)​

비유: 학생 명부를 학년별로 나누기

같은 구조의 테이블을 행(레코드) 단위로 나눈다. 1학년 명부, 2학년 명부, 3학년 명부.

수직 분할(Vertical Partitioning)​

비유: 학생 명부를 항목별로 나누기

이름·학번은 기본 명부에, 성적은 성적 명부에, 건강 정보는 건강 명부에. 열(컬럼) 단위로 나눈다.

샤딩(Sharding)​

비유: 피자를 여러 조각으로 나눠 여러 접시에 담기

데이터를 조각(shard)으로 나눠 서로 다른 서버에 분산 저장한다. 파티셔닝과 유사하지만, 각 조각이 서로 다른 물리적 서버에 있다는 점이 다르다.

샤딩 전략​

  • Range Sharding: 학번 11000은 서버A, 10012000은 서버B. 범위로 분배.
  • Hash Sharding: 학번에 해시 함수를 적용해 서버를 결정. 균등 분배에 유리.
  • Directory Sharding: 별도의 배정표(디렉터리)를 보고 어느 서버에 있는지 찾는다.

9.4 분산 일관성 이론​

CAP 이론​

(7.1 참조) 분산 시스템에서 일관성, 가용성, 분할 내성 중 두 가지만 선택 가능하다.

PACELC 이론​

비유: CAP의 확장판

CAP이 "네트워크 분할(P) 시 C와 A 중 선택"이라면, PACELC은 "정상 상태(E=Else)에서도 지연(L)과 일관성(C) 사이의 트레이드오프가 있다"고 말한다. 비가 올 때(장애)뿐 아니라 맑은 날(정상)에도 선택이 필요하다.

Eventual Consistency vs Strong Consistency​

  • Eventual Consistency(최종 일관성): SNS 게시물이 친구에게 몇 초 뒤에 보이는 것. 시간이 지나면 결국 모두 같은 데이터를 보게 된다.
  • Strong Consistency(강한 일관성): 은행 잔액은 즉시 동기화. 어디서 보든 항상 같은 값.

9.5 데이터 복제(Replication)​

데이터 복제​

비유: 중요 문서의 사본 만들기

원본 문서를 여러 부서에 복사해두면 원본이 유실되어도 안전하고, 각 부서에서 빠르게 열람할 수 있다.

  • Master-Slave Replication: 원본(Master)만 수정 가능하고, 사본(Slave)은 읽기만 가능. 학급 게시판에 선생님만 쓰고 학생은 읽기만.
  • Master-Master Replication: 여러 곳에서 수정 가능. 공동 편집 문서. 충돌 관리가 복잡하다.
  • 동기 복제: 원본과 사본이 동시에 업데이트. 느리지만 일관성 보장.
  • 비동기 복제: 원본 먼저 업데이트하고 사본은 나중에. 빠르지만 잠시 불일치 가능.

10. 데이터 품질 및 거버넌스​

10.1 데이터 거버넌스​

데이터 거버넌스(Data Governance)​

비유: 데이터 헌법

국가가 헌법으로 운영 원칙을 정하듯, 조직이 데이터를 어떻게 수집·관리·활용·폐기할지의 원칙, 조직, 프로세스를 정하는 체계다.

데이터 주권(Data Sovereignty)​

비유: 영토 주권

자국 내 데이터는 자국 법률의 적용을 받는다. 한국 국민의 개인정보는 한국 법에 따라 처리해야 한다.

마스터 데이터 관리(MDM)​

비유: 표준 주소록

부서마다 고객 정보가 다르게 관리되면(마케팅팀: 김철수, 영업팀: 김 철수) 혼란이 생긴다. MDM은 "김철수"로 통일된 하나의 표준 정보를 유지 관리하는 것이다.

10.2 데이터 표준화​

데이터 표준화​

비유: 도량형 통일

A 부서는 cm, B 부서는 inch를 쓰면 소통이 안 된다. 모든 부서가 같은 단위, 같은 용어, 같은 형식을 쓰도록 통일하는 것이다.

  • 표준 용어: "고객"과 "클라이언트"를 "고객"으로 통일
  • 표준 도메인: 전화번호는 항상 VARCHAR(13) 형식
  • 표준 코드: 성별은 반드시 M/F로 표기
  • 명명 규칙: 테이블 이름은 "TB_", 컬럼은 "스네이크_케이스" 등

10.3 데이터 품질​

  • 데이터 무결성(Data Integrity): 데이터가 정확하고 완전한 상태. 건강 검진에서 모든 수치가 정상인 것.
  • 데이터 정합성(Data Consistency): 여러 시스템에서 같은 데이터가 동일한 값을 유지하는 것. 여권과 주민등록증의 이름이 같아야 하는 것.
  • 데이터 프로파일링(Data Profiling): 데이터의 현재 상태를 진단하는 건강검진. 이상값, 결측값, 분포를 분석한다.
  • 데이터 마이그레이션 검증: 이사 후 짐이 다 왔는지, 깨진 건 없는지 확인하는 것. 시스템 전환 시 데이터 정확성을 검증.
  • 데이터 관측가능성(Data Observability): 데이터 파이프라인의 CCTV. 데이터가 언제 변했는지, 어디서 문제가 생겼는지 실시간으로 모니터링한다.

10.4 데이터 품질관리 프레임워크​

데이터 품질관리 프레임워크​

비유: ISO 품질 인증 체계

제품 품질을 관리하듯, 데이터의 정확성·완전성·일관성·적시성을 체계적으로 관리하는 프레임워크다.

  • 데이터 관리: 데이터의 생성·변경·삭제 전반을 관리
  • 데이터 구조관리: 테이블, 관계, 제약조건의 체계적 관리
  • 품질관리 프로세스: 측정→평가→개선의 지속적 순환
  • 품질관리 아키텍처: 품질 도구, 메타데이터 저장소, 대시보드 등 기술 인프라
  • 데이터 품질 성숙도 모델: 조직의 데이터 품질 관리 수준을 단계별로 평가 (초기→관리→정의→정량→최적화)

10.5 데이터 품질 진단·개선​

  • 생명주기별 품질관리: 데이터의 탄생~폐기까지 각 단계마다 품질을 관리. 사람의 영유아→청소년→성인→노년 건강관리처럼.
  • 품질 진단 절차: 건강검진 프로세스. 대상 선정→진단 실행→결과 분석→개선 조치.
  • 예방적 품질관리: 병에 걸리기 전에 예방 접종하듯, 문제 발생 전에 품질 규칙을 적용.

10.6 데이터 가치 및 거래​

데이터 거래(Data Trade)​

비유: 원유 거래

데이터를 "21세기 원유"라고 부르듯, 데이터를 상품으로 사고파는 시장이다. 데이터 거래소에서 데이터셋을 매매한다.

데이터 가치평가​

비유: 부동산 감정평가

땅의 가치를 평가하듯, 데이터의 경제적 가치를 측정한다. 수익 접근법, 비용 접근법, 시장 접근법 등으로 가치를 산정한다.

11. 공간 데이터베이스 및 다차원 색인​

11.1 공간 DB 개요​

공간 데이터베이스(Spatial Database)​

비유: 디지털 지도 저장소

카카오맵이나 네이버 지도의 뒷단에서 건물, 도로, 공원의 위치와 형태를 저장하고 검색하는 데이터베이스다.

공간 데이터 타입​

  • Point: 지도의 핀(점). 음식점 위치.
  • Line: 도로, 강처럼 연결된 선.
  • Polygon: 건물 부지, 행정구역처럼 면적을 가진 영역.

11.2 공간 연산​

공간 연산자(Spatial Operator)​

비유: 지도 위에서 하는 질문들

  • 위상 연산(Topological): "이 건물이 이 구역 안에 있는가?" 포함·인접·교차 등 공간 관계 판단.
  • 거리 연산(Distance): "여기서 가장 가까운 병원은?" 두 객체 사이의 거리 계산.
  • 방향 연산(Direction): "학교 북쪽에 있는 공원은?" 방향을 기준으로 검색.
  • 메트릭 연산(Metric): "이 공원의 면적은?" 길이, 면적, 둘레 등 계량.
  • 집합 연산(Set): "A구역과 B구역의 겹치는 부분은?" 합집합·교집합·차집합.

11.3 공간 색인​

MBR(Minimum Bounding Rectangle)​

비유: 복잡한 도형을 감싸는 최소 직사각형

별 모양의 공원을 네모난 상자로 감싸서, 먼저 상자끼리 겹치는지 빠르게 검사한다. 상자가 겹치면 그때 정밀 검사.

R-Tree / R+Tree / R*Tree​

비유: 지도를 구역별로 접어 정리하는 방법

  • R-Tree: 공간 객체를 MBR로 감싸 트리 구조로 관리. 기본적이지만 MBR 겹침이 있을 수 있다.
  • R+Tree: MBR 겹침을 없앤 개선판. 객체가 여러 노드에 나뉠 수 있다.
  • R*Tree: 삽입·삭제 시 트리를 최적으로 재구성하는 가장 효율적인 R-Tree 변형.

Hilbert R-Tree​

비유: 실 한 가닥으로 모든 칸을 방문하는 동선

힐버트 곡선(공간을 채우는 곡선)을 이용해 2차원 공간을 1차원으로 매핑하여, 가까운 객체가 같은 노드에 들어가도록 한다.

Quad-Tree​

비유: 종이를 4등분하고, 또 4등분하는 것

공간을 4개 사분면으로 나누고, 데이터가 많은 사분면만 다시 4등분한다. 데이터 분포에 맞게 적응적으로 분할.

KD-Tree​

비유: X축으로 자르고, Y축으로 자르고 반복

각 깊이에서 하나의 차원(축)을 기준으로 공간을 이분할한다. K차원의 데이터를 효율적으로 탐색.

Grid File​

비유: 바둑판 격자

공간을 바둑판처럼 균등한 격자로 나누고, 각 칸에 데이터를 배정한다. 단순하지만 데이터 분포가 불균등하면 비효율적.

11.4 다차원 색인 구조​

다차원 색인구조(Multidimensional Index)​

비유: 여러 기준으로 동시에 검색하는 색인

도서관에서 "저자이면서 동시에 출판연도이면서 동시에 장르"로 책을 찾으려면 여러 차원을 동시에 다루는 색인이 필요하다. R-Tree, KD-Tree, Grid File 등이 이 역할을 한다.

12. 해싱 및 신기술 DB​

12.1 해싱(Hashing)​

해시 함수(Hash Function)​

비유: 사물함 번호 공식

학번 20240001을 공식에 넣으면 "37번 사물함"이라는 결과가 나온다. 데이터를 고정 길이의 주소로 변환하는 함수다.

정적 해싱(Static Hashing)​

비유: 고정된 사물함 수

사물함이 100개로 고정. 학생이 200명이 되면 한 사물함에 여러 명이 겹친다(충돌).

동적 해싱(Dynamic Hashing)​

비유: 필요에 따라 사물함을 늘리는 것

학생이 늘면 사물함도 자동으로 추가된다.

확장성 해싱(Extendible Hashing)​

비유: 전화번호부의 색인 탭

처음에는 AZ 하나의 탭이지만, 항목이 많아지면 AM, NZ로 분할하고, 더 늘면 AF, G~M 식으로 디렉터리를 확장한다. 버킷이 넘치면 디렉터리를 두 배로 확장하고 데이터를 재분배한다.

충돌 회피(Collision Resolution)​

비유: 같은 사물함에 두 사람이 배정된 경우 해결법

  • 체이닝: 사물함 옆에 보조 서랍을 연결
  • 개방 주소법: 빈 사물함을 찾아 다른 곳에 넣기

선형 해싱(Linear Hashing)​

비유: 사물함을 한 칸씩 순서대로 추가

확장성 해싱이 디렉터리를 두 배로 늘리는 반면, 선형 해싱은 한 버킷씩 순차적으로 분할한다. 점진적 확장.

12.2 벡터 데이터베이스​

벡터 데이터베이스(Vector Database)​

비유: 의미 기반 도서관

일반 도서관은 제목·저자로 찾지만, 벡터 DB는 "이 책과 비슷한 내용의 책"을 찾아준다. 텍스트, 이미지, 음성을 숫자 벡터(좌표)로 변환해 저장하고, 의미적으로 가까운 것을 검색한다.

HNSW(Hierarchical Navigable Small World)​

비유: 계층적 인맥 네트워크

상위 층에서는 핵심 인물(대표 벡터)끼리 연결하고, 하위 층에서는 더 세밀한 연결을 가진다. 검색 시 상위 층에서 대략적 방향을 잡고 하위 층에서 정밀 탐색한다.

IVF(Inverted File Index)​

비유: 동네별 전화번호부

벡터를 여러 그룹(클러스터)으로 미리 나눠두고, 검색 시 가장 가까운 그룹만 탐색한다. 전국을 다 뒤지지 않고 해당 동네 전화번호부만 보는 것.

PQ(Product Quantization)​

비유: 벡터 압축 기법

고차원 벡터를 작은 조각으로 나눠 각 조각을 대표 코드로 압축한다. 정밀도를 약간 포기하고 메모리와 속도를 크게 절약한다.

ANN(Approximate Nearest Neighbor) 검색​

비유: "정확히 가장 가까운 곳" 대신 "거의 가장 가까운 곳" 찾기

100% 정확한 최근접 이웃을 찾으려면 모든 데이터를 비교해야 하지만, 95% 정도의 정확도로 1000배 빠르게 찾는 방법이다.

임베딩 기반 검색​

비유: 뜻으로 찾기

"강아지"와 "퍼피"는 글자는 다르지만 의미가 비슷하다. 텍스트를 벡터(숫자 좌표)로 변환(임베딩)하면 의미가 비슷한 것들이 가까운 좌표에 위치하여 의미 기반 검색이 가능하다.

12.3 신기술 데이터베이스​

NewSQL​

비유: RDBMS의 안정성 + NoSQL의 확장성을 합친 하이브리드 자동차

기존 SQL의 ACID 보장과 NoSQL의 수평 확장성을 모두 제공한다. 관계형 DB의 신뢰성을 유지하면서 대규모 분산 처리가 가능하다.

Time Series Database​

비유: 주가 차트 전용 저장소

시간 순서로 쌓이는 데이터(주가, 센서값, 로그)를 효율적으로 저장·조회한다. (InfluxDB, TimescaleDB)

Graph Database​

비유: 인맥 관계도 전문 저장소

"A가 B를 알고, B가 C를 안다. A에서 C까지 가는 경로는?"처럼 관계 탐색에 특화된 DB. (Neo4j, JanusGraph)

Multi-Model Database​

비유: 만능 수납함

Key-Value, Document, Graph 등 여러 모델을 하나의 DB에서 지원한다. 상황에 따라 적합한 모델로 데이터에 접근. (ArangoDB, CosmosDB)

Cloud Native DB​

비유: 클라우드에서 태어난 DB

처음부터 클라우드 환경에 맞게 설계된 DB. 자동 확장, 고가용성, 관리 편의성이 핵심. (Aurora, Spanner, CosmosDB)

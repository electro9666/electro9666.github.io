01. 소프트웨어공학

1. 개발방법론​

1.1 전통적 방법론​

1.1.1 순차형 개발​

  • Waterfall: 요구분석→설계→구현→테스트를 순차적으로 진행하는 폭포수 모델
  • V-Model: 개발 단계마다 대응되는 검증(테스트) 단계를 대칭으로 배치한 모델

1.1.2 반복형 개발​

  • Spiral: 위험 분석을 중심으로 계획-분석-개발-평가를 나선형으로 반복하는 모델
  • Evolutionary: 초기 버전을 점진적으로 개선·진화시켜 완성하는 개발 방식

1.1.3 증분형 개발​

  • Incremental: 시스템을 여러 증분(모듈)으로 나눠 순차적으로 개발·통합하는 방식
  • Prototype: 시제품을 먼저 만들어 요구사항을 검증하고 구체화하는 방식
  • RAD: 프로토타이핑과 도구를 활용해 단기간에 개발하는 신속 개발 방법론

1.1.4 프로세스 중심​

  • RUP: UML 기반의 반복적·점진적 통합 프로세스 프레임워크

1.2 Agile 방법론​

1.2.1 Agile 기본개념​

  • Agile Manifesto: 개인·협업·변화 대응을 강조한 애자일 4대 가치 선언문
  • Agile Principles: 애자일 선언을 뒷받침하는 12가지 실천 원칙
  • Agile Mindset: 변화 수용과 지속적 개선을 지향하는 애자일 사고방식

1.2.2 Agile Framework​

  • Scrum: 스프린트 단위로 반복 개발하는 대표적 애자일 프레임워크
  • XP: 짧은 주기 반복과 기술적 실천(TDD·페어)을 강조하는 익스트림 프로그래밍
  • Kanban: 작업 흐름 시각화와 WIP 제한으로 흐름을 관리하는 방법
  • Crystal: 팀 규모·중요도에 따라 유연하게 조정하는 경량 방법론군
  • FDD: 기능(Feature) 단위로 계획·개발하는 기능 주도 개발
  • DSDM: 비즈니스 가치와 정해진 일정·예산을 중시하는 동적 시스템 개발 방법

1.2.3 Scaled Agile​

  • SAFe: 대규모 조직에 애자일을 확장 적용하는 프레임워크
  • LeSS: 스크럼을 대규모 팀으로 최소한의 확장으로 적용하는 방식
  • Nexus: 여러 스크럼 팀의 통합을 다루는 확장 프레임워크
  • Spotify Model: 스쿼드·트라이브 등 자율 조직 기반의 애자일 문화 모델

1.2.4 Agile 운영​

  • Sprint: 일정 기간 동안 목표를 완수하는 반복 개발 주기
  • Product Backlog: 제품에 필요한 요구사항을 우선순위로 정리한 목록
  • Sprint Backlog: 해당 스프린트에서 수행할 작업 목록
  • Product Owner: 제품 가치와 백로그 우선순위를 책임지는 역할
  • Scrum Master: 스크럼 프로세스를 촉진하고 장애를 제거하는 역할
  • Daily Scrum: 매일 진행상황을 공유하는 짧은 일일 미팅
  • Sprint Review: 스프린트 결과물을 이해관계자에게 시연·검토하는 회의
  • Sprint Retrospective: 스프린트 과정을 돌아보고 개선점을 찾는 회고

1.2.5 Agile 측정​

  • Velocity: 스프린트당 완료 작업량을 나타내는 팀 개발 속도 지표
  • Burndown Chart: 남은 작업량이 시간에 따라 줄어드는 추이를 보여주는 차트
  • Burnup Chart: 완료된 작업량 증가와 전체 범위를 함께 보여주는 차트
  • Planning Poker: 카드로 합의하며 작업량을 추정하는 기법

1.3 DevOps​

1.3.1 DevOps 기본​

  • DevOps: 개발과 운영을 통합해 배포 속도와 품질을 높이는 문화·실천
  • CALMS: 문화·자동화·린·측정·공유로 구성된 데브옵스 성숙도 프레임워크
  • Three Ways: 흐름·피드백·지속학습을 강조하는 데브옵스 3대 원칙

1.3.2 Continuous Practice​

  • CI: 코드 변경을 자주 통합·빌드·검증하는 지속적 통합
  • Continuous Testing: 파이프라인 전 과정에서 자동으로 테스트하는 지속적 테스트
  • Continuous Delivery: 언제든 배포 가능한 상태를 유지하는 지속적 전달
  • Continuous Deployment: 검증 통과 시 자동으로 운영에 배포하는 지속적 배포
  • Continuous Monitoring: 운영 상태를 상시 감시하는 지속적 모니터링
  • Continuous Feedback: 사용자·시스템 피드백을 지속적으로 수집·반영하는 활동

1.3.3 DevOps 확장​

  • DevSecOps: 개발 전 과정에 보안을 통합한 데브옵스 확장
  • GitOps: Git을 단일 소스로 삼아 인프라·배포를 선언적으로 관리
  • DataOps: 데이터 파이프라인에 데브옵스 원칙을 적용한 방식
  • MLOps: 머신러닝 모델의 개발·배포·운영을 자동화하는 실천
  • Platform Engineering: 개발자 셀프서비스를 위한 내부 플랫폼을 구축하는 분야

1.4 컴포넌트 기반 개발​

1.4.1 Component​

  • CBD: 재사용 가능한 컴포넌트를 조립해 개발하는 방법론
  • Component: 독립적으로 배포·조립 가능한 소프트웨어 구성 단위
  • Framework: 공통 구조와 흐름을 제공하는 재사용 가능한 개발 골격

1.4.2 재사용​

  • Reuse: 기존 자산을 재활용해 생산성과 품질을 높이는 개념
  • Product Line: 공통 자산을 기반으로 유사 제품군을 개발하는 전략
  • Software Factory: 자동화·표준화로 소프트웨어를 공장식으로 생산하는 방식

1.5 최신 개발방법​

1.5.1 생산성 향상​

  • Low Code: 최소한의 코딩으로 앱을 개발하는 플랫폼 기반 방식
  • No Code: 코딩 없이 시각적 도구로 앱을 개발하는 방식
  • Citizen Development: 비개발자가 직접 애플리케이션을 만드는 개발 문화

1.5.2 개발문화​

  • InnerSource: 오픈소스 방식을 사내 개발에 적용하는 협업 문화
  • Open Source Development: 소스를 공개하고 공동체가 함께 개발하는 방식

1.5.3 AI 개발​

  • AI Assisted Development: AI 도구로 코딩·개발을 보조받는 방식
  • AI Pair Programming: AI가 짝 프로그래머처럼 실시간 코딩을 지원하는 방식

2. 요구사항공학​

2.1 요구사항 개발​

2.1.1 요구사항 도출​

  • Elicitation: 이해관계자로부터 요구사항을 이끌어내는 활동
  • Stakeholder Analysis: 이해관계자를 식별하고 요구·영향을 분석하는 활동

2.1.2 요구사항 분석​

  • Analysis: 도출된 요구사항을 정제·구조화하는 분석 활동
  • Negotiation: 상충하는 요구사항을 조정·합의하는 활동

2.1.3 요구사항 명세​

  • Specification: 요구사항을 명확한 문서로 기술하는 활동
  • SRS: 소프트웨어 요구사항을 체계적으로 정리한 명세서

2.1.4 요구사항 확인​

  • Validation: 올바른 제품을 만드는지(요구 충족) 확인하는 활동
  • Verification: 제품을 올바르게 만드는지(명세 준수) 검증하는 활동

2.2 요구사항 관리​

2.2.1 변경관리​

  • Change Management: 요구사항 변경을 통제·추적·반영하는 관리 활동
  • Baseline: 합의되어 변경 통제의 기준이 되는 확정된 산출물
  • Version: 산출물의 변경 이력을 구분하는 버전 정보

2.2.2 추적관리​

  • Traceability: 요구사항과 산출물 간의 연관성을 추적하는 능력
  • Impact Analysis: 변경이 미치는 영향 범위를 분석하는 활동

2.2.3 우선순위​

  • Prioritization: 요구사항의 중요도·순서를 정하는 활동
  • MoSCoW: Must·Should·Could·Won't로 우선순위를 분류하는 기법

2.3 요구사항 표현​

2.3.1 사용자 중심​

  • User Story: 사용자 관점에서 짧게 기술한 요구사항
  • Persona: 대표 사용자 유형을 구체화한 가상의 인물
  • Story Map: 사용자 활동 흐름에 따라 스토리를 배치한 지도

2.3.2 모델링​

  • Use Case: 시스템과 사용자 간 상호작용을 기술한 사례
  • Scenario: 특정 상황에서의 사용 흐름을 구체적으로 서술한 것
  • Activity: 작업의 처리 흐름·절차를 표현한 모델

2.3.3 완료조건​

  • Acceptance Criteria: 요구사항 충족 여부를 판단하는 인수 기준

2.4 요구사항 품질​

2.4.1 품질기준​

  • SMART: 구체적·측정가능·달성가능·현실적·기한 있는 요구 기준
  • IEEE 830: 소프트웨어 요구사항 명세 작성 표준

2.4.2 요구사항 유형​

  • Functional Requirement: 시스템이 수행해야 할 기능적 요구사항
  • Non-functional Requirement: 성능·보안 등 품질 속성에 대한 비기능 요구사항

2.4.3 품질평가​

  • Requirement Quality: 완전성·일관성 등 요구사항의 품질 특성

3. 분석 및 설계​

3.1 구조적 분석​

3.1.1 분석기법​

  • DFD: 데이터의 흐름과 처리 과정을 표현하는 데이터 흐름도
  • STD: 시스템의 상태 변화와 전이를 표현하는 상태 전이도
  • Decision Tree: 조건 분기를 트리 형태로 표현한 의사결정 도구
  • Decision Table: 조건과 행동의 조합을 표로 정리한 의사결정표

3.1.2 데이터모델​

  • ERD: 개체와 관계를 표현하는 개체-관계 다이어그램

3.2 객체지향​

3.2.1 객체지향 개념​

  • Class: 객체의 속성과 행위를 정의한 틀
  • Object: 클래스로부터 생성된 실체(인스턴스)
  • Encapsulation: 데이터와 기능을 묶고 내부를 은닉하는 캡슐화
  • Inheritance: 상위 클래스의 특성을 물려받는 상속
  • Polymorphism: 동일 인터페이스가 다르게 동작하는 다형성
  • Abstraction: 핵심만 드러내고 세부를 숨기는 추상화

3.2.2 객체지향 원칙​

  • SOLID: 객체지향 설계의 5가지 핵심 원칙
  • GRASP: 책임 할당을 위한 일반적 설계 원칙 패턴

3.2.3 객체지향 설계​

  • Responsibility Driven Design: 책임을 중심으로 객체를 설계하는 기법

3.3 UML​

3.3.1 구조 다이어그램​

  • Class Diagram: 클래스와 관계를 표현하는 구조 다이어그램
  • Component Diagram: 컴포넌트 구성과 의존을 표현하는 다이어그램
  • Deployment Diagram: 하드웨어에 소프트웨어 배치를 표현하는 다이어그램

3.3.2 행위 다이어그램​

  • Sequence Diagram: 객체 간 시간 순 메시지 흐름을 표현하는 다이어그램
  • Activity Diagram: 처리 흐름·분기를 표현하는 활동 다이어그램
  • State Diagram: 객체의 상태 변화를 표현하는 상태 다이어그램

3.4 디자인패턴​

3.4.1 생성패턴​

  • Singleton: 인스턴스를 하나만 생성해 공유하는 패턴
  • Factory: 객체 생성을 하위 클래스에 위임하는 패턴
  • Builder: 복잡한 객체를 단계적으로 조립해 생성하는 패턴

3.4.2 구조패턴​

  • Adapter: 호환되지 않는 인터페이스를 연결하는 패턴
  • Decorator: 객체에 기능을 동적으로 덧붙이는 패턴
  • Facade: 복잡한 서브시스템에 단순한 통합 인터페이스를 제공하는 패턴

3.4.3 행위패턴​

  • Strategy: 알고리즘을 캡슐화해 교체 가능하게 하는 패턴
  • Observer: 상태 변화를 구독자에게 통지하는 패턴
  • Command: 요청을 객체로 캡슐화해 실행·취소를 관리하는 패턴

3.4.4 기타​

  • GoF Pattern: 4인방이 정리한 23가지 대표 디자인 패턴
  • Anti Pattern: 흔히 저지르는 잘못된 설계·관행

4. 구현​

4.1 구현 품질​

4.1.1 코딩품질​

  • Coding Standard: 일관된 코드 작성을 위한 코딩 표준·규칙
  • Clean Code: 읽기 쉽고 유지보수하기 좋은 코드 작성 원칙
  • Refactoring: 동작을 유지하며 코드 구조를 개선하는 활동

4.1.2 협업​

  • Pair Programming: 두 명이 함께 코딩하며 품질을 높이는 방식
  • Code Review: 동료가 코드를 검토해 결함·개선점을 찾는 활동

4.1.3 분석​

  • Static Analysis: 실행 없이 코드를 분석해 결함을 찾는 기법
  • Technical Debt: 빠른 개발로 누적된 기술적 부채

4.1.4 보안​

  • Secure Coding: 취약점을 예방하며 코드를 작성하는 보안 코딩

5. 테스트​

5.1 테스트 수준​

5.1.1 테스트 단계​

  • Unit Test: 개별 모듈·함수를 검증하는 단위 테스트
  • Integration Test: 모듈 간 연동을 검증하는 통합 테스트
  • System Test: 전체 시스템을 요구사항 기준으로 검증하는 테스트
  • Acceptance Test: 사용자 관점에서 인수 기준을 검증하는 테스트

5.2 테스트 기법​

5.2.1 명세기반​

  • Black Box: 내부 구조 없이 입출력으로 검증하는 명세 기반 기법
  • Boundary Value: 경계값 주변을 집중 검증하는 기법
  • Equivalence Partition: 입력을 동등 그룹으로 나눠 대표값을 검증하는 기법

5.2.2 구조기반​

  • White Box: 내부 논리·경로를 기준으로 검증하는 구조 기반 기법

5.2.3 경험기반​

  • Gray Box: 내부 일부를 알고 수행하는 혼합 방식 테스트
  • Mutation Test: 코드를 변형해 테스트의 결함 검출력을 평가하는 기법
  • Decision Table Test: 조건 조합을 표로 정리해 검증하는 기법

5.3 테스트 자동화​

5.3.1 개발기반​

  • TDD: 테스트를 먼저 작성하고 구현하는 테스트 주도 개발
  • BDD: 행위 명세를 기반으로 개발하는 행위 주도 개발
  • ATDD: 인수 기준을 먼저 정의하고 개발하는 방식

5.3.2 자동화도구​

  • Selenium: 웹 브라우저 동작을 자동화하는 테스트 도구
  • Test Automation: 테스트 실행을 자동화하는 기법·체계

5.4 테스트 관리​

5.4.1 테스트 지표​

  • Test Coverage: 테스트가 코드를 얼마나 검증했는지 나타내는 지표
  • Defect Density: 규모 대비 결함 수를 나타내는 결함 밀도
  • Reliability Growth: 결함 제거에 따른 신뢰성 향상 추이
  • Test Maturity: 조직의 테스트 프로세스 성숙도

6. 형상관리​

6.1 SCM​

6.1.1 버전관리​

  • Git: 분산 방식으로 소스 변경 이력을 관리하는 버전관리 도구
  • Branch Strategy: 브랜치 운영 방식을 정의한 전략
  • Merge: 서로 다른 브랜치의 변경을 병합하는 활동

6.1.2 빌드배포​

  • Build: 소스를 실행 가능한 산출물로 변환하는 과정
  • Release: 검증된 산출물을 배포용으로 공식화하는 활동
  • Artifact Repository: 빌드 산출물을 저장·관리하는 저장소

6.1.3 감사​

  • Configuration Audit: 형상 항목의 정합성·완전성을 검증하는 감사

7. 품질관리​

7.1 품질모델​

7.1.1 국제표준​

  • ISO/IEC 25010: 소프트웨어 제품 품질 특성을 정의한 표준
  • ISO/IEC 12207: 소프트웨어 생명주기 프로세스 표준
  • ISO/IEC 15504: 프로세스 능력 평가(SPICE) 표준

7.1.2 성숙도​

  • CMMI: 조직의 프로세스 성숙도를 평가하는 통합 모델
  • SPICE: 프로세스 능력을 평가하는 국제 표준 모델

7.1.3 품질모델​

  • McCall: 제품 운영·수정·전이 관점의 품질 모델
  • Boehm: 사용성·유지보수성 등 계층적 품질 모델
  • Dromey: 제품 특성과 품질 속성을 연결한 품질 모델

7.2 품질측정​

7.2.1 품질지표​

  • Software Metrics: 소프트웨어를 정량적으로 측정하는 지표
  • Reliability: 일정 조건에서 오류 없이 동작하는 신뢰성
  • Maintainability: 수정·개선의 용이성을 나타내는 유지보수성
  • Defect: 요구와 다르게 동작하게 하는 결함

8. 유지보수​

8.1 유지보수 유형​

8.1.1 유지보수​

  • Corrective: 발견된 결함을 수정하는 교정 유지보수
  • Adaptive: 환경 변화에 맞춰 적응시키는 유지보수
  • Perfective: 기능·성능을 개선하는 완전화 유지보수
  • Preventive: 잠재 문제를 사전에 예방하는 유지보수

8.2 시스템 현대화​

8.2.1 현대화 기법​

  • Reverse Engineering: 기존 시스템을 분석해 설계를 복원하는 기법
  • Reengineering: 기존 시스템을 재구조화해 개선하는 기법
  • Legacy Modernization: 노후 시스템을 최신 기술로 현대화하는 활동

9. 생산성 및 관리​

9.1 생산성​

9.1.1 측정기법​

  • Function Point: 기능 규모를 기준으로 산정하는 기능점수 기법
  • LOC: 소스 코드 라인 수로 규모를 측정하는 기법
  • COCOMO: 규모 기반으로 비용·공수를 추정하는 모델
  • Putnam: 시간과 노력의 관계로 비용을 추정하는 모델

9.1.2 프로세스​

  • PSP: 개인의 개발 프로세스를 개선하는 방법
  • TSP: 팀 단위 개발 프로세스를 개선하는 방법

9.1.3 지원도구​

  • CASE: 개발 활동을 지원하는 자동화 도구
  • Repository: 개발 산출물을 저장·관리하는 저장소
  • Knowledge Management: 조직의 지식을 축적·공유하는 관리 체계

10. 최신 소프트웨어공학​

10.1 AI 기반 SW공학​

10.1.1 AI 활용​

  • AI Software Engineering: AI를 소프트웨어 개발 전반에 활용하는 분야
  • AI Pair Programming: AI가 짝처럼 실시간 코딩을 지원하는 방식

10.2 지속가능성​

10.2.1 Green IT​

  • Green Software: 에너지 효율을 고려해 개발하는 친환경 소프트웨어
  • Sustainable Software: 장기적 지속가능성을 고려한 소프트웨어

10.3 공급망​

10.3.1 공급망 보안​

  • Software Supply Chain: 개발·배포에 이르는 소프트웨어 공급망
  • SBOM: 소프트웨어 구성요소를 목록화한 자재명세서
  • Open Source Governance: 오픈소스 사용을 관리·통제하는 거버넌스

10.4 플랫폼​

10.4.1 플랫폼​

  • Digital Engineering: 디지털 모델 기반으로 시스템을 개발하는 공학
  • Inner Development Platform: 개발자 셀프서비스를 위한 내부 개발 플랫폼

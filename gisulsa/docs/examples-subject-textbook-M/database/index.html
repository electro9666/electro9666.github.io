1. 데이터 모델링​

1.1 ERD와 표기법​

데이터 모델링(Data Modeling)은 현실 세계의 업무 요건을 데이터 관점에서 추상화하여 표현하는 과정이다. 개념적 모델링(ERD), 논리적 모델링(릴레이션 스키마), 물리적 모델링(테이블 DDL) 세 단계로 진행되며, 각 단계는 추상화 수준을 낮추면서 구현 세부사항을 구체화한다. ERD(Entity Relationship Diagram)는 엔터티, 속성, 관계를 시각적으로 표현하며 IE 표기법, 바커(Barker) 표기법, UML 클래스 다이어그램 등 다양한 표기법이 사용된다.

카디널리티(Cardinality)는 두 엔터티 간 관계에서 한 엔터티 인스턴스가 상대 엔터티 인스턴스에 대응하는 수를 의미한다. 1:1, 1:N, M:N 관계로 분류되며, M:N 관계는 물리 설계 시 연관 엔터티(교차 테이블)로 분해해야 한다. 관계에서 식별(Identification) 관계는 부모 엔터티의 기본키가 자식 엔터티의 기본키 일부로 사용되는 강한 의존 관계이고, 비식별(Non-Identification) 관계는 부모 기본키가 자식의 일반 외래키로만 사용되는 약한 의존 관계이다.

CRUD 매트릭스는 프로세스(기능)와 엔터티(데이터) 간의 Create, Read, Update, Delete 연산을 행렬로 표현하여 데이터 흐름을 검증하는 도구이다. 모든 엔터티에 C 오퍼레이션이 존재하는지, 업무 프로세스가 누락된 데이터를 참조하지 않는지 확인하는 데 활용된다. 공공기관의 데이터베이스 표준화 지침에서는 테이블 정의서, 컬럼 정의서, 코드 정의서 등의 산출물을 통해 데이터 표준을 유지하도록 규정한다.

1.2 정규화​

정규화(Normalization)는 릴레이션에 존재하는 함수적 종속성을 분석하여 이상현상(Anomaly)을 제거하고 데이터 중복을 최소화하는 과정이다. 이상현상에는 삽입 이상(불필요한 데이터 삽입), 삭제 이상(의도치 않은 데이터 손실), 갱신 이상(일부 레코드만 갱신되어 불일치 발생)의 세 가지 유형이 있다. 정규화는 제1정규형(1NF: 원자값), 제2정규형(2NF: 부분 함수 종속 제거), 제3정규형(3NF: 이행 함수 종속 제거), BCNF(결정자가 후보키), 제4정규형(4NF: 다치 종속 제거), 제5정규형(5NF: 조인 종속 제거) 순으로 진행된다.

제4정규형(4NF)은 릴레이션에서 다치 종속(Multi-valued Dependency)을 제거하는 단계다. 다치 종속이란 속성 A가 속성 B의 값들의 집합을 결정하지만 C와는 독립적인 상황을 의미하며, A ↠ B로 표기한다. 예를 들어 교수-과목-교재 릴레이션에서 교수와 과목, 교수와 교재가 독립적으로 다치 종속이면 4NF 위반이므로 두 릴레이션으로 분리해야 한다. 제5정규형(5NF)은 조인 종속(Join Dependency)을 제거하는 단계로, 릴레이션이 무손실 분해되는 모든 조인 종속이 후보키에 의해서만 함의될 때 5NF를 만족한다.

정규화의 효과로는 데이터 중복 제거, 이상현상 방지, 유지보수성 향상이 있으며, 단점으로는 조인 증가로 인한 조회 성능 저하가 있다. 이를 보완하기 위해 반정규화를 선택적으로 적용한다.

1.3 반정규화​

반정규화(Denormalization)는 정규화된 데이터 모델에서 조회 성능 향상을 위해 의도적으로 중복을 허용하거나 테이블을 합치는 기법이다. 반정규화 유형으로는 테이블 병합(1:1 또는 1:N 관계 테이블 합치기), 테이블 분리(수직 분할, 수평 분할), 중복 컬럼 추가(자주 조인되는 컬럼 중복), 파생 컬럼 추가(집계 결과를 별도 컬럼에 저장), 이력 테이블 추가 등이 있다. 반정규화는 성능상 명확한 이득이 있을 때만 적용해야 하며, 데이터 일관성 유지를 위한 추가 로직이 필요하다.

반정규화를 적용하기 전에는 인덱스 추가, 뷰(View) 생성, 클러스터링 등 성능 개선 방안을 먼저 검토해야 한다. 반정규화로 인한 데이터 중복은 DML 성능 저하와 무결성 훼손 위험을 동반하므로, 트리거(Trigger)나 애플리케이션 로직으로 동기화를 보장해야 한다. 데이터베이스 설계 단계 튜닝의 핵심 기법 중 하나로, 반정규화는 쿼리 빈도와 데이터 변경 빈도를 분석하여 전략적으로 결정한다.

1.4 무결성 제약​

무결성 제약(Integrity Constraint)은 데이터베이스에 저장된 데이터의 정확성과 일관성을 보장하기 위한 규칙이다. 릴레이션 무결성의 주요 유형으로는 도메인 무결성(속성값이 정의된 도메인 범위 내), 개체 무결성(기본키는 NULL 불가, 유일성 보장), 참조 무결성(외래키는 참조 릴레이션의 기본키 값이거나 NULL), 사용자 정의 무결성(업무 규칙 기반 제약)이 있다. 이를 SQL의 PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL 제약으로 구현한다.

참조 무결성(Referential Integrity)은 정보 모델링에서 가장 중요한 제약 중 하나다. 부모 레코드 삭제 시 자식 레코드를 어떻게 처리할지에 대해 CASCADE(연쇄 삭제), RESTRICT(삭제 불가), SET NULL(NULL로 설정), SET DEFAULT(기본값으로 설정) 등의 옵션을 지정할 수 있다. 무결성 제약은 DBMS 엔진 수준에서 강제되므로 애플리케이션 레이어의 실수를 방어하는 안전망 역할을 한다.

2. SQL​

2.1 DDL / DML / DCL​

SQL(Structured Query Language)은 관계형 데이터베이스의 표준 질의 언어로, DDL(Data Definition Language), DML(Data Manipulation Language), DCL(Data Control Language), TCL(Transaction Control Language)로 구분된다. DDL은 데이터 구조를 정의하는 명령어로 CREATE, ALTER, DROP, TRUNCATE가 있으며, 실행 즉시 자동 커밋된다. DML은 데이터를 조작하는 명령어로 SELECT, INSERT, UPDATE, DELETE가 있으며 트랜잭션 단위로 관리된다.

DCL은 데이터베이스 접근 권한을 제어하는 명령어로 GRANT(권한 부여)와 REVOKE(권한 회수)가 있다. 권한은 시스템 권한(데이터베이스 작업 전반)과 객체 권한(특정 테이블·뷰·프로시저에 대한 조작)으로 나뉘며, ROLE을 통해 권한을 묶어 일괄 부여할 수 있다. TCL은 트랜잭션을 제어하는 COMMIT, ROLLBACK, SAVEPOINT 명령을 포함한다.

도메인(Domain)은 속성이 가질 수 있는 값의 집합을 정의하는 개념으로, SQL에서는 CREATE DOMAIN 문으로 사용자 정의 도메인을 만들어 여러 컬럼에 재사용할 수 있다. 이는 데이터 타입 일관성 유지와 업무 규칙 표현에 유용하다.

2.2 JOIN 유형과 성능​

JOIN은 두 개 이상의 테이블을 연결하여 하나의 결과 집합을 생성하는 SQL 연산이다. 표준 JOIN 유형으로는 INNER JOIN(양쪽 테이블에 모두 존재하는 행), LEFT/RIGHT OUTER JOIN(한쪽 테이블의 모든 행 포함), FULL OUTER JOIN(양쪽 테이블의 모든 행 포함), CROSS JOIN(카테시안 곱), SELF JOIN(동일 테이블 간 조인)이 있다. NATURAL JOIN은 동명 컬럼을 자동으로 조인 조건으로 사용하지만 명시성이 떨어져 실무에서는 권장되지 않는다.

JOIN 성능을 높이기 위한 기법으로는 첫째, 조인 컬럼에 인덱스 생성(특히 외래키 컬럼), 둘째, 조인 방식 선택(Nested Loop Join: 소량 데이터, Hash Join: 대량 데이터 동등 조인, Sort-Merge Join: 정렬된 대량 데이터)이 있다. 셋째, 드라이빙 테이블을 작은 결과 집합을 반환하는 테이블로 선택하고, 넷째, 불필요한 컬럼 조회를 줄여 데이터 전송량을 최소화한다. 옵티마이저 힌트를 통해 조인 순서와 방식을 강제할 수도 있다.

실무에서는 M:N 관계의 교차 테이블 조인이나 여러 테이블의 연속 조인이 빈번히 발생한다. 이 경우 실행 계획(Execution Plan)을 분석하여 Full Table Scan이 발생하는 지점을 확인하고, 적절한 인덱스와 조인 방식을 적용해야 한다. 뷰(View)나 공통 테이블 표현식(CTE)을 활용하여 복잡한 조인 쿼리를 단계적으로 분리하면 가독성과 성능을 동시에 개선할 수 있다.

2.3 정적 SQL과 동적 SQL​

정적 SQL(Static SQL)은 프로그램 컴파일 시점에 SQL 문장이 완전히 확정되어 실행 계획이 미리 생성되는 방식이다. 파싱·최적화·바인딩 과정이 컴파일 시 수행되므로 실행 시 오버헤드가 낮고 성능이 안정적이다. 반면 동적 SQL(Dynamic SQL)은 런타임에 SQL 문자열을 생성하여 실행하는 방식으로, 조건에 따라 쿼리 구조가 달라지는 경우에 유연하게 대응할 수 있다.

동적 SQL의 장점은 다양한 조건에 대응하는 유연성과 범용적인 조회 모듈 구현 가능성이다. 단점으로는 매 실행마다 파싱 비용이 발생하고, SQL 인젝션(Injection) 취약점에 노출될 위험이 있으며, 바인드 변수 미사용 시 라이브러리 캐시 히트율이 저하된다. 이를 보완하기 위해 동적 SQL에서도 바인드 변수(Bind Variable)를 사용하여 실행 계획을 재사용하고 보안을 강화한다.

TEXT2SQL은 자연어로 작성된 질의를 자동으로 SQL로 변환하는 기술로, 최근 LLM(Large Language Model) 기반 구현이 활발하다. 데이터 분석가나 비개발자가 자연어로 데이터를 조회할 수 있도록 지원하며, BI 도구 연동, 챗봇 기반 데이터 조회 등의 사례에 활용된다.

3. 트랜잭션​

3.1 ACID 속성​

트랜잭션(Transaction)은 데이터베이스에서 하나의 논리적 작업 단위를 구성하는 연산들의 집합이다. 트랜잭션의 4대 특성인 ACID는 원자성(Atomicity: 전부 실행되거나 전혀 실행되지 않음), 일관성(Consistency: 트랜잭션 실행 전후 DB가 일관된 상태 유지), 격리성(Isolation: 동시 실행 트랜잭션은 서로 독립적), 지속성(Durability: 커밋된 트랜잭션은 영구 반영)을 의미한다.

원자성은 UNDO 로그를 통한 롤백 메커니즘으로 구현되며, 지속성은 REDO 로그(WAL: Write-Ahead Logging)로 보장된다. 일관성은 무결성 제약과 트랜잭션 로직을 통해 유지되고, 격리성은 잠금(Lock) 또는 MVCC 메커니즘으로 구현된다. ACID 특성은 전통적인 RDBMS의 강점이자 NoSQL이 성능 확장을 위해 일부를 완화(BASE: Basically Available, Soft state, Eventually consistent)하는 부분이기도 하다.

3.2 격리 수준과 이상 현상​

트랜잭션 격리 수준(Transaction Isolation Level)은 동시에 실행되는 트랜잭션 간의 가시성을 제어하는 설정이다. SQL 표준에서는 4가지 격리 수준을 정의한다. READ UNCOMMITTED는 커밋되지 않은 변경도 읽을 수 있어 Dirty Read가 발생한다. READ COMMITTED는 커밋된 데이터만 읽지만 Non-Repeatable Read가 발생한다. REPEATABLE READ는 트랜잭션 내 같은 쿼리는 동일 결과를 반환하지만 Phantom Read가 발생할 수 있다. SERIALIZABLE은 완전한 순차 실행과 동일한 결과를 보장하지만 동시성이 가장 낮다.

격리 수준에 따라 발생하는 이상 현상은 세 가지다. Dirty Read는 다른 트랜잭션이 아직 커밋하지 않은 데이터를 읽는 현상으로 READ UNCOMMITTED에서 발생한다. Non-Repeatable Read는 한 트랜잭션 내에서 같은 행을 두 번 읽었을 때 결과가 다른 현상이며, Phantom Read는 같은 조건의 SELECT가 두 번 실행될 때 새로 삽입된 행이 나타나는 현상이다. 이 세 가지 이상 현상이 모두 방지되는 수준이 SERIALIZABLE이다.

격리 수준 선택은 성능과 일관성 간의 트레이드오프다. 일반적인 OLTP 환경에서는 READ COMMITTED 또는 REPEATABLE READ를 주로 사용하며, 금융 거래처럼 강한 일관성이 필요한 경우 SERIALIZABLE을 적용한다. Oracle은 기본값이 READ COMMITTED이고, MySQL InnoDB는 REPEATABLE READ가 기본이다.

3.3 병행 제어​

병행 제어(Concurrency Control)는 다수의 트랜잭션이 동시에 실행될 때 데이터 일관성을 보장하는 기법이다. 병행 수행 시 발생하는 3가지 문제는 갱신 손실(Lost Update: 두 트랜잭션이 같은 데이터를 수정할 때 한 쪽 변경이 사라짐), 비반복 읽기(Non-Repeatable Read: 같은 데이터를 두 번 읽었을 때 결과가 다름), 연쇄 철회(Cascading Rollback: 한 트랜잭션 롤백이 다른 트랜잭션에 영향)가 있다.

병행 제어 기법의 종류로는 잠금(Locking) 기법, 타임스탬프 순서(Timestamp Ordering) 기법, 낙관적 병행 제어(Optimistic Concurrency Control), MVCC(Multi-Version Concurrency Control)가 있다. 잠금 기법에서 2단계 잠금 프로토콜(2PL: Two-Phase Locking)은 확장 단계(잠금 획득)와 수축 단계(잠금 해제)로 나뉘며 직렬성(Serializability)을 보장하지만 교착 상태(Deadlock)가 발생할 수 있다. 교착 상태는 예방(Wait-Die, Wound-Wait), 탐지(대기 그래프 사이클 감지), 회복(희생 트랜잭션 강제 철회) 방법으로 처리한다.

타임스탬프 기법은 각 트랜잭션에 타임스탬프를 부여하여 고유한 순서를 정하고, 이 순서에 따라 충돌을 해결한다. 낙관적 병행 제어는 충돌이 드물다고 가정하고 트랜잭션 실행 후 검증 단계에서 충돌을 확인한다. 읽기 위주의 시스템에서 성능 이점이 있다.

3.4 MVCC​

MVCC(Multi-Version Concurrency Control)는 데이터의 여러 버전을 유지하여 읽기 트랜잭션과 쓰기 트랜잭션이 서로를 차단하지 않도록 하는 병행 제어 기법이다. 쓰기 연산 시 기존 데이터를 덮어쓰지 않고 새로운 버전을 생성하며, 각 트랜잭션은 자신이 시작된 시점의 스냅샷(Snapshot)을 기반으로 일관된 뷰를 제공받는다. 이를 통해 읽기가 쓰기를 블로킹하지 않아 동시성이 크게 향상된다.

PostgreSQL과 MySQL InnoDB 모두 MVCC를 구현하고 있다. PostgreSQL은 각 행에 xmin(생성 트랜잭션 ID), xmax(삭제 트랜잭션 ID) 컬럼을 유지하여 가시성을 판단하고, 오래된 버전을 주기적으로 정리하는 VACUUM 프로세스가 필요하다. MySQL InnoDB는 언두 로그(Undo Log)에 이전 버전을 저장하고 Read View를 통해 트랜잭션별 가시성을 관리한다. MVCC는 쓰기 충돌만 잠금으로 처리하므로 잠금 경합(Lock Contention)을 줄이고 처리량(Throughput)을 높인다.

4. 인덱스와 옵티마이저​

4.1 인덱스 구조와 유형​

인덱스(Index)는 테이블의 특정 컬럼에 대해 별도의 자료구조를 생성하여 검색 성능을 향상시키는 데이터베이스 객체다. 가장 일반적인 B-Tree 인덱스는 균형 트리 구조로 O(log n) 시간 복잡도의 탐색을 제공하며, 범위 검색과 정렬 연산에 적합하다. Hash 인덱스는 등치 검색에 O(1) 성능을 제공하지만 범위 검색과 정렬이 불가능하다. Bitmap 인덱스는 카디널리티가 낮은 컬럼(성별, 상태코드 등)에 유리하며 AND/OR 연산이 효율적이다.

클러스터드 인덱스(Clustered Index)는 인덱스의 순서와 테이블 행의 물리적 저장 순서가 동일한 인덱스다. 테이블당 하나만 생성 가능하며, 범위 검색 시 I/O가 최소화된다. 논클러스터드 인덱스(Non-Clustered Index)는 인덱스와 데이터 행의 저장 순서가 다르며, 인덱스 리프 노드에 데이터 행 포인터(RID 또는 클러스터 키)가 저장된다. 하나의 테이블에 여러 논클러스터드 인덱스를 생성할 수 있지만, 인덱스가 많을수록 DML 성능이 저하된다.

인덱스 설계 원칙으로는 선택도(Selectivity)가 높은 컬럼(카디널리티가 높은 컬럼)에 우선 생성, 쿼리 WHERE 절·JOIN 조건·ORDER BY 절에 자주 사용되는 컬럼 대상, 복합 인덱스 구성 시 선택도 높은 컬럼을 선두에 배치, 그리고 DML 빈도와 조회 빈도를 비교하여 적정 수 유지가 있다.

4.2 옵티마이저​

옵티마이저(Optimizer)는 SQL 문장을 가장 효율적으로 실행할 수 있는 실행 계획(Execution Plan)을 자동으로 생성하는 DBMS의 핵심 구성요소다. 옵티마이저는 파싱(문법 검사) → 쿼리 변환(뷰 병합, 서브쿼리 변환 등) → 실행 계획 생성 → 최적 계획 선택 순으로 동작한다. 실행 계획에는 테이블 접근 방법(Full Scan, Index Scan), 조인 방식(Nested Loop, Hash, Sort-Merge), 조인 순서가 포함된다.

RBO(Rule Based Optimizer)는 사전에 정의된 우선순위 규칙에 따라 실행 계획을 결정한다. 예를 들어 인덱스 스캔이 항상 전체 테이블 스캔보다 우선 순위가 높다. 규칙이 단순하여 동작을 예측하기 쉽지만, 실제 데이터 분포를 고려하지 않아 비효율적인 계획이 생성될 수 있다. CBO(Cost Based Optimizer)는 통계 정보(행 수, 블록 수, 컬럼 분포)를 기반으로 각 실행 계획의 예상 비용을 계산하여 최소 비용 계획을 선택한다. 현재 Oracle, PostgreSQL, MySQL 등 대부분의 DBMS가 CBO를 채택한다.

힌트(Hint)는 옵티마이저가 선택한 실행 계획을 개발자가 직접 제어하는 방법이다. 인덱스 힌트(INDEX, NO_INDEX), 조인 방식 힌트(USE_NL, USE_HASH), 조인 순서 힌트(LEADING, ORDERED), 병렬 처리 힌트(PARALLEL) 등이 있다. 힌트는 옵티마이저가 잘못된 계획을 수립할 때 교정 수단으로 활용하되, 통계 정보를 최신으로 유지하는 것이 근본 해결책이다.

4.3 데이터베이스 튜닝​

데이터베이스 튜닝(DB Tuning)은 시스템의 응답 시간을 단축하고 처리량을 향상시키기 위해 데이터베이스의 설계, SQL, 인스턴스 설정을 최적화하는 활동이다. 튜닝은 설계 단계 튜닝(데이터 모델 최적화, 반정규화, 파티셔닝), SQL 튜닝(인덱스 활용, 조인 최적화, 실행 계획 분석), 인스턴스 튜닝(메모리 할당, I/O 설정, 프로세스 설정)의 세 계층으로 나뉜다. 설계 단계 튜닝이 가장 근본적이고 효과적이다.

SQL 튜닝의 핵심은 불필요한 Full Table Scan을 인덱스 스캔으로 전환하고, 불필요한 정렬 연산을 제거하며, 서브쿼리를 조인 또는 CTE로 변환하는 것이다. 실행 계획을 EXPLAIN(PostgreSQL/MySQL) 또는 EXPLAIN PLAN(Oracle)으로 분석하여 비용이 높은 노드를 식별한다. 인스턴스 튜닝에서는 버퍼 캐시 히트율, 래치 경합, I/O 대기 시간을 모니터링하여 메모리 및 파라미터를 조정한다.

5. NoSQL​

5.1 NoSQL 유형​

NoSQL(Not Only SQL) 데이터베이스는 관계형 모델의 엄격한 스키마와 ACID 제약을 완화하는 대신 수평 확장성과 대용량 처리 성능을 제공하는 데이터베이스다. 주요 유형은 네 가지다. 키-값(Key-Value) 저장소(Redis, DynamoDB)는 단순한 키-값 쌍으로 데이터를 저장하며 캐싱, 세션 관리에 적합하다. 문서(Document) 데이터베이스(MongoDB, CouchDB)는 JSON/BSON 형태의 문서를 저장하며 반정형 데이터 관리에 유리하다.

컬럼 패밀리(Column Family) 데이터베이스(Apache Cassandra, HBase)는 관련 컬럼들을 그룹화하여 저장하는 구조로, 쓰기 처리량이 높고 시계열 데이터, 이벤트 로그 처리에 적합하다. 각 행이 다른 컬럼 구조를 가질 수 있어 스파스 데이터 처리에 효율적이다. 그래프(Graph) 데이터베이스(Neo4j, Amazon Neptune)는 노드(Node)와 엣지(Edge)로 데이터를 표현하며, 소셜 네트워크 분석, 추천 시스템, 지식 그래프와 같이 관계 탐색이 핵심인 도메인에 최적화되어 있다.

인메모리 데이터베이스(In-Memory Database)는 모든 데이터를 메인 메모리에 저장하여 디스크 I/O를 제거함으로써 마이크로초 단위의 응답 시간을 실현한다. Redis, Memcached, VoltDB 등이 대표적이며, 금융 거래 처리, 실시간 분석, 캐싱 계층으로 활용된다. 지속성을 위해 스냅샷(RDB)이나 로그(AOF) 방식으로 디스크에 백업한다.

5.2 NoSQL 모델링​

NoSQL 모델링은 RDBMS의 정규화 중심 접근과 달리 쿼리 패턴 중심으로 데이터 구조를 설계한다. NoSQL 데이터 모델링 절차는 도메인 분석 및 쿼리 요건 파악 → 데이터 접근 패턴 정의 → 집계(Aggregate) 단위 결정 → 모델링 패턴 적용 → 물리적 저장 구조 설계 순으로 진행된다. "쿼리 먼저, 스키마 나중(Query First Modeling)"이 핵심 원칙이다.

주요 NoSQL 모델링 패턴 세 가지는 다음과 같다. 임베디드 도큐먼트(Embedded Document) 패턴은 관련 데이터를 하나의 도큐먼트 안에 중첩하여 저장함으로써 단일 읽기로 완전한 정보를 획득한다. 레퍼런스(Reference) 패턴은 RDBMS의 외래키처럼 다른 도큐먼트의 ID를 참조하여 데이터 중복을 줄인다. 버킷(Bucket) 패턴은 시계열 데이터처럼 시간 단위로 여러 이벤트를 하나의 도큐먼트에 묶어 도큐먼트 수를 줄이고 집계 성능을 높인다.

벡터 데이터베이스(Vector Database)는 AI/ML 모델의 임베딩 벡터를 저장하고 고차원 벡터 간 유사도 검색을 효율적으로 수행하는 전문 데이터베이스다. HNSW(Hierarchical Navigable Small World)는 계층적 그래프 구조를 통해 근사 최근접 이웃(ANN) 검색을 O(log n) 복잡도로 수행하며, IVF(Inverted File Index)는 벡터 공간을 보로노이 셀로 클러스터링하여 검색 범위를 제한한다.

6. 분산 데이터베이스​

6.1 분산 DB 개념과 투명성​

분산 데이터베이스(Distributed Database)는 물리적으로 다른 위치에 있는 여러 사이트에 데이터를 분산하여 저장하지만, 사용자에게는 하나의 통합된 데이터베이스처럼 보이는 시스템이다. 병렬 데이터베이스(Parallel Database)는 단일 위치의 여러 프로세서/디스크를 활용하여 쿼리를 병렬로 처리함으로써 성능을 향상시킨다. 분산 DB는 지리적 분산과 자율성에 초점을 두고, 병렬 DB는 처리 속도 향상에 초점을 둔다.

분산 데이터베이스의 5가지 투명성은 사용자가 데이터의 물리적 분산을 인식하지 못하도록 보장하는 특성이다. 위치 투명성(Location Transparency)은 데이터가 어느 사이트에 있는지 몰라도 접근 가능, 분할 투명성(Fragmentation Transparency)은 데이터가 어떻게 분할되었는지 몰라도 전체를 조회 가능, 복제 투명성(Replication Transparency)은 데이터 복제 여부를 인식하지 않아도 됨, 병행 투명성(Concurrency Transparency)은 동시 트랜잭션 관리가 자동으로 처리됨, 장애 투명성(Failure Transparency)은 일부 사이트 장애 시에도 서비스 지속 가능을 의미한다.

분산 DB 환경에서는 2단계 커밋 프로토콜(2PC: Two-Phase Commit)을 통해 분산 트랜잭션의 원자성을 보장한다. 1단계(준비 단계)에서 코디네이터가 참여자에게 커밋 준비를 요청하고, 2단계(커밋 단계)에서 모든 참여자의 동의를 확인한 후 커밋 또는 롤백을 전달한다. 코디네이터 장애 시 블로킹 문제가 발생하는 한계를 보완하는 3PC(Three-Phase Commit)도 있다.

6.2 샤딩과 파티셔닝​

파티셔닝(Partitioning)은 하나의 큰 테이블을 더 작은 물리적 단위로 분할하는 기법으로, 단일 DBMS 인스턴스 내에서 이루어진다. 수평 파티셔닝(Horizontal Partitioning)은 행을 기준으로 분할하여 각 파티션이 동일한 스키마를 가지며, 수직 파티셔닝(Vertical Partitioning)은 컬럼을 기준으로 분할하여 자주 사용하는 컬럼과 그렇지 않은 컬럼을 분리한다. 파티션 키 선택 방식에 따라 범위 파티셔닝, 리스트 파티셔닝, 해시 파티셔닝, 복합 파티셔닝으로 구분된다.

샤딩(Sharding)은 데이터를 여러 독립적인 데이터베이스 서버(샤드, Shard)에 분산 저장하는 수평 확장(Scale-Out) 기법이다. 각 샤드는 독립적인 DBMS 인스턴스이며, 전체 데이터의 일부만 보유한다. 샤딩 분할 방법으로는 범위 샤딩(Range Sharding), 해시 샤딩(Hash Sharding), 디렉터리 샤딩(Directory Sharding)이 있다. 파티셔닝이 단일 서버의 성능 최적화라면, 샤딩은 다중 서버로의 부하 분산이라는 점에서 차이가 있다.

샤딩 적용 시 고려사항으로는 샤드 키 선택(데이터 분포 균등성), 크로스 샤드 쿼리 처리(분산 조인의 복잡성), 샤드 추가/제거 시 리샤딩 비용, 트랜잭션 범위(단일 샤드 내로 제한 권장), 핫스팟(특정 샤드에 부하 집중) 방지가 있다.

6.3 CAP 이론과 PACELC​

CAP 이론은 분산 시스템에서 일관성(Consistency), 가용성(Availability), 분리 내구성(Partition Tolerance) 세 가지 속성을 동시에 모두 만족할 수 없다는 이론이다. 네트워크 파티션이 발생하면 C(일관성)와 A(가용성) 중 하나를 선택해야 한다. CP 시스템(HBase, Zookeeper)은 파티션 시 일관성을 우선하여 일부 요청을 거부하고, AP 시스템(Cassandra, CouchDB)은 파티션 시 가용성을 유지하되 일관성을 완화한다.

CAP 이론의 한계는 파티션이 발생하지 않는 정상 상태에서의 트레이드오프를 설명하지 못한다는 점이다. 이를 보완하는 PACELC(Partition Availability Consistency Else Latency Consistency) 이론은 파티션 발생 시 A vs C, 파티션이 없는 정상 상태에서도 L(Latency) vs C(Consistency)의 트레이드오프가 존재한다고 확장한다. 예를 들어 DynamoDB는 PA/EL(파티션 시 가용성 선택, 정상 시 지연 선택), Zookeeper는 PC/EC(파티션 시 일관성, 정상 시 일관성)에 해당한다.

7. 데이터 웨어하우스​

7.1 OLTP vs OLAP​

OLTP(Online Transaction Processing)는 기업의 일상적인 업무 트랜잭션을 처리하는 운영 데이터베이스 시스템이다. 소량의 데이터에 대한 빠른 읽기/쓰기가 빈번히 발생하며, 정규화된 스키마로 데이터 중복을 최소화한다. OLAP(Online Analytical Processing)는 대량의 역사적 데이터를 다차원으로 분석하는 시스템으로, 복잡한 집계 쿼리(GROUP BY, 윈도우 함수)가 주를 이루며 읽기 위주로 동작한다.

분석 정보 데이터베이스(데이터 웨어하우스)와 운영 데이터베이스를 분리 운영해야 하는 이유는 크게 두 가지다. 첫째, 복잡한 분석 쿼리가 운영 DB의 OLTP 성능에 영향을 주어 업무 처리가 지연될 수 있다. 둘째, 분석 목적의 비정규화된 스키마(스타 스키마, 스노우플레이크 스키마)는 OLTP의 정규화 요건과 상충된다. 데이터 웨어하우스는 ETL(Extract, Transform, Load) 프로세스를 통해 운영 DB에서 데이터를 주기적으로 추출하여 분석 최적화된 형태로 변환·적재한다.

MOLAP(Multidimensional OLAP)은 데이터를 다차원 큐브(Cube) 형태로 미리 집계하여 저장하므로 쿼리 응답이 빠르지만 저장 공간이 크다. ROLAP(Relational OLAP)은 관계형 DB에 저장된 데이터를 SQL로 집계하여 유연성이 높다. HOLAP(Hybrid OLAP)은 두 방식을 결합한다. MOLAP 설계 시 고려사항으로는 집계 수준(Granularity) 결정, 희소 데이터(Sparsity) 처리, 차원 계층(Hierarchy) 정의가 있다.

7.2 스타 스키마와 다차원 모델​

스타 스키마(Star Schema)는 데이터 웨어하우스에서 가장 널리 사용되는 차원 모델링 기법으로, 중앙의 팩트 테이블(Fact Table)과 이를 둘러싼 비정규화된 차원 테이블(Dimension Table)로 구성된다. 팩트 테이블은 측정값(매출액, 주문 수량 등 가산적 수치)과 차원 테이블을 연결하는 외래키를 포함하며, 차원 테이블은 분석 관점(시간, 지역, 제품, 고객)을 나타낸다. 스타 스키마는 조인 수가 적고 쿼리가 단순하여 OLAP 성능에 유리하다.

스노우플레이크 스키마(Snowflake Schema)는 스타 스키마에서 차원 테이블을 추가로 정규화한 형태로, 데이터 중복을 줄이지만 조인 복잡도가 증가한다. 다차원 데이터 큐브는 차원들의 교점에 측정값이 위치하는 n차원 행렬로, 슬라이싱(Slicing: 한 차원을 고정), 다이싱(Dicing: 특정 범위 추출), 드릴다운(Drill-Down: 세부 수준으로 이동), 롤업(Roll-Up: 상위 집계로 이동), 피벗(Pivot: 차원 축 변경) 등의 OLAP 연산을 지원한다.

8. 공간 데이터베이스​

8.1 공간 인덱스와 R-tree​

공간 데이터베이스(Spatial Database)는 점, 선, 다각형 등의 기하 객체를 저장하고 공간 관계를 효율적으로 질의하는 데이터베이스다. 공간 인덱스의 핵심 개념인 MBR(Minimum Bounding Rectangle, 최소 외접 사각형)은 기하 객체를 축에 평행한 최소 크기의 사각형으로 근사하여 공간 필터링에 활용된다. R-tree는 MBR을 계층적으로 조직화한 균형 트리로, 공간 데이터의 범위 검색과 최근접 이웃 검색에 널리 사용된다.

R-tree는 각 노드가 하위 노드들을 포함하는 MBR로 구성된다. 검색 시 쿼리 영역과 겹치는 MBR 경로만 탐색하므로 불필요한 I/O를 줄인다. 그러나 MBR 간 중첩(Overlap)이 많으면 검색 경로가 증가하여 성능이 저하된다. 이를 개선한 R+트리는 MBR 중첩을 허용하지 않는 대신 객체를 여러 노드에 중복 등록하여 탐색 효율을 높인다. R*트리는 노드 삽입 시 MBR 면적, 둘레, 중첩 면적 등 다중 기준으로 최적 위치를 선택하고 강제 재삽입(Forced Reinsertion)을 도입하여 트리 품질을 향상시킨다.

힐버트 R-tree(Hilbert R-tree)는 힐버트 공간 채움 곡선(Hilbert Space-Filling Curve)의 값에 따라 객체를 정렬하여 R-tree를 구성한다. 공간적으로 인접한 객체들이 같은 노드에 클러스터링되도록 하여 MBR 중첩을 최소화하고 검색 성능을 개선한다.

8.2 공간 연산자​

공간 연산자(Spatial Operator)는 기하 객체 간의 공간적 관계를 판단하거나 새로운 기하 객체를 생성하는 함수다. 위상 관계 연산자로는 ST_Intersects(두 객체가 교차하는지), ST_Contains(A가 B를 완전히 포함하는지), ST_Within(A가 B 내부에 있는지), ST_Touches(두 객체가 경계에서 접하는지), ST_Overlaps(두 객체가 부분적으로 겹치는지), ST_Disjoint(두 객체가 완전히 분리되는지), ST_Crosses(두 객체의 내부가 교차하는지)가 있다.

분석 연산자로는 ST_Distance(두 객체 간 최단 거리), ST_Buffer(특정 거리만큼 확장된 버퍼 영역 생성), ST_Union(두 객체의 합집합 기하), ST_Intersection(교집합 기하), ST_Difference(차집합 기하), ST_Area(다각형 면적), ST_Length(선의 길이) 등이 있다. 공간 연산은 내부적으로 MBR 필터링(1차 필터)과 정밀 기하 연산(2차 필터)의 2단계로 처리되어 성능을 최적화한다.

8.3 다차원 색인 구조​

다차원 색인 구조(Multidimensional Index Structure)는 2차원 이상의 공간이나 다차원 속성을 효율적으로 탐색하기 위한 인덱스 구조다. 대표적인 유형으로 R-tree 계열(공간 데이터의 MBR 기반 계층 구조), kd-tree(k차원 공간을 재귀적으로 이분하는 이진 탐색 트리), Grid File(공간을 균일 또는 비균일 격자로 분할하는 구조), Quad-tree(4분할 재귀 분할 구조)가 있다.

kd-tree는 각 레벨마다 분할 차원을 순환하여 공간을 절반으로 나누는 인메모리 자료구조로, 정적 데이터셋의 최근접 이웃 검색에 효율적이다. 그러나 데이터 삽입·삭제 시 트리 균형 유지가 어렵다. Grid File은 각 차원에 선형 눈금(Linear Scale)을 정의하여 셀(Cell)을 형성하고, 각 셀에 대응하는 버킷을 유지한다. 균일하지 않은 데이터 분포에서는 셀 분할을 동적으로 조정하는 가변 격자(Variable Grid)를 사용한다. 이러한 다차원 색인 구조는 GIS 시스템, CAD 데이터, 과학 시뮬레이션 데이터 관리에 활용된다.

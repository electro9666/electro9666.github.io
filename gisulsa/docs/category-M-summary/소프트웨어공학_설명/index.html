01. 소프트웨어 공학, 키워드로 쭉 훑어보기

1. 개발방법론 — 어떻게 만들 것인가​

자, 소프트웨어 공학이라는 건 결국 "소프트웨어를 체계적으로, 잘 만들자"는 학문이에요. 그냥 코딩만 하는 게 아니라, 기획부터 운영·폐기까지 전체 생명주기를 관리하자는 거죠. 이걸 통합적으로 다루는 개념이 ALM(Application Lifecycle Management)이에요. 요구사항부터 개발, 테스트, 배포, 운영까지 한 줄로 꿰는 거예요.

옛날에는 폭포수 모델처럼 위에서 아래로 한 단계씩 순차적으로 내려갔어요. 근데 이게 변경에 너무 취약하다 보니까 애자일(Agile)이 등장한 거예요. 애자일은 짧은 주기로 반복하면서 고객 피드백을 빠르게 반영하는 방식이죠. 그래서 시험에서도 폭포수와 애자일 비교가 단골로 나와요.

애자일 안에도 여러 방법이 있는데, 대표적으로 스크럼(SCRUM)이 있어요. SCRUM 팀구성 및 개발프로세스를 보면 제품 백로그 → 스프린트 플래닝 → 데일리 스크럼 → 스프린트 리뷰 순서로 돌아가요. 작업 흐름을 시각화하는 칸반도 있고요. 구조적 방법론은 프로세스 중심의 전통적 접근법이고, CBD는 재사용 가능한 컴포넌트를 조립해서 개발하는 거예요. 그래서 애자일(Agile)과 CBD 비교도 출제된 적 있어요.

프로젝트 진행률을 추적할 때는 EVM(Earned Value Management)이나 Burn Down Chart를 써요. EVM은 비용·일정을 정량적으로 측정하고, 번다운 차트는 남은 작업량이 줄어드는 걸 시각적으로 보여주죠. 그리고 방법론을 우리 조직에 맞게 조정하는 걸 테일러링(Tailoring)이라고 해요. 애자일도 마찬가지로 Agile 테일러링을 해서 우리 팀 상황에 맞게 커스터마이징하는 거예요.

빠르게 검증하고 싶을 때는 린 스타트업(Lean Startup) 방식을 써요. MVP(최소 기능 제품)를 빨리 만들어서 시장 반응을 보는 거죠. 요즘은 코딩을 최소화하는 로우코드(Low Code)나 아예 코딩 없이 만드는 노코드 플랫폼도 많이 쓰여요. 로우코드/노코드 플랫폼을 도입하면 비개발자도 앱을 만들 수 있어서 생산성이 확 올라가죠.

개발과 운영의 벽을 허무는 게 데브옵스(DevOps)예요. 개발(Dev)과 운영(Ops)을 하나로 합쳐서 빠르게 빌드·테스트·배포하자는 철학이죠. DevOps 장점과 단점을 따져보면, 배포 속도는 빨라지지만 조직 문화 변경이 필요하다는 게 핵심이에요. 데브옵스(DevOps)와 애자일(Agile) 비교도 자주 나오는데, 애자일은 개발 프로세스 중심이고 DevOps는 개발+운영 통합 중심이에요.

데이터 파이프라인에 DevOps 원칙을 적용한 게 데이터옵스(DataOps)이고, 보안까지 파이프라인에 녹인 게 DevSecOps예요. CI/CD(지속적 통합/지속적 배포)는 코드 변경이 자동으로 빌드·테스트·배포되는 파이프라인이에요. CI/CD DevSecOps를 결합하면 보안 검사까지 자동화되는 거죠.

실행 중인 서비스에 새 버전을 올릴 때는 배포 전략이 중요해요. 블루-그린, 카나리, 롤링 같은 전략이 있고, 동시에 테스트 전략도 함께 세워야 해요.

아키텍처 관점에서는 모놀리스(하나의 덩어리)와 마이크로서비스 아키텍처(MSA)(작은 서비스들의 조합) 비교가 핵심이에요. MSA로 가면 DevOps가 거의 필수가 되죠.

클라우드 환경에서는 PaaS 기반 소프트웨어 개발 방법론을 적용할 수 있고, 유사한 제품군을 효율적으로 만드는 제품계열(Product Line) 방법론도 있어요. 핵심 자산을 공유하면서 제품마다 변이(variation)를 두는 거죠.

2. 요구공학 — 뭘 만들어야 하는가​

소프트웨어를 잘 만들려면 먼저 "뭘 만들어야 하는지"를 제대로 정리해야 해요. 이걸 다루는 분야가 요구공학(Requirement Engineering)이에요. 요구사항은 크게 기능 요구사항(시스템이 해야 할 일), 비기능 요구사항(성능, 보안 등), 인터페이스 요구사항(외부 시스템과의 연동)으로 나눠요.

요구사항의 품질속성이 중요한데, 완전성·일관성·추적가능성·검증가능성 같은 거예요. 요구사항을 뽑아내는 도출기법으로는 인터뷰, 워크숍, 브레인스토밍, 프로토타이핑 같은 게 있고, 사용자 요구사항 도출 기법을 잘 활용해야 빠짐없이 수집할 수 있어요.

이렇게 모은 요구사항을 문서화한 게 SRS(Software Requirement Specification), 즉 요구사항명세서예요. 요구사항명세서 기술항목에는 기능 요구, 비기능 요구, 제약사항, 인터페이스 등이 포함되죠. 그리고 요구사항이 설계·구현·테스트로 제대로 이어지는지 추적하는 도구가 요구사항 추적표(Requirement Traceability Matrix)예요. 이게 있어야 "이 요구사항이 어디서 구현되고 어디서 테스트됐는지"를 확인할 수 있어요.

3. 설계원칙/객체지향 — 어떤 원칙으로 설계할 것인가​

좋은 소프트웨어의 4가지 특징이라고 하면 보통 유지보수성, 신뢰성, 효율성, 사용성을 꼽아요. 이걸 달성하려면 설계 원칙이 중요한데, 핵심이 추상화, 정보은닉, 단계적분해, 모듈화 이 네 가지예요.

추상화는 복잡한 걸 단순하게 표현하는 거고, 정보은닉(Information Hiding)은 모듈 내부 구현을 외부에 감추는 거예요. 비슷한 개념으로 캡슐화(Encapsulation)가 있는데, 캡슐화와 정보은닉을 비교하면 캡슐화는 데이터와 메서드를 하나로 묶는 것이고, 정보은닉은 그 중 내부를 감추는 설계 원칙이에요.

프로그래밍 패러다임으로 보면 절차지향은 함수 중심, 객체지향은 객체 중심이에요. 절차지향 vs 객체지향 프로그래밍 비교에서 객체지향이 재사용성과 유지보수성에서 유리하다는 게 포인트죠.

객체지향 설계에서 의존성 역전 원칙(DIP)은 상위 모듈이 하위 모듈에 직접 의존하지 말고 추상화에 의존하라는 원칙이에요. 이걸 실현하는 기법이 의존성 주입(DI, Dependency Injection)이고, 생성자 주입, 세터 주입, 인터페이스 주입 세 가지 방식이 있어요.

모듈 설계에서는 응집도는 높게, 결합도(Coupling)는 낮게 만드는 게 원칙이에요. fan-in(이 모듈을 호출하는 상위 모듈 수)은 높을수록, fan-out(이 모듈이 호출하는 하위 모듈 수)은 낮을수록 좋아요.

소프트웨어가 시간이 지나면서 얼마나 안정적으로 동작하는지를 수학적으로 모델링한 게 소프트웨어 신뢰성 성장 모델(SRGM)이에요. 테스트를 거듭할수록 결함이 줄어드는 패턴을 예측하는 거죠.

4. 아키텍처/설계 — 큰 그림을 어떻게 그릴 것인가​

소프트웨어 아키텍처는 시스템의 큰 그림이에요. 소프트웨어 아키텍처 모델 유형에는 데이터 중심형, 클라이언트-서버, 계층형, 파이프-필터 등이 있어요.

아키텍처가 잘 설계됐는지 평가하는 기법으로 ATAM(Architecture Tradeoff Analysis Method)이 있어요. 품질 속성 간의 트레이드오프를 분석하는 거예요. 여기에 비용 관점을 더한 게 CBAM(Cost Benefit Analysis Method)이고요.

대표적인 아키텍처 패턴으로는 MVC 패턴(MVC 모델)이 있어요. Model(데이터), View(화면), Controller(제어)를 분리하는 거죠. 마이크로서비스 아키텍처(MSA)는 서비스를 작게 쪼개서 독립적으로 배포하는 구조이고, 서비스 간 통신을 관리하는 서비스 메쉬(Service Mesh)와 함께 쓰여요.

이벤트 기반으로 시스템을 구성하는 EDA(Event Driven Architecture)도 있는데, 중재자 토폴로지와 브로커 토폴로지 두 가지 방식이 있어요.

API 설계 쪽으로 가면, API Gateway가 여러 마이크로서비스 앞에서 진입점 역할을 해요. API 명세를 표준화한 게 OAS(OpenAPI Specification)이고, REST API는 HTTP 기반의 가볍고 유연한 통신 방식이에요. 개방형 API(Open API)는 외부에 공개된 API를 말하고, 과거에 많이 쓰던 SOAP과 REST를 비교하는 문제도 나와요.

설계 패턴 쪽에서는 GoF 디자인 패턴이 바이블이에요. 생성·구조·행위 패턴으로 나뉘고, 아키텍처 스타일과 디자인 패턴의 차이를 구분하는 게 중요해요. 구체적인 패턴으로는 프록시(Proxy) 디자인 패턴 같은 것이 출제돼요.

5. UML/모델링 — 설계를 어떻게 표현할 것인가​

설계를 시각적으로 표현할 때 UML을 써요. UML 행위 다이어그램에는 활동 다이어그램(Activity Diagram), 상태 다이어그램(State Diagram), 유스케이스 다이어그램(Use Case Diagram)이 있어요.

구조 측면에서는 클래스 다이어그램(Class Diagram)이 핵심이에요. Abstract Class(추상클래스)와 Interface(인터페이스)의 차이를 클래스 다이어그램으로 표현할 줄 알아야 해요. 유즈케이스 다이어그램은 사용자(액터)와 시스템 기능 간의 관계를 보여주고, 순차 다이어그램(Sequence Diagram)은 객체 간 메시지 교환 순서를 시간 흐름에 따라 표현해요.

데이터 관점에서는 CRUD 매트릭스를 써서 엔티티와 프로세스 간의 생성(Create)·조회(Read)·수정(Update)·삭제(Delete) 관계를 정리해요.

그리고 로깅이나 트랜잭션 같은 횡단 관심사를 분리하는 AOP(Aspect Oriented Programming)도 있어요. 핵심 비즈니스 로직과 부가 기능을 분리해서 코드 중복을 줄이는 거예요.

6. 테스트/품질 — 제대로 만들었는가​

소프트웨어를 만들었으면 검증을 해야죠. 소프트웨어 테스트 원리에 따르면 테스트는 결함의 존재를 보여줄 수 있지만, 결함이 없다는 것을 증명할 수는 없어요.

크게 블랙박스 테스트와 화이트박스 테스트로 나뉘어요. 블랙박스는 내부 구조를 모르는 상태에서 입출력만 보는 명세 기반이고, 화이트박스는 코드 내부 구조를 보면서 하는 구조 기반이에요. 블랙박스 테스트 기법에는 동등분할, 경계값 분석, 분류트리 기법 등이 있고요. 이런 걸 통틀어 동적 테스트(명세/구조기반)라고 해요.

테스트가 코드를 얼마나 커버하는지 보는 게 코드 커버리지이고, 요구사항을 얼마나 커버하는지 보는 게 테스트 커버리지예요. 이 둘은 관점이 다르니까 헷갈리면 안 돼요.

모듈을 합쳐서 테스트하는 통합 테스트(Integration Test)에서는 드라이버(하위 모듈을 호출하는 가짜 상위 모듈)와 스텁(상위 모듈이 호출하는 가짜 하위 모듈)을 써요. 비점진적 방식(빅뱅)이 있고, 점진적 방식(상향식/하향식/샌드위치)이 있어요.

다른 테스트 유형도 많아요. 몽키 테스트는 무작위 입력으로 예상치 못한 오류를 찾는 거고, 회귀 테스트는 수정 후 다른 곳이 안 깨졌는지 확인하는 거예요. 뮤테이션 테스트(Mutation Test)는 코드를 일부러 변형(뮤턴트)시켜서 테스트가 그 변형을 잡아내는지 확인하는 기법이에요.

성능테스트에서는 리틀의 법칙(동시 사용자 = 도착률 x 평균 응답시간)이 기본 개념이고, 카오스 테스트(Chaos Test)는 일부러 장애를 주입해서 시스템의 회복력을 실험하는 거예요. A/B 테스팅은 두 버전을 사용자에게 보여주고 어떤 게 더 나은지 비교하는 거고요.

신뢰성 테스트는 시스템이 얼마나 안정적으로 동작하는지, 이식성 테스트는 다른 환경으로 옮겼을 때 잘 돌아가는지 확인해요. 임베디드 소프트웨어 테스트는 하드웨어와 밀접한 환경에서의 테스트를 다루고요.

테스트 자동화는 반복 테스트를 자동으로 돌리는 건데, 도구를 잘 선택해야 해요. 소프트웨어 Visualization은 개발 프로세스나 소스코드를 시각화해서 품질을 관리하는 접근법이에요.

품질 비용 관점에서 품질비용은 예방비용, 평가비용, 내부실패비용, 외부실패비용 네 가지로 나눠요. 품질보증(QA)은 프로세스 중심의 사전 예방 활동이고, 품질통제(QC)는 산출물 중심의 사후 검사 활동이에요. 구체적인 QA 활동으로 인스펙션(공식적인 동료 검토 프로세스)이 있어요.

보안 측면의 보안 품질 자동화는 SAST, DAST 같은 도구로 보안 취약점을 자동 탐지하는 거예요. AI 시대에는 AI 소프트웨어 품질보증 테스트 기법이 새로 등장했는데, 메타모픽 테스트(입력 변환 후 출력 관계 검증), 뉴런 커버리지(신경망 활성화 비율), 안전반경 테스트 같은 기법이 있어요.

품질 성숙도 인증으로는 CMMi(단계적 표현과 연속적 표현 두 가지 방식), SPICE(ISO 15504) 등이 있어요. 이런 소프트웨어 품질인증 체계를 통해 조직의 프로세스 역량을 객관적으로 평가받을 수 있어요.

7. 유지보수/리팩토링 — 만든 다음에는 어떻게 할 것인가​

소프트웨어는 한 번 만들면 끝이 아니에요. Lehman의 SW 변화원리에 따르면 사용되는 소프트웨어는 반드시 변화하고, 변화하면 복잡도가 증가해요. 이 과정에서 쌓이는 게 소프트웨어 기술 부채예요. 당장은 빠르게 구현했지만 나중에 갚아야 할 빚 같은 거죠.

기술 부채를 줄이는 대표적인 방법이 리팩토링이에요. 외부 동작은 바꾸지 않으면서 내부 구조를 개선하는 거죠. 리팩토링이 필요한 징후를 코드스멜이라고 하는데, 중복 코드, 긴 메서드, 거대한 클래스 같은 것들이에요. 리팩토링과 디자인패턴은 공통점(코드 구조 개선)과 차이점(리팩토링은 기존 코드 개선, 디자인패턴은 설계 시점 적용)이 있어요.

기존 시스템을 분석하는 역공학(Reverse Engineering)과 그 결과를 바탕으로 새로 구축하는 재공학(Re-engineering)도 중요해요. 여기에 재사용(Re-use)까지 합쳐서 3R(Reverse-Engineering, Re-Engineering, Re-use)이라고 부르고, 소프트웨어 유지보수 3R을 통해 유지보수 비용을 절감할 수 있어요.

8. 형상관리/배포 — 버전과 변경을 어떻게 관리할 것인가​

개발하다 보면 코드도 바뀌고, 문서도 바뀌고, 설정도 바뀌잖아요. 이런 변경을 체계적으로 관리하는 게 소프트웨어 형상관리예요. 형상 항목의 공식적인 기준 시점을 기준선(Baseline)이라고 해요. 기준선이 설정되면 그 이후 변경은 공식적인 변경 통제를 거쳐야 해요.

요즘 공급망 보안이 중요해지면서 SBOM(Software Bill of Material)이 주목받고 있어요. 소프트웨어에 포함된 모든 컴포넌트·라이브러리 목록을 자재명세서처럼 정리하는 거예요. SBOM 기반 오픈소스 관리를 하면 오픈소스 취약점을 체계적으로 추적할 수 있어요.

서비스 배포 시에는 무중단 배포가 핵심이에요. 리버스 프록시로 트래픽을 전환하거나, 로드밸런싱으로 서버 부하를 분산하면서 끊김 없이 배포하는 거죠.

9. SW 안전 — 안전하게 만들었는가​

사람의 생명이나 재산에 영향을 주는 소프트웨어는 소프트웨어 안전성 분석이 필수예요. 개발 전 과정에 보안을 녹인 게 Secure SDLC(보안 소프트웨어 개발 생명주기)예요.

국제 표준으로는 IEC 61508이 있어요. 기능안전이란 안전 관련 시스템이 요구되는 안전 기능을 정확히 수행하는 것을 말해요. 소프트웨어 관점에서 안전(Safety)과 보안(Security)은 다른 개념이니까 구분해야 해요.

위험 분석 기법으로는 FTA(고장 트리 분석), FMEA(고장 모드 영향 분석), HAZOP(위험 및 운전 분석)이 대표적이에요. 하지만 이 전통적 기법들에는 한계가 있어서, 시스템 이론 기반의 STPA(Systems-Theoretic Process Analysis)가 대안으로 나왔어요.

법적 근거로는 소프트웨어 진흥법에 따른 소프트웨어안전 확보 의무가 있어요. SW 안전성 진단을 통해 기능 동작의 정확성을 체계적으로 점검하는 거죠.

10. SW 비용산정 — 얼마나 들 것인가​

프로젝트를 시작하기 전에 "이거 만드는 데 얼마나 들어?"라는 질문에 답해야 해요. 이게 소프트웨어 비용 산정이에요. 크게 상향식(개별 작업을 먼저 산정해서 합산)과 하향식(전체 규모를 먼저 잡고 분배) 방식이 있어요.

비용 산정의 첫 단계가 소프트웨어 규모산정이에요. 규모를 어떻게 측정하느냐에 따라 여러 방식이 있는데, 대표적인 게 기능점수(Function Point)예요. 사용자 관점에서 제공하는 기능의 양을 측정하는 거죠. 수학적 모델로는 COCOMO II가 있는데, 그 중에서도 Post-Architecture Model이 가장 상세한 단계예요.

실제 사업에서는 대가산정이 중요해요. SW 운영단계 대가산정에서는 응용SW 요율제와 투입공수 산정 방식이 있고, 최근에는 소프트웨어 대가산정(AI 서비스)처럼 AI 사업에 대한 별도 산정 기준도 마련되고 있어요.

이렇게 보면 소프트웨어 공학은 "뭘 만들지 → 어떻게 설계하지 → 어떻게 만들지 → 제대로 만들었나 → 얼마나 드나 → 안전한가 → 어떻게 유지하지"를 체계적으로 다루는 학문이에요. 기출 키워드들이 이 흐름 속에 자연스럽게 녹아있다는 걸 기억하면 공부할 때 큰 그림을 잡기 훨씬 수월할 거예요.

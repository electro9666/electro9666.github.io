1. 데이터모델링 — 현실을 어떻게 데이터로 표현할 것인가​

데이터베이스의 출발점은 현실세계 모델링이에요. 현실에 있는 사물·사건·개념을 데이터로 추상화해서 DB에 담는 거죠. 이걸 어떤 방향으로 진행하느냐에 따라 전략이 달라지는데, Inside-out 전략은 핵심 엔티티에서 시작해서 주변으로 확장해 나가는 방식이에요. "중심부터 잡고 바깥으로 퍼져나가자"는 거죠.

관계형 데이터베이스를 설계할 때 쓰는 게 RDBMS 데이터 모델링이에요. 개념 모델링 → 논리 모델링 → 물리 모델링 단계로 진행하면서, 테이블 간 연결 방식을 식별관계(자식이 부모 키에 의존)와 비식별관계(논리적 연결만 있는 것)로 구분해서 설계해요.

모델링 결과를 시각적으로 표현하는 도구가 ERD(Entity Relationship Diagram)예요. 학생-수강신청서처럼 엔티티와 그 사이 관계를 그림으로 나타내는 거죠. ERD를 그리는 표기법 중 하나가 ERD(바커 표기법)인데, 영국의 바커(Richard Barker)가 만든 방식으로 엔티티·속성·관계를 특정한 기호로 표현해요. 설계가 끝나면 이걸 바탕으로 DDL(Data Definition Language, 데이터 정의 언어)로 실제 테이블을 만들어요. 공급자·상품 같은 도메인과 테이블을 DDL로 구현하는 게 실제 시험에서도 자주 나오는 패턴이에요.

엔티티 간의 관계 수를 나타내는 개념이 데이터베이스 카디널리티(Cardinality)예요. 1:1, 1:N, M:N 같은 거죠. 그리고 테이블들 사이에 데이터가 일관되게 유지되어야 한다는 원칙이 정보모델링의 참조 무결성이에요. 자식 테이블의 외래키 값은 반드시 부모 테이블에 존재해야 한다는 규칙이에요.

설계가 어느 정도 잡히면 CRUD 매트릭스를 만들어요. 각 엔티티에 대해 어떤 프로세스가 생성(Create)·조회(Read)·수정(Update)·삭제(Delete)를 수행하는지 표로 정리하는 거예요. 이게 있으면 "이 프로세스가 어떤 데이터를 쓰는지" 한눈에 파악할 수 있어요.

좋은 테이블 설계의 핵심은 정규화(Normalization)예요. 데이터 중복을 제거하고 이상현상(삽입/삭제/수정 이상)을 없애는 과정이에요. 정규형은 1NF부터 시작해서 2NF, 3NF, BCNF, 제4정규형, 데이터베이스 제5정규형까지 올라가요. 4NF는 다치 종속을 제거하고, 5NF는 조인 종속까지 제거한 가장 완전한 형태예요.

그런데 정규화를 너무 철저히 하면 JOIN이 너무 많아져서 성능이 떨어지는 경우가 생겨요. 그럴 때 의도적으로 정규화를 완화하는 게 반정규화(역정규화)예요. 절차·유형·고려사항을 알고 상황에 맞게 적용하는 게 중요해요.

2. SQL — 데이터를 어떻게 다룰 것인가​

데이터베이스와 대화하는 언어가 SQL(Structured Query Language)이에요. 구조화된 질의 언어로, 데이터를 조회·수정·삭제·관리하는 데 쓰이는 표준 언어죠.

SQL이 DBMS 안에서 어떻게 처리되는지가 SQL 처리과정이에요. 여기서 중요한 비교가 Statement와 Prepared Statement예요. Statement는 매번 SQL을 새로 파싱하지만, Prepared Statement는 한 번 파싱해서 템플릿으로 캐싱해 두고 파라미터만 바꿔 실행해요. 그래서 성능도 좋고 SQL 인젝션 방어에도 효과적이에요.

SQL을 얼마나 동적으로 구성하느냐에 따라 정적 SQL과 동적 SQL로 나눠요. 정적 SQL은 컴파일 시점에 SQL 구조가 고정되어 있고, 동적 SQL은 실행 시점에 SQL을 문자열로 조립해서 실행해요. 동적 SQL은 유연하지만 성능 관리가 까다롭고 SQL 인젝션 위험이 있어요.

JOIN은 SQL의 꽃이라고 할 수 있어요. JOIN 유형 및 성능 향상 기법을 보면 INNER JOIN, LEFT/RIGHT OUTER JOIN, FULL OUTER JOIN, CROSS JOIN 등 다양한 유형이 있고, 성능을 위해 인덱스 활용·조인 순서 최적화 같은 기법을 적용해요.

DDL로는 테이블·뷰·인덱스를 만들고, SQL 조회로는 복잡한 쿼리를 작성해요. 테이블에 걸 수 있는 제약이 릴레이션 무결성 제약 유형인데, NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK 같은 것들이에요. 이 제약들이 지켜져야 데이터 품질이 유지되는 거죠.

최근에는 TEXT2SQL도 주목받고 있어요. 자연어로 "지난달 매출 상위 10개 상품 알려줘"라고 물으면 그걸 SQL로 자동 변환해주는 기술이에요. AI가 SQL을 대신 작성해주는 거라 비개발자도 데이터를 조회할 수 있게 되는 거죠.

3. DB관리/튜닝 — 데이터베이스를 어떻게 안정적으로 운영할 것인가​

DB를 운영하다 보면 여러 사람이 동시에 데이터에 접근해요. 이때 일관성을 보장하는 핵심 개념이 데이터베이스 트랜잭션(Transaction)이에요. 트랜잭션은 ACID 특성을 가져야 해요. 원자성(Atomicity, 전부 성공하거나 전부 실패), 일관성(Consistency, 트랜잭션 전후 데이터 상태 일관), 격리성(Isolation, 동시 실행 트랜잭션이 서로 간섭 안 함), 지속성(Durability, 완료된 트랜잭션은 영구 반영)이에요.

여러 트랜잭션이 동시에 실행될 때 생기는 문제를 제어하는 게 데이터베이스 병행수행 제어예요. 병행 제어를 안 하면 세 가지 문제가 생겨요: 갱신 손실(Lost Update), 오손 읽기(Dirty Read), 연쇄 복귀(Cascading Rollback). 이걸 방지하는 게 데이터베이스 병행제어(Concurrency Control)이고, 대표 기법으로 데이터베이스 병행 제어 기법 중 2단계 잠금(2PL), 타임스탬프 기반 제어 등이 있어요.

격리 수준을 얼마나 엄격하게 설정하느냐가 데이터베이스 Isolation Level이에요. 트랜잭션 격리 수준 4가지가 있어요:

  • READ UNCOMMITTED: 커밋 안 된 데이터도 읽어요 (가장 느슨)
  • READ COMMITTED: 커밋된 데이터만 읽어요
  • REPEATABLE READ: 한 트랜잭션 안에서 같은 데이터를 읽으면 항상 같은 값
  • SERIALIZABLE: 트랜잭션을 직렬 실행한 것처럼 완벽히 격리 (가장 엄격)

트랜잭션 격리 수준이 낮을수록 성능은 좋지만 이상현상이 생겨요. Dirty Read는 커밋 안 된 데이터를 다른 트랜잭션이 읽는 것이고, Phantom Read는 한 트랜잭션 안에서 같은 범위를 두 번 조회했을 때 두 번째에 없던 행이 추가되는 현상이에요. 이 두 가지가 격리 수준과 연결된 대표 이상현상이에요.

이런 문제를 잠금(Lock) 없이 해결하는 기법이 MVCC(Multi Version Concurrency Control)예요. 데이터의 여러 버전을 동시에 유지해서 읽기와 쓰기가 서로 블로킹하지 않게 하는 거예요. PostgreSQL, MySQL InnoDB 같은 현대 DBMS들이 이 방식을 써요.

이제 성능 이야기를 해볼게요. 데이터베이스 성능의 핵심은 정규화와 반정규화의 균형, 그리고 인덱스·쿼리 최적화예요. 데이터베이스 인덱스(Index)는 조회 성능을 올리는 자료구조인데, 클러스터드 인덱스는 테이블 데이터 자체를 정렬된 순서로 저장하고(기본키에 자동 적용), 논클러스터드 인덱스는 별도의 인덱스 구조에 포인터를 저장해요. 클러스터드는 테이블당 하나만, 논클러스터드는 여러 개 만들 수 있어요.

쿼리 실행 계획을 세우는 게 데이터베이스 옵티마이저(Optimizer)예요. RBO(Rule Based Optimizer)는 미리 정해진 규칙에 따라 실행 계획을 세우고, CBO(Cost Based Optimizer)는 통계 정보를 바탕으로 비용이 가장 낮은 실행 계획을 선택해요. 요즘은 CBO가 표준이에요.

데이터베이스 튜닝(Tuning)은 DB 전반의 성능을 최적화하는 활동이에요. 설계 단계 튜닝(모델링·인덱스), SQL 튜닝(쿼리 최적화), DBMS 튜닝(파라미터 조정) 세 층위로 나눌 수 있고, 실행 계획을 강제로 유도하는 힌트 유형도 알아야 해요.

메모리에 모든 데이터를 올려놓고 처리하는 게 인메모리 데이터베이스(In-memory Database)예요. 디스크 I/O가 없으니 속도가 극도로 빠르죠. Redis, VoltDB 같은 것들이 이 범주예요.

4. NoSQL — 관계형DB의 한계를 어떻게 넘을 것인가​

NoSQL은 "Not Only SQL"의 줄임말이에요. 관계형 DB의 엄격한 스키마와 수직 확장의 한계를 넘기 위해 등장했어요. 대용량·비정형 데이터에 강하고, 수평 확장(서버 여러 대 추가)이 쉬워요.

NoSQL 3가지 구조로 대표적인 유형을 나눌 수 있어요:

  • Column Family 데이터베이스: Cassandra, HBase처럼 열(column) 단위로 데이터를 묶어 저장해요. 분석 쿼리에 강하죠.
  • 문서형(Document): MongoDB처럼 JSON 형태의 문서로 데이터를 저장해요.
  • 키-값(Key-Value): Redis처럼 단순한 키-값 쌍으로 저장해요.

MongoDB 개념 및 특징을 보면, 컬렉션·도큐먼트 구조로 스키마가 유연하고, 중첩 JSON이 가능해서 다양한 형태의 데이터를 그대로 저장할 수 있어요. 집계 파이프라인으로 복잡한 분석도 할 수 있고요.

NoSQL 특징, 데이터 모델링 패턴/절차는 관계형 DB 모델링과 완전히 달라요. 정규화 대신 역정규화를 기본으로 하고, 쿼리 패턴에 맞춰 데이터 구조를 설계해요. NoSQL 유형과 모델링 절차를 보면 도메인 분석 → 쿼리 패턴 도출 → 데이터 모델 설계 → 최적화 순서로 진행하고요.

NoSQL 모델링 패턴 3가지로는 임베디드 패턴(관련 데이터를 하나의 문서에 포함), 참조 패턴(ID로 다른 문서를 참조), 버킷 패턴(시계열 데이터를 묶어서 저장) 등이 대표적이에요.

5. 데이터웨어하우스/OLAP — 데이터를 어떻게 분석에 활용할 것인가​

업무 처리용 DB와 분석용 DB는 목적이 달라요. OLTP(Online Transaction Processing)는 짧고 빠른 트랜잭션 처리가 목적이고, OLAP(Online Analytical Processing)는 대규모 데이터의 복잡한 분석이 목적이에요. OLAP vs OLTP, 데이터웨어하우스 분리운영이 중요한 이유가 바로 이거예요. OLAP 쿼리는 무거우니까 OLTP 운영 DB에 직접 날리면 서비스에 영향을 주거든요.

분석용으로 데이터를 따로 모아놓은 창고가 데이터웨어하우스예요. 여러 소스에서 데이터를 추출·변환·적재(ETL)해서 분석에 최적화된 형태로 보관해요. 물리적인 DW 대신 기존 데이터 소스를 가상화해서 연결하는 게 로지컬 데이터웨어하우스(LDW)예요. ETL 없이 원본 소스를 논리적으로 통합하는 방식이라 구축이 빠르고 유연해요.

DW에서 데이터를 다차원으로 분석하는 게 다차원 OLAP(MOLAP)이에요. 데이터를 다차원 데이터 큐브로 저장해서 드릴다운(세부 조회), 롤업(집계 조회), 슬라이싱(특정 차원 필터) 같은 분석을 빠르게 할 수 있어요.

DW의 테이블 구조 중 가장 단순한 게 스타 스키마(Star Schema)예요. 중심에 팩트 테이블(측정값), 주변에 차원 테이블(시간·제품·지역 등)을 배치하는 별 모양 구조예요. JOIN이 단순해서 쿼리가 빠르고 이해하기 쉬워요.

DW보다 더 유연한 개념이 Data Lake예요. 구조화·반구조화·비구조화 데이터를 원본 그대로 쏟아붓는 저장소예요. 스키마를 나중에 정의하는 "Schema on Read" 방식이죠. 근데 데이터를 막 쌓기만 하고 관리를 안 하면 데이터 늪(Data Swamp)이 돼버려요. 누가 어떤 데이터를 넣었는지, 데이터 품질이 어떤지 알 수 없는 상태가 되는 거죠. 그래서 Data Lake를 운영할 때는 데이터 카탈로그·거버넌스가 필수예요.

6. 분산DB/샤딩 — 데이터를 어떻게 나눠서 관리할 것인가​

데이터가 너무 많아지면 한 서버에 다 담기 어려워요. 그래서 여러 서버에 데이터를 분산해서 저장·처리하는 게 분산 데이터베이스예요.

분산 DB가 좋으려면 사용자 입장에서 "분산되어 있다는 것을 몰라야" 해요. 이게 분산 데이터베이스 5가지 투명성이에요: 위치 투명성(어디 있는지 몰라도 됨), 분할 투명성(데이터가 나뉘어 있는지 몰라도 됨), 복제 투명성(복사본이 있는지 몰라도 됨), 장애 투명성(일부 장애가 있어도 사용 가능), 병행 투명성(동시 접근해도 문제없음).

병렬 데이터베이스와 분산 데이터베이스 비교를 해볼게요. 병렬 DB는 한 장소에 여러 CPU·디스크가 있는 구조로 속도를 높이고, 분산 DB는 물리적으로 다른 위치의 여러 서버에 데이터를 나눠 저장해요. 관심사가 다른 거죠.

데이터를 실제로 어떻게 나눌지가 데이터베이스 분할(수평/수직분할)이에요. 수평 분할은 행(row) 단위로 나누는 거고(예: 사용자 ID 기준으로 1100만은 서버A, 100만200만은 서버B), 수직 분할은 열(column) 단위로 나누는 거예요(자주 쓰는 컬럼과 드물게 쓰는 컬럼을 분리).

데이터베이스 샤드(database shard)는 이렇게 분할된 데이터 조각 하나하나를 말해요. 그리고 이 샤딩을 체계적으로 하는 게 데이터베이스 샤딩(Sharding)이에요. 분할 방법에는 범위 기반(Range), 해시 기반(Hash), 디렉토리 기반이 있어요. 파티셔닝과 비교하면, 파티셔닝은 단일 DB 내 테이블을 논리적으로 나누는 것이고, 샤딩은 여러 DB 서버로 물리적으로 분산하는 것이에요.

데이터 안정성을 위해 같은 데이터를 여러 서버에 복사하는 게 복제예요. 웹 서비스 데이터 복제 유형에는 마스터-슬레이브, 마스터-마스터, P2P 방식 등이 있어요. 복제하면 가용성은 높아지지만 일관성 관리가 어려워요.

분산 시스템의 한계를 정리한 게 CAP이론이에요. 일관성(Consistency), 가용성(Availability), 분단 허용성(Partition tolerance) 세 가지를 동시에 다 만족할 수 없다는 거예요. 근데 CAP이론은 네트워크 분단이 없을 때의 트레이드오프를 설명 못 한다는 한계가 있어요. 그래서 나온 게 PACELC 이론이에요. 분단이 있을 때(P: Partition)는 가용성-일관성 트레이드오프, 분단이 없을 때(E: Else)는 지연시간-일관성 트레이드오프를 고려하는 거예요.

7. 데이터품질/관리 — 데이터를 어떻게 믿을 수 있게 관리할 것인가​

데이터가 많아도 품질이 나쁘면 아무 소용없어요. 조직 차원에서 데이터를 체계적으로 관리하는 전략이 데이터 거버넌스예요. 데이터의 정의·소유권·품질·보안 정책을 수립하고 실행하는 체계죠. 데이터 주권 개념도 여기 포함돼요. 누가 데이터의 주인이고 어떻게 통제할 것인가의 문제예요.

데이터 거버넌스의 대상 중에서 핵심이 되는 공통 참조 데이터가 마스터 데이터예요. 고객·제품·거래처 같은 기준이 되는 데이터죠. 이걸 일관되게 관리하는 게 MDM(Master Data Management)이에요. 데이터 거버넌스, 마스터 데이터, MDM은 묶어서 이해해야 해요.

데이터를 제대로 쓰려면 용어·형식·도메인을 일관되게 정해야 해요. 이게 데이터 표준화 필요성과 기대효과예요. 부서마다 같은 개념을 다르게 부르면 시스템 통합이 안 되죠. 실제로 공공기관은 테이블 정의서(DB 표준화지침)를 따르도록 되어 있어요. DB 표준화지침에 맞춰 테이블·컬럼 명칭·도메인을 표준화하는 거예요.

DA(Data Architect)와 DBA 역할 비교도 중요해요. DA는 데이터 모델 설계·표준 수립·거버넌스 전략을 담당하고, DBA는 DB 설치·운영·성능 관리·백업을 담당해요. DA가 설계하면 DBA가 운영한다고 보면 돼요.

데이터 품질을 구체적으로 보면 데이터 무결성(데이터가 정확하고 완전함), 정합성(여러 시스템 간 데이터가 일치함), 프로파일링(데이터의 통계적 특성을 분석해서 품질 문제를 발견함)으로 나눌 수 있어요. 시스템 이전 시 마이그레이션 검증에서 이 세 가지가 핵심 체크포인트예요.

데이터 품질관리 프레임워크는 데이터 관리·구조 관리·관리 프로세스를 체계화한 거예요. 데이터 품질관리(생명주기별, 진단/개선)를 보면 데이터의 생산·저장·가공·활용·폐기 각 단계마다 품질을 관리해야 해요. 데이터 품질관리(품질관리 아키텍처/성숙도)에서는 조직의 품질 관리 역량을 단계별로 평가하고, 공공데이터 예방적 품질관리는 데이터를 만들 때부터 품질 문제를 예방하는 진단 영역·진단 항목을 정의해요.

요즘은 데이터 관측가능성(Data Observability)이라는 개념도 중요해졌어요. 데이터 파이프라인 안에서 데이터가 어디에 있고, 어떤 상태이고, 제대로 흐르고 있는지를 실시간으로 모니터링하는 거예요. 문제가 생기면 빨리 탐지하고 원인을 추적할 수 있어요.

데이터가 자산으로 인식되면서 데이터 거래, 데이터 가치평가도 중요해졌어요. 데이터를 사고팔거나 투자 의사결정에 활용하려면 가치를 측정해야 하는데, 비용 접근법·시장 접근법·수익 접근법 같은 데이터 가치평가 모델과 절차가 있어요.

8. 공간DB — 위치와 공간 데이터를 어떻게 다룰 것인가​

지도·GPS·GIS 같은 위치 기반 데이터를 다루는 특수한 DB가 공간 데이터베이스예요.

공간 데이터를 조작하는 연산이 공간 연산자(Spatial Operator) 5개예요. 대표적으로 Contains(포함 여부), Intersects(교차 여부), Distance(거리 계산), Touches(접촉 여부), Overlaps(겹침 여부) 같은 것들이에요.

공간 데이터 검색을 빠르게 하려면 전용 인덱스가 필요해요. 대표적인 게 R트리인데, 공간 객체를 포함하는 최소경계사각형인 MBR(Minimum Bounding Rectangle)로 계층 구조를 만들어요. R+트리는 MBR 간 겹침을 허용하지 않아 검색 성능이 좋지만 삽입이 복잡하고, R*트리는 겹침과 영역 크기를 균형 있게 최적화해요. R트리, R+트리, R*트리(MBR)의 차이를 이해하는 게 공간 인덱스의 핵심이에요.

더 발전된 형태가 힐버트(Hilbert) R-tree예요. 힐버트 곡선을 이용해서 공간 객체에 1차원 순서를 부여하고, 이를 기반으로 R-tree를 구성해요. 공간 국소성(locality)이 좋아서 디스크 I/O를 줄일 수 있어요.

공간 말고 다차원 데이터 전반을 인덱싱하는 게 다차원 색인구조(Multidimensional Index) 3가지예요. R-tree, kd-tree, Grid File 같은 구조가 있고, 각각 데이터 분포와 쿼리 유형에 따라 적합한 상황이 달라요. 다차원 색인구조 개념/유형/활용을 실제 분석 시스템·지도 서비스에서 어떻게 쓰는지까지 이해하면 좋아요.

동적으로 커지는 데이터를 해시로 인덱싱하는 기법이 확장성 해싱(Extendible Hashing)이에요. 버킷이 가득 차면 디렉토리를 두 배로 확장하고 버킷을 분할해서 충돌을 회피해요. 고정 크기 해시 테이블의 오버플로 문제를 해결하는 동적 해싱 기법이에요.

마지막으로 AI·ML 시대의 핵심 DB인 벡터 데이터베이스를 빼놓을 수 없어요. 텍스트·이미지·오디오를 고차원 벡터로 임베딩해서 저장하고, 유사도 기반으로 검색해요. 효율적인 근사 최근접 이웃(ANN) 검색 기법으로 HNSW(Hierarchical Navigable Small World, 계층적 소세계 그래프 기반)와 IVF(Inverted File Index, 클러스터 기반 역색인)가 핵심이에요. 벡터 데이터베이스(HNSW, IVF)는 RAG(검색 증강 생성) 같은 AI 애플리케이션에서 필수 인프라가 됐어요.

이렇게 보면 데이터베이스는 "어떻게 설계할지(모델링) → 어떻게 조회할지(SQL) → 어떻게 안정적으로 운영할지(관리/튜닝) → 관계형의 한계를 어떻게 넘을지(NoSQL) → 어떻게 분석에 쓸지(DW/OLAP) → 어떻게 나눠서 관리할지(분산/샤딩) → 어떻게 품질을 지킬지(데이터 품질) → 위치 데이터는 어떻게 다룰지(공간DB)"를 다루는 분야예요. 키워드들이 이 흐름 안에서 자연스럽게 연결되어 있으니, 큰 그림을 잡으면 개별 키워드도 훨씬 쉽게 기억할 수 있을 거예요.

1_1. WBS(Work Breakdown Structure) 작성방법​

1. 개요​

**WBS(Work Breakdown Structure)**는 프로젝트의 **최종 인도물(Deliverable)**을 기준으로 전체 작업을 계층적으로 분할(Decomposition)하여 범위를 체계적으로 관리하는 기법이다. WBS는 일정·원가·자원관리의 기준(Baseline)이 되며, 작성 시 100% Rule과 MECE 원칙을 준수해야 한다.

2. 작성 절차​

프로젝트 범위 정의
        ↓
주요 인도물 식별
        ↓
계층적 작업 분할
        ↓
Work Package 정의
        ↓
WBS Dictionary 작성
        ↓
검증 및 Baseline 확정

3. 작성방법​

단계주요 내용
범위 정의Scope 및 주요 Deliverable 식별
계층 분할상위→하위 작업으로 Decomposition
Work Package일정·원가 산정 가능한 최소 단위 정의
WBS Dictionary작업코드, 책임자, 산출물, 완료기준 명시
검증100% Rule, MECE, 누락·중복 여부 확인

4. 결론​

WBS는 Activity 중심이 아닌 Deliverable 중심으로 작성하며, 100% Rule, MECE, 적정 Work Package 수준을 확보해야 한다. 이를 통해 범위 누락을 방지하고 일정·원가·품질관리의 기준선을 제공하여 프로젝트 성공 가능성을 높인다.

이 문제는 1교시 비교형입니다. 핵심은 두 개념의 차이를 명확하게 비교하는 것이므로, 정의를 길게 쓰기보다 개념 → 비교 → 활용 순으로 압축하는 것이 좋습니다.

1_2. 대수의 법칙(Law of Large Numbers)과 중심극한정리(Central Limit Theorem)​

1. 개요​

확률·통계에서는 표본을 이용하여 모집단의 특성을 추정한다. **대수의 법칙(LLN)**은 표본의 수가 증가할수록 표본평균이 모집단 평균에 수렴함을 설명하며, **중심극한정리(CLT)**는 표본의 수가 충분히 크면 표본평균의 분포가 정규분포에 근사함을 설명하는 이론이다.

2. 개념도​

모집단
   │
   ├── 표본 수 증가 ──► 표본평균 → 모집단 평균 수렴
   │                    (대수의 법칙)
   │
   └── 반복 추출 ────► 표본평균의 분포
                         ↓
                    정규분포 근사
                  (중심극한정리)

3. 비교​

구분대수의 법칙중심극한정리
목적평균의 수렴성분포의 정규성
대상표본평균표본평균의 분포
의미표본 수 증가 → 모집단 평균에 근접반복 추출 시 정규분포에 근사
활용평균 추정의 신뢰성신뢰구간, 가설검정, AI·통계분석

4. 결론​

대수의 법칙은 표본평균이 모집단 평균으로 수렴하는 성질을, 중심극한정리는 표본평균의 분포가 정규분포를 따른다는 성질을 설명한다. 두 이론은 통계적 추론의 핵심 기반으로, 빅데이터 분석과 AI 모델 평가, 품질관리 및 데이터 기반 의사결정에 폭넓게 활용된다.

1_3. Advanced RAG(Retrieval-Augmented Generation)와 Modular RAG(Retrieval-AugmentedGeneration) 비교​

1. 개요​

RAG(Retrieval-Augmented Generation)는 외부 지식 저장소에서 관련 정보를 검색(Retrieval)한 후 이를 LLM 프롬프트에 증강(Augmentation)하여 정확한 응답을 생성(Generation)하는 기술이다. 최근에는 검색 성능을 고도화한 Advanced RAG와 구조를 모듈화한 Modular RAG가 활용되고 있다.

2. 구조​

Advanced : Query→Hybrid Search→Re-ranking→LLM

Modular : Router→Retriever→Memory→LLM→Tool

3. 비교​

구분Advanced RAGModular RAG
목적검색 정확도 향상구조 유연성
핵심검색 최적화모듈 조합
장점Hallucination 감소확장성·재사용성
단점Latency 증가설계 복잡성
적용Enterprise SearchAI Agent

4. 결론​

Advanced RAG는 Retrieval 성능 개선, Modular RAG는 아키텍처 유연성 확보에 중점을 둔다. 최근에는 Modular 구조에 Advanced Retrieval 기법을 결합하는 형태가 주류이다.

출제 의도는 단순히 위험 종류를 나열하는 것이 아니라 **Negative Risk의 개념과 4가지 대응전략(Avoid, Transfer, Mitigate, Accept)**을 아는지를 평가하는 문제입니다.

1_4. IT 프로젝트에서 발생할 수 있는 부정적 위험(Negative Risk)과 대응 전략​

1. 개요​

**부정적 위험(Negative Risk, Threat)**은 프로젝트 목표(범위·일정·원가·품질)에 부정적인 영향을 미칠 가능성이 있는 불확실성이다. 프로젝트 관리자는 위험을 식별·분석한 후 적절한 대응전략을 수립하여 영향을 최소화해야 한다.

2. 위험관리 절차​

위험 식별
    ↓
위험 분석
    ↓
대응전략 수립
    ↓
모니터링·통제

3. 부정적 위험 대응 전략​

전략주요 내용예시
Avoid(회피)위험 원인 제거 또는 계획 변경요구사항 축소, 기술 변경
Transfer(전가)제3자에게 위험 이전보험, 외주, 고정가 계약
Mitigate(완화)발생확률·영향 감소PoC, 프로토타입, 추가 테스트
Accept(수용)위험을 인정하고 대응계획 마련예비비·Contingency Reserve 확보

4. 결론​

IT 프로젝트에서는 일정 지연, 기술 실패, 품질 저하, 보안 위협 등 다양한 부정적 위험이 발생할 수 있다. 프로젝트 특성에 맞는 회피(Avoid), 전가(Transfer), 완화(Mitigate), 수용(Accept) 전략을 적용하고 지속적인 위험 모니터링을 수행해야 프로젝트 성공 가능성을 높일 수 있다.

이 문제는 1교시 설명형입니다.

핵심은 무중단 배포의 목적을 먼저 제시하고, **대표 배포 방식(Blue-Green, Rolling, Canary)**을 비교하는 것입니다. A/B Testing은 배포 방식이 아니라 실험(Experiment) 기법이므로 보조적으로만 언급하는 것이 좋습니다.

1_5. 소프트웨어 무중단 배포 방식​

1. 개요​

**무중단 배포(Zero Downtime Deployment)**는 서비스 중단 없이 새로운 버전의 소프트웨어를 배포하는 기법이다. 서비스 가용성을 확보하고 장애 발생 시 신속한 롤백을 지원하기 위해 Blue-Green, Rolling, Canary 방식이 주로 활용된다.

2. 배포 방식​

기존 운영환경
      │
      ├── Blue-Green : 운영환경 전환
      ├── Rolling    : 서버 순차 교체
      └── Canary     : 일부 사용자 우선 배포

3. 방식별 비교​

방식특징장점단점
Blue-Green신규 환경 구축 후 전환즉시 전환·롤백 용이인프라 비용 증가
Rolling서버를 순차적으로 교체자원 효율적배포 시간 증가, 버전 혼재
Canary일부 사용자 대상 점진 배포위험 최소화, 품질 검증모니터링·트래픽 제어 필요

4. 결론​

무중단 배포는 서비스 연속성과 안정적인 릴리즈를 위한 핵심 기법이다. 서비스 특성과 인프라 환경을 고려하여 Blue-Green, Rolling, Canary 방식을 선택하고, CI/CD, 모니터링, 자동 롤백을 함께 적용해야 안정적인 운영이 가능하다.

이 문제는 1교시 비교형입니다.

핵심은 **처리 위치(Location)**를 중심축으로 지연시간(Latency), 대역폭(Bandwidth), 확장성(Scalability), 적용 분야를 비교하는 것입니다.

1_6. 엣지(Edge) 컴퓨팅과 클라우드 컴퓨팅의 차이점​

1. 개요​

클라우드 컴퓨팅은 중앙 데이터센터에서 컴퓨팅 자원을 제공하는 방식이며, 엣지 컴퓨팅은 데이터 발생 지점(Edge) 또는 단말 인근에서 데이터를 처리하는 분산 컴퓨팅 방식이다. IoT, AI, 자율주행 등 실시간 서비스 확대로 엣지 컴퓨팅의 활용이 증가하고 있다.

2. 개념도​

IoT Device
    │
 ┌──┴──────────────┐
 │                 │
Edge Computing   Cloud Computing
(현장 처리)      (중앙 처리)
 │                 │
즉시 응답        대규모 분석·저장

3. 차이점​

구분Edge ComputingCloud Computing
처리 위치단말·엣지 서버중앙 데이터센터
지연시간낮음(실시간)상대적으로 높음
네트워크트래픽 감소대역폭 의존
확장성제한적매우 우수
적용 분야IoT, 자율주행, 스마트팩토리AI 학습, 빅데이터, 업무시스템

4. 결론​

엣지 컴퓨팅은 저지연·실시간 처리에, 클라우드 컴퓨팅은 대규모 저장·분석 및 자원 확장에 적합하다. 최근에는 Edge에서 실시간 처리 후 Cloud에서 통합 관리·분석하는 Edge-Cloud Hybrid 아키텍처가 주류로 활용되고 있다.

이 문제는 1교시 설명형입니다.

핵심은 **분산 데이터베이스의 투명성(Transparency)**을 정의하고, 대표적인 5~6가지 투명성을 체계적으로 제시하는 것입니다. 기술사 답안에서는 **위치(Location), 분할(Fragmentation), 복제(Replication)**를 반드시 포함하는 것이 중요합니다.

1_7. 분산 데이터베이스의 투명성(Transparency)​

1. 개요​

분산 데이터베이스의 투명성은 데이터가 여러 사이트에 분산되어 있더라도 사용자에게 하나의 통합된 데이터베이스처럼 보이도록 하는 특성이다. 데이터의 위치, 분할, 복제 등을 사용자에게 숨겨 분산 환경의 복잡성을 최소화한다.

2. 투명성 개념​

사용자
   │
하나의 DB처럼 접근
   │
 ┌────────────────────┐
 │ 분산 데이터베이스 관리시스템 │
 └────────────────────┘
   │
Site A   Site B   Site C

3. 주요 투명성​

투명성주요 내용
위치(Location)데이터 저장 위치를 알 필요 없이 접근
분할(Fragmentation)데이터 분할 여부와 관계없이 동일하게 접근
복제(Replication)복제본 존재를 사용자에게 숨김
장애(Failure)일부 노드 장애에도 서비스 지속
병행(Concurrency)다중 사용자 동시 접근 시 일관성 보장

4. 결론​

분산 데이터베이스의 투명성은 데이터 독립성, 접근 편의성, 가용성을 향상시키는 핵심 특성이다. 이를 위해 위치·분할·복제 투명성을 제공하고, 병행제어와 장애복구 기능을 통해 일관성과 신뢰성을 확보해야 한다.

답안 작성 팁(기술사)​

이 주제는 출제 빈도가 높은 만큼 투명성의 종류를 정확히 쓰는 것이 중요합니다. 일반적으로는 다음 6가지를 암기해 두면 대부분의 문제에 대응할 수 있습니다.

  • 위치 투명성 (Location Transparency)
  • 분할 투명성 (Fragmentation Transparency)
  • 복제 투명성 (Replication Transparency)
  • 병행 투명성 (Concurrency Transparency)
  • 장애 투명성 (Failure Transparency)
  • 성능(또는 성능 최적화) 투명성 (Performance Transparency)

1교시에서는 모든 종류를 장황하게 설명하기보다 핵심 키워드와 한 줄 정의로 정리하는 것이 가장 효율적인 답안입니다.

이 문제는 1교시 설명형입니다.

핵심은 과적합과 과소적합의 원인과 해결방안을 비교하는 것입니다. 기술사 답안에서는 Bias-Variance Trade-off를 결론에 언급하면 좋은 평가를 받을 수 있습니다.

1_8. 과적합(Overfitting)과 과소적합(Underfitting)의 발생 원인과 해결 방안​

1. 개요​

**과적합(Overfitting)**은 학습 데이터에 지나치게 맞춰져 일반화 성능이 저하되는 현상이며, **과소적합(Underfitting)**은 모델이 데이터를 충분히 학습하지 못해 학습·검증 데이터 모두에서 성능이 낮은 현상이다. AI 모델의 성능 향상을 위해 두 현상의 균형을 유지해야 한다.

2. 개념도​

           모델 학습
               │
      ┌────────┴────────┐
      │                 │
  과소적합          과적합
(Model 단순)     (Model 복잡)
      │                 │
모델 복잡도↑      정규화·Dropout
Feature 추가      Early Stopping
학습량 증가       데이터 증강

3. 발생 원인 및 해결 방안​

구분과적합(Overfitting)과소적합(Underfitting)
발생 원인모델 과복잡, 학습데이터 부족, 노이즈 학습모델 단순, 학습 부족, 특징 부족
특징학습 정확도↑, 검증 정확도↓학습·검증 정확도 모두 낮음
해결 방안데이터 증강, 정규화(L1/L2), Dropout, Early Stopping모델 복잡도 증가, Feature 추가, 학습 횟수 증가, 하이퍼파라미터 조정

4. 결론​

과적합은 일반화 성능 저하, 과소적합은 학습 부족이 본질적인 문제이다. 따라서 데이터 품질 개선과 적절한 모델 복잡도 조절을 통해 Bias-Variance Trade-off를 최적화하고, 교차검증(Cross Validation) 등을 활용하여 일반화 성능을 확보해야 한다.

이 문제는 1교시 용어·설명형입니다. 핵심은 제어 흐름 그래프, 계산식, 독립 경로와 테스트 케이스의 관계입니다.

1_9. 맥케이브 순환복잡도(McCabe’s Cyclomatic Complexity)​

1. 개요​

맥케이브 순환복잡도는 프로그램의 **제어 흐름 그래프(Control Flow Graph)**에서 선형적으로 독립된 실행 경로의 수를 측정하는 소프트웨어 복잡도 지표이다. 값이 클수록 분기와 테스트 난도가 증가하며, 화이트박스 테스트의 최소 테스트 케이스 산정에 활용된다.

2. 측정 원리​

       ┌─ 조건 참 ─ 처리 A ─┐
시작 ─ 조건                  ├─ 종료
       └─ 조건 거짓 ─ 처리 B ─┘

Node(N) : 명령·처리 블록
Edge(E) : 제어 흐름
Region  : 그래프의 폐영역

3. 산정 방법​

산정 기준계산식·의미
제어 흐름 그래프V(G) = E − N + 2P
단일 연결 그래프V(G) = E − N + 2
의사결정 수V(G) = 조건 분기 수 + 1
영역 수제어 흐름 그래프의 영역 수

※ E는 간선, N은 노드, P는 연결된 컴포넌트 수이다.

4. 활용 및 고려사항​

  • Basis Path Testing의 독립 경로 및 최소 테스트 케이스 도출
  • 고복잡도 모듈 식별을 통한 리팩터링·유지보수성 개선
  • 함수 분리, 중첩 조건 축소, 구조화 프로그래밍으로 복잡도 감소
  • 단, 코드 구조만 측정하므로 결합도·데이터 복잡도와 함께 평가

5. 결론​

순환복잡도는 제어 흐름의 복잡성과 테스트 규모를 정량화하는 지표이다. 복잡도가 높은 모듈은 결함 가능성과 유지보수 비용이 증가하므로 임계값 관리와 리팩터링을 통해 품질을 확보해야 한다.

1_10. Wi-Fi 7​

Wi-Fi 7은 IEEE 802.11be-2024 기반의 차세대 무선 LAN 기술로, EHT(Extremely High Throughput)를 목표로 한다. 기존 Wi-Fi 6/6E 대비 채널 대역폭, 변조 효율 및 다중 링크 활용을 향상하여 초고속·저지연·고신뢰 통신을 제공한다. (IEEE Standards Association)

1_11. CTEM(Continuous Threat Exposure Management)​

1. 개요​

**CTEM(Continuous Threat Exposure Management)**은 조직의 **공격 노출면(Attack Surface)**을 지속적으로 식별·평가·우선순위화하고 개선하여 실제 공격에 노출되는 위험을 지속적으로 관리하는 보안 관리 프레임워크이다. 기존의 주기적 취약점 점검에서 벗어나 지속적(Continuous) 위험 관리를 지향한다.

2. 관리 흐름​

공격표면 식별
      ↓
노출·취약점 평가
      ↓
위험 우선순위화
      ↓
대응·개선
      ↓
지속적 모니터링

3. 주요 구성​

구성주요 내용
식별(Discovery)자산, 공격표면, 노출요소 파악
평가(Assessment)취약점·위협·영향도 분석
우선순위(Prioritization)비즈니스 영향 기반 위험 선정
개선(Remediation)패치, 설정 변경, 보안통제 적용
검증(Monitoring/Validation)지속적 모니터링 및 효과 확인

4. 특징 및 활용​

  • 공격자 관점의 실제 노출 위험 관리
  • 자산·취약점·위협 정보를 통합하여 우선순위 결정
  • 지속적인 보안 검증과 개선을 통한 공격면 최소화
  • ASM(Attack Surface Management), VM(Vulnerability Management), 침투테스트 등과 연계하여 운영

5. 결론​

CTEM은 취약점 중심 관리에서 노출 위험 중심 관리로 전환하는 접근법이다. 조직은 공격 가능성과 비즈니스 영향을 함께 고려하여 위험을 우선적으로 대응하고, 지속적인 모니터링과 개선을 통해 사이버 복원력을 향상시켜야 한다.

이 문제는 1교시 용어·개념형입니다.

핵심은 양자컴퓨팅과 머신러닝의 결합이라는 개념을 제시하고, **양자 특성(중첩·얽힘)**과 활용 분야 및 한계를 간결하게 기술하는 것입니다.

1_12. 양자머신러닝(QML, Quantum Machine Learning)​

1. 개요​

**양자머신러닝(QML)**은 **양자컴퓨팅(Quantum Computing)**과 **머신러닝(Machine Learning)**을 결합하여 학습·추론 성능을 향상시키는 기술이다. 양자 중첩(Superposition)과 얽힘(Entanglement)을 활용하여 대규모 최적화 및 패턴 분석을 고속으로 수행하는 것을 목표로 한다.

1_13. 개인정보보호를 위한 가명처리 기법​

1. 개요​

**가명처리(Pseudonymization)**는 개인정보의 일부를 삭제·대체·변환하여 추가정보 없이는 특정 개인을 식별할 수 없도록 처리하는 기법이다. 개인정보 활용과 프라이버시 보호의 균형을 위한 핵심 기술로, 데이터 분석·AI 학습 등에 활용된다.

2. 처리 절차​

개인정보
    │
식별자 분리
    │
가명처리
    │
가명정보 활용
    │
추가정보 별도 관리

3. 주요 가명처리 기법​

기법주요 내용
대체(Replacement)이름·주민번호 등을 다른 값으로 치환(Tokenization 등)
총계처리(Aggregation)개별값을 합계·평균 등 통계값으로 변환
삭제(Suppression)일부 식별정보 삭제 또는 마스킹
범주화(Generalization)나이→연령대, 주소→시·도 등 범위화
암호화(Encryption)식별정보를 암호화하고 키를 별도 관리

4. 결론​

가명처리는 데이터 활용성과 개인정보 보호를 동시에 확보하기 위한 기술이다. 재식별 위험을 최소화하기 위해 추가정보의 안전한 분리·관리, 접근통제 및 재식별 위험평가를 함께 수행해야 한다.

2_4. 터보퀀트(TurboQuant)의 개념, 특징, 성능, 기존 양자화 기술과의 차이점, 기대효과에 대하여 설명하시오.​

답안 유형: 설명형(Type B) → 개념 → 특징 → 성능 → 비교 → 기대효과 중심으로 구성하는 것이 채점기준에 적합합니다.

Ⅰ. 개요​

LLM(Large Language Model)의 추론(Inference) 단계에서는 **KV Cache(Key-Value Cache)**가 반복적으로 증가하여 메모리 사용량과 메모리 대역폭이 병목(Bottleneck)이 된다.

TurboQuant는 Google Research가 제안한 Post-Training Quantization(PTQ) 기반의 KV Cache 벡터 양자화 기술로, 학습(Fine-tuning) 없이도 메모리를 크게 절감하면서 정확도 저하를 최소화하는 차세대 양자화 기술이다. PolarQuant와 QJL을 결합하여 초저비트(약 3bit) 양자화에서도 정확도를 유지하는 것이 핵심이다. (Google Research)

Ⅱ. TurboQuant 개념 및 구조​

1. 개념​
  • LLM의 KV Cache를 초저비트로 압축
  • Post-Training Quantization(PTQ) 방식
  • 학습·재학습 없이 적용 가능
  • 정확도 손실을 최소화하면서 메모리 절감
2. 구조​
          LLM KV Cache
               │
               ▼
      PolarQuant (1차 양자화)
   • Random Rotation
   • Polar Decomposition
   • Lloyd-Max Quantization
               │
         Residual Error
               ▼
     QJL (1-bit Residual Encoding)
               │
               ▼
      Compressed KV Cache
               │
               ▼
      Faster Attention Inference

추론속도 향상기존 추론 프레임워크와의 통합 필요
정확도 유지모델·문맥 길이에 따른 성능 검증 필요

Ⅷ. 결론​

TurboQuant는 PolarQuant와 QJL을 결합한 차세대 벡터 양자화 기술로, 재학습 없이 KV Cache를 초저비트로 압축하여 메모리 병목을 완화하고 LLM 추론 성능을 향상시키는 기술이다. 향후 초장문 LLM, 온디바이스 AI, 대규모 AI 서비스에서 인프라 비용 절감과 추론 효율 향상의 핵심 기술로 활용될 것으로 기대된다. (Google Research)

2_5. 행정·공공기관 정보시스템 등급제 및 공공 SLA(Service Level Agreement) 표준​

답안 유형: 설명형 + 적용형(2교시) 답안 구성: (가) 개념·필요성 → (나) 등급별 SLA 적용 → (다) SLA 표준안 및 적용 고려사항

Ⅰ. 개요​

최근 행정·공공기관의 반복적인 전산망 장애(정부24, 나이스 등)를 계기로 서비스 연속성(Business Continuity) 과 국민 서비스 품질 확보가 핵심 과제가 되었다.

이에 정부는 「전자정부법」 개정을 통해 정보시스템 등급제와 공공 SLA(Service Level Agreement) 표준을 도입하여, 중요도에 따라 목표 서비스 수준을 차등 관리하고 2027년부터 의무화를 추진하고 있다. 2026년까지 시범 적용 후 2027년 의무화를 목표로 하고 있으며, 우선 1·2등급 시스템에 표준안을 적용한다. (모바일 정부)

1. 공공 SLA(Service Level Agreement)의 개념​

공공 SLA란 행정기관과 정보시스템 운영사업자 간 서비스 수준을 계약으로 명확히 정의하고, 이를 지속적으로 측정·관리하는 서비스 품질관리 체계이다.

  • 장애 대응시간
  • 서비스 품질지표(KPI)
  • 위약금 및 서비스 크레딧

  • 디지털정부 서비스 품질 향상

2_6. 데이터 가치평가 및 데이터 자산화​

답안유형: 설명형 + 활용형(2교시) 답안구성: (가) 가치평가 → (나) 자산화 → (다) 활용사례 핵심 키워드: Data Valuation, Data Assetization, 데이터 거래, 데이터 거버넌스, 메타데이터, 데이터 카탈로그, 품질관리

Ⅰ. 개요​

디지털 전환(DX)과 AI 시대에는 데이터가 기업의 핵심 생산요소이자 전략적 자산(Data as an Asset) 으로 인식되고 있다. 그러나 데이터는 유형자산과 달리 가치가 명확하지 않으므로 객관적인 가치평가(Data Valuation) 와 체계적인 데이터 자산화(Data Assetization) 가 필요하다.

데이터 가치평가는 데이터의 경제적·활용적 가치를 산정하는 과정이며, 데이터 자산화는 데이터를 지속적으로 활용 가능한 관리대상 자산으로 전환하는 활동이다.

데이터 가치평가는 데이터의 경제적 가치를 객관적으로 산정하는 활동이며, 데이터 자산화는 데이터를 지속적으로 활용 가능한 기업의 핵심 자산으로 관리하는 체계이다. AI·빅데이터 시대에는 가치평가(무엇이 얼마나 가치 있는가) 와 자산화(어떻게 관리하고 활용할 것인가) 를 함께 추진해야 데이터 거래 활성화, AI 경쟁력 확보, 데이터 기반 의사결정 고도화라는 효과를 극대화할 수 있다.

3_1. 다중 에이전트 시스템(MAS, Multi-Agent System)​

답안 유형: 3교시 설명·비교·적용형 답안 전략: 정의 → 아키텍처 → 단일 에이전트 비교 → 효과 → 고려사항 → 기업 적용방안 핵심 키워드: Agentic AI, Multi-Agent Orchestration, Planner, Coordinator, MCP, A2A, 협업, 자율성, 관측성(Observability)

Ⅰ. 개요​

생성형 AI의 발전으로 AI는 단순 질의응답을 넘어 계획(Planning), 추론(Reasoning), 실행(Action) 을 수행하는 AI Agent로 발전하고 있다. 그러나 단일 Agent는 복잡한 업무를 수행하는 데 한계가 있으므로, 여러 전문 Agent가 협업하여 업무를 수행하는 다중 에이전트 시스템(MAS) 이 기업 업무혁신의 핵심 기술로 주목받고 있다.

MAS는 역할별 전문성을 활용하여 업무를 분담하고 협력함으로써 복잡한 비즈니스 프로세스의 자동화와 의사결정 고도화를 실현하는 AI 협업 아키텍처이다.

3_2. 데이터 분석에서 이상치와 편향의 영향 및 처리 방안​

Ⅰ. 개요​

데이터 분석의 신뢰성은 알고리즘뿐 아니라 입력 데이터의 품질과 대표성에 의해 좌우된다. 특히 이상치(Outlier) 는 일부 관측값이 전체 분포에서 크게 벗어나는 현상이며, 편향(Bias) 은 데이터 수집·분석 과정에서 결과가 특정 방향으로 지속적으로 치우치는 현상이다.

따라서 이상치는 개별 값의 비정상성 관점에서, 편향은 데이터와 분석 절차 전반의 체계적 오류 관점에서 구분하여 관리해야 한다.

Ⅱ. 이상치와 편향의 개념​

1. 이상치의 개념​

이상치란 대부분의 관측값과 현저히 다른 특성을 가지며 전체 데이터 분포에서 벗어난 관측값이다.

주요 발생 원인은 다음과 같다.

  • 입력·측정 오류
  • 센서 및 시스템 장애
  • 단위·형식 변환 오류
  • 실제 희귀사건 발생
  • 환경·시간 조건의 변화

이상치는 반드시 오류는 아니며, 금융사기·보안침해·설비고장과 같은 중요한 신호일 수 있다.

2. 편향의 개념​

편향이란 분석 결과가 모집단의 실제 특성이나 참값으로부터 일정한 방향으로 지속적으로 벗어나는 체계적 오류이다.

주요 유형은 다음과 같다.

  • 표본선택 편향: 특정 집단이 과소·과대 대표
  • 측정 편향: 측정도구나 기준에 의한 왜곡
  • 생존자 편향: 성공하거나 남아 있는 사례만 분석
  • 역사적 편향: 과거의 불균형이 데이터에 반영
  • 알고리즘 편향: 모델·목적함수·임계값에 의한 차이

3. 이상치와 편향 비교​

구분이상치편향
대상일부 관측값데이터·분석 과정 전체
성격국소적·우발적구조적·지속적
주요 원인입력오류, 희귀현상표본, 측정, 모델, 해석
주요 영향통계량·모델 왜곡대표성·공정성 저하
처리 방향탐지 후 선별 처리수집부터 운영까지 통제

Ⅲ. 분석 결과에 미치는 영향​

1. 이상치의 영향​

첫째, 평균·분산·상관계수 등 기술통계량을 왜곡한다. 일부 극단값으로 인해 평균이 실제 일반적인 수준보다 높거나 낮게 나타날 수 있다.

둘째, 회귀계수와 분류 경계가 특정 값에 과도하게 영향을 받아 모델 성능이 저하된다.

셋째, K-Means·KNN 등 거리 기반 알고리즘에서는 군집 중심과 이웃관계가 왜곡될 수 있다.

넷째, 이상치를 무조건 제거하면 사기거래·장애징후·희귀질환과 같은 유의미한 정보를 상실할 수 있다.

2. 편향의 영향​

첫째, 표본의 대표성이 훼손되어 분석 결과를 전체 모집단에 일반화하기 어렵다.

둘째, 특정 집단의 오탐률·미탐률이 증가하여 신용평가, 채용, 의료 등의 의사결정이 불공정해질 수 있다.

셋째, 편향된 검증데이터를 사용하면 실제 성능보다 높은 정확도가 산출되는 평가 착시가 발생한다.

넷째, 편향된 모델의 결과가 다시 학습데이터로 축적되면서 편향이 강화되는 피드백 루프가 발생한다.

이상치와 편향의 처리는 분석가만의 업무가 아니며, 데이터 담당자·업무전문가·모델 개발자·감사 담당자가 공동으로 판단해야 한다.

Ⅵ. 결론​

이상치는 일부 관측값이 전체 분포에서 벗어나는 현상이며, 편향은 분석 결과가 특정 방향으로 지속적으로 치우치는 체계적 오류이다.

이상치는 통계량과 모델을 왜곡할 수 있지만 중요한 희귀신호일 수 있으므로 탐지–원인분석–선별처리–재검증 절차가 필요하다. 편향은 표본수집부터 모델운영까지 발생할 수 있으므로 대표성 확보–재표본화–집단별 평가–지속적 모니터링으로 관리해야 한다.

궁극적으로 신뢰성 있는 데이터 분석을 위해서는 정확도뿐 아니라 강건성, 대표성, 공정성, 설명가능성을 함께 확보해야 한다.

아래 답안은 정보관리기술사 3교시 실전 답안(A4 약 2.5장) 수준으로 구성했습니다. 문제의 요구사항인 기술부채 → 코드스멜 → 리팩토링을 중심축으로 연결하여 작성하는 것이 고득점에 유리합니다.

3_3. 명확하지 않은 요구사항으로 인해 발생하는 소프트웨어 품질저하 문제​

Ⅰ. 개요​

소프트웨어 개발에서 요구사항의 불명확성(Ambiguity) 은 잦은 변경, 임시 구현(Quick Fix), 중복 코드 등을 발생시켜 유지보수성을 저하시킨다. 이러한 문제는 기술부채(Technical Debt) 를 누적시키고, 코드 수준에서는 코드스멜(Code Smell) 로 나타나며, 이를 개선하기 위한 대표적인 기법이 리팩토링(Refactoring) 이다.

따라서 요구사항 품질 확보와 지속적인 코드 개선 활동은 소프트웨어 품질과 유지보수성을 확보하기 위한 핵심 요소이다.

Ⅱ. 기술부채(Technical Debt)​

1. 개념​

기술부채란 개발 일정이나 비용 등의 이유로 최적의 설계 대신 단기적인 구현을 선택함으로써 향후 유지보수 비용과 위험이 증가하는 상태를 의미한다.

2. 발생 원인​

  • 불명확한 요구사항
  • 잦은 요구사항 변경
  • 일정 압박으로 인한 임시 구현
  • 설계 검토 부족
  • 테스트 및 문서화 미흡

3. 영향​

  • 유지보수 비용 증가
  • 변경 영향도 확대
  • 장애 발생 가능성 증가
  • 개발 생산성 저하
  • 시스템 복잡도 증가

        ↓
   기술부채 누적
        ↓

Ⅲ. 코드스멜(Code Smell)​

1. 개념​

코드스멜은 즉시 오류를 발생시키지는 않지만, 설계 품질이 저하되어 향후 유지보수와 확장이 어려워질 가능성을 나타내는 코드의 징후이다.

2. 주요 유형​

유형내용

Feature Envy다른 객체 데이터에 과도하게 의존

3. 영향​

  • 코드 가독성 저하
  • 테스트 어려움
  • 재사용성 감소
  • 변경 영향 확대
  • 기술부채 가속

Ⅳ. 리팩토링(Refactoring)​

1. 개념​

리팩토링이란 외부 기능은 변경하지 않고 내부 코드 구조를 개선하여 가독성, 유지보수성 및 확장성을 향상시키는 활동이다.

2. 주요 기법​

Ⅵ. 적용 시 고려사항​

1. 기술적 고려사항​

  • 요구사항 명확화(BRS, SRS)
  • 정적분석(SonarQube 등) 활용
  • 단위·회귀 테스트 자동화
  • CI/CD 기반 지속적 품질관리
  • 코드리뷰 및 아키텍처 리뷰 수행

2. 관리적 고려사항​

  • 기술부채 우선순위 관리
  • 리팩토링 일정 확보
  • 변경 이력 및 형상관리
  • 품질지표(복잡도, 코드커버리지) 관리
  • DevOps 및 지속적 개선 문화 정착

Trade-off​

장점고려사항

Ⅶ. 결론​

기술부채, 코드스멜, 리팩토링은 각각 독립적인 개념이 아니라 소프트웨어 품질관리의 연속적인 흐름이다. 명확하지 않은 요구사항은 기술부채를 발생시키고, 이는 코드스멜이라는 형태로 나타난다. 이를 지속적인 리팩토링과 자동화된 품질관리를 통해 개선함으로써 유지보수성, 확장성 및 소프트웨어 품질을 확보할 수 있다.

따라서 조직은 요구사항 명확화 → 기술부채 관리 → 코드스멜 식별 → 리팩토링 → 지속적 품질관리(CI/CD, 코드리뷰) 체계를 구축하여 소프트웨어의 장기적인 품질과 개발 생산성을 확보해야 한다.

기술사 답안 팁: 이 문제는 세 개념을 각각 설명하는 것보다 **"요구사항 불명확 → 기술부채 → 코드스멜 → 리팩토링 → 품질향상"**의 인과관계를 그림으로 연결하면 채점자가 구조적인 이해를 높게 평가할 가능성이 큽니다.

아래 답안은 정보관리기술사 3교시 실전 답안(A4 약 2.5장) 수준으로 구성하였습니다. 이 문제는 SW공학 + 테스트기법을 묻는 대표 문제이므로, (가) 원리 → (나) 테스트 기법 → (다) 테스트케이스 작성으로 자연스럽게 연결하는 것이 중요합니다.

3_4. 소프트웨어 테스트(Software Testing)​

Ⅰ. 개요​

소프트웨어 테스트는 소프트웨어가 요구사항을 만족하는지 검증(Verification)하고, 사용자 요구에 부합하는지 확인(Validation)하기 위한 품질보증(QA) 활동이다. 테스트는 결함이 없음을 증명하는 것이 아니라 결함의 존재를 발견하는 과정이며, 체계적인 테스트 설계기법을 적용하여 테스트 효율성과 품질을 향상시킨다.

가. 소프트웨어 테스트의 7대 원리​

1. 테스트 7대 원리​

원리주요 내용
결함 존재 증명테스트는 결함의 존재를 발견할 뿐, 결함이 없음을 증명하지 못한다.
완전 테스트 불가능모든 입력과 경로를 테스트하는 것은 현실적으로 불가능하다.
조기 테스트요구사항·설계 단계부터 테스트를 수행할수록 비용이 감소한다.
결함 집중대부분의 결함은 일부 모듈에 집중된다(Pareto 법칙).
살충제 패러독스동일한 테스트를 반복하면 새로운 결함을 발견하기 어렵다.
테스트는 상황 의존적시스템 특성에 따라 테스트 전략이 달라져야 한다.
오류 부재의 궤변결함이 없어도 요구사항을 만족하지 못하면 실패한 시스템이다.

나. 화이트박스 테스트와 블랙박스 테스트 비교​

1. 개념​

화이트박스 테스트(White Box Test)​

프로그램의 내부 구조, 제어 흐름, 소스코드를 기반으로 수행하는 구조 기반 테스트이다.

블랙박스 테스트(Black Box Test)​

프로그램 내부 구조는 고려하지 않고 요구사항과 입·출력 명세를 기준으로 수행하는 기능 기반 테스트이다.

Ⅴ. 결론​

소프트웨어 테스트는 결함 발견과 품질 확보를 위한 핵심 검증 활동으로, 7대 원리를 기반으로 효율적인 테스트 전략을 수립해야 한다. 또한 화이트박스 테스트는 내부 구조를, 블랙박스 테스트는 기능 요구사항을 검증하는 상호보완적 기법이며, 동등분할과 경계값 분석을 활용하면 최소한의 테스트 케이스로 최대의 결함 검출 효과를 얻을 수 있다. 따라서 요구사항 기반 테스트 설계와 자동화된 지속적 테스트 체계를 구축하는 것이 고품질 소프트웨어 확보의 핵심이다.

기술사 고득점 포인트​

이 문제는 단순 암기 문제가 아니라 **"원리 → 테스트 유형 → 실제 테스트 설계"**의 연결성을 보여주는 것이 중요합니다. 특히 (다)의 테스트 케이스 표가 배점 비중이 높으므로, 실제 답안에서는 약 40% 정도의 분량을 테스트 케이스 작성에 할애하는 것이 효과적입니다.

이 문제는 자료구조 + 네트워크를 융합하는 문제입니다. 기술사에서는 단순히 BST를 설명하거나 라우팅 테이블을 설명하는 것이 아니라, **"탐색 알고리즘 관점에서 둘의 상관관계"**를 논리적으로 연결하는 것이 핵심입니다.

아래는 정보관리기술사 3교시 실전 답안(A4 약 2.5장) 수준입니다.

3_5. 이진 탐색 트리(Binary Search Tree)와 라우팅 테이블 탐색 알고리즘의 상관관계​

Ⅰ. 개요​

네트워크 장비의 라우팅 테이블(Routing Table) 은 목적지 IP 주소에 대해 최적의 경로를 신속하게 검색해야 한다. 라우팅 테이블의 규모가 증가할수록 탐색 성능이 네트워크 처리속도를 좌우하므로 효율적인 탐색 알고리즘이 요구된다.

이진 탐색 트리(BST) 는 데이터를 정렬된 계층구조로 저장하여 O(log n) 수준의 탐색 성능을 제공하는 자료구조이며, 이러한 탐색 원리는 라우팅 테이블 검색 알고리즘의 기본 개념과 밀접한 관련이 있다.

Ⅱ. 이진 탐색 트리(BST)의 개념​

1. 개념​

이진 탐색 트리(Binary Search Tree)는 왼쪽 서브트리에는 작은 값, 오른쪽 서브트리에는 큰 값을 저장하는 이진 트리로, 탐색·삽입·삭제를 효율적으로 수행하는 자료구조이다.

BST 구조​
          50
        /    \
      30      70
     /  \    /  \
   20   40 60   80
특징​
  • 정렬 상태 유지
  • 탐색·삽입·삭제 효율적
  • 평균 탐색시간 : O(log n)
  • 불균형 발생 시 최악 O(n)

Ⅲ. 라우팅 테이블 탐색 알고리즘​

1. 개념​

라우팅 테이블 탐색은 목적지 IP 주소를 기반으로 최적의 다음 홉(Next Hop)을 찾는 과정이다.

라우터는 수만~수십만 개 이상의 경로를 관리하므로 고속 탐색과 메모리 효율성이 요구된다.

탐색 과정​
Destination IP
       │
       ▼
Routing Table Lookup
       │
Longest Prefix Match
       │
       ▼
Next Hop 결정

2. 주요 탐색 알고리즘​

  • 선형 탐색(Linear Search)
  • 이진 탐색(Binary Search)
  • Trie(Prefix Tree)
  • Patricia Trie(Radix Tree)
  • TCAM(Ternary CAM)

실제 고성능 라우터는 Longest Prefix Match(LPM) 를 효율적으로 수행하기 위해 Trie 계열 구조와 TCAM을 주로 사용한다.

Ⅳ. BST와 라우팅 테이블 탐색 알고리즘의 상관관계​

1. 공통점​

두 구조 모두 탐색 시간을 최소화하기 위한 계층적 탐색 구조를 사용한다.

  • 비교를 통한 탐색 범위 축소
  • 계층적(Tree) 구조 활용
  • 탐색 효율 향상
  • 대규모 데이터 검색 최적화

2. 차이점​

구분이진 탐색 트리(BST)라우팅 테이블 탐색
탐색 기준Key 값 비교IP Prefix 비교
자료구조Binary TreeTrie, Patricia Trie, TCAM
목적데이터 검색최적 경로 탐색
검색 방식값 비교Longest Prefix Match
시간복잡도평균 O(log n)Trie는 Prefix 길이에 비례, TCAM은 하드웨어 병렬 검색

3. 상관관계​

BST의 "탐색 공간을 단계적으로 줄이는 원리" 는 라우팅 테이블 검색에도 동일하게 적용된다.

다만 IP 주소는 단순한 크기 비교보다 접두어(Prefix) 기반 검색이 중요하므로, 실제 라우팅에서는 BST보다 Trie 계열 자료구조가 더 적합하다.

BST
Key 비교
    │
좌/우 탐색
    │
검색 완료


Routing Lookup
Prefix 비교
      │
Trie 탐색
      │
Longest Prefix Match
      │
Next Hop 결정

즉, BST는 탐색 알고리즘의 기본 개념을 제공하고, Trie는 이를 IP 주소 검색에 최적화한 자료구조라고 볼 수 있다.

Ⅴ. 적용 시 고려사항​

1. 성능 관점​

고려사항주요 내용
탐색속도라우팅 성능에 직접 영향
메모리 사용Trie는 노드 수 증가 가능
확장성IPv6 주소 증가 고려
갱신 성능동적 라우팅 시 삽입·삭제 효율

2. 기술별 Trade-off​

기술장점단점
BST구현 단순, 평균 O(log n)Prefix 검색에 부적합, 불균형 시 성능 저하
TriePrefix 검색 최적화메모리 사용량 증가
Patricia Trie메모리 절감, Trie 최적화구현 복잡
TCAM초고속 병렬 검색비용·전력소모 높음

Ⅵ. 결론​

이진 탐색 트리는 탐색 공간을 단계적으로 축소하여 검색 효율을 높이는 기본 자료구조이며, 이러한 원리는 라우팅 테이블 탐색 알고리즘의 기반 개념과 동일하다. 그러나 라우팅은 IP Prefix 기반의 Longest Prefix Match 가 핵심이므로 실제 네트워크 장비에서는 Trie 및 Patricia Trie, TCAM과 같은 자료구조를 활용하여 고속 탐색을 수행한다.

따라서 BST와 라우팅 탐색 알고리즘의 관계는 "탐색 원리는 동일하지만, 적용 대상의 특성(IP Prefix)에 맞게 자료구조가 발전한 관계" 로 이해하는 것이 적절하다.

기술사 채점 포인트​

이 문제에서 가장 높은 점수를 받는 답안은 **"BST가 라우팅 테이블에 직접 사용된다"**고 쓰는 것이 아니라,

BST → 탐색 원리 제공 → Prefix 검색 필요 → Trie/Patricia Trie로 발전 → Longest Prefix Match 구현

이라는 진화 과정을 설명하는 답안입니다. 이 흐름을 제시하면 자료구조와 네트워크를 연결하는 기술사다운 분석력을 보여줄 수 있습니다.

이 문제는 AI + 데이터 품질관리를 묻는 문제이지만, 실제 채점 포인트는 AI 데이터 생명주기 관점에서 품질관리를 설명하는 것입니다. 단순히 데이터 품질 6대 특성만 쓰면 점수가 낮고, AI 학습데이터의 특성(라벨링, 편향, 대표성)과 연결해야 기술사답습니다.

4_2. 운영체제의 프로세스 동기화 기법 : 뮤텍스(Mutex), 세마포어(Semaphore), 모니터(Monitor)​

Ⅰ. 개요​

멀티프로세스 및 멀티스레드 환경에서는 여러 실행 흐름이 공유 자원(Shared Resource) 에 동시에 접근할 수 있다. 이 경우 Race Condition, 데이터 불일치, 교착상태(Deadlock) 등이 발생할 수 있으므로 프로세스 동기화(Process Synchronization) 가 필요하다.

프로세스 동기화는 임계영역(Critical Section) 에 대한 상호배제(Mutual Exclusion)를 보장하여 데이터의 일관성을 유지하는 기법이며, 대표적인 방법으로 뮤텍스(Mutex), 세마포어(Semaphore), 모니터(Monitor) 가 있다.

            Process A        Process B
                 │                │
                 └──── 공유자원 ────┘
                         │
                  동기화(Synchronization)
                         │
      ┌──────────┬──────────┬──────────┐
      │          │          │
    Mutex    Semaphore    Monitor

Ⅱ. 뮤텍스(Mutex)​

1. 개념​

뮤텍스(Mutual Exclusion)는 하나의 공유 자원에 대해 하나의 프로세스(또는 스레드)만 접근하도록 허용하는 Lock 기반 동기화 기법이다.

2. 동작 원리​

Thread A
   │
Lock 획득
   │
Critical Section
   │
Unlock
   │
Thread B 진입

3. 특징​

  • Binary Lock(0 또는 1)
  • Lock을 획득한 스레드만 Unlock 가능
  • 상호배제 보장
  • 구현이 단순하고 오버헤드가 적음
  • 임계영역 보호에 적합
활용​
  • 파일 접근
  • 메모리 공유
  • 자료구조 보호(STL, Java Collection 등)

Ⅲ. 세마포어(Semaphore)​

1. 개념​

세마포어는 공유 자원에 접근 가능한 프로세스의 개수를 카운터로 관리하는 동기화 기법이다.

P(Operation, Wait)와 V(Operation, Signal)를 이용하여 자원 접근을 제어한다.

2. 동작 원리​

Semaphore = N

Wait(P)
   │
Counter--
   │
Critical Section
   │
Signal(V)
   │
Counter++

3. 종류​

구분특징
Binary Semaphore0 또는 1 (Mutex와 유사)
Counting SemaphoreN개의 자원 동시 관리

4. 특징​

  • 다수 자원 관리 가능
  • 프로세스 간 동기화 가능
  • 생산자-소비자 문제 해결
  • Lock 소유권 개념 없음
활용​
  • Connection Pool
  • Producer-Consumer
  • Reader-Writer
  • 자원 개수 제한

Ⅳ. 모니터(Monitor)​

1. 개념​

모니터는 공유 자원과 동기화 기능을 하나의 추상 자료형(Abstract Data Type)으로 캡슐화한 고수준 동기화 기법이다.

컴파일러 또는 운영체제가 상호배제를 자동으로 보장하며, 조건변수(Condition Variable)를 이용하여 스레드 간 협력을 지원한다.

2. 구조​

        Monitor
 ┌─────────────────┐
 │ Shared Data     │
 │ Monitor Method  │
 │ Condition Queue │
 └─────────────────┘
         │
   자동 상호배제

3. 특징​

  • 자동 Lock 관리
  • Condition Variable 지원
  • 캡슐화로 안전성 향상
  • 개발자 실수 감소
  • 객체지향 언어(Java synchronized 등)에 적합
활용​
  • Java synchronized
  • C# Monitor
  • 병행 객체(Concurrent Object)

1. 기술적 고려사항​

Ⅶ. 결론​

뮤텍스, 세마포어, 모니터는 모두 공유 자원의 일관성과 상호배제를 보장하기 위한 프로세스 동기화 기법이다. 뮤텍스는 단일 자원의 상호배제, 세마포어는 복수 자원의 접근 제어, 모니터는 객체지향 환경에서 동기화를 캡슐화한 고수준 기법이라는 차이가 있다.

최근에는 멀티코어 및 클라우드 환경에서 병행성이 증가함에 따라 Lock-Free 자료구조, Read-Write Lock, CAS(Compare-And-Swap), STM(Software Transactional Memory) 등의 기술과 함께 활용되며, 시스템 특성에 맞는 동기화 기법 선택이 성능과 안정성을 좌우한다.

기술사 고득점 포인트​

이 문제는 단순히 세 기법을 나열하는 것보다 발전 과정을 보여주면 좋습니다.

임계영역 문제 → Mutex(단일 Lock) → Semaphore(자원 개수 관리) → Monitor(객체지향 캡슐화)

이 흐름을 그림으로 표현하면 운영체제와 소프트웨어공학을 연결한 기술사다운 답안이 됩니다.

아래 답안은 정보관리기술사 4교시(25점) 실전 답안 수준으로 작성하였습니다. 이 문제는 단순히 DR센터를 설명하는 것이 아니라 전쟁·지진·홍수 등 광역 재난 관점에서 IDC 입지선정과 BCP/DR 전략을 통합적으로 설명하는 것이 핵심입니다.

4_3. 전쟁 등 재난·재해를 대비한 데이터센터(IDC)의 지리적 위치선정 및 대응전략​

Ⅰ. 개요​

디지털 정부와 기업의 핵심 서비스는 데이터센터(IDC)에 의존하고 있으며, 전쟁·지진·홍수·산불·정전·사이버공격 등 대규모 재난은 국가 정보서비스의 중단을 초래할 수 있다. 따라서 데이터센터는 재해위험을 최소화하는 입지 선정과 업무연속성(BCP) 및 재해복구(DR) 체계를 함께 구축해야 한다.

특히 최근에는 기후변화와 국가안보 위협이 증가함에 따라 단일 IDC 운영에서 벗어나 지역 분산형(Geo-Redundant) 데이터센터 구축이 중요해지고 있다.

Ⅵ. 결론​

전쟁과 같은 국가적 위기나 자연재해에 대비한 데이터센터는 입지 선정과 재해복구 전략을 통합적으로 고려해야 한다. 입지 선정 단계에서는 재난 위험 분산, 전력·통신 이중화, 지역적 독립성을 확보하고, 운영 단계에서는 BCP, DR센터, 데이터 복제, 자동 장애조치를 통해 서비스 연속성을 보장해야 한다.

향후에는 Geo-Redundant IDC, Hybrid/Multi Cloud, Zero Trust 보안, AI 기반 장애예측을 결합한 지능형 재난 대응체계가 국가와 기업의 핵심 정보서비스를 보호하는 기반이 될 것이다.

4_4. 가상메모리(Virtual Memory)​

Ⅰ. 개요​

가상메모리는 보조기억장치의 일부를 주기억장치처럼 사용하여 실제 물리 메모리보다 큰 주소 공간을 제공하는 메모리 관리 기법이다. 프로그램은 연속된 논리주소(Logical Address)를 사용하지만 운영체제가 이를 물리주소(Physical Address)로 변환하여 실행함으로써 메모리 활용률과 다중 프로그래밍 효율을 향상시킨다.

그러나 메모리 관리 방식에 따라 내부 단편화(Internal Fragmentation) 와 외부 단편화(External Fragmentation) 가 발생할 수 있으므로 적절한 관리기법과 단편화 최소화 전략이 필요하다.

프로세스
    │
논리주소(Logical Address)
    │
 MMU + 페이지/세그먼트 변환
    │
물리메모리(RAM)
    │
보조기억장치(Swap)

세그멘테이션(Segmentation)프로그램의 논리 단위(코드, 데이터, 스택)로 분할내부 단편화 적음, 외부 단편화 발생

나. 가상메모리 단편화 유형​

1. 내부 단편화(Internal Fragmentation)​

메모리를 고정 크기로 할당할 때 실제 사용하지 않는 공간이 블록 내부에 남는 현상이다.

  • 주요 원인 : 페이징, 고정분할 방식
  • 특징 : 블록 내부의 낭비 공간 발생

예) 페이지 크기 4KB, 실제 사용 3KB → 1KB 내부 단편화

2. 외부 단편화(External Fragmentation)​

메모리 해제와 재할당이 반복되면서 연속된 큰 메모리 공간이 부족해지는 현상이다.

  • 주요 원인 : 가변분할, 세그멘테이션
  • 특징 : 전체 여유공간은 충분하지만 연속 공간 부족

단편화 구조​

→ 작은 빈 공간이 분산
→ 외부 단편화

[■■■□]
     ↑

→ 내부 단편화

가상메모리는 논리주소와 물리주소를 분리하여 메모리 활용률을 높이는 핵심 운영체제 기술이다. 대표적인 관리기법인 페이징은 외부 단편화를 제거하지만 내부 단편화가 발생하며, 세그멘테이션은 논리적 관리가 용이하지만 외부 단편화가 발생한다.

따라서 시스템 특성에 따라 Paged Segmentation, 적절한 페이지 크기, Compaction, Buddy System, Working Set 관리 등을 적용하여 단편화를 최소화하고 메모리 효율과 시스템 성능을 향상시키는 것이 중요하다.

4_5. VPP(Virtual Power Plant)의 AI 기반 전력수요 예측 기술 : 시계열 딥러닝, 강화학습, 그래프신경망​

Ⅰ. 개요​

VPP(Virtual Power Plant)는 태양광, 풍력, ESS(Energy Storage System), 전기차(EV), 수요자원(DR) 등 분산에너지자원(DER) 을 ICT와 AI로 통합하여 하나의 발전소처럼 운영하는 기술이다.

재생에너지는 기상과 소비패턴에 따라 출력 변동성이 크므로 정확한 수요예측과 실시간 운영 최적화가 필수이며, 이를 위해 시계열 딥러닝(Time-series Deep Learning), 강화학습(Reinforcement Learning), 그래프신경망(Graph Neural Network, GNN) 이 핵심 AI 기술로 활용된다.

가. 시계열 딥러닝(Time-series Deep Learning)​

1. 개념​

시계열 딥러닝은 시간의 순서(Time Dependency)를 갖는 데이터를 학습하여 미래 값을 예측하는 딥러닝 기법이다. 전력 사용량, 발전량, 기온, 일사량 등의 시계열 데이터를 분석하여 수요와 공급을 예측한다.

2. 주요 모델​

다. 그래프신경망(Graph Neural Network)​

1. 개념​

전력망은 발전기, 변전소, ESS, 소비자가 연결된 그래프 구조이므로 GNN이 효과적으로 적용된다.

Ⅵ. 결론​

VPP는 분산에너지자원의 효율적인 운영을 위해 예측(Predict)–최적화(Optimize)–관계분석(Analyze) 이 유기적으로 결합되어야 한다. 시계열 딥러닝은 전력수요와 발전량을 예측하고, 강화학습은 ESS 및 수요반응을 최적으로 제어하며, 그래프신경망은 전력망의 연결 구조와 전력 흐름을 분석한다.

향후에는 디지털 트윈, MLOps, 연합학습(Federated Learning), 설명가능한 AI(XAI) 와 결합하여 안정성과 효율성을 동시에 확보하는 지능형 VPP로 발전할 것으로 기대된다.

기술사 고득점 포인트​

이 문제는 세 가지 AI 기술을 각각 설명하는 데 그치지 말고 VPP 운영 단계와 연결하면 높은 평가를 받을 수 있습니다.

VPP 업무적용 AI
전력수요·발전량 예측시계열 딥러닝(LSTM, Transformer)
ESS·DR 운영 최적화강화학습(DQN, PPO 등)
전력망 구조·전력 흐름 분석그래프신경망(GCN, GAT 등)

즉, **"예측 → 제어 → 계통분석"**의 흐름을 제시하면 AI와 전력시스템을 통합적으로 이해하고 있음을 보여주는 기술사 수준의 답안이 됩니다.

아래 답안은 정보관리기술사 4교시 실전 답안 수준으로 구성하였습니다. 핵심은 Supernetting과 Subnetting의 방향성 차이를 설명하고, VLSM은 반드시 필요 호스트 수가 큰 순서대로 할당하는 것입니다.

4_6. 네트워크 슈퍼네팅(Supernetting), 서브네팅(Subnetting) 및 VLSM 설계​

Ⅰ. 개요​

IP 네트워크는 주소 공간의 효율적 사용과 라우팅 테이블 축약을 위해 네트워크 대역을 분할하거나 통합한다.

  • 서브네팅(Subnetting) 은 하나의 큰 네트워크를 여러 개의 작은 네트워크로 분할하는 기법이다.
  • 슈퍼네팅(Supernetting) 은 여러 개의 연속된 네트워크를 하나의 큰 네트워크로 통합하는 기법이다.
  • VLSM(Variable Length Subnet Mask) 은 각 서브넷의 호스트 수에 따라 서로 다른 서브넷 마스크를 적용하여 주소 낭비를 최소화한다.
주소 분할                         주소 통합
/22 ──Subnetting──► /23, /24, /25     /24 + /24 ──Supernetting──► /23

가. 슈퍼네팅과 서브네팅의 개념​

1. 서브네팅(Subnetting)​

서브네팅은 호스트 비트 일부를 네트워크 비트로 전환하여 하나의 네트워크를 여러 개의 논리적 하위 네트워크로 분할하는 기법이다.

목적​
  • IP 주소의 효율적 할당
  • 부서·업무별 네트워크 분리
  • 브로드캐스트 도메인 축소
  • 보안 정책과 장애 범위 분리
  • 네트워크 관리성 향상
예시​
192.168.0.0/24
       │
       ├─ 192.168.0.0/25
       └─ 192.168.0.128/25

프리픽스 길이가 /24 → /25로 증가하므로 네트워크 수는 증가하고, 각 네트워크의 호스트 수는 감소한다.

2. 슈퍼네팅(Supernetting)​

슈퍼네팅은 연속된 여러 네트워크의 공통 상위 비트를 기준으로 하나의 더 큰 네트워크 주소로 집약하는 기법이다. 라우트 집약(Route Aggregation) 또는 CIDR 집약이라고도 한다.

목적​
  • 라우팅 테이블 항목 축소
  • 라우팅 업데이트 트래픽 감소
  • 경로 탐색 효율 향상
  • 네트워크 확장성 확보
예시​
192.168.0.0/24 ┐
192.168.1.0/24 ├──► 192.168.0.0/22
192.168.2.0/24 │
192.168.3.0/24 ┘

프리픽스 길이가 /24 → /22로 감소하므로 여러 네트워크가 하나의 상위 경로로 통합된다.

3. 슈퍼네팅과 서브네팅 비교​

구분서브네팅슈퍼네팅
목적네트워크 분할네트워크 통합
프리픽스증가감소
네트워크 수증가감소
호스트 수서브넷별 감소통합 대역 증가
주요 활용부서별 망 분리라우팅 경로 집약
핵심 효과주소 효율·보안·관리성라우팅 효율·확장성

나. 192.168.0.0/22 대역의 VLSM 분할​

1. 요구사항 분석​

대상 네트워크는 192.168.0.0/22이며 전체 주소 범위는 다음과 같다.

  • 전체 주소: 192.168.0.0 ~ 192.168.3.255
  • 전체 주소 수: 2^(32-22) = 1,024개
  • 사용 가능한 호스트 수: 1,022개

각 부서의 요구 호스트 수를 충족하도록 네트워크 주소와 브로드캐스트 주소를 포함한 최소 블록을 산정한다.

부서필요 호스트필요 주소 수최소 블록PrefixSubnet Mask사용 가능 호스트
개발팀500502 이상512/23255.255.254.0510

인사팀125127 이상128/25255.255.255.128126

필요한 총 주소 수는 다음과 같다.

512 + 256 + 128 + 128 = 1,024개

따라서 /22 대역 전체를 낭비 없이 정확하게 사용할 수 있다.

2. VLSM 할당 원칙​

VLSM은 주소 중첩과 단편화를 방지하기 위해 호스트 수가 가장 많은 부서부터 내림차순으로 할당한다.

192.168.0.0/22
        │
        ├─ 개발팀  /23 : 512개
        ├─ 영업팀  /24 : 256개
        ├─ 인사팀  /25 : 128개
        └─ 보안팀  /25 : 128개

본 문제의 주소 공간은 요구량과 정확히 일치하므로 추가 호스트 증가, 게이트웨이·서버·프린터·네트워크 장비의 IP까지 고려하면 여유 주소가 부족할 수 있다. 실무에서는 향후 증가율을 반영하여 더 큰 주소 대역을 확보하거나 사용자 단말 수를 재산정해야 한다.

Ⅳ. 결론​

서브네팅은 하나의 네트워크를 여러 하위 네트워크로 분할하여 주소 효율성, 보안성 및 관리성을 향상시키고, 슈퍼네팅은 연속된 네트워크를 하나의 경로로 집약하여 라우팅 테이블과 라우팅 트래픽을 감소시킨다.

주어진 192.168.0.0/22 대역은 VLSM을 적용하여 개발팀 /23, 영업팀 /24, 인사팀과 보안팀 각각 /25로 분할할 수 있다. 이 설계는 전체 1,024개 주소를 정확히 사용하지만 예비 주소가 없으므로, 실제 구축 시에는 향후 확장성과 네트워크 장비용 주소까지 함께 고려해야 한다.

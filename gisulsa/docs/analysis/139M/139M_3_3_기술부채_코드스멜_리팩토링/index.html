문제 3) 명확하지 않은 요구사항으로 인한 소프트웨어 품질저하

답)

I. 개요​

명확하지 않은 요구사항은 잘못된 설계 결정과 임시방편적 구현을 유발하여 기술부채(Technical Debt)를 누적시키고, 코드 수준에서는 코드스멜(Code Smell)로 발현되며, 이를 개선하는 활동이 리팩토링(Refactoring)이다. 세 개념은 요구사항 불명확 → 기술부채 누적 → 코드스멜 발현 → 리팩토링 개선의 연쇄적 인과 관계를 가지며, 소프트웨어 품질과 유지보수성을 결정하는 핵심 관리 대상이다.

II. 기술부채(Technical Debt) (가)​

1. 기술부채의 개념​

구분내용
정의단기적 편의를 위해 최선이 아닌 설계 구현을 선택하여 향후 추가 비용을 발생시키는 부채
비유Ward Cunningham이 제시한 금융 부채 비유, 원금과 이자가 발생
이자부채를 방치할수록 유지보수 비용과 결함 가능성이 누적 증가

기술부채의 총비용은 다음과 같이 표현할 수 있다.

Costtotal=Principal+∑t=1nInteresttCost_{total} = Principal + \sum_{t=1}^{n} Interest_tCosttotal​=Principal+∑t=1n​Interestt​

여기서 원금은 정상적 개선 비용, 이자는 부채 방치로 인한 누적 추가 비용이다.

2. 기술부채의 유형​

유형설명
코드 부채중복, 복잡도 높은 코드, 임시방편 구현
설계 아키텍처 부채잘못된 구조, 강한 결합, 부적절한 추상화
문서 부채누락되거나 오래된 명세 및 주석
테스트 부채부족한 테스트 커버리지, 부재한 자동화
인프라 부채노후 환경, 미흡한 CI/CD 자동화

3. Martin Fowler의 기술부채 사분면​

Martin Fowler는 부채 발생 의도(고의/무심)와 신중함(신중/무모)을 두 축으로 사분면을 제시하였다.

사분면분류설명예시
무모한 고의 Reckless Deliberate의도적이나 무책임설계 시간 없이 일단 출시"설계할 시간 없으니 그냥 짜자"
신중한 고의 Prudent Deliberate전략적 선택위험을 알고 의도적으로 부채 수용"지금 출시하고 결과는 감수한다"
무모한 무심 Reckless Inadvertent무지에 의한 부채좋은 설계를 모르고 발생"계층 분리가 무엇인가"
신중한 무심 Prudent Inadvertent사후 학습형완성 후 더 나은 방법 인지"이제야 어떻게 했어야 하는지 알겠다"

4. 기술부채 관리 전략​

전략내용
식별정적 분석, 코드 리뷰로 부채 가시화
측정부채 지수, 복잡도, 커버리지 지표화
우선순위화이자가 큰 부채 우선 상환
상환리팩토링, 재설계로 부채 해소
예방명확한 요구사항, 코딩 표준, 정의 완료 기준

기술부채 측정 지표​

지표의미
기술부채 비율 SQALE개선 비용 대비 전체 개발 비용 비율
순환 복잡도 Cyclomatic Complexity코드 분기 경로 수, 높을수록 위험
코드 중복률중복 코드의 비율
테스트 커버리지테스트로 검증되는 코드 비율
결합도 응집도모듈 간 의존성과 내부 응집 정도

III. 코드스멜(Code Smell) (나)​

1. 코드스멜의 개념​

구분내용
정의버그는 아니지만 더 깊은 설계 문제를 시사하는 코드상의 징후
제안자Kent Beck이 명명, Martin Fowler가 체계화
의미리팩토링이 필요함을 알려주는 신호이자 기술부채의 표면적 증상

2. 대표적인 코드스멜 유형​

코드스멜설명대응 리팩토링
중복 코드 Duplicated Code동일 로직 반복메소드 추출, 상위 클래스로 추출
긴 메소드 Long Method하나의 메소드가 과도하게 김메소드 추출 Extract Method
거대 클래스 Large Class너무 많은 책임을 가진 클래스클래스 추출 Extract Class
긴 매개변수 목록 Long Parameter List인자가 지나치게 많음매개변수 객체화
기능 욕심 Feature Envy다른 클래스 데이터에 과도 의존메소드 이동 Move Method
산탄총 수술 Shotgun Surgery한 변경이 여러 곳 수정 유발기능 한 곳으로 모으기
발산적 변경 Divergent Change한 클래스가 여러 이유로 변경클래스 분리
데이터 뭉치 Data Clumps항상 함께 다니는 데이터객체로 묶기
주석 과다 Comments나쁜 코드를 주석으로 변명코드 자체를 명확히
죽은 코드 Dead Code사용되지 않는 코드제거

3. 코드스멜 탐지​

탐지 방법설명
정적 분석 도구SonarQube, PMD, ESLint 등으로 자동 탐지
코드 메트릭순환 복잡도, 결합도, 응집도 측정
코드 리뷰동료 검토를 통한 정성적 식별

IV. 리팩토링(Refactoring) (다)​

1. 리팩토링의 개념​

구분내용
정의외부 동작을 변경하지 않으면서 내부 구조를 개선하는 활동
목적가독성, 유지보수성, 확장성 향상 및 기술부채 상환
전제회귀 테스트로 동작 불변 보장

리팩토링은 기능 추가와 명확히 구분된다. Martin Fowler의 "Two Hats" 원칙에 따라 기능 추가와 리팩토링을 동시에 수행하지 않는다.

2. 리팩토링 기법​

기법설명대응 코드스멜
메소드 추출 Extract Method코드 일부를 별도 메소드로 분리긴 메소드, 중복 코드
클래스 추출 Extract Class책임을 별도 클래스로 분리거대 클래스
메소드 이동 Move Method메소드를 적절한 클래스로 이동기능 욕심
변수 인라인 Inline불필요한 임시변수 제거불필요 요소
이름 변경 Rename의도가 드러나는 이름 부여주석 과다
조건문 분해 Decompose Conditional복잡한 조건문 단순화긴 메소드
매개변수 객체화인자들을 객체로 묶음긴 매개변수 목록
상속을 위임으로부적절한 상속을 위임으로 교체객체지향 남용
# 리팩토링 전: 긴 메소드 + 중복
def print_invoice(orders):
    total = 0
    for o in orders:
        total += o.price * o.qty
    print("Total:", total)
    tax = total * 0.1
    print("Tax:", tax)

# 리팩토링 후: 메소드 추출
def calc_total(orders):
    return sum(o.price * o.qty for o in orders)

def print_invoice(orders):
    total = calc_total(orders)
    print("Total:", total)
    print("Tax:", total * 0.1)

3. 리팩토링 절차​

단계활동
1. 식별코드스멜 및 개선 대상 파악
2. 테스트 확보동작 보장을 위한 테스트 작성
3. 소규모 변경작은 단위로 점진적 개선
4. 검증매 변경마다 테스트 실행
5. 반복스멜 해소까지 반복 후 커밋

4. 세 개념의 연관관계​

개념관점역할
기술부채관리 경제 관점누적된 품질 비용의 추상적 개념
코드스멜코드 진단 관점부채의 구체적 증상이자 탐지 신호
리팩토링개선 행위 관점스멜 제거 및 부채 상환 활동

결론​

불명확한 요구사항은 기술부채를 누적시키고, 이는 코드스멜로 표면화되며, 리팩토링을 통해 상환된다. 세 개념은 원인-증상-치료의 인과 사슬로 연결되며, 소프트웨어 품질 관리의 핵심 축을 이룬다.

핵심 요약내용
기술부채단기 편의의 대가, Fowler 사분면으로 분류
코드스멜부채의 표면적 증상, 리팩토링 신호
리팩토링동작 불변 하 구조 개선, 점진적 절차

정보관리기술사 관점에서, 가장 근본적인 해법은 사후 리팩토링이 아니라 명확한 요구사항 정의와 정의 완료 기준(Definition of Done) 확립을 통한 부채 예방이다. 신중한 고의 부채는 ADR로 기록하여 의사결정을 추적하고, 정적 분석과 코드 리뷰를 CI 파이프라인에 통합하여 코드스멜을 조기에 가시화하며, 보이스카우트 규칙에 따라 지속적 소규모 리팩토링을 일상화하는 것이 소프트웨어 품질의 장기적 건전성을 보장한다.

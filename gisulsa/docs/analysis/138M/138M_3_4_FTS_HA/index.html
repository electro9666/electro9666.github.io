문제 4) 가용성 보장 - FTS와 HA 구현 방법

답)

개요​

IT 시스템의 가용성(Availability)은 서비스가 중단 없이 정상 운영되는 능력으로, 기업의 비즈니스 연속성과 직결된다. 가용성 보장을 위한 핵심 접근 방식으로 결함허용시스템(FTS: Fault Tolerant System)과 고가용성(HA: High Availability)이 있으며, 두 개념은 목표와 구현 방식에서 차이가 있다.

가. FTS(Fault Tolerant System) 구현 방법​

1. FTS 개념과 목표​

**결함허용시스템(Fault Tolerant System)**은 하드웨어나 소프트웨어의 일부 구성 요소에 결함(Fault)이 발생하더라도 시스템 전체 기능이 중단 없이 계속 운영되도록 설계된 시스템이다.

구분내용
목표단일 장애점(SPOF) 제거, 무중단 운영
가용성 목표99.9999% (Six Nine, 연간 31.5초 이하 다운타임)
핵심 개념결함 감지(Detection) → 격리(Isolation) → 복구(Recovery)
주요 대상미션 크리티컬 시스템 (금융거래, 항공, 의료)

2. FTS 구현 원칙​

(1) 중복성 (Redundancy)​

중복성 수준설명비용
N+1 중복N개 운영 + 1개 예비중간
2N 중복운영 시스템을 완전 복제높음
2N+1 중복완전 복제 + 추가 예비매우 높음

(2) 다양성 (Diversity)​

  • 소프트웨어 다양성: 동일 기능을 서로 다른 팀이 독립적으로 구현
  • 하드웨어 다양성: 다른 벤더의 장비 혼용
  • 공통 원인 고장(Common Cause Failure) 방지

(3) 격리성 (Isolation)​

  • 결함 전파 방지를 위한 구성요소 간 격리
  • 장애 도메인(Fault Domain) 분리

3. FTS 구현 기술​

(1) 하드웨어 중복화​

구성요소중복화 방법표준/기술
CPU다중 CPU 소켓, ECC 메모리Intel/AMD 서버 CPU
메모리ECC, 미러링, 스페어 뱅크JEDEC DDR5
스토리지RAID 1/5/6/10, 핫스페어RAID, NVMe, SAN
네트워크NIC 티밍, LACP 본딩IEEE 802.3ad
전원이중화 PSU, UPS, 발전기2N 전원 설계
냉각N+1 냉각 유닛ASHRAE 기준

(2) 소프트웨어 결함허용 기법​

체크포인팅 (Checkpointing)​
시스템 상태 주기적 저장 → 결함 발생 시 마지막 체크포인트로 롤백

Process A → [Checkpoint 1] → [Checkpoint 2] → Fault!
                                    ↓
               복구: Checkpoint 2 상태로 재시작
트랜잭션 롤백 (Transaction Rollback)​
BEGIN TRANSACTION;
    UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
    UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
    -- 오류 발생 시 자동 롤백으로 일관성 유지
COMMIT;
워치독 타이머 (Watchdog Timer)​
  • 소프트웨어 행(Hang) 감지 및 자동 재시작
  • 임베디드/실시간 시스템에서 필수 구현

(3) TMR (Triple Modular Redundancy)​

구분내용
원리3개 독립 모듈 운영, 다수결로 출력 결정
특징1개 모듈 고장 시에도 정상 출력 보장
활용항공기 비행제어, 우주선, 원자력 발전소

(4) 미션 크리티컬 시스템 적용 사례​

시스템FTS 구현 방식목표 가용성
항공 비행제어TMR + 소프트웨어 다양성99.9999999%
금융 거래 시스템Active-Active 클러스터 + 이중화99.999%
원자력 제어쿼드 중복 + 하드웨어 다양성99.9999%+
의료 생명유지하드웨어 이중화 + UPS99.9999%

4. FTS 구현 시 고려사항​

항목내용
결함 가정Byzantine Fault vs Fail-Stop Fault
검증 방법FMEA(고장 모드 영향 분석), FTA(결함 트리 분석)
비용이중화로 인한 2~3배 하드웨어 비용
복잡성동기화, 일관성 유지를 위한 설계 복잡도

나. HA(High Availability) 구현 방법​

1. HA 개념과 목표​

**고가용성(High Availability)**은 시스템 장애 발생 시 최소한의 다운타임으로 서비스를 복구하는 능력이다. FTS와 달리 일시적 중단을 허용하지만 자동화된 페일오버(Failover)로 신속한 복구를 보장한다.

가용성 등급연간 다운타임해당 표준
99% (Two Nine)87.6시간일반 시스템
99.9% (Three Nine)8.76시간비즈니스 시스템
99.99% (Four Nine)52.6분엔터프라이즈 HA
99.999% (Five Nine)5.26분통신/금융 HA
99.9999% (Six Nine)31.5초FTS 수준

2. HA 구현 기술​

(1) 클러스터링 (Clustering)​

Active-Passive 클러스터​
구분내용
구성운영 노드 1개 + 대기 노드 N개
장점구성 단순, 비용 절감
단점Passive 노드 자원 낭비
페일오버 시간수십 초 ~ 수분
활용DB 서버, ERP 시스템
Active-Active 클러스터​
구분내용
구성모든 노드가 동시 서비스
장점자원 효율 극대화, 선형 확장
단점데이터 일관성 보장 복잡
페일오버 시간수 초 (로드밸런서 헬스체크 주기)
활용웹 서버, API 서버, 캐시 서버

(2) 페일오버 (Failover) 메커니즘​

페일오버 유형설명RTO
자동 페일오버감지 즉시 자동 전환수 초 ~ 수 분
수동 페일오버관리자 확인 후 전환수 분 ~ 수 시간
계획된 페일오버유지보수 위한 사전 전환초 단위
그레이스풀 페일오버세션 유지하며 전환투명 전환

(3) 이중화 (Replication) 기술​

데이터베이스 이중화​
복제 방식특성적합 사례
동기 복제RPO=0, 성능 영향 있음금융 거래, 의료
비동기 복제성능 우수, 소량 데이터 손실 가능일반 웹서비스
반동기 복제최소 1개 레플리카 확인 후 커밋균형 선택
논리 복제선택적 테이블/컬럼 복제이기종 DB 간
MySQL InnoDB Cluster (Group Replication)​
-- Primary 장애 시 자동 선출
-- 그룹 복제 상태 확인
SELECT MEMBER_HOST, MEMBER_ROLE, MEMBER_STATE
FROM performance_schema.replication_group_members;

(4) 로드 밸런싱 (Load Balancing)​

알고리즘방식특성
Round Robin순환 할당단순, 균등 분배
Least Connections최소 연결 노드부하 기반 동적 분배
IP Hash클라이언트 IP 해시세션 고정
Weighted가중치 기반이기종 서버 구성
Health Check정상 노드만 분배자동 장애 노드 제외

(5) 무중단 배포 (Zero-Downtime Deployment)​

방식설명리스크
블루-그린 배포두 환경 교차 전환낮음 (즉시 롤백 가능)
카나리 배포일부 트래픽 → 점진적 전환최소 (소수 사용자 영향)
롤링 업데이트노드 순차 업데이트중간 (구/신 버전 혼재)
기능 플래그코드 배포 후 기능 활성화매우 낮음

(6) HA 인프라 구성 아키텍처​

다. FTS와 HA 비교 설명​

1. 개념적 차이​

비교 항목FTS (결함허용시스템)HA (고가용성)
핵심 목표결함 발생 시에도 무중단 운영장애 발생 시 신속 복구
다운타임0초 (Zero Downtime)최소화 (수 초 ~ 수 분)
결함 처리결함 마스킹 (Fault Masking)결함 후 복구 (Post-fault Recovery)
중복 수준완전 하드웨어 중복 (2N 이상)소프트웨어 클러스터 + 부분 중복

2. 기술적 비교​

비교 항목FTSHA
가용성 목표99.9999%+ (Six Nine)99.99%~99.999% (Four/Five Nine)
연간 다운타임31.5초 이하5.26분 ~ 52.6분
구현 방식하드웨어 완전 중복, TMR클러스터링, 페일오버, 복제
장애 감지하드웨어 레벨 즉시 감지헬스체크 기반 (수 초 지연)
복구 시간무감지 (Transparent)RPO/RTO 기반 (수 초~수 분)
데이터 손실없음 (Zero Data Loss)복제 지연에 따라 소량 가능
비용매우 높음 (일반 대비 3~5배)중간 (일반 대비 1.5~2배)
복잡성매우 높음중간

3. 장애 대응 시나리오 비교​

4. 적용 영역 비교​

적용 영역FTS 적합HA 적합
항공 비행제어 시스템OX
원자력 발전소 제어OX
심장 박동기 / 의료기기OX
주식 거래 시스템OO
금융 코어뱅킹선택적O
전자상거래 플랫폼XO
기업 ERP 시스템XO
웹 서비스 / APIXO
데이터 분석 플랫폼XO

5. 비용-효과 분석​

투자 대비 효과일반HAFTS
연간 다운타임87.6시간52.6분31.5초
구축 비용1배1.5~2배3~5배
운영 비용1배1.5배2~3배
비즈니스 손실 위험높음낮음극히 낮음

6. 클라우드 환경에서의 FTS/HA​

클라우드 서비스FTS/HA 구현 방식
AWS Multi-AZ가용 영역 간 자동 페일오버 (HA)
GCP Regional MIG다중 영역 인스턴스 그룹 (HA)
Azure Availability Zones물리적 분리 데이터센터 (HA/FTS 경계)
Kubernetes Pod 재시작컨테이너 레벨 자동 복구 (HA)
AWS RDS Multi-AZDB 동기 복제 + 자동 페일오버 (HA)

결론​

구분선택 기준
FTS 선택생명/안전과 직결, 다운타임 허용 불가, 비용 제약 없음
HA 선택비즈니스 연속성 중요, 합리적 비용으로 고가용성 달성
혼합 적용핵심 컴포넌트 FTS + 주변 시스템 HA

디지털 전환 시대에는 클라우드 네이티브 HA 아키텍처(멀티 리전, 카오스 엔지니어링, SRE 방법론)를 통해 비용 효율적 가용성 보장이 가능하며, 서비스 중요도에 따른 차등화된 가용성 목표(Tiered SLA) 설계가 핵심이다.

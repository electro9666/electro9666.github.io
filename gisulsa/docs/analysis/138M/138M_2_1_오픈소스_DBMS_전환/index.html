문제 1) 오픈소스 DBMS 전환

답)

가. 오픈소스 DBMS 전환 배경​

1) 비용 절감 압력​

비용 항목상용 DBMS오픈소스 DBMS
초기 라이선스CPU 코어당 수천만 원무료
연간 유지보수라이선스의 20~22%커뮤니티 지원 or 유상 지원 선택
클라우드 배포BYOL 또는 추가 과금자유로운 배포
교육/컨설팅벤더 종속다수 전문업체 선택 가능

2) 기술 성숙도 향상​

오픈소스 DBMS는 과거의 기능·성능 격차를 대폭 해소하였다.

영역과거 한계현재 수준
성능대용량 처리 한계TPC-C 벤치마크에서 상용 대비 90% 이상 수준
고가용성클러스터링 미지원Patroni, Galera Cluster, PG Replication 등 완성
보안감사 기능 부족Row-Level Security, SSL, 감사 플러그인 지원
운영 도구GUI 도구 빈약pgAdmin, DBeaver, Percona Monitoring 등 성숙

3) 정책·규제 환경​

  • 공공기관 오픈소스 전환 권고: 행정안전부 전자정부 표준프레임워크 오픈소스 우선 정책
  • 클라우드 네이티브 전환(CN전환) 사업: 공공 정보시스템의 클라우드·오픈소스 전환 의무화 추진
  • SW산업 진흥법: 국산·오픈소스 소프트웨어 우선 구매 원칙

4) 생태계 성숙​

나. 오픈소스 DBMS 전환 시 검토해야 할 제약사항​

1) 기술적 제약사항​

제약 영역상세 내용위험도
SQL 방언 차이Oracle PL/SQL → PostgreSQL PL/pgSQL 문법 차이 (ROWNUM, CONNECT BY, DECODE 등)매우 높음
데이터 타입 불일치NUMBER, VARCHAR2, DATE 등 상용 DBMS 고유 타입 변환 필요높음
저장 프로시저패키지, 트리거, 함수의 문법 및 동작 차이높음
히든 파라미터상용 DBMS 비공개 튜닝 파라미터 의존 로직중간
문자셋한글 처리 방식(EUC-KR vs UTF-8) 및 콜레이션 차이중간
파티셔닝파티션 유형·문법 차이 (INTERVAL, COMPOSITE 등)중간
실행 계획옵티마이저 특성 차이로 인한 성능 재튜닝 필요높음

2) 애플리케이션 연동 제약​

3) 운영 역량 제약​

제약 항목내용
DBA 역량상용 DBMS 전문 DBA의 오픈소스 재교육 필요 (평균 6개월~1년)
기술 지원벤더 24×7 지원 → 커뮤니티 or 유상 지원사 계약으로 대체
장애 대응SLA 수준 유지를 위한 자체 장애 대응 체계 구축
모니터링기존 모니터링 도구 교체 또는 연동 재구성

4) 라이선스 검토​

오픈소스라이선스상업적 사용주의사항
PostgreSQLPostgreSQL License자유제한 거의 없음
MySQL CommunityGPL v2제한적파생 서비스 배포 시 GPL 적용
MariaDBGPL v2제한적MySQL과 동일
MySQL Enterprise상용자유유료 라이선스

다. 오픈소스 DBMS 전환 시 단계별 마이그레이션 절차​

전체 절차 개요​

1단계: 현황 분석​

분석 항목내용산출물
DB 인벤토리테이블 수, 뷰, 프로시저, 트리거, 인덱스 목록오브젝트 목록
데이터 볼륨총 데이터 크기, 테이블별 레코드 수용량 분석서
SQL 쿼리 분석애플리케이션에서 사용되는 SQL 패턴 수집SQL 목록
의존성 파악DB 링크, 외부 연동, 배치 등 의존 시스템의존성 맵
성능 기준선현재 트랜잭션 처리량, 응답시간 측정성능 베이스라인

2단계: 전환 설계​

데이터 타입 매핑 예시 (Oracle → PostgreSQL):

OraclePostgreSQL주의사항
NUMBER(p,s)NUMERIC(p,s)정밀도 동일
VARCHAR2(n)VARCHAR(n)바이트/문자 단위 차이
DATETIMESTAMPOracle DATE는 시분초 포함
CLOBTEXT크기 제한 없음
BLOBBYTEA대용량 저장 방식 차이
ROWNUMROW_NUMBER() / LIMIT페이징 쿼리 재작성
SYSDATENOW() / CURRENT_TIMESTAMP함수명 변경
NVL(a,b)COALESCE(a,b)다중 인수 지원
DECODECASE WHEN표준 SQL로 변환

3단계: 환경 구축​

  • 오픈소스 DBMS 설치 및 초기 설정 (파라미터 튜닝, 문자셋 설정)
  • HA 인프라 구성 (Primary/Standby, 로드밸런서)
  • 백업·모니터링 도구 설치

4단계: 데이터 및 오브젝트 변환​

5단계: 검증 및 테스트​

테스트 유형검증 항목합격 기준
데이터 정합성레코드 건수, 체크섬, 샘플 비교100% 일치
기능 테스트전체 애플리케이션 기능 시나리오결함 0건 (Critical)
성능 테스트트랜잭션 처리량, 응답시간기준선 대비 90% 이상
회귀 테스트기존 SQL 결과값 동등성결과 100% 일치
부하 테스트최대 동시 접속자 처리SLA 기준 충족

6단계: 전환 실행 (Cut-over)​

7단계: 안정화​

  • 전환 후 30~90일 집중 모니터링
  • 성능 이상 시 쿼리 튜닝, 인덱스 재설계
  • DBA 역량 강화 교육 지속

라. 신뢰성 확보를 위한 고가용성(HA) 아키텍처 구성 방안​

1) HA 아키텍처 전체 구성​

2) HA 구성 요소별 역할​

구성요소역할오픈소스 솔루션
리더 선출Primary 장애 시 자동 Standby 승격Patroni + etcd/Consul/ZooKeeper
스트리밍 복제Primary → Standby 실시간 WAL 전송PostgreSQL 내장 기능
커넥션풀링연결 수 제한, 읽기/쓰기 분리pgBouncer, PgPool-II
로드밸런서DB 엔드포인트 추상화, Failover 감지HAProxy
백업/복구Point-in-Time Recovery, WAL 아카이빙pgBackRest, Barman
모니터링성능 메트릭 수집·시각화Prometheus + pmm-server

3) Failover 시나리오​

4) RPO/RTO 목표 달성 방안​

지표정의달성 방안
RTO (복구 목표 시간)장애 후 서비스 재개까지 시간Patroni 자동 Failover: 30초 이내
RPO (복구 목표 시점)허용 가능한 데이터 손실 범위동기 복제(synchronous_commit=on): 0 데이터 손실

5) 구성 옵션 비교​

구성특징적용 대상
Single Primary + Async Standby비용 최소, 약간의 데이터 손실 가능개발/테스트, 비중요 업무
Primary + Sync Standby + Async DR로컬 무손실, DR 확보일반 운영 시스템
Galera Cluster (MariaDB)다중 Primary, 동기 멀티마스터고쓰기 분산, 금융계
Citus (PostgreSQL 분산)샤딩 기반 수평 확장빅데이터, OLAP

6) 모니터링 체계​

핵심 모니터링 지표:

  • 복제 지연 시간 (replication_lag)
  • 커넥션 수 (active / idle)
  • 트랜잭션 처리량 (TPS)
  • WAL 생성량 및 아카이빙 상태
  • 자동 VACUUM 상태 (PostgreSQL 특이사항)
  • Bloat(테이블/인덱스 팽창) 비율

오픈소스 DBMS 전환은 단순한 비용 절감을 넘어 기술 자립과 클라우드 네이티브 전환의 핵심 과제로, 충분한 사전 분석과 단계적 마이그레이션, 그리고 검증된 HA 아키텍처 구성을 통해 안정적인 전환을 실현해야 한다.
